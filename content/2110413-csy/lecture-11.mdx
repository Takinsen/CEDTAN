## ส่วนที่ 1 — เครือข่ายคือโปรโตคอลหลายชั้นที่เชื่อกันเอง

### เปิดเว็บหนึ่งหน้า ต้องเชื่อคนอื่นกี่ครั้ง

<Why>
ลองนึกถึงการพิมพ์ `nicebank.com` ลงในเบราว์เซอร์หนึ่งครั้ง

ก่อนเว็บจะขึ้น เครื่องเราต้องถามเครื่องอื่นก่อนว่าชื่อนี้อยู่ที่เลขที่อยู่อะไร

เครื่องเราอยู่ใน <Term en="LAN" th="เครือข่ายวงเล็กในบ้านหรือออฟฟิศ" /> ทางออกจาก LAN ไปอินเทอร์เน็ตคือ <Term en="Gateway" th="ทางออกจาก LAN" /> ซึ่งเครื่องต้องถามก่อนว่าอยู่ที่ไหน

จากนั้นข้อมูลถูกส่งออกไปเป็นก้อน เรียกว่า <Term en="Packet" th="ก้อนข้อมูลที่ส่งบนเครือข่าย" /> แล้ว <Term en="Router" th="อุปกรณ์ส่งต่อ packet ข้ามเครือข่าย" /> หลายตัวส่งต่อ packet กันไป จนได้คำตอบที่อ้างว่ามาจากธนาคาร

ทุกขั้นเชื่อคำตอบของเครื่องอื่น ถ้าขั้นไหนได้คำตอบที่โกหก ขั้นที่เหลือก็ทำงานถูกทุกอย่าง แต่บนข้อมูลที่ผิด
</Why>

แต่ละขั้นข้างบนทำตามข้อตกลงของมันเอง ข้อตกลงนี้เรียกว่า <Term en="Protocol" th="ข้อตกลงว่าสองเครื่องคุยกันแบบไหน" />

protocol แต่ละตัวทำงานเดียว และวางซ้อนกันเป็นชั้น ชั้นบนเรียกใช้ชั้นล่าง

เครือข่ายแบบ <Term en="TCP/IP" th="ชุดโปรโตคอลที่อินเทอร์เน็ตใช้" /> จึง **เป็นระบบที่ซับซ้อนมาก มันพึ่งบริการและโปรโตคอลที่เกี่ยวข้องกันจำนวนมาก จึงมีหลายจุดที่พังได้**

  <ProtocolStackMap />
</Figure>

<Term en="OSI Model" th="แบบจำลองเครือข่ายเจ็ดชั้น" /> แบ่งเครือข่ายไว้เจ็ดชั้น ส่วน **TCP/IP Model** ยุบสามชั้นบนของ OSI คือ Application, Presentation และ Session รวมเป็นชั้น Application ชั้นเดียว จึงเหลือห้าชั้น

ตารางนี้รวม Data link กับ Physical ไว้ในแถวเดียว

| ชั้น | โปรโตคอล | งาน |
| --- | --- | --- |
| Application | Telnet, FTP, SMTP, DNS, RIP, SNMP | งานที่ผู้ใช้ต้องการจริง เช่นล็อกอินระยะไกล ส่งไฟล์ ส่งอีเมล แปลงชื่อเป็นที่อยู่ |
| Transport | TCP, UDP | ส่งข้อมูลถึงโปรแกรมที่ถูกตัว TCP ส่งครบและเรียงลำดับ ส่วน UDP ส่งทีละก้อนโดยไม่รับประกัน |
| Network | IP, ARP, IGMP, ICMP | หาทางส่ง packet ข้ามเครือข่ายไปถึงเครื่องปลายทาง |
| Data link และ Physical | Ethernet, Token Ring, Frame Relay, ATM | ส่งสัญญาณจริงบนสายหรือคลื่น ระหว่างเครื่องที่ต่อกันตรง ๆ |

Telnet, FTP และ SMTP วิ่งบน TCP ส่วน DNS, RIP และ SNMP วิ่งบน UDP

สองตัวนี้ต่างกันตั้งแต่ก่อนส่งข้อมูล TCP ต้องทำ <Term en="TCP Handshake" th="ขั้นตอนเปิดการเชื่อมต่อของ TCP" /> ก่อนคุย ต้นทางส่งคำขอ ปลายทางตอบกลับพร้อมเลขสุ่มหนึ่งตัว แล้วต้นทางต้องส่งเลขนั้นคืนมาให้ถูก การเชื่อมต่อถึงจะเริ่มได้

ส่วน UDP ไม่มีขั้นนี้ ต้นทางส่งข้อมูลไปเลยทีละก้อน และปลายทางตอบได้ทันที

<Detail label="โปรโตคอลในตารางที่หน้านี้ไม่ได้ใช้ต่อ แต่ละตัวทำอะไร">
| โปรโตคอล | ชั้น | ทำอะไร |
| --- | --- | --- |
| RIP (Routing Information Protocol) | Application | ให้ router บอกเส้นทางที่ตัวเองรู้ให้ router ข้างเคียง |
| SNMP (Simple Network Management Protocol) | Application | ให้ผู้ดูแลอ่านสถานะและตั้งค่าอุปกรณ์เครือข่ายจากระยะไกล |
| IGMP (Internet Group Management Protocol) | Network | ให้เครื่องแจ้ง router ว่าขอรับ packet ที่ส่งถึงกลุ่ม (multicast) ไหน |
| ICMP (Internet Control Message Protocol) | Network | ส่งข้อความแจ้งปัญหาและข้อความควบคุม เช่นส่งไม่ถึงปลายทาง และ `ping` |
| Token Ring | Data link | LAN แบบวงแหวน เครื่องที่ถือ token อยู่เท่านั้นที่ส่งได้ |
| Frame Relay | Data link | บริการเช่าสายรุ่นเก่า ใช้ต่อเครือข่ายของสาขาที่อยู่ไกลกัน |
| ATM (Asynchronous Transfer Mode) | Data link | ส่งข้อมูลเป็นก้อนขนาดตายตัว 53 ไบต์ ใช้ในเครือข่ายหลักของผู้ให้บริการโทรคมนาคม |
</Detail>

### header บอกว่า packet ไปเครื่องไหน โปรแกรมไหน

<Why>
คำขอเปิด `nicebank.com` ต้องผ่าน router หลายตัวกว่าจะถึงเครื่องของธนาคารที่ `1.1.1.1` พอถึงแล้วก็ยังต้องไปถึงโปรแกรมเว็บ ไม่ใช่โปรแกรมอื่นบนเครื่องเดียวกัน

router แต่ละตัว และเครื่องปลายทาง รู้ได้ยังไงว่าต้องส่ง packet นี้ต่อไปที่ไหน
</Why>

packet ทุกก้อนมี <Term en="Header" th="ส่วนหัวของ packet" /> อยู่ข้างหน้า และเนื้อข้อมูลอยู่ข้างหลัง ใน header มีของสองอย่างที่หน้านี้ใช้ตลอด

- <Term en="IP Address" th="เลขที่อยู่ของเครื่อง" /> ของผู้ส่งและผู้รับ เช่น `2.2.2.2` บอกว่าเป็นเครื่องไหน
- <Term en="Port" th="เลขบอกโปรแกรมบนเครื่อง" /> ของผู้ส่งและผู้รับ บอกว่าเป็นโปรแกรมไหนบนเครื่องนั้น

บริการที่รู้จักกันมีเลข port ประจำ เช่น `21` คือ FTP สำหรับส่งไฟล์, `22` คือ SSH สำหรับล็อกอินระยะไกลแบบเข้ารหัส, `23` คือ Telnet สำหรับล็อกอินระยะไกลแบบไม่เข้ารหัส และ `80` คือเว็บ

<Analogy>
**header ของ packet ก็เหมือนป้ายหน้ากล่องพัสดุที่สั่งของออนไลน์**

- ที่อยู่ผู้รับบนป้าย คือ destination IP address
- ชื่อผู้รับบนป้าย คือ destination port เพราะที่อยู่พาไปถึงบ้าน ส่วนชื่อบอกว่าเป็นของคนไหนในบ้าน
- ที่อยู่ผู้ส่งที่ร้านพิมพ์ลงป้ายเอง คือ source IP address
- ของในกล่อง คือเนื้อข้อมูล
- ศูนย์คัดแยกแต่ละแห่งที่อ่านแค่ป้ายแล้วส่งต่อไปศูนย์ถัดไป คือ router

ที่อยู่ผู้ส่งบนป้าย ร้านจะพิมพ์อะไรลงไปก็ได้ และศูนย์คัดแยกไม่เคยตรวจว่าจริงไหม router ก็ไม่ตรวจ source IP address เหมือนกัน ซึ่งคือเรื่องของส่วนที่ 3

อุปมานี้ใช้ไม่ได้ตรงที่ **packet ถูกห่อซ้อนกันหลายชั้น และแต่ละชั้นมี header ของตัวเอง** header ชั้น IP อยู่กับ packet ตั้งแต่ต้นทางถึงปลายทาง แต่ห่อชั้นนอกสุดที่ใช้ใน LAN (Ethernet) ถูกแกะทิ้งและห่อใหม่ทุกครั้งที่ผ่าน router การปลอมห่อชั้นนอกจึงได้ผลแค่ใน LAN เดียว
</Analogy>

<Quiz question="packet ที่ขอหน้าเว็บของ nicebank.com ไปถึงเครื่อง 1.1.1.1 ของธนาคารถูกต้อง แต่ destination port ใน header เขียนว่า 22 แทนที่จะเป็น 80 หน้าเว็บจะขึ้นไหม">
destination IP address เลือกแค่ว่าเป็น **เครื่องไหน** ส่วน destination port เลือกว่าเป็น **โปรแกรมไหน** บนเครื่องนั้น เครื่อง `1.1.1.1` จึงส่งข้อมูลก้อนนี้ให้โปรแกรมที่รออยู่ที่ port 22 ซึ่งคือ SSH และ SSH ไม่เข้าใจคำขอหน้าเว็บ

คำตอบคือ **หน้าเว็บไม่ขึ้น** คำขอไปถึงเครื่องที่ถูก แต่ไปผิดโปรแกรม

คำตอบที่ผิดบ่อยคือ "IP ถูกแล้วก็ถึงเว็บ" ซึ่งลืมไปว่าเครื่องเดียวรันได้หลายโปรแกรม และ IP อย่างเดียวไม่ได้บอกว่าข้อมูลเป็นของโปรแกรมไหน
</Quiz>

## ส่วนที่ 2 — ผู้โจมตีเริ่มจากเรียนรู้เป้าหมาย

### สองประตูที่จะเข้าไปในเครื่อง

<Why>
ผู้โจมตีที่นั่งอยู่บ้านอยากเข้าเซิร์ฟเวอร์ของ `nicebank.com` ที่ `1.1.1.1` เขาไม่ได้อยู่หน้าเครื่อง จึงต้องเข้าผ่านเครือข่าย
</Why>

ทางเข้าจากระยะไกลมีประตูหลักสองบาน

- <Term en="Remote Login" th="ล็อกอินเข้าเครื่องจากระยะไกล" /> — **หาชื่อผู้ใช้และรหัสผ่านที่ใช้ได้** วิธีเดาและเจาะรหัสผ่านอยู่ใน [Lecture 3](/2110413-csy/lecture-3#ส่วนที่-5--วิธีที่คนใช้เจาะรหัสผ่าน)
- <Term en="Remote Exploit" th="ใช้ช่องโหว่ของโปรแกรมจากระยะไกล" /> — **หาบริการที่มีช่องโหว่แล้วใช้ช่องนั้น**

ทั้งสองบานเริ่มจากเรื่องเดียวกัน คือ **เข้าใจเป้าหมาย** และ **หาช่องโหว่ที่คนรู้กันอยู่แล้ว** ประตูแรกต้องรู้ว่าใครมีบัญชีบ้าง ประตูที่สองต้องรู้ว่าเครื่องรันโปรแกรมอะไร รุ่นไหน

ข้อมูลที่ต้องหาจึงมีสองกลุ่ม คือ **ข้อมูลทางสังคม** ว่าใครเป็นเจ้าของ ติดต่อทางไหน และ **ข้อมูลเครือข่ายและสภาพแวดล้อม** ว่ามีเครื่องอะไร เปิดบริการอะไร

### ข้อมูลทางสังคมจาก whois

<Why>
ถ้าจะหลอกให้ใครกรอกรหัสผ่าน หรือจะเดารหัสผ่านของใคร เราต้องรู้ก่อนว่าคนคนนั้นคือใคร ใช้อีเมลอะไร และทำงานกับบริษัทไหน

สำหรับเว็บไซต์ ข้อมูลชุดนี้มีคนจดไว้ให้แล้วตอนจดทะเบียนชื่อโดเมน
</Why>

<Term en="WHOIS" th="บริการค้นผู้จดทะเบียนโดเมน" /> ตอบว่าโดเมนหนึ่งจดทะเบียนกับใคร และใครเป็นผู้ติดต่อ แต่ละโดเมนค้นได้จากที่ต่างกัน

- **โดเมน `.th`** ค้นที่ THNIC ผู้ดูแลทะเบียนโดเมน `.th` — [https://www.thnic.co.th/th/whois/](https://www.thnic.co.th/th/whois/)
- **โดเมน `.com`** ค้นที่ ICANN องค์กรที่ดูแลระบบชื่อโดเมนของทั้งโลก — [https://whois.icann.org/](https://whois.icann.org/)

<Example title="ข้อมูล whois ของโดเมนหนึ่ง">
| ช่อง | ค่า |
| --- | --- |
| Registrar | GoDaddy.com, LLC |
| IANA ID | 146 |
| Abuse Contact Email | `abuse@godaddy.com` |
| Abuse Contact Phone | `tel:480-624-2505` |
| Registrant | Deverhood Co.,Ltd — Bangkok, Thailand |
| Technical | Deverhood Co.,Ltd — Bangkok, Thailand |
| Administrative | Deverhood Co.,Ltd |

<Term en="Registrar" th="บริษัทที่รับจดโดเมน" /> คือบริษัทที่เราเช่าชื่อโดเมนด้วย ส่วน Registrant, Technical และ Administrative คือผู้ติดต่อสามบทบาท ได้แก่เจ้าของ คนดูแลด้านเทคนิค และคนดูแลด้านธุรการ

<Detail label="ช่อง IANA ID และ Abuse Contact">

</Detail>
</Example>

ข้อมูลแค่นี้เปิดทางโจมตีได้ทั้งสาย สมมติว่าเรารู้ว่าโดเมนหนึ่งจดทะเบียนกับ GoDaddy.com ด้วยอีเมลหนึ่ง **การเจาะอีเมลนั้นได้ จะพาเราไปถึงตัวโดเมน**

เพราะบัญชีที่ registrar มักกู้รหัสผ่านผ่านอีเมลนั้น และใครที่เข้าบัญชีได้ก็เปลี่ยนได้ว่าชื่อโดเมนชี้ไปเครื่องไหน ทุกคนที่พิมพ์ชื่อเว็บนั้นจึงถูกพาไปเครื่องของผู้โจมตี

ตัวอีเมลเองถูกเจาะได้ด้วยวิธีที่เล่นงานคน อย่าง [phishing](/2110413-csy/lecture-1#phishing) และ [social engineering](/2110413-csy/lecture-1#social-engineering) ใน Lecture 1

### ข้อมูลเครือข่าย — ดักดู packet และสแกน port

<Why>
แต่โปรแกรมและรุ่นที่เครื่องเป้าหมายรัน เจ้าของไม่ได้ประกาศไว้ให้ใครอ่าน

ทางหาคำตอบมีสองแบบ คือฟัง packet ที่วิ่งอยู่แล้ว กับเคาะประตูเครื่องเป้าหมายเองแล้วดูว่ามันตอบอะไร
</Why>

เครื่องมือแบบฟังมีเช่น

- <Term en="Packet Sniffer" th="โปรแกรมดักดู packet" /> อย่าง **Wireshark** ที่แสดง packet เป็นหน้าจอให้คลิกดูทีละชั้น
- **tcpdump** ที่ดักแบบเดียวกัน แต่พิมพ์ออกมาเป็นบรรทัด
- **Snort** ที่รู้จักกันในฐานะ IDS ใน [Lecture 5](/2110413-csy/lecture-5#ส่วนที่-4--เอาไปจับผู้บุกรุก) ซึ่งมีโหมดดักดู packet เฉย ๆ ด้วย (`snort -v`)

ส่วนเครื่องมือแบบเคาะมีเช่น <Term en="Nmap" th="โปรแกรมสแกนเครือข่าย" /> ที่ส่ง packet ไปหาเครื่องและ port ต่าง ๆ แล้วดูว่าอะไรตอบกลับมา

แต่ sniffer มีข้อจำกัด คือเห็นเฉพาะ packet ที่วิ่งผ่านการ์ดเครือข่ายของเครื่องตัวเอง

<Term en="Switch" th="อุปกรณ์ต่อเครื่องใน LAN" /> คืออุปกรณ์กลางของ LAN ที่ส่งข้อมูลซึ่งจ่าหน้าถึงเครื่องหนึ่ง ไปที่สายของเครื่องนั้นเท่านั้น ไม่กระจายให้ทุกเครื่อง ใน LAN ที่ใช้ switch packet ของคนอื่นจึงไม่ผ่านมาที่เครื่องเราเลย

ข้อจำกัดนี้คือเหตุผลที่ ARP spoofing ในส่วนที่ 3 มีประโยชน์กับผู้โจมตี

### Nmap เผยหน้าตาของเครือข่าย

**Nmap ใช้ทำแผนที่เครือข่ายของเป้าหมายได้** ข้อมูลที่ได้มีเช่น

- **บริการและ port ที่เปิดอยู่** port ที่เปิดแต่ละ port คือประตูหนึ่งบานที่มีโปรแกรมรอรับอยู่
- <Term en="OS Fingerprint" th="เดาระบบปฏิบัติการจากวิธีตอบ" /> แต่ละระบบปฏิบัติการตอบ packet แปลก ๆ ไม่เหมือนกัน nmap เอาความต่างนั้นไปเทียบกับฐานข้อมูล เพื่อเดาว่าเครื่องรันอะไร

**Zenmap** คือหน้าต่างกราฟิกของ nmap ซึ่งวาดผลสแกนเป็นแผนที่ได้ ผลคือแผนที่ว่าเป้าหมายแต่ละตัวอยู่หลัง router ตัวไหนบ้าง

<Detail label="คำสั่งที่ใช้วาดแผนที่ใน Zenmap และวิธีอ่านแผนที่">
ตัวอย่างคือคำสั่ง `nmap -T4 -A -F -PN` ที่สแกน `www.google.com`, `www.facebook.com`, `twitter.com`, `microsoft.com`, `insecure.org`, `slashdot.org` และเว็บอื่นอีกหลายเว็บพร้อมกัน

- `-T4` สแกนเร็วขึ้น `-F` สแกนแค่ port ที่พบบ่อย และ `-PN` ข้ามขั้นถามว่าเครื่องเปิดอยู่ไหม
- `-A` เปิดหลายอย่างพร้อมกัน คือเดาระบบปฏิบัติการ ถามรุ่นของบริการ รันสคริปต์ตรวจ และไล่ว่า packet ผ่าน router ตัวไหนบ้าง

แท็บ Topology เอาเส้นทางที่ไล่ได้มาวาด เครื่องของเราอยู่ตรงกลาง เป้าหมายแต่ละตัวอยู่บนวงแหวนตามจำนวน router ที่ต้องผ่าน และจุดเล็ก ๆ ระหว่างทางคือ router แต่ละตัว

เป้าหมายที่ใช้ router ร่วมกันจะแตกกิ่งจากเส้นเดียวกัน ส่วนรายการเครื่องข้างแผนที่มีไอคอนบอกระบบปฏิบัติการที่เดาได้
</Detail>

<Example added title="สแกนเครื่องตัวเองด้วย nmap">
เปิดเว็บเซิร์ฟเวอร์ของ Python ไว้ที่ port 8080 บน `127.0.0.1` แล้วสแกนห้า port สองแบบ คือไม่ใส่และใส่ `-sV`

```bash
python3 -m http.server 8080 --bind 127.0.0.1
nmap -p 21,22,23,80,8080 127.0.0.1
```

ลองทายก่อน: ถ้าไม่ใส่ `-sV` nmap จะบอกว่า port 8080 รันอะไร

```text
8080/tcp open   http-proxy
```

```bash
nmap -sV -p 21,22,23,80,8080 127.0.0.1
```

```text
8080/tcp open   http    SimpleHTTPServer 0.6 (Python 3.14.4)
```

`http-proxy` เป็นแค่ชื่อที่ตารางของ nmap ผูกไว้กับเลข 8080 โดยไม่ได้ถามโปรแกรมเลย ส่วน `-sV` คุยกับบริการที่เปิดอยู่จนได้ชื่อโปรแกรมและรุ่นจริงมา

<Detail label="ผลเต็มของทั้งสองแบบ">
ตัดบรรทัดหัวและท้ายที่ nmap พิมพ์ทุกครั้งออก (Starting Nmap…, Nmap scan report…, Host is up…)

ไม่ใส่ `-sV`

```text
PORT     STATE  SERVICE
21/tcp   closed ftp
22/tcp   closed ssh
23/tcp   closed telnet

8080/tcp open   http-proxy

```

ใส่ `-sV`


`closed` แปลว่าเครื่องตอบกลับมาว่าไม่มีโปรแกรมรออยู่ที่ port นั้น ส่วน `open` แปลว่ามี ผลทั้งหมดนี้ได้จาก nmap 7.98
</Detail>
</Example>

### อย่าให้สัญญาณเตือนดัง

**การรัน nmap บนเครือข่ายอาจทำให้สัญญาณเตือนดัง ต้องระวัง เพราะอาจถูกบล็อก** ผู้สอนวิชานี้เคยเผลอรัน nmap บนเครือข่ายของโรงแรม แล้วถูกบล็อก ต้องโทรให้ฝ่ายไอทีของโรงแรมปลดบล็อกให้ถึงจะใช้เครือข่ายได้อีก

<Why>
ผู้ใช้ธรรมดาไม่เคยเคาะเครื่องเดียวทีละหลายสิบ port ในไม่กี่วินาที รูปแบบนี้จึงเป็น signature ที่ [IDS](/2110413-csy/lecture-5#ส่วนที่-4--เอาไปจับผู้บุกรุก) จับได้ง่าย ถ้าเครือข่ายนั้นมี IPS ที่เปิดโหมดบล็อกไว้ มันอาจตัดเครื่องที่สแกนออกทันที

การถามรุ่นด้วย `-sV` ยังทิ้งร่องรอยไว้ใน log ของบริการที่ถูกถามด้วย
</Why>

<Detail label="log ของเว็บเซิร์ฟเวอร์ระหว่างถูกสแกนด้วย -sV">
นี่คือบางบรรทัดใน log ของเว็บเซิร์ฟเวอร์ Python ในตัวอย่างข้างบน ระหว่างที่ nmap ถามรุ่น

```text
127.0.0.1 - - [12/Nov/2026 15:03:43] "POST /sdk HTTP/1.1" 501 -
127.0.0.1 - - [12/Nov/2026 15:03:43] "GET /nmaplowercheck1794470623 HTTP/1.1" 404 -
127.0.0.1 - - [12/Nov/2026 15:03:43] "GET /HNAP1 HTTP/1.1" 404 -
127.0.0.1 - - [12/Nov/2026 15:03:43] "GET /evox/about HTTP/1.1" 404 -
```

คำขอทั้งหมดมาในวินาทีเดียวกัน และบรรทัดที่สองมีคำว่า `nmap` อยู่ในตัวเลย คนที่อ่าน log หรือกฎของ IDS ที่หาคำนี้ จะรู้ทันทีว่าเครื่องถูกสแกน
</Detail>

ชื่อและรุ่นของโปรแกรมที่ได้จาก nmap คือสิ่งที่ผู้โจมตีเอาไปค้นต่อในหัวข้อถัดไป

### ปักหมุดเป้าหมาย — ช่องโหว่ที่คนรู้กันอยู่แล้ว

<Why>
สมมติ nmap ตอบว่า port 80 ของเป้าหมายรัน Apache httpd 2.2.15 ซึ่งเป็นเว็บเซิร์ฟเวอร์ที่ใช้กันแพร่หลาย

ผู้โจมตีจะรู้ได้ยังไงว่ารุ่นนี้มีช่องโหว่อะไรบ้าง โดยไม่ต้องหาช่องโหว่เองตั้งแต่ศูนย์
</Why>

**เมื่อรู้แล้วว่าเป้าหมายเปิด port อะไร รันบริการอะไร และใช้ระบบปฏิบัติการอะไร ก็ไปค้นช่องโหว่ที่รู้กันอยู่แล้วได้จากฐานข้อมูลสาธารณะ เช่น <Term en="CERT" th="หน่วยงานที่รวบรวมและประกาศช่องโหว่" />** และ **บางครั้งก็ได้สคริปต์ฟรีมาให้ลองด้วย**

แต่รายการเดียวกันก็บอกผู้โจมตีว่าจะยิงตรงไหน ช่วงระหว่างวันที่ช่องโหว่ถูกประกาศ กับวันที่เครื่องของเราลง patch จึงอันตรายที่สุด

### Script kiddie — เจาะได้โดยไม่ต้องเข้าใจช่องโหว่

สคริปต์ฟรีจากฐานข้อมูลช่องโหว่ใช้ได้โดยไม่ต้องเข้าใจช่องโหว่เลย

คนที่เอาสคริปต์แบบนี้มารัน ทั้งที่ไม่รู้ว่าช่องโหว่คืออะไร และสคริปต์ทำอะไรกับเครื่องเป้าหมาย เรียกว่า <Term en="Script Kiddie" th="คนที่รันสคริปต์ของคนอื่นโดยไม่เข้าใจ" />

คำนี้ใช้ในเชิงดูถูก แต่ความเสียหายที่คนกลุ่มนี้ทำได้เป็นของจริง เพราะสคริปต์ทำงานได้ไม่ว่าคนกดจะเข้าใจหรือไม่

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **เว็บของเราเล็ก ไม่มีข้อมูลมีค่า ไม่มีใครเสียเวลามาเจาะหรอก**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะเราคิดว่าผู้โจมตีเลือกเป้าหมายก่อน แล้วค่อยหาวิธีเจาะ คนที่เก่งพอจะหาช่องโหว่เองก็มักทำแบบนั้นจริง

สิ่งที่ถูกต้องคือ **script kiddie เลือกสคริปต์ก่อน แล้วค่อยหาเป้าหมาย** สคริปต์สำหรับ `VU#405811` ใช้ได้กับทุกเครื่องที่รัน Apache รุ่นที่มีช่องโหว่ ผู้โจมตีแค่สแกนหาเครื่องที่ตอบรุ่นนั้นกลับมาให้ได้มากที่สุด เว็บของเราถูกเลือกเพราะบรรทัด `VERSION` ไม่ใช่เพราะมีค่า
</Pitfall>

### Nmap ในภาพยนตร์ — ทั้งสายในฉากเดียว

**Nmap เคยปรากฏในภาพยนตร์หลายเรื่อง** เช่น **Matrix Reloaded**, **Ocean's 8** และ **Elysium** รายชื่อทั้งหมดอยู่ที่ [https://nmap.org/movies/](https://nmap.org/movies/)

ฉากใน Matrix Reloaded เดินครบทั้งสายของส่วนนี้ในจอเดียว ตั้งแต่สแกนหาบริการ ไปจนถึงใช้ช่องโหว่ที่รู้กันอยู่แล้ว คำสั่ง nmap ในฉากเป็นคำสั่งจริง ส่วน `sshnuke` เป็นโปรแกรมของภาพยนตร์

จอข้างล่างตัดเหลือเฉพาะบรรทัดที่ตัดสิน

```text
# nmap -v -sS -O 10.2.2.2
Interesting ports on 10.2.2.2:
22/tcp     open     ssh
No exact OS matches for host
# sshnuke 10.2.2.2 -rootpw="Z1ON0101"
Connecting to 10.2.2.2:ssh ... successful.
Attempting to exploit SSHv1 CRC32 ... successful.
Reseting root password to "Z1ON0101".
System open: Access Level <9>
# ssh 10.2.2.2 -l root
root@10.2.2.2's password:
```

nmap บอกว่า port 22 ที่รัน SSH เปิดอยู่ ตัวละครจึงใช้โปรแกรมที่เจาะช่องโหว่ของ SSH version 1 ตั้งรหัสผ่านของ root ใหม่ แล้วล็อกอินด้วยรหัสนั้น

`SSHv1 CRC32` ในจอเป็นช่องโหว่จริงของ SSH version 1 ที่ให้ผู้โจมตีรันโค้ดบนเครื่องได้

<Detail label="ตัวเลือกในคำสั่ง nmap ของฉากนี้">
ในคำสั่ง nmap ตัวเลือก `-v` ให้รายงานละเอียดขึ้น `-sS` ส่งแค่ขั้นแรกของ TCP handshake ไปเคาะแต่ละ port โดยไม่ต่อให้ครบ และ `-O` เดาระบบปฏิบัติการ ซึ่งบรรทัด `No exact OS matches for host` คือผลของมัน

สองตัวเลือกหลังต้องสร้าง packet เอง จึงต้องรันเป็น root คือบัญชีผู้ดูแลสูงสุดของ Unix ซึ่งพรอมต์ `#` บอกไว้

บรรทัดที่ตัดออกจากจอคือเลขรุ่นของ nmap คำเตือนเรื่อง TCP sequencing รายงาน port ที่ปิดอยู่ หัวตาราง และบรรทัดสรุปตอนจบ
</Detail>

<Quiz question="nmap บอกว่าเครื่องหนึ่งเปิด port 22 ที่รัน OpenSSH รุ่นล่าสุด และ port 80 ที่รัน Apache httpd 2.2.15 ผู้โจมตีจะเลือกประตูไหน และใช้ข้อมูลอะไรต่อ">
ประตู remote login ผ่าน SSH ต้องมีชื่อผู้ใช้และรหัสผ่าน ซึ่งยังไม่มี และ OpenSSH รุ่นล่าสุดน่าจะยังไม่มีช่องโหว่ที่ประกาศแล้ว ส่วน Apache 2.2.15 เป็นรุ่น 2.x ที่ตรงกับ `VU#405811` ในตารางข้างบนพอดี แต่ช่องนั้นเป็น DoS ผ่าน Range header คือทำให้เซิร์ฟเวอร์ล่ม ไม่ได้ให้สั่งงานเครื่อง

คำตอบคือ **เลือกประตู remote exploit ที่ port 80** เอารุ่น 2.2.15 ไปค้นในฐานข้อมูลช่องโหว่ต่อ เพื่อหาช่องที่ให้รันโค้ดได้ เพราะรุ่นเก่าขนาดนี้มักมีช่องโหว่ที่ประกาศแล้วหลายตัว ถ้าจะลองประตู SSH ด้วย ก็ต้องย้อนไปหาข้อมูลทางสังคมก่อนว่าใครน่าจะมีบัญชีบนเครื่องนี้

คำตอบที่ผิดบ่อยคือ "เดารหัสผ่าน SSH เพราะ port 22 เป็นประตูของผู้ดูแลระบบ" ประตูนี้ต้องใช้ข้อมูลมากที่สุดในกรณีนี้ และการเดารหัสผ่านซ้ำ ๆ ก็เป็นอีกรูปแบบที่ IDS จับได้ง่าย
</Quiz>

## ส่วนที่ 3 — เขียนที่อยู่บน header เอง: โจมตีโดยไม่เผยตัว

**ผู้โจมตีทำตัวให้มองไม่เห็นได้** เพราะ **header ของ packet ก็เหมือนป้ายหน้ากล่องพัสดุ ถ้าเราสร้าง packet เองได้ ก็เขียนที่อยู่ผู้ส่งและผู้รับลงไปเองได้ตามใจ**

การปลอมที่อยู่แบบนี้มีสองระดับ คือปลอม IP address และปลอมที่อยู่ที่ใช้ใน LAN

### IP Spoofing — ปลอมที่อยู่ผู้ส่ง

<Why>
เครื่อง `2.2.2.2` ไว้ใจเครื่อง `3.3.3.3` จึงยอมให้ล็อกอินเข้ามาได้โดยไม่ต้องใส่รหัสผ่าน ผู้โจมตีที่เครื่อง `1.1.1.1` อยากได้สิทธิ์เดียวกัน (`1.1.1.1` ตรงนี้เป็นคนละเครื่องกับธนาคารในส่วนอื่นของหน้า)

ถ้า `2.2.2.2` ตัดสินว่าใครเป็นใครจากที่อยู่ผู้ส่งใน header อย่างเดียว ผู้โจมตีก็แค่เขียนที่อยู่นั้นลงไปเอง
</Why>

<Term en="IP Spoofing" th="ปลอม source IP ใน header" /> คือการส่ง packet ที่ source IP address ไม่ใช่ที่อยู่ของเราเอง

<Example added title="packet ที่เขียนที่อยู่ผู้ส่งเอง">
สคริปต์ Python สร้าง packet หนึ่งใบลงไฟล์ให้ `tcpdump` อ่าน ผู้สร้างอยู่ที่ `1.1.1.1` แต่เขียน source เป็น `3.3.3.3` และส่งไปที่ port 513 ของ `2.2.2.2`

```bash
tcpdump -nn -t -x -r spoof.pcap
```

```text
IP 3.3.3.3.1023 > 2.2.2.2.513: Flags [S], seq 1000, win 64240, length 0
0x0000:  4500 0028 0001 0000 4006 70c6 0303 0303
0x0010:  0202 0202 03ff 0201 0000 03e8 0000 0000
0x0020:  5002 faf0 a100 0000
```

ไบต์ `0303 0303` คือ source address `3.3.3.3` และ `0202 0202` ที่ตามมาคือ destination address `2.2.2.2`

ทุกเครื่องที่อ่าน packet นี้เห็นผู้ส่งเป็น `3.3.3.3` และ `1.1.1.1` ไม่อยู่ตรงไหนใน packet เลย

<Detail label="อ่านแบบไม่มีไบต์ และไบต์ที่เหลือหมายถึงอะไร">
```bash
tcpdump -nn -t -r spoof.pcap
```

```text
IP 3.3.3.3.1023 > 2.2.2.2.513: Flags [S], seq 1000, win 64240, length 0
```

`Flags [S]` คือขั้นแรกของ TCP handshake

ที่อยู่ทั้งสองช่องเป็นแค่ช่องสี่ไบต์ที่ผู้สร้างกรอกลงไป ไม่มีลายเซ็นอะไรพิสูจน์ว่าเป็นของจริง

`tcpdump -vv` รายงานว่า checksum ของ packet นี้ `(correct)` คือ packet ถูกรูปแบบทุกอย่าง

`03ff` คือ port ต้นทาง 1023 และ `0201` คือ port ปลายทาง 513 ซึ่งเป็น port ของ rlogin บริการล็อกอินระยะไกลรุ่นเก่า ที่ยอมให้เครื่องในรายชื่อที่ไว้ใจเข้าได้โดยไม่ต้องใส่รหัสผ่าน
</Detail>
</Example>

ปัญหาของผู้โจมตีคือ **คำตอบวิ่งกลับไปหาเจ้าของที่อยู่ที่เขียนไว้ ไม่ใช่กลับมาหาคนส่ง** การปลอมที่อยู่จึงได้ผลกับงานสองแบบ คืองานที่ไม่ต้องการคำตอบ และงานที่เครื่องปลายทางเชื่อผู้ส่งจากที่อยู่อย่างเดียว

<Figure number={2} caption="ผู้โจมตีเขียนที่อยู่ของเครื่องที่เหยื่อไว้ใจ คำตอบจึงวิ่งไปที่เครื่องนั้น ไม่ใช่กลับมาหาผู้โจมตี">
  <IpSpoofing />
</Figure>

รูปที่ 2 คือแบบที่สอง ผู้โจมตีส่ง packet ที่อ้างว่ามาจาก `3.3.3.3` เหยื่อ `2.2.2.2` ไว้ใจเครื่องนั้นจึงยอมทำตาม

ผลคือผู้โจมตีได้สิทธิ์ที่เหยื่อให้ไว้กับ `3.3.3.3` เช่นล็อกอินโดยไม่ใส่รหัสผ่าน ซึ่งเป็น **ช่องโหว่ด้านความปลอดภัยของเหยื่อ** ส่วนเครื่อง `3.3.3.3` ตัวจริง **อาจตกเป็นเป้าของการโจมตีแบบ DoS ไปด้วย**

<Callout type="info" title="ทำไมต้องยิงเครื่องที่ถูกอ้างชื่อให้ล่ม">
ในรูปที่ 2 คำตอบขั้นที่สองของ TCP handshake ซึ่งมีเลขสุ่ม วิ่งไปที่ `3.3.3.3` ตัวจริง ซึ่งจะบอกเหยื่อว่าไม่ได้ขออะไรเลย แล้วการเชื่อมต่อก็ถูกยกเลิก

ผู้โจมตีจึงต้องยิง `3.3.3.3` ให้ล่มก่อน แล้วเดาเลขสุ่มนั้นเองโดยไม่เคยเห็นมัน
</Callout>

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **log บอกว่า packet มาจาก IP ไหน ก็แปลว่าคนยิงอยู่ที่ IP นั้น**

ความเชื่อนี้ไม่จริงเสมอไป

มันดูจริงเพราะการเชื่อมต่อที่เราเห็นทุกวันส่วนใหญ่เป็น TCP ที่ handshake ครบแล้ว ซึ่งคนส่งต้องได้รับคำตอบจริง ที่อยู่จึงมักเป็นของจริง

สิ่งที่ถูกต้องคือ **ที่อยู่ผู้ส่งเป็นแค่ช่องที่คนส่งกรอกเอง** อย่าง packet ในตัวอย่างข้างบนที่ทุกเครื่องเห็นเป็น `3.3.3.3` ทั้งที่มาจาก `1.1.1.1` packet เดี่ยว ๆ ที่ไม่ต้องรอคำตอบ เช่น UDP ทั้งหมด หรือคำขอแรกของ TCP handshake จึงไม่ได้บอกเลยว่าใครเป็นคนส่ง
</Pitfall>

### ARP/MAC Spoofing — แย่งรับ packet ใน LAN

<Why>
ผู้โจมตีที่อยู่ใน LAN เดียวกับเหยื่อ เช่นในร้านกาแฟ อยากอ่านทุกอย่างที่เหยื่อส่งออกอินเทอร์เน็ต

แต่ switch ส่ง packet ของเหยื่อไปที่ gateway ตรง ๆ ไม่ผ่านเครื่องของผู้โจมตี sniffer ของผู้โจมตีจึงไม่เห็นอะไร ตามข้อจำกัดในส่วนที่ 2

ทางเดียวคือหลอกให้เครื่องของเหยื่อเชื่อว่าเครื่องของผู้โจมตีคือ gateway
</Why>

ใน LAN แต่ละ packet ถูกห่อด้วยชั้นนอกสุดอีกชั้น เรียกว่า <Term en="Frame" th="ก้อนข้อมูลที่ส่งใน LAN" />

frame ถูกส่งไปตาม <Term en="MAC Address" th="เลขประจำการ์ดเครือข่าย" /> ของการ์ดเครือข่ายปลายทาง ไม่ใช่ตาม IP

แต่เครื่องของเหยื่อรู้แค่ IP ของ gateway คือ `192.168.1.1` จึงต้องถามก่อนว่า IP นี้ใช้ MAC address อะไร

<Term en="ARP (Address Resolution Protocol)" th="ถามว่า IP นี้ใช้ MAC อะไร" /> ทำงานแบบนี้ เครื่องตะโกนถามทั้ง LAN ว่า "ใครเป็น `192.168.1.1`" เจ้าของตอบกลับด้วย ARP reply ว่า "`192.168.1.1` อยู่ที่ MAC นี้"

แล้วเครื่องที่ถามจดคำตอบไว้ใน <Term en="ARP Cache" th="ตารางจำคู่ IP กับ MAC" /> ใช้ต่อไปเรื่อย ๆ

จุดอ่อนคือ **ARP ไม่มีอะไรพิสูจน์ว่าคนตอบเป็นเจ้าของ IP นั้นจริง** และเครื่องส่วนใหญ่รับคำตอบแม้ตัวเองไม่ได้ถาม ARP reply จากเจ้าของจริงกับจากผู้โจมตีต่างกันแค่ช่อง MAC address

<Detail label="ARP reply ของจริงกับของปลอมที่สร้างขึ้นเอง ใน tcpdump">
สคริปต์ Python ตัวเดียวกับตัวอย่าง IP spoofing สร้าง ARP reply สองใบถึงเครื่อง `192.168.1.10` ใบแรกจาก gateway ตัวจริง ใบที่สองจากผู้โจมตี

```bash
tcpdump -nn -t -e -r arp.pcap
```

```text
02:00:00:00:00:01 > 02:00:00:00:00:0a, ethertype ARP (0x0806), length 42: Reply 192.168.1.1 is-at 02:00:00:00:00:01, length 28
02:00:00:00:00:66 > 02:00:00:00:00:0a, ethertype ARP (0x0806), length 42: Reply 192.168.1.1 is-at 02:00:00:00:00:66, length 28
```

สองบรรทัดต่างกันแค่ MAC address และไม่มีช่องไหนบอกได้ว่าใบไหนมาจากเจ้าของ `192.168.1.1` ตัวจริง
</Detail>

ผู้โจมตีจึงส่ง ARP reply ว่า "`192.168.1.1` อยู่ที่ MAC ของฉัน" ซ้ำไปเรื่อย ๆ จน ARP cache ของเหยื่อจดทับของจริง

การส่ง ARP reply ปลอมแบบนี้เรียกว่า <Term en="ARP Spoofing" th="ปลอมคำตอบ ARP" /> หรือ <Term en="ARP Cache Poisoning" th="ทำให้ ARP cache จำ MAC ผิด" />

<Figure number={3} caption="ARP reply ปลอมเปลี่ยนบรรทัดเดียวใน ARP cache ของแต่ละฝั่ง แต่ทำให้ทุก frame ระหว่างผู้ใช้กับ gateway วิ่งผ่านผู้โจมตีก่อน ทั้งขาไปและขากลับ">
  <ArpSpoofing />
</Figure>

ผู้โจมตีทำแบบเดียวกันกับ gateway ด้วย คือบอก gateway ว่า "`192.168.1.10` ซึ่งเป็น IP ของเหยื่อ อยู่ที่ MAC ของฉัน" frame ขากลับจึงผ่านผู้โจมตีเช่นกัน ถ้าทำฝั่งเดียว ผู้โจมตีจะเห็นแค่ครึ่งเดียวของบทสนทนา

ผู้โจมตีส่งทุก frame ต่อให้ปลายทางตัวจริง เหยื่อจึงใช้อินเทอร์เน็ตได้ตามปกติ ไม่รู้ว่ามีคนนั่งอยู่ตรงกลาง นี่คือ [man-in-the-middle](/2110413-csy/lecture-1#man-in-the-middle) ใน LAN ผู้โจมตีอ่านทุกอย่างที่ไม่ได้เข้ารหัส และแก้ข้อความก่อนส่งต่อได้

ARP spoofing ปลอมคู่ระหว่าง IP กับ MAC ส่วนอีกทางที่ใกล้กันคือปลอมตัว MAC address เอง เรียกว่า <Term en="MAC Spoofing" th="ใช้ MAC ของเครื่องอื่น" />

MAC address ติดมากับการ์ดเครือข่ายจากโรงงานก็จริง แต่ระบบปฏิบัติการเปลี่ยนค่าที่การ์ดใช้ได้ ผู้โจมตีจึงตั้ง MAC ของตัวเองให้ตรงกับเครื่องอื่น เพื่อสวมรอยเป็นเครื่องนั้นใน LAN

### DDoS ด้วยคำขอที่ปลอมต้นทาง

<Why>
[DDoS ใน Lecture 1](/2110413-csy/lecture-1#botnet-และ-ddos) ใช้ botnet คือเครื่องที่ถูกยึดมาแล้วจำนวนมาก ยิงเป้าหมายตรง ๆ

ทางนั้นมีต้นทุนสองอย่าง ต้องยึดเครื่องมาก่อน และเครื่องที่ยิงก็ทิ้งที่อยู่ของตัวเองไว้ที่เหยื่อ ซึ่งสาวกลับไปหาได้

IP spoofing ตัดต้นทุนทั้งสองข้อทิ้ง
</Why>

**ผู้โจมตีหลอกเครื่องหรือเซิร์ฟเวอร์ของคนอื่น ให้ส่งคำตอบที่ถูกต้องตามปกติไปถล่มเหยื่อได้**

วิธีคือส่งคำขอไปหาเซิร์ฟเวอร์ UDP จำนวนมาก โดยเขียนที่อยู่ผู้ส่งเป็นที่อยู่ของเหยื่อ เซิร์ฟเวอร์ทุกเครื่องทำหน้าที่ตามปกติคือตอบคำขอ และคำตอบทั้งหมดวิ่งไปที่เหยื่อ

เซิร์ฟเวอร์ทำหน้าที่เหมือนกระจกที่สะท้อนคำขอไปหาเหยื่อ การโจมตีแบบนี้จึงเรียกว่า <Term en="Reflection Attack" th="สะท้อนคำตอบไปหาเหยื่อ" />

<Figure number={4} caption="ผู้โจมตีไม่ได้ส่งอะไรถึงเหยื่อเลยสัก packet ทุก packet ที่เหยื่อได้รับเป็นคำตอบจริงจากเซิร์ฟเวอร์จริง">
  <ReflectionDdos />
</Figure>

ต้องเป็น UDP เพราะ UDP ไม่มี handshake เซิร์ฟเวอร์ตอบทันทีที่ได้คำขอใบเดียว โดยไม่มีจังหวะไหนให้ตรวจว่าที่อยู่ผู้ส่งเป็นของจริง

ถ้าคำตอบใหญ่กว่าคำขอมาก ผู้โจมตียิ่งได้กำลังเพิ่มฟรี ส่งคำขอเล็ก ๆ ออกไป แต่เหยื่อได้รับคำตอบก้อนใหญ่กว่าหลายเท่า กำลังที่เพิ่มขึ้นแบบนี้เรียกว่า <Term en="Amplification" th="คำตอบใหญ่กว่าคำขอหลายเท่า" />

เช่นเซิร์ฟเวอร์ DNS ส่งคำตอบที่ใหญ่กว่าคำขอได้ราว 28 ถึง 54 เท่า ตามตัวเลขในประกาศของ [CISA](https://www.cisa.gov/news-events/alerts/2014/01/17/udp-based-amplification-attacks)

<Quiz question="ผู้ดูแลเครือข่ายของเหยื่อในรูปที่ 4 เห็น traffic ท่วมเข้ามา จึงบล็อกทุก IP ที่ส่งมาเยอะที่สุด ผลจะเป็นยังไง">
IP ที่ส่งมาเยอะที่สุดคือเซิร์ฟเวอร์ UDP ที่ถูกหลอก ซึ่งอาจเป็น DNS server ที่องค์กรเองใช้อยู่ ส่วนผู้โจมตีไม่เคยส่ง packet ถึงเหยื่อเลย จึงไม่มี IP ของผู้โจมตีให้บล็อก

คำตอบคือ **ผู้โจมตีไม่ได้รับผลอะไรเลย** ผู้โจมตีเปลี่ยนไปใช้เซิร์ฟเวอร์ชุดใหม่ได้ทันที และการบล็อกอาจตัดเหยื่อออกจากบริการที่ตัวเองต้องใช้ด้วย

คำตอบที่ผิดบ่อยคือ "บล็อกแล้วการโจมตีก็หยุด" ซึ่งใช้ได้เมื่อต้นทางคือคนยิงจริง แต่ในการโจมตีแบบนี้ ต้นทางที่เหยื่อเห็นเป็นแค่กระจกที่สะท้อนคำขอมา
</Quiz>

## ส่วนที่ 4 — DNS poisoning: โปรโตคอลที่ออกแบบมาให้ทำงาน

**โปรโตคอลและบริการเครือข่ายจำนวนมากถูกออกแบบมาให้ทำงานได้ ไม่ได้ออกแบบมาให้ปลอดภัย** ตัวอย่างที่ชัดที่สุดคือ DNS ซึ่งตอบคำถามแรกสุดของทุกการเชื่อมต่อ

### DNS ทำงานยังไง

<Why>
ก่อนเบราว์เซอร์จะส่ง packet ไปหา `NiceBank.com` ได้ มันต้องรู้ก่อนว่าชื่อนี้คือ IP อะไร
</Why>

<Term en="DNS (Domain Name System)" th="ระบบแปลงชื่อเว็บเป็น IP" /> คือสิ่งที่แปลง `NiceBank.com` เป็น IP address อย่าง `1.1.1.1` คำถามของเครื่องเราไม่ได้วิ่งไปถึงเจ้าของชื่อตรง ๆ แต่ผ่าน DNS server ตัวกลางก่อน

- <Term en="Local DNS Server" th="DNS server ประจำเครือข่าย" /> — ตอบคำถามแทนทุกเครื่องในเครือข่าย ถ้ายังไม่รู้คำตอบก็ไปถามต่อ
- <Term en="Master DNS Server" th="DNS server ของเจ้าของชื่อ" /> — รู้คำตอบจริงของชื่อนั้น

คำตอบที่ local DNS server ได้มา จะถูกจดไว้ใน <Term en="Cache" th="ที่จำคำตอบเก่าไว้ใช้ซ้ำ" /> ใครถามชื่อเดิมอีก server ก็ตอบจาก cache ทันที ไม่ต้องไปถามต่อ

คำถามและคำตอบของ DNS วิ่งบน UDP เป็น packet เดี่ยว ๆ local DNS server จึงต้องจับคู่ว่าคำตอบที่เข้ามาเป็นของคำถามไหน ด้วยเลขที่ตัวเองสุ่มใส่ไว้ในคำถาม เรียกว่า <Term en="Transaction ID" th="เลขประจำคำถาม" />

ID นี้ยาว 16 บิต มีได้ 65,536 ค่า คำตอบใบแรกที่ ID ตรงถูกรับไว้และจดลง cache ใบที่มาทีหลังถูกทิ้ง

<Example added title="dig รับคำตอบที่ ID ตรง ไม่ว่าในนั้นจะเขียนอะไร">
ใช้ `dig` ซึ่งเป็นคำสั่งถาม DNS จาก command line ถาม DNS server จำลองบน `127.0.0.1` ซึ่งส่งคำตอบปลอม `5.5.5.5` ก่อนคำตอบจริง `1.1.1.1`

รอบแรกคำตอบปลอมใส่ ID ผิดไปหนึ่ง รอบที่สองใส่ ID ถูก

```bash
# round 1: the forged answer carries a wrong ID
dig @127.0.0.1 -p 5300 nicebank.com A
```

```text
;; Warning: ID mismatch: expected ID 62508, got 62509
nicebank.com.		300	IN	A	1.1.1.1
```

```bash
# round 2: the forged answer carries the right ID
dig @127.0.0.1 -p 5300 nicebank.com A
```

```text
nicebank.com.		300	IN	A	5.5.5.5
```

รอบแรก `dig` ทิ้งใบที่ ID ไม่ตรง รอบที่สองมันรับ `5.5.5.5` ทันที และไม่สนใจคำตอบจริงที่มาทีหลัง

<Detail label="ตัวอย่างนี้ต่างจากของจริงตรงไหน">
คำตอบปลอมมาถึงก่อนคำตอบจริง 0.3 วินาที ผลข้างบนตัดเหลือบรรทัดที่ตัดสินของแต่ละครั้ง และตัวอย่างนี้ส่งคำตอบทั้งสองใบจากโปรแกรมเดียวกัน ในเครือข่ายจริง คำตอบปลอมมาจากเครื่องของผู้โจมตี ตามหัวข้อถัดไป
</Detail>
</Example>

### DNS cache poisoning

<Why>
ถ้าผู้โจมตีทำให้ local DNS server ขององค์กรหนึ่งจำว่า `NiceBank.com` อยู่ที่ `5.5.5.5` ได้ ทุกคนที่ใช้ server นั้นจะถูกส่งไปเว็บปลอม ทั้งที่พิมพ์ชื่อเว็บถูกทุกตัวอักษร และไม่ได้คลิกลิงก์อะไรเลย
</Why>

<Term en="DNS Cache Poisoning" th="ทำให้ cache ของ DNS จำคำตอบปลอม" /> ใช้สองข้อที่เห็นมาแล้วรวมกัน คือ DNS เชื่อคำตอบใบแรกที่ ID ตรง และที่อยู่ผู้ส่งปลอมได้ คำตอบปลอมจึงเขียนที่อยู่ผู้ส่งเป็นของ master DNS server ด้วย IP spoofing

<Figure number={5} caption="ผู้โจมตีเป็นคนเริ่มคำถามเอง จึงรู้จังหวะ แล้วส่งคำตอบปลอมที่เดา ID หลายค่าไปแข่งกับคำตอบจริง">
  <DnsCachePoisoning />
</Figure>

ขั้นที่ทำให้มันได้ผลคือขั้นที่ 1 ผู้โจมตีถาม local DNS server เอง จึงรู้แน่ว่าในเสี้ยววินาทีถัดไป server จะรอคำตอบของ `NiceBank.com` อยู่

สิ่งเดียวที่ไม่รู้คือ ID ผู้โจมตีจึงยิงคำตอบปลอมหลายใบที่เดา ID ต่างกันไปแข่ง ถ้าใบไหนเดาตรงก่อนคำตอบจริงมาถึง cache ของ server ก็จำ `5.5.5.5` ไว้แทนที่อยู่จริง

นี่คือ <Term en="Pharming Attack" th="พาไปเว็บปลอมโดยแก้ขั้นแปลงชื่อ" /> ที่อยู่ในรายชื่อ[ภัยเก้าอย่างของ Lecture 1](/2110413-csy/lecture-1#ภัยเก้าอย่างที่ต้องแยกให้ออก) มันพาเราไปเว็บปลอมด้วยการแก้ขั้นตอนที่แปลงชื่อเว็บเป็นที่อยู่

ภาพเคลื่อนไหวของการโจมตีนี้ดูได้ที่ [https://www.youtube.com/watch?v=1d1tUefYn4U](https://www.youtube.com/watch?v=1d1tUefYn4U)

<Example added title="ต้องแข่งกี่รอบถึงจะชนะ">
สูตรข้างล่างคิดว่าผู้โจมตีต้องแข่งกี่รอบถึงจะมีโอกาสชนะ โค้ดนี้แสดงแค่สูตร ส่วนที่วนค่า k และพิมพ์ผลถูกตัดออก

```python
# k = forged answers sent in one race, each with a different guessed ID
p = k / 2**16                               # chance one race is won
races = math.ceil(math.log(0.5) / math.log(1 - p))  # races for a 50% chance
```

ลองทายก่อน: ยิงรอบละ 1,000 ใบ ต้องแข่งกี่รอบถึงจะมีโอกาสชนะครึ่งต่อครึ่ง

```text
forged answers per race     4: win one race 0.0061%, races for a 50% chance 11357
forged answers per race   100: win one race 0.1526%, races for a 50% chance 454
forged answers per race  1000: win one race 1.5259%, races for a 50% chance 46
```

<Detail label="ทำไมของจริงยากกว่านี้ และทำไมยังไม่พอ">
แต่ละรอบที่แพ้ คำตอบจริงจะถูกจดลง cache และอยู่จนหมดอายุ ผู้โจมตีจึงแข่งซ้ำกับชื่อเดิมทันทีไม่ได้

แต่ผู้โจมตีเลี่ยงข้อนี้ได้ ด้วยการถามชื่อย่อยที่ไม่มีอยู่จริงใหม่ทุกรอบ แล้วแนบข้อมูลปลอมของโดเมนหลักไปกับคำตอบปลอม

ทางแก้ที่ใช้กันคือให้ local DNS server สุ่ม port ต้นทางของคำถามด้วย ผู้โจมตีต้องเดาทั้ง ID และ port ให้ถูกพร้อมกัน เครื่อง Linux ที่รันตัวอย่างนี้ใช้ port ช่วง 32768 ถึง 60999 ซึ่งมี 28,232 port

```text
random port too, 1000 per race: win one race 0.00005405%, races for 50% 1,282,470
```

จาก 46 รอบกลายเป็นราวหนึ่งล้านสามแสนรอบ แต่ทางแก้นี้แค่ทำให้เดายากขึ้น ไม่ได้ทำให้คำตอบพิสูจน์ได้ว่ามาจากเจ้าของจริง
</Detail>
</Example>

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ถ้าพิมพ์ชื่อเว็บเองทุกตัวอักษร ไม่คลิกลิงก์ในอีเมล ก็ไม่มีทางไปโผล่ที่เว็บปลอม**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะ phishing ที่เราถูกสอนให้ระวัง ทำงานด้วยการหลอกให้คลิกลิงก์ที่ชื่อเพี้ยนไปจากของจริง การพิมพ์เองจึงกันได้

สิ่งที่ถูกต้องคือ **pharming ไม่ได้แก้ชื่อที่เราพิมพ์ แต่แก้คำตอบที่ได้จากชื่อนั้น** ในรูปที่ 5 ผู้ใช้พิมพ์ `NiceBank.com` ถูกทุกตัว แต่ local DNS server ตอบ `5.5.5.5` เบราว์เซอร์ก็ไปที่นั่นตามคำตอบ
</Pitfall>

<Quiz question="NiceBank.com ใช้ HTTPS ทั้งเว็บ ถ้า local DNS server ที่ผู้ใช้ใช้อยู่ถูก poison ให้ตอบ 5.5.5.5 ผู้ใช้จะเห็นอะไรเมื่อเปิดเว็บ">
DNS ถูกถามก่อนเริ่ม HTTPS เบราว์เซอร์จึงต่อไปที่ `5.5.5.5` จริง ๆ แต่ HTTPS ต้องให้เซิร์ฟเวอร์ยื่นใบรับรองของชื่อ `NiceBank.com` ที่ CA ซึ่งเบราว์เซอร์เชื่อเป็นคนเซ็น ผู้โจมตีที่ `5.5.5.5` ไม่มี private key ของใบจริง และขอใบใหม่จาก CA ไม่ได้ เพราะไม่ได้เป็นเจ้าของโดเมน

คำตอบคือ **เบราว์เซอร์เตือนว่าใบรับรองเชื่อถือไม่ได้** ผู้ใช้จะปลอดภัยถ้าไม่กดข้ามคำเตือน และไม่มี CA ไหนออกใบผิดให้ผู้โจมตี อย่างกรณีใน [Lecture 7](/2110413-csy/lecture-7#ส่วนที่-6--เมื่อความเชื่อถูกใช้ผิดทาง)

คำตอบที่ผิดบ่อยคือ "HTTPS เข้ารหัสอยู่แล้ว DNS จึงถูก poison ไม่ได้" ซึ่ง HTTPS ไม่ได้ป้องกัน DNS เลย มันแค่จับได้ทีหลังว่าปลายทางไม่ใช่ตัวจริง
</Quiz>

## ส่วนที่ 5 — ป้องกันด้วยระบบ คน และซอฟต์แวร์

### สามด้านของการป้องกัน

<Why>
การโจมตีในหน้านี้ใช้ช่องต่างกัน คือ port ที่เปิดทิ้งไว้ ที่อยู่ที่ไม่มีใครตรวจ และคนที่ whois บอกว่าต้องหลอกใคร

ทางป้องกันจึงต้องมีสามด้าน
</Why>

**ด้านระบบ**

- **Firewall** — กั้นระหว่างอินเทอร์เน็ตกับเครือข่ายภายใน ให้ผ่านเฉพาะ traffic ที่อนุญาต รายละเอียดอยู่ใน [Lecture 5](/2110413-csy/lecture-5#firewall)
- **Patch และการอัปเดต** — ปิดช่องโหว่ที่ถูกประกาศในฐานข้อมูลอย่าง CERT ก่อนที่ script kiddie จะสแกนมาเจอ
- <Term en="System Hardening" th="ปิดสิ่งที่ไม่จำเป็นในระบบ" /> — ปิดบริการและ port ที่ไม่ได้ใช้ ทุก port ที่ nmap เห็นว่า `open` คือประตูที่ต้องมีคนเฝ้า
- **Encryption** — ทำให้คนที่ดัก packet ได้อ่านเนื้อหาไม่ออก แต่ **อย่าลืมว่าการเข้ารหัสมีจุดอ่อนต่อการวิเคราะห์ทางสถิติ** ทั้งที่ตัวข้อความเอง ตาม[ส่วนที่ 9 ของ Lecture 6](/2110413-csy/lecture-6#ส่วนที่-9--การเข้ารหัสให้อะไร-และไม่ให้อะไร) และที่ข้อมูลใน header ซึ่งยังอ่านออกอยู่ ตามความเชื่อผิดข้างล่าง

**ด้านคน**

- **Awareness** — ผู้ใช้ต้องรู้ทันการหลอก เพราะ whois ทำให้ผู้โจมตีรู้ว่าต้องหลอกใคร และ[ผู้ใช้คือแนวป้องกันด่านแรก](/2110413-csy/lecture-1#ทางที่สอง--หลอกคนที่ใช้ระบบ)

**ด้านซอฟต์แวร์**

- <Term en="Secure by Design" th="ออกแบบให้ปลอดภัยตั้งแต่แรก" /> — สิ่งที่ IP, ARP และ DNS รุ่นแรกไม่มี เพราะทั้งสามตัวถูกออกแบบมาให้ทำงานในเครือข่ายที่ทุกคนไว้ใจกัน

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ถ้าเข้ารหัสทุกอย่างแล้ว คนที่ดัก packet จะไม่ได้ข้อมูลอะไรเลย**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะเนื้อหาที่เข้ารหัสดีแล้วอ่านไม่ออกจริง ๆ เปิดดูใน Wireshark ก็เห็นเป็นไบต์มั่ว ๆ

สิ่งที่ถูกต้องคือ **การเข้ารหัสปิดกล่องให้ไม่มีใครเห็นของข้างใน แต่ป้ายหน้ากล่องต้องอ่านออกเสมอ** เพราะ router ต้องอ่านที่อยู่ใน header ถึงจะส่งต่อได้ คนดักจึงยังเห็นว่าเครื่องไหนคุยกับเครื่องไหน ที่ port อะไร เมื่อไหร่ และส่งไปกี่ไบต์ ข้อมูลพวกนี้วิเคราะห์ทางสถิติได้ เช่นเครื่องที่คุยกับ port 22 ของเซิร์ฟเวอร์ทุกเช้าน่าจะเป็นเครื่องของผู้ดูแลระบบ
</Pitfall>

| สแกนหา port และรุ่น | system hardening, firewall และ IDS ที่จับการสแกน |
| ช่องโหว่ที่ประกาศแล้ว | ลง patch ให้เร็วกว่าคนสแกน |
| IP spoofing และ DDoS ด้วยคำขอปลอมต้นทาง | ผู้ให้บริการอินเทอร์เน็ตทิ้ง packet ที่ลูกค้าส่งเข้ามา ถ้าที่อยู่ผู้ส่งไม่ใช่ที่อยู่ที่แจกให้ลูกค้ารายนั้น |
| ARP spoofing | switch ที่ตรวจ ARP reply เทียบกับตารางที่รู้ว่าเครื่องไหนได้ IP อะไร หรือจด MAC ของ gateway ไว้ตายตัว |
| DNS cache poisoning | สุ่ม port ต้นทาง (กล่อง "ทำไมของจริงยากกว่านี้" ในส่วนที่ 4) และให้เจ้าของโดเมนเซ็นคำตอบด้วย[ลายเซ็นดิจิทัล](/2110413-csy/lecture-6#digital-signature) |
</Callout>

<Quiz question="ผู้ดูแลระบบรัน nmap กับเซิร์ฟเวอร์ของบริษัทตัวเอง แล้วเจอว่า port 23 ที่รัน Telnet เปิดอยู่ ทั้งที่ทุกคนล็อกอินผ่าน SSH ที่ port 22 กันหมดแล้ว ควรทำอะไร และทำไม">
port ที่ไม่มีใครใช้แต่ยังเปิดอยู่ไม่ได้ให้อะไรกับบริษัทเลย แต่เป็นประตูเพิ่มอีกบานให้ผู้โจมตี และ Telnet ส่งทุกอย่างรวมถึงรหัสผ่านแบบไม่เข้ารหัส คนที่ดัก packet ได้ด้วย sniffer หรือ ARP spoofing จะอ่านรหัสผ่านได้ตรง ๆ

คำตอบคือ **ปิด Telnet ทิ้ง** ซึ่งเป็น system hardening แล้วรัน nmap ซ้ำเพื่อยืนยันว่า port 23 กลายเป็น `closed`

คำตอบที่ผิดบ่อยคือ "ตั้ง firewall บล็อก port 23 จากข้างนอกก็พอ" ซึ่งกันได้แค่คนนอก ผู้โจมตีที่อยู่ใน LAN เดียวกัน หรือเครื่องในบริษัทที่ถูกยึดแล้ว ยังเข้าถึงได้ ของที่ไม่ใช้ควรถูกปิด ไม่ใช่แค่ถูกบัง
</Quiz>

### เจาะระบบตัวเองก่อนคนอื่น

ในโลกที่ทุกอย่างเชื่อมต่อกัน ความปลอดภัยของเครือข่ายสำคัญมาก และทางที่ได้ผลคือ **เรียนรู้ระบบของตัวเองเสมอ เจาะมันก่อนที่คนอื่นจะเจาะ** (*Hack it first, before others will.*)

นั่นคือเอาเครื่องมือทั้งหมดของส่วนที่ 2 มาหันใส่ระบบของตัวเอง สแกนด้วย nmap ให้รู้ว่าเปิดอะไรไว้ เอารุ่นที่ได้ไปค้นใน CERT แล้วปิดหรือ patch ก่อนที่คนอื่นจะทำแบบเดียวกัน และทำบนเครือข่ายที่ตัวเองได้รับอนุญาตเท่านั้น

<Recap>

**[เครือข่ายคือโปรโตคอลหลายชั้น](#ส่วนที่-1--เครือข่ายคือโปรโตคอลหลายชั้นที่เชื่อกันเอง)**

- เครือข่าย TCP/IP **ซับซ้อนมาก พึ่งบริการและโปรโตคอลที่เกี่ยวข้องกันจำนวนมาก จึงพังได้หลายทาง**
- OSI มีเจ็ดชั้น TCP/IP ยุบสามชั้นบนเป็น Application เหลือห้าชั้น
- Telnet, FTP, SMTP บน TCP · DNS, RIP, SNMP บน UDP · IP, ARP, IGMP, ICMP ในชั้น Network · Ethernet, Token Ring, Frame Relay, ATM ในชั้นล่าง
- **header ของ packet เหมือนป้ายหน้ากล่องพัสดุ** มี IP address บอกเครื่อง และ port บอกโปรแกรม
- TCP ต้องทำ handshake ก่อนคุย UDP ส่งได้ทันที

**[เรียนรู้เป้าหมาย](#ส่วนที่-2--ผู้โจมตีเริ่มจากเรียนรู้เป้าหมาย)**

- สองประตู: **remote login** (หาชื่อผู้ใช้และรหัสผ่าน) และ **remote exploit** (หาบริการที่มีช่องโหว่)
- ข้อมูลทางสังคมจาก **whois** — `.th` ที่ THNIC, `.com` ที่ ICANN · เจาะอีเมลที่ใช้จดโดเมนได้ ก็ไปถึงตัวโดเมน
- ข้อมูลเครือข่ายจาก **Wireshark, tcpdump, Snort, Nmap**
- **Nmap** หา port และบริการที่เปิด, OS fingerprint และแผนที่เครือข่าย · `-sV` ได้ชื่อและรุ่นของโปรแกรม
- Nmap อยู่ในภาพยนตร์ Matrix Reloaded, Ocean's 8, Elysium
- **การสแกนอาจทำให้สัญญาณเตือนดังและถูกบล็อก**
- ได้รุ่นแล้วไปค้นช่องโหว่ใน **CERT** บางทีได้สคริปต์ฟรีด้วย · **script kiddie** คือคนที่รันสคริปต์ของคนอื่นโดยไม่เข้าใจ

**[ปลอมที่อยู่บน header](#ส่วนที่-3--เขียนที่อยู่บน-header-เอง-โจมตีโดยไม่เผยตัว)**

- สร้าง packet เองได้ ก็เขียนที่อยู่ผู้ส่งและผู้รับเองได้
- **IP spoofing** — คำตอบวิ่งไปหาเจ้าของที่อยู่ ใช้ได้กับงานที่ไม่ต้องรอคำตอบ หรือเหยื่อที่เชื่อจากที่อยู่
- **ARP/MAC spoofing** — ARP reply ปลอมทำให้ frame ที่จะไป gateway วิ่งผ่านผู้โจมตี เป็น man-in-the-middle ใน LAN · MAC spoofing ตั้ง MAC ของตัวเองให้ตรงกับเครื่องอื่น
- **DDoS ด้วยคำขอที่ปลอมต้นทาง** — หลอกเซิร์ฟเวอร์ UDP ให้ส่งคำตอบจริงไปถล่มเหยื่อ เหยื่อไม่เห็นผู้โจมตี (reflection) · คำตอบใหญ่กว่าคำขอหลายเท่า (amplification)

**[DNS poisoning](#ส่วนที่-4--dns-poisoning-โปรโตคอลที่ออกแบบมาให้ทำงาน)**

- **โปรโตคอลจำนวนมากออกแบบมาให้ทำงาน ไม่ใช่ให้ปลอดภัย**
- local DNS server รับคำตอบใบแรกที่ transaction ID ตรง ไม่ตรวจว่าใครส่ง
- ผู้โจมตีถามเอง แล้วยิงคำตอบปลอมที่เดา ID แข่งกับ master DNS server · ชนะแล้ว cache จำ `NiceBank.com = 5.5.5.5` ทุกคนที่ใช้ server นั้นไปเว็บปลอม
- นี่คือ **pharming** — พิมพ์ชื่อเว็บถูกก็ยังโดน

**[ป้องกัน](#ส่วนที่-5--ป้องกันด้วยระบบ-คน-และซอฟต์แวร์)**

- **ระบบ:** firewall, patches/updates, system hardening, encryption — **การเข้ารหัสยังแพ้การวิเคราะห์ทางสถิติได้**
- **คน:** awareness
- **ซอฟต์แวร์:** secure by design
- **เรียนรู้ระบบของตัวเอง เจาะมันก่อนที่คนอื่นจะเจาะ**

<Quiz question="เครื่องหนึ่งรับคำสั่งผ่าน UDP จากเครื่องที่มันไว้ใจ โดยดูแค่ source IP ผู้โจมตีปลอม source IP เป็นของเครื่องที่ถูกไว้ใจ ต้องเห็นคำตอบไหม คำสั่งถึงจะทำงาน">
UDP ไม่มี handshake เครื่องปลายทางทำตามคำสั่งทันทีที่ได้ packet ใบเดียว ไม่มีเลขสุ่มให้ต้องส่งคืน คำตอบจะวิ่งไปหาเครื่องที่ถูกไว้ใจ แต่คำสั่งทำงานไปแล้ว

คำตอบคือ **ไม่ต้องเห็น** ผู้โจมตีพลาดแค่ผลลัพธ์ที่เครื่องตอบกลับ ไม่ได้พลาดตัวคำสั่ง

คำตอบที่ผิดบ่อยคือ "ต้องได้คำตอบ ถึงจะคุยต่อได้" ซึ่งเป็นปัญหาของ TCP เท่านั้น เพราะ TCP handshake ต้องส่งเลขสุ่มจากคำตอบคืนก่อน การเชื่อมต่อถึงจะเริ่ม
</Quiz>

<Quiz question="ผู้โจมตีใน LAN ส่ง ARP reply ปลอมให้เครื่องของเหยื่ออย่างเดียว ไม่ได้ส่งให้ gateway ผู้โจมตีจะเห็นอะไร">
ARP cache ของเหยื่อจับคู่ IP ของ gateway กับ MAC ของผู้โจมตี frame ที่เหยื่อส่งออกจึงวิ่งผ่านผู้โจมตี แต่ ARP cache ของ gateway ยังจับคู่ IP ของเหยื่อกับ MAC จริง frame ขากลับจึงวิ่งตรงถึงเหยื่อ

คำตอบคือ **เห็นแค่ขาไป** คือสิ่งที่เหยื่อส่งออกอินเทอร์เน็ต ไม่เห็นสิ่งที่ตอบกลับมา

คำตอบที่ผิดบ่อยคือ "เห็นทั้งหมด เพราะอยู่ตรงกลางแล้ว" ซึ่งลืมว่าแต่ละเครื่องเลือกทางส่งจาก ARP cache ของตัวเอง ผู้โจมตีต้องหลอก cache ทั้งสองฝั่งถึงจะอยู่ตรงกลางจริง
</Quiz>

<Quiz question="local DNS server มีคำตอบของ NiceBank.com อยู่ใน cache แล้ว และยังไม่หมดอายุ ผู้โจมตียิงคำตอบปลอมที่เดา ID ไปหลายพันใบตอนนี้ จะได้ผลไหม">
server ตอบชื่อนี้จาก cache ทันที จึงไม่ได้ถาม master DNS server และไม่มีคำถามไหนรอคำตอบอยู่ คำตอบปลอมทุกใบจึงไม่มี ID ให้จับคู่ และถูกทิ้งหมด

คำตอบคือ **ไม่ได้ผล** ผู้โจมตีต้องรอจนคำตอบใน cache หมดอายุ หรือถามชื่อย่อยที่ไม่มีอยู่จริง เพื่อให้ server ต้องไปถามต่อ

คำตอบที่ผิดบ่อยคือ "ยิงมากพอก็ต้องมีใบที่ ID ตรง" ซึ่งใช้ได้เฉพาะตอนที่ server กำลังรอคำตอบอยู่ ไม่มีคำถามก็ไม่มี ID ที่ถูกให้เดา
</Quiz>
