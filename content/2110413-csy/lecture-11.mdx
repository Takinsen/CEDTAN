<KeyIdea>
โปรโตคอลเครือข่ายรุ่นแรกถูกออกแบบมาให้ **ทำงานได้ ไม่ได้ออกแบบมาให้ปลอดภัย** แต่ละชั้นเชื่อสิ่งที่อีกเครื่องบอกมาโดยไม่ตรวจ ผู้โจมตีจึงเริ่มจากเรียนรู้เป้าหมาย แล้วเขียนที่อยู่ปลอมลงบนแพ็กเก็ตเพื่อหายตัว หรือตอบคำถามแทนเครื่องจริงอย่างใน DNS poisoning ทางป้องกันจึงต้องครบทั้งระบบ คน และซอฟต์แวร์ และต้องเจาะระบบของตัวเองให้เจอก่อนคนอื่น
</KeyIdea>

## ส่วนที่ 1 — เครือข่ายคือโปรโตคอลหลายชั้นที่เชื่อกันเอง

### เปิดเว็บหนึ่งหน้า ต้องเชื่อคนอื่นกี่ครั้ง

<Why>
ลองนึกถึงการพิมพ์ `nicebank.com` ลงในเบราว์เซอร์หนึ่งครั้ง

ก่อนหน้าเว็บจะขึ้น เครื่องเราต้องถามเครื่องอื่นว่าชื่อนี้อยู่ที่เลขที่อยู่อะไร ถามเครื่องใน <Term en="LAN" th="วงแลน คือเครือข่ายวงเล็กในบ้าน ร้าน หรือออฟฟิศ ที่เครื่องต่อถึงกันตรง ๆ" /> ว่า <Term en="Gateway" th="เครื่องที่เป็นทางออกจากวงแลนไปอินเทอร์เน็ต" /> อยู่ที่ไหน ฝากแพ็กเก็ตให้ <Term en="Router" th="เครื่องที่ส่งต่อแพ็กเก็ตจากเครือข่ายหนึ่งไปอีกเครือข่ายหนึ่ง" /> หลายตัวส่งต่อกันไป แล้วรอคำตอบที่อ้างว่ามาจากธนาคาร

ทุกขั้นเชื่อคำตอบของเครื่องอื่น ถ้าขั้นไหนได้คำตอบที่โกหก ขั้นที่เหลือทั้งหมดก็ทำงานถูกต้องทุกอย่างบนข้อมูลที่ผิด
</Why>

<Term en="Protocol" th="ข้อตกลงว่าสองเครื่องจะคุยกันด้วยข้อความหน้าตาแบบไหน" /> แต่ละตัวทำงานเดียว และวางซ้อนกันเป็นชั้น ชั้นบนเรียกใช้ชั้นล่าง เครือข่ายแบบ <Term en="TCP/IP" th="ชุดโปรโตคอลที่อินเทอร์เน็ตใช้" /> **เป็นระบบที่ซับซ้อนมาก มันพึ่งบริการและโปรโตคอลที่เกี่ยวข้องกันจำนวนมาก จึงมีหลายจุดที่พังได้**

ชั้นมีสองแบบที่ใช้เรียกกัน <Term en="OSI Model" th="แบบจำลองเครือข่ายเจ็ดชั้น" /> แบ่งไว้เจ็ดชั้น ส่วน **TCP/IP Model** ยุบสามชั้นบนของ OSI คือ Application, Presentation และ Session ลงเป็นชั้น Application ชั้นเดียว เหลือห้าชั้น โปรโตคอลที่วางอยู่บนแต่ละชั้นมีดังนี้ โดยตารางรวม Data link กับ Physical ไว้ในแถวเดียว

| ชั้น | โปรโตคอล | งาน |
| --- | --- | --- |
| Application | Telnet, FTP, SMTP, DNS, RIP, SNMP | งานที่ผู้ใช้หรือระบบต้องการจริง เช่นล็อกอินระยะไกล ส่งไฟล์ ส่งอีเมล แปลงชื่อเป็นที่อยู่ |
| Transport | TCP, UDP | ส่งข้อมูลถึงโปรแกรมที่ถูกตัว TCP ส่งครบและเรียงลำดับ ส่วน UDP ส่งทีละก้อนโดยไม่รับประกัน |
| Network | IP, ARP, IGMP, ICMP | หาทางส่งแพ็กเก็ตข้ามเครือข่ายไปถึงเครื่องปลายทาง |
| Data link และ Physical | Ethernet, Token Ring, Frame Relay, ATM | ส่งสัญญาณจริงบนสายหรือคลื่น ระหว่างเครื่องที่ต่อกันโดยตรง |

ในรูปที่ 1 Telnet, FTP และ SMTP วิ่งบน TCP ส่วน DNS, RIP และ SNMP วิ่งบน UDP คอลัมน์ "งาน" ในตารางเป็นคำอธิบายเสริม

<Detail label="โปรโตคอลในตารางที่หน้านี้ไม่ได้ใช้ต่อ แต่ละตัวทำอะไร">
| โปรโตคอล | ชั้น | ทำอะไร |
| --- | --- | --- |
| RIP (Routing Information Protocol) | Application | ให้ router บอกเส้นทางที่ตัวเองรู้ให้ router ข้างเคียงรู้ |
| SNMP (Simple Network Management Protocol) | Application | ให้ผู้ดูแลอ่านสถานะและตั้งค่าอุปกรณ์เครือข่ายจากระยะไกล |
| IGMP (Internet Group Management Protocol) | Network | ให้เครื่องแจ้ง router ว่าขอรับแพ็กเก็ตที่ส่งถึงกลุ่ม (multicast) ไหน |
| ICMP (Internet Control Message Protocol) | Network | ส่งข้อความแจ้งปัญหาและข้อความควบคุม เช่นส่งไม่ถึงปลายทาง และ `ping` |
| Token Ring | Data link | วงแลนแบบวงแหวนที่ส่ง token ต่อกันเป็นทอด เครื่องที่ถือ token อยู่เท่านั้นที่ส่งได้ |
| Frame Relay | Data link | บริการเช่าสายรุ่นเก่าของผู้ให้บริการ ใช้ต่อเครือข่ายของสาขาที่อยู่ไกลกัน |
| ATM (Asynchronous Transfer Mode) | Data link | ส่งข้อมูลเป็นก้อนขนาดตายตัว 53 ไบต์ ใช้ในเครือข่ายหลักของผู้ให้บริการโทรคมนาคม |

ทั้งตารางนี้เป็นข้อมูลเสริม
</Detail>

### ส่วนหัวของแพ็กเก็ตคือซองจดหมาย

<Why>
คำขอเปิด `nicebank.com` ต้องผ่าน router หลายตัวกว่าจะถึงเครื่องของธนาคารที่ `1.1.1.1` และพอถึงเครื่องนั้นแล้ว ก็ยังต้องไปถึงโปรแกรมเว็บ ไม่ใช่โปรแกรมอื่นที่รันอยู่บนเครื่องเดียวกัน

router แต่ละตัว และตัวเครื่องปลายทาง รู้ได้ยังไงว่าต้องส่งข้อมูลก้อนนี้ต่อไปที่ไหน
</Why>

ข้อมูลทุกก้อนที่วิ่งบนเครือข่ายถูกหั่นเป็น <Term en="Packet" th="ก้อนข้อมูลหนึ่งก้อนที่ส่งบนเครือข่าย" /> แต่ละก้อนมี <Term en="Header" th="ส่วนหัวที่บอกว่าแพ็กเก็ตมาจากไหนและไปไหน" /> อยู่ข้างหน้า และเนื้อข้อมูลอยู่ข้างหลัง

ใน header มีของสองอย่างที่หน้านี้ใช้ตลอด

- <Term en="IP Address" th="เลขที่อยู่ของเครื่องบนเครือข่าย" /> ของผู้ส่งและผู้รับ เช่น `2.2.2.2` บอกว่าเป็นเครื่องไหน
- <Term en="Port" th="เลขช่องที่บอกว่าข้อมูลเป็นของโปรแกรมไหนบนเครื่องนั้น" /> ของผู้ส่งและผู้รับ บอกว่าเป็นโปรแกรมไหนบนเครื่องนั้น บริการที่รู้จักกันมีเลขประจำ เช่น `21` คือ FTP สำหรับส่งไฟล์, `22` คือ SSH สำหรับล็อกอินระยะไกลแบบเข้ารหัส, `23` คือ Telnet สำหรับล็อกอินระยะไกลแบบไม่เข้ารหัส และ `80` คือเว็บ

<Analogy>
**ส่วนหัวของแพ็กเก็ตก็เหมือนซองจดหมาย**

- ที่อยู่ผู้รับหน้าซอง คือ destination IP address
- ชื่อคนในบ้านที่จะรับจดหมาย คือ destination port
- ที่อยู่ผู้ส่งมุมซองที่ไว้ให้ตอบกลับ คือ source IP address
- จดหมายข้างใน คือเนื้อข้อมูล
- บุรุษไปรษณีย์ที่อ่านแค่หน้าซองแล้วส่งต่อ คือ router

ที่อยู่ผู้ส่งบนซองจริง ใครจะเขียนอะไรลงไปก็ได้ และบุรุษไปรษณีย์ก็ไม่เคยตรวจ แพ็กเก็ตก็เป็นแบบนั้นเหมือนกัน ซึ่งคือเรื่องของส่วนที่ 3

อุปมานี้ใช้ไม่ได้ตรงที่ **แพ็กเก็ตมีซองซ้อนกันหลายชั้น** ซองชั้นใน (IP) อยู่กับแพ็กเก็ตตั้งแต่ต้นทางถึงปลายทาง แต่ซองชั้นนอกสุดที่ใช้ส่งในวงแลน (Ethernet) ถูกแกะทิ้งแล้วเปลี่ยนซองใหม่ทุกครั้งที่ผ่าน router การปลอมซองชั้นนอกจึงได้ผลแค่ในวงแลนเดียว ประโยคนี้เป็นคำอธิบายเสริม
</Analogy>

<Quiz question="แพ็กเก็ตที่ขอหน้าเว็บของ nicebank.com ไปถึงเครื่อง 1.1.1.1 ของธนาคารถูกต้อง แต่ destination port ในส่วนหัวเขียนว่า 22 แทนที่จะเป็น 80 หน้าเว็บจะขึ้นไหม">
destination IP address เลือกแค่ว่าเป็น **เครื่องไหน** ส่วน destination port เลือกว่าเป็น **โปรแกรมไหน** บนเครื่องนั้น เครื่อง `1.1.1.1` จึงส่งข้อมูลก้อนนี้ให้โปรแกรมที่รออยู่ที่พอร์ต 22 ซึ่งคือ SSH และ SSH ไม่เข้าใจคำขอหน้าเว็บ

คำตอบคือ **หน้าเว็บไม่ขึ้น** คำขอไปถึงเครื่องที่ถูก แต่ไปผิดโปรแกรม

คำตอบที่ผิดบ่อยคือ "IP ถูกแล้วก็ถึงเว็บ" ซึ่งมองข้ามว่าเครื่องเดียวรันได้หลายโปรแกรม และที่อยู่ของเครื่องอย่างเดียวไม่ได้บอกว่าข้อมูลเป็นของโปรแกรมไหน
</Quiz>

## ส่วนที่ 2 — ผู้โจมตีเริ่มจากเรียนรู้เป้าหมาย

### สองประตูที่จะเข้าไปในเครื่อง

การเจาะระบบจากระยะไกลมีประตูหลักสองบาน

- <Term en="Remote Login" th="ล็อกอินเข้าเครื่องจากระยะไกลเหมือนผู้ใช้จริง" /> — **หาชื่อผู้ใช้และรหัสผ่านที่ใช้ได้** วิธีเดาและเจาะรหัสผ่านอยู่ใน [Lecture 3](/2110413-csy/lecture-3#ส่วนที่-5--วิธีที่คนใช้เจาะรหัสผ่าน)
- <Term en="Remote Exploit" th="ใช้ช่องโหว่ของโปรแกรมที่เปิดรับการเชื่อมต่อ เพื่อสั่งงานเครื่องนั้น" /> — **หาบริการที่มีช่องโหว่แล้วใช้ช่องนั้น**

ทั้งสองบานต้องเริ่มจากเรื่องเดียวกันคือ **เข้าใจเป้าหมาย** และ **หาช่องโหว่ที่คนรู้กันอยู่แล้ว** ประตูแรกต้องรู้ว่าใครมีบัญชีอยู่บ้าง ประตูที่สองต้องรู้ว่าเครื่องนั้นรันโปรแกรมอะไร รุ่นไหน

ข้อมูลที่ต้องหามีสองกลุ่ม คือ **ข้อมูลทางสังคม** ว่าใครเป็นเจ้าของ ติดต่อทางไหน และ **ข้อมูลเครือข่ายและสภาพแวดล้อม** ว่ามีเครื่องอะไร เปิดบริการอะไร

### ข้อมูลทางสังคมจาก whois

<Why>
ถ้าจะหลอกให้ใครกรอกรหัสผ่าน หรือเดารหัสผ่านของใคร เราต้องรู้ก่อนว่าคนคนนั้นคือใคร ใช้อีเมลอะไร และทำงานกับบริษัทไหน

สำหรับเว็บไซต์ ข้อมูลชุดนี้มีคนจดไว้ให้แล้วตอนจดทะเบียนชื่อโดเมน
</Why>

<Term en="WHOIS" th="บริการค้นว่าใครเป็นผู้จดทะเบียนชื่อโดเมน" /> คือบริการที่ตอบว่าโดเมนหนึ่งจดทะเบียนกับใคร และใครเป็นผู้ติดต่อ แต่ละโดเมนค้นได้จากที่ต่างกัน

- **โดเมน `.th`** ค้นที่ THNIC (Thai Network Information Center) ผู้ดูแลทะเบียนโดเมน `.th` — [https://www.thnic.co.th/th/whois/](https://www.thnic.co.th/th/whois/)
- **โดเมน `.com`** ค้นที่ ICANN (Internet Corporation for Assigned Names and Numbers) องค์กรที่ประสานระบบชื่อโดเมนของทั้งโลก และรับรอง registrar ที่ขายโดเมน `.com` — [https://whois.icann.org/](https://whois.icann.org/)

คำขยายชื่อ THNIC และ ICANN เป็นข้อมูลเสริม

<Example title="ข้อมูล whois ของโดเมนหนึ่ง">
| ช่อง | ค่า |
| --- | --- |
| Registrar | GoDaddy.com, LLC |
| IANA ID | 146 |
| Abuse Contact Email | `abuse@godaddy.com` |
| Registrant | Deverhood Co.,Ltd — Bangkok, Thailand |
| Technical | Deverhood Co.,Ltd — Bangkok, Thailand |
| Administrative | Deverhood Co.,Ltd |

<Term en="Registrar" th="บริษัทที่รับจดทะเบียนชื่อโดเมน" /> คือบริษัทที่เรามาเช่าชื่อโดเมนด้วย ส่วน Registrant, Technical และ Administrative คือผู้ติดต่อสามบทบาทของโดเมนนั้น คือเจ้าของ คนดูแลด้านเทคนิค และคนดูแลด้านธุรการ IANA ID คือเลขประจำตัวที่ IANA (หน่วยงานที่ดูแลเลขและชื่อกลางของอินเทอร์เน็ต) ออกให้ registrar แต่ละรายที่ ICANN รับรอง และ Abuse Contact Email คืออีเมลของ registrar สำหรับแจ้งว่าโดเมนถูกใช้ทำผิด เช่นส่งสแปมหรือทำเว็บ phishing ประโยคเรื่อง IANA ID และ Abuse Contact Email เป็นคำอธิบายเสริม
</Example>

ข้อมูลแค่นี้เปิดทางโจมตีได้ทั้งสาย สมมติว่าเรารู้ว่าโดเมนหนึ่งจดทะเบียนกับ GoDaddy.com ด้วยอีเมลหนึ่ง **การเจาะอีเมลนั้นได้ จะพาเราไปถึงตัวโดเมน** เพราะบัญชีที่ registrar มักกู้รหัสผ่านผ่านอีเมลนั้น และใครที่เข้าบัญชีที่ registrar ได้ ก็เปลี่ยนได้ว่าชื่อโดเมนนี้ชี้ไปที่เครื่องไหน คนทั้งโลกที่พิมพ์ชื่อเว็บนั้นจะถูกพาไปที่เครื่องของผู้โจมตี ขั้นตอนตั้งแต่การกู้รหัสผ่านเป็นคำอธิบายเสริม

ตัวอีเมลเองถูกเจาะได้ด้วยวิธีที่เล่นงานคน อย่าง [phishing](/2110413-csy/lecture-1#phishing) และ [social engineering](/2110413-csy/lecture-1#social-engineering) ใน Lecture 1

<Callout type="info" title="whois วันนี้ปิดข้อมูลส่วนตัวไว้มากขึ้น">
ตั้งแต่กฎหมายคุ้มครองข้อมูลส่วนบุคคลของยุโรป (GDPR) มีผลในปี 2018 registrar ส่วนใหญ่ซ่อนชื่อ อีเมล และเบอร์โทรของผู้จดทะเบียนที่เป็นบุคคลไว้ ข้อมูลของบริษัทและของ registrar ยังเห็นได้เหมือนในตัวอย่าง กล่องนี้เป็นข้อมูลเสริม
</Callout>

### ข้อมูลเครือข่าย — ดักดูแพ็กเก็ต และสแกนพอร์ต

<Why>
ประตูที่สองต้องรู้ว่าเครื่องเป้าหมายรันโปรแกรมอะไร รุ่นไหน ซึ่งเจ้าของเครื่องไม่ได้ประกาศไว้ให้ใครอ่าน

ทางหาคำตอบมีสองแบบ คือฟังแพ็กเก็ตที่วิ่งอยู่แล้ว กับเคาะประตูเครื่องเป้าหมายเองแล้วดูว่ามันตอบอะไร
</Why>

วิธีหาข้อมูลเครือข่ายและสภาพแวดล้อมมีหลายทาง เครื่องมือแบบฟังมีเช่น

- <Term en="Packet Sniffer" th="โปรแกรมดักดูแพ็กเก็ตที่วิ่งผ่านการ์ดเครือข่าย" /> อย่าง **Wireshark** ที่แสดงแพ็กเก็ตเป็นหน้าจอให้คลิกดูทีละชั้น
- **tcpdump** ที่ดักแพ็กเก็ตแบบเดียวกันแต่พิมพ์ออกมาเป็นบรรทัด
- **Snort** ที่รู้จักกันในฐานะ IDS ใน [Lecture 5](/2110413-csy/lecture-5#ส่วนที่-4--เอาไปจับผู้บุกรุก) ซึ่งมีโหมดดักดูแพ็กเก็ตเฉย ๆ ด้วย (`snort -v` ข้อนี้เป็นข้อมูลเสริม)

ส่วนเครื่องมือแบบเคาะคือ <Term en="Nmap" th="โปรแกรมสแกนเครือข่าย หาเครื่อง พอร์ตที่เปิด และรุ่นของบริการ" /> ที่ส่งแพ็กเก็ตไปหาเครื่องและพอร์ตต่าง ๆ แล้วดูว่าอะไรตอบกลับมา

sniffer เห็นเฉพาะแพ็กเก็ตที่วิ่งผ่านการ์ดเครือข่ายของเครื่องตัวเอง ในวงแลนที่ใช้สวิตช์ แพ็กเก็ตของคนอื่นจะไม่ผ่านมาเลย ข้อจำกัดนี้คือเหตุผลที่ ARP spoofing ในส่วนที่ 3 มีประโยชน์กับผู้โจมตี ย่อหน้านี้เป็นคำอธิบายเสริม

### Nmap เผยหน้าตาของเครือข่าย

**Nmap ใช้ทำแผนที่เครือข่ายของเป้าหมายได้** ข้อมูลที่ได้มีเช่น

- **บริการและพอร์ตที่เปิดอยู่** แต่ละพอร์ตที่เปิดคือประตูหนึ่งบานที่มีโปรแกรมรอรับอยู่
- <Term en="OS Fingerprint" th="การเดาระบบปฏิบัติการจากรายละเอียดเล็ก ๆ ที่ต่างกันในการตอบแพ็กเก็ต" /> แต่ละระบบปฏิบัติการตอบแพ็กเก็ตแปลก ๆ ไม่เหมือนกัน nmap เอาความต่างนั้นไปเทียบกับฐานข้อมูลเพื่อเดาว่าเครื่องนั้นรันอะไร

**Zenmap** ซึ่งเป็นหน้าต่างกราฟิกของ nmap วาดผลสแกนออกมาเป็นแผนที่ได้ ตัวอย่างคือคำสั่ง `nmap -T4 -A -F -PN` ที่สแกน `www.google.com`, `www.facebook.com`, `twitter.com`, `microsoft.com`, `insecure.org`, `slashdot.org` และเว็บอื่นอีกหลายเว็บพร้อมกัน ความหมายของแต่ละตัวเลือกข้างล่างเป็นข้อมูลเสริม

- `-T4` สแกนเร็วขึ้น `-F` สแกนแค่พอร์ตที่พบบ่อย และ `-PN` ข้ามขั้นถามว่าเครื่องเปิดอยู่ไหม
- `-A` เปิดหลายอย่างพร้อมกัน คือเดาระบบปฏิบัติการ ถามรุ่นของบริการ รันสคริปต์ตรวจ และไล่เส้นทางว่าแพ็กเก็ตผ่าน router ตัวไหนบ้าง

แท็บ Topology เอาเส้นทางที่ไล่ได้มาวาด เครื่องของเราอยู่ตรงกลาง แต่ละเป้าหมายอยู่บนวงแหวนตามจำนวน router ที่ต้องผ่าน และจุดเล็ก ๆ ระหว่างทางคือ router แต่ละตัว เป้าหมายที่ใช้ router ร่วมกันจะแตกกิ่งออกจากเส้นเดียวกัน ผลที่ได้คือแผนที่ว่าเป้าหมายแต่ละตัวอยู่หลังอะไรบ้าง ส่วนรายการเครื่องข้างแผนที่มีไอคอนบอกระบบปฏิบัติการที่เดาได้

<Example added title="สแกนเครื่องตัวเองด้วย nmap">
สไลด์ไม่ได้แสดงวิธีอ่านผลสแกน ตัวอย่างนี้จึงเปิดเว็บเซิร์ฟเวอร์ของ Python ทิ้งไว้ที่พอร์ต 8080 บน `127.0.0.1` แล้วสแกนห้าพอร์ตสองแบบ คือไม่ใส่และใส่ `-sV`

```bash
python3 -m http.server 8080 --bind 127.0.0.1
nmap -p 21,22,23,80,8080 127.0.0.1
```

ลองทายก่อน: ถ้าไม่ใส่ `-sV` nmap จะบอกว่าพอร์ต 8080 รันอะไร

```text
8080/tcp open   http-proxy
```

```bash
nmap -sV -p 21,22,23,80,8080 127.0.0.1
```

```text
8080/tcp open   http    SimpleHTTPServer 0.6 (Python 3.14.4)
```

`http-proxy` เป็นแค่ชื่อที่ตารางของ nmap ผูกไว้กับเลข 8080 โดยไม่ได้ถามโปรแกรมเลย ส่วน `-sV` สั่งให้ nmap คุยกับบริการที่เปิดอยู่จนได้ชื่อโปรแกรมและรุ่นจริงมา

<Detail label="ผลของทั้งสองแบบ และการเดาระบบปฏิบัติการ">
ตัดบรรทัดหัวและท้ายที่ nmap พิมพ์ทุกครั้งออก (Starting Nmap…, Nmap scan report…, Host is up…, Nmap done…)

`closed` แปลว่าเครื่องตอบกลับมาว่าไม่มีโปรแกรมรออยู่ที่พอร์ตนั้น ส่วน `open` แปลว่ามี

การเดาระบบปฏิบัติการด้วย `-O` ต้องใช้สิทธิ์ผู้ดูแลระบบ เพราะต้องสร้างแพ็กเก็ตแปลก ๆ เอง ถ้ารันด้วยผู้ใช้ธรรมดา nmap จะตอบว่า

ผลทั้งหมดนี้ได้จาก nmap 7.98

### อย่าให้สัญญาณเตือนดัง

**การรัน nmap บนเครือข่ายอาจทำให้สัญญาณเตือนดัง ต้องระวัง เพราะอาจถูกบล็อก** ผู้สอนวิชานี้เคยเผลอรัน nmap บนเครือข่ายของโรงแรม แล้วถูกบล็อกจนต้องโทรให้ฝ่ายไอทีของโรงแรมปลดบล็อกให้ถึงจะใช้เครือข่ายได้อีก

<Why>
ผู้ใช้ธรรมดาไม่เคยเคาะประตูเครื่องเดียวทีละหลายสิบพอร์ตในเวลาไม่กี่วินาที รูปแบบนี้จึงเป็น signature ที่ [IDS](/2110413-csy/lecture-5#ส่วนที่-4--เอาไปจับผู้บุกรุก) จับได้ง่าย และถ้าเครือข่ายนั้นมี IPS ที่เปิดโหมดบล็อกไว้ มันอาจตัดเครื่องที่สแกนออกทันที

นอกจากนี้ การถามรุ่นด้วย `-sV` ทิ้งร่องรอยไว้ใน log ของบริการที่ถูกถามด้วย
</Why>

<Detail label="log ของเว็บเซิร์ฟเวอร์ระหว่างถูกสแกนด้วย -sV">
นี่คือบางบรรทัดใน log ของเว็บเซิร์ฟเวอร์ Python ในตัวอย่างข้างบน ระหว่างที่ nmap ถามรุ่น

```text
127.0.0.1 - - [12/Nov/2026 15:03:43] "POST /sdk HTTP/1.1" 501 -
127.0.0.1 - - [12/Nov/2026 15:03:43] "GET /nmaplowercheck1794470623 HTTP/1.1" 404 -
127.0.0.1 - - [12/Nov/2026 15:03:43] "GET /HNAP1 HTTP/1.1" 404 -
127.0.0.1 - - [12/Nov/2026 15:03:43] "GET /evox/about HTTP/1.1" 404 -
```

คำขอทั้งหมดมาในวินาทีเดียวกัน และบรรทัดที่สองมีคำว่า `nmap` อยู่ในตัวเลย คนที่อ่าน log หรือกฎของ IDS ที่หาคำนี้ จะรู้ทันทีว่าเครื่องถูกสแกน
</Detail>

ชื่อและรุ่นของโปรแกรม คือสิ่งที่ผู้โจมตีเอาไปค้นต่อในหัวข้อถัดไป

### ปักหมุดเป้าหมาย — ช่องโหว่ที่คนรู้กันอยู่แล้ว

<Why>
สมมติ nmap ตอบว่าพอร์ต 80 ของเป้าหมายรัน Apache httpd 2.2.15 ซึ่งเป็นโปรแกรมเว็บเซิร์ฟเวอร์ที่ใช้กันแพร่หลาย

ผู้โจมตีจะรู้ได้ยังไงว่ารุ่นนี้มีช่องโหว่อะไรบ้าง โดยไม่ต้องนั่งหาช่องโหว่เองตั้งแต่ศูนย์
</Why>

**เมื่อรู้แล้วว่าเป้าหมายเปิดพอร์ตอะไร รันบริการอะไร และใช้ระบบปฏิบัติการอะไร ก็ไปค้นช่องโหว่ที่รู้กันอยู่แล้วได้จากฐานข้อมูลสาธารณะ เช่น <Term en="CERT" th="หน่วยงานที่รวบรวมและประกาศช่องโหว่ด้านความปลอดภัย" />** และ **บางครั้งก็ได้สคริปต์ฟรีมาให้ลองด้วย**

ฐานข้อมูลนี้เปิดให้ทุกคนอ่าน เพราะคนที่ต้องรู้มากที่สุดคือผู้ดูแลระบบที่ต้องไปลง <Term en="Patch" th="ชุดแก้ไขที่ผู้ผลิตออกมาปิดช่องโหว่" /> แต่รายการเดียวกันก็บอกผู้โจมตีด้วยว่าจะยิงตรงไหน เวลาระหว่างวันที่ช่องโหว่ถูกประกาศ กับวันที่เครื่องของเราลงแพตช์ จึงเป็นช่วงที่อันตรายที่สุด ย่อหน้านี้เป็นคำอธิบายเสริม

### Script kiddie คืออะไร

สไลด์ตั้งคำถามว่า **What is Script kiddie?** ไว้โดยไม่ได้ตอบ คำตอบข้างล่างเป็นข้อมูลเสริม

<Term en="Script Kiddie" th="คนที่โจมตีด้วยสคริปต์สำเร็จรูปของคนอื่นโดยไม่เข้าใจว่ามันทำงานยังไง" /> คือคนที่เอาสคริปต์ฟรีที่ว่าข้างบนมารัน ทั้งที่ไม่รู้ว่าช่องโหว่คืออะไร และสคริปต์ทำอะไรกับเครื่องเป้าหมาย คำนี้ใช้ในเชิงดูถูก แต่ความเสียหายที่คนกลุ่มนี้ทำได้เป็นของจริง เพราะสคริปต์ทำงานได้ไม่ว่าคนกดจะเข้าใจหรือไม่

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **เว็บของเราเล็ก ไม่มีข้อมูลมีค่า ไม่มีใครเสียเวลามาเจาะหรอก**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะเราคิดว่าผู้โจมตีเลือกเป้าหมายก่อน แล้วค่อยหาวิธีเจาะ คนที่เก่งพอจะเขียนช่องโหว่เองก็มักทำแบบนั้นจริง

สิ่งที่ถูกต้องคือ **script kiddie เลือกสคริปต์ก่อน แล้วค่อยหาเป้าหมาย** สคริปต์สำหรับ `VU#405811` ใช้ได้กับทุกเครื่องที่รัน Apache รุ่นที่มีช่องโหว่ สิ่งที่ต้องทำก็แค่สแกนหาเครื่องที่ตอบรุ่นนั้นกลับมาให้ได้มากที่สุด เว็บของเราถูกเลือกเพราะบรรทัด `VERSION` ไม่ใช่เพราะมีค่า
</Pitfall>

### Nmap ในภาพยนตร์ — ทั้งสายในฉากเดียว

**Nmap เคยปรากฏในภาพยนตร์หลายเรื่อง** เช่น **Matrix Reloaded**, **Ocean's 8** และ **Elysium** รายชื่อทั้งหมดอยู่ที่ [https://nmap.org/movies/](https://nmap.org/movies/)

ฉากใน Matrix Reloaded เดินครบทั้งสายของส่วนนี้ในจอเดียว ตั้งแต่สแกนหาบริการ ไปจนถึงใช้ช่องโหว่ที่รู้กันอยู่แล้ว คำสั่ง nmap ในฉากเป็นคำสั่งจริง ส่วน `sshnuke` เป็นโปรแกรมของภาพยนตร์ บรรทัดข้างล่างตัดมาเฉพาะที่ตัดสิน บรรทัดที่ตัดออกคือเลขรุ่นของ nmap คำเตือนเรื่อง TCP sequencing รายงานพอร์ตที่ปิดอยู่ หัวตาราง และบรรทัดสรุปตอนจบ

```text
# nmap -v -sS -O 10.2.2.2
Interesting ports on 10.2.2.2:
22/tcp     open     ssh
No exact OS matches for host
# sshnuke 10.2.2.2 -rootpw="Z1ON0101"
Connecting to 10.2.2.2:ssh ... successful.
Attempting to exploit SSHv1 CRC32 ... successful.
Reseting root password to "Z1ON0101".
System open: Access Level <9>
# ssh 10.2.2.2 -l root
root@10.2.2.2's password:
```

nmap บอกว่ามีพอร์ต 22 ที่รัน SSH เปิดอยู่ ตัวละครเลือกโปรแกรมที่ใช้ช่องโหว่ของ SSH version 1 แล้วตั้งรหัสผ่านของ root ใหม่

ในคำสั่ง nmap ตัวเลือก `-v` ให้รายงานละเอียดขึ้น `-sS` ส่งแค่คำขอเชื่อมต่อแรกของ TCP ไปเคาะแต่ละพอร์ตโดยไม่ต่อให้ครบ และ `-O` เดาระบบปฏิบัติการ ซึ่งบรรทัด `No exact OS matches for host` คือผลของมัน สองตัวเลือกหลังต้องสร้างแพ็กเก็ตเอง จึงต้องรันเป็น root คือบัญชีผู้ดูแลระบบสูงสุดของ Unix ซึ่งพรอมต์ `#` บอกไว้ ส่วน CRC32 คือค่าตรวจว่าข้อมูลเพี้ยนไหมที่ SSH version 1 ใช้ และโค้ดที่ SSH ใส่ไว้กันการโจมตีผ่าน CRC32 นั้นมีบั๊กที่ให้ผู้โจมตีรันโค้ดบนเครื่องได้ เป็นช่องโหว่จริงที่ประกาศในปี 2001 ย่อหน้านี้เป็นข้อมูลเสริม

<Quiz question="nmap บอกว่าเครื่องหนึ่งเปิดพอร์ต 22 ที่รัน OpenSSH รุ่นล่าสุด และพอร์ต 80 ที่รัน Apache httpd 2.2.15 ผู้โจมตีจะเลือกประตูไหน และใช้ข้อมูลอะไรต่อ">
ประตู remote login ผ่าน SSH ต้องมีชื่อผู้ใช้และรหัสผ่าน ซึ่งยังไม่มี และ OpenSSH รุ่นล่าสุดน่าจะยังไม่มีช่องโหว่ที่ประกาศแล้ว ส่วน Apache 2.2.15 เป็นรุ่น 2.x ที่ตรงกับ `VU#405811` ในตารางข้างบนพอดี แต่ช่องโหว่นั้นเป็น DoS ผ่าน Range header คือทำให้เซิร์ฟเวอร์ล่มได้ ไม่ได้ให้สั่งงานเครื่อง

คำตอบคือ **เลือกประตู remote exploit ที่พอร์ต 80** เอารุ่น 2.2.15 ไปค้นในฐานข้อมูลช่องโหว่ต่อ เพื่อหาช่องที่ให้รันโค้ดได้ ไม่ใช่แค่ทำให้ล่ม เพราะรุ่นเก่าขนาดนี้มักมีช่องโหว่ที่ประกาศแล้วหลายตัว ถ้าอยากลองประตู SSH ด้วย ก็ต้องย้อนไปหาข้อมูลทางสังคมก่อน ว่าใครน่าจะมีบัญชีบนเครื่องนี้

คำตอบที่ผิดบ่อยคือ "เดารหัสผ่าน SSH เพราะพอร์ต 22 เป็นประตูของผู้ดูแลระบบ" ซึ่งเป็นประตูที่ต้องใช้ข้อมูลมากที่สุดในกรณีนี้ และการเดารหัสผ่านซ้ำ ๆ ก็เป็นอีกรูปแบบที่ IDS จับได้ง่าย
</Quiz>

## ส่วนที่ 3 — เขียนที่อยู่บนซองเอง: โจมตีโดยไม่เผยตัว

**ผู้โจมตีทำตัวให้มองไม่เห็นได้** เหตุผลอยู่ที่ซองจดหมายในส่วนที่ 1 — **ส่วนหัวของแพ็กเก็ตก็เหมือนซองจดหมาย ถ้าเราสร้างแพ็กเก็ตเองได้ เราก็เขียนที่อยู่ผู้ส่งและผู้รับลงไปเองได้ตามใจ** การปลอมที่อยู่แบบนี้มีสองระดับ คือปลอม IP address และปลอมที่อยู่ที่ใช้ในวงแลน

### IP Spoofing — ปลอมที่อยู่ผู้ส่ง

<Why>
เครื่อง `2.2.2.2` ไว้ใจเครื่อง `3.3.3.3` จึงยอมให้ล็อกอินเข้ามาได้โดยไม่ต้องใส่รหัสผ่าน ผู้โจมตีที่นั่งอยู่ที่เครื่อง `1.1.1.1` อยากได้สิทธิ์เดียวกัน ที่อยู่ชุดนี้เป็นคนละสถานการณ์กับ `nicebank.com` ที่ `1.1.1.1` ในส่วนอื่นของหน้า

ถ้า `2.2.2.2` ตัดสินว่าใครเป็นใครจากที่อยู่ผู้ส่งบนซองอย่างเดียว ผู้โจมตีก็แค่ต้องเขียนที่อยู่นั้นลงไปเอง
</Why>

<Term en="IP Spoofing" th="การเขียนที่อยู่ผู้ส่งปลอมลงใน IP header" /> คือการส่งแพ็กเก็ตที่ source IP address ไม่ใช่ที่อยู่ของเราเอง

<Example added title="แพ็กเก็ตที่เขียนที่อยู่ผู้ส่งเอง">
สไลด์ไม่ได้แสดงว่าแพ็กเก็ตปลอมหน้าตาเป็นยังไง สคริปต์ Python จึงสร้างแพ็กเก็ตหนึ่งใบเป็นไบต์ลงไฟล์ให้ `tcpdump` อ่าน โดยผู้สร้างอยู่ที่ `1.1.1.1` แต่เขียนที่อยู่ผู้ส่งเป็น `3.3.3.3` และส่งไปที่พอร์ต 513 ของ `2.2.2.2`

```bash
tcpdump -nn -t -x -r spoof.pcap
```

```text
IP 3.3.3.3.1023 > 2.2.2.2.513: Flags [S], seq 1000, win 64240, length 0
0x0000:  4500 0028 0001 0000 4006 70c6 0303 0303
0x0010:  0202 0202 03ff 0201 0000 03e8 0000 0000
0x0020:  5002 faf0 a100 0000
```

ไบต์ `0303 0303` คือ source address `3.3.3.3` และ `0202 0202` ที่ตามมาคือ destination address `2.2.2.2` และ `Flags [S]` คือคำขอเชื่อมต่อแรกของ TCP (กล่องเรื่องการจับมือข้างล่างอธิบายต่อ)

<Detail label="อ่านแบบไม่มีไบต์ และไบต์ที่เหลือหมายถึงอะไร">
```bash
tcpdump -nn -t -r spoof.pcap
```

```text
IP 3.3.3.3.1023 > 2.2.2.2.513: Flags [S], seq 1000, win 64240, length 0
```

ทุกเครื่องที่อ่านแพ็กเก็ตนี้เห็นผู้ส่งเป็น `3.3.3.3` และ `1.1.1.1` ไม่ได้อยู่ตรงไหนในแพ็กเก็ตเลย ที่อยู่ทั้งสองช่องเป็นแค่ช่องสี่ไบต์ที่ผู้สร้างกรอกลงไป ไม่มีลายเซ็นหรืออะไรที่พิสูจน์ว่าเป็นของจริง `tcpdump -vv` รายงานว่า checksum ของแพ็กเก็ตนี้ `(correct)` คือแพ็กเก็ตถูกรูปแบบทุกอย่าง

`03ff` คือพอร์ตต้นทาง 1023 และ `0201` คือพอร์ตปลายทาง 513 ซึ่งเป็นพอร์ตของ rlogin บริการล็อกอินระยะไกลรุ่นเก่า ที่ยอมให้เครื่องที่อยู่ในรายชื่อเครื่องที่ไว้ใจเข้าได้โดยไม่ต้องใส่รหัสผ่าน
</Detail>
</Example>

ปัญหาของผู้โจมตีคือ **คำตอบวิ่งกลับไปหาเจ้าของที่อยู่ที่เขียนไว้ ไม่ใช่กลับมาหาคนส่ง** การปลอมที่อยู่จึงได้ผลกับงานสองแบบ คืองานที่ไม่ต้องการคำตอบ และงานที่เครื่องปลายทางเชื่อผู้ส่งจากที่อยู่อย่างเดียว

รูปที่ 2 คือกรณีที่สอง ซึ่งเป็นกรณีที่เปิดหัวข้อนี้ ผู้โจมตีส่งแพ็กเก็ตที่อ้างว่ามาจาก `3.3.3.3` เหยื่อ `2.2.2.2` ที่ไว้ใจเครื่องนั้นจึงยอมทำตาม ผลคือ **ช่องโหว่ด้านความปลอดภัยของเหยื่อ** ส่วนเครื่อง `3.3.3.3` ตัวจริง **อาจตกเป็นเป้าของการโจมตีแบบ DoS ไปด้วย**

<Callout type="info" title="ทำไมต้องยิงเครื่องที่ถูกอ้างชื่อให้ล่ม">
TCP ต้องจับมือกันก่อนคุย เรียกว่า <Term en="TCP Handshake" th="การจับมือสามขั้นที่ TCP ทำก่อนเริ่มส่งข้อมูล" /> ต้นทางส่งคำขอ ปลายทางตอบกลับพร้อมเลขสุ่มหนึ่งตัว แล้วต้นทางต้องส่งเลขนั้นคืนมาให้ถูก การเชื่อมต่อถึงจะเริ่มได้

ในรูปที่ 2 คำตอบที่มีเลขสุ่มวิ่งไปที่ `3.3.3.3` ตัวจริง ซึ่งจะตอบเหยื่อว่าไม่ได้ขออะไรเลย แล้วการเชื่อมต่อก็ถูกยกเลิก ผู้โจมตีจึงต้องยิง `3.3.3.3` ให้ล่มก่อน แล้วเดาเลขสุ่มนั้นเองโดยไม่เคยเห็นมัน กรณีจริงที่โด่งดังคือการเจาะเครื่องของ Tsutomu Shimomura โดย Kevin Mitnick ในปี 1994 ซึ่งใช้ครบทั้งสามขั้น คือยิงเครื่องที่ถูกไว้ใจให้ล่ม เดาเลขสุ่ม และส่งแพ็กเก็ตในนามเครื่องที่ถูกไว้ใจ กล่องนี้เป็นข้อมูลเสริม
</Callout>

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **log บอกว่าแพ็กเก็ตมาจาก IP ไหน ก็แปลว่าคนยิงอยู่ที่ IP นั้น**

ความเชื่อนี้ไม่จริงเสมอไป

มันดูจริงเพราะการเชื่อมต่อส่วนใหญ่ที่เราเห็นทุกวัน คือการเชื่อมต่อ TCP ที่จับมือกันครบแล้ว ซึ่งคนส่งต้องได้รับคำตอบจริง ที่อยู่จึงมักเป็นของจริง

สิ่งที่ถูกต้องคือ **ที่อยู่ผู้ส่งเป็นแค่ช่องที่คนส่งกรอกเอง** อย่างแพ็กเก็ตในตัวอย่างข้างบน ซึ่งทุกเครื่องเห็นเป็น `3.3.3.3` ทั้งที่มาจาก `1.1.1.1` แพ็กเก็ตเดี่ยว ๆ ที่ไม่ต้องรอคำตอบ เช่น UDP ทั้งหมด หรือคำขอจับมือแรกของ TCP จึงไม่ได้บอกอะไรเลยว่าใครเป็นคนส่ง ย่อหน้านี้เป็นคำอธิบายเสริม
</Pitfall>

### ARP/MAC Spoofing — แย่งรับแพ็กเก็ตในวงแลน

<Why>
ผู้โจมตีที่นั่งอยู่ในวงแลนเดียวกับเหยื่อ เช่นในร้านกาแฟ อยากอ่านทุกอย่างที่เหยื่อส่งออกอินเทอร์เน็ต

แต่สวิตช์ส่งแพ็กเก็ตของเหยื่อไปที่ gateway ตรง ๆ ไม่ผ่านเครื่องของผู้โจมตีเลย sniffer ของผู้โจมตีจึงไม่เห็นอะไร

ทางเดียวคือหลอกให้เครื่องของเหยื่อเชื่อว่าเครื่องของผู้โจมตีคือ gateway
</Why>

ในวงแลน แพ็กเก็ตถูกใส่ซองชั้นนอกสุดในอุปมาของส่วนที่ 1 ซึ่งเรียกว่า <Term en="Frame" th="เฟรม คือก้อนข้อมูลที่ส่งในวงแลน มีแพ็กเก็ตอยู่ข้างใน" /> และเฟรมถูกส่งไปตาม <Term en="MAC Address" th="เลขประจำการ์ดเครือข่าย ใช้ส่งข้อมูลในวงแลนเดียวกัน" /> เครื่องรู้แค่ว่า gateway อยู่ที่ IP `192.168.1.1` จึงต้องถามก่อนว่า IP นี้ใช้ MAC address อะไร

<Term en="ARP (Address Resolution Protocol)" th="โปรโตคอลที่ถามว่า IP นี้ใช้ MAC address อะไร" /> ทำงานแบบนี้ เครื่องตะโกนถามทั้งวงแลนว่า "ใครเป็น `192.168.1.1`" เจ้าของตอบกลับว่า "`192.168.1.1` อยู่ที่ MAC นี้" แล้วเครื่องที่ถามจดคำตอบไว้ใน <Term en="ARP Cache" th="ตารางที่จำว่า IP ไหนใช้ MAC ไหน" /> ใช้ต่อไปเรื่อย ๆ

จุดอ่อนคือ **ARP ไม่มีอะไรพิสูจน์ว่าคนตอบเป็นเจ้าของ IP นั้นจริง** และเครื่องส่วนใหญ่ยอมรับคำตอบแม้ตัวเองไม่ได้ถาม ผู้โจมตีจึงส่งคำตอบว่า "`192.168.1.1` อยู่ที่ MAC ของฉัน" ซ้ำไปเรื่อย ๆ ARP cache ของเหยื่อก็จดทับของจริง การโจมตีนี้จึงเรียกอีกชื่อว่า <Term en="ARP Cache Poisoning" th="การวางยา ARP cache ให้จำ MAC ผิด" />

ผู้โจมตีทำแบบเดียวกันกับ gateway ด้วย คือบอก gateway ว่า "`192.168.1.10` อยู่ที่ MAC ของฉัน" เฟรมขากลับจาก gateway จึงวิ่งผ่านผู้โจมตีเช่นกัน ถ้าวางยาฝั่งเดียว ผู้โจมตีจะเห็นแค่ครึ่งเดียวของบทสนทนา ผู้โจมตีส่งทุกเฟรมต่อให้ปลายทางตัวจริง เหยื่อจึงยังใช้อินเทอร์เน็ตได้ตามปกติ ไม่รู้ตัวว่ามีคนนั่งอยู่ตรงกลาง นี่คือ [man-in-the-middle](/2110413-csy/lecture-1#man-in-the-middle) ในระดับวงแลน ผู้โจมตีอ่านทุกอย่างที่ไม่ได้เข้ารหัส และแก้ข้อความก่อนส่งต่อได้

สไลด์แสดงแค่เส้นทางที่เปลี่ยนไป สคริปต์เดียวกันสร้าง ARP reply สองใบถึงเครื่อง `192.168.1.10` ใบแรกจาก gateway ตัวจริง ใบที่สองจากผู้โจมตี

### DDoS ด้วยคำขอที่ปลอมต้นทาง

<Why>
[DDoS ใน Lecture 1](/2110413-csy/lecture-1#botnet-และ-ddos) ใช้ botnet คือเครื่องที่ถูกยึดมาแล้วจำนวนมากยิงเป้าหมายตรง ๆ

IP spoofing ตัดต้นทุนทั้งสองข้อทิ้ง

## ส่วนที่ 4 — DNS poisoning: โปรโตคอลที่ออกแบบมาให้ทำงาน

**โปรโตคอลและบริการเครือข่ายจำนวนมากถูกออกแบบมาให้ทำงานได้ ไม่ได้ออกแบบมาให้ปลอดภัย** ตัวอย่างที่ชัดที่สุดคือ DNS ซึ่งตอบคำถามแรกสุดของทุกการเชื่อมต่อ

### DNS ทำงานยังไง

<Term en="DNS (Domain Name System)" th="ระบบที่แปลงชื่อเว็บเป็น IP address" /> คือสิ่งที่แปลง `NiceBank.com` เป็น IP address อย่าง `1.1.1.1` คำถามของเครื่องเราไม่ได้วิ่งไปถึงเจ้าของชื่อโดยตรง แต่ผ่าน DNS server ตัวกลางก่อน

- <Term en="Local DNS Server" th="DNS server ที่ตอบคำถามแทนเครื่องทุกเครื่องในเครือข่าย" /> — เครื่องที่ตอบคำถามแทนทุกคนในเครือข่าย ถ้าเคยถามชื่อนี้แล้วก็ตอบจาก <Term en="Cache" th="ที่จำคำตอบเก่าไว้ใช้ซ้ำ" /> ทันที ถ้ายังไม่เคย ก็ไปถามต่อ
- <Term en="Master DNS Server" th="DNS server ของเจ้าของชื่อ ที่รู้คำตอบจริง" /> — เครื่องที่รู้คำตอบจริงของชื่อนั้น

คำถามและคำตอบของ DNS วิ่งบน UDP เป็นแพ็กเก็ตเดี่ยว ๆ local DNS server จึงต้องจับคู่ว่าคำตอบที่เข้ามาเป็นของคำถามไหน ด้วยเลขที่ตัวเองสุ่มใส่ไว้ในคำถาม เรียกว่า <Term en="Transaction ID" th="เลขประจำคำถาม ที่คำตอบต้องใส่กลับมาให้ตรง" /> ซึ่งยาว 16 บิต คือมีได้ 65,536 ค่า คำตอบใบแรกที่ ID ตรงจะถูกรับไว้และจดลง cache ใบที่มาทีหลังถูกทิ้ง

<Example added title="dig รับคำตอบที่ ID ตรง ไม่ว่าในนั้นจะเขียนอะไร">
สไลด์แสดงว่าคำตอบถูกจับคู่ด้วย ID แต่ไม่ได้แสดงว่าใบที่ ID ไม่ตรงถูกทิ้ง และใบแรกที่ตรงเป็นฝ่ายชนะ ตัวอย่างนี้ใช้ `dig` ซึ่งเป็นคำสั่งถาม DNS จาก command line ถาม DNS server จำลองบน `127.0.0.1` ที่ส่งคำตอบปลอม `5.5.5.5` ก่อนคำตอบจริง `1.1.1.1` 0.3 วินาที โดยรอบแรกคำตอบปลอมใส่ ID ผิดไปหนึ่ง และรอบที่สองใส่ ID ถูก

```bash
# run twice: wrong ID, then right ID
dig @127.0.0.1 -p 5300 nicebank.com A
```

```text
;; Warning: ID mismatch: expected ID 62508, got 62509
nicebank.com.		300	IN	A	1.1.1.1

nicebank.com.		300	IN	A	5.5.5.5
```

รอบแรก `dig` ทิ้งใบที่ ID ไม่ตรง รอบที่สองมันรับ `5.5.5.5` ทันทีและไม่สนใจคำตอบจริงที่มาทีหลัง

<Detail label="ตัวอย่างนี้ต่างจากของจริงตรงไหน">
ผลข้างบนตัดเหลือบรรทัดที่ตัดสินของแต่ละครั้ง และตัวอย่างนี้ส่งคำตอบทั้งสองใบจากโปรแกรมเดียวกัน ส่วนในเครือข่ายจริง คำตอบปลอมมาจากเครื่องของผู้โจมตี ซึ่งหัวข้อถัดไปอธิบาย
</Detail>
</Example>

### DNS cache poisoning

<Why>
ถ้าผู้โจมตีทำให้ local DNS server ขององค์กรหนึ่งจำว่า `NiceBank.com` อยู่ที่ `5.5.5.5` ได้ ทุกคนที่ใช้ server นั้นจะถูกส่งไปเว็บปลอม ทั้งที่พิมพ์ชื่อเว็บถูกทุกตัวอักษร และไม่ได้คลิกลิงก์อะไรเลย
</Why>

<Term en="DNS Cache Poisoning" th="การวางยา cache ของ DNS ให้จำคำตอบปลอม" /> ใช้สองข้อข้างบนรวมกัน คือ DNS เชื่อคำตอบที่ ID ตรงใบแรก และที่อยู่ผู้ส่งปลอมได้ คำตอบปลอมจึงเขียนที่อยู่ผู้ส่งเป็นของ master DNS server ด้วย IP spoofing

<Figure number={5} caption="ผู้โจมตีเป็นคนเริ่มคำถามเอง จึงรู้จังหวะ แล้วส่งคำตอบปลอมที่เดา ID หลายค่าไปแข่งกับคำตอบจริง">
  <DnsCachePoisoning />
</Figure>

ขั้นที่ทำให้มันได้ผลคือขั้นที่ 1 ผู้โจมตีถาม local DNS server เอง จึงรู้แน่ว่าในเสี้ยววินาทีถัดไป server จะรอคำตอบของ `NiceBank.com` อยู่ สิ่งเดียวที่ไม่รู้คือ ID จึงยิงคำตอบปลอมหลายใบที่เดา ID ต่างกันไปแข่ง ถ้าใบไหนเดาตรงก่อนคำตอบจริงมาถึง cache ของ server ก็จำ `5.5.5.5` ไว้แทนที่อยู่จริง

นี่คือ <Term en="Pharming Attack" th="การพาเหยื่อไปเว็บปลอมโดยไม่ต้องหลอกให้คลิก" /> ที่อยู่ในรายชื่อ[ภัยเก้าอย่างของ Lecture 1](/2110413-csy/lecture-1#ภัยเก้าอย่างที่ต้องแยกให้ออก) ซึ่งพาเราไปเว็บปลอมโดยแก้ขั้นตอนที่แปลงชื่อเว็บเป็นที่อยู่ ภาพเคลื่อนไหวของการโจมตีนี้ดูได้ที่ [https://www.youtube.com/watch?v=1d1tUefYn4U](https://www.youtube.com/watch?v=1d1tUefYn4U)

<Example added title="ต้องแข่งกี่รอบถึงจะชนะ">
สไลด์ไม่ได้บอกว่าการเดา ID ยากแค่ไหน สคริปต์นี้จึงคิดโอกาสชนะเมื่อ ID มี 65,536 ค่า

```python
# k = forged answers sent in one race, each with a different guessed ID
p = k / 2**16                               # chance one race is won
races = math.ceil(math.log(0.5) / math.log(1 - p))  # races for a 50% chance
```

ลองทายก่อน: ยิงรอบละ 1,000 ใบ ต้องแข่งกี่รอบถึงจะมีโอกาสชนะครึ่งต่อครึ่ง

```text
forged answers per race     4: win one race 0.0061%, races for a 50% chance 11357
forged answers per race   100: win one race 0.1526%, races for a 50% chance 454
forged answers per race  1000: win one race 1.5259%, races for a 50% chance 46
```

ถ้ายิงคำตอบปลอมได้รอบละ 1,000 ใบ แข่งแค่ 46 รอบก็มีโอกาสชนะครึ่งต่อครึ่ง

<Detail label="ทำไมของจริงยากกว่านี้ และทำไมยังไม่พอ">
แต่ละรอบที่แพ้ คำตอบจริงจะถูกจดลง cache และอยู่ไปจนหมดอายุ ผู้โจมตีจึงแข่งซ้ำกับชื่อเดิมทันทีไม่ได้ ในปี 2008 Dan Kaminsky แสดงว่าผู้โจมตีเลี่ยงข้อนี้ได้ ด้วยการถามชื่อย่อยที่ไม่มีอยู่จริงใหม่ทุกรอบ แล้วแนบข้อมูลปลอมของโดเมนหลักไปกับคำตอบปลอม

ทางแก้ที่ใช้กันหลังจากนั้นคือให้ local DNS server สุ่มพอร์ตต้นทางของคำถามด้วย ผู้โจมตีต้องเดาทั้ง ID และพอร์ตให้ถูกพร้อมกัน เครื่อง Linux ที่รันตัวอย่างนี้ใช้พอร์ตช่วง 32768 ถึง 60999 ซึ่งมี 28,232 พอร์ต

```text
random port too, 1000 per race: win one race 0.00005405%, races for 50% 1,282,470
```

จาก 46 รอบกลายเป็นราวหนึ่งล้านสามแสนรอบ ทางแก้นี้ทำให้เดายากขึ้นเท่านั้น ไม่ได้ทำให้คำตอบพิสูจน์ได้ว่ามาจากเจ้าของจริง สองย่อหน้าและตัวเลขในกล่องนี้เป็นข้อมูลเสริม
</Detail>
</Example>

ความเชื่อที่ต้องทิ้งคือ **ถ้าพิมพ์ชื่อเว็บเองทุกตัวอักษร ไม่คลิกลิงก์ในอีเมล ก็ไม่มีทางไปโผล่ที่เว็บปลอม**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะ phishing ที่เราถูกสอนให้ระวังมาตลอด ทำงานด้วยการหลอกให้คลิกลิงก์ที่ชื่อเพี้ยนไปจากของจริง การพิมพ์เองจึงกันได้

สิ่งที่ถูกต้องคือ **pharming ไม่ได้แก้ชื่อที่เราพิมพ์ แต่แก้คำตอบที่ได้จากชื่อนั้น** ในรูปที่ 5 ผู้ใช้พิมพ์ `NiceBank.com` ถูกทุกตัว แต่ local DNS server ตอบ `5.5.5.5` เบราว์เซอร์ก็ไปที่นั่นตามคำตอบ
</Pitfall>

<Quiz question="NiceBank.com ใช้ HTTPS ทั้งเว็บ ถ้า local DNS server ที่ผู้ใช้ใช้อยู่ถูกวางยาให้ตอบ 5.5.5.5 ผู้ใช้จะเห็นอะไรเมื่อเปิดเว็บ">
DNS ถูกถามก่อนจะเริ่ม HTTPS เบราว์เซอร์จึงต่อไปที่ `5.5.5.5` จริง ๆ แต่ HTTPS ต้องให้ฝั่งเซิร์ฟเวอร์ยื่นใบรับรองของชื่อ `NiceBank.com` ที่ CA ซึ่งเบราว์เซอร์เชื่อเป็นคนเซ็น ผู้โจมตีที่ `5.5.5.5` ไม่มี private key ของใบจริง และขอใบใหม่จาก CA ไม่ได้ เพราะไม่ได้เป็นเจ้าของโดเมน

คำตอบคือ **เบราว์เซอร์เตือนว่าใบรับรองเชื่อถือไม่ได้** ความปลอดภัยรอดถ้าผู้ใช้ไม่กดข้ามคำเตือน และไม่มี CA ไหนออกใบผิดให้ผู้โจมตี อย่างกรณีใน [Lecture 7](/2110413-csy/lecture-7#ส่วนที่-6--เมื่อความเชื่อถูกใช้ผิดทาง)

คำตอบที่ผิดบ่อยคือ "HTTPS เข้ารหัสอยู่แล้ว DNS จึงถูกวางยาไม่ได้" ซึ่ง HTTPS ไม่ได้ป้องกัน DNS เลย สิ่งที่มันทำคือจับได้ทีหลังว่าปลายทางไม่ใช่ตัวจริง คำอธิบายในข้อนี้เป็นข้อมูลเสริม
</Quiz>

## ส่วนที่ 5 — ป้องกันด้วยระบบ คน และซอฟต์แวร์

### สามด้านของการป้องกัน

การป้องกันแบ่งได้เป็นสามด้าน

**ด้านระบบ**

- **Firewall** — กั้นระหว่างอินเทอร์เน็ตกับเครือข่ายภายใน ให้ผ่านเฉพาะทราฟฟิกที่อนุญาต รายละเอียดอยู่ใน [Lecture 5](/2110413-csy/lecture-5#firewall)
- **Patch และการอัปเดต** — ปิดช่องโหว่ที่ถูกประกาศในฐานข้อมูลอย่าง CERT ก่อนที่ script kiddie จะสแกนมาเจอ
- <Term en="System Hardening" th="การลดสิ่งที่เปิดทิ้งไว้ในระบบให้เหลือเท่าที่จำเป็น" /> — ปิดบริการและพอร์ตที่ไม่ได้ใช้ ทุกพอร์ตที่ nmap เห็นว่า `open` คือประตูที่ต้องมีคนเฝ้า
- **Encryption** — ทำให้คนที่ดักแพ็กเก็ตได้อ่านเนื้อหาไม่ออก แต่ **อย่าลืมว่าการเข้ารหัสมีจุดอ่อนต่อการวิเคราะห์ทางสถิติ** ทั้งที่ตัวข้อความเอง ตาม[ส่วนที่ 9 ของ Lecture 6](/2110413-csy/lecture-6#ส่วนที่-9--การเข้ารหัสให้อะไร-และไม่ให้อะไร) และที่ข้อมูลบนซองซึ่งยังอ่านออกอยู่ ตามกล่องข้างล่าง

**ด้านคน**

- **Awareness** — ผู้ใช้ต้องรู้ทันการหลอก เพราะ whois ทำให้ผู้โจมตีรู้ว่าต้องหลอกใคร และ [ผู้ใช้คือแนวป้องกันด่านแรก](/2110413-csy/lecture-1#ทางที่สอง--หลอกคนที่ใช้ระบบ)

**ด้านซอฟต์แวร์**

- <Term en="Secure by Design" th="ออกแบบให้ปลอดภัยตั้งแต่แรก ไม่ใช่มาปะทีหลัง" /> — สิ่งที่ IP, ARP และ DNS รุ่นแรกไม่มี เพราะทั้งสามตัวถูกออกแบบมาให้ทำงานได้ในเครือข่ายที่ทุกคนไว้ใจกัน

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ถ้าเข้ารหัสทุกอย่างแล้ว คนที่ดักแพ็กเก็ตจะไม่ได้ข้อมูลอะไรเลย**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะเนื้อหาที่เข้ารหัสดีแล้วอ่านไม่ออกจริง ๆ ถ้าเปิดดูใน Wireshark ก็เห็นเป็นไบต์มั่ว ๆ

สิ่งที่ถูกต้องคือ **การเข้ารหัสปิดผนึกจดหมาย แต่ซองต้องอ่านออกเสมอ** เพราะ router ต้องอ่านที่อยู่บนซองถึงจะส่งต่อได้ คนดักยังเห็นว่าเครื่องไหนคุยกับเครื่องไหน ที่พอร์ตอะไร เมื่อไหร่ และส่งไปกี่ไบต์ ข้อมูลพวกนี้เอามาวิเคราะห์ทางสถิติได้ เช่นเครื่องที่คุยกับพอร์ต 22 ของเซิร์ฟเวอร์ทุกเช้าน่าจะเป็นเครื่องของผู้ดูแลระบบ ย่อหน้านี้เป็นคำอธิบายเสริม
</Pitfall>

<Callout type="info" title="ทางแก้ของแต่ละการโจมตีในหน้านี้">
สไลด์ให้ทางป้องกันเป็นหมวดกว้าง ๆ ตารางนี้จับคู่การโจมตีแต่ละแบบในหน้านี้กับทางแก้ที่ใช้กันจริง ทั้งตารางเป็นข้อมูลเสริม

| การโจมตี | ทางแก้ |
| --- | --- |
| สแกนหาพอร์ตและรุ่น | system hardening, firewall และ IDS ที่จับการสแกน |
| ช่องโหว่ที่ประกาศแล้ว | patch ให้เร็วกว่าคนสแกน |
| IP spoofing และ DDoS แบบสะท้อน | ผู้ให้บริการอินเทอร์เน็ตทิ้งแพ็กเก็ตที่ลูกค้าส่งเข้ามา ถ้าที่อยู่ผู้ส่งไม่ใช่ที่อยู่ที่แจกให้ลูกค้ารายนั้น เรียกว่า ingress filtering ตามแนวปฏิบัติ BCP 38 (Best Current Practice ฉบับที่ 38 ของ IETF คือ RFC 2827 ปี 2000) |
| ARP spoofing | สวิตช์ที่ตรวจ ARP reply เทียบกับตารางที่รู้ว่าเครื่องไหนได้ IP อะไร หรือจด MAC ของ gateway ไว้ตายตัว |
| DNS cache poisoning | สุ่มพอร์ตต้นทาง (กล่อง "ทำไมของจริงยากกว่านี้" ในส่วนที่ 4) และ DNSSEC ที่ให้เจ้าของโดเมนเซ็นคำตอบด้วย[ลายเซ็นดิจิทัล](/2110413-csy/lecture-6#digital-signature) |
</Callout>

<Quiz question="ผู้ดูแลระบบรัน nmap กับเซิร์ฟเวอร์ของบริษัทตัวเองแล้วเจอว่าพอร์ต 23 ที่รัน Telnet เปิดอยู่ ทั้งที่ทุกคนล็อกอินผ่าน SSH ที่พอร์ต 22 กันหมดแล้ว ควรทำอะไร และทำไม">
พอร์ตที่ไม่มีใครใช้แต่ยังเปิดอยู่ ไม่ได้ให้อะไรกับบริษัทเลย แต่เป็นประตูเพิ่มอีกบานให้ผู้โจมตี และ Telnet ส่งทุกอย่างรวมถึงรหัสผ่านแบบไม่เข้ารหัส คนที่ดักแพ็กเก็ตได้ด้วย sniffer หรือ ARP spoofing จะอ่านรหัสผ่านได้ตรง ๆ

คำตอบคือ **ปิด Telnet ทิ้ง** ซึ่งเป็น system hardening แล้วรัน nmap ซ้ำเพื่อยืนยันว่าพอร์ต 23 กลายเป็น `closed`

คำตอบที่ผิดบ่อยคือ "ตั้ง firewall บล็อกพอร์ต 23 จากข้างนอกก็พอ" ซึ่งกันได้แค่คนนอก ผู้โจมตีที่อยู่ในวงแลนเดียวกันหรือเครื่องในบริษัทที่ถูกยึดแล้วยังเข้าถึงได้ ของที่ไม่ใช้ควรถูกปิด ไม่ใช่แค่ถูกบัง
</Quiz>

### เจาะระบบตัวเองก่อนคนอื่น

ในโลกที่ทุกอย่างเชื่อมต่อกัน ความปลอดภัยของเครือข่ายสำคัญมาก และทางที่ได้ผลคือ **เรียนรู้ระบบของตัวเองเสมอ เจาะมันก่อนที่คนอื่นจะเจาะ** (*Hack it first, before others will.*)

ทางนี้คือการเอาเครื่องมือทั้งหมดของส่วนที่ 2 มาหันใส่ระบบของตัวเอง สแกนด้วย nmap ให้รู้ว่าเปิดอะไรไว้ เอารุ่นที่ได้ไปค้นใน CERT แล้วปิดหรือแพตช์ก่อนที่คนอื่นจะทำแบบเดียวกัน และทำบนเครือข่ายที่ตัวเองได้รับอนุญาตเท่านั้น เพื่อไม่ให้สัญญาณเตือนของคนอื่นดัง

<Recap>

**[เครือข่ายคือโปรโตคอลหลายชั้น](#ส่วนที่-1--เครือข่ายคือโปรโตคอลหลายชั้นที่เชื่อกันเอง)**

- เครือข่าย TCP/IP **ซับซ้อนมาก พึ่งบริการและโปรโตคอลที่เกี่ยวข้องกันจำนวนมาก จึงพังได้หลายทาง**
- OSI มีเจ็ดชั้น TCP/IP ยุบสามชั้นบนเป็น Application เหลือห้าชั้น
- Telnet, FTP, SMTP บน TCP · DNS, RIP, SNMP บน UDP · IP, ARP, IGMP, ICMP ในชั้น Network · Ethernet, Token Ring, Frame Relay, ATM ในชั้นล่าง
- **ส่วนหัวของแพ็กเก็ตเหมือนซองจดหมาย** มี IP address บอกเครื่อง และ port บอกโปรแกรม

**[เรียนรู้เป้าหมาย](#ส่วนที่-2--ผู้โจมตีเริ่มจากเรียนรู้เป้าหมาย)**

- สองประตู: **remote login** (หาชื่อผู้ใช้และรหัสผ่าน) และ **remote exploit** (หาบริการที่มีช่องโหว่)
- ข้อมูลทางสังคมจาก **whois** — `.th` ที่ THNIC, `.com` ที่ ICANN · เจาะอีเมลที่ใช้จดโดเมนได้ ก็ไปถึงตัวโดเมน
- ข้อมูลเครือข่ายจาก **Wireshark, tcpdump, Snort, Nmap**
- **Nmap** หาพอร์ตและบริการที่เปิด, OS fingerprint และแผนที่เครือข่าย · `-sV` ได้ชื่อและรุ่นของโปรแกรม
- Nmap อยู่ในภาพยนตร์ Matrix Reloaded, Ocean's 8, Elysium
- **การสแกนอาจทำให้สัญญาณเตือนดังและถูกบล็อก**
- ได้รุ่นแล้วไปค้นช่องโหว่ใน **CERT** บางทีได้สคริปต์ฟรีด้วย · **script kiddie** คือคนที่รันสคริปต์ของคนอื่นโดยไม่เข้าใจ

**[ปลอมที่อยู่บนซอง](#ส่วนที่-3--เขียนที่อยู่บนซองเอง-โจมตีโดยไม่เผยตัว)**

- สร้างแพ็กเก็ตเองได้ ก็เขียนที่อยู่ผู้ส่งและผู้รับเองได้
- **IP spoofing** — คำตอบวิ่งไปหาเจ้าของที่อยู่ ใช้ได้กับงานที่ไม่ต้องรอคำตอบ หรือเหยื่อที่เชื่อจากที่อยู่
- **ARP/MAC spoofing** — ARP reply ปลอมทำให้เฟรมที่จะไป gateway วิ่งผ่านผู้โจมตี เป็น man-in-the-middle ในวงแลน
- **DDoS ด้วยคำขอที่ปลอมต้นทาง** — หลอกเซิร์ฟเวอร์ UDP ให้ส่งคำตอบจริงไปถล่มเหยื่อ เหยื่อไม่เห็นผู้โจมตี

**[DNS poisoning](#ส่วนที่-4--dns-poisoning-โปรโตคอลที่ออกแบบมาให้ทำงาน)**

- **โปรโตคอลจำนวนมากออกแบบมาให้ทำงาน ไม่ใช่ให้ปลอดภัย**
- local DNS server รับคำตอบใบแรกที่ transaction ID ตรง ไม่ตรวจว่าใครส่ง
- ผู้โจมตีถามเอง แล้วยิงคำตอบปลอมที่เดา ID แข่งกับ master DNS server · ชนะแล้ว cache จำ `NiceBank.com = 5.5.5.5` ทุกคนที่ใช้ server นั้นไปเว็บปลอม
- นี่คือ **pharming** — พิมพ์ชื่อเว็บถูกก็ยังโดน

**[ป้องกัน](#ส่วนที่-5--ป้องกันด้วยระบบ-คน-และซอฟต์แวร์)**

- **ระบบ:** firewall, patches/updates, system hardening, encryption — **การเข้ารหัสยังแพ้การวิเคราะห์ทางสถิติได้**
- **คน:** awareness
- **ซอฟต์แวร์:** secure by design
- **เรียนรู้ระบบของตัวเอง เจาะมันก่อนที่คนอื่นจะเจาะ**

</Recap>
