## ส่วนที่ 1 — ชิ้นส่วนที่มีอยู่แล้ว

### ระบบที่ปลอดภัยต้องมีอะไรบ้าง

สองคำที่ใช้ทั้งวิชามีนิยามเดิมจาก [Lecture 2](/2110413-csy/lecture-2#ส่วนที่-1--security-กับ-privacy-ไม่ใช่เรื่องเดียวกัน)

- **Security** — Who can do what when? ใครทำอะไรได้ เมื่อไหร่
- **Privacy** — อิสระที่จะควบคุมการเข้าถึงข้อมูลส่วนตัวของเราเอง

คำถามของคาบนี้คือ **ต้องมีอะไรบ้างถึงจะสร้างระบบที่ปลอดภัยได้** ชิ้นส่วนแรกที่มีอยู่แล้วคือ AAA สามด่านจาก [Lecture 2](/2110413-csy/lecture-2#ส่วนที่-3--aaa-สามองค์ประกอบของความปลอดภัย)

| ด่าน | คำถามที่ด่านนี้ถาม |
| --- | --- |
| Authentication | Who are you? Are you really the person whom you claim to be? |
| Authorization | Do you have the authority to do what you are trying to do? |
| Accounting (Auditing) | What did you do? |

อีกสามชิ้นคือแนวคิดหนุนจาก [ส่วนที่ 4 ของ Lecture 2](/2110413-csy/lecture-2#ส่วนที่-4--สองแนวคิดที่มาช่วยหนุน)

- **Integrity** — "the quality or state of being complete or undivided" คือของยังครบ ไม่ถูกแก้
- **Software Engineering & Threat Modeling** — "Threat modeling is a method of addressing and documenting the security risks associated with an application." คือวิธีจัดการและจดความเสี่ยงของแอปพลิเคชันหนึ่ง ๆ
- **Validation of Input** — "All input is evil until proven otherwise"

Integrity บางครั้งถูกเรียกว่า Authenticity จึงถูกนับเป็น **A ตัวที่สี่** ของชิ้นส่วนความปลอดภัย ส่วนคำถามว่าจะรักษา integrity ของข้อมูลได้ยังไง อยู่ใน [Lecture 6](/2110413-csy/lecture-6#ส่วนที่-1--integrity-คือ-a-ตัวที่สี่)

ของที่เรียนมาทั้งหมดจัดได้เป็นสามหัวข้อ โดยหัวข้อกลางแตกเป็น CIA จาก [Lecture 4](/2110413-csy/lecture-4#ส่วนที่-2--นโยบายตัดสินจากอะไร)

- **Authentication**
- **Authorization** — Confidentiality, Integrity, Availability
- **Auditing**

Integrity จึงอยู่สองที่ ในฐานะ A ตัวที่สี่ มันถามว่าข้อมูลยังเหมือนเดิมไหม ในฐานะตัว I ของ CIA มันถามว่าใครมีสิทธิ์แก้ข้อมูล

ส่วน Threat Modeling กับ Validation of Input คือส่วนที่ 4 และส่วนที่ 5 ของคาบนี้ ชิ้นส่วนทั้งหมดบอกว่าระบบต้องมี **อะไร** คาบนี้ถามต่อว่าต้องเอามาประกอบกัน **ตอนไหนและยังไง**

## ส่วนที่ 2 — โปรแกรมที่ทำงานถูก แต่ยังรั่ว

### โปรแกรม login สามแบบ

<Why>
โปรแกรม login สามตัวข้างล่างทำงานถูกทุกตัว ใส่ชื่อกับรหัสผ่านถูกก็เข้าได้ ใส่ผิดก็ถูกไล่ออก ถ้าวัดแค่ว่า "ใช้งานได้ไหม" ทั้งสามตัวสอบผ่าน

แต่ถ้าถามว่า "ผู้โจมตีที่ยังไม่รู้รหัสผ่านของใครเลย เรียนรู้อะไรจากโปรแกรมนี้ได้บ้าง" คำตอบของสามตัวไม่เท่ากัน
</Why>

```text
Prog 1.                      Prog 2.                      Prog 3.
1. Input [login name]        1. Input [login name]        1. Input [login name]
2. Fetch [saved password]    2. Input [password]          2. Input [password]
3. If no entry then          3. Fetch [saved password]    3. Fetch [saved password]
     Exit                    4. If no entry then          4. If no entry then
4. Input [password]               Exit                         [saved password] <- random
5. Compare passwords.        5. Compare passwords.        5. Compare passwords.
6. If valid then             6. If valid then             6. If valid then
     start session                start session                start session
   else                         else                         else
     exit                         exit                         exit
   End if                       End if                       End if
```

- **Prog 1** ค้นชื่อก่อน ถ้าไม่มีชื่อนี้ก็ออกทันทีโดยไม่ถามรหัสผ่าน ผู้โจมตีจึงพิมพ์ชื่อไปทีละชื่อ แล้วดูว่าชื่อไหนถูกถามรหัสผ่านต่อ ชื่อนั้นคือบัญชีที่มีอยู่จริง
- **Prog 2** ถามทั้งชื่อและรหัสผ่านก่อนค่อยค้น หน้าจอจึงเหมือนกันทุกกรณี แต่ถ้าไม่มีชื่อนี้ โปรแกรมออกเลยโดยไม่ต้องเทียบรหัส คำตอบจึงกลับมา **เร็วกว่า** ผู้โจมตีที่จับเวลาได้ก็ยังแยกชื่อจริงออกจากชื่อมั่วได้
- **Prog 3** แก้ด้วยบรรทัดเดียว ถ้าไม่มีชื่อนี้ ก็สุ่มรหัสผ่านขึ้นมาแล้วเทียบตามปกติ ทุกกรณีจึงเดินผ่านขั้นตอนเดียวกันและใช้เวลาเท่ากัน ผู้โจมตีรู้แค่ว่า "เข้าไม่ได้"

<Example added title="จับเวลาสามโปรแกรมนี้จริง">
Prog 2 รั่วทางเวลา แต่ต่างกันแค่ไหน โค้ด Python ข้างล่างเขียนสามโปรแกรมนี้ใหม่ เทียบรหัสด้วย hash ที่ตั้งใจให้ช้าแบบระบบจริง (PBKDF2 วน 600,000 รอบ ดู [Lecture 3](/2110413-csy/lecture-3#รหัสผ่านถูกเก็บยังไง)) แล้วใส่รหัสผิดทุกครั้ง

```text
prog1 alice  -> exit | asked password: True
prog1 nobody -> exit (no password prompt) | asked password: False
prog2  alice   wrong password     90.6 ms  -> exit
prog2  nobody  wrong password      0.0 ms  -> exit
prog3  alice   wrong password     90.3 ms  -> exit
prog3  nobody  wrong password     90.7 ms  -> exit
```

ทุกบรรทัดตอบ `exit` เหมือนกัน สิ่งที่รั่วคือการถูกถามรหัส (Prog 1) และเวลา 90 ms กับ 0 ms (Prog 2) ส่วน Prog 3 ต่างกันไม่ถึง 1 ms

<Detail label="โค้ดที่ใช้รัน">
```python
# three login programs from the deck; password check uses a slow hash, as real systems do
import hashlib, os, time, hmac

def slow_hash(pw, salt):
    return hashlib.pbkdf2_hmac('sha256', pw.encode(), salt, 600_000)

salt = os.urandom(16)
users = {'alice': (salt, slow_hash('correct horse', salt))}

def prog1(name, ask_pw):
    entry = users.get(name)
    if entry is None:
        return 'exit (no password prompt)'
    pw = ask_pw()
    return 'session' if hmac.compare_digest(slow_hash(pw, entry[0]), entry[1]) else 'exit'

def prog2(name, pw):
    entry = users.get(name)
    if entry is None:
        return 'exit'
    return 'session' if hmac.compare_digest(slow_hash(pw, entry[0]), entry[1]) else 'exit'

def prog3(name, pw):
    entry = users.get(name)
    if entry is None:
        entry = (os.urandom(16), os.urandom(32))  # saved password <- random
    return 'session' if hmac.compare_digest(slow_hash(pw, entry[0]), entry[1]) else 'exit'

prompts = []
r = prog1('alice', lambda: prompts.append('alice') or 'guess')
r2 = prog1('nobody', lambda: prompts.append('nobody') or 'guess')
print('prog1 alice ->', r, '| asked password:', 'alice' in prompts)
print('prog1 nobody ->', r2, '| asked password:', 'nobody' in prompts)

for prog in (prog2, prog3):
    for name in ('alice', 'nobody'):
        best = min(
            (lambda t0: (prog(name, 'guess'), time.perf_counter() - t0))(time.perf_counter())[1]
            for _ in range(5))
        print(f'{prog.__name__}  {name:6}  wrong password  {best*1000:7.1f} ms  -> {prog(name, "guess")}')
```

เวลาที่แสดงคือค่าที่เร็วที่สุดจากห้ารอบ รันสองครั้งได้ผลห่างกันไม่เกิน 1 ms
</Detail>
</Example>

### Secure by Design คืออะไร

สามโปรแกรมนี้ทำงานได้เหมือนกัน ที่ต่างคือตอนเขียนมีคนถามหรือเปล่าว่า "ผู้โจมตีจะเห็นอะไร"

<Term en="Secure by Design" th="ออกแบบให้ปลอดภัยตั้งแต่ต้น" /> คือการถามคำถามนี้ตั้งแต่ตอนออกแบบ มีสามส่วน

- **Plan more than just functionality (Plan for Security)** — วางแผนมากกว่าแค่ว่าโปรแกรมทำอะไรได้ คือวางแผนเรื่องความปลอดภัยไปด้วย
- <Term en="Attack Surface Reduction" th="ลดจุดที่เปิดให้โจมตี" /> — ส่วนที่ 3
- **Threats & Risk Modeling** — ไล่หาภัยและประเมินความเสี่ยงอย่างเป็นระบบ ส่วนที่ 4

<Analogy>
นิทานลูกหมูสามตัว

- **บ้านสามหลัง** คือโปรแกรมสามตัว ทุกหลังอยู่อาศัยได้ เหมือนที่ทุกโปรแกรมทำงานได้
- **หมาป่า** คือผู้โจมตี
- **วัสดุที่เลือกก่อนลงมือสร้าง** คือการตัดสินใจเรื่องความปลอดภัยตอนออกแบบ

อุปมานี้ใช้ไม่ได้ตรงที่บ้านฟางต้องรื้อทั้งหลังถึงจะเป็นบ้านอิฐ แต่ Prog 2 กลายเป็น Prog 3 ได้ด้วยบรรทัดเดียว สิ่งที่ต้องมีตั้งแต่ตอนออกแบบจึงไม่ใช่วัสดุทั้งหลัง แต่เป็นคำถามว่า "ผู้โจมตีจะเห็นอะไร" ถ้าไม่มีใครถาม บรรทัดนั้นก็ไม่มีใครเขียน
</Analogy>

<Quiz question="หน้า 'ลืมรหัสผ่าน' ของเว็บหนึ่งให้กรอกอีเมล ถ้ามีอีเมลนี้ในระบบจะขึ้นว่า 'ส่งลิงก์ไปแล้ว' ถ้าไม่มีจะขึ้นว่า 'ไม่พบอีเมลนี้' หน้านี้เหมือนโปรแกรมตัวไหน และควรแก้ยังไง">
หน้านี้ตอบต่างกันตามว่ามีบัญชีอยู่จริงไหม ผู้โจมตีจึงกรอกอีเมลไปทีละอันแล้วรู้ว่าใครเป็นสมาชิก แบบเดียวกับ Prog 1

คำตอบคือ **เหมือน Prog 1 แก้ด้วยการตอบข้อความเดียวกันทุกกรณี** เช่น "ถ้ามีบัญชีนี้ เราได้ส่งลิงก์ไปแล้ว" และต้องตอบในเวลาใกล้กันด้วย ไม่อย่างนั้นจะกลายเป็น Prog 2

คำตอบที่ผิดบ่อยคือ "ไม่เป็นไร ผู้โจมตียังไม่รู้รหัสผ่าน" แต่รายชื่อบัญชีที่มีจริงคือครึ่งแรกของการเดารหัส และเป็นรายชื่อเป้าหมายสำหรับส่ง phishing ได้ทันที
</Quiz>

## ส่วนที่ 3 — ลดพื้นที่ที่เปิดให้โจมตี

### Attack Surface คืออะไร

<Why>
หมาป่าที่เป่าบ้านอิฐไม่พังจะหันไปหาปล่องไฟ ผู้โจมตีก็ไม่ได้เจาะจุดที่เราป้องกันแน่นที่สุด แต่หาจุดไหนก็ได้ที่เปิดอยู่ ระบบยิ่งมีประตู หน้าต่าง และปล่องไฟมาก โอกาสที่สักช่องจะลืมล็อกก็ยิ่งมาก
</Why>

<Term en="Attack Surface" th="จุดทั้งหมดที่ถูกโจมตีได้" /> คือ **ชุดของเป้าหมายทั้งหมดที่ผู้โจมตีเข้าถึงได้** ทั้งช่องโหว่ เครือข่าย และ control เอง (vulnerabilities, controls, networks) control ก็นับด้วย เพราะของที่ตั้งไว้กันการโจมตี เช่นหน้า login ก็ถูกโจมตีได้

Attack surface รวม (Aggregate Attack Surface) มีสามชั้น

- **Human Attack Surface** — คน เช่นผู้ใช้ที่ถูกหลอกด้วย [social engineering](/2110413-csy/lecture-1#social-engineering)
- **Network Attack Surface** — เครือข่าย
- **System Attack Surface** — ตัวระบบ

<Figure number={2} caption="การโจมตีเดียวกัน ถ้าไม่ทำ ASR จะทะลุถึงระบบ ถ้าทำแล้วจะบางลงทีละชั้นจนความเสียหายถูกจำกัด">
  <AttackSurfaceLayers />
</Figure>

ระบบที่ไม่ลด attack surface ปล่อยให้การโจมตีทะลุทั้งสามชั้นจนยึดระบบได้ (System Owned)

ระบบที่ลดแล้วกันไว้ทีละชั้น ที่ชั้นเครือข่าย network controls กันเครื่องมือและเทคนิคโจมตีส่วนใหญ่ไว้ ที่ชั้นตัวระบบ authentication, authorization และการเปิด process กับข้อมูลให้น้อยที่สุดกันไว้อีกชั้น ความเสียหายจึงถูกจำกัด (Damage Contained)

แต่ต้องหา **จุดสมดุล** (Balance) กับความสะดวก เพราะทุกช่องที่ปิดคือความสะดวกที่หายไป

**Attack Surface Reduction** หรือ ASR ทำด้วยหลักสามข้อ

- **Defense in Depth** — ป้องกันหลายชั้น ชั้นหนึ่งพังยังมีชั้นถัดไป ([หลักการที่ 2 ใน Lecture 1](/2110413-csy/lecture-1#หลักการที่-2--defense-in-depth))
- **Least Privilege** — ให้สิทธิ์น้อยที่สุดเท่าที่งานต้องใช้ ([หลักการที่ 1 ใน Lecture 1](/2110413-csy/lecture-1#หลักการที่-1--least-privilege))
- <Term en="Secure Defaults" th="ค่าเริ่มต้นที่ปลอดภัย" /> — Less code running = less stuff to attack โค้ดที่รันน้อยลง ของให้โจมตีก็น้อยลง ([หัวข้อ Secure Defaults](#secure-defaults))

### Defense in Depth ของจริง — MS03-007

MS03-007 คือ security bulletin ฉบับที่ 7 ของปี 2003 ของ Microsoft แต่ละฉบับประกาศช่องโหว่พร้อม patch ที่แก้

ช่องโหว่ของฉบับนี้เป็น <Term en="Buffer Overrun" th="เขียนข้อมูลเกินขนาด buffer" /> ใน `NTDLL.DLL` ของ Windows ผู้โจมตีเข้าถึงมันได้ผ่าน web server IIS ที่เปิด <Term en="WebDAV" th="ส่วนขยาย HTTP สำหรับจัดการไฟล์" /> ไว้ และมันกระทบ Windows 2000

แต่ **Windows Server 2003 ไม่โดน** และไม่ได้รอดเพราะชั้นเดียว มีถึงหกชั้น แต่ละชั้นถามว่า "ถ้าชั้นก่อนหน้าพังล่ะ"

| กรณี | ชั้นที่กันไว้ |
| --- | --- |
| ชั้นแรก: โค้ดใน `NTDLL.DLL` | ถูกแก้ไปแล้วช่วง Windows Security Push |
| *ต่อให้* มันมีช่องโหว่ | IIS 6.0 ไม่ได้รันเป็นค่าเริ่มต้นบน Windows Server 2003 |
| *ต่อให้* IIS รันอยู่ | IIS 6.0 ไม่ได้เปิด WebDAV เป็นค่าเริ่มต้น |
| *ต่อให้* เปิด WebDAV | ความยาว URL สูงสุดที่ตั้งไว้คือ 16 KB แต่การโจมตีต้องใช้เกิน 64 KB |
| *ต่อให้* buffer ใหญ่พอ | process หยุดทำงานแทนที่จะรันโค้ดร้าย เพราะโค้ดตรวจจับ buffer overrun ที่ compiler ใส่ให้ด้วยตัวเลือก `-GS` |
| *ต่อให้* มี buffer overrun ที่ใช้ได้จริง | ผู้โจมตีได้แค่สิทธิ์ของ `network service` ซึ่งเท่ากับผู้ใช้ธรรมดา |

Windows Security Push คือช่วงที่ทีม Windows หยุดเขียนฟีเจอร์ใหม่ แล้วไล่ตรวจโค้ดเดิมหาช่องโหว่

`-GS` วางค่า canary ไว้ข้าง buffer ถ้าค่านั้นถูกทับ โปรแกรมจะหยุดเองก่อนที่โค้ดของผู้โจมตีจะได้รัน กลไกเต็มอยู่ใน [Lecture 8](/2110413-csy/lecture-8)

สังเกตว่ามีแค่ชั้นแรกที่เป็นโค้ดที่ดีขึ้น ชั้นที่ 2–4 เป็น **ค่าเริ่มต้น** ล้วน ๆ คือ IIS ไม่รัน WebDAV ไม่เปิด และความยาว URL ถูกจำกัด

### Secure Defaults

ค่าเริ่มต้นที่ปลอดภัยให้ผลหกข้อ

- **Less code running by default = less stuff to attack by default**
- **Slammer และ CodeRed จะไม่เกิด ถ้าฟีเจอร์ที่ถูกโจมตีไม่ได้เปิดไว้เป็นค่าเริ่มต้น** ทั้งสองเป็น worm ที่แพร่จากเครื่องไปเครื่องเอง CodeRed เจาะ IIS ส่วน Slammer เจาะ SQL Server
- **ลดความเร่งด่วนในการลง patch** ช่องโหว่ระดับ "critical" อาจถูกลดเป็น "important" เพราะต้องมีคนไปเปิดฟีเจอร์นั้นเองก่อน
- **Defense in depth ตัด single point of failure ทิ้ง** คือไม่มีจุดเดียวที่พังแล้วพังทั้งระบบ
- **ลูกค้าไม่ต้อง "harden" ระบบเอง** คือไม่ต้องไล่ปิดของที่ไม่ใช้ด้วยตัวเอง
- **งานทดสอบของ*ผู้พัฒนา*เองก็ลดลง** เพราะของที่ปิดอยู่มีทางให้ผิดพลาดน้อยกว่า

### ลด attack surface ของบริการหนึ่งตัว ทีละขั้น

เริ่มจากบริการหนึ่งตัวที่ **เริ่มทำงานเองตอนเปิดเครื่อง (Autostart) ด้วยสิทธิ์ SYSTEM** ซึ่งสูงสุดในเครื่อง มันเปิดพอร์ตสามพอร์ต ทั้ง TCP และ UDP ให้ใครก็ได้บนอินเทอร์เน็ตต่อเข้ามา และมีที่เก็บข้อมูลอยู่ข้างหลัง แต่ละขั้นข้างล่างปิดของไปทีละชิ้น

<StepThrough>
<Step title="ปิดพอร์ตที่ไม่ค่อยได้ใช้">
สามพอร์ตเหลือพอร์ตเดียวที่จำเป็นจริง ทุกพอร์ตที่ปิดคือประตูที่ผู้โจมตีไม่มีให้ลอง
</Step>
<Step title="ปิดการเชื่อมต่อแบบ UDP">
พอร์ตที่เหลือรับแค่ TCP (TCP only) เพราะ TCP ต้องจับมือกันก่อนคุย ฝ่ายที่ปลอมที่อยู่ต้นทางไม่เห็นเลขสุ่มที่ปลายทางส่งกลับ จึงปลอมได้ยาก UDP ไม่มีขั้นนี้ จึงปลอมที่อยู่ได้ง่าย ([IP Spoofing ใน Lecture 11](/2110413-csy/lecture-11#ip-spoofing--ปลอมที่อยู่ผู้ส่ง))
</Step>
<Step title="รับคำขอเฉพาะช่วง IP เล็ก ๆ และ subnet ภายใน">
คนทั้งอินเทอร์เน็ตต่อเข้ามาไม่ได้อีก เหลือแค่เครื่องในเครือข่ายภายในไม่กี่เครื่อง
</Step>
<Step title="Authenticate connections">
คนในเครือข่ายภายในเองก็ต้องพิสูจน์ตัวตนก่อน ถึงจะคุยกับบริการได้
</Step>
<Step title="ลดสิทธิ์ และปิดบริการที่ไม่ใช้">
บริการเปลี่ยนจาก Autostart ด้วยสิทธิ์ SYSTEM เป็นเริ่มเองไม่ได้ (Manual) และรันด้วยบัญชี Network Service ที่สิทธิ์ต่ำ เช่นบริการ Network DDE เปลี่ยนจาก `Started · Automatic · Local System` เป็น `Manual · Network Service`
</Step>
<Step title="Harden ACLs">
สิทธิ์บนที่เก็บข้อมูลเปลี่ยนจาก `Everyone (Full Control)` เป็น `Admin (Full Control)`, `Everyone (Read)` และ `Service (RW)` ACL คือรายชื่อผู้มีสิทธิ์ที่ผูกกับตัวของ ([Lecture 4](/2110413-csy/lecture-4#acl-กับ-capability-ต่างกันยังไง))
</Step>
</StepThrough>

ผลของหกขั้นสรุปเป็นสองฝั่ง และกฎคือ **attack surface ที่มากขึ้น ต้องแลกด้วยการตรวจความปลอดภัยที่เข้มขึ้น** (Increased Attack Surface means Increased Security Scrutiny)

| Attack surface มาก — ต้องตรวจละเอียด | Attack surface น้อย |
| --- | --- |
| On by default | Off by default |
| Running as SYSTEM | Running with least privilege |
| Open, unauthenticated TCP socket | Open TCP socket limited to local subnet |

ผู้โจมตีเลือกเจาะได้ทั้งสองฝั่ง แต่ฝั่งซ้ายให้มากกว่า เพราะเปิดอยู่เองโดยไม่ต้องรอใครเปิด เจาะสำเร็จแล้วได้สิทธิ์ SYSTEM และไม่ต้องพิสูจน์ตัวตนก่อน ทีมที่ตรวจโค้ดจึงต้องเอาแว่นขยายส่องฝั่งซ้ายก่อน

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ถ้าโค้ดไม่มีบั๊ก การเปิดบริการไว้เป็นค่าเริ่มต้นก็ไม่เสียหายอะไร**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะช่องโหว่ทุกตัวเกิดจากบั๊ก ถ้าไม่มีบั๊กก็ไม่มีช่องโหว่

สิ่งที่ถูกคือ **เราไม่มีวันรู้ว่าโค้ดไม่มีบั๊ก** ใน MS03-007 `NTDLL.DLL` ของ Windows Server 2003 ถูกแก้ไปแล้ว แต่ตารางหกชั้นยังถามต่อว่า "ต่อให้มันยังมีช่องโหว่ล่ะ" แล้ววาง IIS ที่ไม่รันกับ WebDAV ที่ไม่เปิดไว้เป็นชั้นถัดไป สองชั้นนี้ไม่ได้ทำให้โค้ดถูกขึ้น แต่ถ้าการแก้โค้ดพลาด โค้ดที่ผิดก็ไม่มีใครเรียกถึง
</Pitfall>

<Quiz question="เราติดตั้ง database บน server หนึ่งเครื่อง ค่าเริ่มต้นของมันคือฟังพอร์ต 5432 บนทุก network interface รันด้วย root และมีบัญชี admin ที่ไม่มีรหัสผ่าน ถ้าทำ ASR ได้ข้อเดียวก่อน ควรเลือกข้อไหน">
ต้องดูว่าข้อไหนตัดผู้โจมตีออกได้มากที่สุดก่อนเขาจะแตะอย่างอื่นได้ บัญชีที่ไม่มีรหัสผ่านคือประตูที่ไม่ได้ล็อก แต่คนจะเดินมาถึงประตูนั้นได้ก็ต่อเมื่อพอร์ตเปิดให้คนนอกต่อเข้ามา

คำตอบคือ **ให้ฟังเฉพาะ interface ภายใน** (ขั้น "รับคำขอเฉพาะ subnet ภายใน") คนทั้งอินเทอร์เน็ตจึงหายไปจากรายชื่อผู้โจมตีทันที อีกสองข้อยังต้องทำตาม เพราะคนในเครือข่ายเองก็โจมตีได้

คำตอบที่ผิดบ่อยคือ "เปลี่ยนจาก root เป็นผู้ใช้ธรรมดา" ข้อนี้ลดความเสียหายหลังโดนเจาะ แต่ไม่ได้ลดจำนวนคนที่เข้ามาถึงได้ ลำดับของ ASR คือลดคนที่เข้าถึงได้ก่อน แล้วค่อยลดสิ่งที่เขาทำได้
</Quiz>

## ส่วนที่ 4 — Threat Modeling: คิดแบบผู้โจมตีอย่างเป็นขั้นตอน

### Threat ไม่ใช่ Vulnerability

<Why>
ASR ปิดของที่ไม่ใช้ แต่ของที่จำเป็น เช่นหน้า login ยังต้องเปิดอยู่ คำถามต่อไปคือ "ผู้ไม่หวังดีจะทำอะไรกับระบบนี้ได้บ้าง" (What will a bad guy do to your software/system?) และต้องตอบให้ครบก่อนเขียนโค้ด ไม่ใช่หลังโดนเจาะ

หลักคือ **คิดแบบผู้ร้าย แต่อย่าเป็นผู้ร้ายเสียเอง** (Think like a bad guy, but do not be a bad guy yourself)
</Why>

ซอฟต์แวร์ที่ปลอดภัยเริ่มจากการเข้าใจภัย (Secure software starts with understanding the threats) และต้องแยกสามคำนี้ให้ออก

<Term en="Threat" th="ภัยคุกคาม" /> คือ **เป้าหมายของผู้โจมตี** เช่น "เข้าบัญชีของ alice ให้ได้" ภัยไม่มีวันหายไป (Threats live forever) ตราบใดที่บัญชีของ alice ยังมีค่า ก็จะมีคนอยากได้มันเสมอ

<Term en="Vulnerability" th="ช่องโหว่" /> คือ **จุดอ่อนที่ทำให้เป้าหมายนั้นสำเร็จ** เช่นการรั่วทางเวลาของ Prog 2 ช่องโหว่แก้แล้วหายได้ อย่างที่ค่าสุ่มใน Prog 3 ทำ

<Term en="Mitigation" th="สิ่งที่กั้นภัยไว้" /> คือ **สิ่งที่กั้นภัยไว้ก่อนถึงช่องโหว่** เช่นจำกัดจำนวนครั้งที่ลอง login ได้ต่อชั่วโมง Prog 2 ยังรั่วอยู่ และลองครั้งเดียวก็แยกชื่อได้ (90.6 ms กับ 0.0 ms) แต่ผู้โจมตีไล่ชื่อได้ช้าลงมาก

ภัยที่วิ่งไปเจอ mitigation จะหยุดอยู่ตรงนั้น ภัยที่วิ่งไปเจอช่องโหว่โดยไม่มีอะไรกั้น จะไปถึง <Term en="Asset" th="ของที่ต้องปกป้อง" />

**Threats are not vulnerabilities** เพราะแก้ช่องโหว่หมดแล้วภัยก็ยังอยู่ รอช่องโหว่ใหม่ในรุ่นถัดไป

### กระบวนการสี่ขั้น

การทำ threat model มีสี่ขั้น ข้างล่างนี้ลองทำกับระบบ login ของส่วนที่ 2 ไปพร้อมกัน

#### ขั้นที่ 1 — Gather Background Info

เก็บข้อมูลพื้นฐานของระบบสามอย่าง

- **Use-scenarios** — ระบบถูกใช้ยังไง เช่นผู้ใช้กรอกชื่อและรหัสผ่านผ่านหน้าเว็บ
- **Bound scope** — ขีดขอบเขตว่าครั้งนี้ดูถึงไหน เช่นดูแค่การ login ไม่รวมการสมัครสมาชิก
- **Determine dependencies** — ระบบพึ่งอะไรอยู่ เช่นที่เก็บรหัสผ่าน

#### ขั้นที่ 2 — Model the System

วาดระบบเป็น <Term en="Data Flow Diagram" th="แผนภาพการไหลของข้อมูล" /> หรือ DFD ซึ่งมีของสี่ชนิด

| ชนิด | วาดเป็น | ในระบบ login |
| --- | --- | --- |
| Interactor (external entity) — คนหรือระบบนอกที่เราคุมไม่ได้ | สี่เหลี่ยม | ผู้ใช้ |
| Process — โค้ดที่ทำงาน | วงกลม | โปรแกรม login |
| Data Store — ที่เก็บข้อมูล | เส้นขนานสองเส้น | ที่เก็บ hash ของรหัสผ่าน |
| Data Flow — ข้อมูลที่วิ่งระหว่างของสามชนิดข้างบน | ลูกศร | ผู้ใช้ → login (ชื่อ, รหัส), login → ผู้ใช้ (ผล), login → ที่เก็บ (ค้นชื่อ), ที่เก็บ → login (hash) |

จาก DFD ให้ชี้สามอย่าง <Term en="Entry Point" th="ทางที่ข้อมูลจากข้างนอกเข้ามา" /> คือทางที่ข้อมูลจากข้างนอกเข้ามา **assets** คือของที่ต้องปกป้อง และ <Term en="Threat Path" th="ทางที่ผู้โจมตีเดินไปถึงของ" /> คือทางที่ผู้โจมตีเดินจาก entry point ไปถึง asset

ในระบบ login entry point คือช่องกรอกชื่อและรหัสผ่าน asset คือบัญชีของ alice และ hash ในที่เก็บ threat path หนึ่งเส้นคือผู้โจมตีกรอกชื่อทีละชื่อที่ช่องนั้น แล้วจับเวลาคำตอบของ Prog 2 จนรู้ว่าบัญชีไหนมีอยู่จริง

#### ขั้นที่ 3 — Identify Threats

ขั้นนี้ใช้เครื่องมือสามอย่าง คือชนิดของภัย (STRIDE) threat tree และความเสี่ยง (risk) หัวข้อถัดไปอธิบายทีละตัว แล้วจึงถึงขั้นที่ 4 เพราะการเลือกว่าจะทำอะไรกับภัยแต่ละข้อต้องรู้ความเสี่ยงของมันก่อน

### STRIDE: ภัยหกชนิด และ mitigation ของแต่ละชนิด

<Why>
ถ้าถามลอย ๆ ว่า "ระบบ login นี้โดนอะไรได้บ้าง" คนส่วนใหญ่นึกถึงการเดารหัสผ่านแล้วหยุดแค่นั้น ภัยอย่าง "alice อ้างว่าไม่ได้ login ตอนตีสาม และเราไม่มี log พิสูจน์" แทบไม่มีใครนึกออก ถ้าไม่มีรายการให้ไล่ทีละข้อ
</Why>

<Term en="STRIDE" th="ตัวย่อของภัยหกชนิด" /> คือรายการนั้น เป็นภัยหกชนิดที่เกิดกับซอฟต์แวร์และระบบ แต่ละชนิดทำลายคุณสมบัติหนึ่งข้อ และ mitigation ของมันคือคุณสมบัติข้อนั้นเอง

| ภัย | ความหมาย | ในระบบ login | Mitigation |
| --- | --- | --- | --- |
| **S**poofing | ปลอมเป็นคนอื่น | เข้าเป็น alice ด้วยรหัสที่เดาได้ | Authentication |
| **T**ampering | แก้ข้อมูลโดยไม่มีสิทธิ์ | แก้ hash ในที่เก็บให้เป็นของรหัสที่ตัวเองรู้ | Integrity |
| **R**epudiation | ปฏิเสธว่าไม่ได้ทำ | alice อ้างว่าไม่ได้ login ตอนตีสาม และไม่มี log พิสูจน์ | Nonrepudiation |
| **I**nformation Disclosure | ข้อมูลรั่วถึงคนที่ไม่ควรรู้ | Prog 1 และ Prog 2 เฉลยว่าชื่อไหนมีอยู่จริง | Confidentiality |
| **D**enial of Service | ทำให้ใช้งานไม่ได้ | ยิงคำขอ login จนเครื่องคำนวณ hash ไม่ทัน | Availability |
| **E**levation of Privilege | ได้สิทธิ์สูงกว่าที่ควรได้ | ผู้ใช้ธรรมดาได้สิทธิ์ admin | Authorization |

คอลัมน์สุดท้ายคือชิ้นส่วนเดิมจากส่วนที่ 1 ทั้งหมด คือ Authentication, Authorization ที่แตกเป็น Confidentiality, Integrity, Availability และ Nonrepudiation ซึ่งได้มาจาก Auditing กับลายเซ็นดิจิทัล ([Lecture 7](/2110413-csy/lecture-7#ส่วนที่-1--ช่องเดียวที่การเข้ารหัสยังปิดไม่ได้))

Threat modeling จึงบอกว่า **ชิ้นส่วนไหนต้องไปวางไว้ตรงไหน** ส่วนหลักที่ใช้เลือก mitigation แต่ละตัวอยู่ใน[สิบหลักการของ Lecture 1](/2110413-csy/lecture-1#ส่วนที่-4--สิบหลักการความปลอดภัย)

### ของแต่ละชนิดใน DFD โดนภัยคนละชุด

ของแต่ละชิ้นใน DFD โดนภัยได้หนึ่งชนิดขึ้นไป แต่ไม่ใช่ทุกชนิด เพราะภัยบางชนิดไม่มีความหมายกับของบางอย่าง เช่น data flow ปลอมตัวเป็นใครไม่ได้

| ชนิดของ | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| Data Flow | | ✓ | | ✓ | ✓ | |
| Data Store | | ✓ | | ✓ | ✓ | |
| Interactor | ✓ | | ✓ | | | |
| Process | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

ป้ายสั้นที่แปะบน DFD จึงมีสามแบบ คือ **SR** บน interactor, **TID** บน data flow และ data store, **STRIDE** บน process

**ทุก ✓ คือภัยที่อาจเกิดกับระบบหนึ่งข้อ** และภัยแต่ละข้อเกิดได้ก็ต่อเมื่อมีเงื่อนไขบางอย่างเป็นจริง หัวข้อถัดไปจะไล่หาเงื่อนไขพวกนั้น

### Threat Tree: ภัยหนึ่งข้อเกิดได้จากเงื่อนไขอะไรบ้าง

<Why>
ภัยข้อเดียวอย่าง "เข้าเป็น alice" เกิดได้หลายทาง เดารหัสผ่าน ขโมยไฟล์ hash ดักรหัสระหว่างทาง หรือรู้ก่อนว่า alice มีบัญชีแล้วค่อยเดา ปิดไปสามทางแล้ว จะรู้ได้ยังไงว่าไม่มีทางที่สี่เหลืออยู่
</Why>

<Term en="Threat Tree" th="แผนภาพเงื่อนไขที่ทำให้ภัยเกิด" /> วางภัยไว้ที่ราก แล้วแตกกิ่งลงเป็น **เงื่อนไข (condition)** ที่ทำให้ภัยนั้นเกิดได้ กิ่งมีสองแบบ

- **Or clause** — ลูกข้อใดข้อหนึ่งเป็นจริงก็พอ วาดเป็นเส้นแยกธรรมดา
- **And clause** — ลูกทุกข้อต้องเป็นจริงพร้อมกัน วาดเป็นเส้นแยกที่มีส่วนโค้งคาดทับ

กิ่ง And เป็นข่าวดีของฝ่ายป้องกัน เพราะตัดลูกข้อเดียวก็ตัดทั้งกิ่ง ส่วนกิ่ง Or ต้องปิดลูกทุกข้อ

ตัวอย่างจากส่วนที่ 2 คือกิ่ง "รู้ว่า alice มีบัญชี ผ่าน Prog 2" ซึ่งต้องจริงสองข้อพร้อมกัน คือโปรแกรมออกเร็วเมื่อไม่มีชื่อนี้ **และ** ผู้โจมตีจับเวลาได้ กิ่งนี้จึงเป็น And Prog 3 ตัดข้อแรกทิ้งข้อเดียว กิ่งนี้ก็หายไปทั้งกิ่ง ถึงผู้โจมตีจะยังจับเวลาได้ก็ตาม

ต้นไม้ไม่ต้องคิดใหม่ทุกครั้ง ภัยแต่ละชนิดมี **threat tree pattern** ให้หยิบมาใช้ pattern ของ **Spoofing Interactor or Process** แตกเป็นสี่กิ่ง ทุกกิ่งพูดถึง <Term en="Credential" th="ของที่ใช้พิสูจน์ตัวตน" /> เช่นรหัสผ่าน

| กิ่ง | เงื่อนไขย่อย |
| --- | --- |
| Obtain legitimate credentials — ได้ credential ของจริงมา | Weak storage (ฝั่ง server หรือฝั่ง client), Weak transit, Weak change management |
| Falsify credentials — ปลอม credential | Guessed, Equivalence |
| Leverage insufficient authentication — อาศัยการพิสูจน์ตัวตนที่อ่อน | Null credentials, Downgrade authentication, Predictable credentials, Tampering threats against auth process |
| No authentication system — ไม่มีระบบพิสูจน์ตัวตนเลย | Secure channel (ยังเหลือ tampering และ information disclosure threats against data flows), Non-secure channel |

วิธีใช้คือแปะคำถามไว้ที่เงื่อนไขแต่ละข้อ แล้วเอาไปถามระบบของเรา กิ่งไหนไม่เกี่ยวก็ตัดทิ้ง ต้นไม้ของ **Spoofing User** ข้างล่างตัดกิ่ง No authentication system ทิ้ง เพราะระบบมีระบบพิสูจน์ตัวตนอยู่แล้ว (There is an authentication system, so this threat tree doesn't apply)

| เงื่อนไข | คำถามที่ต้องตอบให้ได้ |
| --- | --- |
| Weak storage — server | Where are the password stored on the server? — รหัสผ่านเก็บไว้ที่ไหนบน server |
| Weak storage — client | Are credentials stored on the client? If so, how? — client เก็บ credential ไว้ไหม ถ้าเก็บ เก็บยังไง เช่น client บน Mac มักเก็บรหัสผ่านไว้ใน alias (ไฟล์ทางลัดของ Mac) |
| Weak transit | How are credentials transmitted to the server? — credential ถูกส่งไปถึง server ยังไง |
| Weak change management | How are credentials changed? — เปลี่ยน credential ยังไง |
| Guessed | Are there password quality features? — มีอะไรบังคับให้รหัสผ่านเดายากไหม |
| Equivalence | Are there agency relationships? What if the client is acting as a server itself? Can a request to user1 (in its server role) cause it to automatically authenticate as a client? — มีเครื่องที่ทำงานแทนกันไหม ถ้า client ทำหน้าที่เป็น server ด้วยล่ะ คำขอที่ส่งไปหา user1 ในบทบาท server ทำให้มันพิสูจน์ตัวตนออกไปในฐานะ client โดยอัตโนมัติได้ไหม |
| Null credentials | Are null credentials possible? — credential ว่างใช้ได้ไหม |
| Downgrade authentication | Is there more than one authentication method, and if so, is it negotiable? — มีวิธีพิสูจน์ตัวตนมากกว่าหนึ่งวิธีไหม ถ้ามี ต่อรองเลือกวิธีได้ไหม |
| Predictable credentials | Are the credentials a function of the username? Client address? Time? — credential คำนวณได้จากชื่อผู้ใช้ ที่อยู่ของ client หรือเวลาไหม |

<Quiz question="เงื่อนไข 'Weak storage — server' จะทำให้ผู้โจมตีได้รหัสผ่านของ alice ไปใช้ได้จริง ต้องมีอะไรเป็นจริงบ้าง กิ่งนี้เป็น And หรือ Or">
รหัสผ่านที่เก็บอยู่บน server อย่างเดียวยังไม่พอ ผู้โจมตีต้องได้ไฟล์ที่เก็บรหัสผ่านมาก่อน และไฟล์นั้นต้องถอดกลับเป็นรหัสผ่านได้ในเวลาที่รับได้ เช่นเก็บเป็นข้อความตรง ๆ หรือเป็น hash ที่ไม่มี salt ([Lecture 3](/2110413-csy/lecture-3#รหัสผ่านถูกเก็บยังไง))

คำตอบคือ **เป็นกิ่ง And** "ได้ไฟล์มา" และ "ไฟล์ถอดได้" ต้องจริงพร้อมกัน ฝ่ายป้องกันจึงตัดกิ่งนี้ได้ด้วยการปิดข้อใดข้อหนึ่ง และ hash ที่ช้ากับ salt ปิดข้อที่สองได้ แม้ไฟล์จะหลุดไปแล้ว

คำตอบที่ผิดบ่อยคือ "เป็น Or เพราะมีหลายวิธีที่จะได้ไฟล์มา" วิธีขโมยไฟล์หลายวิธีต่อกันแบบ Or ก็จริง แต่อยู่ใต้ข้อ "ได้ไฟล์มา" ข้อเดียว และข้อนั้นยังต้องคู่กับข้อที่สองแบบ And
</Quiz>

### ให้คะแนนความเสี่ยงเป็นตัวเลข

ภัยที่ไล่ได้มีหลายสิบข้อ และแก้ไม่ทันทุกข้อ จึงมีวิธีให้คะแนนความเสี่ยงเป็นตัวเลข เช่น <Term en="DREAD" th="ให้คะแนนความเสี่ยงห้าด้าน" />

DREAD ให้คะแนนห้าด้าน คือ Damage (เสียหายแค่ไหน), Reproducibility (ทำซ้ำง่ายไหม), Exploitability (ลงมือยากไหม), Affected users (กระทบคนกี่คน) และ Discoverability (หาเจอง่ายไหม)

ปัญหาของการให้คะแนนแบบนี้มีสามข้อ

- **Very subjective** — คนสองคนให้คะแนนภัยเดียวกันได้คนละค่า
- **มักต้องให้ผู้เชี่ยวชาญด้านความปลอดภัยเป็นคนประเมิน** ลองตอบดูว่า ในสเกล 0.0 ถึง 1.0 ผู้โจมตีมีโอกาสเข้าถึง private key ได้แค่ไหน คนทั่วไปไม่มีพื้นให้ตอบ
- **จะขีดเส้นตรงไหน** ถ้าตั้งว่าแก้ทุกข้อที่เสี่ยงเกิน 0.4 แล้วข้อที่ต่ำกว่าติดป้าย "Won't Fix" ทั้งหมด ข้อที่ได้ 0.39 กับ 0.41 ต่างกันจริง หรือแค่คนให้คะแนนอารมณ์ไม่เหมือนกัน

สเกล 0.0 ถึง 1.0 ในคำถามข้อสองคือความน่าจะเป็น 0.0 คือไม่มีทางเกิด และ 1.0 คือเกิดแน่นอน

### ขั้นที่ 4 — Resolve Threats

ภัยแต่ละข้อที่พบและให้คะแนนแล้ว ต้องตัดสินว่าจะทำอะไรกับมัน มีสี่ทาง

- **Fix** — แก้ให้หาย เช่นแก้ Prog 2 เป็น Prog 3
- **Work-around** — อ้อมไป เช่นจำกัดจำนวนครั้งที่ลอง login ได้ ช่องโหว่ยังอยู่ แต่ไล่ชื่อได้ช้าลง
- **Notification** — แจ้งผู้ใช้หรือผู้ดูแลให้รู้ความเสี่ยง
- **Do nothing** — ยอมรับความเสี่ยงไว้ ถ้าคุ้มกว่าการแก้ ซึ่งต้องรู้คะแนนความเสี่ยงของภัยข้อนั้นก่อนถึงจะตัดสินได้

### Threat Model Checklist

- **No design is complete without a threat model!** — งานออกแบบที่ไม่มี threat model ยังไม่เสร็จ
- **Follow anonymous data paths** — ไล่ทุกเส้นทางที่ข้อมูลจากคนที่ยังไม่พิสูจน์ตัวตนวิ่งเข้ามาได้ เพราะใครในโลกก็ใช้เส้นทางนั้นได้
- **Every threat needs a security test plan** — ภัยทุกข้อต้องมีแผนทดสอบว่ามันถูกกันไว้จริง
- **Check all information disclosure threats – are they privacy issues?** — ข้อมูลที่รั่วเป็นข้อมูลส่วนตัวของใครหรือเปล่า
- **Be wary of elevated processes** — ระวัง process ที่รันด้วยสิทธิ์สูง เพราะถ้าโดนยึด ผู้โจมตีได้สิทธิ์นั้นไปทั้งหมด
- **Use the threat modeling tool** — ใช้เครื่องมือช่วยทำ threat model

<Quiz question="แอปจองห้องสมุดมีหน้าค้นหนังสือที่ไม่ต้อง login และหน้าจองที่ต้อง login ถ้ามีเวลาทำ threat model ได้แค่ส่วนเดียว ควรเริ่มที่หน้าไหน และเป็นของชนิดไหนใน DFD">
หน้าค้นหนังสือรับข้อมูลจากใครก็ได้ในโลกโดยไม่ต้องพิสูจน์ตัวตน จึงเป็น anonymous data path ในข้อที่สองของ checklist และคำค้นที่ผู้ใช้พิมพ์วิ่งไปถึง process ที่ค้นฐานข้อมูล

คำตอบคือ **เริ่มที่หน้าค้นหนังสือ** ส่วนที่ต้องไล่คือ data flow จากผู้ใช้ (TID) และ process ที่ค้น (STRIDE ครบหกข้อ) เพราะ process เป็นของชนิดเดียวที่โดนได้ทุกภัย

คำตอบที่ผิดบ่อยคือ "หน้าจอง เพราะมีข้อมูลสำคัญกว่า" แต่หน้าจองมี authentication กั้นอยู่แล้วหนึ่งชั้น ส่วนหน้าค้นเปิดให้คนทั้งโลกยิงเข้ามาตรง ๆ และ process นั้นอาจต่อกับฐานข้อมูลเดียวกับหน้าจอง
</Quiz>

## ส่วนที่ 5 — Input ทุกตัวเป็นของร้าย

### ทำไม input ถึงสำคัญ

> All input is evil, until proven otherwise.
>
> input ทุกตัวเป็นของร้าย จนกว่าจะพิสูจน์ได้ว่าไม่ใช่
>
> — Michael Howard, Microsoft

<Why>
AAA ตอบคำถาม "ใครทำอะไรได้ เมื่อไหร่" โดยไม่ได้ดูเลยว่า **ข้อมูล** ที่คนคนนั้นส่งเข้ามาหน้าตาเป็นยังไง ผู้ใช้ที่ login ถูกต้องและมีสิทธิ์ค้นหา ก็ยังส่งข้อความที่ทำให้ระบบทำสิ่งที่ไม่มีใครอนุญาตได้

**ข้อมูลเป็นอันตรายได้** แม้คนที่ส่งมาจะผ่านทั้งสามด่านแล้ว
</Why>

ปัญหาจาก input ที่เจอบ่อยมีสามแบบ

- <Term en="SQL Injection" th="แทรกคำสั่ง SQL ผ่าน input" /> — input ถูกเอาไปต่อเป็นคำสั่งฐานข้อมูล แล้วกลายเป็นส่วนหนึ่งของคำสั่ง หัวข้อถัดไปลงรายละเอียด
- <Term en="Cross-Site Scripting" th="แทรกสคริปต์ลงหน้าเว็บ" /> (XSS) — input ถูกเอาไปแสดงบนหน้าเว็บโดยไม่แปลง เบราว์เซอร์ของผู้ชมคนอื่นจึงรันมันเป็น JavaScript รายละเอียดอยู่ใน [Lecture 13](/2110413-csy/lecture-13)
- **Buffer-Overflow Attacks** — buffer overrun แบบเดียวกับ MS03-007 ในส่วนที่ 3

### ทำไมการต่อข้อความถึงผิด

โค้ดค้นสถานะพัสดุข้างล่างสร้างคำสั่ง SQL ด้วยการเอาเลขที่ผู้ใช้กรอก (`Id`) ไปต่อตรง ๆ

```text
sqlstring="SELECT HasShipped" +
        " FROM Shipment WHERE ID='" + Id + "'";
```

ผู้ใช้สี่คนกรอกสี่แบบ

| ผู้ใช้ | กรอกว่า | คำสั่งที่ได้ |
| --- | --- | --- |
| Good Guy | `1001` | `SELECT HasShipped FROM Shipment WHERE ID='1001'` |
| Not so Good Guy | `1001' or 2>1 --` | `... WHERE ID= '1001' or 2>1 -- '` |
| Really Bad Guy | `1001' drop table orders --` | `... WHERE ID= '1001' drop table orders -- '` |
| Downright Evil Guy | `1001' exec xp_cmdshell('...') --` | `... WHERE ID= '1001' exec xp_cmdshell('...') -- '` |

กลไกมีสามชิ้น

- `'` ปิดข้อความที่โปรแกรมเปิดไว้ก่อนเวลา
- ข้อความหลังจากนั้นจึงกลายเป็นคำสั่ง
- `--` ทำให้ส่วนที่เหลือของบรรทัดเป็น comment เครื่องหมาย `'` ตัวสุดท้ายของโปรแกรมจึงไม่ทำให้คำสั่งพัง

ลองทายก่อน: คนที่สองไม่รู้เลขพัสดุของใครนอกจาก `1001` เขาจะได้ผลลัพธ์กี่แถว

```text
SQL : SELECT HasShipped FROM Shipment WHERE ID='1001'
rows: [(1,)]
SQL : SELECT HasShipped FROM Shipment WHERE ID='1001' or 2>1 --'
rows: [(1,), (0,), (1,)]
```

ผลนี้ได้จากการรันโค้ดเดียวกันบน SQLite ที่มีพัสดุสามรายการ `2>1` จริงเสมอ คนที่สองจึงได้ **ทุกแถวในตาราง**

คนที่สามสั่งลบตาราง `orders` ทั้งตาราง

คนที่สี่เรียก `xp_cmdshell` ซึ่งเป็นคำสั่งของ Microsoft SQL Server ที่สั่งรันคำสั่งของระบบปฏิบัติการ เขากรอก `exec xp_cmdshell('net user add URHacked Pa$sw0rd')` แล้วตามด้วย `exec xp_cmdshell('net localgroup admins URHacked /add')` คือสร้างบัญชีใหม่บนเครื่อง แล้วจับบัญชีนั้นเข้ากลุ่มผู้ดูแลระบบ จากช่องค้นพัสดุช่องเดียว ผู้โจมตีกลายเป็น admin ของ server

สองคำสั่งนั้นเขียนไม่ตรงกับไวยากรณ์จริง บน Windows ต้องเขียน `net user URHacked Pa$sw0rd /add` และกลุ่มผู้ดูแลชื่อ `Administrators` แต่เจตนายังเหมือนเดิม

#### ป้ายทะเบียนรถก็เป็น input

input ไม่ได้มาจากคีย์บอร์ดเสมอไป กล้องจับความเร็วอ่านป้ายทะเบียนรถเป็นตัวอักษร เช่นอ่านได้ `DW 530GS` แล้วขึ้นป้ายเตือนให้ชะลอ ตัวอักษรที่อ่านได้มักถูกเอาไปต่อเป็นคำสั่งค้นฐานข้อมูล

ถ้าเจ้าของรถทำป้ายทะเบียนเป็น `'OR 1=1;--` คำสั่งที่ออกมาจะเป็น

```sql
SELECT * FROM car WHERE plateno=''OR 1=1;--'
```

กลไกเดียวกับข้างบน เพิ่มแค่ `;` ที่จบคำสั่ง `1=1` จริงเสมอ คำสั่งนี้จึงคืนรถ **ทุกคัน** ในตาราง

อีกป้ายหนึ่งต่อท้ายเลขทะเบียนด้วย `', 0, 0);` แล้วตามด้วย `DROP DATABASE` ป้ายนี้เล็งคำสั่ง INSERT ซึ่งเขียนค่าที่จะบันทึกไว้ในวงเล็บ มันปิดข้อความด้วย `'` เติมค่าของคอลัมน์ที่เหลือ (`0, 0`) แล้วปิดวงเล็บและจบคำสั่งเดิม ก่อนจะสั่ง `DROP DATABASE` ลบทั้งฐานข้อมูล

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ฐานข้อมูลของเราไม่ยอมรันสองคำสั่งต่อกัน จึงไม่ต้องกลัว SQL injection**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะคำสั่งของคนที่สามรันไม่ได้บนหลายระบบ บน SQLite ผ่าน Python ได้ `OperationalError near "drop": syntax error` ต่อให้เติม `;` คั่นก็ยังได้ `You can only execute one statement at a time.` แต่บน SQL Server ที่ตัวอย่างนี้ตั้งใจใช้ สองคำสั่งต่อกันได้โดยไม่ต้องมี `;`

สิ่งที่ถูกคือ **คนที่สองไม่ได้ต่อคำสั่งใหม่เลย** เขาแค่แก้เงื่อนไข `WHERE` ของคำสั่งเดิม ซึ่งทำได้บนทุกระบบ และอ่านข้อมูลทั้งตารางออกไปได้อย่างที่เห็นข้างบน
</Pitfall>

### Input Validation สี่แบบ

**Validate all input.** ตรวจ input ทุกตัว ด้วยการตรวจสี่แบบ

| การตรวจ | ตรวจอะไร | ตัวอย่าง input ที่ถูกตีกลับ |
| --- | --- | --- |
| Type Checks | ชนิดของข้อมูล เช่นต้องเป็นตัวเลขเท่านั้น (numeric only) | `1001' or 2>1 --` |
| Length Checks | ความยาว | `100000000000000000001` (ตัวเลขล้วน แต่ยาว 21 หลัก) |
| Range Checks | ค่าอยู่ในช่วงที่ยอมรับ เช่นตัวอักษร A ถึง z | `0999` (สี่หลัก แต่ต่ำกว่า 1000) |
| Format Checks | รูปแบบ เช่นต้องเป็นอีเมล | `somchai@` ในช่องอีเมล |

สามแถวแรกเป็นช่องเลขพัสดุสี่หลัก 1000–9999 แต่ละแถวผ่านการตรวจแบบก่อนหน้ามาแล้ว แต่ถูกตีกลับด้วยการตรวจของแถวนั้น แถวสุดท้ายเป็นช่องอีเมล

**การทดสอบความปลอดภัย (security testing)** อยู่นอกขอบเขตของบทนี้ วิธีทดสอบเว็บแอปอยู่ใน[ส่วนที่ 7 ของ Lecture 13](/2110413-csy/lecture-13#ส่วนที่-7--ทดสอบเว็บแอป)

<Callout type="info" title="ทางแก้ SQL injection ที่ตรงที่สุด">
บทนี้ไม่ได้พูดถึง <Term en="Parameterized Query" th="คำสั่งที่ส่งค่าแยกจากตัวคำสั่ง" /> คือเขียนคำสั่งเป็น `SELECT HasShipped FROM Shipment WHERE ID=?` แล้วส่งค่า `Id` แยกไปอีกช่อง ฐานข้อมูลจึงถือค่านั้นเป็นข้อมูลเสมอ ไม่มีทางกลายเป็นคำสั่ง

ส่ง `1001' or 2>1 --` เข้าไปแบบนี้บน SQLite ได้ศูนย์แถว เพราะไม่มีพัสดุที่ ID เป็นข้อความทั้งก้อนนั้น แต่ยังต้องตรวจ input คู่กันเสมอ เพราะ XSS และ buffer overflow ไม่ได้ผ่านฐานข้อมูล
</Callout>

<Quiz question="ช่องกรอกชื่อจริงตรวจด้วยเงื่อนไข 'ตัวอักษร A ถึง z เท่านั้น' (regex [A-z]+) ชื่อ Som_chai, Som\chai และ Som'chai อันไหนผ่านบ้าง">
ช่วง A ถึง z ในตาราง ASCII ไม่ได้มีแค่ตัวอักษร ระหว่าง `Z` (รหัส 90) กับ `a` (รหัส 97) มีอักขระอีกหกตัวคือ `` [ \ ] ^ _ ` `` ช่วงนี้จึงรับหกตัวนั้นไปด้วย

คำตอบคือ **`Som_chai` กับ `Som\chai` ผ่าน ส่วน `Som'chai` ไม่ผ่าน** (รันด้วย `re.fullmatch('[A-z]+', ...)` ใน Python) ตัวตรวจยังกัน `'` ได้ แต่ปล่อย `\` ซึ่งเป็นตัว escape ในฐานข้อมูลบางตัวเข้ามา ช่วงที่ตั้งใจต้องเขียนเป็น `[A-Za-z]`

คำตอบที่ผิดบ่อยคือ "ไม่ผ่านทั้งสามชื่อ เพราะมีอักขระที่ไม่ใช่ตัวอักษร" ซึ่งเชื่อชื่อของช่วง แทนที่จะดูว่าช่วงนั้นครอบรหัสอะไรบ้าง
</Quiz>

## ส่วนที่ 6 — Secure by Design ของจริงที่ Microsoft

### จาก "evil empire" สู่ Secure by Design

- ก่อนยุค Windows Server 2003 และ Windows XP Service Pack 2 Microsoft ถูกเรียกอย่างเสีย ๆ หาย ๆ ว่า **evil empire**
- **Microsoft เคยขายฟังก์ชัน ไม่ได้ขายความปลอดภัย**
- **Mike Howard (Michael Howard) และทีมของเขา** นำ Microsoft ไปสู่ Secure by Design
- **Microsoft ใช้ Secure by Design มาตั้งแต่ปี 2004**

ทีมที่ดูแลเรื่องนี้ชื่อ **The Security Engineering & Communications Group** มีหน้าที่ช่วยทีมผลิตภัณฑ์อื่นทำของให้ปลอดภัย (Help you secure your products)

ทีมนี้นิยามงานของตัวเองว่า **"Security-as-in-threats" ไม่ใช่ "Security-as-in-crypto"** คือมองความปลอดภัยเป็นเรื่องของภัยที่ต้องรับมือแบบในส่วนที่ 4 ไม่ใช่เรื่องการเลือกอัลกอริทึมเข้ารหัส

ทีมอยู่ใต้ <Term en="Trustworthy Computing" th="โครงการความน่าเชื่อถือของ Microsoft" /> ซึ่งมีสี่เสา คือ **Security, Privacy, Reliability และ Business Integrity** ช่องทางติดต่อทีมคือ `mailto:switeam`, `http://swi` และ `http://msnsecurity/sdl`

### Security Development Lifecycle

<Term en="Security Development Lifecycle" th="วงจรพัฒนาที่ใส่งานความปลอดภัย" /> หรือ SDL คือการวางงานด้านความปลอดภัยซ้อนบนวงจรพัฒนาซอฟต์แวร์แบบเดิมของ Microsoft ทีละช่วง โดยมี **Security Training** คลุมช่วงต้นทั้งหมด

| ช่วง | งานเดิม | งานความปลอดภัยที่เพิ่มเข้ามา |
| --- | --- | --- |
| Requirements | feature lists, quality guidelines, architecture docs, schedules | Security Kickoff & Register with SWI |
| Design | functional specifications, design specifications | Security Design Best Practices, Security Architecture & Attack Surface Review, **Threat Modeling** |
| Implementation | development of new code | Use Security Development Tools & Security Best Dev & Test Practices, Create Security Documentation and Tools for Product |
| Verification | testing and verification, bug fixes | Prepare Security Response Plan, Security Push, Pen Testing, Final Security Review |
| Release | code signing & checkpoint express signoff, RTM | — |
| Support & Servicing | product support, service packs/QFEs, security updates | Security Servicing & Response Execution |

ตัวย่อในตาราง

- **SWI** — Secure Windows Initiative ทีมความปลอดภัยของ Windows
- **RTM** — Release to Manufacturing รุ่นที่ส่งออกขาย
- **QFE** — patch แก้ปัญหาเฉพาะจุด
- **Security Push** — ช่วงหยุดเขียนฟีเจอร์เพื่อไล่หาช่องโหว่ แบบเดียวกับ Windows Security Push ในส่วนที่ 3

**Threat Modeling** อยู่ในช่วง Design ซึ่งคือเนื้อหาของส่วนที่ 4 และ Attack Surface Review ในช่วงเดียวกันคือเนื้อหาของส่วนที่ 3 สองงานนี้อยู่ก่อนเขียนโค้ดบรรทัดแรก ซึ่งคือความหมายตรงตัวของคำว่า by design

### ผลลัพธ์ที่วัดได้

| ระบบ | ใช้ SDL | bulletin ใน 455 วัน |
| --- | --- | --- |
| Windows 2000 Servers | ไม่ใช้ | **55** |
| Windows Server 2003 | ใช้ | **17** |

bulletin ของ Windows 2000 Servers เพิ่มขึ้นเรื่อย ๆ ตลอด 455 วันจนถึง 55 ส่วนของ Windows Server 2003 แทบไม่เพิ่มเลยเกือบทั้งช่วง แล้วค่อยขึ้นไปถึง 17 ตอนท้าย

- **Prog 2** ถามครบแต่ออกเร็วถ้าไม่มีชื่อ → รั่วทางเวลา (วัดได้ 90 ms กับ 0 ms)
- **Prog 3** ไม่มีชื่อก็เทียบกับ **ค่าสุ่ม** → ทุกกรณีเหมือนกัน
- Secure by Design = **plan more than functionality**, **attack surface reduction**, **threats & risk modeling**

**[ลดพื้นที่ที่เปิดให้โจมตี](#ส่วนที่-3--ลดพื้นที่ที่เปิดให้โจมตี)**

- **Attack surface** = เป้าหมายทั้งหมดที่ผู้โจมตีเข้าถึงได้ แบ่งเป็นชั้นคน เครือข่าย ตัวระบบ
- ASR = **Defense in Depth + Least Privilege + Secure Defaults** (less code running = less stuff to attack)
- **MS03-007**: Windows Server 2003 รอดด้วยหกชั้น — โค้ดแก้แล้ว, IIS 6.0 ปิด, WebDAV ปิด, URL สูงสุด 16 KB (ต้องใช้ >64 KB), `-GS`, สิทธิ์แค่ network service
- Secure defaults: Slammer และ CodeRed จะไม่เกิด, critical อาจเหลือ important, ไม่มี single point of failure, ลูกค้าไม่ต้อง harden, งานทดสอบลดลง
- ASR ทีละขั้น: ปิดพอร์ต → ปิด UDP → จำกัด IP/subnet → authenticate → ลดสิทธิ์ (Manual, Network Service) → harden ACL
- **Increased attack surface = increased security scrutiny**

**[Threat Modeling](#ส่วนที่-4--threat-modeling-คิดแบบผู้โจมตีอย่างเป็นขั้นตอน)**

- Think like a bad guy (but do not be one) · **Threats are not vulnerabilities, threats live forever**
- สี่ขั้น: **Gather background info → Model the system (DFD) → Identify threats (STRIDE, threat trees, risk) → Resolve (fix, work-around, notification, do nothing)**
- **STRIDE** → mitigation: Spoofing–Authentication, Tampering–Integrity, Repudiation–Nonrepudiation, Information Disclosure–Confidentiality, DoS–Availability, Elevation of Privilege–Authorization
- DFD: interactor **SR**, data flow และ data store **TID**, process **STRIDE** ทุก ✓ คือภัยหนึ่งข้อ
- Threat tree มีกิ่ง **And** (ต้องจริงทุกข้อ) กับ **Or** (ข้อเดียวพอ) และมี pattern สำเร็จรูป เช่น spoofing สี่กิ่ง
- **DREAD** ให้คะแนนได้ แต่ subjective ต้องใช้ผู้เชี่ยวชาญ และเส้นแบ่งอย่าง 0.4 ขีดยาก
- Checklist: ไม่มี threat model = ออกแบบยังไม่เสร็จ, ไล่ anonymous data paths, ทุกภัยต้องมี test plan, เช็ก information disclosure ว่าเป็นเรื่อง privacy ไหม, ระวัง elevated processes, ใช้เครื่องมือ

**[Input ทุกตัวเป็นของร้าย](#ส่วนที่-5--input-ทุกตัวเป็นของร้าย)**

- **"All input is evil, until proven otherwise."** — Michael Howard
- AAA ไม่ได้ดูข้อมูล แต่ **ข้อมูลเป็นอันตรายได้**: SQL injection, XSS, buffer overflow (แม้แต่ป้ายทะเบียนรถ)
- `'` ปิดข้อความ, ส่วนที่ตามมากลายเป็นคำสั่ง, `--` ทิ้งท้ายบรรทัด · `or 2>1` อ่านได้ทั้งตาราง, `xp_cmdshell` ยึดเครื่องได้
- อย่ากรองด้วยการลบคำ: `DELDELETEETE` → `DELETE`
- Validate all input: **Type, Length, Range, Format checks**

**[Microsoft](#ส่วนที่-6--secure-by-design-ของจริงที่-microsoft)**

- เคยถูกเรียก evil empire, เคยขายฟังก์ชันไม่ใช่ความปลอดภัย, ใช้ Secure by Design ตั้งแต่ **2004** นำโดย Mike Howard
