## ส่วนที่ 1 — Public Key: กุญแจคนละดอก

### ปัญหาที่กุญแจเดียวแก้ไม่ได้

โจทย์คือ **อาจารย์คนหนึ่งต้องการแชร์ข้อมูลกับนิสิต 100 คน ต้องใช้กุญแจแบบสมมาตรกี่ดอก ถ้าต้องการพิสูจน์ [integrity](/2110413-csy/lecture-6#นิยาม) ของข้อมูล คือพิสูจน์ว่าเอกสารนี้อาจารย์เป็นคนสร้าง และมีแต่อาจารย์เท่านั้นที่สร้างได้**

คำใบ้คือ **ถ้ามีกุญแจดอกเดียว ใครก็ตามที่มีกุญแจนั้นก็เขียนข้อความได้**

<Quiz question="ต้องใช้กี่ดอก และทำไม">
เหตุผลอยู่ในคำใบ้ ถ้าใช้ดอกเดียวร่วมกันทั้งชั้น นิสิตคนที่ 47 ก็สร้างเอกสารที่ดูเหมือนมาจากอาจารย์ได้ เพราะเขามีกุญแจดอกเดียวกัน จึงพิสูจน์ไม่ได้ว่าใครเป็นคนเขียน

ต้องแยกดอกต่อคน กุญแจดอกที่ 47 มีแค่อาจารย์กับนิสิตคนที่ 47 ที่ถือ นิสิตคนที่ 47 จึงรู้ว่าข้อความที่เปิดด้วยดอกนี้ได้ต้องมาจากอาจารย์ เพราะอีกคนเดียวที่ถือดอกนี้คือตัวเขาเอง

คำตอบคือ **100 ดอก** คือดอกละคน

คำตอบที่ผิดบ่อยคือ **1 ดอก** ซึ่งพอสำหรับเก็บความลับจากคนนอกชั้น แต่พิสูจน์ไม่ได้ว่าใครในชั้นเป็นคนเขียน
</Quiz>

คำตอบ 100 ดอกย้ายปัญหาไปที่อื่น ไม่ได้ทำให้มันหายไป

- อาจารย์ต้องเก็บกุญแจ 100 ดอก และต้องส่งกุญแจแต่ละดอกถึงเจ้าของอย่างปลอดภัยด้วย
- ถ้าให้นิสิตคุยกันเองทุกคู่ จำนวนกุญแจจะกลายเป็น `100 × 99 ÷ 2` เท่ากับ 4,950 ดอก
- แต่ละดอกที่หลุด คือช่องทางหนึ่งช่องที่ถูกยึด

นี่คือ **ปัญหาเรื่องขนาด** ของการเข้ารหัสแบบสมมาตร และเป็นเหตุผลที่ต้องมีกุญแจคนละดอกข้างล่าง

<Term en="Asymmetric Encryption" th="การเข้ารหัสแบบกุญแจไม่สมมาตร" /> หรือที่เรียกกันว่า **Public Key** แก้ปัญหาข้างบนด้วยการเลิกใช้กุญแจดอกเดียว

หลักการมีสองข้อ

- **สร้างจากจำนวนเฉพาะ ได้ออกมาเป็นกุญแจหนึ่งคู่** คือ <Term en="Private Key" th="กุญแจส่วนตัว" /> กับ <Term en="Public Key" th="กุญแจสาธารณะ" />
- **ข้อความที่ล็อกด้วย private key เปิดได้ด้วย public key ของคู่นั้นเท่านั้น และในทางกลับกันก็เช่นกัน**

<Figure number={1} caption="กุญแจคู่เดียวกัน ใช้คนละทิศได้ผลคนละอย่าง">
  <PublicKeyDirections />
</Figure>

ผลที่ได้คือ **เราเก็บแค่ private key ส่วน public key แจกได้อย่างอิสระ เช่นเอาไปแปะไว้บนหน้าเว็บส่วนตัว**

แต่ยังมีปัญหาค้างอยู่หนึ่งข้อ — **ยังไม่มีอะไรยืนยันตัวตนจริง ๆ ของเจ้าของ public key**

<Why>
ปัญหานี้ฟังดูเล็กแต่ใหญ่มาก

ใครก็สร้างกุญแจคู่หนึ่งขึ้นมา แล้วประกาศว่า public key ดอกนี้เป็นของธนาคารได้ ตัวกุญแจไม่มีชื่อเจ้าของเขียนอยู่ในตัวมันเอง มันเป็นแค่ตัวเลขก้อนหนึ่ง

การเข้ารหัสจึงย้ายปัญหาความไว้ใจ ไม่ได้ลบมันทิ้ง เดิมต้องส่งกุญแจลับให้ถึงมืออีกฝ่ายอย่างปลอดภัย ตอนนี้ต้องรู้ให้ได้ว่า public key ดอกนี้เป็นของใครจริง

สิ่งที่มาแก้ข้อนี้คือ certificate ซึ่งบทนี้บอกไว้ว่าจะกลับมาพูดถึงในเรื่อง <Term en="PKI" th="Public Key Infrastructure ระบบที่รับรองว่า public key เป็นของใคร" /> ทีหลัง
</Why>

### ล็อกสองชั้นให้ได้ทั้งความลับและการพิสูจน์ตัวตน

โจทย์คือ **Bob อยากส่งข้อความหา Alice โดยที่มีแต่ Alice ที่อ่านได้ และ Alice พิสูจน์ได้ว่าข้อความมาจาก Bob จะทำยังไง**

ลองทายก่อน: แบบ A `((message)Bob's Priv)Alice's Pub` กับแบบ B `((message)Alice's Pub)Bob's Priv` ใช้กุญแจสี่ดอกเดียวกัน ต่างกันแค่ลำดับ แบบไหนปลอดภัยกว่า

<Compare>
<Wrong>
**แบบ B** — `((message)Alice's Pub)Bob's Priv`

ล็อกด้วย public key ของ Alice ก่อน แล้วค่อยล็อกทับด้วย private key ของ Bob

ชั้นนอกสุดคือลายเซ็นของ Bob ซึ่ง **ใครก็แกะออกได้** เพราะ public key ของ Bob เป็นของสาธารณะ

ผลที่ตามมาคือมีคนดักกลางระหว่างทาง ลอกลายเซ็นของ Bob ทิ้ง แล้วเซ็นทับด้วย private key ของตัวเอง จากนั้นส่งต่อให้ Alice ได้

Alice จะแกะออกมาแล้วอ่านข้อความได้ตามปกติ แต่เชื่อว่าข้อความมาจากคนดักกลาง ทั้งที่คนคนนั้นไม่เคยอ่านข้อความนั้นเลยสักครั้ง
</Wrong>

<Right>
**แบบ A** — `((message)Bob's Priv)Alice's Pub`

เซ็นด้วย private key ของ Bob ก่อน แล้วค่อยล็อกทับด้วย public key ของ Alice

ชั้นนอกสุดคือชั้นที่มีแต่ Alice เปิดได้ ลายเซ็นของ Bob จึงถูกห่ออยู่ข้างใน คนที่ไม่ใช่ Alice แตะมันไม่ได้เลย

Alice เปิดชั้นนอกด้วย private key ของตัวเอง แล้วเจอลายเซ็นของ Bob ข้างใน ซึ่งตรวจได้ว่าเป็นของ Bob จริง

ได้ครบทั้งสองข้อ คือความลับจากชั้นนอก และการพิสูจน์ต้นทางจากชั้นใน
</Right>
</Compare>

<KeyIdea>
หลักที่จำง่ายคือ **เซ็นก่อน แล้วค่อยปิดผนึก**
</KeyIdea>

<Analogy>
เหมือนจดหมาย กระดาษที่เซ็นชื่อคือชั้น `Bob's Priv` และซองคือชั้น `Alice's Pub` เซ็นชื่อบนกระดาษแล้วค่อยใส่ซอง ไม่ใช่ใส่ซองแล้วเซ็นบนซอง เพราะซองถูกเปลี่ยนได้

อุปมานี้ใช้ไม่ได้ตรงที่ ซองจริงใครก็ฉีกอ่านได้ แต่ชั้น `Alice's Pub` มีแต่ Alice ที่เปิดได้
</Analogy>

<Quiz question="Alice อยากประกาศข่าวให้ทุกคนอ่านได้ และให้ทุกคนตรวจได้ว่าข่าวมาจาก Alice จริง ต้องล็อกข่าวด้วยกุญแจดอกไหน">
ดอกที่ล็อกต้องเป็นดอกที่มีแต่ Alice ถือ คนอื่นจึงสร้างข้อความแบบนี้ไม่ได้ และดอกที่ใช้เปิดต้องเป็นดอกที่ทุกคนมี ทุกคนจึงอ่านและตรวจได้

คำตอบคือ **private key ของ Alice** แล้วทุกคนเปิดด้วย public key ของ Alice

คำตอบที่ผิดบ่อยคือ **public key ของ Alice** ซึ่งกลับทิศ ใครก็ล็อกด้วย public key ได้ จึงพิสูจน์ไม่ได้ว่าใครเขียน และมีแต่ Alice ที่เปิดอ่านได้ ซึ่งตรงข้ามกับที่ต้องการ
</Quiz>

### ราคาที่ต้องจ่าย

เรียงความเร็วจากช้าไปเร็ว **Public Key ช้าที่สุด** เพราะทำงานด้วยฟังก์ชันเลขยกกำลัง **block cipher กับ stream cipher เร็วกว่า** ซึ่งคือ [symmetric สองแบบ](/2110413-csy/lecture-6-2#ส่วนที่-3--symmetric-กุญแจดอกเดียวสองฝั่ง) เพราะทำงานด้วยฟังก์ชันตรรกะ และ **hash เร็วที่สุด**

ลำดับนี้คือเหตุผลที่ของจริงใช้ public key กับของชิ้นเล็กที่สุดเท่านั้น แล้วให้ตัวที่เร็วกว่ารับงานหนัก ซึ่งส่วนที่ 3 จะดูว่าต่อกันยังไง

<KeyIdea>
Public key แก้ปัญหาจำนวนกุญแจได้ เพราะ private key อยู่กับเจ้าของคนเดียว ส่วน public key แจกใครก็ได้ แต่มันช้าที่สุด ของจริงจึงใช้มันกับของชิ้นเล็กเท่านั้น
</KeyIdea>

## ส่วนที่ 2 — การเข้ารหัสให้อะไร และไม่ให้อะไร

### สรุปว่าการเข้ารหัสให้อะไรกับเราบ้าง

คำตอบมีสามข้อ และข้อสุดท้ายสำคัญที่สุด

- **ถ้าจัดการกุญแจดี การเข้ารหัสให้ได้ทั้ง authentication และ authorization**
- **สำหรับ authorization มันให้ได้ทั้ง confidentiality และ integrity**
- **แต่การเข้ารหัสมีจุดอ่อนต่อการวิเคราะห์ทางสถิติ และถ้ามีกำลังประมวลผลมากพอ ทุกอย่างถูกเจาะได้**

สองข้อแรกอธิบายได้ด้วยกรณีที่เจอมาแล้ว ลายเซ็นในส่วนที่ 1 บอกได้ว่าใครเป็นคนเขียน นั่นคือ authentication ส่วน authorization เกิดจากการที่ **การถือกุญแจกลายเป็นสิทธิ์** คนที่มีสิทธิ์อ่านคือคนที่ถือดอกที่เปิดได้ ซึ่งคือ confidentiality ใน [Lecture 4](/2110413-csy/lecture-4) และคนที่มีสิทธิ์สร้างข้อความที่ถูกต้องคือคนที่ถือดอกที่ใช้เขียน เช่นกุญแจของอาจารย์ในโจทย์นิสิต 100 คน ซึ่งคือ integrity

<Pitfall>
**คนส่วนใหญ่คิดว่าการเข้ารหัสปลอดภัย** ซึ่งประโยคสุดท้ายข้างบนบอกว่าไม่จริงเสมอไป

ความเชื่อนี้ดูถูก เพราะวันนี้คนที่ไม่มีกุญแจเปิดข้อความที่เข้ารหัสดีแล้วไม่ออกจริง ๆ

แต่การเข้ารหัสไม่ได้ทำให้ข้อความอ่านไม่ได้ มันทำให้ข้อความ **อ่านไม่คุ้ม** ในกรอบเวลาที่มีความหมาย

เงื่อนไขคำว่าคุ้มเปลี่ยนได้ตลอด เพราะกำลังประมวลผลเพิ่มขึ้นทุกปี ของที่เข้ารหัสวันนี้แล้วถูกเก็บไว้ อาจถูกเปิดอ่านได้ในสิบปีข้างหน้า

และนี่คือเหตุผลที่หัวข้อถัดไปต้องมี
</Pitfall>

### ความท้าทายของยุคนี้

ภัยที่มามีสี่อย่าง

- **Quantum Computing**
- **Machine Learning Attacks**
- **Side-Channel Attacks**
- **กำลังประมวลผลที่เพิ่มขึ้น**

ส่วนงานวิจัยที่รับมือมีสองทาง ซึ่งไม่ได้จับคู่กับภัยข้อใดข้อหนึ่ง

- **Post-Quantum Cryptography**
- **Blockchain Technologies ?**

<Callout type="info" title="ภัยสามอย่างและงานวิจัยสองทาง">
**Quantum Computing** โจมตี **คณิตศาสตร์** ที่อยู่ใต้ public key คือทำให้การแยกตัวประกอบจำนวนเฉพาะ ซึ่งเป็นฐานของ RSA และ discrete logarithm ซึ่งเป็นฐานของ DSA แก้ได้เร็วขึ้นมาก จึงกระทบทั้งสองตัวโดยตรง แต่กระทบ hash และ symmetric น้อยกว่ามาก

**Side-Channel Attacks** ไม่โจมตีอัลกอริทึมเลย แต่ดู **ร่องรอยที่การทำงานทิ้งไว้** เช่นเวลาที่ใช้ ไฟที่กิน หรือเสียงที่เกิด แล้วเดากุญแจจากตรงนั้น อัลกอริทึมที่พิสูจน์แล้วว่าแข็งแรงก็ยังแพ้ทางนี้ได้ถ้าเขียนโค้ดไม่ระวัง

**Machine Learning Attacks** ใช้โมเดลหาแบบแผนในผลลัพธ์ที่ควรจะดูเหมือนสุ่ม ซึ่งเป็นการวิเคราะห์ทางสถิติในรูปแบบที่แรงกว่าเดิมมาก

**Post-Quantum Cryptography** คืออัลกอริทึม public key ชุดใหม่ ที่สร้างบนโจทย์คณิตศาสตร์ซึ่งเชื่อว่าคอมพิวเตอร์ควอนตัมก็แก้ได้ไม่เร็ว

**Blockchain** คือบันทึกที่แต่ละก้อนเก็บค่า hash ของก้อนก่อนหน้า ถ้าแก้ก้อนเก่า hash ที่ก้อนหลังจากนั้นเก็บไว้จะไม่ตรงกันทันที จึงเกี่ยวกับ integrity ตรง ๆ

เครื่องหมายคำถามหลัง Blockchain เป็นของบทนี้เอง
</Callout>

ภัยที่เปลี่ยนตลอดทำให้ cryptography เป็นสาขาที่ **dynamic และพัฒนาไม่หยุด** เป็น **ส่วนผสมของคณิตศาสตร์ วิทยาการคอมพิวเตอร์ และความปลอดภัย** ซึ่ง **สำคัญต่อความปลอดภัยดิจิทัลยุคนี้** และ **ต้องเรียนรู้ต่อเนื่อง** ทางเรียนต่อที่แนะนำคือ เข้าใจหลักพื้นฐาน ลองลงมือ implement ติดตามเทคโนโลยีที่เกิดใหม่ และฝึกคิดวิเคราะห์

<KeyIdea>
การเข้ารหัสไม่ได้ทำให้ข้อความอ่านไม่ได้ แต่ทำให้อ่านไม่คุ้มในกรอบเวลาที่มีความหมาย และเส้นของคำว่าคุ้มขยับทุกครั้งที่กำลังประมวลผลเพิ่มหรือมีภัยแบบใหม่
</KeyIdea>

## ส่วนที่ 3 — Security Protocol: เอาหลายอย่างมาต่อกัน

<Why>
[Lecture 6.2](/2110413-csy/lecture-6-2) กับส่วนที่ 1 ให้เครื่องมือมาสามชิ้น และแต่ละชิ้นเก่งคนละอย่าง

- **Hash** เร็วที่สุด แต่ส่งความลับไม่ได้ และไม่รู้ว่าใครเป็นคนย่อย
- **Symmetric** เร็ว แต่ต้องส่งกุญแจถึงกันก่อน และไม่บอกว่าใครเป็นคนเขียน
- **Public Key** แจกกุญแจง่ายและบอกได้ว่าใครเขียน แต่ช้าที่สุด

ไม่มีชิ้นไหนใช้เดี่ยว ๆ แล้วพอ ของจริงจึงเป็นการต่อกัน โดยให้แต่ละชิ้นทำเฉพาะสิ่งที่มันเก่ง
</Why>

<Term en="Security Protocol" th="พิธีการความปลอดภัย" /> คือ **การเอาอัลกอริทึมหลายตัวมารวมกัน โดยรวมข้อดีและข้อเสียของแต่ละตัวเข้าด้วยกัน**

### Digital Signature

กลับไปที่โจทย์อาจารย์กับนิสิต 100 คนในส่วนที่ 1 ด้วยกุญแจแบบสมมาตร ต้องมี 100 ดอก และทุกดอกต้องส่งถึงมือแต่ละคนอย่างปลอดภัย ด้วยเครื่องมือในหัวข้อนี้ อาจารย์มีกุญแจคู่เดียว เซ็นเอกสารหนึ่งครั้ง แล้วแปะ public key ไว้บนหน้าเว็บ

นิสิตกี่คนก็ตรวจได้ ไม่ว่าจะ 100 หรือ 100,000 คน โดยอาจารย์ไม่ต้องทำอะไรเพิ่มเลย และไม่มีนิสิตคนไหนปลอมลายเซ็นได้ เพราะไม่มีใครมี private key ของอาจารย์

<Figure number={2} caption="ย่อด้วย hash เพราะเร็ว เซ็นด้วย private key เพราะพิสูจน์ตัวตนได้">
  <DigitalSignature />
</Figure>

<Term en="Digital Signature" th="ลายเซ็นดิจิทัล" /> ทำแบบนั้นได้ด้วยการย่อข้อความด้วย hash แล้วล็อกค่าย่อยด้วย private key มีคุณสมบัติสองข้อ

- **ผู้รับตรวจสอบความเป็นต้นฉบับของข้อความธรรมดาได้**
- **รวมความเร็วของ message digest เข้ากับความยืดหยุ่นเรื่องจำนวนของ public key**

<Pitfall>
คนมักคิดว่า **ข้อความที่มีลายเซ็นดิจิทัลถูกเข้ารหัสแล้ว คนอื่นอ่านไม่ได้** ซึ่งไม่จริง

ความเชื่อนี้ดูถูก เพราะการเซ็นคือการล็อกด้วย private key ซึ่งฟังเหมือนการเข้ารหัส แต่ของที่ถูกล็อกคือค่าย่อย และดอกที่เปิดคือ public key ซึ่งใครก็มี

ลายเซ็นดิจิทัล **ไม่ได้ปิดบังข้อความ** ในรูปที่ 2 ข้อความเดินทางไปพร้อมลายเซ็นเป็นข้อความธรรมดาที่ใครดักอ่านก็อ่านออก ที่มันรับประกันคือข้อความไม่ถูกแก้ และคนเซ็นเป็นเจ้าของ private key จริง

ถ้าต้องการปิดบังด้วย ต้องห่อชั้นนอกเพิ่มอีกชั้น ซึ่งก็คือแบบ A ในส่วนที่ 1
</Pitfall>

จุดสำคัญมีสามข้อ

- **ไคลเอนต์เป็นคนเลือกว่าจะใช้ stream หรือ block cipher ตัวไหนพร้อมกุญแจ ขึ้นกับสภาพแวดล้อม**
- **มีแต่เซิร์ฟเวอร์ที่ถือ private key จึงมีแต่ไคลเอนต์กับเซิร์ฟเวอร์ที่รู้กุญแจสมมาตรดอกนั้น**
- **รวมความเร็วของกุญแจสมมาตร เข้ากับความยืดหยุ่นเรื่องจำนวนของ public key**

<Why>

**ปัญหาจำนวนกุญแจ** หายไป เพราะเซิร์ฟเวอร์มีกุญแจคู่เดียวสำหรับผู้ใช้ทุกคนในโลก

**ปัญหาการส่งกุญแจ** หายไป เพราะกุญแจสมมาตรถูกสุ่มขึ้นใหม่ต่อการเชื่อมต่อ แล้วส่งไปในซองที่มีแต่เซิร์ฟเวอร์เปิดได้

**ปัญหาความช้า** หายไป เพราะ public key ถูกใช้แค่ครั้งเดียวกับของชิ้นเล็ก คือกุญแจหนึ่งดอก ส่วนข้อมูลจริงทั้งหมดวิ่งด้วยกุญแจสมมาตรที่เร็วกว่า

สิ่งเดียวที่ยังค้างคือจังหวะที่ 2 — เราจะรู้ได้ยังไงว่า public key ที่ส่งมานั้นเป็นของ `chula.ac.th` จริง นั่นคืองานของ certificate ซึ่งบทนี้ยกไปพูดในเรื่อง PKI
</Why>

### สิ่งที่บทนี้ยังไม่ได้พูด

บทนี้บอกไว้เองว่ามีสี่เรื่องที่ยังไม่ได้ลง

- **Key management** คือการสร้าง แจก เก็บ เปลี่ยน และยกเลิกกุญแจ ซึ่งจะกลับมาในเรื่อง PKI
- **การหา collision ของฟังก์ชัน hash ได้จริง** คือสร้างข้อมูลสองชิ้นที่ได้ค่า hash เดียวกัน ([Lecture 6.2](/2110413-csy/lecture-6-2#collision-คืออะไร-และทำไมมันต้องมี)) โดยมีตัวอย่างจริงที่ [MD5 collision demo](http://www.mathstat.dal.ca/~selinger/md5collision/)
- **Post-Quantum Encryption**
- **Elliptic-curve cryptography** คือ public key ที่สร้างจากเส้นโค้งวงรี ได้ความแข็งแรงเท่า RSA ด้วยกุญแจที่สั้นกว่ามาก

### ข้อสรุปเรื่อง integrity

- **Integrity ต้องการอย่างใดอย่างหนึ่ง คือฮาร์ดแวร์หนุน หรือการเข้ารหัส** ฝั่งฮาร์ดแวร์อยู่ใน [Lecture 6.1](/2110413-csy/lecture-6#ส่วนที่-3--ฮาร์ดแวร์ที่ทำให้ขอบเขตเป็นจริง)
- **ฮาร์ดแวร์บวกระบบปฏิบัติการรวมกัน เป็นฐานของ integrity ซึ่งก็คือฐานของความปลอดภัย**
- **กล่องที่มี integrity แข็งแรง แปลว่ามันเก็บของข้างในไว้ในสภาพเดิมได้เป็นปี ๆ**
- **ไม่มี integrity ที่สมบูรณ์แบบ ส่วนใหญ่แล้วการถูกเจาะระบบก็คือการที่ integrity แตก** เช่นขโมยทุบกระจกแล้วเข้าไปในบ้าน

<Analogy>
บ้านที่ขโมยทุบกระจกเข้าไปคือระบบที่ integrity แตก ตัวบ้านคือระบบ และกระจกคือส่วนของระบบที่ต้องคงสภาพเดิม

บ้านหลังนั้นมี authentication คือกุญแจประตู มี authorization คือใครเข้าห้องไหนได้ มี auditing คือกล้องวงจรปิด

แต่ขโมยไม่ได้ผ่านประตู เขาเปลี่ยนรูปร่างของตัวบ้าน กระจกที่เคยเป็นแผ่นเดียวกลายเป็นช่องทางเข้า

ทั้งสามระบบข้างบนยังทำงานปกติทุกอย่าง มันแค่ไม่เกี่ยวข้องอีกต่อไป เพราะสิ่งที่มันเฝ้าอยู่ไม่ใช่เส้นทางที่ถูกใช้

อุปมานี้ใช้ไม่ได้ตรงที่ กระจกแตกเห็นได้ทันทีด้วยตา แต่ไฟล์ที่ถูกแก้หน้าตาเหมือนเดิมทุกอย่าง ต้องมี hash หรือลายเซ็นดิจิทัลถึงจะรู้ว่ามันไม่ใช่ชิ้นเดิม
</Analogy>

<KeyIdea>
Integrity ได้มาจากสองทาง คือฮาร์ดแวร์ที่กั้นไว้ในเครื่อง หรือการเข้ารหัสที่ติดไปกับตัวข้อมูล และของจริงอย่าง HTTPS ต่อเครื่องมือเข้ารหัสหลายตัวเข้าด้วยกัน ให้แต่ละตัวทำเฉพาะสิ่งที่มันเก่ง
</KeyIdea>

- **มีแต่เซิร์ฟเวอร์ที่ถือ private key จึงมีแค่สองฝั่งที่รู้กุญแจสมมาตร**

**[ข้อสรุปของบท](#ข้อสรุปเรื่อง-integrity)**

- **Integrity ต้องการฮาร์ดแวร์หนุน หรือการเข้ารหัส อย่างใดอย่างหนึ่ง**
- **ฮาร์ดแวร์บวกระบบปฏิบัติการคือฐานของ integrity ซึ่งคือฐานของความปลอดภัย**
- **กล่องที่ integrity แข็งแรง เก็บของข้างในไว้ในสภาพเดิมได้เป็นปี ๆ**
- **ไม่มี integrity ที่สมบูรณ์แบบ การถูกเจาะระบบส่วนใหญ่คือการที่ integrity แตก**
- เรื่องที่ยังไม่ได้ลง: **key management (ไปต่อที่ PKI), การหา collision ของ hash ได้จริง, post-quantum encryption, elliptic-curve cryptography**

<Quiz question="ระบบสำรองข้อมูลต้องส่งไฟล์ 50 GB ข้ามอินเทอร์เน็ตทุกคืน ผู้ออกแบบเสนอให้เข้ารหัสทั้งไฟล์ด้วย public key ของเครื่องปลายทางตรง ๆ เพราะไม่ต้องส่งกุญแจลับให้กันก่อน ข้อเสนอนี้มีปัญหาตรงไหน และควรต่อเครื่องมือยังไง">
public key ช้าที่สุดในสามกลุ่ม เพราะทำงานด้วยฟังก์ชันเลขยกกำลัง ใช้กับไฟล์ 50 GB ทั้งก้อนจึงช้าเกินไป HTTPS แก้ปัญหาเดียวกันด้วยการให้ public key ทำงานกับของชิ้นเล็กชิ้นเดียว คือกุญแจหนึ่งดอก

คำตอบคือ **สุ่มกุญแจสมมาตรขึ้นมาหนึ่งดอก ล็อกกุญแจดอกนั้นด้วย public key ของปลายทาง แล้วเข้ารหัสตัวไฟล์ด้วยกุญแจสมมาตร** ได้ความเร็วของกุญแจสมมาตร และยังไม่ต้องส่งกุญแจลับให้กันก่อน แบบนี้ได้แค่ความลับ ใครก็เข้ารหัสด้วย public key ของปลายทางได้ ปลายทางจึงยังไม่รู้ว่าใครส่งมา ถ้าต้องการรู้ด้วยต้องเพิ่ม [digital signature](#digital-signature)

คำตอบที่ผิดบ่อยคือ "ไม่มีปัญหา เพราะ public key ปลอดภัยกว่า" ข้อเสนอนี้ไม่ได้พังเรื่องความลับ แต่พังเรื่องความเร็ว และการย้ายตัวไฟล์ไปใช้กุญแจสมมาตรก็ไม่ได้เปิดช่องให้ใคร เพราะคนที่แกะกุญแจดอกนั้นออกมาได้ยังมีแค่เจ้าของ private key ของปลายทาง เหมือนใน HTTPS
