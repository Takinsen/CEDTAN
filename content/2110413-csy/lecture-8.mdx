<KeyIdea>
buffer overflow จะยึดโปรแกรมได้ก็ต่อเมื่อมันเขียนทับ **address ที่โปรแกรมจะกระโดดไปหา** เช่น return address หรือ function pointer ด้วยข้อมูลที่มาจากนอก process วิธีป้องกันแต่ละแบบดักขั้นใดขั้นหนึ่งของเส้นทางนั้น และพลาดเมื่อการโจมตีเดินทางอื่นที่มันไม่ได้ดัก
</KeyIdea>

## ส่วนที่ 1 — ช่องโหว่เก่าที่ยังไม่หายไป

### worm ดังเกือบทุกตัวเข้าทางเดียวกัน

<Term en="Buffer Overflow" th="เขียนข้อมูลเกินขนาด buffer" /> คือการเขียนข้อมูลลง buffer เกินกว่าที่จองไว้ ส่วนที่เกินจึงไปทับข้อมูลที่อยู่ติดกันในหน่วยความจำ

worm อินเทอร์เน็ตตัวดังเกือบทุกตัวใช้ช่องโหว่นี้เข้าเครื่อง [worm](/2110413-csy/lecture-1#malicious-software) คือโปรแกรมที่แพร่จากเครื่องหนึ่งไปอีกเครื่องได้เองโดยไม่ต้องมีคนกด ตารางข้างล่างเป็นแค่ส่วนหนึ่งของรายชื่อ

| ปี | worm | รายละเอียด |
| --- | --- | --- |
| 1988 | Morris worm, worm ตัวแรก | `fingerd` บริการบน Unix ที่ตอบว่าเครื่องนี้มีผู้ใช้ชื่ออะไร ติดไป 10% ของอินเทอร์เน็ตในตอนนั้น |
| 2001 | Code Red | — |
| 2003 | Slammer | — |
| 2003 | Blaster และ Welchia | DCOM RPC ของ Windows บริการที่ให้เครื่องอื่นเรียกฟังก์ชันบนเครื่องนี้ผ่านเครือข่าย |
| 2004 | Witty | ออกมาหนึ่งวันหลังประกาศช่องโหว่ |
| 2004 | Sasser | LSASS ของ Windows process ที่ตรวจรหัสผ่านตอน login คาดว่าแกะวิธีมาจากประกาศช่องโหว่ |
| 2006 | ช่องโหว่บน Mac | ส่วน wireless |

### ความเสียหายนอกจอคอมพิวเตอร์

Slammer ปี 2003 ลามไปถึงระบบที่ไม่มีใครคิดว่าเป็นคอมพิวเตอร์ ในเดือนมกราคมมันเข้าเครือข่ายภายในของโรงไฟฟ้านิวเคลียร์ Davis-Besse ในโอไฮโอ ระบบเฝ้าระวังความปลอดภัยใช้การไม่ได้เกือบห้าชั่วโมง ทั้งที่พนักงานเชื่อว่ามี firewall กันอยู่ ([หลักการที่ 9 ของ Lecture 1](/2110413-csy/lecture-1#หลักการที่-9--dont-extend-trust-easily))

ผลอื่นของ Slammer มีอีกสามอย่าง

- เครื่องรับแจ้งเหตุ 911 ของเมือง Bellevue รัฐวอชิงตัน ล่ม
- ตู้ ATM ของ Bank of America 13,000 เครื่องล่ม
- packet ที่มันส่งออกมาท่วม router จนโครงสร้างพื้นฐานของอินเทอร์เน็ตบางส่วนล่มตาม

<Detail label="ที่มาของข่าว Slammer">

- อีกสามอย่าง: บทความ "Inside the Slammer Worm" ใน IEEE Security and Privacy ฉบับกรกฎาคม–สิงหาคม 2003
</Detail>

ความเชื่อที่ผิดคือ **ไฟดับครั้งใหญ่ในอเมริกาและแคนาดาวันที่ 14 สิงหาคม 2003 เกิดจาก worm Blaster**

ข้อนี้ไม่จริง ตามรายงานเบื้องต้นเรื่องสาเหตุของไฟดับครั้งนั้น ("Interim Report: Causes of the August 14th Blackout in the United States and Canada")

มันดูจริงเพราะ Blaster ระบาดในสัปดาห์เดียวกันพอดี หลังวันที่ 11 สิงหาคม มันติดเครื่อง Windows ไปมากกว่าหนึ่งล้านเครื่อง

ที่เกิดจริงคือ **เครื่องที่คุมการผลิตและจ่ายไฟแยกขาดจากอินเทอร์เน็ต จึงไม่โดน Blaster เลย** ต้นเหตุคือระบบเตือนภัยของบริษัทไฟฟ้า FirstEnergy ในโอไฮโอล้มต่อกันเป็นทอด ทั้งเครื่องที่รัน "alarm and logging software" ของห้องควบคุม เครื่องสำรอง และ remote-control console อีกหลายตัว ผู้ควบคุมจึงไม่รู้ว่าเกิดอะไรขึ้น และสกัดปัญหาไม่ทัน

## ส่วนที่ 2 — ข้อมูลที่ล้นไปเปลี่ยนทางเดินของโปรแกรมได้ยังไง

### ล้นคืออะไร — ชื่อที่ยาวเกินไปหนึ่งตัวอักษร

<Why>
โปรแกรมข้างล่างถามอายุก่อน แล้วถามชื่อ ช่องเก็บชื่อจุได้ 8 ไบต์ คนชื่อ `Krerk.P01` พิมพ์อายุ 15 แต่โปรแกรมตอบว่าเขาอายุ 49
</Why>

```c
int age;
char name[8];
char tmp[20];
printf("Enter your age:");
gets(tmp);
age=atoi(tmp);
printf("Enter your name:");
gets(name);
printf("-----------\n%s is %d years old\n",name,age);
```

```text
$ gcc -fno-stack-protector -o age age.c
$ ./age
Enter your age:15
Enter your name:Krerk.P01
-----------
Krerk.P01 is 49 years old
```

`-fno-stack-protector` ปิดการป้องกันที่ gcc เปิดไว้เองตามปกติ บรรทัดคำเตือนของ linker เรื่อง `gets` ถูกตัดออกจากผลนี้ ส่วนที่ 3 ยกมันมาให้ดู

`gets` อ่านทั้งบรรทัดลง buffer ที่ได้รับมา โดยไม่รู้ว่า buffer นั้นยาวเท่าไร

`Krerk.P01` ยาว 9 ตัวอักษร บวก `\0` ที่ปิดท้ายสตริงอีกหนึ่งไบต์เป็น 10 ไบต์ แต่ `name` จุได้แค่ 8 สองไบต์ที่เกินจึงลงไปในตัวแปรที่อยู่ถัดไปในหน่วยความจำ ซึ่งคือ `age`

| ไบต์ของ `age` | ก่อน `gets(name)` | หลัง `gets(name)` |
| --- | --- | --- |
| ไบต์แรก | `0x0F` (15) | `0x31` คือตัวอักษร `'1'` |
| ไบต์ที่สอง | `0x00` | `0x00` คือ `\0` |
| ค่าของ `age` | 15 | `0x31` = **49** |

x86 เก็บไบต์ที่มีค่าน้อยที่สุดของจำนวนเต็มไว้ก่อน ไบต์แรกที่ถูกทับจึงเป็นไบต์ล่างสุดของ `age` พอดี

นี่คือนิยามของ buffer overflow

> **Definition 1:** The condition wherein the data transferred to a buffer exceeds the storage capacity of the buffer and some of the data "overflows" into another buffer, one that the data was not intended to go into.
>
> สภาพที่ข้อมูลซึ่งถูกส่งเข้า buffer มีมากกว่าที่ buffer จุได้ แล้วส่วนที่เกินล้นเข้าไปใน buffer อื่นที่ข้อมูลนั้นไม่ได้ตั้งใจจะไป

<Quiz question="ถ้าพิมพ์ชื่อยาวพอดี 8 ตัวอักษร เช่น Krerk.P0 ซึ่งเท่ากับขนาดของ name พอดี age จะออกมาเป็นเท่าไร">
`Krerk.P0` ยาว 8 ตัว แต่ `gets` ต่อท้ายด้วย `\0` อีกหนึ่งไบต์เสมอ ไบต์ที่ 9 จึงลงไปทับไบต์แรกของ `age` ซึ่งเก็บ `0x0F` อยู่ แล้วเปลี่ยนเป็น `0x00`

คำตอบคือ **0** รันจริงได้ `Krerk.P0 is 0 years old`

คำตอบที่ผิดบ่อยคือ "15 เพราะชื่อยาวไม่เกินที่จุ" ซึ่งลืมว่าสตริงใน C กินที่มากกว่าจำนวนตัวอักษรหนึ่งไบต์เสมอ การล้นเกินมาไบต์เดียวแบบนี้เจอบ่อยมากในโค้ดจริง
</Quiz>

### Control Data — ค่าที่ตัดสินว่าโปรแกรมจะไปไหนต่อ

ตัวอย่างอายุแค่เปลี่ยนตัวเลข แต่ถ้าค่าที่ถูกทับเป็นค่าที่โปรแกรมใช้ตัดสินว่าจะไปรันคำสั่งที่ไหนต่อ การล้นจะเปลี่ยนทางเดินของทั้งโปรแกรม

<Term en="Control Data" th="ค่าที่บอกว่าจะไปรันโค้ดตรงไหนต่อ" /> คือค่าในหน่วยความจำที่เก็บ address ของโค้ด โปรแกรมอ่านค่านี้แล้วกระโดดไปรันโค้ดที่อยู่ตรงนั้น

ค่าพวกนี้ส่วนใหญ่อยู่บน <Term en="Stack" th="หน่วยความจำที่ใช้ตอนเรียกฟังก์ชัน" /> ทุกครั้งที่เรียกฟังก์ชัน โปรแกรมจองพื้นที่บน stack หนึ่งก้อนไว้เก็บ argument และตัวแปรภายในของฟังก์ชันนั้น ก้อนนี้เรียกว่า <Term en="Stack Frame" th="ก้อนบน stack ของการเรียกหนึ่งครั้ง" />

ใน stack frame ยังมี <Term en="Return Address" th="ที่ที่จะกลับไปเมื่อฟังก์ชันจบ" /> ด้วย มันคือ address ของคำสั่งในผู้เรียก ที่โปรแกรมต้องกลับไปรันต่อเมื่อฟังก์ชันทำงานเสร็จ

`strcpy(dst, src)` คัดลอกสตริงจาก `src` ลง `dst` ไปจนเจอ `\0` โดยไม่ดูว่า `dst` จุได้เท่าไร เหมือน `gets`

บน x86 ตัวแปรภายในอยู่ที่ address ต่ำกว่า return address และ `gets` กับ `strcpy` เขียนจาก address ต่ำขึ้นไปหา address สูง ข้อมูลที่ล้นออกจาก buffer จึงวิ่งเข้าหา return address พอดี

control data ที่เจอบ่อยมีสี่ชนิด

- **return address** — มีอยู่ในทุก stack frame
- **function pointer** — ตัวแปรที่เก็บ address ของฟังก์ชัน
- **exception handler** — address ของโค้ดที่จะรันเมื่อเกิด error
- **virtual method** — ในภาษา OOP object เก็บ pointer ไปยังตาราง address ของ method

ทั้งสี่ชนิดอยู่ปนกับข้อมูลธรรมดาใน stack frame ตัวอย่างของ Michael Howard จาก Microsoft คือฟังก์ชันนี้

```c
void func(char *p, int i) {
    int j = 0;
    CFoo foo;
    int (*fp)(int) = &func;
    char b[128];
    strcpy(b,p);
}
```

นอกจาก return address แล้ว frame นี้ยังมี control data อีกสองตัว `fp` เก็บ address ของฟังก์ชัน ส่วน `foo` เป็น object ของคลาส `CFoo` ซึ่งเก็บ pointer ไปยังตาราง virtual method ไว้ในตัว

ถ้า `p` ชี้ไปที่ข้อมูลที่ยาวเกิน 128 ไบต์ `strcpy` จะเขียนเลย `b` ขึ้นไปทาง address สูง

ช่องหนึ่งในรูปคือ saved EBP ส่วน EBP เองคือ register ที่ x86 แบบ 32 บิตใช้เป็น <Term en="Frame Pointer" th="register ที่ชี้ stack frame ปัจจุบัน" /> ฟังก์ชันหาตัวแปรของตัวเองโดยนับระยะจาก EBP

ตอนเข้าฟังก์ชัน ค่า EBP ของผู้เรียกถูกเก็บไว้บน stack เรียกว่า saved EBP แล้วถูกโหลดคืนตอนกลับ ถ้า saved EBP ถูกทับ ผู้เรียกจะนับระยะจาก address ผิด ทุกค่าที่มันอ่านหลังจากนั้นจึงมาจากที่ที่ผู้โจมตีเลือก

การโจมตีจึงแบ่งตามช่องที่ถูกทับได้สามแบบ

- **Return-address attack** หรือ <Term en="Stack Smashing" th="ทับ return address บน stack" /> — ทับ return address พอฟังก์ชันจบ โปรแกรมกลับไปที่ address ใหม่ แทนที่จะกลับไปหาผู้เรียก
- **Function-pointer attack** — ทับ `fp` ครั้งต่อไปที่โปรแกรมเรียกผ่าน `fp` ก็ไปที่อื่น
- **Frame-pointer attack** — ทับ saved EBP

### ทับ pointer ธรรมดา — ล้นสองขั้น

การโจมตีอีกแบบไม่ได้ทับ control data ตรง ๆ แต่ทับ **data pointer** ธรรมดาที่อยู่ติดกับ buffer

```c
int vulnerable(char **argv) {
    int x;
    char *ptr;
    char buffer[30];
    ptr=buffer;
    printf("ptr %p - before\n",ptr);
    strcpy(ptr,argv[1]);
    printf("ptr %p - after\n",ptr);
    strcpy(ptr,argv[2]);
    printf("done\n");
}
```

```text
ptr 0xbffff960 - before
ptr 0x8049730 - after
```

`strcpy` ครั้งแรกล้นจาก `buffer` ไปทับ `ptr` ที่อยู่ติดกัน ก่อนล้น `ptr` ชี้ไปที่ `buffer` บน stack หลังล้นมันเป็นค่าที่ผู้โจมตีใส่มา

พอถึง `strcpy` ครั้งที่สอง โปรแกรมเขียนลงที่ที่ `ptr` ชี้ ซึ่งตอนนี้เป็นที่ที่ผู้โจมตีเลือก **pointer ตัวเดียวที่ทับได้จึงกลายเป็นการเขียนลงที่ไหนก็ได้ในหน่วยความจำ** เป้าหมายมักเป็น control data ที่อยู่ไกลออกไป

เป้าที่นิยมคือ <Term en="Global Offset Table (GOT)" th="ตาราง address ของฟังก์ชันในไลบรารี" /> โปรแกรมไม่รู้ล่วงหน้าว่า `printf` ในไลบรารีจะถูกโหลดไปอยู่ที่ไหน จึงเรียกผ่านตารางนี้ ช่องหนึ่งในตารางเรียกว่า **jump slot** ซึ่งก็คือ function pointer ตัวหนึ่ง

ถ้า jump slot ของ `printf` ถูกเปลี่ยน ทุกครั้งที่โปรแกรมเรียก `printf` หลังจากนั้นก็ไปที่อื่น worm **SLAPPER** ที่เจาะ Apache ใช้วิธีนี้

**การเขียนครั้งที่สองไม่ได้ล้นต่อเนื่องจาก buffer** มันข้ามทุกอย่างที่อยู่ระหว่าง buffer กับเป้าหมายไปเลย

### ช่องโหว่สองแบบที่ทำงานคล้ายกัน

- <Term en="Integer Overflow" th="ตัวเลขเกินขนาดจนวนกลับ" /> — นับเป็นส่วนย่อยของ buffer overflow ขนาดที่คำนวณได้เกินค่าสูงสุดของตัวแปรแล้ววนกลับเป็นค่าน้อย การตรวจความยาวจึงผ่าน แต่การคัดลอกจริงเขียนเกินที่จอง
- **ช่องโหว่ของ `printf`** — โปรแกรมส่งสตริงจากผู้ใช้เข้าไปเป็น format string ของ `printf` ตรง ๆ ผู้ใช้จึงสั่งให้ `printf` อ่านหรือเขียนหน่วยความจำได้ผ่าน format specifier

<Detail label="ตัวอย่าง: ขนาดที่วนกลับเป็นศูนย์">
<Example added title="ขนาดที่วนกลับเป็นศูนย์">
โปรแกรมจองที่ `len + 1` ไบต์ไว้เผื่อ `\0` ถ้า `len` เป็น unsigned int 32 บิตที่มีค่าสูงสุด ผลบวกจะวนกลับเป็นศูนย์

```text
len=4294967295  len+1=0
```

โปรแกรมจึงจองที่ 0 ไบต์ แต่ยังคัดลอกตาม `len`
</Example>
</Detail>

ส่วนช่องโหว่ของ `printf` ทำงานแบบนี้ ถ้าโปรแกรมเรียก `printf(buf)` แล้วผู้ใช้พิมพ์ `%x %x %x` มา `printf` จะพิมพ์สามค่าจากตำแหน่งที่ควรเป็น argument ซึ่งบน x86 แบบ 32 บิตคือค่าบน stack

`%n` ไปไกลกว่านั้น มันเขียนจำนวนตัวอักษรที่พิมพ์ไปแล้วลงที่ address ซึ่งอยู่ในตำแหน่งของ argument ตัวถัดไป ผู้ใช้จึงเขียนหน่วยความจำได้ด้วย

### สองเงื่อนไขที่การโจมตีต้องมีครบ

การโจมตีด้วย buffer overflow ต้องได้ทั้งสองข้อ

1. **มีโค้ดหรือข้อมูลที่จะให้รัน** — ฉีดเข้าไปเองพร้อมกับข้อมูลที่ล้น หรือรู้ address ของโค้ดที่มีอยู่ในหน่วยความจำแล้ว
2. **พาโปรแกรมไปรันสิ่งนั้น** — เปลี่ยน control data ให้ชี้ไปหามัน

ข้อสองคือหัวใจของนิยามการโจมตี control data

> **Definition 2:** A buffer-overflow attack on control data is an attack that (possibly implicitly) uses memory-manipulating operations to overflow a buffer which results in the modification of an address to point to malicious or unexpected code.
>
> การโจมตี control data ด้วย buffer overflow คือการโจมตีที่ใช้คำสั่งจัดการหน่วยความจำ (อาจโดยอ้อม) ทำให้ buffer ล้น จน address ตัวหนึ่งถูกเปลี่ยนให้ชี้ไปหาโค้ดอันตรายหรือโค้ดที่ไม่ควรถูกรัน

คำว่า <Term en="Domain" th="ขอบเขตของ process" /> ในที่นี้มองจาก process ที่กำลังทำงาน ของจาก domain อื่นคือของที่มาจากนอก process เช่นจากเครื่องอื่นหรือ process อื่น ผ่านเครือข่าย ไฟล์ หรือคีย์บอร์ด ของที่ process สร้างเองไม่มีเจตนาร้ายให้กลัว

ข้อสังเกตที่ใช้ต่อจนจบคือ **buffer ที่ล้นเข้ามาเป็นของที่ส่งมาจาก domain อื่นเสมอ** และนั่นคือที่มาของเจตนาร้าย

<Quiz question="ถ้าคอมไพเลอร์วาง j ของฟังก์ชัน func ไว้ติดเหนือ b พอดี และ strcpy ล้นมาแค่ 4 ไบต์ ทับแค่ j ซึ่งเป็น int โปรแกรมถูกยึดได้ไหม">
`j` เป็นตัวเลขธรรมดา ไม่ใช่ address ของโค้ด โปรแกรมไม่ได้กระโดดตาม `j` ไปไหน

คำตอบคือ **ทางเดินของโปรแกรมไม่เปลี่ยน แต่ผลลัพธ์อาจผิด** เหมือนอายุที่กลายเป็น 49 ซึ่งเป็นปัญหาความถูกต้อง แต่ไม่เข้า Definition 2

คำตอบที่ผิดบ่อยคือ "ไม่มีผลอะไรเลย" ถ้า `j` เป็นค่าที่ใช้ตัดสินสิทธิ์ เช่นตัวแปร `is_admin` การเปลี่ยนมันอันตรายมาก แม้ไม่มี address ไหนถูกเปลี่ยน การโจมตีแบบนี้อยู่นอกขอบเขตของวิธีป้องกันส่วนใหญ่ในคาบนี้ รวมถึง Secure Bit ใน [Lecture 8.2](/2110413-csy/lecture-8-2) ด้วย
</Quiz>

### Static Analysis — จับก่อนใช้งาน แต่จับได้แค่ที่รู้จัก

<Why>
ถ้าเครื่องมือจับ `gets` ในตัวอย่างอายุได้ตั้งแต่ตอน build ช่องโหว่นั้นก็ไม่ถึงมือผู้ใช้
</Why>

ข้อจำกัดของ static analysis มีสามข้อ

- **จับได้แค่ปัญหาที่รู้จักแล้ว** ช่องโหว่รูปแบบใหม่ที่ไม่อยู่ในกฎก็หลุดไปได้
- **ไม่มีข้อมูลตอนรัน** ไม่รู้ว่า input จริงยาวเท่าไร
- **เตือนผิดได้** (false alarm) โค้ดที่ปลอดภัยก็ถูกเตือน จนคนเลิกอ่านคำเตือน

| Splint, BOON | lint ที่เพิ่มการตรวจด้าน security และวิเคราะห์ความหมายของโค้ด (semantic) |
| STOBO | profiling tool เตือนเมื่อปลายทางของ `strcpy` จุไม่พอ แม้ input ทดสอบไม่ได้ล้นจริง |

## ส่วนที่ 4 — ปกป้อง address ไม่ให้ถูกเปลี่ยนโดยไม่มีใครรู้

### สี่คำถามที่วิธีตรวจตอนรันทุกวิธีต้องตอบ

Dynamic solution ทุกแบบในส่วนนี้และส่วนถัดไปเก็บ <Term en="Metadata" th="ข้อมูลที่เก็บเพิ่มไว้ใช้ตรวจ" /> แล้วตรวจมันตอนรัน การเทียบวิธีพวกนี้จึงถามคำถามเดียวกันได้สี่ข้อ

1. **Assumptions** — มันสมมติอะไรเกี่ยวกับการโจมตี เช่นสมมติว่าการล้นเขียนต่อเนื่องจาก buffer
2. **Creation of metadata** — metadata ถูกสร้างตอนไหน และใครสร้าง
3. **Validation of metadata** — ตรวจตอนไหน และ metadata เองถูกปลอมได้ไหม
4. **Handling of invalid data** — เจอของผิดแล้วทำอะไร หยุดโปรแกรม หรือซ่อมคืน

### สี่แบบของ Address Protection

<Why>
ใน `func` ของรูปที่ 1 ถ้า `p` ยาวพอ `strcpy` จะล้นไปถึง return address แต่ค่าที่ถูกทับยังไม่ทำอะไรจนกว่า `func` จะ return ถ้าจับได้ก่อนจังหวะนั้นว่า address ถูกเปลี่ยน โปรแกรมก็หยุดได้ทัน
</Why>

<Term en="Address Protection" th="กัน address ไม่ให้ถูกแก้เงียบ ๆ" /> เก็บ metadata อีกชุดคู่กับ address ที่สำคัญ แล้วตรวจก่อนใช้ metadata มีสี่แบบ

บางแบบทำงานทีละ <Term en="Word" th="หน่วยที่ CPU อ่านหรือเขียนทีละครั้ง" /> เช่น 4 ไบต์บน x86 แบบ 32 บิต

| แบบ | metadata | ตัวอย่าง |
| --- | --- | --- |
| **Canary Words** | ค่าที่วางไว้หน้า return address | StackGuard, ProPolice |
| **Address Encode** | เข้ารหัสตัว address เอง | PointGuard |
| **Copy of Address** | สำเนาของ return address | StackGhost, SRAS, Split Stack, RAD, DISE, StackShield, SCACHE, LibVerify |
| **Tags** | บิตหนึ่งบิตบนทุก word | IBM System/38 |

### Canary — StackGuard

<Term en="Canary" th="ค่าที่วางไว้จับการล้น" /> คือ word หนึ่งที่ compiler วางไว้ระหว่าง buffer กับ return address ตอนเข้าฟังก์ชัน แล้วตรวจว่ายังเป็นค่าเดิมก่อนฟังก์ชันกลับ

การล้นที่เขียนจาก buffer ขึ้นไปหา return address ต้องทับ canary ก่อนเสมอ ถ้าค่าเปลี่ยน โปรแกรมหยุดทันทีโดยไม่กระโดดไปตาม return address **StackGuard** ของ Oregon Graduate Institute (Immunix) ทำแบบนี้

ค่าของ canary มีหลายแบบ

- **Random canary** — สุ่มตอนโปรแกรมเริ่ม ผู้โจมตีที่ไม่รู้ค่าก็เขียนค่าเดิมกลับลงไปไม่ได้
- **Terminator canary** — มีไบต์ `0x00` อยู่ในค่า จะผ่าน canary ได้ต้องเขียน `0x00` นั้นกลับคืน แต่ `strcpy` หยุดทันทีที่เขียน `0x00` ไบต์หลังจากนั้นจึงไปไม่ถึง return address canary ที่เป็นศูนย์ทั้ง word เรียกว่า **null canary**

สไลด์ยังมีอีกสองข้อที่ไม่ได้อธิบาย คือ **terminator with diversity canary** และคำถาม **Alignment?**

<Example added title="smash.c — strcpy ข้อความ 48 ตัวลง char b[16] ทั้งแบบมีและไม่มี canary">
```text
$ gcc -fno-stack-protector -o smash smash.c && ./smash $(python3 -c 'print("A"*48)')
copied 48 bytes
Segmentation fault         (core dumped)
$ gcc -fstack-protector -o smash smash.c && ./smash $(python3 -c 'print("A"*48)')
copied 48 bytes
*** stack smashing detected ***: terminated
Aborted                    (core dumped)
```

แบบไม่มี canary พังที่คำสั่ง `ret` เพราะ return address ที่ถูกทับด้วย `0x4141414141414141` ไม่ใช่ address ที่ใช้ได้ ถ้า address นั้นชี้ไปที่โค้ดที่รันได้ มันจะไม่พังเลย แต่ไปรันโค้ดนั้นแทน ส่วนแบบมี canary หยุดเองก่อนจะกระโดด

</Example>

ถามสี่คำถามของ dynamic solution กับ canary ได้คำตอบแบบนี้

| คำถาม | คำตอบของ canary |
| --- | --- |
| Assumptions | การล้นเขียนต่อเนื่องจาก buffer ขึ้นไปหา return address |
| Creation of metadata | compiler ใส่โค้ดที่วาง canary ตอนเข้าฟังก์ชัน ส่วน random canary ถูกสุ่มตอนโปรแกรมเริ่ม |
| Validation of metadata | ตรวจตอนฟังก์ชันกำลังจะ return ปลอมได้ถ้าผู้โจมตีรู้ค่าแล้วเขียนค่าเดิมกลับลงไป |
| Handling of invalid data | หยุดโปรแกรม เช่น `*** stack smashing detected ***` ในตัวอย่างข้างบน |

### MemGuard — return address ที่อ่านได้อย่างเดียว

**MemGuard** ของทีม StackGuard อยู่ในตระกูลเดียวกันแต่ไม่ใช้ canary มันใช้กลไก virtual memory ทำให้ return address เป็นแบบอ่านอย่างเดียวระหว่างที่ฟังก์ชันทำงาน การเขียนทับจึงถูก CPU จับได้ทันที

ราคาของ MemGuard คือความช้า สิทธิ์อ่านอย่างเดียวคุมได้ทีละ page การเขียนลง word อื่นใน page เดียวกัน ซึ่งบน stack เกิดตลอดเวลา จึงถูกจับด้วย แล้วต้องให้ซอฟต์แวร์เขียนแทนทีละครั้ง

### ProPolice — ย้ายตัวแปรอันตรายออกจากทางล้น

<Why>
canary ถูกตรวจแค่ตอนฟังก์ชันกำลังจะกลับ ใน `func` ของรูปที่ 1 function pointer `fp` อยู่เหนือ `b` แต่ต่ำกว่า canary ที่วางไว้ใต้ return address การล้นจึงทับ `fp` ได้ และถ้าฟังก์ชันเรียกผ่าน `fp` ก่อนจบ โปรแกรมก็กระโดดไปที่อื่นก่อนที่ canary จะถูกตรวจ
</Why>

**ProPolice** ของ IBM Research ญี่ปุ่น ใช้ canary แบบเดียวกับ StackGuard ซึ่งมันเรียกว่า **guard** แล้วทำเพิ่มอีกอย่าง คือ **จัดลำดับตัวแปรใหม่** ให้ stack frame เรียงจาก address สูงลงต่ำแบบนี้

| ช่อง | ทำไมอยู่ตรงนี้ |
| --- | --- |
| arguments (A) | ผู้เรียกวางไว้ |
| return address | ต้องปกป้อง |
| previous frame pointer | ต้องปกป้อง |
| **guard** | การล้นจาก array ต้องผ่านตรงนี้ก่อน |
| arrays (B) | buffer ทุกตัวรวมกันอยู่ติด guard |
| local variables (C) | pointer และตัวแปรธรรมดา อยู่ใต้ buffer ทุกตัว |

การล้นเขียนจาก buffer ไปทาง address สูง ตัวแปรในกลุ่ม C จึงอยู่นอกทางล้นทั้งหมด

ตัวอย่างเช่น ถ้าโปรแกรมเมอร์ประกาศ function pointer ไว้ก่อน buffer แบบนี้

```c
int bar() {
    void (* funct2)();
    char buff[80];
}
```

gcc ที่ปิด stack protector วางตัวแปรที่ประกาศก่อนไว้ที่ address สูงกว่า `funct2` จึงอยู่เหนือ `buff` ในทางล้น

ProPolice จะจัดใหม่ให้เหมือนเขียนว่า

```c
int bar() {
    char buff[80];
    void (* funct2)();
}
```

ที่ ProPolice ทำไม่ได้คือ **pointer ที่อยู่ใน struct** ภาษา C กำหนดลำดับของ field ใน struct ไว้ตายตัวตามที่ประกาศ ถ้า struct มี buffer ตามด้วย function pointer compiler ก็สลับให้ไม่ได้

ลองทายก่อน: compile `age.c` ตัวเดิมด้วย `gcc` เฉย ๆ แล้วพิมพ์ `15` กับ `Krerk.P01` เหมือนเดิม โปรแกรมจะบอกว่าอายุเท่าไร

<Example added title="ตัวอย่างอายุตัวเดิม เมื่อเปิด stack protector">
```text
$ gcc -o age age.c && ./age
Enter your age:15
Enter your name:Krerk.P01
-----------
Krerk.P01 is 15 years old
```

บรรทัดคำเตือนของ linker เรื่อง `gets` ถูกตัดออกจากผลนี้เช่นกัน gcc บน Ubuntu เปิด `-fstack-protector-strong` ไว้เป็นค่าเริ่มต้น ซึ่งคือ ProPolice รุ่นที่อยู่ใน gcc มันย้าย `age` ลงไปไว้ใต้ `name`

<Detail label="ตำแหน่งตัวแปรจาก objdump">
| ตัวแปร (ตำแหน่งจาก `objdump -d` วัดจาก `rbp` ซึ่งคือ EBP ของ x86-64) | `-fno-stack-protector` | ค่าเริ่มต้น (`-fstack-protector-strong`) |
| --- | --- | --- |
| `age` | `rbp-0x4` อยู่เหนือ `name` | `rbp-0x2c` ย้ายลงไปอยู่ใต้ `name` |
| `name` | `rbp-0xc` | `rbp-0x28` |
| `tmp` | `rbp-0x20` | `rbp-0x20` |
| canary | ไม่มี | `rbp-0x8` |
</Detail>

ชื่อยังล้นสองไบต์เท่าเดิม แต่สองไบต์นั้นไปลงที่ `tmp[0]` และ `tmp[1]` ซึ่งโปรแกรมใช้เสร็จไปแล้ว และไม่ถึง canary โปรแกรมจึงไม่หยุด
</Example>

### PointGuard — เข้ารหัส pointer

<Why>
ProPolice สลับ field ใน struct ไม่ได้ ถ้าย้าย pointer ออกจากทางล้นไม่ได้ อีกทางคือทำให้ค่าที่ผู้โจมตีเขียนลงไปใช้ไม่ได้
</Why>

**PointGuard** ของ Oregon Graduate Institute (Immunix) **เข้ารหัส pointer ด้วย key ที่กำหนดไว้ก่อนทุกครั้งที่เก็บลงหน่วยความจำ และถอดรหัสทุกครั้งที่จะใช้** ค่าที่อยู่ในหน่วยความจำจึงไม่ใช่ address จริง

ถ้าผู้โจมตีล้นทับ pointer ด้วย address ที่ต้องการ ค่านั้นยังไม่ได้ถูกเข้ารหัส พอโปรแกรมดึงมาใช้ มันถูกถอดรหัสก่อน จึงกลายเป็น address สุ่ม ๆ ที่ไม่ใช่ทั้งของเดิมและของผู้โจมตี โปรแกรมจึงอ่านข้อมูลมั่วหรือพัง แทนที่จะไปถึงที่ที่ผู้โจมตีเลือก

<Detail label="ตัวอย่าง: เข้ารหัสด้วย XOR">
<Example added title="เข้ารหัสด้วย XOR">
PointGuard เข้ารหัสด้วยการ XOR กับ key ลับ โปรแกรม C เล็ก ๆ ที่ใช้ key `0x5f3c9a21` ให้ผลแบบนี้

| ค่าที่ลงไปในหน่วยความจำ | ค่าที่เก็บอยู่ | ถอดออกมาได้ |
| --- | --- | --- |
| pointer จริง `0x0804a010` ผ่านการเข้ารหัส | `0x57383a31` | `0x0804a010` ตรงเดิม |
| ค่าที่ถูกเขียนทับลงไปตรง ๆ | `0x41414141` | `0x1e7ddb60` ไม่ใช่ทั้งของเดิมและของผู้เขียน |
</Example>
</Detail>

คำถามที่ PointGuard ต้องตอบมีสี่ข้อ

- **Compatibility** — โค้ดที่ไม่ได้ compile ด้วย PointGuard เช่นไลบรารีเก่า อ่าน pointer แบบไม่ถอดรหัส
- **Initialization** — key ถูกสร้างตอนไหน และ pointer ที่มีอยู่ก่อน key จะถูกเข้ารหัสยังไง
- **Performance** — ต้องถอดรหัสทุกครั้งที่ใช้ pointer
- **Encryption Algorithm** — ต้องเร็วพอจะทำทุกครั้งที่แตะ pointer แต่แข็งพอที่ผู้โจมตีจะเดา key ไม่ได้

### Copy of Address — เก็บ return address ไว้อีกที่

ถ้า return address มีสำเนาอยู่ในที่ที่การล้นเอื้อมไม่ถึง ตอนฟังก์ชันกลับก็เทียบสองค่ากันได้ หรือใช้สำเนาแทนไปเลย ระบบในกลุ่มนี้ต่างกันที่ว่าสำเนาอยู่ที่ไหน

- **Split Stack** (UIUC) — แยก stack เป็นสองอัน **control stack** เก็บ return address อย่างเดียว ส่วน **data stack** เก็บ parameter, frame pointer และตัวแปร
  - แบบที่ compiler ทำ (compiler-based split stack) data stack ยังมี return address อยู่ และ control stack เป็นสำเนา
  - แบบที่ฮาร์ดแวร์ช่วย (architecture-supported split stack) return address ออกจาก data stack ไปเลย buffer ล้นเท่าไรก็ไม่เจอ return address
- **SRAS** (UIUC) — ใช้ <Term en="Return Address Stack (RAS)" th="stack ของ return address ใน CPU" /> ซึ่งเป็นวงจรที่ CPU มีอยู่แล้วไว้ทายว่า return จะกลับไปที่ไหน มาเป็นสำเนาไว้ตรวจ ปัญหามีสามข้อ
  - RAS มีขนาดจำกัดจึงเต็มได้ (overflow)
  - RAS ถูกอัปเดตตอน CPU ทำงานล่วงหน้าแบบ speculative
  - SRAS รับมือกับ <Term en="Non-LIFO Control Flow" th="call กับ return ไม่จับคู่ตามลำดับ" /> ไม่ได้ [Lecture 8.2](/2110413-csy/lecture-8-2#โปรแกรมที่ไม่ได้กลับตามลำดับ) มีตัวอย่างโค้ดแบบนี้

<Detail label="ระบบอื่นในกลุ่ม copy of address">
- **StackGhost** (Purdue) — ใช้ register window ของ CPU SPARC ซึ่งถือ return address ไว้ใน register ก่อนจะย้ายลง stack จึงมีจังหวะให้ตรวจหรือเก็บสำเนาไว้
- **RAD** (State U. of New York at Stony Brook) — เก็บสำเนาไว้ใน **Return Address Repository (RAR)** แบบ MineZone RAR ล้อม RAR ด้วย page ที่ห้ามแตะ ส่วนแบบ Read-only RAR ใช้ `mprotect` ทำให้ RAR อ่านได้อย่างเดียว คำถามที่ค้างคือ performance
- **StackShield** (Vendicator) — เก็บสำเนาของ return address ไว้ ตอนกลับจะคัดลอกสำเนาทับของเดิม หรือเทียบกับสำเนาก็ได้ และบังคับให้การเรียกผ่าน function pointer ไปได้แค่ส่วนโค้ด (text section) ข้อนี้ขัดกับโปรแกรมที่สร้างโค้ดใน heap เช่นด้วย `malloc` แล้วรันโค้ดนั้นอย่างถูกต้อง เช่น LISP และภาษา OOP บางระบบ
- **LibVerify** (Bell Labs) — ตัวที่อยู่ในกลุ่ม copy of address แก้ binary ของโปรแกรมให้ทุกฟังก์ชันเข้าผ่านโค้ดห่อ ขาเข้าเก็บ return address ขาออกตรวจก่อนกลับ
- **LibSafe** (Bell Labs) — มาคู่กับ LibVerify แต่ไม่ได้เก็บสำเนา address มันแทน `strcpy` และฟังก์ชันพวกเดียวกันด้วยรุ่นที่คำนวณก่อนว่าปลายทางยาวได้แค่ไหน โดยใช้ frame pointer เป็นขอบบน การล้นจึงไปได้ไม่เกิน stack frame ของตัวเอง
- **DISE** (Dynamic Instruction Stream Editing) — ฮาร์ดแวร์ที่แก้สายคำสั่งของโปรแกรมระหว่าง decode จึงแทรกคำสั่งที่เก็บและตรวจ return address ได้
- **SCACHE** — cache ที่เก็บสำเนาแบบอ่านอย่างเดียวของ return address ไว้ในตัว แล้วเทียบกับค่าที่ดึงจาก stack ตอนกลับ
</Detail>

### Tags — tag หนึ่งบิตที่ตัว word

แบบสุดท้ายติดบิตหนึ่งบิตให้ทุก word ในหน่วยความจำ บอกว่า word นั้นเป็น return address หรือ function pointer CPU จึงรู้ว่า word ไหนห้ามถูกทับด้วยข้อมูลธรรมดา IBM System/38 ทำแบบนี้ในฮาร์ดแวร์ แนวคิดเดียวกับ [tagged memory ใน Lecture 6](/2110413-csy/lecture-6#tagged-memory)

Tags ใกล้กับ Secure Bit ใน [Lecture 8.2](/2110413-csy/lecture-8-2) ที่สุด ต่างกันตรงที่ tag บอกว่า word ไหน **เป็น** address ส่วน Secure Bit บอกว่า word ไหน **มาจากข้างนอก**

<Quiz question="โปรแกรมหนึ่ง compile ด้วย StackGuard และ ProPolice ฟังก์ชันหนึ่งมีตัวแปร struct ที่ประกาศ field char name[16] ตามด้วย function pointer on_done แล้วคัดลอก input ลง name ด้วย strcpy จากนั้นเรียก on_done ก่อนฟังก์ชันจบ ถ้า input ยาวเกิน 16 ไบต์ วิธีไหนจับได้">
ProPolice ย้ายตัวแปรทั้งตัวได้ แต่สลับ field ใน struct ไม่ได้ `on_done` จึงยังอยู่เหนือ `name` ในทางล้น ส่วน canary อยู่เหนือ struct ทั้งก้อนและถูกตรวจตอนฟังก์ชันกลับ แต่โปรแกรมกระโดดผ่าน `on_done` ที่ถูกทับไปก่อนจังหวะนั้น

คำตอบคือ **ไม่มีวิธีไหนจับได้** โปรแกรมไปที่ที่ค่าใหม่ของ `on_done` ชี้ ก่อนที่ canary จะถูกตรวจ

คำตอบที่ผิดบ่อยคือ "canary จับได้ เพราะการล้นเขียนต่อเนื่องจาก buffer" การล้นต่อเนื่องจริง และถ้ายาวพอก็จะทับ canary ด้วย แต่การตรวจเกิดตอนกลับ ซึ่งช้าไปแล้ว
</Quiz>

## ส่วนที่ 5 — taint input ตรวจขอบเขต และสุ่ม address

### Input Protection — ห้ามใช้ input เป็น control data

<Why>
ข้อสังเกตในส่วนที่ 2 บอกว่าของที่ล้นเข้ามามาจาก domain อื่นเสมอ ถ้า CPU จำได้ว่าค่าไหนมาจากข้างนอก มันไม่ต้องสนใจเลยว่าค่านั้นไปลงที่ไหน แค่ไม่ยอมใช้ค่านั้นเป็น address ที่จะกระโดดไปหา
</Why>

<Term en="Input Protection" th="ป้องกันที่ตัว input" /> มีกฎข้อเดียวคือ **input ห้ามถูกใช้เป็น control data**

ข้อมูลที่เข้ามาจาก domain ที่ไม่น่าไว้ใจจะถูก <Term en="Taint" th="ทำเครื่องหมายว่าไม่น่าไว้ใจ" /> และเครื่องหมายนี้ติดไปกับค่าทุกครั้งที่ถูกคัดลอกหรือคำนวณต่อ

ระบบในกลุ่มนี้ต่างกันสองจุด คือ taint ที่ขอบเขตไหน และ untaint เมื่อไร

| ระบบ | taint ที่ขอบเขตไหน (Boundary) | untaint เมื่อไร (Untaint) |
| --- | --- | --- |
| **Minos** | segment พิเศษที่ kernel ใช้คัดลอก input | ตัดสินจากเวลาที่ข้อมูลถูกสร้าง (creation time) |
| **Tainted pointer** | ฟังก์ชัน I/O ของ SimpleScalar ซึ่งเป็นโปรแกรมจำลอง CPU แบบ RISC | เมื่อค่าผ่านคำสั่ง `CMP` หรือ `XOR` |
| **Dynamic Flow Tracking** | ฟังก์ชัน I/O ของ SimpleScalar | เมื่อค่าผ่านคำสั่ง `XOR` |

Minos taint ทุก word ที่ kernel คัดลอกเข้า process ผ่าน segment พิเศษ ส่วนไฟล์ที่สร้างหรือแก้ก่อนเวลาที่ตั้งไว้ตอนติดตั้งระบบ เช่นไลบรารี ถือว่าไว้ใจได้

การ untaint มีไว้ให้โปรแกรมที่ตรวจ input แล้วใช้มันต่อได้ `CMP` คือการเทียบค่า ระบบจึงถือว่าค่าที่ถูกเทียบแล้วผ่านการตรวจมาแล้ว ส่วน `XOR` ของ register กับตัวเองให้ศูนย์เสมอ ผลจึงไม่ขึ้นกับ input เลย

ราคาของกฎแบบนี้คือการ untaint ผิดที่ ค่าที่ถูกเทียบแล้วไม่ได้แปลว่าปลอดภัยเสมอไป

<Example added title="CMP ที่ untaint input ทั้งบรรทัด">
```c
while ((c = getchar()) != '\n') buf[i++] = c;
```

ลูปนี้เทียบทุกไบต์ของ input กับ `'\n'` เพื่อหาท้ายบรรทัด ตามกฎของ Tainted pointer ทุกไบต์ที่ลง `buf` จึงถูก untaint รวมทั้ง address ที่ผู้โจมตีแฝงมาในบรรทัดนั้น ทั้งที่การเทียบนี้ไม่ได้ตรวจความปลอดภัยเลย
</Example>

### Bounds Checking — ทุกการเข้าถึงต้องรู้ขอบ

<Why>
`name` ในตัวอย่างอายุล้นเพราะ `gets` ไม่รู้ว่า `name` จุได้ 8 ไบต์ ถ้าทุกการเขียนรู้ขอบของ buffer ไบต์ที่ 9 ก็ถูกจับก่อนถึง `age`
</Why>

<Term en="Bounds Checking" th="ตรวจว่าเขียนไม่เกินขอบ buffer" /> แก้ปัญหาตรงที่สุด คือตรวจทุกครั้งที่เขียนว่ายังอยู่ใน buffer หรือเปล่า

ทุก buffer ต้องถูกประกาศพร้อมฐาน (base) และขอบ (boundary) ซึ่งเก็บไว้ใน symbol table หรือใน **segment descriptor table** ของ CPU

อีกแบบคือ **enhanced pointer** ที่ pointer หนึ่งตัวเก็บสามค่า คือ base, ค่าของ pointer และ limit ของ storage object ที่มันชี้

CPU ที่ทำแบบนี้ในฮาร์ดแวร์คือ Intel IA-32 ผ่าน segmentation และ Intel iAPX 432 (I-432) ซึ่งต้องประกาศขอบเขตให้ **ทุกตัวแปร** รวมทั้ง int และ float เพราะ pointer เขียนลงตัวแปรตัวไหนก็ได้ ถ้าตัวแปรไหนไม่มีขอบเขตกำกับ การเขียนที่เลยเข้าไปในตัวนั้นก็ตรวจไม่ได้

```c
char *a;
char b[10];
a = b;
for (a=b; a<&b[10]; a++)
    *a='0';
b[11]=10;
```

pointer `a` รับ base และ limit ของ `b` มาด้วย ลูปเขียนได้ครบสิบช่องเพราะอยู่ในขอบ แต่ `b[11]=10;` อยู่นอกขอบจึงถูกจับตอนรัน

<Detail label="บรรทัดที่สามของโค้ดต้นฉบับ compile ไม่ผ่าน">
บรรทัดที่สามในสไลด์เขียนว่า `*a = &b;` ซึ่ง compile ไม่ผ่าน gcc 15.2 ตอบว่า `error: assignment to 'char' from 'char (*)[10]' makes integer from pointer without a cast` โค้ดข้างบนจึงใช้ `a = b;` ซึ่งตรงกับเจตนาของตัวอย่าง
</Detail>

ราคาของการตรวจแบบนี้คือ **ช้าลงมากกว่า 30 เท่า**

### Obfuscation — ทำให้เดา address ไม่ได้

ผู้โจมตีต้องรู้ address ของสิ่งที่จะให้โปรแกรมกระโดดไปหา <Term en="Address Obfuscation" th="ทำให้เดา address ไม่ได้" /> ของ Stony Brook จึงทำให้ address เปลี่ยนไปทุกครั้งที่รัน ด้วยสามวิธี

- สุ่ม base address ของแต่ละ segment ของหน่วยความจำ คือ stack, <Term en="Heap" th="หน่วยความจำที่จองตอนรัน" />, BSS, data และ text
- สลับลำดับของตัวแปร ฟังก์ชัน และ structure
- เว้นช่องว่างขนาดสุ่มระหว่าง object เช่นระหว่าง buffer กับ return address ผู้โจมตีจึงไม่รู้ว่าต้องล้นกี่ไบต์ถึงจะถึง

BSS เก็บตัวแปร global ที่ไม่ได้ให้ค่าเริ่มต้น data เก็บตัวแปร global ที่มีค่าเริ่มต้น และ text เก็บโค้ดซึ่งอ่านได้อย่างเดียว

ปัญหาของมันมีสองข้อ

- **Fragmentation** — หน่วยความจำแตกเป็นชิ้น
- **Compatibility** — โปรแกรมที่ฝัง address ตายตัวไว้ทำงานไม่ได้

วิธีที่คล้ายกันและใช้กันแพร่หลายคือ <Term en="Address Space Layout Randomization (ASLR)" th="สุ่มตำแหน่งในหน่วยความจำ" /> ของ PaX

PaX คือชุด patch ของ Linux kernel ที่เพิ่มการป้องกันหน่วยความจำ

ASLR ต่างจาก address obfuscation ตรงที่มันสุ่มแค่ base ของแต่ละ segment ทั้ง stack จึงย้ายไปทั้งก้อน ระยะห่างระหว่างตัวแปรใน frame เดียวกันเท่าเดิม

### ทำให้ฉีดโค้ดไม่ได้ — ISR และ SPEF

อีกสองวิธีไม่ได้ซ่อน address แต่ทำให้โค้ดที่ผู้โจมตีฉีดเข้ามารันไม่ได้

<Term en="Instruction-Set Randomization (ISR)" th="สุ่มรหัสคำสั่งแยกต่อ process" /> ของ Columbia U. และ Drexel U. XOR ทุกคำสั่งของโปรแกรมด้วย key ประจำ process แล้ว CPU XOR กลับก่อนรัน โค้ดที่ฉีดเข้ามาไม่ได้ถูก XOR ไว้ล่วงหน้า พอถูก XOR กลับจึงกลายเป็นคำสั่งมั่ว ๆ

ISR มีคำถามค้างสองข้อ ไลบรารีที่หลาย process ใช้ร่วมกันจะใช้ key ของใคร (Library?) และการโจมตีที่ไม่ได้ฉีดโค้ดแต่เปลี่ยนข้อมูลจะถูกจับได้ยังไง (Data?)

**SPEF** หรือ Secure Program Execution Framework ของ Microsoft และ UCLA ใช้การเข้ารหัสตอนติดตั้งโปรแกรม ตัวติดตั้งคำนวณค่าตรวจสอบของคำสั่งทีละก้อนด้วย key ที่ฝังอยู่ใน CPU แต่ละตัว แล้วซ่อนค่านั้นไว้ในก้อนคำสั่งเอง

ตอนรัน CPU ถอดรหัสและเรียงคำสั่งคืนใน instruction cache (I-CACHE) แล้วตรวจค่านั้นก่อนรัน โค้ดที่ไม่ได้ผ่านการติดตั้งไม่มีค่าที่ถูกต้อง จึงรันไม่ได้

คำถามที่ค้างของ SPEF คือ performance และข้อมูลที่ไม่ใช่โค้ด

<Pitfall>
ความเชื่อที่ผิดคือ **ถ้าทำให้ผู้โจมตีฉีดโค้ดเข้ามาไม่ได้ ก็โจมตีด้วย buffer overflow ไม่ได้แล้ว**

ข้อนี้ไม่จริง

มันดูจริงเพราะภาพจำของการโจมตีคือการส่งโค้ดอันตรายเข้าไปพร้อมกับข้อมูลที่ล้น และ ISR กับ SPEF ก็ปิดทางนั้นได้จริง

ที่ถูกคือ **เงื่อนไขข้อแรกในส่วนที่ 2 มีสองทาง** คือฉีดโค้ดเข้าไปเอง หรือรู้ address ของโค้ดที่มีอยู่ในหน่วยความจำแล้ว การสาธิตใน [Lecture 8.2](/2110413-csy/lecture-8-2#ทดสอบสี่ด้าน) ใช้ทางที่สอง `residentcode()` เป็นฟังก์ชันที่มีอยู่แล้วในโปรแกรมและเปิด `/bin/sh` ผู้โจมตีแค่เขียน address ของมันลงในช่องที่โปรแกรมจะกระโดดไป จึงไม่มีคำสั่งไหนของผู้โจมตีให้ ISR หรือ SPEF จับ
</Pitfall>

<Quiz question="เครื่องหนึ่งเปิด ASLR ไว้ และใช้ ISR ด้วย ผู้โจมตีส่งข้อมูลเข้าไปให้ล้นตัวแปร is_admin ที่อยู่ติดกับ buffer ทั้งสองวิธีช่วยได้ไหม">
ASLR ซ่อน address ซึ่งมีผลเมื่อผู้โจมตีต้องเขียน address ลงไป ISR ทำให้โค้ดที่ฉีดเข้ามารันไม่ได้ แต่การทับ `is_admin` ไม่ต้องรู้ address ของอะไรเลย เพราะตัวแปรอยู่ติดกับ buffer เสมอไม่ว่า stack จะย้ายไปไหน และไม่ได้ฉีดโค้ดสักบรรทัด

คำตอบคือ **ไม่ช่วยทั้งคู่** เหมือนที่ตัวอย่างอายุในส่วนที่ 2 ยังได้ 49 เมื่อ compile โดยปิด stack protector ไม่ว่าจะสุ่ม address หรือไม่

คำตอบที่ผิดบ่อยคือ "ASLR ช่วยได้ เพราะผู้โจมตีไม่รู้ว่าตัวแปรอยู่ที่ไหน" ซึ่งลืมว่า ASLR ย้ายทั้ง stack ไปพร้อมกัน ระยะห่างระหว่างตัวแปรใน frame เดียวกันไม่เปลี่ยน วิธีที่ช่วยในเคสนี้คือการจัดลำดับใหม่ของ ProPolice ซึ่งย้าย `is_admin` ไปไว้ใต้ buffer
</Quiz>

## ส่วนที่ 6 — Isolation: ยอมให้ล้น แต่จำกัดผล

<Why>
สมมติว่าทุกการตรวจในส่วนที่ 4 และ 5 พลาดหมด return address ถูกทับโดยไม่มีใครจับได้ และโปรแกรมกำลังรันโค้ดที่ผู้โจมตีเลือก สิ่งที่ยังทำได้คือขีดเส้นว่าโค้ดนั้นแตะอะไรได้บ้าง
</Why>

Isolation ไม่พยายามจับการล้นเลย แต่จำกัดว่าโค้ดที่ได้จากการโจมตีทำอะไรได้ มีสามแบบ

- **จำกัดการรันโค้ด** — <Term en="Non-Executable Memory (NX)" th="หน่วยความจำที่ห้ามรันเป็นโค้ด" /> ห้ามรันคำสั่งจาก stack หรือหน่วยความจำส่วนข้อมูล ทำได้ทั้งในซอฟต์แวร์และฮาร์ดแวร์ และมีแบบที่ป้องกัน kernel ด้วย (kernel NX)
- **กัก process ทั้งตัวใน sandbox** — ห้าม process แตะทรัพยากรบางอย่างของระบบตาม policy ที่ตั้งไว้ก่อน ตัวอย่างคือ TCPA (Trusted Computing Platform Alliance) กลุ่มบริษัทที่วางมาตรฐานฮาร์ดแวร์ trusted computing หลักเดียวกับ [sandbox ใน Lecture 6](/2110413-csy/lecture-6#sandbox)
- **ติดตั้งโค้ดและสภาพแวดล้อมตอนรันอย่างปลอดภัย** — SPEF ในส่วนที่ 5

NX มีคำถามสามข้อที่มันตอบไม่ได้

- **Heap-based attack** — NX ไม่ได้กันการล้นเลย มันกันแค่การรันคำสั่งจาก page ที่ห้ามรัน NX แบบที่ห้ามแค่ stack จึงยังปล่อยให้โค้ดที่ถูกฉีดไว้ใน heap รันได้
- **โปรแกรมที่ต้องรันโค้ดบน stack จริง ๆ** — โปรแกรมบางแบบสร้างโค้ดบน stack หรือ heap แล้วรันอย่างถูกต้อง NX ทำให้โปรแกรมพวกนี้พัง
- **การโจมตีที่ไม่ได้ฉีดโค้ด** — แบบเดียวกับใน pitfall ของส่วนที่ 5 NX ไม่มีอะไรให้จับ

### LaGrande และ NGSCB — แยก domain ด้วยฮาร์ดแวร์

<Why>
sandbox ที่บังคับด้วยซอฟต์แวร์ถูกโค้ดที่มันกักไว้เขียนทับได้ ถ้าทั้งสองรันด้วยสิทธิ์เดียวกันในหน่วยความจำเดียวกัน ([ส่วนที่ 3 ของ Lecture 6](/2110413-csy/lecture-6#ส่วนที่-3--ฮาร์ดแวร์ที่ทำให้ขอบเขตเป็นจริง)) จึงต้องให้ฮาร์ดแวร์เป็นคนแยก domain
</Why>

LaGrande ของ Intel และ NGSCB ของ Microsoft คือแพลตฟอร์มที่ฮาร์ดแวร์ช่วยทำ sandbox โดยแยก domain ออกจากกัน (domain separation)

<Detail label="ความสามารถสี่ข้อของ NGSCB และชั้นของ LaGrande">
NGSCB มีสี่ความสามารถ

- **Strong process isolation** — process หนึ่งแตะหน่วยความจำของอีก process ไม่ได้
- **Sealed storage** — ข้อมูลที่เก็บไว้ผูกกับโปรแกรมที่เก็บ โปรแกรมอื่นเปิดไม่ได้
- **Secure user interface** — ทางเชื่อมระหว่างผู้ใช้กับโปรแกรมที่โปรแกรมอื่นดักไม่ได้
- **Attestation** — พิสูจน์ให้เครื่องอื่นเห็นว่ากำลังรันซอฟต์แวร์อะไรอยู่

LaGrande แบ่งเป็นชั้นแบบนี้

- **Standard partition** — รันแอปบน OS ตามปกติ
- **Protected partition** — รัน applet ซึ่งเป็นโปรแกรมเล็กที่ทำงานเฉพาะอย่าง บน kernel ของตัวเองใน protected memory และยังขอใช้ทรัพยากรฝั่ง Standard ได้
- **Domain Manager** — อยู่ใต้ทั้งสองฝั่ง และแยกสองฝั่งออกจากกัน
- **ฮาร์ดแวร์** — CPU และ chipset ที่รองรับ LT (LaGrande Technology), protected I/O และ TPM ช่วยกันกันการเข้าถึงทรัพยากรและทำ attestation

TPM ย่อจาก Trusted Platform Module เป็นชิปที่เก็บ key และบันทึกค่าที่วัดได้จากซอฟต์แวร์ที่บูตขึ้นมา
</Detail>

Secure Bit วางตัวเป็นส่วนเสริมของสองระบบนี้ ไม่ใช่ของแทน คำถามที่ตามมาคือ **trusted เท่ากับ secure หรือเปล่า**

คำตอบคือไม่เท่ากัน process ที่ถูกแยกไว้อย่างดีและพิสูจน์ได้ว่าเป็นโปรแกรมที่ถูกต้อง ยังมี buffer overflow อยู่ข้างในได้ การแยก domain กันไม่ให้ความเสียหายลามออกไป แต่ไม่ได้กันการถูกยึดภายใน domain นั้นเอง

<Quiz question="เว็บเซิร์ฟเวอร์ตัวหนึ่งรันใน sandbox ที่ห้ามแตะไฟล์ทุกไฟล์นอกโฟลเดอร์ของเว็บ แล้วถูกยึดด้วย buffer overflow ผู้โจมตีทำอะไรได้บ้าง">
sandbox จำกัดตาม policy ของ process ไม่ได้ดูว่าใครเป็นคนสั่ง โค้ดที่ผู้โจมตีพาโปรแกรมไปรันจึงได้สิทธิ์เท่ากับเว็บเซิร์ฟเวอร์ทุกประการ

คำตอบคือ **ทำได้ทุกอย่างที่เว็บเซิร์ฟเวอร์ทำได้** อ่านและแก้ไฟล์ในโฟลเดอร์เว็บ ส่งข้อมูลออกทางเครือข่าย และเห็นข้อมูลของผู้ใช้ทุกคนที่เชื่อมต่อเข้ามา แต่แตะไฟล์ระบบนอกโฟลเดอร์นั้นไม่ได้

คำตอบที่ผิดบ่อยคือ "ทำอะไรไม่ได้ เพราะอยู่ใน sandbox" ซึ่งลืมว่า isolation ยอมให้การโจมตีสำเร็จตั้งแต่แรก มันแค่ขีดเส้นว่าความเสียหายไปได้ไกลแค่ไหน
</Quiz>

- คำถามสี่ข้อของ dynamic solution: assumptions, การสร้าง metadata, การตรวจ metadata, การจัดการข้อมูลผิด

**[ปกป้อง address](#ส่วนที่-4--ปกป้อง-address-ไม่ให้ถูกเปลี่ยนโดยไม่มีใครรู้)**

- canary (StackGuard): random, terminator ค่าเปลี่ยนเมื่อไรก็หยุดก่อนกลับ; MemGuard ทำ return address ให้อ่านอย่างเดียว
- ProPolice: guard + ย้าย array ไปติด guard และ pointer ไปไว้ใต้ array กัน pointer ใน struct ไม่ได้
- PointGuard: เข้ารหัส pointer ตอนเก็บ ถอดตอนใช้
- copy of address: Split Stack, StackGhost, SRAS, RAD, StackShield, LibVerify, DISE, SCACHE
- tags: IBM System/38
- canary จับการเขียนผ่าน pointer ที่ข้ามมันไม่ได้

**[taint input ตรวจขอบเขต สุ่ม address](#ส่วนที่-5--taint-input-ตรวจขอบเขต-และสุ่ม-address)**

- input protection: input ห้ามเป็น control data (Minos, Tainted pointer, Dynamic Flow Tracking); untaint ผิดที่ทำให้หลุด
- bounds checking: base และ boundary ทุกตัวแปร ช้าลงกว่า **30 เท่า**
- obfuscation: สุ่ม base, สลับลำดับ, เว้นช่องสุ่ม, PaX ASLR
- ทำให้ฉีดโค้ดไม่ได้: ISR, SPEF (SPEF นับเป็น isolation ด้วย)
- ฉีดโค้ดไม่ได้ไม่ได้แปลว่าปลอดภัย เพราะใช้โค้ดที่มีอยู่แล้วได้

**[Isolation](#ส่วนที่-6--isolation-ยอมให้ล้น-แต่จำกัดผล)**

- NX, sandbox (TCPA), SPEF; NX ไม่ช่วยกับ heap, โปรแกรมที่ต้องรันโค้ดบน stack และการโจมตีที่ไม่ฉีดโค้ด
- NGSCB: strong process isolation, sealed storage, secure user interface, attestation — trusted ไม่ได้แปลว่า secure
