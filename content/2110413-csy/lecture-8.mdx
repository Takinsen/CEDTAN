<KeyIdea>
buffer overflow จะยึดโปรแกรมได้ก็ต่อเมื่อมันเขียนทับ **address ที่โปรแกรมจะกระโดดไปหา** เช่น return address หรือ function pointer ด้วยข้อมูลที่มาจากนอก process วิธีป้องกันทุกแบบในคาบนี้ดักขั้นใดขั้นหนึ่งของเส้นทางนั้น ส่วน <Term en="Secure Bit" th="บิตบอกว่าข้อมูลมาจากข้างนอก" /> ติดบิตหนึ่งบิตให้ทุกค่าที่เข้ามาจากข้างนอก แล้วให้ CPU ไม่ยอมกระโดดไปตาม address ที่มีบิตนั้น
</KeyIdea>

## ส่วนที่ 1 — ช่องโหว่เก่าที่ยังไม่หายไป

### worm ดังเกือบทุกตัวเข้าทางเดียวกัน

<Term en="Buffer Overflow" th="เขียนข้อมูลเกินขนาด buffer" /> คือการเขียนข้อมูลลง buffer เกินกว่าที่จองไว้ ส่วนที่เกินจึงไปทับข้อมูลที่อยู่ติดกันในหน่วยความจำ ส่วนที่ 2 จะแสดงให้เห็นทีละไบต์

worm อินเทอร์เน็ตตัวดังเกือบทุกตัวใช้ช่องโหว่นี้เข้าเครื่อง [worm](/2110413-csy/lecture-1#malicious-software) คือโปรแกรมที่แพร่จากเครื่องหนึ่งไปอีกเครื่องได้เองโดยไม่ต้องมีคนกด

| ปี | worm | ล้นที่ไหน |
| --- | --- | --- |
| 1988 | Morris worm, worm ตัวแรก | `fingerd` บริการบน Unix ที่ตอบว่าเครื่องนี้มีผู้ใช้ชื่ออะไร ติดไป 10% ของอินเทอร์เน็ตในตอนนั้น |
| 2001 | Code Red | buffer overflow |
| 2003 | Slammer | buffer overflow |
| 2003 | Blaster และ Welchia | DCOM RPC ของ Windows บริการที่ให้เครื่องอื่นเรียกฟังก์ชันบนเครื่องนี้ผ่านเครือข่าย |
| 2004 | Witty | ออกมาหนึ่งวันหลังประกาศช่องโหว่ |
| 2004 | Sasser | LSASS ของ Windows process ที่ตรวจรหัสผ่านตอน login คาดว่าแกะวิธีมาจากประกาศช่องโหว่ |
| 2006 | ช่องโหว่บน Mac | ส่วน wireless |

สองแถวของปี 2004 บอกเรื่องเดียวกัน คือ **ประกาศช่องโหว่และ patch เป็นแผนที่ให้ผู้โจมตีด้วย** Witty ใช้เวลาแค่หนึ่งวันจากวันประกาศถึงวันที่ worm ออก คนที่รอลง patch สัปดาห์หน้าจึงช้าไปแล้ว และรายการนี้ยังยาวกว่านี้อีกมาก

### ความเสียหายนอกจอคอมพิวเตอร์

Slammer ปี 2003 ลามไปถึงระบบที่ไม่มีใครคิดว่าเป็นคอมพิวเตอร์

ข่าวของ SecurityFocus วันที่ 19 สิงหาคม 2003 ("Slammer worm crashed Ohio nuke plant network") รายงานว่าในเดือนมกราคม Slammer เข้าไปในเครือข่ายภายในของโรงไฟฟ้านิวเคลียร์ Davis-Besse ในโอไฮโอ ระบบเฝ้าระวังความปลอดภัยใช้การไม่ได้เกือบห้าชั่วโมง ทั้งที่พนักงานเชื่อว่ามี firewall กันอยู่ เรื่องนี้เล่าเต็มไว้ใน [หลักการที่ 9 ของ Lecture 1](/2110413-csy/lecture-1#หลักการที่-9--dont-extend-trust-easily)

บทความ "Inside the Slammer Worm" ใน IEEE Security and Privacy ฉบับกรกฎาคม–สิงหาคม 2003 รายงานอีกสามอย่าง

- เครื่องรับแจ้งเหตุ 911 ของเมือง Bellevue รัฐวอชิงตัน ล่ม
- ตู้ ATM ของ Bank of America 13,000 เครื่องล่ม
- packet ที่มันส่งออกมาท่วม router จนโครงสร้างพื้นฐานของอินเทอร์เน็ตบางส่วนล่มตาม

<Pitfall>
ความเชื่อที่ผิดคือ **ไฟดับครั้งใหญ่ในอเมริกาและแคนาดาวันที่ 14 สิงหาคม 2003 เกิดจาก worm Blaster**

ข้อนี้ไม่จริง ตามรายงานเบื้องต้นเรื่องสาเหตุของไฟดับครั้งนั้น ("Interim Report: Causes of the August 14th Blackout in the United States and Canada")

มันดูจริงเพราะ Blaster ระบาดในสัปดาห์เดียวกันพอดี หลังวันที่ 11 สิงหาคม มันติดเครื่อง Windows ไปมากกว่าหนึ่งล้านเครื่อง

ที่เกิดจริงคือ **เครื่องที่คุมการผลิตและจ่ายไฟแยกขาดจากอินเทอร์เน็ต จึงไม่โดน Blaster เลย** ต้นเหตุคือระบบเตือนภัยของบริษัทไฟฟ้า FirstEnergy ในโอไฮโอล้มต่อกันเป็นทอด ทั้งเครื่องที่รัน "alarm and logging software" ของห้องควบคุม เครื่องสำรอง และ remote-control console อีกหลายตัว ผู้ควบคุมจึงไม่รู้ว่าเกิดอะไรขึ้น และสกัดปัญหาไม่ทัน

ในเวลาเดียวกัน เครื่องแสดงสถานะของ Midwest Independent Transmission System Operator หน่วยงานที่ดูแลการจ่ายไฟของภูมิภาค ก็เสีย ช่างที่มาซ่อมลืมเปิดเครื่องกลับก่อนออกไปกินข้าวกลางวัน
</Pitfall>

ข่าวจาก CERT วันที่ 7 กันยายน 2006 มีบันทึกช่องโหว่สองฉบับห่างกันสองวัน ทั้งคู่ทำให้ **ผู้โจมตีสั่งรันโค้ดอะไรก็ได้บนเครื่องเหยื่อ**

- VU#821156 (24 สิงหาคม 2006) — Microsoft Internet Explorer ล้นเมื่อเจอ URL ที่ยาวมาก
- VU#394444 (22 สิงหาคม 2006) — stack buffer overflow ใน Microsoft Hyperlink Object Library

สิบสี่ปีต่อมาก็ยังไม่หาย ค้นคำว่า buffer overflow ในฐานข้อมูลช่องโหว่ของ CERT ที่ Software Engineering Institute ได้ 1,347 ฉบับ แยกตามปีได้แบบนี้

| ปี | 2015 | 2016 | 2017 | 2018 | 2019 | 2020 |
| --- | --- | --- | --- | --- | --- | --- |

ตัวเลขนี้คือจำนวนผลค้นหาที่เว็บแยกตามปีให้ ไม่ใช่จำนวนช่องโหว่ทั้งหมดที่พบในปีนั้น ปี 2020 ที่กระโดดเป็น 213 จึงอ่านเป็นแนวโน้มไม่ได้ ที่บอกได้คือช่องโหว่ชนิดนี้ยังถูกบันทึกเพิ่มทุกปี

## ส่วนที่ 2 — ข้อมูลที่ล้นไปเปลี่ยนทางเดินของโปรแกรมได้ยังไง

### ล้นคืออะไร — ชื่อที่ยาวเกินไปหนึ่งตัวอักษร

<Why>
โปรแกรมข้างล่างถามอายุก่อน แล้วถามชื่อ ช่องเก็บชื่อจุได้ 8 ไบต์ คนชื่อ `Krerk.P01` พิมพ์อายุ 15 แต่โปรแกรมตอบว่าเขาอายุ 49
</Why>

```c
int age;
char name[8];
char tmp[20];
printf("Enter your age:");
gets(tmp);
age=atoi(tmp);
printf("Enter your name:");
gets(name);
printf("-----------\n%s is %d years old\n",name,age);
```

```text
$ gcc -fno-stack-protector -o age age.c
$ ./age
Enter your age:15
Enter your name:Krerk.P01
-----------
Krerk.P01 is 49 years old
```

`gets` อ่านทั้งบรรทัดลง buffer ที่ได้รับมา โดยไม่รู้ว่า buffer นั้นยาวเท่าไร

`Krerk.P01` ยาว 9 ตัวอักษร บวก `\0` ที่ปิดท้ายสตริงอีกหนึ่งไบต์เป็น 10 ไบต์ แต่ `name` จุได้แค่ 8 สองไบต์ที่เกินจึงลงไปในตัวแปรที่อยู่ถัดไปในหน่วยความจำ ซึ่งคือ `age`

| ไบต์ของ `age` | ก่อน `gets(name)` | หลัง `gets(name)` |
| --- | --- | --- |
| ไบต์แรก | `0x0F` (15) | `0x31` คือตัวอักษร `'1'` |
| ไบต์ที่สอง | `0x00` | `0x00` คือ `\0` |
| ค่าของ `age` | 15 | `0x31` = **49** |

x86 เก็บไบต์ที่มีค่าน้อยที่สุดของจำนวนเต็มไว้ก่อน ไบต์แรกที่ถูกทับจึงเป็นไบต์ล่างสุดของ `age` พอดี

นี่คือนิยามของ buffer overflow

> **Definition 1:** The condition wherein the data transferred to a buffer exceeds the storage capacity of the buffer and some of the data "overflows" into another buffer, one that the data was not intended to go into.
>
> สภาพที่ข้อมูลซึ่งถูกส่งเข้า buffer มีมากกว่าที่ buffer จุได้ แล้วส่วนที่เกินล้นเข้าไปใน buffer อื่นที่ข้อมูลนั้นไม่ได้ตั้งใจจะไป

หน้านี้จะกลับมาใช้ตัวอย่างอายุอีกหลายครั้ง เพราะวิธีป้องกันบางแบบเปลี่ยนผลของมันได้

<Quiz question="ถ้าพิมพ์ชื่อยาวพอดี 8 ตัวอักษร เช่น Krerk.P0 ซึ่งเท่ากับขนาดของ name พอดี age จะออกมาเป็นเท่าไร">
`Krerk.P0` ยาว 8 ตัว แต่ `gets` ต่อท้ายด้วย `\0` อีกหนึ่งไบต์เสมอ ไบต์ที่ 9 จึงลงไปทับไบต์แรกของ `age` ซึ่งเก็บ `0x0F` อยู่ แล้วเปลี่ยนเป็น `0x00`

คำตอบคือ **0** รันจริงได้ `Krerk.P0 is 0 years old`

คำตอบที่ผิดบ่อยคือ "15 เพราะชื่อยาวไม่เกินที่จุ" ซึ่งลืมว่าสตริงใน C กินที่มากกว่าจำนวนตัวอักษรหนึ่งไบต์เสมอ การล้นเกินมาไบต์เดียวแบบนี้เจอบ่อยมากในโค้ดจริง
</Quiz>

### Control Data — ค่าที่ตัดสินว่าโปรแกรมจะไปไหนต่อ

ตัวอย่างอายุแค่เปลี่ยนตัวเลข แต่ถ้าค่าที่ถูกทับเป็นค่าที่โปรแกรมใช้ตัดสินว่าจะไปรันคำสั่งที่ไหนต่อ การล้นจะเปลี่ยนทางเดินของทั้งโปรแกรม

<Term en="Control Data" th="ค่าที่บอกว่าจะไปรันโค้ดตรงไหนต่อ" /> คือค่าในหน่วยความจำที่เก็บ address ของโค้ด โปรแกรมอ่านค่านี้แล้วกระโดดไปรันโค้ดที่อยู่ตรงนั้น

ค่าพวกนี้ส่วนใหญ่อยู่บน <Term en="Stack" th="หน่วยความจำที่ใช้ตอนเรียกฟังก์ชัน" /> ทุกครั้งที่เรียกฟังก์ชัน โปรแกรมจองพื้นที่บน stack หนึ่งก้อนไว้เก็บ argument, return address และตัวแปรภายในของฟังก์ชันนั้น

บน x86 ตัวแปรภายในอยู่ใต้ return address แต่ `gets` และ `strcpy` เขียนจาก address ต่ำขึ้นไปหา address สูง ข้อมูลที่ล้นออกจาก buffer จึงวิ่งเข้าหา return address พอดี

control data ที่เจอบ่อยมีสี่ชนิด

- **return address** — address ที่ฟังก์ชันจะกลับไปเมื่อทำงานเสร็จ ถูกเก็บบน stack ทุกครั้งที่เรียกฟังก์ชัน
- **function pointer** — ตัวแปรที่เก็บ address ของฟังก์ชัน
- **exception handler** — address ของโค้ดที่จะรันเมื่อเกิด error
- **virtual method** — ในภาษา OOP object เก็บ pointer ไปยังตาราง address ของ method

ทั้งสี่ชนิดอยู่ปนกับข้อมูลธรรมดาใน <Term en="Stack Frame" th="ก้อนบน stack ของการเรียกหนึ่งครั้ง" /> ตัวอย่างของ Michael Howard จาก Microsoft คือฟังก์ชันนี้

```c
void func(char *p, int i) {
    int j = 0;
    CFoo foo;
    int (*fp)(int) = &func;
    char b[128];
    strcpy(b,p);
}
```

นอกจาก return address แล้ว frame นี้ยังมี control data อีกสองตัว `fp` เก็บ address ของฟังก์ชัน ส่วน `foo` เป็น object ของคลาส `CFoo` ซึ่งเก็บ pointer ไปยังตาราง virtual method ไว้ในตัว

ถ้า `p` ชี้ไปที่ข้อมูลที่ยาวเกิน 128 ไบต์ `strcpy` จะเขียนเลย `b` ขึ้นไปทาง address สูง

การโจมตีจึงแบ่งตามช่องที่ถูกทับได้สามแบบ

- **Return-address attack** หรือ <Term en="Stack Smashing" th="ทับ return address บน stack" /> — ทับ return address พอฟังก์ชันจบ โปรแกรมกลับไปที่ address ใหม่ แทนที่จะกลับไปหาผู้เรียก
- **Function-pointer attack** — ทับ `fp` ครั้งต่อไปที่โปรแกรมเรียกผ่าน `fp` ก็ไปที่อื่น
- **Frame-pointer attack** — ทับ saved EBP

แบบที่สามต้องรู้จัก EBP ก่อน EBP คือ register ที่ x86 แบบ 32 บิตใช้เป็น <Term en="Frame Pointer" th="register ที่ชี้ stack frame ปัจจุบัน" /> ฟังก์ชันหาตัวแปรของตัวเองโดยนับระยะจาก EBP

ตอนเข้าฟังก์ชัน ค่า EBP ของผู้เรียกถูกเก็บไว้บน stack เรียกว่า saved EBP แล้วถูกโหลดคืนตอนกลับ ถ้า saved EBP ถูกทับ ผู้เรียกจะนับระยะจาก address ผิด ทุกค่าที่มันอ่านหลังจากนั้นจึงมาจากที่ที่ผู้โจมตีเลือก

### ทับ pointer ธรรมดา — ล้นสองขั้น

การโจมตีอีกแบบไม่ได้ทับ control data ตรง ๆ แต่ทับ **data pointer** ธรรมดาที่อยู่ติดกับ buffer

```c
int vulnerable(char **argv) {
    int x;
    char *ptr;
    char buffer[30];
    ptr=buffer;
    printf("ptr %p - before\n",ptr);
    strcpy(ptr,argv[1]);
    printf("ptr %p - after\n",ptr);
    strcpy(ptr,argv[2]);
    printf("done\n");
}
```

`strcpy` ครั้งแรกล้นจาก `buffer` ไปทับ `ptr` ซึ่งอยู่ติดกัน `printf` ก่อนและหลังบรรทัดนั้นพิมพ์ค่าของ `ptr` ออกมา ให้เห็นว่ามันถูกเปลี่ยนไปแล้ว

พอถึง `strcpy` ครั้งที่สอง โปรแกรมเขียนลงที่ที่ `ptr` ชี้ ซึ่งตอนนี้เป็นที่ที่ผู้โจมตีเลือก **pointer ตัวเดียวที่ทับได้จึงกลายเป็นการเขียนลงที่ไหนก็ได้ในหน่วยความจำ** เป้าหมายมักเป็น control data ที่อยู่ไกลออกไป

เป้าที่นิยมคือ <Term en="Global Offset Table (GOT)" th="ตาราง address ของฟังก์ชันในไลบรารี" /> โปรแกรมไม่รู้ล่วงหน้าว่า `printf` ในไลบรารีจะถูกโหลดไปอยู่ที่ไหน จึงเรียกผ่านตารางนี้ ช่องหนึ่งในตารางเรียกว่า **jump slot** ซึ่งก็คือ function pointer ตัวหนึ่ง

ถ้า jump slot ของ `printf` ถูกเปลี่ยน ทุกครั้งที่โปรแกรมเรียก `printf` หลังจากนั้นก็ไปที่อื่น worm **SLAPPER** ที่เจาะ Apache ใช้วิธีนี้

จำข้อนี้ไว้ใช้ในส่วนที่ 4: **การเขียนครั้งที่สองไม่ได้ล้นต่อเนื่องจาก buffer** มันข้ามทุกอย่างที่อยู่ระหว่าง buffer กับเป้าหมายไปเลย

### ช่องโหว่สองแบบที่ทำงานคล้ายกัน

- <Term en="Integer Overflow" th="ตัวเลขเกินขนาดจนวนกลับ" /> — นับเป็นส่วนย่อยของ buffer overflow ขนาดที่คำนวณได้เกินค่าสูงสุดของตัวแปรแล้ววนกลับเป็นค่าน้อย การตรวจความยาวจึงผ่าน แต่การคัดลอกจริงเขียนเกินที่จอง
- **ช่องโหว่ของ `printf`** — โปรแกรมส่งสตริงจากผู้ใช้เข้าไปเป็น format string ของ `printf` ตรง ๆ ผู้ใช้จึงสั่งให้ `printf` อ่านหรือเขียนหน่วยความจำได้ผ่าน format specifier

<Example added title="ขนาดที่วนกลับเป็นศูนย์">
โปรแกรมจองที่ `len + 1` ไบต์ไว้เผื่อ `\0` ถ้า `len` เป็น unsigned int 32 บิตที่มีค่าสูงสุด ผลบวกจะวนกลับเป็นศูนย์

```text
len=4294967295  len+1=0
```

โปรแกรมจึงจองที่ 0 ไบต์ แต่ยังคัดลอกตาม `len`
</Example>

### สองเงื่อนไขที่การโจมตีต้องมีครบ

การโจมตีด้วย buffer overflow ต้องได้ทั้งสองข้อ

1. **มีโค้ดหรือข้อมูลที่จะให้รัน** — ฉีดเข้าไปเองพร้อมกับข้อมูลที่ล้น หรือรู้ address ของโค้ดที่มีอยู่ในหน่วยความจำแล้ว
2. **พาโปรแกรมไปรันสิ่งนั้น** — เปลี่ยน control data ให้ชี้ไปหามัน

ข้อสองคือนิยามของการโจมตีที่คาบนี้สนใจ

> **Definition 2:** A buffer-overflow attack on control data is an attack that (possibly implicitly) uses memory-manipulating operations to overflow a buffer which results in the modification of an address to point to malicious or unexpected code.
>
> การโจมตี control data ด้วย buffer overflow คือการโจมตีที่ใช้คำสั่งจัดการหน่วยความจำ (อาจโดยอ้อม) ทำให้ buffer ล้น จน address ตัวหนึ่งถูกเปลี่ยนให้ชี้ไปหาโค้ดอันตรายหรือโค้ดที่ไม่ควรถูกรัน

ข้อสังเกตที่ใช้ต่อทั้งคาบคือ **buffer ที่ล้นเข้ามาเป็นของที่ส่งมาจาก domain อื่นเสมอ** และนั่นคือที่มาของเจตนาร้าย

<Term en="Domain" th="ขอบเขตของ process" /> ในที่นี้มองจาก process ที่กำลังทำงาน ของจาก domain อื่นคือของที่มาจากนอก process เช่นจากเครื่องอื่นหรือ process อื่น ผ่านเครือข่าย ไฟล์ หรือคีย์บอร์ด ของที่ process สร้างเองไม่มีเจตนาร้ายให้กลัว

<Quiz question="ถ้าคอมไพเลอร์วาง j ของฟังก์ชัน func ไว้ติดเหนือ b พอดี และ strcpy ล้นมาแค่ 4 ไบต์ ทับแค่ j ซึ่งเป็น int โปรแกรมถูกยึดได้ไหม">
`j` เป็นตัวเลขธรรมดา ไม่ใช่ address ของโค้ด โปรแกรมไม่ได้กระโดดตาม `j` ไปไหน

คำตอบคือ **ทางเดินของโปรแกรมไม่เปลี่ยน แต่ผลลัพธ์อาจผิด** เหมือนอายุที่กลายเป็น 49 ซึ่งเป็นปัญหาความถูกต้อง แต่ไม่เข้า Definition 2

คำตอบที่ผิดบ่อยคือ "ไม่มีผลอะไรเลย" ถ้า `j` เป็นค่าที่ใช้ตัดสินสิทธิ์ เช่นตัวแปร `is_admin` การเปลี่ยนมันอันตรายมาก แม้ไม่มี address ไหนถูกเปลี่ยน การโจมตีแบบนี้อยู่นอกขอบเขตของวิธีป้องกันส่วนใหญ่ในคาบนี้ รวมถึง Secure Bit ด้วย
</Quiz>

## ส่วนที่ 3 — แผนที่ของวิธีป้องกัน

### สามตระกูลใหญ่

วิธีป้องกัน buffer overflow แบ่งตามจังหวะที่มันเข้าไปขวางได้สามตระกูล

| ตระกูล | ทำงานเมื่อไร | แบบย่อย |
| --- | --- | --- |
| <Term en="Static Analysis" th="ตรวจโค้ดโดยไม่รัน" /> | ก่อนเอาโปรแกรมไปใช้ | Lexical Analysis, Semantic Analysis |
| <Term en="Dynamic Solution" th="ตรวจตอนโปรแกรมรัน" /> | ระหว่างโปรแกรมรัน | Address Protection, Input Protection, Bounds Checking, Obfuscation |
| <Term en="Isolation" th="จำกัดผลหลังถูกเจาะ" /> | หลังการโจมตีสำเร็จแล้ว | Non-executable, Sandboxing |

ตระกูลแรกพยายามไม่ให้มีช่องโหว่ ตระกูลที่สองจับการล้น หรือจับตอนโปรแกรมจะใช้ค่าที่ถูกทับ ตระกูลที่สามยอมว่าการโจมตีอาจสำเร็จ แต่จำกัดว่าโค้ดที่ได้มาทำอะไรได้บ้าง

### Static Analysis — จับก่อนใช้งาน แต่จับได้แค่ที่รู้จัก

Static analysis ตรวจโค้ดก่อนเอาไปใช้ ข้อจำกัดของมันมีสามข้อ

- **จับได้แค่ปัญหาที่รู้จักแล้ว** ช่องโหว่รูปแบบใหม่ที่ไม่อยู่ในกฎก็หลุดไปได้
- **ไม่มีข้อมูลตอนรัน** ไม่รู้ว่า input จริงยาวเท่าไร
- **เตือนผิดได้** (false alarm) โค้ดที่ปลอดภัยก็ถูกเตือน จนคนเลิกอ่านคำเตือน

เครื่องมือที่ใช้กันมีหลายระดับ

| เครื่องมือ | วิธี |
| --- | --- |
| ITS4 | string matching หาชื่อฟังก์ชันอันตราย (lexical) |
| FlawFinder, RATS | สแกนหาฟังก์ชันอันตรายแบบเดียวกัน |
| Splint, BOON | lint ที่เพิ่มการตรวจด้าน security และวิเคราะห์ความหมายของโค้ด (semantic) |
| STOBO | profiling tool จดขนาดของทุก buffer ระหว่างรันทดสอบ แล้วเตือนเมื่อปลายทางของ `strcpy` จุไม่พอ แม้ input ทดสอบไม่ได้ล้นจริง |
| LibSafe | ไลบรารี C มาตรฐานรุ่นปลอดภัยที่แทน `strcpy` ตอนรัน ไม่ได้ตรวจโค้ดก่อนใช้ (ส่วนที่ 4) |

<Example added title="lexical analysis ที่เจอกันทุกวัน">
compile ตัวอย่างอายุในส่วนที่ 2 ด้วย gcc 15.2 แล้ว linker เตือนจากชื่อฟังก์ชันอย่างเดียว

```text
age.c:(.text+0x2f): warning: the `gets' function is dangerous and should not be used.
```

`gets` ไม่รับขนาดของปลายทางเลย จึงไม่มีทางเรียกให้ปลอดภัย (มาตรฐาน C11 ตัด `gets` ออกไปแล้ว ตัวอย่างนี้ต้องประกาศ `gets` เองถึงจะ compile ผ่าน) แต่ `strcpy` ปลอดภัยได้ถ้าเช็กความยาวก่อน เครื่องมือที่ดูแค่ชื่อจึงต้องเลือกระหว่างเงียบกับเตือนผิด
</Example>

### สี่คำถามที่วิธีตรวจตอนรันทุกวิธีต้องตอบ

Dynamic solution ทุกแบบในสองส่วนถัดไปเก็บ <Term en="Metadata" th="ข้อมูลที่เก็บเพิ่มไว้ใช้ตรวจ" /> แล้วตรวจมันตอนรัน การเทียบวิธีพวกนี้จึงถามคำถามเดียวกันได้สี่ข้อ

1. **Assumptions** — มันสมมติอะไรเกี่ยวกับการโจมตี เช่นสมมติว่าการล้นเขียนต่อเนื่องจาก buffer
2. **Creation of metadata** — metadata ถูกสร้างตอนไหน และใครสร้าง
3. **Validation of metadata** — ตรวจตอนไหน และ metadata เองถูกปลอมได้ไหม
4. **Handling of invalid data** — เจอของผิดแล้วทำอะไร หยุดโปรแกรม หรือซ่อมคืน

<Quiz question="เครื่องมือ static analysis ตัวหนึ่งรายงานว่าโปรแกรมของเราไม่มีการเรียก gets, strcpy หรือ sprintf เลย สรุปได้ไหมว่าโปรแกรมไม่มี buffer overflow">
เครื่องมือแบบนี้ตรวจจากรายชื่อฟังก์ชันที่รู้ว่าอันตราย แต่การล้นเกิดจากลูปที่เขียนเองก็ได้ เช่น `for` ที่คัดลอกทีละไบต์แล้วนับเกินไปหนึ่งรอบ ซึ่งไม่มีชื่อฟังก์ชันอันตรายสักตัว

คำตอบคือ **สรุปไม่ได้** มันบอกได้แค่ว่าไม่มีรูปแบบที่อยู่ในรายการของมัน

คำตอบที่ผิดบ่อยคือ "สรุปได้ เพราะ buffer overflow เกิดจากฟังก์ชันพวกนี้" ซึ่งเอาสาเหตุที่พบบ่อยมาเป็นสาเหตุเดียว นี่คือข้อจำกัด "จับได้แค่ปัญหาที่รู้จักแล้ว" ข้างบน
</Quiz>

## ส่วนที่ 4 — ปกป้อง address ไม่ให้ถูกเปลี่ยนโดยไม่มีใครรู้

### สี่แบบของ Address Protection

<Why>
ถ้าโปรแกรมเขียนมาผิดแล้ว เราห้าม `strcpy` เขียนเกิน buffer ไม่ได้ แต่การล้นจะอันตรายจริงก็ตอนที่โปรแกรม **ใช้** address ที่ถูกทับ ถ้าจับได้ก่อนจังหวะนั้นว่า address ถูกเปลี่ยน โปรแกรมก็หยุดได้ทันก่อนกระโดดไปผิดที่
</Why>

<Term en="Address Protection" th="กัน address ไม่ให้ถูกแก้เงียบ ๆ" /> เก็บ metadata อีกชุดคู่กับ address ที่สำคัญ แล้วตรวจก่อนใช้ metadata มีสี่แบบ

บางแบบทำงานทีละ <Term en="Word" th="หน่วยที่ CPU อ่านหรือเขียนทีละครั้ง" /> เช่น 4 ไบต์บน x86 แบบ 32 บิต

| แบบ | metadata | ตัวอย่าง |
| --- | --- | --- |
| **Canary Words** | ค่าที่วางไว้หน้า return address | StackGuard, ProPolice |
| **Address Encode** | เข้ารหัสตัว address เอง | PointGuard |
| **Copy of Address** | สำเนาของ return address | StackGhost, <Term en="Return Address Stack (RAS)" th="stack ของ return address ใน CPU" />, Split Stack, RAD, DISE, StackShield, SCACHE, LibVerify |
| **Tags** | บิตหนึ่งบิตบนทุก word | IBM System/38 |

### Canary — StackGuard

<Term en="Canary" th="ค่าที่วางไว้จับการล้น" /> คือ word หนึ่งที่ compiler วางไว้ระหว่าง buffer กับ return address ตอนเข้าฟังก์ชัน แล้วตรวจว่ายังเป็นค่าเดิมก่อนฟังก์ชันกลับ

การล้นที่เขียนจาก buffer ขึ้นไปหา return address ต้องทับ canary ก่อนเสมอ ถ้าค่าเปลี่ยน โปรแกรมหยุดทันทีโดยไม่กระโดดไปตาม return address **StackGuard** ของ Oregon Graduate Institute (Immunix) ทำแบบนี้

<Analogy>
ชื่อมาจากนกคีรีบูนที่คนงานเหมืองถ่านหินหิ้วลงไปด้วย นกตายก่อนคนเมื่อมีแก๊สพิษ นกคือ canary แก๊สที่ลอยมาถึงคือข้อมูลที่ล้นขึ้นมา และคนงานที่เห็นนกตายแล้วรีบออกจากเหมืองคือโปรแกรมที่หยุดทำงาน

อุปมานี้ใช้ไม่ได้ตรงที่แก๊สฆ่านกได้จากทุกทิศ แต่ canary จับได้เฉพาะการเขียนที่ไล่ทับต่อเนื่องจาก buffer ขึ้นมา การเขียนผ่าน pointer ที่ข้าม canary ไปลง return address ตรง ๆ จะไม่แตะ canary เลย
</Analogy>

ค่าของ canary มีหลายแบบ

- **Random canary** — สุ่มตอนโปรแกรมเริ่ม ผู้โจมตีที่ไม่รู้ค่าก็เขียนค่าเดิมกลับลงไปไม่ได้
- **Terminator canary** — มีไบต์อย่าง `0x00` อยู่ในค่า การล้นจะรอดได้ก็ต่อเมื่อเขียน canary กลับเป็นค่าเดิมทุกไบต์ รวมทั้ง `0x00` แต่ `strcpy` หยุดคัดลอกทันทีที่เขียน `0x00` การล้นด้วย `strcpy` จึงไปไม่ถึง return address ที่อยู่เหนือ canary แบบที่เป็นศูนย์ทั้ง word เรียกว่า null canary

รายการของ StackGuard ยังมีอีกสองข้อที่ไม่ได้อธิบายไว้ คือ **terminator with diversity canary** และคำถาม **Alignment?**

**MemGuard** ของทีม StackGuard อยู่ในตระกูลเดียวกันแต่ไม่ใช้ canary มันใช้กลไก virtual memory ทำให้ return address เป็นแบบอ่านอย่างเดียวระหว่างที่ฟังก์ชันทำงาน การเขียนทับจึงถูก CPU จับได้ทันที

ราคาของ MemGuard คือความช้า สิทธิ์อ่านอย่างเดียวคุมได้ทีละ page การเขียนลง word อื่นใน page เดียวกัน ซึ่งบน stack เกิดตลอดเวลา จึงถูกจับด้วย แล้วต้องให้ซอฟต์แวร์เขียนแทนทีละครั้ง

<Example added title="ล้น 48 ไบต์ใส่ buffer 16 ไบต์ ทั้งแบบมีและไม่มี canary">
`smash.c` คือฟังก์ชันแบบ `func` ในส่วนที่ 2 ที่เหลือแค่ `strcpy` ลง `char b[16]` แล้วรับข้อความ 48 ตัวอักษรเท่ากันในการ compile สองแบบ

```text
$ gcc -fno-stack-protector -o smash smash.c && ./smash $(python3 -c 'print("A"*48)')
copied 48 bytes
Segmentation fault         (core dumped)
$ gcc -fstack-protector -o smash smash.c && ./smash $(python3 -c 'print("A"*48)')
copied 48 bytes
*** stack smashing detected ***: terminated
Aborted                    (core dumped)
```

แบบไม่มี canary กระโดดไปตาม return address ที่ถูกทับแล้วค่อยพัง ถ้า address นั้นชี้ไปที่โค้ดที่รันได้ มันจะไม่พังเลย แต่ไปรันโค้ดนั้นแทน ส่วนแบบมี canary หยุดเองก่อนจะกระโดด

</Example>

### ProPolice — ย้ายตัวแปรอันตรายออกจากทางล้น

<Why>
canary ถูกตรวจแค่ตอนฟังก์ชันกำลังจะกลับ ใน `func` ของรูปที่ 1 function pointer `fp` อยู่เหนือ `b` แต่ต่ำกว่า canary ที่วางไว้ใต้ return address การล้นจึงทับ `fp` ได้ และถ้าฟังก์ชันเรียกผ่าน `fp` ก่อนจบ โปรแกรมก็กระโดดไปที่อื่นก่อนที่ canary จะถูกตรวจ
</Why>

**ProPolice** ของ IBM Research ญี่ปุ่น ใช้ canary แบบเดียวกับ StackGuard ซึ่งมันเรียกว่า **guard** แล้วทำเพิ่มอีกอย่าง คือ **จัดลำดับตัวแปรใหม่** ให้ stack frame เรียงจาก address สูงลงต่ำแบบนี้

| ช่อง | ทำไมอยู่ตรงนี้ |
| --- | --- |
| arguments (A) | ผู้เรียกวางไว้ |
| return address | ต้องปกป้อง |
| previous frame pointer | ต้องปกป้อง |
| **guard** | การล้นจาก array ต้องผ่านตรงนี้ก่อน |
| arrays (B) | buffer ทุกตัวรวมกันอยู่ติด guard |
| local variables (C) | pointer และตัวแปรธรรมดา อยู่ใต้ buffer ทุกตัว |

การล้นเขียนจาก buffer ไปทาง address สูง ตัวแปรในกลุ่ม C จึงอยู่นอกทางล้นทั้งหมด ถ้าโปรแกรมเมอร์ประกาศ function pointer ไว้ก่อน buffer แบบนี้

```c
int bar() {
    void (* funct2)();
    char buff[80];
}
```

ProPolice จะจัดใหม่ให้เหมือนเขียนว่า

```c
int bar() {
    char buff[80];
    void (* funct2)();
}
```

คือย้าย `funct2` ไปไว้ใต้ `buff` ในหน่วยความจำ `buff` ล้นเท่าไรก็ไม่ถึง `funct2`

ที่ ProPolice ทำไม่ได้คือ **pointer ที่อยู่ใน struct** ภาษา C กำหนดลำดับของ field ใน struct ไว้ตายตัวตามที่ประกาศ ถ้า struct มี buffer ตามด้วย function pointer compiler ก็สลับให้ไม่ได้

ลองทายก่อน: compile `age.c` ตัวเดิมด้วย `gcc` เฉย ๆ แล้วพิมพ์ `15` กับ `Krerk.P01` เหมือนเดิม โปรแกรมจะบอกว่าอายุเท่าไร

<Example added title="ตัวอย่างอายุตัวเดิม เมื่อเปิด stack protector">
```text
$ gcc -o age age.c && ./age
Enter your age:15
Enter your name:Krerk.P01
-----------
Krerk.P01 is 15 years old
```

gcc บน Ubuntu เปิด `-fstack-protector-strong` ไว้เป็นค่าเริ่มต้น ซึ่งคือ ProPolice รุ่นที่อยู่ใน gcc `objdump -d` บอกว่ามันจัดตัวแปรใหม่แบบนี้ โดยวัดระยะจาก `rbp` ซึ่งคือ frame pointer ของ x86-64 ตัวเดียวกับ EBP

| ตัวแปร | `-fno-stack-protector` | ค่าเริ่มต้น (`-fstack-protector-strong`) |
| --- | --- | --- |
| `age` | `rbp-0x4` อยู่เหนือ `name` | `rbp-0x2c` ย้ายลงไปอยู่ใต้ `name` |
| `name` | `rbp-0xc` | `rbp-0x28` |
| `tmp` | `rbp-0x20` | `rbp-0x20` |
| canary | ไม่มี | `rbp-0x8` |

ชื่อยังล้นสองไบต์เท่าเดิม แต่สองไบต์นั้นไปลงที่ `tmp[0]` และ `tmp[1]` ซึ่งโปรแกรมใช้เสร็จไปแล้ว และไม่ถึง canary โปรแกรมจึงไม่หยุด
</Example>

### PointGuard — เข้ารหัส pointer

**PointGuard** ของ Oregon Graduate Institute (Immunix) **เข้ารหัส pointer ด้วย key ที่กำหนดไว้ก่อนทุกครั้งที่เก็บลงหน่วยความจำ และถอดรหัสทุกครั้งที่จะใช้** ค่าที่อยู่ในหน่วยความจำจึงไม่ใช่ address จริง

ถ้าผู้โจมตีล้นทับ pointer ด้วย address ที่ต้องการ ค่านั้นยังไม่ได้ถูกเข้ารหัส พอโปรแกรมดึงมาใช้ มันถูกถอดรหัสก่อน จึงกลายเป็น address สุ่ม ๆ ที่ไม่ใช่ทั้งของเดิมและของผู้โจมตี โปรแกรมจึงอ่านข้อมูลมั่วหรือพัง แทนที่จะไปถึงที่ที่ผู้โจมตีเลือก

<Example added title="เข้ารหัสด้วย XOR">
PointGuard เข้ารหัสด้วยการ XOR กับ key ลับ โปรแกรม C เล็ก ๆ ที่ใช้ key `0x5f3c9a21` ให้ผลแบบนี้

| ค่าที่ลงไปในหน่วยความจำ | ค่าที่เก็บอยู่ | ถอดออกมาได้ |
| --- | --- | --- |
| pointer จริง `0x0804a010` ผ่านการเข้ารหัส | `0x57383a31` | `0x0804a010` ตรงเดิม |
| ค่าที่ถูกเขียนทับลงไปตรง ๆ | `0x41414141` | `0x1e7ddb60` ไม่ใช่ทั้งของเดิมและของผู้เขียน |
</Example>

คำถามที่ PointGuard ต้องตอบมีสี่ข้อ

- **Compatibility** — โค้ดที่ไม่ได้ compile ด้วย PointGuard เช่นไลบรารีเก่า อ่าน pointer แบบไม่ถอดรหัส
- **Initialization** — key ถูกสร้างตอนไหน และ pointer ที่มีอยู่ก่อน key จะถูกเข้ารหัสยังไง
- **Performance** — ต้องถอดรหัสทุกครั้งที่ใช้ pointer
- **Encryption Algorithm** — ต้องเร็วพอจะทำทุกครั้งที่แตะ pointer แต่แข็งพอที่ผู้โจมตีจะเดา key ไม่ได้

### Copy of Address — เก็บ return address ไว้อีกที่

ถ้า return address มีสำเนาอยู่ในที่ที่การล้นเอื้อมไม่ถึง ตอนฟังก์ชันกลับก็เทียบสองค่ากันได้ หรือใช้สำเนาแทนไปเลย ระบบในกลุ่มนี้ต่างกันที่ว่าสำเนาอยู่ที่ไหน

- **Split Stack** (UIUC) — แยก stack เป็นสองอัน **control stack** เก็บ return address อย่างเดียว ส่วน **data stack** เก็บ parameter, frame pointer และตัวแปร
  - แบบที่ compiler ทำ (compiler-based split stack) data stack ยังมี return address อยู่ และ control stack เป็นสำเนา
  - แบบที่ฮาร์ดแวร์ช่วย (architecture-supported split stack) return address ออกจาก data stack ไปเลย buffer ล้นเท่าไรก็ไม่เจอ return address
- **StackGhost** (Purdue) — ใช้ register window ของ CPU SPARC ซึ่งถือ return address ไว้ใน register ก่อนจะย้ายลง stack จึงมีจังหวะให้ตรวจหรือเก็บสำเนาไว้
- **SRAS** (UIUC) — ใช้ RAS ซึ่งเป็นวงจรที่ CPU มีอยู่แล้วไว้ทายว่า return จะกลับไปที่ไหน มาเป็นสำเนาไว้ตรวจ ปัญหาคือ RAS มีขนาดจำกัดจึงเต็มได้ (overflow) ถูกอัปเดตตอน CPU ทำงานล่วงหน้าแบบ speculative และรับมือกับ <Term en="Non-LIFO Control Flow" th="call กับ return ไม่จับคู่ตามลำดับ" /> ไม่ได้ ส่วนที่ 7 มีตัวอย่างโค้ดแบบนี้
- **RAD** (State U. of New York at Stony Brook) — เก็บสำเนาไว้ใน **Return Address Repository (RAR)** แบบ MineZone RAR ล้อม RAR ด้วย page ที่ห้ามแตะ ส่วนแบบ Read-only RAR ใช้ `mprotect` ทำให้ RAR อ่านได้อย่างเดียว คำถามที่ค้างคือ performance
- **StackShield** (Vendicator) — เก็บสำเนาของ return address ไว้ ตอนกลับจะคัดลอกสำเนาทับของเดิม หรือเทียบกับสำเนาก็ได้ และบังคับให้การเรียกผ่าน function pointer ไปได้แค่ส่วนโค้ด (text section) ข้อนี้ขัดกับโปรแกรมที่สร้างโค้ดใน <Term en="Heap" th="หน่วยความจำที่จองตอนรัน" /> เช่นด้วย `malloc` แล้วรันโค้ดนั้นอย่างถูกต้อง เช่น LISP และภาษา OOP บางระบบ
- **LibSafe และ LibVerify** (Bell Labs) — สองตัวนี้มาด้วยกันแต่ทำงานคนละแบบ LibSafe ไม่ได้เก็บสำเนา address แต่แทน `strcpy` และฟังก์ชันพวกเดียวกันด้วยรุ่นที่คำนวณก่อนว่าปลายทางยาวได้แค่ไหน โดยใช้ frame pointer เป็นขอบบน การล้นจึงไปได้ไม่เกิน stack frame ของตัวเอง ส่วน LibVerify ซึ่งเป็นตัวที่อยู่ในกลุ่ม copy of address แก้ binary ของโปรแกรมให้ทุกฟังก์ชันเข้าผ่านโค้ดห่อ ขาเข้าเก็บ return address ขาออกตรวจก่อนกลับ
- **DISE** (Dynamic Instruction Stream Editing) — ฮาร์ดแวร์ที่แก้สายคำสั่งของโปรแกรมระหว่าง decode จึงแทรกคำสั่งที่เก็บและตรวจ return address ได้
- **SCACHE** — cache ที่เก็บสำเนาแบบอ่านอย่างเดียวของ return address ไว้ในตัว แล้วเทียบกับค่าที่ดึงจาก stack ตอนกลับ

### Tags — ติดป้ายที่ตัว word

แบบสุดท้ายติดบิตหนึ่งบิตให้ทุก word ในหน่วยความจำ บอกว่า word นั้นเป็น return address หรือ function pointer CPU จึงรู้ว่า word ไหนห้ามถูกทับด้วยข้อมูลธรรมดา IBM System/38 ทำแบบนี้ในฮาร์ดแวร์ แนวคิดเดียวกับ [tagged memory ใน Lecture 6](/2110413-csy/lecture-6#tagged-memory)

Tags ใกล้กับ Secure Bit ในส่วนที่ 9 ที่สุด ต่างกันตรงที่ tag บอกว่า word ไหน **เป็น** address ส่วน Secure Bit บอกว่า word ไหน **มาจากข้างนอก**

<Quiz question="โปรแกรมหนึ่ง compile ด้วย StackGuard และ ProPolice ฟังก์ชันหนึ่งมีตัวแปร struct ที่ประกาศ field char name[16] ตามด้วย function pointer on_done แล้วคัดลอก input ลง name ด้วย strcpy จากนั้นเรียก on_done ก่อนฟังก์ชันจบ ถ้า input ยาวเกิน 16 ไบต์ วิธีไหนจับได้">
ProPolice ย้ายตัวแปรทั้งตัวได้ แต่สลับ field ใน struct ไม่ได้ `on_done` จึงยังอยู่เหนือ `name` ในทางล้น ส่วน canary อยู่เหนือ struct ทั้งก้อนและถูกตรวจตอนฟังก์ชันกลับ แต่โปรแกรมกระโดดผ่าน `on_done` ที่ถูกทับไปก่อนจังหวะนั้น

คำตอบคือ **ไม่มีวิธีไหนจับได้** โปรแกรมไปที่ที่ค่าใหม่ของ `on_done` ชี้ ก่อนที่ canary จะถูกตรวจ

คำตอบที่ผิดบ่อยคือ "canary จับได้ เพราะการล้นเขียนต่อเนื่องจาก buffer" การล้นต่อเนื่องจริง และถ้ายาวพอก็จะทับ canary ด้วย แต่การตรวจเกิดตอนกลับ ซึ่งช้าไปแล้ว
</Quiz>

## ส่วนที่ 5 — ติดป้าย input ตรวจขอบเขต และสุ่ม address

### Input Protection — ห้ามใช้ input เป็น control data

<Why>
ข้อสังเกตในส่วนที่ 2 บอกว่าของที่ล้นเข้ามามาจาก domain อื่นเสมอ ถ้า CPU จำได้ว่าค่าไหนมาจากข้างนอก มันไม่ต้องสนใจเลยว่าค่านั้นไปลงที่ไหน แค่ไม่ยอมใช้ค่านั้นเป็น address ที่จะกระโดดไปหา
</Why>

<Term en="Input Protection" th="ห้ามใช้ input เป็น control data" /> มีกฎข้อเดียวคือ **input ห้ามถูกใช้เป็น control data**

ข้อมูลที่เข้ามาจาก domain ที่ไม่น่าไว้ใจถูกติดป้าย เรียกว่า <Term en="Taint" th="ติดป้ายว่าไม่น่าไว้ใจ" /> ป้ายนี้ติดไปกับค่าทุกครั้งที่ถูกคัดลอกหรือคำนวณต่อ ระบบในกลุ่มนี้ต่างกันสองจุด คือติดป้ายที่ขอบเขตไหน และล้างป้าย (untaint) เมื่อไร

| ระบบ | ติดป้ายตรงไหน (Boundary) | ล้างป้ายเมื่อไร (Untaint) |
| --- | --- | --- |
| **Minos** | ใช้ segmentation แยก | ตอนสร้างข้อมูล (creation time) |
| **Tainted pointer** | ฟังก์ชัน I/O ของ SimpleScalar ซึ่งเป็นโปรแกรมจำลอง CPU แบบ RISC | เมื่อค่าผ่านคำสั่ง `CMP` หรือ `XOR` |
| **Dynamic Flow Tracking** | ฟังก์ชัน I/O ของ SimpleScalar | เมื่อค่าผ่านคำสั่ง `XOR` |

การล้างป้ายมีไว้ให้โปรแกรมที่ตรวจ input แล้วใช้มันต่อได้ `CMP` คือการเทียบค่า ระบบจึงถือว่าค่าที่ถูกเทียบแล้วผ่านการตรวจมาแล้ว ส่วน `XOR` ของ register กับตัวเองให้ศูนย์เสมอ ผลจึงไม่ขึ้นกับ input เลย

ราคาของกฎแบบนี้คือการล้างป้ายผิดที่ ค่าที่ถูกเทียบแล้วไม่ได้แปลว่าปลอดภัยเสมอไป

### Bounds Checking — ทุกการเข้าถึงต้องรู้ขอบ

<Term en="Bounds Checking" th="ตรวจว่าเขียนไม่เกินขอบ buffer" /> แก้ปัญหาตรงที่สุด คือตรวจทุกครั้งที่เขียนว่ายังอยู่ใน buffer หรือเปล่า

ทุก buffer ต้องถูกประกาศพร้อมฐาน (base) และขอบ (boundary) ซึ่งเก็บไว้ใน symbol table หรือใน **segment descriptor table** ของ CPU อีกแบบคือ **enhanced pointer** ที่ pointer หนึ่งตัวเก็บสามค่า คือ base, ค่าของ pointer และ limit ของ storage object ที่มันชี้

CPU ที่ทำแบบนี้ในฮาร์ดแวร์คือ Intel IA-32 ผ่าน segmentation และ Intel iAPX 432 (I-432) ซึ่งต้องประกาศขอบเขตให้ **ทุกตัวแปร** รวมทั้ง int และ float เพราะ pointer เขียนลงตัวแปรตัวไหนก็ได้ ถ้าตัวแปรไหนไม่มีขอบเขตกำกับ การเขียนที่เลยเข้าไปในตัวนั้นก็ตรวจไม่ได้

```c
char *a;
char b[10];
a = b;
for (a=b; a<&b[10]; a++)
    *a='0';
b[11]=10;
```

pointer `a` รับ base และ limit ของ `b` มาด้วย ลูปเขียนได้ครบสิบช่องเพราะอยู่ในขอบ แต่ `b[11]=10;` อยู่นอกขอบจึงถูกจับตอนรัน

บรรทัดที่สามในสไลด์เขียนว่า `*a = &b;` ซึ่ง compile ไม่ผ่าน gcc 15.2 ตอบว่า `error: assignment to 'char' from 'char (*)[10]' makes integer from pointer without a cast` โค้ดข้างบนจึงใช้ `a = b;` ซึ่งตรงกับเจตนาของตัวอย่าง

ราคาของการตรวจแบบนี้คือ **ช้าลงมากกว่า 30 เท่า**

### Obfuscation — ทำให้เดา address ไม่ได้

ผู้โจมตีต้องรู้ address ของสิ่งที่จะให้โปรแกรมกระโดดไปหา <Term en="Address Obfuscation" th="ทำให้เดา address ไม่ได้" /> ของ Stony Brook จึงทำให้ address เปลี่ยนไปทุกครั้งที่รัน ด้วยสามวิธี

- สุ่ม base address ของแต่ละ segment ของหน่วยความจำ คือ stack, heap, BSS (ตัวแปร global ที่ไม่ได้ให้ค่าเริ่มต้น), data (ตัวแปร global ที่มีค่าเริ่มต้น) และ text (โค้ด อ่านได้อย่างเดียว)
- สลับลำดับของตัวแปร ฟังก์ชัน และ structure
- เว้นช่องว่างขนาดสุ่มระหว่าง object เช่นระหว่าง buffer กับ return address ผู้โจมตีจึงไม่รู้ว่าต้องล้นกี่ไบต์ถึงจะถึง

ปัญหาของมันคือหน่วยความจำแตกเป็นชิ้น (fragmentation) และโปรแกรมที่ฝัง address ตายตัวไว้ทำงานไม่ได้ (compatibility)

วิธีที่คล้ายกันและใช้กันแพร่หลายคือ <Term en="Address Space Layout Randomization (ASLR)" th="สุ่มตำแหน่งในหน่วยความจำ" /> ของ PaX ซึ่งเป็นชุด patch ของ Linux kernel ที่เพิ่มการป้องกันหน่วยความจำ รวมทั้ง ASLR และการห้ามรันโค้ดในหน่วยความจำส่วนข้อมูล

### ทำให้ฉีดโค้ดไม่ได้ — ISR และ SPEF

อีกสองวิธีไม่ได้ซ่อน address แต่ทำให้โค้ดที่ผู้โจมตีฉีดเข้ามารันไม่ได้

<Term en="Instruction-Set Randomization (ISR)" th="สุ่มรหัสคำสั่งแยกต่อ process" /> ของ Columbia U. และ Drexel U. XOR ทุกคำสั่งของโปรแกรมด้วย key ประจำ process แล้ว CPU XOR กลับก่อนรัน โค้ดที่ฉีดเข้ามาไม่ได้ถูก XOR ไว้ล่วงหน้า พอถูก XOR กลับจึงกลายเป็นคำสั่งมั่ว ๆ

ISR มีคำถามค้างสองข้อ ไลบรารีที่หลาย process ใช้ร่วมกันจะใช้ key ของใคร (Library?) และการโจมตีที่ไม่ได้ฉีดโค้ดแต่เปลี่ยนข้อมูลจะถูกจับได้ยังไง (Data?)

**SPEF** หรือ Secure Program Execution Framework ของ Microsoft และ UCLA ใช้การเข้ารหัสตอนติดตั้งโปรแกรม แล้วถอดรหัสและเรียงคำสั่งคืนใน instruction cache (I-CACHE) ตอนรัน โค้ดที่ไม่ได้ผ่านการติดตั้งจึงรันไม่ได้ คำถามที่ค้างคือ performance และข้อมูลที่ไม่ใช่โค้ด

<Pitfall>
ความเชื่อที่ผิดคือ **ถ้าทำให้ผู้โจมตีฉีดโค้ดเข้ามาไม่ได้ ก็โจมตีด้วย buffer overflow ไม่ได้แล้ว**

ข้อนี้ไม่จริง

มันดูจริงเพราะภาพจำของการโจมตีคือการส่งโค้ดอันตรายเข้าไปพร้อมกับข้อมูลที่ล้น และ ISR กับ SPEF ก็ปิดทางนั้นได้จริง

ที่ถูกคือ **เงื่อนไขข้อแรกในส่วนที่ 2 มีสองทาง** คือฉีดโค้ดเข้าไปเอง หรือรู้ address ของโค้ดที่มีอยู่ในหน่วยความจำแล้ว ไลบรารีมาตรฐานที่ทุกโปรแกรมโหลดมีฟังก์ชันที่ทำได้แทบทุกอย่างอยู่แล้ว ผู้โจมตีแค่เปลี่ยน return address ให้ชี้ไปหาฟังก์ชันพวกนั้น จึงไม่มีคำสั่งไหนของผู้โจมตีให้ ISR หรือ SPEF จับ
</Pitfall>

<Quiz question="เครื่องหนึ่งเปิด ASLR ไว้ และใช้ ISR ด้วย ผู้โจมตีส่งข้อมูลเข้าไปให้ล้นตัวแปร is_admin ที่อยู่ติดกับ buffer ทั้งสองวิธีช่วยได้ไหม">
ASLR ซ่อน address ซึ่งมีผลเมื่อผู้โจมตีต้องเขียน address ลงไป ISR ทำให้โค้ดที่ฉีดเข้ามารันไม่ได้ แต่การทับ `is_admin` ไม่ต้องรู้ address ของอะไรเลย เพราะตัวแปรอยู่ติดกับ buffer เสมอไม่ว่า stack จะย้ายไปไหน และไม่ได้ฉีดโค้ดสักบรรทัด

คำตอบคือ **ไม่ช่วยทั้งคู่** เหมือนที่ตัวอย่างอายุในส่วนที่ 2 ยังได้ 49 เมื่อ compile โดยปิด stack protector ไม่ว่าจะสุ่ม address หรือไม่

คำตอบที่ผิดบ่อยคือ "ASLR ช่วยได้ เพราะผู้โจมตีไม่รู้ว่าตัวแปรอยู่ที่ไหน" ซึ่งลืมว่า ASLR ย้ายทั้ง stack ไปพร้อมกัน ระยะห่างระหว่างตัวแปรใน frame เดียวกันไม่เปลี่ยน วิธีที่ช่วยในเคสนี้คือการจัดลำดับใหม่ของ ProPolice ซึ่งย้าย `is_admin` ไปไว้ใต้ buffer
</Quiz>

## ส่วนที่ 6 — Isolation: ยอมให้ล้น แต่จำกัดผล

<Why>
สมมติว่าทุกการตรวจในส่วนที่ 4 และ 5 พลาดหมด return address ถูกทับโดยไม่มีใครจับได้ และโปรแกรมกำลังรันโค้ดที่ผู้โจมตีเลือก สิ่งที่ยังทำได้คือขีดเส้นว่าโค้ดนั้นแตะอะไรได้บ้าง
</Why>

Isolation ไม่พยายามจับการล้นเลย แต่จำกัดว่าโค้ดที่ได้จากการโจมตีทำอะไรได้ มีสามแบบ

- **จำกัดการรันโค้ด** — <Term en="Non-Executable Memory (NX)" th="หน่วยความจำที่ห้ามรันเป็นโค้ด" /> ห้ามรันคำสั่งจาก stack หรือหน่วยความจำส่วนข้อมูล ทำได้ทั้งในซอฟต์แวร์และฮาร์ดแวร์ และมีแบบที่ป้องกัน kernel ด้วย (kernel NX)
- **กัก process ทั้งตัวใน sandbox** — ห้าม process แตะทรัพยากรบางอย่างของระบบตาม policy ที่ตั้งไว้ก่อน ตัวอย่างคือ TCPA (Trusted Computing Platform Alliance) กลุ่มบริษัทที่วางมาตรฐานฮาร์ดแวร์ trusted computing เช่นชิป TPM หลักเดียวกับ [sandbox ใน Lecture 6](/2110413-csy/lecture-6#sandbox)
- **ติดตั้งโค้ดและสภาพแวดล้อมตอนรันอย่างปลอดภัย** — SPEF ในส่วนที่ 5

NX มีคำถามสามข้อที่มันตอบไม่ได้

- **Heap-based attack** — NX ไม่ได้กันการล้นเลย มันกันแค่การรันคำสั่งจาก page ที่ห้ามรัน NX แบบที่ห้ามแค่ stack จึงยังปล่อยให้โค้ดที่ถูกฉีดไว้ใน heap รันได้
- **โปรแกรมที่ต้องรันโค้ดบน stack จริง ๆ** — โปรแกรมบางแบบสร้างโค้ดบน stack หรือ heap แล้วรันอย่างถูกต้อง NX ทำให้โปรแกรมพวกนี้พัง
- **การโจมตีที่ไม่ได้ฉีดโค้ด** — แบบเดียวกับใน pitfall ของส่วนที่ 5 NX ไม่มีอะไรให้จับ

### LaGrande และ NGSCB — แยก domain ด้วยฮาร์ดแวร์

LaGrande ของ Intel และ NGSCB ของ Microsoft คือแพลตฟอร์มที่ฮาร์ดแวร์ช่วยทำ sandbox โดยแยก domain ออกจากกัน (domain separation)

LaGrande แบ่งเป็นชั้นแบบนี้

- **Standard partition** — รันแอปบน OS ตามปกติ
- **Protected partition** — รัน applet ซึ่งเป็นโปรแกรมเล็กที่ทำงานเฉพาะอย่าง บน kernel ของตัวเองใน protected memory และยังขอใช้ทรัพยากรฝั่ง Standard ได้
- **Domain Manager** — อยู่ใต้ทั้งสองฝั่ง และแยกสองฝั่งออกจากกัน
- **ฮาร์ดแวร์** — CPU และ chipset ที่รองรับ LT (LaGrande Technology), protected I/O และ TPM (Trusted Platform Module ชิปที่เก็บ key และบันทึกค่าที่วัดได้จากซอฟต์แวร์ที่บูตขึ้นมา) ช่วยกันกันการเข้าถึงทรัพยากรและทำ attestation

NGSCB มีสี่ความสามารถ

- **Strong process isolation** — process หนึ่งแตะหน่วยความจำของอีก process ไม่ได้
- **Sealed storage** — ข้อมูลที่เก็บไว้ผูกกับโปรแกรมที่เก็บ โปรแกรมอื่นเปิดไม่ได้
- **Secure user interface** — ทางเชื่อมระหว่างผู้ใช้กับโปรแกรมที่โปรแกรมอื่นดักไม่ได้
- **Attestation** — พิสูจน์ให้เครื่องอื่นเห็นว่ากำลังรันซอฟต์แวร์อะไรอยู่

Secure Bit วางตัวเป็นส่วนเสริมของสองระบบนี้ ไม่ใช่ของแทน คำถามที่ตามมาคือ **trusted เท่ากับ secure หรือเปล่า**

คำตอบคือไม่เท่ากัน process ที่ถูกแยกไว้อย่างดีและพิสูจน์ได้ว่าเป็นโปรแกรมที่ถูกต้อง ยังมี buffer overflow อยู่ข้างในได้ การแยก domain กันไม่ให้ความเสียหายลามออกไป แต่ไม่ได้กันการถูกยึดภายใน domain นั้นเอง

<Quiz question="เว็บเซิร์ฟเวอร์ตัวหนึ่งรันใน sandbox ที่ห้ามแตะไฟล์ทุกไฟล์นอกโฟลเดอร์ของเว็บ แล้วถูกยึดด้วย buffer overflow ผู้โจมตีทำอะไรได้บ้าง">
sandbox จำกัดตาม policy ของ process ไม่ได้ดูว่าใครเป็นคนสั่ง โค้ดที่ผู้โจมตีพาโปรแกรมไปรันจึงได้สิทธิ์เท่ากับเว็บเซิร์ฟเวอร์ทุกประการ

คำตอบคือ **ทำได้ทุกอย่างที่เว็บเซิร์ฟเวอร์ทำได้** อ่านและแก้ไฟล์ในโฟลเดอร์เว็บ ส่งข้อมูลออกทางเครือข่าย และเห็นข้อมูลของผู้ใช้ทุกคนที่เชื่อมต่อเข้ามา แต่แตะไฟล์ระบบนอกโฟลเดอร์นั้นไม่ได้

คำตอบที่ผิดบ่อยคือ "ทำอะไรไม่ได้ เพราะอยู่ใน sandbox" ซึ่งลืมว่า isolation ยอมให้การโจมตีสำเร็จตั้งแต่แรก มันแค่ขีดเส้นว่าความเสียหายไปได้ไกลแค่ไหน
</Quiz>

## ส่วนที่ 7 — ทำไมยังไม่มีวิธีไหนปิดเรื่องนี้ได้

### สี่จุดที่วิธีป้องกันพลาด

วิธีป้องกันในสามส่วนที่ผ่านมาพลาดได้สี่ทาง

- **Pitfalls** — ช่องโหว่ในตัววิธีเอง มีสองแบบ
  - **ข้อสมมติไม่พอ (insufficient assumptions)** — canary สมมติว่าการล้นเขียนต่อเนื่องจาก buffer แต่ worm SLAPPER เขียนผ่าน pointer ซึ่งไม่ได้ล้นต่อเนื่องไปหาเป้าหมาย canary จึงยังเป็นค่าเดิมทุกไบต์
  - **ปกป้อง metadata ไม่พอ (insufficient protection of metadata)** — ถ้าผู้โจมตีอ่านหรือเขียนทับ canary หรือสำเนาของ address ได้ การตรวจก็ไม่มีความหมาย
- **Performance** — bounds checking ช้าลงกว่า 30 เท่า
- **Compatibility และ transparency** — ต้องใช้กับโปรแกรมเดิมได้โดยไม่ต้องแก้ รวมถึงโปรแกรมที่ไหลแบบ non-LIFO ในหัวข้อโปรแกรมที่ไม่ได้กลับตามลำดับข้างล่าง
- **Deployment และ cost** — ต้อง compile ใหม่ ติดตั้งไลบรารีใหม่ หรือเปลี่ยนฮาร์ดแวร์แค่ไหน

SLAPPER หลุดวิธีกลุ่ม copy of address ด้วย วิธีอย่าง split stack จับการเขียนผ่าน pointer ได้เฉพาะเมื่อเป้าหมายคือ return address แต่ SLAPPER เขียนลง jump slot ใน GOT

### metadata ต้องใช้ที่เท่าไร

ทุกวิธีใน dynamic solution ต้องเก็บ metadata เพิ่ม และขนาดของมันต่างกันมาก

| วิธี | metadata | จ่ายเมื่อไร |
| --- | --- | --- |
| Segmentation | descriptor ขนาด 64 บิตบน IA-32 และ 128 บิตบน I-432 ตัวแปรละหนึ่ง descriptor | ทุกตัวแปร |
| StackGuard | canary หนึ่ง word | ทุกครั้งที่เรียกฟังก์ชัน |
| Secure Bit | 1 บิตต่อหนึ่ง word (ส่วนที่ 9) ซึ่งอาจเป็นขั้นต่ำที่เป็นไปได้ | ครั้งเดียว ตอนเพิ่มบิตเข้าไปในฮาร์ดแวร์ |

สำหรับ Secure Bit ยังต้องตอบอีกสองข้อ คือหนึ่งบิตพอจะได้ผลจริงไหม (effectiveness) และทำให้ช้าลงแค่ไหน (run-time penalty) ส่วนที่ 10 ตอบทั้งสองข้อ

### โปรแกรมที่ไม่ได้กลับตามลำดับ

ในสายตาของวิธีที่เฝ้า return address โค้ดบางแบบดูเหมือนการโจมตีทุกประการ เพราะ return address ถูกยกออกแล้วใส่กลับ หรือถูกใช้กระโดดโดยไม่ได้มาจาก `CALL`

โค้ดพวกนี้คือ non-LIFO control flow ที่ SRAS ในส่วนที่ 4 รับมือไม่ได้ ตัวอย่างจาก x86 แบบ 16 บิตคือ routine ที่ถูกเรียกได้ทั้งแบบ near และแบบ far

ต้องรู้จัก register สองตัวก่อน IP (instruction pointer) คือ address ของคำสั่งถัดไป ส่วน CS (code segment) บอกว่าโค้ดอยู่ใน segment ไหน การเรียกแบบ near เก็บแค่ IP ไว้บน stack ส่วนแบบ far เก็บทั้ง IP และ CS

```asm
NEAR_ENTRY:
    POP  AX      ; POP instruction pointer (IP) from the top of stack into AX
    PUSH CS      ; PUSH CS
    PUSH AX      ; PUSH IP back onto stack
FAR_ENTRY:
    ...
    RETF         ; POP IP and CS off stack
```

ทางเข้าแบบ near หยิบ return address ออกมา ใส่ CS ลงไปใต้มัน แล้วใส่ return address กลับคืน stack จึงหน้าตาเหมือนการเรียกแบบ far และทั้งสองทางเข้าใช้ `RETF` ตัวเดียวกันได้

อีกแบบที่พบบ่อยคือการ optimize ให้โค้ดสั้นลง เช่นใช้ `RET` แทน `JMP`

วิธีที่มีอยู่จึงทำได้สองทางกับโค้ดพวกนี้ คือ **ไม่สนใจ (ignore)** ซึ่งเปิดช่องให้ผู้โจมตี หรือ **รับมือไม่ได้ (cannot handle)** ซึ่งทำให้โปรแกรมที่ถูกต้องพัง

### สองข้อเท็จจริงที่ทำให้เรื่องนี้ยาก

- **buffer overflow เกิดได้ใน Java, Perl และภาษาที่ type-safe ทั้งหลาย** แม้ตัวภาษาจะตรวจขอบเขตให้ แต่ virtual machine, interpreter และไลบรารีที่มันเรียกใช้ส่วนใหญ่เขียนด้วย C
- **ไม่มีวิธีป้องกันไหนสมบูรณ์** วิธีที่ดูเหมือนจะสมบูรณ์ต้องเขียนโค้ดใหม่ทั้งหมด ตั้งแต่ BIOS, kernel, ไลบรารีทั้งแบบ static และ dynamic, driver ไปจนถึงแอปพลิเคชัน ซึ่งแทบเป็นไปไม่ได้

คำตอบที่วงการคอมพิวเตอร์รู้มานานแล้วคือให้ฮาร์ดแวร์กำกับข้อมูลทีละ word บทความใน Microprogramming เดือนเมษายน 1972 เขียนว่า

> I believe that the average computer of the year 2000 will: …. Have word by word protection and data description, …
>
> ผมเชื่อว่าคอมพิวเตอร์ทั่วไปในปี 2000 จะ … มีการป้องกันและการบรรยายข้อมูลทีละ word …

และใน ACM SIGARCH เดือนกรกฎาคม 2003 ก็ยังมีคนถามว่า

> Is anyone up for a discussion of capabilities, segments, 2-dimensional memory? Techniques which, among other things, render buffer overrun impossible.
>
> มีใครอยากคุยเรื่อง capability, segment, หน่วยความจำสองมิติไหม เทคนิคพวกนี้ทำให้ buffer overrun เป็นไปไม่ได้ ท่ามกลางข้อดีอื่น ๆ

สามสิบเอ็ดปีผ่านไป คำทำนายแรกก็ยังไม่เป็นจริง เพราะวิธีพวกนี้ต้องเปลี่ยนทั้งระบบ คำถามของ Secure Bit คือ **เปลี่ยนให้น้อยที่สุดได้แค่ไหน** โดยยังพิสูจน์ได้ว่าพอ

<Quiz question="แอป Java ตัวหนึ่งไม่มีโค้ด C ของตัวเองเลย แต่ใช้ไลบรารีอ่านรูปภาพที่เรียกผ่าน native code ถ้ามีคนส่งไฟล์รูปที่ออกแบบมาให้ล้นเข้ามา แอปนี้ปลอดภัยเพราะเป็น Java ไหม">

คำตอบคือ **ไม่ปลอดภัย** ความปลอดภัยของภาษาคุ้มครองแค่โค้ดที่เขียนด้วยภาษานั้น

คำตอบที่ผิดบ่อยคือ "ปลอดภัย เพราะ Java เป็นภาษา type-safe" ซึ่งมองแค่ชั้นบนสุด ทั้งที่ JVM เองและไลบรารีข้างล่างไม่ได้เขียนด้วย Java

## ส่วนที่ 8 — พิสูจน์ว่ากันอะไรถึงจะพอ

### address ที่ไม่ถูกแตะคือเงื่อนไขที่พอ

<Why>
ทุกวิธีที่ผ่านมาถูกออกแบบจากการโจมตีที่รู้จัก แล้วก็พลาดให้กับการโจมตีแบบถัดไป ถ้าจะหลุดจากวงจรนี้ ต้องหาสิ่งที่ **การโจมตีทุกแบบ** ต้องทำ แล้วพิสูจน์ว่ากันสิ่งนั้นได้ก็พอ
</Why>

ทฤษฎีเริ่มจาก Definition 1 และ 2 ในส่วนที่ 2 กับข้อสังเกตว่าของที่ล้นมาจาก domain อื่นเสมอ แล้วนิยามเพิ่มอีกข้อ

> **Definition 3:** Maintaining the integrity of an address means that the address has not been modified by overflowing with a buffer passed from another domain.
>
> การรักษา integrity ของ address หมายถึง address นั้นไม่ได้ถูกเปลี่ยนด้วยการล้นจาก buffer ที่ส่งมาจาก domain อื่น

> **Postulate 1:** In buffer-overflow attacks on control data, the generic buffer/memory-manipulating operations are used by the vulnerable routine to overflow the address (e.g. a return address or a function pointer).
>
> ในการโจมตี control data โปรแกรมที่มีช่องโหว่ใช้คำสั่งจัดการ buffer หรือหน่วยความจำทั่วไปเป็นตัวล้นทับ address เช่น return address หรือ function pointer

Postulate 1 บอกว่าผู้โจมตีไม่ได้เขียนลงหน่วยความจำเอง โปรแกรมเป็นคนเขียน ด้วยคำสั่งอย่าง `strcpy` ที่ใช้คัดลอกข้อมูลธรรมดาทุกวัน

ผลที่ตามมาคือ ถ้าฮาร์ดแวร์ทำให้คำสั่งคัดลอกทุกคำสั่งยกบิตไปพร้อมข้อมูล บิตนั้นจะตามข้อมูลจากข้างนอกไปถึง address ที่ถูกทับได้ทุกครั้ง ส่วนที่ 9 ใช้ข้อนี้

> **Theorem 1:** Modifying an address by replacing ("overflowing") it using a buffer passed from another domain is a necessary condition for buffer-overflow attack on control data.
>
> **Restatement:** If there is to be a buffer-overflow attack on control data, an address must be modified using a buffer passed from another domain.

พูดง่าย ๆ คือ ถ้าจะมีการโจมตี control data ด้วย buffer overflow ต้องมี address ตัวหนึ่งถูกเปลี่ยนด้วย buffer ที่มาจาก domain อื่น

บทพิสูจน์บอกว่าตามมาจาก Definition 1 และ 2 ตรง ๆ เพราะการโจมตีตามนิยามต้องเปลี่ยน address ด้วยการล้น buffer ส่วนคำว่า "จาก domain อื่น" มาจากข้อสังเกตในส่วนที่ 2

> **Corollary 1.1:** Preserving the integrity of an address is a sufficient condition for preventing a buffer-overflow attack.
>
> **Restatement:** If the integrity of an address is preserved, that is a sufficient condition for preventing a buffer-overflow attack.

การรักษา integrity ของ address ไว้ได้เป็นเงื่อนไขที่ **พอ** สำหรับกันการโจมตี บทพิสูจน์ใช้ <Term en="Contrapositive" th="ประพจน์แย้งสลับที่" /> ของ Theorem 1

ถ้าประโยค "ถ้า A แล้ว B" จริง ประโยค "ถ้าไม่ B แล้วไม่ A" ก็จริงด้วยเสมอ เช่น "ถ้าฝนตก ถนนเปียก" จริง ก็ได้ว่า "ถ้าถนนไม่เปียก ฝนไม่ได้ตก"

| | ประโยค |
| --- | --- |
| Theorem 1 | ถ้ามีการโจมตี แล้ว address ต้องถูกเปลี่ยนด้วย buffer จากข้างนอก |
| Contrapositive | ถ้าไม่มี address ไหนถูกเปลี่ยนด้วย buffer จากข้างนอก แล้วการโจมตีเกิดไม่ได้ |

ประโยคที่สองคือ Corollary 1.1 บทพิสูจน์เขียนเงื่อนไขนี้ว่า address "cannot be modified (or such modification can be detected)" คือถูกเปลี่ยนไม่ได้ หรือการเปลี่ยนถูกจับได้ก่อนถูกใช้ ซึ่งนับว่าเท่ากับไม่ถูกเปลี่ยน

ประโยคนี้คือเป้าหมายของ Secure Bit ไม่ต้องรู้ว่าการล้นมาทางไหน ขอแค่จับได้ว่า address ถูกเปลี่ยนด้วยข้อมูลจากข้างนอก

### ระบบที่ปลอดภัยต่อ buffer overflow

เพื่อพูดคำว่า "ปลอดภัย" ให้แม่น ทฤษฎีใช้นิยามของ Bishop จาก [Lecture 4](/2110413-csy/lecture-4#security-policy-และ-secure-system)

- **Definition 4:** security policy แบ่งสถานะทั้งหมดของระบบเป็นสถานะที่ได้รับอนุญาต (secure) กับไม่ได้รับอนุญาต (nonsecure)
- **Definition 5:** secure system คือระบบที่เริ่มจากสถานะที่ได้รับอนุญาต และเข้าสู่สถานะที่ไม่ได้รับอนุญาตไม่ได้เลย

> **Lemma 2:** A system which preserves the integrity of an address (e.g. a return addresses or a function pointer) is a secure system with respect to buffer-overflow attacks.
>
> **Restatement:** A system that does not use input as a control data is a secure system with respect to buffer-overflow attacks on control data.

บทพิสูจน์แบ่งสถานะของระบบเป็นสองกอง คือ **normal operation** กับ **buffer-overflow attack** แล้วเดินสามขั้น

1. ทางเดียวที่จะเข้ากอง attack คือ address ถูกเขียนทับด้วย address ที่มากับ input ตาม Definition 2
2. ถ้าการเขียนทับแบบนั้นถูกจับได้และถูกกันไว้ ระบบก็เข้ากอง attack ไม่ได้ ตาม Definition 3
3. ระบบเริ่มจาก normal operation และเข้ากอง attack ไม่ได้ จึงเป็น secure system ตาม Definition 5

> **Lemma 3:** Secure Bit and Protocol 1 can preserve the integrity of an address, and result in a secure system with respect to buffer-overflow attacks.

Protocol 1 ในส่วนที่ 9 คือกฎว่าทุก word ที่ข้าม domain เข้ามาได้บิต 1 Secure Bit กับ Protocol 1 จึงจับได้ว่า address ถูกล้นทับด้วย buffer จาก domain อื่น

จับได้ก็รักษา integrity ได้ตาม Definition 3 แล้ว Lemma 2 ก็บอกว่าระบบนั้นปลอดภัย

<Pitfall>
ความเชื่อที่ผิดคือ **มีบทพิสูจน์แล้ว Secure Bit จึงกัน buffer overflow ได้ทุกแบบ**

ข้อนี้ไม่จริง

มันดูจริงเพราะ Corollary 1.1 เขียนสั้น ๆ ว่า "preventing a buffer-overflow attack" และ Lemma 3 ก็ใช้คำว่า secure system

ที่ถูกคือ **ทุกบทพิสูจน์ปลอดภัยแค่ต่อการโจมตี control data** ตาม Definition 2 ตัวอย่างอายุในส่วนที่ 2 ล้นทับ `age` ซึ่งเป็นตัวเลข ไม่มี address ไหนถูกเปลี่ยน Secure Bit จึงปล่อยผ่าน และโปรแกรมก็ยังตอบว่า 49 ตัวแปรอย่าง `is_admin` ก็เช่นกัน
</Pitfall>

<Quiz question="ระบบหนึ่งรักษา return address ได้สมบูรณ์ ไม่มีทางถูกเขียนทับ แต่ไม่ได้ดูแล function pointer เลย Corollary 1.1 รับรองว่าระบบนี้กันการโจมตี control data ได้ไหม">
Theorem 1 บอกว่าการโจมตีต้องเปลี่ยน **address ตัวหนึ่ง** ตัวไหนก็ได้ที่โปรแกรมจะกระโดดตาม Corollary 1.1 จึงต้องการ integrity ของทุก address ที่ถูกใช้เป็นเป้าหมายของการกระโดด

คำตอบคือ **ไม่รับรอง** การโจมตีทาง function pointer หรือทาง jump slot ใน GOT ยังเปลี่ยน address ได้ เงื่อนไขของ Corollary จึงไม่ครบ

คำตอบที่ผิดบ่อยคือ "รับรอง เพราะ stack smashing ถูกกันแล้ว" ซึ่งเอาการโจมตีแบบที่ดังที่สุดมาเป็นทั้งหมด ช่องนี้เองที่ทำให้ split stack และวิธีในกลุ่ม copy of address ไม่พอ
</Quiz>

## ส่วนที่ 9 — Secure Bit: บิตเดียวที่ติดไปกับทุก word

> Give me a little Bit and I will solve buffer-overflow attacks.

### สองกฎ

<Why>
Corollary 1.1 ต้องการ integrity ของ **ทุก** address ที่โปรแกรมจะกระโดดตาม แต่วิธีในส่วนที่ 4 เฝ้าทีละตำแหน่ง และพลาดตำแหน่งที่ไม่ได้เฝ้า ทางที่ไม่ต้องรู้ว่า address อยู่ตรงไหน คือดูว่าค่านั้น **มาจากไหน** แทนที่จะดูว่ามันไปลงที่ไหน ซึ่งก็คือกฎของ input protection ในส่วนที่ 5 ที่ย้ายมาทำในฮาร์ดแวร์
</Why>

Secure Bit ใช้บิตหนึ่งบิตต่อหนึ่ง word ของหน่วยความจำ บอกว่า word นั้นมาจาก domain อื่นหรือไม่

ทุก word ใน process ตั้งแต่ parameters, return address, function pointers ไปจนถึง buffer เริ่มที่บิต 0 ซึ่งแปลว่า trustworthy ส่วน word ที่ input จากอุปกรณ์หรือผู้ใช้ผ่าน OS และ driver ลงไปอยู่ได้บิต 1 ซึ่งแปลว่า untrustworthy แล้วบังคับด้วยสองกฎ

- **Protocol 1:** การส่ง buffer ข้าม domain ซึ่งได้แก่อุปกรณ์ เครื่อง และ process ต้องตั้ง Secure Bit เสมอ พูดอีกแบบคือ **input ทุก word มี Secure Bit เป็น 1**
- **Protocol 2 (Hardware Enforcement):** ข้อมูลจาก domain อื่นที่มี Secure Bit เป็น 1 ห้ามถูกใช้เป็นเป้าหมายของการกระโดด

แนวคิดนี้มีมาก่อนในรูปของหลักการเขียนโปรแกรม Howard และ LeBlanc เขียนไว้ว่า "All input is evil until proven otherwise" และ "Data must be validated as it crosses the boundary between untrusted and trusted environments" คือ input ทุกตัวอันตรายจนกว่าจะพิสูจน์ได้ว่าไม่ และข้อมูลต้องถูกตรวจตอนข้ามจากฝั่งที่ไม่น่าไว้ใจเข้ามาฝั่งที่ไว้ใจ

หลักนี้คือ [Validation of Input ใน Lecture 2](/2110413-csy/lecture-2#validation-of-input--เชื่อ-input-ไม่ได้) Secure Bit เอามันไปไว้ในฮาร์ดแวร์ โปรแกรมเมอร์จึงลืมไม่ได้

### Protocol Enforcement — ใครเป็นคนตั้งบิต

<Term en="sbit_write mode" th="โหมดที่ทุกการเขียนได้บิต 1" /> คือโหมดใหม่ของ CPU ระหว่างอยู่ในโหมดนี้ ทุก word ที่ถูกเขียนลงหน่วยความจำได้ Secure Bit เป็น 1

kernel ใช้ sbit_write mode ทุกครั้งที่ย้ายข้อมูลข้าม domain ส่วนคำสั่ง Call, Jump และ Return ถูกแก้ให้ตรวจ Secure Bit ของ address ปลายทางก่อนกระโดด

### ฮาร์ดแวร์ — หน่วยความจำ ชุดคำสั่ง และ register

**หน่วยความจำ** มีบิตเพิ่มหนึ่งบิตต่อหนึ่ง word เก็บแยกไว้ใน **Secure Bit Storage** ข้างที่เก็บข้อมูลปกติ CPU กับชิปหน่วยความจำมีสาย Secure Bit (I/O) เพิ่มอีกเส้นข้างสาย Address, Data, CS และ R/W โดย CS ตรงนี้คือ chip select ที่เลือกว่าจะคุยกับชิปไหน ไม่ใช่ code segment ในส่วนที่ 7

การหา address ของบิตทำแบบนี้

1. แบ่ง physical memory address เป็นบิตส่วนบน (high order bits) กับ 3 บิตล่าง
2. บิตส่วนบนบวกกับ **Base Register** ได้ address ใน Secure Bit Storage
3. 3 บิตล่างเข้า **8-1 Line Selector** เลือกหนึ่งในแปดบิตของไบต์นั้น

ไบต์หนึ่งไบต์ใน Secure Bit Storage จึงเก็บบิตของแปดตำแหน่งติดกัน เช่นที่ตำแหน่ง `0x1234` ตัด 3 บิตล่างทิ้งได้ไบต์ที่ `0x246` และ 3 บิตล่างมีค่า 4 คือบิตที่ 4 ซึ่งมี mask `0x10`

ในแบบที่ใช้ Base Register นี้ Secure Bit Storage ไม่ใช่ชิปแยก แต่เป็นช่วงหนึ่งของหน่วยความจำหลักที่กันไว้เก็บบิต (SecureBits) และ Base Register เก็บ address เริ่มต้นของช่วงนั้น

ตรงนี้สไลด์ขัดกันเอง หัวข้อบอกว่าเพิ่มหนึ่งบิตต่อ **หนึ่ง word** แต่ถ้า physical address เป็น address ระดับไบต์อย่างบน x86 การเลือกด้วย 3 บิตล่างจะได้หนึ่งบิตต่อ **หนึ่งไบต์** และโค้ดของ BOCHS ในส่วนที่ 10 ก็เก็บแบบนั้นจริง หน้านี้ใช้คำว่า "ต่อหนึ่ง word" ตามแนวคิด ส่วนตัวเลขขนาดในส่วนที่ 10 คิดให้ทั้งสองแบบ

**ชุดคำสั่ง** เปลี่ยนสี่จุด

- มี flag ใหม่ชื่อ `sbit_write`
- `CALL` และ `JUMP` ตรวจ Secure Bit ของเป้าหมาย `RET` คือการกระโดดไปตามค่าที่ดึงจาก stack และ Return อยู่ในรายการของ protocol enforcement ข้างบน จึงถูกตรวจเหมือนกัน รูปที่ 2 จึงแสดง `RET` เป็นตัวปฏิเสธ
- คำสั่งอื่นที่แตะหน่วยความจำ ยก Secure Bit ไปพร้อมกับ word ที่ย้ายเมื่อ sbit_write mode ปิดอยู่ และตั้ง Secure Bit ที่ปลายทางเมื่อ sbit_write mode เปิดอยู่
- การคำนวณทุกแบบ ทั้ง shift, เลขคณิต และตรรกะ ถ้ามี operand ตัวไหนไม่ปลอดภัย ผลก็ไม่ปลอดภัย ส่วนค่าคงที่ที่ฝังในคำสั่ง (immediate) ถือว่าปลอดภัย

ข้อสุดท้ายทำใน **ALU** ด้วย OR gate สามขา ขาเข้าคือบิตของ operand ตัวที่หนึ่ง บิตของ operand ตัวที่สอง และ flag `sbit_write` จาก FLAGS register ผลทุกตัวที่คำนวณระหว่างอยู่ใน sbit_write mode จึงได้บิต 1 ด้วย

**register** ทุกตัว เช่น EAX ต้องมี Secure Bit ติดไปด้วย และ **Program Counter** ก็ต้องมี ส่วนว่า CPU จะยก exception ตอนไหนเมื่อบิตของ PC เป็น 1 ยังเป็นคำถามที่ต้องออกแบบ

นอกจาก BOCHS ในส่วนที่ 10 อีกแพลตฟอร์มที่ใช้ทดลองได้คือ **SimpleScalar** สถาปัตยกรรม RISC ของมันมีชุดคำสั่งเรียบง่ายและออกแบบไม่ซับซ้อน แต่ยังมีเรื่องที่ต้องคิด คือ parallelism, hazard และ cache เพราะบิตต้องเดินทางไปกับค่าผ่านทุกส่วนเหล่านั้น

### ระบบปฏิบัติการ

ฝั่ง OS มีงานสองอย่าง

- **Domains and Buffer Manipulation** — ย้ายข้อมูลระหว่าง kernel กับ process ใน sbit_write mode ตามหัวข้อ protocol enforcement ข้างบน
- **Virtual Memory** — Secure Bit ผูกกับ physical address ไม่ใช่ virtual address จัดการได้สามแบบ คือให้ firmware ดูแล ให้ซอฟต์แวร์จัดการ หรือใช้ paging ตามปกติบนฮาร์ดแวร์ที่แก้แล้ว

### BOCHS — ตัวจำลอง x86

Secure Bit ถูกสร้างบน **BOCHS** ซึ่งเป็นโปรแกรมจำลองเครื่อง x86 เขียนด้วย C++ แบ่งเป็น object คือ CPU, หน่วยความจำ, I/O peripheral, BIOS, disk และอื่น ๆ

BOCHS มีขอบเขตของหน่วยความจำชัดเจน สร้างได้หลาย instance และจำลองชุดคำสั่งทั้งหมด มันมีมากกว่า 5,304 routine โดย 3,600 อยู่ใน object ของ CPU

การตั้งหรือล้าง Secure Bit ของข้อมูลยาว `len` ไบต์ที่ตำแหน่ง `a20addr` เขียนแบบนี้

```cpp
// Set/Clear Secure Bit by KPR
Bit32u a20addr_s;
Bit8u sbyte;
for (int i=0;i<len ;i++ )
{
  a20addr_s=(a20addr+i)>>3;
  sbyte=(a20addr+i) & 0x00000007;
  sbyte=1 << sbyte;
  if (*sbit==1)
  { // set
    vector_s[a20addr_s]|=(sbyte&0xff);
  }
  else
  { // clear
    vector_s[a20addr_s]&=~(sbyte&0xff);
  }
  sbyte=sbyte<<1;
}
```

นี่คือการหา address ของบิตในส่วนที่ 9 ในรูปของโค้ด `vector_s` คือ Secure Bit Storage `>>3` ตัด 3 บิตล่างทิ้งเพื่อหาไบต์ใน `vector_s` และ `& 7` เอา 3 บิตล่างมาเลือกบิตในไบต์ เหมือนตัวอย่าง `0x1234`

routine คู่กันชื่อ Read Secure Bit วนหาบิตแบบเดียวกัน แต่ OR บิตของทั้ง `len` ไบต์รวมเป็นค่าเดียว word ที่ยาวหลายไบต์จึงไม่ปลอดภัยทั้ง word ถ้ามีไบต์ไหนสักไบต์ไม่ปลอดภัย

ส่วนอื่นที่ต้องแก้

- **Memory interface** — เพิ่ม `readPhysicalPage` และ `writePhysicalPage` รุ่นที่รับพารามิเตอร์ `sbit` เพิ่ม แบบ overload รุ่นเดิมที่ไม่สนใจ Secure Bit ยังอยู่ จึงไม่ต้องแก้ routine กว่า 3,000 ตัวที่เรียกมัน
- **พารามิเตอร์ `ignore`** — รุ่นเขียนอีกรุ่นมี `ignore` ด้วย คอมเมนต์ในโค้ดบอกว่า `ignore=0` คือเขียนข้อมูลโดยปล่อย Secure Bit เดิมไว้ ซึ่งกลับกับที่ชื่อพารามิเตอร์ชวนให้เดา
- **macro ของ ALU** — macro หนึ่งตัวต่อชนิดของคำสั่ง ALU เช่น `SBIT_ADD(sbit1,sbit2)` ให้ 0 เมื่อทั้งสองบิตเป็น 0 นอกนั้นให้ 1 ตามกฎ OR ในส่วนที่ 9 มีครบทั้ง SHX, ROX, XOR, AND, OR, NOT, ADD, SUB และ MUL ซึ่งใช้กับ DIV ด้วย SHX กับ ROX คือกลุ่มคำสั่ง shift และ rotate macro ของมันรับแค่บิตของค่าที่ถูกเลื่อน
- **การตั้งบิต** — `sbit=(sbit_mode)? 1:sbit;`
- **การตรวจเป้าหมายของ call** — ถ้า `sbit != 0` ให้บันทึก log ว่า `call_ew: sbit of target is not secure` ส่วนการยก `BX_GP_EXCEPTION` อยู่ใน `#ifdef HAS_SBIT_EXCEPTION` จึงเกิดเฉพาะเมื่อ compile โดยกำหนดค่านี้ไว้ ถ้าไม่กำหนด โปรแกรมแค่บันทึก log แล้วทำงานต่อ
- **ขนาดของงาน** — รวมแล้วแก้ประมาณ 2,410 บรรทัดใน 607 routine

### Linux — ทางเข้าทุกทางผ่านจุดเดียว

<Term en="Threat Surface" th="ทุกทางที่ input เข้ามาได้" /> คือ input ทุกทางที่ข้ามเข้ามาผ่าน interface ของซอฟต์แวร์

ใน Linux ข้อมูลจากทุกแหล่งของ kernel ทั้ง input device, storage device, TCP/IP, standard input และอื่น ๆ เข้าถึง process ผ่านการ **คัดลอกลง buffer ของผู้ใช้** ใน `usercopy.c` threat surface จึงแคบลงเหลือฟังก์ชันไม่กี่ตัว แก้ตรงนั้นที่เดียว ทุก word ที่ลงไปใน buffer ของ process ก็ได้บิต 1

```c
#define SET_SBITMODE() \
  asm volatile( \
    " pushl %eax\n" \
    " lahf\n" \
    " orb $0x20, %ah\n" \
    " sahf\n" \
    " popl %eax" )

unsigned long
__generic_copy_to_user(void *to, const void *from, unsigned long n)
{
  SET_SBITMODE();
  if (access_ok(VERIFY_WRITE, to, n))
    __copy_user(to,from,n);
  CLR_SBITMODE();
  return n;
}
```

`lahf` คัดลอก 8 บิตล่างของ FLAGS ลง `AH` แล้ว `orb $0x20` ตั้งบิตที่ 5 ก่อน `sahf` เขียนคืน `CLR_SBITMODE` ทำกลับกันด้วย `andb $0xdf`

บิตที่ 5 ของ FLAGS เป็นบิตที่ x86 สงวนไว้และไม่ได้ใช้ Secure Bit จึงเอามาเป็น flag `sbit_write` ได้โดยไม่ชนกับ flag เดิม

การสาธิตใช้การโจมตีสองขั้นกับโปรแกรม `vulnerable` ในส่วนที่ 2 ขั้นแรกทับ `ptr` ให้ชี้ไปที่ช่องของ `printf` ใน GOT ขั้นที่สอง `strcpy` ครั้งที่สองเขียน address ของ `residentcode()` ลงในช่องนั้น

`residentcode()` เป็นฟังก์ชันที่มีอยู่แล้วในโปรแกรมและเปิด `/bin/sh` พอโปรแกรมเรียก `printf` ครั้งถัดไปจึงกระโดดไปเปิด shell แทน โดยไม่ต้องฉีดโค้ดใหม่เลย

บนตัวจำลองที่ไม่มี Secure Bit ผู้โจมตีได้ shell ไป ส่วนบนตัวจำลองที่มี Secure Bit (รุ่นที่เรียกว่า Secure Bit2) โปรแกรมจบด้วย `Segmentation fault` และคอนโซลของตัวจำลองรายงานว่า

```text

Device: [CPU ]
Message: jmp_ed: sbit of target is not secure
```

- Slammer ทำ Davis-Besse ใช้การไม่ได้เกือบ 5 ชั่วโมง ล้ม 911 ของ Bellevue และ ATM ของ Bank of America 13,000 เครื่อง
- ไฟดับปี 2003 ไม่ได้เกิดจาก Blaster แต่จากระบบเตือนภัยของ FirstEnergy ที่ล้มเหลว
- CERT มีบันทึกเรื่อง buffer overflow 1,347 ฉบับ ปี 2020 มี 213 ฉบับ เช่น GRUB2 (VU#174059) และ Netgear (VU#576779)

**[ล้นแล้วเปลี่ยนทางเดินของโปรแกรม](#ส่วนที่-2--ข้อมูลที่ล้นไปเปลี่ยนทางเดินของโปรแกรมได้ยังไง)**

- `Krerk.P01` ใส่ `name[8]` ทับ `age` จาก 15 เป็น 49 เพราะ `'1'` คือ `0x31`
- **control data** คือ return address, function pointer, exception handler, virtual method
- การโจมตีสามแบบ: return-address (stack smashing), function-pointer, frame-pointer และแบบสองขั้นที่ทับ pointer ธรรมดาแล้วเขียนไปที่ไหนก็ได้ เช่น jump slot ใน GOT (SLAPPER)
- เงื่อนไขที่ต้องมีครบ: มีโค้ดให้รัน (ฉีดเอง **หรือ** รู้ address ของโค้ดที่มีอยู่) และพาโปรแกรมไปรัน
- integer overflow และช่องโหว่ `printf` ทำงานคล้ายกัน

**[แผนที่ของวิธีป้องกัน](#ส่วนที่-3--แผนที่ของวิธีป้องกัน)**

- สามตระกูล: static analysis, dynamic solution (address protection, input protection, bounds checking, obfuscation), isolation (NX, sandboxing)
- static analysis จับได้แค่ที่รู้จัก ไม่มีข้อมูลตอนรัน และเตือนผิดได้
- คำถามสี่ข้อของ dynamic solution: assumptions, การสร้าง metadata, การตรวจ metadata, การจัดการข้อมูลผิด

**[ปกป้อง address](#ส่วนที่-4--ปกป้อง-address-ไม่ให้ถูกเปลี่ยนโดยไม่มีใครรู้)**

- canary (StackGuard): random, terminator, terminator with diversity ค่าเปลี่ยนเมื่อไรก็หยุดก่อนกลับ
- ProPolice: guard + ย้าย array ไปติด guard และ pointer ไปไว้ใต้ array กัน pointer ใน struct ไม่ได้
- PointGuard: เข้ารหัส pointer ตอนเก็บ ถอดตอนใช้
- copy of address: Split Stack, StackGhost, SRAS, RAD, StackShield, LibVerify, DISE, SCACHE
- tags: IBM System/38
- canary จับการเขียนผ่าน pointer ที่ข้ามมันไม่ได้

**[ติดป้าย input ตรวจขอบเขต สุ่ม address](#ส่วนที่-5--ติดป้าย-input-ตรวจขอบเขต-และสุ่ม-address)**

- input protection: input ห้ามเป็น control data (Minos, Tainted pointer, Dynamic Flow Tracking)
- bounds checking: base และ boundary ทุกตัวแปร ช้าลงกว่า **30 เท่า**
- obfuscation: สุ่ม base, สลับลำดับ, เว้นช่องสุ่ม, PaX ASLR
- ทำให้ฉีดโค้ดไม่ได้: ISR, SPEF (SPEF นับเป็น isolation ด้วย)
- ฉีดโค้ดไม่ได้ไม่ได้แปลว่าปลอดภัย เพราะใช้โค้ดที่มีอยู่แล้วได้

**[Isolation](#ส่วนที่-6--isolation-ยอมให้ล้น-แต่จำกัดผล)**

- NX, sandbox (TCPA), SPEF; NX ไม่ช่วยกับ heap, โปรแกรมที่ต้องรันโค้ดบน stack และการโจมตีที่ไม่ฉีดโค้ด
- NGSCB: strong process isolation, sealed storage, secure user interface, attestation — trusted ไม่ได้แปลว่า secure

**[ทำไมยังไม่จบ](#ส่วนที่-7--ทำไมยังไม่มีวิธีไหนปิดเรื่องนี้ได้)**

- จุดพลาด: assumptions ไม่พอ, ปกป้อง metadata ไม่พอ, performance, compatibility (non-LIFO), deployment
- metadata: descriptor 64 บิต (IA-32) / 128 บิต (I-432) ต่อตัวแปร, canary ต่อการเรียก, Secure Bit 1 บิตต่อ word
- overflow เกิดใน Java และ Perl ได้ เพราะชั้นล่างเขียนด้วย C

**[ทฤษฎี](#ส่วนที่-8--พิสูจน์ว่ากันอะไรถึงจะพอ)**

- Theorem 1: การเปลี่ยน address ด้วย buffer จาก domain อื่นเป็นเงื่อนไข **จำเป็น** ของการโจมตี control data
- Corollary 1.1: รักษา integrity ของ address ได้เป็นเงื่อนไข **พอ** พิสูจน์ด้วย contrapositive
- Lemma 2: ระบบที่ไม่ใช้ input เป็น control data คือ secure system (นิยามของ Bishop)
- Lemma 3: Secure Bit กับ Protocol 1 รักษา integrity ได้ — ปลอดภัยต่อการโจมตี **control data** เท่านั้น

**[Secure Bit](#ส่วนที่-9--secure-bit-บิตเดียวที่ติดไปกับทุก-word)**

- Protocol 1: input ทุก word มีบิต 1 · Protocol 2: ห้ามใช้ค่าบิต 1 เป็นเป้าหมายของการกระโดด
- kernel ย้ายข้อมูลข้าม domain ใน sbit_write mode; Call, Jump, Return ตรวจบิต
- ALU: operand ไม่ปลอดภัยตัวเดียว ผลก็ไม่ปลอดภัย (OR); immediate ปลอดภัย
- address ของบิต = base register + บิตส่วนบน, 3 บิตล่างเลือกบิตในไบต์

**[สร้างจริง](#ส่วนที่-10--สร้างจริงและวัดผล)**

- BOCHS: มากกว่า 5,304 routine, แก้ประมาณ 2,410 บรรทัดใน 607 routine, overload memory interface เลี่ยงการแก้ 3,000+ routine
- Linux: ตั้ง sbit_write ใน `usercopy.c` ด้วย `orb $0x20, %ah`
- ทดสอบ: บูต Linux, แอปเดิม (SPEC, Apache + mod_ssl, OpenSSH, JVM ฯลฯ), hacking test, คำสั่งที่แก้
- ผล: เข้ากันได้กับ binary เดิม 100%, แก้แค่ CPU, ไม่ช้าลงอย่างมีนัยสำคัญ
