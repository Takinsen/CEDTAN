## ส่วนที่ 1 — ช่องโหว่เก่าที่ยังไม่หายไป

### หนอนดังเกือบทุกตัวเข้าทางเดียวกัน

<Term en="Buffer Overflow" th="ข้อมูลล้นที่พัก" /> คือการเขียนข้อมูลลง buffer ซึ่งเป็นที่พักข้อมูลในหน่วยความจำ เกินกว่าที่จองไว้ จนทับของที่อยู่ข้าง ๆ (ส่วนที่ 2 แสดงให้เห็นทีละไบต์) มันคือช่องโหว่ที่หนอนอินเทอร์เน็ตตัวดังเกือบทุกตัวใช้เข้าเครื่อง [หนอน](/2110413-csy/lecture-1#malicious-software) คือโปรแกรมที่แพร่จากเครื่องหนึ่งไปอีกเครื่องเองโดยไม่ต้องมีคนกด

สไลด์ไม่ได้บอกว่า Code Red และ Slammer ล้นในโปรแกรมไหน สองช่องนั้นและคำอธิบายชื่อโปรแกรมในวงเล็บเป็นข้อมูลเสริม

| ปี | หนอน | รายละเอียด |
| --- | --- | --- |
| 1988 | Morris worm หนอนตัวแรก | ล้นใน `fingerd` (โปรแกรมบน Unix ที่ตอบคำถามจากเครื่องอื่นว่าเครื่องนี้มีผู้ใช้ชื่ออะไร) ติดไป 10% ของอินเทอร์เน็ตในตอนนั้น |
| 2001 | Code Red | ล้นในบริการทำดัชนีของเว็บเซิร์ฟเวอร์ Microsoft IIS |
| 2003 | Slammer | ล้นใน Microsoft SQL Server 2000 |
| 2003 | Blaster และ Welchia | ล้นใน DCOM RPC ของ Windows (บริการที่ให้โปรแกรมบนเครื่องอื่นเรียกฟังก์ชันบนเครื่องนี้ผ่านเครือข่าย) |
| 2004 | Witty | ออกมาหนึ่งวันหลังประกาศช่องโหว่ |
| 2004 | Sasser | ล้นใน LSASS ของ Windows (โพรเซสที่ตรวจรหัสผ่านตอนล็อกอินและคุมนโยบายความปลอดภัยของเครื่อง) สันนิษฐานว่าแกะวิธีมาจากประกาศช่องโหว่ |
| 2006 | ช่องโหว่บน Mac | ล้นในส่วน wireless |

สองแถวของปี 2004 บอกเรื่องเดียวกัน คือ **ประกาศช่องโหว่กับแพตช์เป็นแผนที่ให้ผู้โจมตีด้วย** Witty ใช้เวลาแค่หนึ่งวันจากวันประกาศถึงวันที่หนอนออก คนที่รอแพตช์สัปดาห์หน้าจึงช้าไปแล้ว และรายการนี้ยังมีอีกมาก

### ความเสียหายนอกจอคอมพิวเตอร์

Slammer ปี 2003 เป็นตัวอย่างว่าหนอนตัวเดียวลามไปถึงระบบที่ไม่มีใครคิดว่าเป็นคอมพิวเตอร์

ข่าวของ SecurityFocus วันที่ 19 สิงหาคม 2003 ("Slammer worm crashed Ohio nuke plant network") รายงานว่าในเดือนมกราคม Slammer เข้าไปในเครือข่ายภายในของโรงไฟฟ้านิวเคลียร์ Davis-Besse ในโอไฮโอ แล้วทำให้ระบบเฝ้าระวังความปลอดภัยใช้การไม่ได้เกือบห้าชั่วโมง ทั้งที่พนักงานเชื่อว่ามีไฟร์วอลล์กันอยู่ เคสนี้เล่าเต็มไว้ใน [หลักการที่ 9 ของ Lecture 1](/2110413-csy/lecture-1#หลักการที่-9--dont-extend-trust-easily)

ส่วนบทความ "Inside the Slammer Worm" ใน IEEE Security and Privacy ฉบับกรกฎาคม–สิงหาคม 2003 รายงานความเสียหายอีกสามอย่าง

- ทำให้เครื่องรับแจ้งเหตุ 911 ของเมือง Bellevue รัฐวอชิงตัน ล่ม
- ทำให้ตู้ ATM ของ Bank of America 13,000 เครื่องล่ม
- ส่งแพ็กเก็ตจนเราเตอร์รับไม่ไหว โครงสร้างพื้นฐานของอินเทอร์เน็ตบางส่วนจึงล่มตาม

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ไฟดับครั้งใหญ่ในอเมริกาและแคนาดาเมื่อ 14 สิงหาคม 2003 เกิดจากหนอน Blaster**

ข้อนี้ไม่จริงตามรายงานเบื้องต้นเรื่องสาเหตุของไฟดับครั้งนั้น ("Interim Report: Causes of the August 14th Blackout in the United States and Canada")

มันดูจริงเพราะ Blaster ระบาดในสัปดาห์เดียวกันพอดี หลังวันที่ 11 สิงหาคมมันติดเครื่อง Windows ไปมากกว่าหนึ่งล้านเครื่อง

สิ่งที่เกิดขึ้นจริงคือ **เครื่องที่คุมการผลิตและจ่ายไฟแยกขาดจากอินเทอร์เน็ต และไม่โดน Blaster เลย** ต้นเหตุคือระบบเตือนภัยที่บริษัทไฟฟ้า FirstEnergy ในโอไฮโอล้มเหลวต่อกันเป็นทอด ทั้งเครื่องที่รันซอฟต์แวร์ alarm and logging เครื่องสำรอง และคอนโซลควบคุมระยะไกลอีกหลายตัว ผู้ควบคุมจึงไม่รู้ว่าเกิดอะไรขึ้นและสกัดปัญหาไม่ทัน ในเวลาเดียวกัน เครื่องแสดงสถานะของ Midwest Independent Transmission System Operator ซึ่งดูแลการจ่ายไฟของภูมิภาคก็เสีย ช่างที่มาซ่อมลืมเปิดเครื่องกลับก่อนออกไปกินข้าวกลางวัน บทเรียนคือความล้มเหลวที่ดูเหมือนการโจมตี อาจเป็นแค่ระบบที่ไม่มีใครเฝ้า
</Pitfall>

### ยังเจออยู่ทุกปี

ข่าวจาก CERT วันที่ 7 กันยายน 2006 มีบันทึกช่องโหว่สองฉบับห่างกันสองวัน ทั้งคู่ทำให้ **ผู้โจมตีสั่งรันโค้ดอะไรก็ได้บนเครื่องเหยื่อ**

- VU#821156 (24 สิงหาคม 2006) — Microsoft Internet Explorer ล้นเมื่อเจอ URL ที่ยาวมาก
- VU#394444 (22 สิงหาคม 2006) — stack buffer overflow ใน Microsoft Hyperlink Object Library

สิบสี่ปีต่อมาก็ยังไม่หาย ค้นคำว่า buffer overflow ในฐานข้อมูลช่องโหว่ของ CERT ที่ Software Engineering Institute ได้ 1,347 ฉบับ แยกตามปีได้แบบนี้

| ปี | 2015 | 2016 | 2017 | 2018 | 2019 | 2020 |
| --- | --- | --- | --- | --- | --- | --- |
| จำนวนบันทึก | 11 | 17 | 9 | 4 | 8 | 213 |

สไลด์ไม่ได้อธิบายว่าทำไมปี 2020 ได้ 213 ฉบับ ในขณะที่ห้าปีก่อนหน้าได้ปีละ 4 ถึง 17 ตัวเลขพวกนี้คือจำนวนผลค้นหาที่เว็บไซต์แยกตามปีให้ ไม่ใช่จำนวนช่องโหว่ทั้งหมดที่พบในปีนั้น จึงอ่านเป็นแนวโน้มไม่ได้ สิ่งที่มันบอกได้คือช่องโหว่ชนิดนี้ยังถูกบันทึกเพิ่มทุกปี

สองผลบนสุดของการค้นนั้นเป็นของปี 2020

- **VU#174059** (29 กรกฎาคม 2020) — boot loader GRUB2 ล้น ทำให้รันโค้ดอะไรก็ได้ระหว่างบูตเครื่อง แม้เปิด Secure Boot อยู่
- **VU#576779** (26 มิถุนายน 2020) — เว็บเซิร์ฟเวอร์ในอุปกรณ์ Netgear หลายรุ่นมี stack buffer overflow ตอนจัดการ `upgrade_check.cgi` ทำให้คนที่ไม่ได้ล็อกอินรันโค้ดด้วยสิทธิ์ root ได้

## ส่วนที่ 2 — ข้อมูลล้นไปเปลี่ยนทางเดินของโปรแกรมได้ยังไง

### ล้นคืออะไร — ชื่อที่ยาวเกินไปหนึ่งตัวอักษร

<Why>
โปรแกรมข้างล่างถามอายุก่อน แล้วถามชื่อ ช่องเก็บชื่อจุได้ 8 ไบต์ คนชื่อ `Krerk.P01` พิมพ์อายุ 15 แต่โปรแกรมตอบว่าเขาอายุ 49
</Why>

```c
int age;
char name[8];
char tmp[20];
printf("Enter your age:");
gets(tmp);
age=atoi(tmp);
printf("Enter your name:");
gets(name);
printf("-----------\n%s is %d years old\n",name,age);
```

```text
$ gcc -fno-stack-protector -o age age.c
$ ./age
Enter your age:15
Enter your name:Krerk.P01
-----------
Krerk.P01 is 49 years old
```

`gets` อ่านทั้งบรรทัดลงไปในที่ที่ได้รับมาโดยไม่รู้ว่าที่นั้นยาวเท่าไร `Krerk.P01` ยาว 9 ตัวอักษร บวกตัวปิดท้ายสตริง `\0` อีกหนึ่งไบต์เป็น 10 ไบต์ แต่ `name` มีแค่ 8 สองไบต์ที่เกินจึงลงไปในตัวแปรที่อยู่ถัดไปในหน่วยความจำ ซึ่งคือ `age`

| ไบต์ของ `age` | ก่อน `gets(name)` | หลัง `gets(name)` |
| --- | --- | --- |
| ไบต์แรก | `0x0F` (15) | `0x31` คือตัวอักษร `'1'` |
| ไบต์ที่สอง | `0x00` | `0x00` คือ `\0` |
| ค่าของ `age` | 15 | `0x31` = **49** |

เครื่อง x86 เก็บไบต์ที่มีค่าน้อยที่สุดของจำนวนเต็มไว้ก่อน ไบต์แรกที่ถูกทับจึงเป็นหลักหน่วยของ `age` พอดี

นี่คือนิยามของ buffer overflow

> **Definition 1:** The condition wherein the data transferred to a buffer exceeds the storage capacity of the buffer and some of the data "overflows" into another buffer, one that the data was not intended to go into.
>
> สภาพที่ข้อมูลซึ่งถูกส่งเข้า buffer มีมากกว่าที่ buffer จุได้ แล้วส่วนที่เกินล้นเข้าไปใน buffer อื่นที่ข้อมูลนั้นไม่ได้ตั้งใจจะไป

ตัวอย่างนี้ใช้ทั้งหน้า เพราะวิธีป้องกันหลายแบบในส่วนต่อไปเปลี่ยนผลของมันได้

<Quiz question="ถ้าพิมพ์ชื่อยาวพอดี 8 ตัวอักษร เช่น Krerk.P0 ซึ่งเท่ากับขนาดของ name พอดี age จะออกมาเป็นเท่าไร">
`Krerk.P0` ยาว 8 ตัว แต่ `gets` ยังต่อท้ายด้วย `\0` อีกหนึ่งไบต์เสมอ ไบต์ที่ 9 นั้นจึงลงไปทับไบต์แรกของ `age` ซึ่งเก็บ `0x0F` อยู่ แล้วเปลี่ยนเป็น `0x00`

คำตอบคือ **0** รันจริงได้ `Krerk.P0 is 0 years old`

คำตอบที่ผิดบ่อยคือ "15 เพราะชื่อยาวไม่เกินที่จุ" ซึ่งลืมว่าสตริงใน C กินที่มากกว่าจำนวนตัวอักษรหนึ่งไบต์เสมอ การล้นเกินมาไบต์เดียวแบบนี้เกิดบ่อยมากในโค้ดจริง
</Quiz>

### Control Data — ค่าที่ตัดสินว่าโปรแกรมจะไปไหนต่อ

ตัวอย่างข้างบนทำแค่เปลี่ยนตัวเลข ถ้าค่าที่ถูกทับเป็นค่าที่โปรแกรมใช้ตัดสินว่าจะไปรันคำสั่งที่ไหนต่อ การล้นจะเปลี่ยนทางเดินของโปรแกรมทั้งโปรแกรม

<Term en="Control Data" th="ข้อมูลควบคุม" /> คือค่าในหน่วยความจำที่เป็นที่อยู่ของโค้ด และโปรแกรมจะกระโดดไปตามค่านั้น ค่าพวกนี้ส่วนใหญ่อยู่บน <Term en="Stack" th="กองซ้อนของการเรียกฟังก์ชัน" /> ซึ่งเป็นพื้นที่หน่วยความจำที่โปรแกรมใช้ตอนเรียกฟังก์ชัน การเรียกแต่ละครั้งจองพื้นที่หนึ่งก้อนไว้เก็บอาร์กิวเมนต์ ที่อยู่ขากลับ และตัวแปรภายในของฟังก์ชันนั้น ข้อมูลเสริมจากสถาปัตยกรรม x86 คือการเรียกครั้งใหม่ได้ก้อนที่อยู่ต่ำลงไปเรื่อย ๆ ภายในก้อนเดียวกัน ตัวแปรภายในจึงอยู่ใต้ที่อยู่ขากลับ และการคัดลอกลง buffer ซึ่งเขียนจากที่อยู่ต่ำขึ้นไปหาที่อยู่สูง ก็เขียนเข้าหาที่อยู่ขากลับ

ข้อมูลควบคุมที่เจอบ่อยมีสี่ชนิด

- **return address** — ที่อยู่ที่ฟังก์ชันจะกลับไปเมื่อทำงานเสร็จ ถูกเก็บไว้บน stack ทุกครั้งที่เรียกฟังก์ชัน
- **function pointer** — ตัวแปรที่เก็บที่อยู่ของฟังก์ชัน
- **exception handler** — ที่อยู่ของโค้ดที่จะรันเมื่อเกิดข้อผิดพลาด
- **virtual method** — ในภาษาเชิงวัตถุ วัตถุเก็บตัวชี้ไปยังตารางที่อยู่ของเมธอด

ทั้งสี่ชนิดอยู่ปนกับข้อมูลธรรมดาใน <Term en="Stack Frame" th="พื้นที่บน stack ของการเรียกฟังก์ชันหนึ่งครั้ง" /> ตัวอย่างของ Michael Howard จาก Microsoft คือฟังก์ชันนี้

```c
void func(char *p, int i) {
    int j = 0;
    CFoo foo;
    int (*fp)(int) = &func;
    char b[128];
    strcpy(b,p);
}
```

ในเฟรมนี้มีข้อมูลควบคุมอยู่สองตัวนอกจากที่อยู่ขากลับ `fp` เก็บที่อยู่ของฟังก์ชัน ส่วน `foo` เป็นวัตถุของคลาส `CFoo` ซึ่งเก็บตัวชี้ไปยังตารางที่อยู่ของ virtual method ของคลาสนั้นไว้ในตัว ถ้า `p` ชี้ไปที่ข้อมูลที่ยาวเกิน 128 ไบต์ `strcpy` จะเขียนต่อเลย `b` ไปทางที่อยู่สูง

การโจมตีจึงแบ่งตามช่องที่ถูกทับได้สามแบบ

- **Return-address attack** หรือ <Term en="Stack Smashing" th="การทุบ stack" /> — ทับที่อยู่ขากลับ พอฟังก์ชันจบ โปรแกรมกลับไปที่ที่อยู่ใหม่แทนที่จะกลับไปหาผู้เรียก
- **Function-pointer attack** — ทับ `fp` ครั้งต่อไปที่โปรแกรมเรียกผ่าน `fp` ก็ไปที่อื่น
- **Frame-pointer attack** — ทับ saved EBP ทุกค่าที่ผู้เรียกอ่านหลังจากนั้นจึงมาจากที่ที่ผู้โจมตีเลือก EBP คือ register ที่ x86 แบบ 32 บิตใช้เป็น <Term en="Frame Pointer" th="ตัวชี้ไปยัง stack frame ที่กำลังทำงาน" /> ฟังก์ชันหาตัวแปรของตัวเองโดยนับระยะจากค่านี้ ตอนเข้าฟังก์ชัน ค่า EBP ของผู้เรียกถูกเก็บไว้บน stack (saved EBP) แล้วถูกโหลดคืนตอนกลับ

### เขียนทับตัวชี้ข้อมูล — ล้นสองขั้น

การโจมตีอีกแบบไม่ได้ทับข้อมูลควบคุมตรง ๆ แต่ทับ **ตัวชี้ข้อมูล** ธรรมดาที่อยู่ติดกับ buffer

```c
int vulnerable(char **argv) {
    int x;
    char *ptr;
    char buffer[30];
    ptr=buffer;
    printf("ptr %p - before\n",ptr);
    strcpy(ptr,argv[1]);
    printf("ptr %p - after\n",ptr);
    strcpy(ptr,argv[2]);
    printf("done\n");
}
```

`strcpy` ครั้งแรกล้นจาก `buffer` ไปทับ `ptr` ซึ่งอยู่ติดกัน พอถึงครั้งที่สอง โปรแกรมเขียนลงที่ที่ `ptr` ชี้อยู่ ซึ่งตอนนี้เป็นที่ที่ผู้โจมตีเลือกเอง `printf` ก่อนและหลัง `strcpy` ครั้งแรกพิมพ์ค่าของ `ptr` ออกมาให้เห็นว่ามันถูกเปลี่ยนไปแล้ว ผลคือ **ตัวชี้ที่เขียนทับได้หนึ่งตัวกลายเป็นการเขียนลงที่ไหนก็ได้ในหน่วยความจำ** และเป้าหมายมักเป็นข้อมูลควบคุมที่อยู่ไกลออกไป

เป้าที่นิยมคือ <Term en="Global Offset Table (GOT)" th="ตารางที่อยู่ของฟังก์ชันในไลบรารี" /> โปรแกรมไม่รู้ล่วงหน้าว่าฟังก์ชันอย่าง `printf` ในไลบรารีจะถูกโหลดไปอยู่ที่ไหน จึงเรียกผ่านตารางนี้ ช่องหนึ่งช่องในตารางเรียกว่า **jump slot** ซึ่งก็คือ function pointer ตัวหนึ่ง ถ้าช่องของ `printf` ถูกเปลี่ยน ทุกครั้งที่โปรแกรมเรียก `printf` หลังจากนั้นจะไปที่อื่น หนอน **SLAPPER** ที่เจาะ Apache ใช้การโจมตีแบบนี้

จุดที่ต้องจำไว้ใช้ในส่วนที่ 4 คือ **การเขียนครั้งที่สองไม่ได้ล้นต่อเนื่องจาก buffer** มันกระโดดข้ามทุกอย่างที่อยู่ระหว่าง buffer กับเป้าหมายไปเลย

### ช่องโหว่สองแบบที่ทำงานคล้ายกัน

- <Term en="Integer Overflow" th="จำนวนเต็มล้นหลัก" /> — นับเป็นส่วนย่อยของ buffer overflow การคำนวณขนาดล้นหลักแล้ววนกลับเป็นค่าน้อย การตรวจความยาวจึงผ่าน แต่การคัดลอกจริงเขียนเกินที่จอง ตัวอย่างเสริม: โปรแกรมจองที่ `len + 1` ไบต์ไว้เผื่อ `\0` ถ้า `len` เป็นจำนวนเต็มไม่มีเครื่องหมายขนาด 32 บิตที่มีค่า 4,294,967,295 ผลบวกจะวนกลับเป็น `len+1=0` ตามที่โปรแกรม C ทดสอบพิมพ์ออกมา โปรแกรมจึงจองที่ 0 ไบต์ แต่ยังคัดลอกตาม `len`
- **ช่องโหว่ของ `printf`** — โปรแกรมส่งสตริงจากผู้ใช้เข้าไปเป็น format string ของ `printf` ตรง ๆ ผู้ใช้จึงสั่งให้ `printf` อ่านหรือเขียนหน่วยความจำได้ผ่านตัวกำหนดรูปแบบ

### สองเงื่อนไขที่การโจมตีต้องมีครบ

การโจมตีด้วย buffer overflow ต้องได้ทั้งสองข้อ

1. **มีโค้ดหรือข้อมูลที่จะให้รัน** — ฉีดเข้าไปเองพร้อมกับข้อมูลที่ล้น หรือรู้ที่อยู่ของโค้ดที่มีอยู่ในหน่วยความจำแล้ว
2. **พาโปรแกรมไปรันสิ่งนั้น** — เปลี่ยนข้อมูลควบคุมให้ชี้ไปหามัน

ข้อสองคือนิยามของการโจมตีที่บทนี้สนใจ

> **Definition 2:** A buffer-overflow attack on control data is an attack that (possibly implicitly) uses memory-manipulating operations to overflow a buffer which results in the modification of an address to point to malicious or unexpected code.
>
> การโจมตีข้อมูลควบคุมด้วย buffer overflow คือการโจมตีที่ใช้คำสั่งจัดการหน่วยความจำ (อาจโดยอ้อม) ทำให้ buffer ล้น จนที่อยู่ตัวหนึ่งถูกเปลี่ยนให้ชี้ไปหาโค้ดอันตรายหรือโค้ดที่ไม่ควรถูกรัน

ข้อสังเกตที่ใช้ต่อทั้งบทคือ **buffer ที่ล้นเข้ามาเป็นของที่ส่งมาจาก domain อื่นเสมอ** <Term en="Domain" th="ขอบเขตของโพรเซส" /> คือขอบเขตเมื่อมองจากโพรเซสที่กำลังทำงานอยู่ ของจาก domain อื่นคือของที่มาจากนอกโพรเซส เช่นจากเครื่องอื่นหรือโพรเซสอื่น เช่นข้อมูลจากเครือข่าย ไฟล์ หรือคีย์บอร์ด ถ้ามันมาจากในโพรเซสเองก็ไม่มีเจตนาร้ายให้กลัว

<Quiz question="ถ้าคอมไพเลอร์วาง j ของฟังก์ชัน func ไว้ติดเหนือ b พอดี และ strcpy ล้นมาแค่ 4 ไบต์ ทับแค่ j ซึ่งเป็น int โปรแกรมถูกยึดได้ไหม">
`j` เป็นตัวเลขธรรมดา ไม่ใช่ที่อยู่ของโค้ด โปรแกรมไม่ได้กระโดดตาม `j` ไปไหน

คำตอบคือ **ทางเดินของโปรแกรมไม่เปลี่ยน แต่ผลลัพธ์อาจผิด** เหมือนอายุที่กลายเป็น 49 ซึ่งยังเป็นปัญหาความถูกต้อง แต่ไม่เข้านิยาม Definition 2

คำตอบที่ผิดบ่อยคือ "ไม่มีผลอะไรเลย" ถ้า `j` เป็นค่าที่ใช้ตัดสินสิทธิ์ เช่นตัวแปร `is_admin` การเปลี่ยนมันอันตรายมาก แม้จะไม่ได้เปลี่ยนที่อยู่ไหนเลย การโจมตีแบบนี้อยู่นอกขอบเขตของวิธีป้องกันส่วนใหญ่ในบทนี้ รวมถึง Secure Bit ด้วย

## ส่วนที่ 3 — แผนที่ของวิธีป้องกัน

### สามตระกูลใหญ่

วิธีป้องกัน buffer overflow แบ่งตามจังหวะที่มันเข้าไปขวางได้สามตระกูล

| ตระกูล | ทำงานเมื่อไร | แบบย่อย |
| --- | --- | --- |
| <Term en="Static Analysis" th="การวิเคราะห์โค้ดโดยไม่รัน" /> | ก่อนเอาโปรแกรมไปใช้ | Lexical Analysis, Semantic Analysis |
| <Term en="Dynamic Solution" th="วิธีที่ตรวจขณะโปรแกรมรัน" /> | ระหว่างโปรแกรมรัน | Address Protection, Input Protection, Bounds Checking, Obfuscation |
| <Term en="Isolation" th="การกักบริเวณ" /> | หลังการโจมตีสำเร็จแล้ว | Non-executable, Sandboxing |

ตระกูลแรกพยายามไม่ให้มีช่องโหว่ ตระกูลที่สองจับการล้นหรือการใช้ค่าที่ถูกล้นทับ ตระกูลที่สามยอมว่าการโจมตีอาจสำเร็จ แต่จำกัดว่าโค้ดที่ได้มาทำอะไรได้บ้าง

### Static Analysis — จับก่อนใช้งาน แต่จับได้แค่ที่รู้จัก

Static analysis ตรวจโค้ดก่อนเอาไปใช้ ข้อจำกัดของมันมีสามข้อ

- **จับได้แค่ปัญหาที่รู้จักแล้ว** ช่องโหว่รูปแบบใหม่ที่ไม่อยู่ในกฎก็ผ่านไปได้
- **ไม่มีข้อมูลตอนรัน** ไม่รู้ว่า input จริงยาวเท่าไร
- **เตือนผิดได้** โค้ดที่ปลอดภัยก็ถูกเตือน จนคนเลิกอ่านคำเตือน

เครื่องมือที่ใช้กันมีหลายระดับ สไลด์บอกแค่ว่า STOBO เป็น profiling tool คำอธิบายว่ามันทำงานยังไงในตารางเป็นข้อมูลเสริม

| เครื่องมือ | วิธี |
| --- | --- |
| ITS4 | จับคู่สตริง หาชื่อฟังก์ชันอันตราย (lexical) |
| FlawFinder, RATS | สแกนหาฟังก์ชันอันตรายแบบเดียวกัน |
| Splint, BOON | lint ที่เพิ่มการตรวจด้านความปลอดภัย วิเคราะห์ความหมายของโค้ด (semantic) |
| STOBO | profiling tool ใส่โค้ดที่จดขนาดของทุก buffer ลงในโปรแกรม แล้วระหว่างรันทดสอบ ตรวจอาร์กิวเมนต์ของฟังก์ชันอย่าง `strcpy` ว่าปลายทางจุพอไหม จึงเตือนได้แม้ input ทดสอบไม่ได้ล้นจริง |
| LibSafe | ไลบรารี C มาตรฐานรุ่นที่ปลอดภัยขึ้น ซึ่งแทน `strcpy` ตอนรัน ไม่ได้ตรวจโค้ดก่อนใช้ (ส่วนที่ 4) |

การตรวจระดับ lexical ทำงานแบบนี้ทุกวันในเครื่องมือที่ทุกคนใช้อยู่ ตอน compile ตัวอย่างอายุในส่วนที่ 2 ด้วย gcc 15.2 ตัว linker เตือนจากชื่อฟังก์ชันอย่างเดียว

```text
age.c:(.text+0x2f): warning: the `gets' function is dangerous and should not be used.
```

คำอธิบายต่อไปนี้เป็นข้อมูลเสริม มันรู้ว่า `gets` อันตรายเพราะ `gets` ไม่รับขนาดของที่ปลายทางเลย จึงใช้ให้ปลอดภัยไม่ได้ไม่ว่าจะเรียกแบบไหน มาตรฐาน C11 ตัด `gets` ออกไปแล้ว ตัวอย่างนี้ต้องประกาศ `gets` เองถึงจะ compile ผ่าน ส่วน `strcpy` ใช้ปลอดภัยได้ถ้าเช็กความยาวก่อน การเตือนจากชื่ออย่างเดียวจึงต้องเลือกระหว่างเงียบกับเตือนผิด

### สี่คำถามที่วิธีตรวจขณะรันทุกวิธีต้องตอบ

Dynamic solution ทุกแบบในสองส่วนถัดไปทำงานโดยเก็บ <Term en="Metadata" th="ข้อมูลกำกับ" /> เพิ่ม แล้วตรวจมันตอนรัน การเทียบวิธีพวกนี้จึงถามคำถามเดียวกันได้สี่ข้อ

1. **Assumptions** — มันสมมติอะไรเกี่ยวกับการโจมตี เช่นสมมติว่าการล้นเขียนต่อเนื่องจาก buffer
2. **Creation of metadata** — ข้อมูลกำกับถูกสร้างตอนไหน และใครเป็นคนสร้าง
3. **Validation of metadata** — ตรวจตอนไหน และข้อมูลกำกับเองถูกปลอมได้ไหม
4. **Handling of invalid data** — เจอของผิดแล้วทำอะไร หยุดโปรแกรม หรือซ่อมคืน

<Quiz question="เครื่องมือ static analysis ตัวหนึ่งรายงานว่าโปรแกรมของเราไม่มีการเรียก gets, strcpy หรือ sprintf เลย สรุปได้ไหมว่าโปรแกรมไม่มี buffer overflow">
เครื่องมือแบบนี้ตรวจจากรายชื่อฟังก์ชันที่รู้ว่าอันตราย แต่การล้นเกิดได้จากลูปที่เขียนเองด้วย เช่น `for` ที่คัดลอกทีละไบต์แล้วนับเกินไปหนึ่งรอบ ซึ่งไม่มีชื่อฟังก์ชันอันตรายสักตัว

## ส่วนที่ 4 — ปกป้องที่อยู่ไม่ให้ถูกเปลี่ยนโดยไม่มีใครรู้

### สี่วิธีของ Address Protection

<Why>
เราห้าม `strcpy` เขียนเกิน buffer ไม่ได้ ถ้าโปรแกรมเขียนมาผิดแล้ว แต่การล้นจะเป็นอันตรายจริงก็ตอนที่โปรแกรม **ใช้** ที่อยู่ที่ถูกทับ ถ้าจับได้ก่อนจังหวะนั้นว่าที่อยู่ถูกเปลี่ยน โปรแกรมก็หยุดได้ทันก่อนกระโดดไปผิดที่
</Why>

<Term en="Address Protection" th="การปกป้องที่อยู่" /> เก็บข้อมูลเพิ่มอีกชุดคู่กับที่อยู่ที่สำคัญ แล้วตรวจก่อนใช้ ข้อมูลกำกับมีสี่แบบ หลายแบบทำงานทีละ <Term en="Word" th="คำ" /> ซึ่งคือหน่วยข้อมูลที่ตัวประมวลผลอ่านหรือเขียนในครั้งเดียว เช่น 4 ไบต์บน x86 แบบ 32 บิต

| แบบ | ข้อมูลกำกับ | ตัวอย่าง |
| --- | --- | --- |
| **Canary Words** | ค่าเฝ้ายามหน้าที่อยู่ขากลับ | StackGuard, ProPolice |
| **Address Encode** | ตัวที่อยู่เองถูกเข้ารหัส | PointGuard |
| **Copy of Address** | สำเนาของที่อยู่ขากลับ | StackGhost, <Term en="Return Address Stack (RAS)" th="stack ของที่อยู่ขากลับในตัวประมวลผล" />, Split Stack, RAD, DISE, StackShield, SCACHE, LibVerify |
| **Tags** | บิตป้ายบนทุกคำ | IBM System/38 |

### Canary — StackGuard

<Term en="Canary" th="ค่าเฝ้ายาม" /> คือคำหนึ่งคำที่ compiler วางไว้ระหว่าง buffer กับที่อยู่ขากลับตอนเข้าฟังก์ชัน และตรวจว่ายังเป็นค่าเดิมก่อนฟังก์ชันกลับ การล้นที่เขียนจาก buffer ขึ้นไปหาที่อยู่ขากลับต้องเขียนทับ canary ก่อนเสมอ ถ้าค่าเปลี่ยน โปรแกรมหยุดทันทีโดยไม่กระโดดไปตามที่อยู่ขากลับ **StackGuard** ของ Oregon Graduate Institute (Immunix) ทำแบบนี้

<Analogy>
ชื่อมาจากนกคีรีบูนที่คนงานเหมืองถ่านหินหิ้วลงไปด้วย นกตายก่อนคนเมื่อมีแก๊สพิษ คนงานเห็นนกตายก็รู้ว่าต้องออกจากเหมือง นกคือ canary แก๊สที่ลอยมาถึงคือข้อมูลที่ล้นขึ้นมา และการที่คนงานออกจากเหมืองคือโปรแกรมที่หยุดทำงาน

อุปมานี้ใช้ไม่ได้ตรงที่แก๊สฆ่านกได้จากทุกทิศ แต่ canary จับได้เฉพาะการเขียนที่ไล่ทับต่อเนื่องจาก buffer ขึ้นมา การเขียนผ่านตัวชี้ที่กระโดดข้าม canary ไปลงที่ที่อยู่ขากลับตรง ๆ จะไม่แตะ canary เลย
</Analogy>

ค่าของ canary มีหลายแบบ

- **Random canary** — ค่าสุ่มตอนโปรแกรมเริ่ม ผู้โจมตีที่ไม่รู้ค่าก็เขียนค่าเดิมกลับลงไปไม่ได้
- **Terminator canary** — ค่าที่มีไบต์อย่าง `0x00` อยู่ การล้นจะผ่านไปโดยไม่ถูกจับได้ก็ต่อเมื่อเขียน canary กลับเป็นค่าเดิมทุกไบต์ รวมทั้ง `0x00` ด้วย แต่ฟังก์ชันสตริงอย่าง `strcpy` หยุดคัดลอกทันทีที่เขียน `0x00` การล้นด้วย `strcpy` จึงไปไม่ถึงที่อยู่ขากลับซึ่งอยู่เหนือ canary ขึ้นไป แบบที่เป็นศูนย์ทั้งคำเรียกว่า null canary
- **Terminator with diversity canary** — มีชื่ออยู่ในรายการ แต่สไลด์ไม่ได้อธิบายว่ามันต่างจากสองแบบแรกยังไง

**ProPolice** ของ IBM ใช้ canary แบบเดียวกันและมีหัวข้อของตัวเองข้างล่าง ส่วน **MemGuard** ของทีม StackGuard อยู่ในตระกูล address protection เช่นกันแต่ไม่ใช้ canary คำอธิบาย MemGuard ต่อไปนี้เป็นข้อมูลเสริม MemGuard ใช้กลไก virtual memory ทำให้ที่อยู่ขากลับเป็นแบบอ่านอย่างเดียวระหว่างที่ฟังก์ชันทำงาน การเขียนทับจึงถูกตัวประมวลผลจับได้ทันที แลกกับความช้า เพราะสิทธิ์อ่านอย่างเดียวคุมได้ทีละหน้าหน่วยความจำ การเขียนลงคำอื่นที่อยู่หน้าเดียวกับที่อยู่ขากลับ ซึ่งบน stack เกิดตลอดเวลา จึงถูกจับด้วย แล้วต้องให้ซอฟต์แวร์ทำการเขียนนั้นแทนทีละครั้ง

<Example added title="canary ของเครื่องจริงมีไบต์ศูนย์อยู่เสมอ">
บทนี้ไม่ได้แสดงค่า canary จริง โปรแกรมเล็ก ๆ ที่อ่านค่าจาก `%fs:0x28` ซึ่งเป็นที่ที่ gcc บน x86-64 เก็บ canary ของโพรเซส รันสามครั้งได้แบบนี้

```text
canary = 0xe6a17196aabf6200
canary = 0xb34023dca1230a00
canary = 0x5b913e72e766ab00
```

เจ็ดไบต์บนสุดสุ่มใหม่ทุกครั้ง ส่วนไบต์ต่ำสุดเป็น `00` ทุกครั้ง
</Example>

ข้อสรุปจากผลนี้ก็เป็นข้อมูลเสริมเช่นกัน ไบต์ `00` นั้นอยู่ติดกับ buffer และเป็นไบต์แรกที่การล้นต้องเขียนทับ glibc จึงรวม random กับ terminator ไว้ในค่าเดียว คือสุ่มจนเดาไม่ได้ และมีไบต์ศูนย์ที่ `strcpy` เขียนกลับลงไปแล้วเขียนต่อไม่ได้

<Example added title="ล้น 48 ไบต์ใส่ buffer 16 ไบต์ ทั้งแบบมีและไม่มี canary">
บทนี้ไม่ได้รันให้เห็นว่า canary เปลี่ยนผลยังไง `smash.c` คือฟังก์ชันแบบ `func` ในส่วนที่ 2 ที่เหลือแค่ `strcpy` ลง `char b[16]` และรับข้อความ 48 ตัวอักษรเหมือนกันในการ compile สองแบบ

```text
$ gcc -fno-stack-protector -o smash smash.c && ./smash $(python3 -c 'print("A"*48)')
copied 48 bytes
Segmentation fault         (core dumped)
$ gcc -fstack-protector -o smash smash.c && ./smash $(python3 -c 'print("A"*48)')
copied 48 bytes
*** stack smashing detected ***: terminated
Aborted                    (core dumped)
```

แบบไม่มี canary กระโดดไปตามที่อยู่ขากลับที่ถูกทับแล้วค่อยพัง ส่วนแบบมี canary หยุดเองก่อนจะกระโดด

<Detail label="โค้ดของ smash.c และ exit code">
```c
#include <stdio.h>
#include <string.h>
void func(char *p) { char b[16]; strcpy(b,p); printf("copied %zu bytes\n", strlen(p)); }
int main(int argc,char *argv[]) { func(argv[1]); printf("returned normally\n"); return 0; }
```

`echo $?` หลังแต่ละรอบได้ `139` และ `134` ตามลำดับ shell รายงานโปรแกรมที่ตายด้วยสัญญาณเป็น 128 บวกเลขของสัญญาณ 139 คือ 128 + 11 (`SIGSEGV` เข้าถึงหน่วยความจำผิดที่) ส่วน 134 คือ 128 + 6 (`SIGABRT` ซึ่งโค้ดตรวจ canary สั่งให้โปรแกรมหยุดตัวเอง)

ส่งข้อความสั้น 10 ตัวอักษรเข้าไป โปรแกรมพิมพ์ `copied 10 bytes` และ `returned normally` แล้วจบด้วย exit 0
</Detail>
</Example>

ถ้าที่อยู่ขากลับที่ถูกทับชี้ไปที่ที่โค้ดรันได้ แบบแรกจะไม่พังเลยแต่ไปรันโค้ดนั้นแทน ส่วนแบบที่สองไม่มีโอกาสนั้น

สี่คำถามในส่วนที่ 3 ใช้กับ canary ได้แบบนี้

| คำถาม | คำตอบของ canary |
| --- | --- |
| Assumptions | การล้นเขียนต่อเนื่องจาก buffer ขึ้นไปหาที่อยู่ขากลับ |
| Creation of metadata | compiler ใส่โค้ดที่วาง canary ตอนเข้าฟังก์ชัน ค่าของ random canary สุ่มตอนโปรแกรมเริ่ม |
| Validation of metadata | ตรวจครั้งเดียวก่อนฟังก์ชันกลับ ถ้าผู้โจมตีอ่านค่า canary ได้ ก็เขียนค่าเดิมกลับลงไปได้ (ส่วนที่ 7) |
| Handling of invalid data | หยุดโปรแกรมทันที เหมือน `smash` ที่จบด้วย `Aborted` ข้างบน |

รายการของ StackGuard ยังมีคำถาม **Alignment?** ซึ่งสไลด์ไม่ได้ตอบ

### ProPolice — ย้ายตัวแปรที่อันตรายออกจากทางล้น

<Why>
canary ถูกตรวจแค่ตอนฟังก์ชันกำลังจะกลับ ใน `func` ของรูปที่ 1 ตัวชี้ฟังก์ชัน `fp` อยู่เหนือ `b` แต่ต่ำกว่าจุดที่ canary ถูกวางไว้ใต้ที่อยู่ขากลับ การล้นจึงทับ `fp` ได้ และถ้าฟังก์ชันเรียกผ่าน `fp` ก่อนจบ โปรแกรมก็กระโดดไปที่อื่นก่อนที่ canary จะมีโอกาสถูกตรวจ
</Why>

**ProPolice** ของ IBM Research ญี่ปุ่น ใช้ canary แบบเดียวกับ StackGuard ซึ่งมันเรียกว่า **guard** และทำเพิ่มอีกอย่างคือ **จัดลำดับตัวแปรใหม่** โดยวาง stack frame แบบนี้ เรียงจากที่อยู่สูงลงต่ำ

| ช่อง | ทำไมอยู่ตรงนี้ |
| --- | --- |
| arguments (A) | ผู้เรียกวางไว้ |
| return address | ที่ต้องปกป้อง |
| previous frame pointer | ที่ต้องปกป้อง |
| **guard** | การล้นจาก array ต้องผ่านตรงนี้ก่อน |
| arrays (B) | buffer ทั้งหมดรวมกันอยู่ติด guard |
| local variables (C) | ตัวชี้และตัวแปรธรรมดา อยู่ใต้ buffer ทุกตัว |

การล้นเขียนจาก buffer ไปทางที่อยู่สูง ตัวแปรในกลุ่ม C จึงอยู่นอกทางล้นทั้งหมด ถ้าโปรแกรมเมอร์ประกาศตัวชี้ฟังก์ชันไว้ก่อน buffer แบบนี้

```c
int bar() {
    void (* funct2)();
    char buff[80];
}
```

ProPolice จะจัดใหม่ให้เหมือนเขียนว่า

```c
int bar() {
    char buff[80];
    void (* funct2)();
}
```

คือย้าย `funct2` ไปไว้ใต้ `buff` ในหน่วยความจำ `buff` ล้นเท่าไรก็ไม่ถึง `funct2`

ข้อที่ ProPolice ทำไม่ได้คือ **ตัวชี้ที่อยู่ใน struct** ภาษา C กำหนดลำดับของฟิลด์ใน struct ไว้ตายตัวตามที่ประกาศ ถ้า struct มี buffer ตามด้วยตัวชี้ฟังก์ชัน compiler ก็สลับให้ไม่ได้

ลองทายก่อน: compile `age.c` ตัวเดิมด้วย `gcc` เฉย ๆ แล้วพิมพ์ `15` กับ `Krerk.P01` เหมือนเดิม โปรแกรมจะบอกว่าอายุเท่าไร

<Example added title="ตัวอย่างอายุตัวเดิม เมื่อเปิด stack protector">
บทนี้ไม่ได้แสดงผลของการจัดลำดับใหม่กับโปรแกรมจริง

```text
$ gcc -o age age.c && ./age
Enter your age:15
Enter your name:Krerk.P01
-----------
Krerk.P01 is 15 years old
```

gcc บน Ubuntu เปิด `-fstack-protector-strong` ไว้เป็นค่าเริ่มต้น ซึ่งคือ ProPolice รุ่นที่อยู่ใน gcc และ `objdump -d` บอกว่ามันจัดตัวแปรใหม่แบบนี้ โดยวัดระยะจาก `rbp` ซึ่งคือ frame pointer ของ x86-64 ตัวเดียวกับ EBP

| ตัวแปร | `-fno-stack-protector` | ค่าเริ่มต้น (`-fstack-protector-strong`) |
| --- | --- | --- |
| `age` | `rbp-0x4` อยู่เหนือ `name` | `rbp-0x2c` ย้ายลงไปอยู่ใต้ `name` |
| `name` | `rbp-0xc` | `rbp-0x28` |
| `tmp` | `rbp-0x20` | `rbp-0x20` |
| canary | ไม่มี | `rbp-0x8` |

ชื่อยังล้นสองไบต์เท่าเดิม แต่สองไบต์นั้นไปลงที่ `tmp[0]` และ `tmp[1]` ซึ่งโปรแกรมใช้เสร็จไปแล้ว และไม่ไปถึง canary โปรแกรมจึงไม่หยุด
</Example>

### PointGuard — เข้ารหัสตัวชี้

**PointGuard** ของ Oregon Graduate Institute (Immunix) **เข้ารหัสตัวชี้ด้วยกุญแจที่กำหนดไว้ก่อนทุกครั้งที่เก็บลงหน่วยความจำ และถอดรหัสทุกครั้งที่จะใช้** ค่าที่อยู่ในหน่วยความจำจึงไม่ใช่ที่อยู่จริง

ถ้าผู้โจมตีล้นทับตัวชี้ด้วยที่อยู่ที่ตัวเองต้องการ ค่านั้นยังไม่ได้ถูกเข้ารหัส พอโปรแกรมดึงมาใช้ ตัวประมวลผลจะถอดรหัสมันก่อน แล้วได้ที่อยู่สุ่ม ๆ ที่ไม่ใช่ทั้งของเดิมและของผู้โจมตี โปรแกรมจึงไปอ่านข้อมูลมั่ว ๆ หรือพัง แทนที่จะไปถึงข้อมูลของผู้โจมตี

ตัวอย่างเสริม: PointGuard เข้ารหัสด้วยการ XOR กับกุญแจลับ โปรแกรม C เล็ก ๆ ที่ใช้กุญแจ `0x5f3c9a21` เก็บตัวชี้ `0x0804a010` ลงหน่วยความจำเป็น `0x57383a31` และถอดกลับได้ `0x0804a010` ตรงเดิม แต่ค่า `0x41414141` ที่ถูกเขียนทับลงไปตรง ๆ ถอดออกมาเป็น `0x1e7ddb60` ซึ่งไม่ใช่ทั้งของเดิมและของผู้เขียน

คำถามที่วิธีนี้ต้องตอบมีสี่ข้อ

- **Compatibility** — โค้ดที่ไม่ได้ compile ด้วย PointGuard เช่นไลบรารีเก่า อ่านตัวชี้แบบไม่ถอดรหัส
- **Initialization** — กุญแจถูกสร้างตอนไหน และตัวชี้ที่มีอยู่ก่อนกุญแจถูกเข้ารหัสยังไง
- **Performance** — ต้องถอดรหัสทุกครั้งที่ใช้ตัวชี้
- **Encryption Algorithm** — ต้องเร็วพอจะทำทุกครั้งที่แตะตัวชี้ แต่แข็งพอที่ผู้โจมตีจะเดากุญแจไม่ได้

### Copy of Address — เก็บที่อยู่ขากลับไว้อีกที่

ถ้าที่อยู่ขากลับมีสำเนาอยู่ในที่ที่การล้นเอื้อมไม่ถึง ตอนฟังก์ชันกลับก็เทียบสองค่ากันได้ หรือใช้สำเนาแทนไปเลย ระบบในกลุ่มนี้ต่างกันแค่ว่าสำเนาอยู่ที่ไหน

- **Split Stack** (UIUC) — แยก stack เป็นสองอัน **control stack** เก็บที่อยู่ขากลับอย่างเดียว ส่วน **data stack** เก็บพารามิเตอร์ frame pointer และตัวแปร แบบที่ compiler ทำ (compiler-based split stack) data stack ยังมีที่อยู่ขากลับอยู่เหมือนเดิม และ control stack เป็นสำเนา แบบที่ฮาร์ดแวร์ช่วย (architecture-supported split stack) ที่อยู่ขากลับออกจาก data stack ไปเลย buffer ล้นเท่าไรก็ไม่เจอที่อยู่ขากลับ
- **StackGhost** (Purdue) — ใช้ register window คำอธิบายต่อไปนี้เป็นข้อมูลเสริม register window เป็นกลไกของตัวประมวลผล SPARC ซึ่งถือที่อยู่ขากลับไว้ใน register ก่อนจะย้ายลง stack จึงมีจังหวะให้ตรวจหรือเก็บสำเนาของมันไว้
- **SRAS** (UIUC) — ใช้ RAS ซึ่งเป็นวงจรที่ตัวประมวลผลมีอยู่แล้วไว้ทายว่าคำสั่ง return จะกลับไปที่ไหน เอามาเป็นสำเนาไว้ตรวจ ปัญหาคือ RAS มีขนาดจำกัดจึงเต็มได้ (overflow) ถูกอัปเดตตอนทำงานล่วงหน้าแบบ speculative และรับมือกับ <Term en="Non-LIFO Control Flow" th="การไหลที่ไม่ได้กลับตามลำดับเข้าหลังออกก่อน" /> ไม่ได้ คือโค้ดที่ call กับ return ไม่ได้จับคู่กันตามลำดับ ซึ่งส่วนที่ 7 ยกตัวอย่างให้ดู
- **RAD** (State U. of New York at Stony Brook) — เก็บสำเนาไว้ใน **Return Address Repository (RAR)** แบบ MineZone RAR ล้อมด้วยหน้าหน่วยความจำที่ห้ามแตะ ส่วนแบบ Read-only RAR ใช้ `mprotect` ทำให้ RAR เป็นแบบอ่านอย่างเดียว คำถามที่ค้างคือ performance
- **StackShield** (Vendicator) — เก็บสำเนาของที่อยู่ขากลับไว้ แล้วตอนกลับจะคัดลอกสำเนาทับของเดิม หรือเทียบกับสำเนาก็ได้ และบังคับให้การเรียกผ่าน function pointer ไปได้แค่ส่วนโค้ด (text section) ข้อนี้ขัดกับโปรแกรมที่สร้างโค้ดใน <Term en="Heap" th="พื้นที่หน่วยความจำที่จองระหว่างรัน" /> ซึ่งเป็นพื้นที่ที่โปรแกรมขอจองระหว่างรัน เช่นด้วย `malloc` แล้วรันโค้ดนั้นอย่างถูกต้อง เช่น LISP และภาษาเชิงวัตถุบางระบบ
- **LibSafe และ LibVerify** (Bell Labs) — LibSafe แทน `strcpy` และฟังก์ชันพวกเดียวกันด้วยรุ่นที่คำนวณก่อนว่าปลายทางยาวได้แค่ไหน โดยใช้ frame pointer เป็นขอบบน การล้นจึงไปได้ไม่เกิน stack frame ของตัวเอง ส่วน LibVerify แก้ไบนารีของโปรแกรมให้ทุกฟังก์ชันเข้าผ่านโค้ดห่อ ขาเข้าเก็บที่อยู่ขากลับ ขาออกตรวจก่อนกลับ

ชื่อ RAS, DISE และ SCACHE อยู่ในกลุ่มนี้ด้วย แต่สไลด์ไม่ได้ให้รายละเอียดของ DISE และ SCACHE คำอธิบายต่อไปนี้เป็นข้อมูลเสริม DISE (Dynamic Instruction Stream Editing) คือฮาร์ดแวร์ที่แก้สายคำสั่งของโปรแกรมระหว่าง decode ซึ่ง Corliss, Lewis และ Roth นำมาใช้ป้องกันที่อยู่ขากลับ ส่วน SCache เป็น cache ที่เก็บสำเนาแบบอ่านอย่างเดียวของที่อยู่ขากลับไว้ในตัว แล้วเทียบกับค่าที่ดึงจาก stack ตอนกลับ

### Tags — ติดป้ายที่ตัวคำ

แบบสุดท้ายติดบิตหนึ่งบิตให้ทุกคำในหน่วยความจำ บอกว่าคำนั้นเป็นที่อยู่ขากลับหรือ function pointer ตัวประมวลผลจึงรู้ว่าคำไหนห้ามถูกเขียนทับด้วยข้อมูลธรรมดา IBM System/38 ทำแบบนี้ในฮาร์ดแวร์ แนวคิดเดียวกับ [tagged memory ใน Lecture 6](/2110413-csy/lecture-6#tagged-memory) และเป็นญาติใกล้ที่สุดของ Secure Bit ในส่วนที่ 9 ความต่างคือ tag บอกว่าคำไหน **เป็น** ที่อยู่ ส่วน Secure Bit บอกว่าคำไหน **มาจากข้างนอก**

<Quiz question="โปรแกรมหนึ่ง compile ด้วย StackGuard และ ProPolice ฟังก์ชันหนึ่งมีตัวแปร struct ที่ประกาศฟิลด์ char name[16] ตามด้วยตัวชี้ฟังก์ชัน on_done แล้วคัดลอก input ลง name ด้วย strcpy จากนั้นเรียก on_done ก่อนฟังก์ชันจบ ถ้า input ยาวเกิน 16 ไบต์ วิธีไหนจับได้">
ProPolice ย้ายตัวแปรทั้งตัวได้ แต่สลับฟิลด์ใน struct ไม่ได้ `on_done` จึงยังอยู่เหนือ `name` ในทางล้น ส่วน canary อยู่เหนือ struct ทั้งก้อนและถูกตรวจตอนฟังก์ชันกลับ แต่โปรแกรมกระโดดผ่าน `on_done` ที่ถูกทับไปก่อนจังหวะนั้น

คำตอบคือ **ไม่มีวิธีไหนจับได้** โปรแกรมไปที่ที่ค่าใหม่ของ `on_done` ชี้ ก่อนที่ canary จะถูกตรวจ

คำตอบที่ผิดบ่อยคือ "canary จับได้ เพราะการล้นเขียนต่อเนื่องจาก buffer" การล้นต่อเนื่องจริง และถ้ายาวพอก็จะทับ canary ด้วย แต่การตรวจเกิดตอนกลับ ซึ่งช้าไปแล้ว
</Quiz>

## ส่วนที่ 5 — ติดป้าย input ตรวจขอบเขต และสุ่มที่อยู่

### Input Protection — ห้ามใช้ input เป็นข้อมูลควบคุม

<Why>
ข้อสังเกตในส่วนที่ 2 บอกว่าของที่ล้นเข้ามามาจาก domain อื่นเสมอ ถ้าตัวประมวลผลจำได้ว่าคำไหนมาจากข้างนอก มันไม่ต้องสนใจเลยว่าคำนั้นไปลงที่ไหน แค่ไม่ยอมใช้คำนั้นเป็นที่อยู่ที่จะกระโดดไปหา
</Why>

<Term en="Input Protection" th="การปกป้องด้วยการติดป้าย input" /> มีกฎข้อเดียวคือ **input ห้ามถูกใช้เป็นข้อมูลควบคุม** ข้อมูลที่เข้ามาจาก domain ที่ไม่น่าไว้ใจถูกติดป้าย หรือที่เรียกว่า <Term en="Taint" th="ทำเครื่องหมายว่าแปดเปื้อน" /> แล้วป้ายนั้นติดไปกับค่าทุกครั้งที่ถูกคัดลอกหรือคำนวณต่อ ระบบในกลุ่มนี้ต่างกันสองจุด คือติดป้ายที่ขอบเขตไหน และล้างป้ายเมื่อไร

| ระบบ | ติดป้ายตรงไหน (Boundary) | ล้างป้ายเมื่อไร (Untaint) |
| --- | --- | --- |
| **Minos** | ใช้ segmentation แยก | ตอนสร้างข้อมูล (creation time) |
| **Tainted pointer** | ฟังก์ชัน I/O ของ SimpleScalar ซึ่งเป็นโปรแกรมจำลองตัวประมวลผลแบบ RISC | เมื่อค่าผ่านคำสั่ง `CMP` หรือ `XOR` |
| **Dynamic Flow Tracking** | ฟังก์ชัน I/O ของ SimpleScalar | เมื่อค่าผ่านคำสั่ง `XOR` |

การล้างป้ายมีไว้ให้โปรแกรมที่ตรวจ input แล้วใช้มันต่อได้ `CMP` คือการเทียบค่า ระบบจึงถือว่าค่าที่ถูกเทียบแล้วผ่านการตรวจมาแล้ว ส่วน `XOR` ของ register กับตัวเองให้ศูนย์เสมอ ผลจึงไม่ขึ้นกับ input เลย ราคาของกฎนี้คือการล้างป้ายผิดที่ ค่าที่ถูกเทียบแล้วไม่ได้แปลว่าปลอดภัยเสมอไป

### Bounds Checking — ทุกการเข้าถึงต้องรู้ขอบ

<Term en="Bounds Checking" th="การตรวจขอบเขต" /> ตอบปัญหาตรงที่สุด คือตรวจทุกครั้งที่เขียนว่ายังอยู่ใน buffer หรือเปล่า ทุก buffer ต้องถูกประกาศพร้อมฐาน (base) และขอบ (boundary) ซึ่งเก็บไว้ในตารางสัญลักษณ์ หรือใน **segment descriptor table** ของตัวประมวลผล อีกแบบคือ **enhanced pointer** ที่ตัวชี้หนึ่งตัวเก็บสามค่า คือ base, ค่าตัวชี้ และ limit ของ storage object ที่มันชี้อยู่

ตัวประมวลผลที่ทำแบบนี้ในฮาร์ดแวร์คือ Intel IA-32 ผ่าน segmentation และ Intel iAPX 432 (I-432) ซึ่งต้องประกาศขอบเขตให้ **ทุกตัวแปร** รวมทั้ง int และ float ด้วย เหตุผลคือการเขียนผ่านตัวชี้ไปลงตัวแปรตัวไหนก็ได้ ถ้าตัวแปรตัวไหนไม่มีขอบเขตกำกับ การเขียนที่เลยเข้าไปในตัวนั้นก็ตรวจไม่ได้

```c
char *a;
char b[10];
a = b;
for (a=b; a<&b[10]; a++)
    *a='0';
b[11]=10;
```

ตัวชี้ `a` รับ base และ limit ของ `b` มาด้วย ลูปเขียนได้ครบสิบช่องเพราะอยู่ในขอบ แต่ `b[11]=10;` อยู่นอกขอบจึงถูกจับตอนรัน

บรรทัดที่สามในสไลด์เขียนว่า `*a = &b;` ซึ่ง compile ไม่ผ่าน gcc 15.2 ตอบว่า `error: assignment to 'char' from 'char (*)[10]' makes integer from pointer without a cast` หน้านี้จึงใช้ `a = b;` ซึ่งตรงกับเจตนาของตัวอย่าง

ราคาของการตรวจแบบนี้คือ **ช้าลงมากกว่า 30 เท่า**

### Obfuscation — ทำให้เดาที่อยู่ไม่ได้

ผู้โจมตีต้องรู้ที่อยู่ของสิ่งที่จะให้โปรแกรมกระโดดไปหา <Term en="Address Obfuscation" th="การพรางที่อยู่" /> ของ Stony Brook จึงทำให้ที่อยู่เปลี่ยนไปทุกครั้งที่รัน ด้วยสามวิธี

- สุ่ม base address ของแต่ละส่วนของหน่วยความจำ คือ stack, heap, BSS ซึ่งเก็บตัวแปร global ที่ไม่ได้ให้ค่าเริ่มต้น, data ซึ่งเก็บตัวแปร global ที่มีค่าเริ่มต้น และ text ซึ่งเป็นส่วนโค้ดแบบอ่านอย่างเดียว
- สลับลำดับของตัวแปรและฟังก์ชัน
- เว้นช่องว่างขนาดสุ่มระหว่างวัตถุ เช่นระหว่าง buffer กับที่อยู่ขากลับ ผู้โจมตีจึงไม่รู้ว่าต้องล้นกี่ไบต์ถึงจะถึง

ปัญหาของมันคือหน่วยความจำแตกเป็นชิ้น (fragmentation) และโปรแกรมที่ฝังที่อยู่ตายตัวไว้ทำงานไม่ได้ (compatibility) วิธีที่คล้ายกันและใช้กันแพร่หลายคือ <Term en="Address Space Layout Randomization (ASLR)" th="การสุ่มผังหน่วยความจำ" /> ของ PaX ข้อมูลเสริมคือ PaX เป็นชุดแก้ kernel ของ Linux ที่เพิ่มการป้องกันหน่วยความจำ รวมทั้ง ASLR และการห้ามรันโค้ดในหน่วยความจำส่วนข้อมูล

<Example added title="ASLR บน Linux ปัจจุบัน">
บทนี้ไม่ได้แสดง ASLR ทำงานจริง โปรแกรมนี้พิมพ์ที่อยู่ของตัวแปรบน stack, ก้อนหน่วยความจำจาก `malloc` และฟังก์ชัน `main` รันสามครั้งตามปกติ แล้วอีกสองครั้งด้วย `setarch -R` ซึ่งปิดการสุ่มเฉพาะโปรแกรมนั้น

```text
$ ./aslr; ./aslr; ./aslr
stack 0x7ffcd2bd72ec  heap 0x5d11dbd01010  code 0x5d11d9834189
stack 0x7ffeeacdb0bc  heap 0x59af62b7f010  code 0x59af32beb189
stack 0x7ffe996e9acc  heap 0x56ff9be40010  code 0x56ff83379189
$ setarch -R ./aslr; setarch -R ./aslr
stack 0x7fffffffd15c  heap 0x555555559010  code 0x555555555189
stack 0x7fffffffd15c  heap 0x555555559010  code 0x555555555189
```

ทั้งสามส่วนย้ายที่ทุกครั้ง แต่สามหลักท้ายของ heap และ code ไม่เปลี่ยน เพราะการสุ่มย้ายทีละหน้าหน่วยความจำขนาด 4 KB
</Example>

### ทำให้ฉีดโค้ดไม่ได้ — ISR และ SPEF

อีกสองวิธีไม่ได้ซ่อนที่อยู่ แต่ทำให้โค้ดที่ผู้โจมตีฉีดเข้ามารันไม่ได้

- <Term en="Instruction-Set Randomization (ISR)" th="การสุ่มชุดคำสั่ง" /> ของ Columbia U. และ Drexel U. — XOR ทุกคำสั่งของโปรแกรมด้วยกุญแจประจำโพรเซส ตัวประมวลผล XOR กลับก่อนรัน โค้ดที่ฉีดเข้ามาไม่ได้ถูก XOR ไว้ล่วงหน้า พอถูก XOR กลับจึงกลายเป็นคำสั่งมั่ว ๆ คำถามที่ค้างคือไลบรารีที่หลายโพรเซสใช้ร่วมกันจะใช้กุญแจของใคร และการโจมตีที่ไม่ได้ฉีดโค้ดแต่เปลี่ยนข้อมูลจะถูกจับได้ยังไง
- **SPEF** หรือ Secure Program Execution Framework ของ Microsoft และ UCLA — เข้ารหัสโปรแกรมตอนติดตั้ง แล้วถอดรหัสและเรียงคำสั่งคืนใน instruction cache ตอนรัน โค้ดที่ไม่ได้ผ่านการติดตั้งจึงรันไม่ได้ คำถามที่ค้างคือ performance และข้อมูลที่ไม่ใช่โค้ด

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ถ้าทำให้ผู้โจมตีฉีดโค้ดเข้ามาไม่ได้ ก็โจมตีด้วย buffer overflow ไม่ได้แล้ว**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะภาพจำของการโจมตีคือการส่งโค้ดอันตรายเข้าไปพร้อมกับข้อมูลที่ล้น และ ISR กับ SPEF ก็ปิดทางนั้นได้จริง

สิ่งที่ถูกต้องคือ **เงื่อนไขข้อแรกในส่วนที่ 2 มีสองทาง** คือฉีดโค้ดเข้าไปเอง หรือรู้ที่อยู่ของโค้ดที่มีอยู่ในหน่วยความจำแล้ว ไลบรารีมาตรฐานที่ทุกโปรแกรมโหลดมีฟังก์ชันที่ทำอะไรได้แทบทุกอย่างอยู่แล้ว ผู้โจมตีแค่ต้องเปลี่ยนที่อยู่ขากลับให้ชี้ไปหาฟังก์ชันพวกนั้น ไม่มีคำสั่งไหนของผู้โจมตีให้ ISR หรือ SPEF จับ ความยากในการฉีดโค้ดจึงไม่ได้ป้องกันระบบจาก buffer overflow
</Pitfall>

<Quiz question="เครื่องหนึ่งเปิด ASLR ไว้ และใช้ ISR ด้วย ผู้โจมตีส่งข้อมูลเข้าไปให้ล้นตัวแปร is_admin ที่อยู่ติดกับ buffer ทั้งสองวิธีช่วยได้ไหม">
ASLR ซ่อนที่อยู่ ซึ่งมีผลเมื่อผู้โจมตีต้องเขียนที่อยู่ลงไป ISR ทำให้โค้ดที่ฉีดเข้ามารันไม่ได้ แต่การทับ `is_admin` ไม่ต้องรู้ที่อยู่ของอะไรเลย เพราะตัวแปรอยู่ติดกับ buffer เสมอไม่ว่า stack จะย้ายไปไหน และไม่ได้ฉีดโค้ดเลยสักบรรทัด

## ส่วนที่ 6 — กักบริเวณ: ยอมให้ล้น แต่จำกัดผล

<Why>
สมมติว่าทุกการตรวจในส่วนที่ 4 และ 5 พลาดหมด ที่อยู่ขากลับถูกทับโดยไม่มีใครจับได้ และโปรแกรมกำลังรันโค้ดที่ผู้โจมตีเลือก สิ่งที่ยังทำได้คือขีดเส้นว่าโค้ดนั้นแตะอะไรได้บ้าง
</Why>

Isolation ไม่พยายามจับการล้นเลย แต่จำกัดว่าโค้ดที่ได้จากการโจมตีทำอะไรได้ มีสามแบบ

- **จำกัดการรันโค้ด** — <Term en="Non-Executable Memory (NX)" th="หน่วยความจำที่ห้ามรันเป็นโค้ด" /> ห้ามรันคำสั่งจาก stack หรือหน่วยความจำส่วนข้อมูล ทำได้ทั้งในซอฟต์แวร์และฮาร์ดแวร์ และมีแบบที่ป้องกัน kernel ด้วย (kernel NX)
- **กัก process ทั้งตัวใน sandbox** — ห้ามโพรเซสแตะทรัพยากรบางอย่างของระบบตามนโยบายที่ตั้งไว้ก่อน ตัวอย่างคือ TCPA หลักการเดียวกับ [sandbox ใน Lecture 6](/2110413-csy/lecture-6#sandbox) ข้อมูลเสริมคือ TCPA (Trusted Computing Platform Alliance) เป็นกลุ่มบริษัทที่ Compaq, HP, IBM, Intel และ Microsoft ตั้งขึ้นในปี 1999 เพื่อกำหนดมาตรฐานแพลตฟอร์มที่เชื่อถือได้ ภายหลังถูกแทนที่ด้วย Trusted Computing Group (2003) ซึ่งรับมาตรฐานของ TCPA ไปดูแลต่อ
- **ติดตั้งโค้ดและสภาพแวดล้อมตอนรันอย่างปลอดภัย** — SPEF ในส่วนที่ 5

NX มีคำถามสามข้อที่มันตอบไม่ได้

- **Heap-based attack** — NX ไม่ได้กันการล้นเลย มันกันแค่การรันคำสั่งจากหน้าหน่วยความจำที่ห้ามรัน NX แบบที่ห้ามแค่ stack จึงยังปล่อยให้โค้ดที่ถูกฉีดไว้ใน heap รันได้
- **โปรแกรมที่ต้องรันโค้ดบน stack จริง ๆ** — โปรแกรมบางแบบสร้างโค้ดบน stack หรือ heap แล้วรันอย่างถูกต้อง NX ทำให้โปรแกรมพวกนี้พัง
- **การโจมตีที่ไม่ได้ฉีดโค้ด** — แบบเดียวกับใน pitfall ของส่วนที่ 5 NX ไม่มีอะไรให้จับ

### LaGrande และ NGSCB — แยก domain ด้วยฮาร์ดแวร์

LaGrande ของ Intel และ NGSCB ของ Microsoft คือแพลตฟอร์มที่ฮาร์ดแวร์ช่วยทำ sandbox โดยแยก domain ออกจากกัน (domain separation)

บน LaGrande ซอฟต์แวร์แบ่งเป็นสองฝั่ง ฝั่ง **Standard partition** รันแอปบนระบบปฏิบัติการตามปกติ ฝั่ง **Protected partition** รัน applet ซึ่งคือโปรแกรมเล็ก ๆ ที่ทำงานเฉพาะอย่าง บน kernel ของตัวเองในหน่วยความจำที่ถูกกันไว้ (protected memory) และ applet ฝั่งนี้ยังขอใช้ทรัพยากรฝั่ง Standard ได้ ทั้งสองฝั่งตั้งอยู่บน **Domain Manager** ซึ่งเป็นตัวแยกสองฝั่งออกจากกัน และใต้นั้นคือฮาร์ดแวร์ของ LaGrande ได้แก่ CPU และ chipset ที่รองรับ LT, protected I/O และ TPM ซึ่งช่วยกันการเข้าถึงทรัพยากรและทำ attestation ข้อมูลเสริมคือ LT ย่อจาก LaGrande Technology ซึ่งภายหลัง Intel เปลี่ยนชื่อเป็น Trusted Execution Technology (TXT) ส่วน TPM (Trusted Platform Module) คือชิปตามมาตรฐานของ Trusted Computing Group ที่เก็บกุญแจและบันทึกค่าที่วัดได้จากซอฟต์แวร์ที่บูตขึ้นมา

NGSCB มีสี่ความสามารถ

- **Strong process isolation** — โพรเซสหนึ่งแตะหน่วยความจำของอีกโพรเซสไม่ได้
- **Sealed storage** — ข้อมูลที่เก็บไว้ถูกผูกกับโปรแกรมที่เก็บ โปรแกรมอื่นเปิดไม่ได้
- **Secure user interface** — ทางเชื่อมระหว่างผู้ใช้กับโปรแกรมที่โปรแกรมอื่นดักไม่ได้
- **Attestation** — พิสูจน์ให้เครื่องอื่นเห็นว่ากำลังรันซอฟต์แวร์อะไรอยู่

Secure Bit วางตัวเป็นส่วนเสริมของสองระบบนี้ ไม่ใช่ของแทน คำถามที่ตามมาคือ **trusted เท่ากับ secure หรือเปล่า** โพรเซสที่ถูกแยกไว้อย่างดีและพิสูจน์ได้ว่าเป็นโปรแกรมที่ถูกต้อง ยังมี buffer overflow อยู่ข้างในได้ การแยก domain กันไม่ให้ความเสียหายลามออกไป แต่ไม่ได้กันการถูกยึดภายใน domain นั้นเอง

<Quiz question="เว็บเซิร์ฟเวอร์ตัวหนึ่งรันใน sandbox ที่ห้ามแตะไฟล์ทุกไฟล์นอกโฟลเดอร์ของเว็บ แล้วถูกยึดด้วย buffer overflow ผู้โจมตีทำอะไรได้บ้าง">
sandbox จำกัดตามนโยบายของโพรเซส ไม่ได้ดูว่าใครเป็นคนสั่ง โค้ดที่ผู้โจมตีพาโปรแกรมไปรันจึงได้สิทธิ์เท่ากับเว็บเซิร์ฟเวอร์ทุกประการ

คำตอบคือ **ทำได้ทุกอย่างที่เว็บเซิร์ฟเวอร์ทำได้** อ่านและแก้ไฟล์ในโฟลเดอร์เว็บ ส่งข้อมูลออกทางเครือข่าย และเห็นข้อมูลของผู้ใช้ทุกคนที่เชื่อมต่อเข้ามา แต่แตะไฟล์ระบบนอกโฟลเดอร์นั้นไม่ได้

คำตอบที่ผิดบ่อยคือ "ทำอะไรไม่ได้ เพราะอยู่ใน sandbox" ซึ่งลืมว่า isolation ยอมให้การโจมตีสำเร็จตั้งแต่แรก มันแค่ขีดเส้นว่าความเสียหายไปได้ไกลแค่ไหน
</Quiz>

## ส่วนที่ 7 — ทำไมยังไม่มีวิธีไหนปิดเรื่องนี้ได้

### สี่จุดที่วิธีป้องกันพลาด

วิธีป้องกันในสามส่วนที่ผ่านมาพลาดได้สี่ทาง

- **Pitfalls** — ช่องโหว่ในตัววิธีเอง มีสองแบบ
  - **ข้อสมมติไม่พอ (insufficient assumptions)** — canary สมมติว่าการล้นเขียนต่อเนื่องจาก buffer หนอน SLAPPER ใช้การเขียนผ่านตัวชี้ ซึ่งไม่ได้ล้นต่อเนื่องไปหาเป้าหมายเลย ข้อสมมตินั้นจึงไม่จริง canary ยังเป็นค่าเดิมทุกไบต์ วิธีที่เทียบที่อยู่ขากลับกับสำเนา เช่น split stack จับการเขียนผ่านตัวชี้ได้เฉพาะเมื่อเป้าหมายคือที่อยู่ขากลับ แต่ SLAPPER เขียนลงช่อง jump slot ใน GOT จึงหลุดวิธีกลุ่มนี้ไปด้วย
  - **ปกป้องข้อมูลกำกับไม่พอ (insufficient protection of metadata)** — ถ้าผู้โจมตีอ่านหรือเขียนทับ canary หรือสำเนาของที่อยู่ได้ การตรวจก็ไม่มีความหมาย
- **Performance** — bounds checking ช้าลงกว่า 30 เท่า
- **Compatibility และ transparency** — ต้องใช้กับโปรแกรมเดิมได้โดยไม่ต้องแก้ ซึ่งรวมถึงโปรแกรมที่ไหลแบบ non-LIFO ในหัวข้อโปรแกรมที่ไม่ได้กลับตามลำดับข้างล่าง
- **Deployment และ cost** — ต้อง compile ใหม่ ติดตั้งไลบรารีใหม่ หรือเปลี่ยนฮาร์ดแวร์แค่ไหน

### ข้อมูลกำกับต้องใช้ที่เท่าไร

ทุกวิธีใน dynamic solution ต้องเก็บข้อมูลกำกับเพิ่ม และขนาดของมันต่างกันมาก

| วิธี | ข้อมูลกำกับ | จ่ายเมื่อไร |
| --- | --- | --- |
| Segmentation | descriptor ขนาด 64 บิตบน IA-32 และ 128 บิตบน I-432 ตัวแปรละหนึ่ง descriptor | ทุกตัวแปร |
| StackGuard | canary หนึ่งคำ | ทุกครั้งที่เรียกฟังก์ชัน |
| Secure Bit | 1 บิตต่อหนึ่งคำของหน่วยความจำ (ส่วนที่ 9) ซึ่งอาจเป็นขั้นต่ำที่เป็นไปได้ | ครั้งเดียว ตอนเพิ่มบิตเข้าไปในฮาร์ดแวร์ |

คำถามที่ต้องตอบต่อสำหรับ Secure Bit คือหนึ่งบิตพอจะได้ผลจริงไหม (effectiveness) และทำให้ช้าลงแค่ไหน (run-time penalty) ส่วนที่ 10 ตอบทั้งสองข้อ

### โปรแกรมที่ไม่ได้กลับตามลำดับ

ในสายตาของวิธีที่เฝ้าที่อยู่ขากลับ โค้ดบางแบบดูเหมือนการโจมตีทุกประการ เพราะที่อยู่ขากลับถูกยกออกและใส่กลับ หรือถูกใช้กระโดดโดยไม่ได้มาจาก `CALL` โค้ดพวกนี้คือ non-LIFO control flow ที่ SRAS ในส่วนที่ 4 รับมือไม่ได้ คือโค้ดที่จัดการที่อยู่ขากลับบน stack เองแทนที่จะปล่อยให้ call กับ return จับคู่กันตามปกติ ตัวอย่างจาก x86 แบบ 16 บิต คือ routine ที่ถูกเรียกได้ทั้งแบบ near ซึ่งเก็บแค่ IP และแบบ far ซึ่งเก็บทั้ง IP และ CS โดย IP (instruction pointer) คือตำแหน่งของคำสั่งถัดไป และ CS (code segment) คือ register ที่บอกว่าโค้ดอยู่ใน segment ไหนของหน่วยความจำ

```asm
NEAR_ENTRY:
    POP  AX      ; POP instruction pointer (IP) from the top of stack into AX
    PUSH CS      ; PUSH CS
    PUSH AX      ; PUSH IP back onto stack
FAR_ENTRY:
    ...
    RETF         ; POP IP and CS off stack
```

ทางเข้าแบบ near หยิบที่อยู่ขากลับออกมา ใส่ CS ลงไปใต้มัน แล้วใส่ที่อยู่ขากลับกลับคืน stack จึงหน้าตาเหมือนการเรียกแบบ far ทั้งสองทางเข้าใช้ `RETF` ตัวเดียวกันได้ อีกแบบที่พบบ่อยคือการใช้ `RET` แทน `JMP` เพื่อให้โค้ดสั้นลง

วิธีที่มีอยู่จึงทำได้สองทางกับโค้ดพวกนี้ คือ **ไม่สนใจโค้ดพวกนี้** ซึ่งเปิดช่องให้ผู้โจมตี หรือ **รับมือไม่ได้** ซึ่งทำให้โปรแกรมถูกต้องพัง

### สองข้อเท็จจริงที่ทำให้เรื่องนี้ยาก

- **buffer overflow เกิดได้ใน Java, Perl และภาษาที่ type-safe ทั้งหลาย** แม้ตัวภาษาจะตรวจขอบเขตให้ แต่ virtual machine, interpreter และไลบรารีที่มันเรียกใช้ส่วนใหญ่เขียนด้วย C
- **ไม่มีวิธีป้องกันไหนสมบูรณ์** และวิธีที่ดูเหมือนจะสมบูรณ์ต้องเขียนโค้ดใหม่ทั้งหมด ตั้งแต่ BIOS, kernel, ไลบรารีทั้งแบบ static และ dynamic, ไดรเวอร์ ไปจนถึงแอปพลิเคชัน ซึ่งแทบเป็นไปไม่ได้

คำตอบที่วงการคอมพิวเตอร์รู้มานานแล้วคือการให้ฮาร์ดแวร์กำกับข้อมูลทีละคำ บทความใน Microprogramming เดือนเมษายน 1972 เขียนว่า

> I believe that the average computer of the year 2000 will: …. Have word by word protection and data description, …
>
> ผมเชื่อว่าคอมพิวเตอร์ทั่วไปในปี 2000 จะ … มีการป้องกันและการบรรยายข้อมูลทีละคำ …

และใน ACM SIGARCH เดือนกรกฎาคม 2003 ก็ยังมีคนถามว่า

> Is anyone up for a discussion of capabilities, segments, 2-dimensional memory? Techniques which, among other things, render buffer overrun impossible.
>
> มีใครอยากคุยเรื่อง capability, segment, หน่วยความจำสองมิติไหม เทคนิคพวกนี้ทำให้ buffer overrun เป็นไปไม่ได้ ท่ามกลางข้อดีอื่น ๆ

สามสิบเอ็ดปีผ่านไปคำทำนายแรกยังไม่เป็นจริง เพราะวิธีพวกนี้ต้องเปลี่ยนทั้งระบบ คำถามของ Secure Bit คือ **ทำให้น้อยที่สุดได้แค่ไหน** โดยยังพิสูจน์ได้ว่าพอ

<Quiz question="แอป Java ตัวหนึ่งไม่มีโค้ด C ของตัวเองเลย แต่ใช้ไลบรารีอ่านรูปภาพที่เรียกผ่าน native code ถ้ามีคนส่งไฟล์รูปที่ออกแบบมาให้ล้นเข้ามา แอปนี้ปลอดภัยเพราะเป็น Java ไหม">

## ส่วนที่ 8 — พิสูจน์ว่ากันอะไรถึงจะพอ

### ที่อยู่ที่ไม่ถูกแตะคือเงื่อนไขที่พอ

<Why>
ทุกวิธีที่ผ่านมาถูกออกแบบจากการโจมตีที่รู้จัก แล้วก็พลาดให้กับการโจมตีแบบถัดไป ถ้าจะหลุดจากวงจรนี้ ต้องหาสิ่งที่ **การโจมตีทุกแบบ** ต้องทำ แล้วพิสูจน์ว่ากันสิ่งนั้นได้ก็พอ
</Why>

ทฤษฎีเริ่มจาก Definition 1 และ 2 ในส่วนที่ 2 กับข้อสังเกตว่าของที่ล้นมาจาก domain อื่นเสมอ แล้วนิยามเพิ่มอีกข้อ

> **Definition 3:** Maintaining the integrity of an address means that the address has not been modified by overflowing with a buffer passed from another domain.
>
> การรักษา integrity ของที่อยู่ หมายถึงที่อยู่นั้นไม่ได้ถูกเปลี่ยนด้วยการล้นจาก buffer ที่ส่งมาจาก domain อื่น

> **Postulate 1:** In buffer-overflow attacks on control data, the generic buffer/memory-manipulating operations are used by the vulnerable routine to overflow the address (e.g. a return address or a function pointer).
>
> ในการโจมตีข้อมูลควบคุม โปรแกรมที่มีช่องโหว่ใช้คำสั่งจัดการ buffer หรือหน่วยความจำทั่วไปเป็นตัวล้นทับที่อยู่ เช่นที่อยู่ขากลับหรือ function pointer

ข้อนี้บอกว่าผู้โจมตีไม่ได้เขียนลงหน่วยความจำเอง โปรแกรมเป็นคนเขียน ด้วยคำสั่งอย่าง `strcpy` ที่ใช้คัดลอกข้อมูลธรรมดาทุกวัน บทพิสูจน์บนสไลด์ไม่ได้อ้าง Postulate 1 ตรง ๆ สักข้อ หน้านี้อ่านว่ามันมีน้ำหนักในส่วนที่ 9 เพราะการล้นทำด้วยคำสั่งคัดลอกธรรมดา ฮาร์ดแวร์ที่ให้คำสั่งคัดลอกทุกคำสั่งยกบิตไปพร้อมข้อมูล จึงตามข้อมูลจากข้างนอกไปจนถึงที่อยู่ที่ถูกทับได้ทุกครั้ง

> **Theorem 1:** Modifying an address by replacing ("overflowing") it using a buffer passed from another domain is a necessary condition for buffer-overflow attack on control data.
>
> **Restatement:** If there is to be a buffer-overflow attack on control data, an address must be modified using a buffer passed from another domain.

ถ้าจะมีการโจมตีข้อมูลควบคุมด้วย buffer overflow ต้องมีที่อยู่ตัวหนึ่งถูกเปลี่ยนด้วย buffer ที่มาจาก domain อื่น บทพิสูจน์ตามมาจาก Definition 1 และ 2 ตรง ๆ คือการโจมตีตามนิยามต้องเปลี่ยนที่อยู่ด้วยการล้น buffer บทพิสูจน์บนสไลด์อ้างแค่ Definition 1 และ 2 ส่วนที่ว่าข้อมูลที่ล้นนั้นส่งมาจากข้างนอก หน้านี้อ่านว่ามาจากข้อสังเกตในส่วนที่ 2 ที่ว่าของที่ล้นเข้ามามาจาก domain อื่นเสมอ

> **Corollary 1.1:** Preserving the integrity of an address is a sufficient condition for preventing a buffer-overflow attack.

การรักษา integrity ของที่อยู่ไว้ได้ เป็นเงื่อนไขที่ **พอ** สำหรับกันการโจมตี บทพิสูจน์ใช้ <Term en="Contrapositive" th="ประพจน์แย้งสลับที่" /> ของ Theorem 1 ประโยค "ถ้า A แล้ว B" จริงเมื่อไร ประโยค "ถ้าไม่ B แล้วไม่ A" ก็จริงด้วยเสมอ เช่น "ถ้าฝนตก ถนนเปียก" จริง ก็ได้ว่า "ถ้าถนนไม่เปียก ฝนไม่ได้ตก" ในที่นี้

| | ประโยค |
| --- | --- |
| Theorem 1 | ถ้ามีการโจมตี แล้วที่อยู่ต้องถูกเปลี่ยนด้วย buffer จากข้างนอก |
| Contrapositive | ถ้าไม่มีที่อยู่ไหนถูกเปลี่ยนด้วย buffer จากข้างนอก แล้วการโจมตีเกิดไม่ได้ |

ประโยคที่สองคือ Corollary 1.1 บทพิสูจน์ของมันเขียนเงื่อนไขนี้ว่าที่อยู่ "cannot be modified (or such modification can be detected)" คือที่อยู่ถูกเปลี่ยนไม่ได้ หรือการเปลี่ยนถูกจับได้ก่อนถูกใช้ ซึ่งนับว่าเท่ากับไม่ถูกเปลี่ยน ประโยคนี้เป็นเป้าหมายของ Secure Bit คือไม่ต้องรู้ว่าการล้นมาทางไหน ขอแค่จับได้ว่าที่อยู่ถูกเปลี่ยนด้วยข้อมูลจากข้างนอก

### ระบบที่ปลอดภัยต่อ buffer overflow

เพื่อพูดว่า "ปลอดภัย" ให้แม่น ทฤษฎีใช้นิยามของ Bishop จาก [Lecture 4](/2110413-csy/lecture-4#security-policy-และ-secure-system) คือ

- **Definition 4:** security policy แบ่งสถานะทั้งหมดของระบบเป็นสถานะที่ได้รับอนุญาต (secure) กับไม่ได้รับอนุญาต (nonsecure)
- **Definition 5:** secure system คือระบบที่เริ่มจากสถานะที่ได้รับอนุญาต และเข้าสู่สถานะที่ไม่ได้รับอนุญาตไม่ได้เลย

> **Lemma 2:** A system which preserves the integrity of an address (e.g. a return addresses or a function pointer) is a secure system with respect to buffer-overflow attacks.
>
> **Restatement:** A system that does not use input as a control data is a secure system with respect to buffer-overflow attacks on control data.

บทพิสูจน์แบ่งสถานะของระบบเป็นสองกอง คือ **normal operation** กับ **buffer-overflow attack** แล้วเดินสามขั้น

1. ทางเดียวที่จะเข้ากอง attack ได้คือที่อยู่ถูกเขียนทับด้วยที่อยู่ที่มากับ input ตาม Definition 2
2. ถ้าการเขียนทับแบบนั้นถูกจับได้และถูกกันไว้ ระบบก็เข้ากอง attack ไม่ได้ ตาม Definition 3
3. ระบบเริ่มจาก normal operation และเข้ากอง attack ไม่ได้ จึงเป็น secure system ตาม Definition 5

> **Lemma 3:** Secure Bit and Protocol 1 can preserve the integrity of an address, and result in a secure system with respect to buffer-overflow attacks.

Protocol 1 ซึ่งอธิบายในส่วนที่ 9 คือกฎว่าทุกคำที่ข้าม domain เข้ามาได้บิต 1 Secure Bit กับ Protocol 1 จึงจับได้ว่าที่อยู่ถูกล้นทับด้วย buffer จาก domain อื่น จับได้ก็รักษา integrity ได้ตาม Definition 3 แล้ว Lemma 2 ก็บอกว่าระบบนั้นปลอดภัย

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **มีบทพิสูจน์แล้ว Secure Bit จึงกัน buffer overflow ได้ทุกแบบ**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะ Corollary 1.1 เขียนสั้น ๆ ว่า "preventing a buffer-overflow attack" และ Lemma 3 ก็ใช้คำว่า secure system

สิ่งที่ถูกต้องคือ **ทุกบทพิสูจน์ปลอดภัยแค่ต่อการโจมตีข้อมูลควบคุม** ตาม Definition 2 ตัวอย่างอายุในส่วนที่ 2 ล้นทับ `age` ซึ่งเป็นตัวเลข ไม่มีที่อยู่ไหนถูกเปลี่ยน Secure Bit จึงปล่อยผ่าน และโปรแกรมก็ยังตอบว่า 49 ตัวแปรอย่าง `is_admin` ก็เช่นกัน
</Pitfall>

<Quiz question="ระบบหนึ่งรักษาที่อยู่ขากลับได้สมบูรณ์ ไม่มีทางถูกเขียนทับ แต่ไม่ได้ดูแล function pointer เลย Corollary 1.1 รับรองว่าระบบนี้กันการโจมตีข้อมูลควบคุมได้ไหม">
Theorem 1 บอกว่าการโจมตีต้องเปลี่ยน **ที่อยู่ตัวหนึ่ง** ตัวไหนก็ได้ที่โปรแกรมจะกระโดดตาม Corollary 1.1 จึงต้องการ integrity ของที่อยู่ทุกตัวที่ถูกใช้เป็นเป้าหมายของการกระโดด

คำตอบคือ **ไม่รับรอง** การโจมตีทาง function pointer หรือทาง jump slot ใน GOT ยังเปลี่ยนที่อยู่ได้ เงื่อนไขของ Corollary จึงไม่ครบ

คำตอบที่ผิดบ่อยคือ "รับรอง เพราะ stack smashing ถูกกันแล้ว" ซึ่งเอาการโจมตีแบบที่ดังที่สุดมาเป็นทั้งหมด ช่องนี้เองที่ทำให้ split stack และวิธีในกลุ่ม copy of address ไม่พอ
</Quiz>

## ส่วนที่ 9 — Secure Bit: บิตเดียวที่ติดไปกับทุกคำ

### สองกฎ

<Why>
Corollary 1.1 ต้องการ integrity ของที่อยู่ **ทุกตัว** ที่โปรแกรมจะกระโดดตาม แต่วิธีในส่วนที่ 4 เฝ้าทีละตำแหน่ง และพลาดตำแหน่งที่ไม่ได้เฝ้า ทางที่ไม่ต้องรู้ว่าที่อยู่อยู่ตรงไหน คือดูว่าค่านั้น **มาจากไหน** แทนที่จะดูว่ามันไปลงที่ไหน ซึ่งคือกฎของ input protection ในส่วนที่ 5 ที่ย้ายมาทำในฮาร์ดแวร์
</Why>

Secure Bit ใช้บิตหนึ่งบิตต่อหนึ่งคำของหน่วยความจำ บอกว่าคำนั้นมาจาก domain อื่นหรือไม่ ทุกคำในโพรเซส ตั้งแต่ parameters, return address, function pointers ไปจนถึง buffer เริ่มที่บิต 0 ซึ่งแปลว่า trustworthy ส่วนคำที่ input จากอุปกรณ์หรือผู้ใช้ผ่านระบบปฏิบัติการและไดรเวอร์ลงไปอยู่ได้บิต 1 ซึ่งแปลว่า untrustworthy แล้วบังคับด้วยสองกฎ

- **Protocol 1:** การส่ง buffer ข้าม domain ซึ่งได้แก่อุปกรณ์ เครื่อง และโพรเซส ต้องตั้ง Secure Bit เสมอ พูดอีกแบบคือ **input ทุกคำมี Secure Bit เป็น 1**
- **Protocol 2 (Hardware Enforcement):** ข้อมูลจาก domain อื่นที่มี Secure Bit เป็น 1 ห้ามถูกใช้เป็นเป้าหมายของการกระโดด

แนวคิดเดียวกันนี้มีมาก่อนในรูปของหลักการเขียนโปรแกรม Howard และ LeBlanc เขียนไว้ว่า "All input is evil until proven otherwise" และ "Data must be validated as it crosses the boundary between untrusted and trusted environments" คือ input ทุกตัวอันตรายจนกว่าจะพิสูจน์ได้ว่าไม่ และข้อมูลต้องถูกตรวจตอนข้ามจากฝั่งที่ไม่น่าไว้ใจเข้ามาฝั่งที่ไว้ใจ หลักเดียวกับ [Validation of Input ใน Lecture 2](/2110413-csy/lecture-2#validation-of-input--เชื่อ-input-ไม่ได้) Secure Bit เอาหลักนี้ไปไว้ในฮาร์ดแวร์ โปรแกรมเมอร์จึงลืมไม่ได้

### Protocol Enforcement — ใครเป็นคนตั้งบิต

<Term en="sbit_write mode" th="โหมดเขียนที่ตั้ง Secure Bit" /> คือโหมดใหม่ของตัวประมวลผล ระหว่างอยู่ในโหมดนี้ ทุกคำที่ถูกเขียนลงหน่วยความจำได้ Secure Bit เป็น 1 domain ในที่นี้คือ domain ตามส่วนที่ 2 ที่มองจากโพรเซสที่กำลังทำงาน

kernel ใช้ sbit_write mode ทุกครั้งที่ย้ายข้อมูลข้าม domain ส่วนคำสั่ง Call, Jump และ Return ถูกแก้ให้ตรวจ Secure Bit ของที่อยู่ปลายทางก่อนกระโดด

### ฮาร์ดแวร์ — หน่วยความจำ คำสั่ง และ register

**หน่วยความจำ** มีบิตเพิ่มหนึ่งบิตต่อหนึ่งคำ เก็บแยกไว้ใน **Secure Bit Storage** ข้างที่เก็บข้อมูลปกติ ตัวประมวลผลกับชิปหน่วยความจำมีสาย Secure Bit (I/O) เพิ่มอีกเส้นข้างสาย Address, Data, CS และ R/W โดย CS ตรงนี้คือ chip select สายที่เลือกว่าจะคุยกับชิปไหน ไม่ใช่ code segment ในส่วนที่ 7 การหาที่อยู่ของบิตทำแบบนี้

1. แบ่งที่อยู่จริง (physical memory address) เป็นบิตส่วนบน (high order bits) กับ 3 บิตล่าง
2. บิตส่วนบนบวกกับ **Base Register** ได้ที่อยู่ใน Secure Bit Storage
3. 3 บิตล่างเข้า **8-1 Line Selector** เลือกหนึ่งในแปดบิตของไบต์นั้น

ไบต์หนึ่งไบต์ใน Secure Bit Storage จึงเก็บบิตของแปดตำแหน่งติดกัน เช่นที่ตำแหน่ง `0x1234` ตัด 3 บิตล่างทิ้งได้ไบต์ที่ `0x246` และ 3 บิตล่างมีค่า 4 คือบิตที่ 4 ซึ่งมี mask `0x10`

สไลด์ขัดกันเองตรงนี้ หัวข้อเขียนว่าเพิ่มหนึ่งบิตต่อ **หนึ่งคำ** แต่ถ้าที่อยู่จริงที่ใช้เป็นที่อยู่ระดับไบต์อย่างบน x86 การเลือกด้วย 3 บิตล่างให้หนึ่งบิตต่อ **หนึ่งไบต์** และโค้ดของ BOCHS ในส่วนที่ 10 ก็เก็บแบบนั้นจริง หน้านี้ใช้คำว่า "ต่อหนึ่งคำ" ตามแนวคิด ส่วนตัวเลขขนาดในส่วนที่ 10 คิดทั้งสองแบบ ในแบบที่ใช้ Base Register นี้ Secure Bit Storage ไม่ใช่ชิปแยก แต่เป็นช่วงหนึ่งของหน่วยความจำหลักที่กันไว้เก็บบิต (SecureBits) และ Base Register เก็บที่อยู่เริ่มต้นของช่วงนั้น

**ชุดคำสั่ง** เปลี่ยนสี่จุด

- มี flag ใหม่ชื่อ `sbit_write`
- `CALL` และ `JUMP` ตรวจ Secure Bit ของเป้าหมาย รายการชุดคำสั่งในสไลด์ระบุแค่สองคำสั่งนี้ ขณะที่หัวข้อ protocol enforcement นับ Return ด้วย `RET` คือการกระโดดไปตามค่าที่ดึงจาก stack จึงต้องถูกตรวจเหมือนกัน รูปที่ 2 จึงแสดง `RET` เป็นตัวปฏิเสธ
- คำสั่งอื่นที่แตะหน่วยความจำ ยก Secure Bit ไปพร้อมกับคำที่ย้าย เมื่อ sbit_write mode ปิดอยู่ และตั้ง Secure Bit ที่ปลายทาง เมื่อ sbit_write mode เปิดอยู่
- การคำนวณทุกแบบ ทั้ง shift, เลขคณิต และตรรกะ ถ้ามี operand ตัวไหนไม่ปลอดภัย ผลก็ไม่ปลอดภัย ส่วนค่าคงที่ที่ฝังในคำสั่ง (immediate) ถือว่าปลอดภัย

ข้อสุดท้ายทำใน **ALU** ด้วย OR gate สามขา ขาเข้าคือบิตของ operand ตัวที่หนึ่ง บิตของ operand ตัวที่สอง และ flag `sbit_write` จาก FLAGS register ผลทุกตัวที่คำนวณระหว่างอยู่ใน sbit_write mode จึงได้บิต 1 ด้วย นอกจากนั้น **register** ทุกตัว เช่น EAX ต้องมี Secure Bit ติดไปด้วย และ **Program Counter** ก็ต้องมี ตัวประมวลผลจะยก exception ตอนไหนเมื่อบิตของ PC เป็น 1 เป็นคำถามที่ต้องออกแบบ

นอกจาก BOCHS ในส่วนที่ 10 อีกแพลตฟอร์มที่ใช้ทดลองได้คือ **SimpleScalar** สถาปัตยกรรม RISC ของมันมีชุดคำสั่งเรียบง่ายและออกแบบไม่ซับซ้อน แต่ยังมีเรื่องที่ต้องคิดคือ parallelism, hazard และ cache เพราะบิตต้องเดินทางไปกับค่าผ่านทุกส่วนเหล่านั้น

### ระบบปฏิบัติการ

ฝั่งระบบปฏิบัติการมีงานสองอย่าง

- **Domains and Buffer Manipulation** — คือจุดที่ kernel ใช้ sbit_write mode ตามหัวข้อ protocol enforcement ข้างบน
- **Virtual Memory** — Secure Bit ผูกกับที่อยู่จริง ไม่ใช่ที่อยู่เสมือน จัดการได้สามแบบ คือให้ firmware ดูแล ให้ซอฟต์แวร์จัดการ หรือใช้ paging ตามปกติบนฮาร์ดแวร์ที่แก้แล้ว

### BOCHS — ตัวจำลอง x86

Secure Bit ถูกสร้างบน **BOCHS** ซึ่งเป็นโปรแกรมจำลองเครื่อง x86 เขียนด้วย C++ แบ่งเป็นวัตถุ คือ CPU, หน่วยความจำ, I/O peripheral, BIOS, disk และอื่น ๆ มีขอบเขตของหน่วยความจำชัดเจน สร้างได้หลาย instance และจำลองชุดคำสั่งทั้งหมด BOCHS มีมากกว่า 5,304 routine โดย 3,600 อยู่ในวัตถุ CPU

การตั้งหรือล้าง Secure Bit ของข้อมูลยาว `len` ไบต์ที่ตำแหน่ง `a20addr` เขียนแบบนี้

```cpp
// Set/Clear Secure Bit by KPR
Bit32u a20addr_s;
Bit8u sbyte;
for (int i=0;i<len ;i++ )
{
  a20addr_s=(a20addr+i)>>3;
  sbyte=(a20addr+i) & 0x00000007;
  sbyte=1 << sbyte;
  if (*sbit==1)
  { // set
    vector_s[a20addr_s]|=(sbyte&0xff);
  }
  else
  { // clear
    vector_s[a20addr_s]&=~(sbyte&0xff);
  }
  sbyte=sbyte<<1;
}
```

นี่คือการหาที่อยู่ของบิตในหัวข้อฮาร์ดแวร์ของส่วนที่ 9 ในรูปของโค้ด `vector_s` คือ Secure Bit Storage `>>3` ตัด 3 บิตล่างทิ้งเพื่อหาไบต์ใน `vector_s` และ `& 7` เอา 3 บิตล่างมาเลือกบิตในไบต์ เหมือนตัวอย่าง `0x1234` ในส่วนที่ 9

routine คู่กันชื่อ Read Secure Bit วนหาบิตแบบเดียวกัน แต่ OR บิตของทั้ง `len` ไบต์รวมเป็นค่าเดียว คำที่ยาวหลายไบต์จึงไม่ปลอดภัยทั้งคำ ถ้ามีไบต์ไหนสักไบต์ไม่ปลอดภัย

ส่วนอื่นที่ต้องแก้

- **Memory interface** — เพิ่ม `readPhysicalPage` และ `writePhysicalPage` รุ่นที่รับพารามิเตอร์ `sbit` เพิ่ม แบบ overload รุ่นเดิมที่ไม่สนใจ Secure Bit ยังอยู่ จึงไม่ต้องแก้ routine กว่า 3,000 ตัวที่เรียกมัน รุ่นเขียนมีพารามิเตอร์ `ignore` ด้วย คอมเมนต์ในโค้ดบอกว่า `ignore=0` คือเขียนข้อมูลโดยปล่อย Secure Bit เดิมไว้ตามเดิม ซึ่งกลับกับที่ชื่อพารามิเตอร์ชวนให้เดา
- **macro ของ ALU** — macro หนึ่งตัวต่อชนิดของคำสั่ง ALU เช่น `SBIT_ADD(sbit1,sbit2)` ให้ 0 เมื่อทั้งสองบิตเป็น 0 นอกนั้นให้ 1 ตามกฎ OR ในส่วนที่ 9 มีครบทั้ง SHX, ROX, XOR, AND, OR, NOT, ADD, SUB และ MUL ซึ่งใช้กับ DIV ด้วย SHX กับ ROX คือกลุ่มคำสั่ง shift และ rotate และ macro ของมันรับแค่บิตของค่าที่ถูกเลื่อน
- **การตั้งและตรวจบิต** — การตั้งบิตคือ `sbit=(sbit_mode)? 1:sbit;` และการตรวจเป้าหมายของ call คือ ถ้า `sbit != 0` ให้บันทึก log ว่า `call_ew: sbit of target is not secure` ส่วนการยก `BX_GP_EXCEPTION` อยู่ใน `#ifdef HAS_SBIT_EXCEPTION` จึงเกิดเฉพาะเมื่อ compile โดยกำหนดค่านี้ไว้ ถ้าไม่กำหนด โปรแกรมแค่บันทึก log แล้วทำงานต่อ
- **ขนาดของงาน** — รวมแล้วแก้ประมาณ 2,410 บรรทัดใน 607 routine

### Linux — ทางเข้าทุกทางผ่านจุดเดียว

ใน Linux ข้อมูลจากทุกแหล่งของ kernel ทั้ง input device, storage device, TCP/IP, standard input และอื่น ๆ เข้าถึงโพรเซสผ่านการ **คัดลอกลง buffer ของผู้ใช้** ใน `usercopy.c` <Term en="Threat Surface" th="พื้นผิวที่ภัยเข้ามาได้" /> คือ input ทุกทางที่ข้ามเข้ามาผ่าน interface ของซอฟต์แวร์ ใน Linux มันจึงแคบลงเหลือฟังก์ชันไม่กี่ตัว แก้ตรงนั้นที่เดียว ทุกคำที่ลงไปใน buffer ของโพรเซสก็ได้บิต 1

```c
#define SET_SBITMODE() \
  asm volatile( \
    " pushl %eax\n" \
    " lahf\n" \
    " orb $0x20, %ah\n" \
    " sahf\n" \
    " popl %eax" )

unsigned long
__generic_copy_to_user(void *to, const void *from, unsigned long n)
{
  SET_SBITMODE();
  if (access_ok(VERIFY_WRITE, to, n))
    __copy_user(to,from,n);
  CLR_SBITMODE();
  return n;
}
```

`lahf` คัดลอก 8 บิตล่างของ FLAGS ลง `AH` แล้ว `orb $0x20` ตั้งบิตที่ 5 ก่อน `sahf` เขียนคืน `CLR_SBITMODE` ทำกลับกันด้วย `andb $0xdf` คำอธิบายต่อไปนี้เป็นข้อมูลเสริม บิตที่ 5 ของ FLAGS เป็นบิตที่ x86 สงวนไว้และไม่ได้ใช้ Secure Bit จึงเอามาเป็น flag `sbit_write` ได้โดยไม่ชนกับ flag เดิม

### ผลการวิเคราะห์ และตัวเลขที่ต้องระวัง

- **Space และ memory interface** — แก้น้อยมาก ในฮาร์ดแวร์จริงคือชิปหน่วยความจำเพิ่มหนึ่งตัวต่อแผง ใช้ที่น้อยที่สุดเมื่อเทียบกับ segmentation และอ้างว่า Moore's law ชดเชยที่ที่เพิ่มได้ใน 3 วัน
- **Backward compatibility** — ใช้กับไบนารีของผู้ใช้รุ่นเก่าได้ 100%
- **Deployment** — แก้แค่ตัวประมวลผล
- **Performance** — ไม่ช้าลงอย่างมีนัยสำคัญ

ข้อสรุปของงานมีสามข้อ

- **Compatibility และ transparency** — ใช้กับไบนารีเดิมได้ และทำงานกับ thread, การไหลแบบ non-LIFO และการสื่อสารระหว่างโพรเซสได้ เพราะ Secure Bit ไม่ได้สนใจว่าที่อยู่ขากลับถูกย้ายไปไหน สนใจแค่ว่าค่านั้นมาจากข้างนอกหรือไม่
- **Effectiveness** — จับการโจมตีข้อมูลควบคุมด้วย buffer overflow ได้ทุกแบบ
- **Simple** — ฮาร์ดแวร์แก้น้อยมาก

- เงื่อนไขที่ต้องมีครบ: มีโค้ดให้รัน (ฉีดเอง **หรือ** รู้ที่อยู่ของโค้ดที่มีอยู่) และพาโปรแกรมไปรัน
- integer overflow และช่องโหว่ `printf` ทำงานคล้ายกัน

**[แผนที่ของวิธีป้องกัน](#ส่วนที่-3--แผนที่ของวิธีป้องกัน)**

- สามตระกูล: static analysis, dynamic solution (address protection, input protection, bounds checking, obfuscation), isolation (NX, sandboxing)
- static analysis จับได้แค่ที่รู้จัก ไม่มีข้อมูลตอนรัน และเตือนผิดได้
- คำถามสี่ข้อของ dynamic solution: assumptions, การสร้าง metadata, การตรวจ metadata, การจัดการข้อมูลผิด

**[ปกป้องที่อยู่](#ส่วนที่-4--ปกป้องที่อยู่ไม่ให้ถูกเปลี่ยนโดยไม่มีใครรู้)**

- canary (StackGuard): random, terminator, terminator with diversity เปลี่ยนเมื่อไรหยุดก่อนกลับ canary ของ glibc มีไบต์ล่าง `00` เสมอ
- ProPolice: guard + ย้าย array ไปติด guard และตัวชี้ไปไว้ใต้ array กันตัวชี้ใน struct ไม่ได้
- PointGuard: เข้ารหัสตัวชี้ตอนเก็บ ถอดตอนใช้
- copy of address: Split Stack, StackGhost, SRAS, RAD, StackShield, LibSafe/LibVerify
- tags: IBM System/38
- canary จับการเขียนผ่านตัวชี้ที่ข้ามมันไม่ได้

**[ติดป้าย input ตรวจขอบเขต สุ่มที่อยู่](#ส่วนที่-5--ติดป้าย-input-ตรวจขอบเขต-และสุ่มที่อยู่)**

- input protection: input ห้ามเป็น control data (Minos, Tainted pointer, Dynamic Flow Tracking)
- bounds checking: base และ boundary ทุกตัวแปร ช้าลงกว่า **30 เท่า**
- obfuscation: สุ่ม base, สลับลำดับ, เว้นช่องสุ่ม, PaX ASLR
- ทำให้ฉีดโค้ดไม่ได้: ISR, SPEF (SPEF นับเป็น isolation ด้วย)
- ฉีดโค้ดไม่ได้ไม่ได้แปลว่าปลอดภัย เพราะใช้โค้ดที่มีอยู่แล้วได้

**[กักบริเวณ](#ส่วนที่-6--กักบริเวณ-ยอมให้ล้น-แต่จำกัดผล)**

- NX, sandbox (TCPA), SPEF; NX ไม่ช่วยกับ heap, โปรแกรมที่ต้องรันโค้ดบน stack และการโจมตีที่ไม่ฉีดโค้ด
- NGSCB: strong process isolation, sealed storage, secure user interface, attestation — trusted ไม่ได้แปลว่า secure

**[ทำไมยังไม่จบ](#ส่วนที่-7--ทำไมยังไม่มีวิธีไหนปิดเรื่องนี้ได้)**

- จุดพลาด: assumptions ไม่พอ, ปกป้อง metadata ไม่พอ, performance, compatibility (non-LIFO), deployment
- metadata: descriptor 64 บิต (IA-32) / 128 บิต (I-432) ต่อตัวแปร, canary ต่อการเรียก, Secure Bit 1 บิตต่อคำ
- overflow เกิดใน Java และ Perl ได้ เพราะชั้นล่างเขียนด้วย C

**[ทฤษฎี](#ส่วนที่-8--พิสูจน์ว่ากันอะไรถึงจะพอ)**

- Theorem 1: การเปลี่ยนที่อยู่ด้วย buffer จาก domain อื่นเป็นเงื่อนไข **จำเป็น** ของการโจมตีข้อมูลควบคุม
- Corollary 1.1: รักษา integrity ของที่อยู่ได้เป็นเงื่อนไข **พอ** พิสูจน์ด้วย contrapositive
- Lemma 2: ระบบที่ไม่ใช้ input เป็น control data คือ secure system (นิยามของ Bishop)
- Lemma 3: Secure Bit กับ Protocol 1 รักษา integrity ได้ — ปลอดภัยต่อการโจมตี **ข้อมูลควบคุม** เท่านั้น

**[Secure Bit](#ส่วนที่-9--secure-bit-บิตเดียวที่ติดไปกับทุกคำ)**

- Protocol 1: input ทุกคำมีบิต 1 · Protocol 2: ห้ามใช้ค่าบิต 1 เป็นเป้าหมายของการกระโดด
- kernel ย้ายข้อมูลข้าม domain ใน sbit_write mode; Call, Jump, Return ตรวจบิต
- ALU: operand ไม่ปลอดภัยตัวเดียว ผลก็ไม่ปลอดภัย (OR); immediate ปลอดภัย
- ที่อยู่ของบิต = base register + บิตส่วนบน, 3 บิตล่างเลือกบิตในไบต์

**[สร้างจริง](#ส่วนที่-10--สร้างจริงและวัดผล)**

- BOCHS: มากกว่า 5,304 routine, แก้ประมาณ 2,410 บรรทัดใน 607 routine, overload memory interface เลี่ยงการแก้ 3,000+ routine
- Linux: ตั้ง sbit_write ใน `usercopy.c` ด้วย `orb $0x20, %ah`
- ทดสอบ: บูต Linux, แอปเดิม (SPEC, Apache + mod_ssl, OpenSSH, JVM ฯลฯ), hacking test, คำสั่งที่แก้
- ผล: เข้ากันได้กับไบนารีเดิม 100%, แก้แค่ตัวประมวลผล, ไม่ช้าลงอย่างมีนัยสำคัญ
