## ส่วนที่ 1 — Digital Forensics คืออะไร

### หลักฐานที่อยู่ในเครื่อง

<Why>
ผู้ต้องสงสัยคนหนึ่งวางแผนทุกอย่างในโน้ตบุ๊ก คุยกับพวกทางโทรศัพท์ แล้วลบไฟล์ทิ้งก่อนถูกจับ ตำรวจยึดเครื่องมาได้

ถ้าเจ้าหน้าที่เปิดเครื่องแล้วไล่กดหาไฟล์เอง จะเจอปัญหาสองข้อ ข้อแรก ไฟล์ที่สำคัญที่สุดถูกลบไปแล้ว ไล่กดยังไงก็ไม่เจอ ข้อสอง ทุกการกดเปลี่ยนข้อมูลในเครื่อง ทนายฝ่ายจำเลยจึงถามได้ว่าไฟล์ที่เจอมีอยู่ตั้งแต่แรก หรือเกิดขึ้นตอนเจ้าหน้าที่กด

ที่ต้องการคือวิธีทำงานที่ทั้งหาของที่ถูกซ่อนเจอ และพิสูจน์ได้ว่าไม่ได้แตะของกลาง
</Why>

<Term en="Digital Forensics" th="นิติวิทยาศาสตร์ดิจิทัล" /> คือ **สาขาหนึ่งของนิติวิทยาศาสตร์ที่ว่าด้วยการกู้และสืบสวนข้อมูลที่พบในอุปกรณ์ดิจิทัล ซึ่งมักเกี่ยวกับอาชญากรรมคอมพิวเตอร์** นิยามนี้มาจาก Wikipedia

อาชญากรรมคอมพิวเตอร์มีนิยามอยู่ใน [Lecture 1](/2110413-csy/lecture-1#cyber-crime-คืออะไร)

### ห้าสาขา แยกตามว่าหลักฐานอยู่ที่ไหน

อุปกรณ์แต่ละชนิดเก็บข้อมูลไม่เหมือนกัน digital forensics จึงแยกเป็นสาขาตาม **ชนิดของอุปกรณ์ สื่อ หรือร่องรอย (artifact) ที่ถือหลักฐานไว้** และแต่ละสาขาต้องมี **เครื่องมือและ framework** ของตัวเอง

| สาขา | หลักฐานที่ดู |
| --- | --- |
| <Term en="Computer Forensics" th="สืบจากคอมพิวเตอร์" /> | memory และ storage |
| <Term en="Mobile Device Forensics" th="สืบจากโทรศัพท์และอุปกรณ์พกพา" /> | ตำแหน่งที่เครื่องเคยอยู่ ซึ่งรู้จากเสาสัญญาณที่เครื่องเกาะ (cell site) รวมถึง SMS และอีเมล |
| <Term en="Network Forensics" th="สืบจากข้อมูลที่วิ่งในเครือข่าย" /> | packet ที่ดักไว้ได้ระหว่างทาง |
| <Term en="Forensic Data Analysis" th="วิเคราะห์ข้อมูลหาหลักฐาน" /> | ต่อจุดให้เห็นภาพในคดีการเงิน เช่นเงินที่ไหลผ่านหลายบัญชี |
| <Term en="Database Forensics" th="สืบจากฐานข้อมูล" /> | ตัวฐานข้อมูล และข้อมูลที่ระบบจดไว้เกี่ยวกับมัน เช่นใครแก้แถวไหนเมื่อไร |

### Computer forensics หาอะไร

งานหลักของ computer forensics มีสามอย่าง

- **กู้ข้อมูลที่ถูกลบ** ซึ่งเป็นเรื่องของส่วนที่ 3
- **กู้สถานะของหน่วยความจำ** คือของที่อยู่ใน RAM ตอนเครื่องยังเปิด เช่นโปรแกรมที่กำลังรันและการเชื่อมต่อที่เปิดอยู่
- **กู้เอกสาร อีเมล และ access log** log คือร่องรอยแบบเดียวกับ audit trail ใน [Lecture 5](/2110413-csy/lecture-5#ส่วนที่-2--ร่องรอยมาจากไหน)

<Quiz question="บริษัทหนึ่งสงสัยว่าพนักงานบัญชีโอนเงินออกทีละน้อยไปเข้าบัญชีญาติมาสองปี หลักฐานอยู่ในระบบบัญชีที่เก็บในฐานข้อมูล และในอีเมลบนโน้ตบุ๊กของเขา งานนี้ต้องใช้สาขาไหนบ้าง">
แยกหลักฐานตามที่อยู่ทีละชิ้น ยอดโอนเล็ก ๆ หลายร้อยรายการต้องถูกต่อให้เห็นว่าเงินไหลไปทางไหน ระบบบัญชีอยู่ในฐานข้อมูลที่บอกได้ว่าใครแก้รายการไหนเมื่อไร ส่วนอีเมลอยู่ใน storage ของโน้ตบุ๊ก

คำตอบคือ **สามสาขา forensic data analysis สำหรับเส้นทางเงิน database forensics สำหรับระบบบัญชี และ computer forensics สำหรับโน้ตบุ๊ก** network forensics จะเข้ามาก็ต่อเมื่อมี packet ที่ดักไว้ได้ตอนเกิดเหตุ

คำตอบที่ผิดบ่อยคือ "computer forensics อย่างเดียว เพราะทุกอย่างอยู่ในคอมพิวเตอร์" แต่สาขาแบ่งตามชนิดของหลักฐาน และฐานข้อมูลกับเส้นทางเงินต้องใช้เครื่องมือคนละชุดกับการกู้ไฟล์จากโน้ตบุ๊ก
</Quiz>

## ส่วนที่ 2 — กฎข้อแรก: ห้ามแตะของกลาง

### หลักฐานที่ถูกแตะแล้ว เชื่อไม่ได้อีก

<Why>
ทนายถามว่า "ผู้ต้องสงสัยเปิดไฟล์แผนการครั้งสุดท้ายเมื่อไร" ไฟล์ทุกไฟล์มีเวลากำกับหลายค่า ค่าหนึ่งคือ <Term en="Access Time" th="เวลาที่ไฟล์ถูกอ่านล่าสุด" /> หรือ atime ผู้สืบตอบคำถามนี้จากค่านั้น

ถ้า atime ถูกเขียนทับไปก่อนแล้ว คำตอบก็ผิด โดยไม่มีใครรู้ตัว ในงานนิติวิทยาศาสตร์ **หลักฐานที่มีตำหนิพาให้การสืบสวนผิดทาง** ข้อนี้จริงทั้งกับคราบเลือดและกับไฟล์
</Why>

กฎที่ตามมาคือ **Don't tamper with your evidence** อย่าแตะของกลาง กฎนี้เข้มกว่าที่ฟังดู เพราะการแตะไม่ได้แปลว่าแก้ไฟล์เท่านั้น

ลองทายก่อน: แค่เปิดอ่านไฟล์ โดยไม่แก้อะไรสักตัวอักษร จะมีอะไรในดิสก์เปลี่ยนไหม

<Example added title="แค่อ่านไฟล์ เวลาในไฟล์ก็เปลี่ยน">
ตั้ง atime ของ `diary.txt` เป็นเช้าวันที่ 15 มกราคม 2020 แล้วอ่านไฟล์ด้วย `cat` หนึ่งครั้ง

```bash
touch -d '2020-01-15 09:00' diary.txt
stat -c 'Access: %x' diary.txt
cat diary.txt > /dev/null
stat -c 'Access: %x' diary.txt
```

```text
Access: 2020-01-15 09:00:00.000000000 +0700
Access: 2026-11-12 15:04:21.185325270 +0700
```

เวลาที่บอกว่าเจ้าของอ่านไฟล์ล่าสุดเมื่อไร กลายเป็นเวลาที่ผู้สืบเปิดดู ทั้งที่ไม่มีใครแก้เนื้อหาเลย
</Example>

### ขั้นตอนตั้งแต่ที่เกิดเหตุจนส่งมอบ

ทุกขั้นทำตามกฎข้อแรก คือแตะต้นฉบับให้น้อยและเร็วที่สุด แล้วย้ายไปทำงานบนสำเนา งานทั้งหมดแบ่งได้สี่ช่วง

**ช่วงที่ 1 ที่เกิดเหตุ** มีสองงาน

- <Term en="Barring Access" th="กันคนออกจากระบบ" /> — ไม่ให้ใครเข้าถึงระบบที่จะเอาไปวิเคราะห์ ทั้งคนหน้าเครื่องและคนที่เข้ามาทางเครือข่าย
- **Never play with the machine** — ห้ามเล่นกับเครื่อง มีกฎย่อยสี่ข้อตามตารางด้านล่าง

| กฎย่อย | เหตุผล |
| --- | --- |
| เครื่องปิดอยู่ ปล่อยให้ปิด | การบูตเขียนข้อมูลลงดิสก์จำนวนมาก ทั้ง log และเวลาของไฟล์ แบบตัวอย่าง atime ข้างบน |
| เครื่องเปิดอยู่ ถ่ายรูปหน้าจอ | สิ่งที่อยู่บนจอหายทันทีที่มีคนแตะเครื่องหรือเครื่องดับ |
| เก็บ live data ก่อน โดยเฉพาะ RAM | live data คือข้อมูลที่หายเมื่อเครื่องดับ เช่น RAM ส่วนดิสก์รอได้ |
| ยึดทุกชิ้นใส่ถุงกันไฟฟ้าสถิต (static evidence bag) | ไฟฟ้าสถิตจากมือหรือเสื้อผ้าทำวงจรเสียได้ |

RAM เก็บได้ด้วยการ **dump หน่วยความจำลงดิสก์** คือคัดลอกทุกไบต์ใน RAM ลงเป็นไฟล์

ในแผนภาพต้นฉบับ Never play with the machine อยู่ **หลัง** การทำ image ซึ่งขัดกับกฎย่อยของมันเองที่ให้เก็บ live data และ RAM ก่อน ถ้าทำสำเนาดิสก์ก่อน เครื่องที่เปิดอยู่ก็ถูกแตะระหว่างนั้น และ RAM อาจหายก่อนได้เก็บ หน้านี้จึงวางมันไว้ในช่วงที่ 1

**ช่วงที่ 2 ทำสำเนา** (Creating image/clone) คือทำสำเนาของดิสก์ที่จะวิเคราะห์ มีสองแบบ

- <Term en="Image" th="สำเนาดิสก์ในรูปไฟล์" /> — เก็บทุกไบต์ของดิสก์ลงเป็นไฟล์ไฟล์เดียว เรียกว่า image file ไฟล์นี้ตรวจได้ว่าเหมือนต้นฉบับทุกไบต์ ทำสำเนาต่อได้ และเปิดด้วยเครื่องมือวิเคราะห์ได้ตรง ๆ
- <Term en="Clone" th="สำเนาดิสก์ลงดิสก์อีกลูก" /> — เขียนเนื้อหาของดิสก์ลงดิสก์อีกลูก ได้ดิสก์ที่เสียบใช้แทนลูกเดิมได้

บน Linux หรือ Unix ทำ image ได้ทั้งของดิสก์ทั้งลูก และของ volume เดียว volume คือพื้นที่ที่ระบบมองเป็นก้อนเดียว เช่นช่วงหนึ่งของดิสก์

คดีในหน้านี้ทำงานบน image file ทั้งหมด

**ช่วงที่ 3 วิเคราะห์บนสำเนา** มีสามงาน

- <Term en="Carving" th="แกะไฟล์ออกจากไบต์ดิบ" /> — แกะข้อมูลออกจากดิสก์หรือ image (ส่วนที่ 3)
- **Analyse raw data** — อ่านข้อมูลที่เปิดดูได้ตรง ๆ (ส่วนที่ 4)
- **Analyse system artifacts** — อ่านร่องรอยที่ระบบสร้างไว้ (ส่วนที่ 4)

**ช่วงที่ 4 ส่งมอบหลักฐาน ในลักษณะเดียวกับที่ได้มา** (Submit the evidence in the manner you acquire) ในทางปฏิบัติคือบอกได้ว่าได้หลักฐานมาด้วยวิธีไหน ให้คนอื่นทำซ้ำแล้วได้ผลเดียวกัน และจดไว้ว่าใครถือหลักฐานเมื่อไร ทำอะไรกับมันบ้าง

### คดีตัวอย่าง — กล่องแบตเตอรี่ที่ไม่ใช่แบตเตอรี่

ต้นปี 2020 กองบังคับการปราบปรามการกระทำความผิดเกี่ยวกับอาชญากรรมทางเทคโนโลยี (Technology Crime Suppression Division หรือ TCSD, `tcsd.go.th`) ขอให้ Krerk Piromsopa ผู้สอนวิชานี้ ไปช่วยตรวจและเป็นพยานให้กับอุปกรณ์ที่แฮกเกอร์ใช้ **ดักจี้สัญญาณไร้สาย**

ที่เกิดเหตุมีกล่องหลายใบ แต่ละใบหน้าตาเหมือนแบตเตอรี่ก้อนใหญ่ ฉลากเขียนว่า `Waterproof super power lithium batteries`

- **วงจรและอุปกรณ์ข้างในทั้งหมดถูกหุ้มด้วย epoxy** เพื่อไม่ให้เครื่อง x-ray ตรวจเจอ

### ทำสำเนาการ์ดโดยไม่แตะต้นฉบับ

ก่อนทำอะไรกับการ์ด ต้องกันไม่ให้มีอะไรถูกเขียนลงไป การ์ดจึงถูกเสียบผ่าน adapter ที่เลื่อนสวิตช์ไว้ตำแหน่ง **read-only** แล้วจึงทำ image ด้วยคำสั่ง `dd`

<Example title="ทำ image ของ microSD ทั้งใบ">
```bash
dd if=/dev/sdb of=evidence.img status=progress
```

```text
7971783168 bytes (8.0 GB, 7.4 GiB) copied, 103 s, 77.4 MB/s
15677440+0 records in
15677440+0 records out
8026849280 bytes (8.0 GB, 7.5 GiB) copied, 103.88 s, 77.3 MB/s
```

- `if=/dev/sdb` คือต้นทาง ซึ่งเป็นการ์ดทั้งใบ
- `of=evidence.img` คือไฟล์ปลายทาง
- `status=progress` ให้แสดงความคืบหน้า บรรทัดสุดท้ายของผลคือยอดรวมจริง
- 8.0 GB กับ 7.5 GiB คือขนาดเดียวกัน GB นับทีละ 10⁹ ไบต์ ส่วน GiB นับทีละ 2³⁰ ไบต์

<Detail label="อ่านตัวเลขของ dd">
บรรทัดแรกของผลคือความคืบหน้าครั้งสุดท้ายก่อนเสร็จ ยังไม่ใช่ยอดรวม

`dd` อ่านทีละ 512 ไบต์ เรียกว่า record และ 15677440 × 512 = 8026849280 ไบต์ ตรงกับบรรทัดสุดท้ายพอดี `+0` แปลว่าไม่มี record ไหนอ่านมาไม่เต็ม
</Detail>
</Example>

ทำไมต้องเอาทั้งใบ ดิสก์ถูกแบ่งเป็นช่วง ๆ เรียกว่า <Term en="Partition" th="ช่วงที่แบ่งไว้บนดิสก์" /> แต่ละช่วงมีระบบไฟล์ของตัวเอง

แต่ละ partition เริ่มและจบที่ไหนจดไว้ใน <Term en="Partition Table" th="ตารางบอกขอบเขตของ partition" /> การคัดลอก `/dev/sdb` จึงได้ทุกไบต์บนการ์ด รวมทั้งตัว partition table และพื้นที่ที่ระบบมองว่าว่าง

ได้ทุกไบต์มาแล้ว ยังต้องพิสูจน์ให้คนอื่นเห็นว่าสำเนาเหมือนต้นฉบับทุกไบต์ เครื่องมือที่ใช้คือ hash จาก [ส่วนที่ 5 ของ Lecture 6](/2110413-csy/lecture-6#ส่วนที่-5--hash-ทางเดียว-ความยาวคงที่) ซึ่งเปลี่ยนไปทั้งค่าถ้าข้อมูลต่างกันแม้แต่บิตเดียว

<Example added title="พิสูจน์ว่าสำเนาตรงกับต้นฉบับ">
`card.img` คือการ์ดจำลองขนาด 8 MiB ที่ใช้ระบบไฟล์ ext4 ของ Linux และมีรูปถูกลบไปหนึ่งรูป

`card-copy.img` คือสำเนาที่ทำด้วย `dd` แบบข้างบน และส่วนที่ 3 กับ 7 จะใช้มันต่อ

```bash
sha256sum card.img card-copy.img
```

```text
f50366deb69691f037c0467a2896859d1bdf795f35337340743aa1aa3c79c150  card.img
f50366deb69691f037c0467a2896859d1bdf795f35337340743aa1aa3c79c150  card-copy.img
```

ค่า hash ที่จดไว้ทันทีนี้ ใครคำนวณซ้ำแล้วได้ค่าเดิม แปลว่าไม่มีใครแตะต้นฉบับตั้งแต่ทำสำเนา

<Detail label="คำสั่ง dd ที่ทำสำเนาการ์ดจำลอง">
```bash
dd if=card.img of=card-copy.img status=progress
```

```text
16384+0 records in
16384+0 records out
8388608 bytes (8.4 MB, 8.0 MiB) copied, 0.0118857 s, 763 MB/s
```
</Detail>
</Example>

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ตั้งการ์ดเป็น read-only หรือ mount แบบ `ro` แล้ว ไม่มีอะไรถูกเขียนลงไปได้แน่นอน**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะชื่อบอกตรง ๆ ว่าอ่านอย่างเดียว และพอลองแก้ไฟล์ ระบบก็ไม่ยอมจริง ๆ

ที่จริงแล้ว read-only ทั้งสองแบบเป็น **คำขอ ไม่ใช่กำแพง** สวิตช์บนการ์ด SD เป็นแค่ชิ้นพลาสติกที่เครื่องอ่านการ์ดตรวจตำแหน่ง แล้วระบบปฏิบัติการเลือกเองว่าจะเคารพมันไหม

ส่วน mount คือการเปิดระบบไฟล์ขึ้นมาเป็นโฟลเดอร์ คู่มือ `mount` บน Linux เตือนว่าแม้จะ mount แบบ `ro` ระบบไฟล์ ext3 และ ext4 **จะ replay journal ถ้าระบบไฟล์ไม่ได้ถูกปิดอย่างเรียบร้อย**

<Term en="Journal" th="บันทึกงานเขียนที่ยังไม่เสร็จ" /> คือบันทึกที่ระบบไฟล์จดไว้ก่อนเขียนจริง การ replay คือเขียนงานที่ค้างใน journal ลงดิสก์ให้เสร็จ

ถ้าจะกันจริงต้องใช้ `ro,noload` และสิ่งที่ยืนยันได้จริงคือค่า hash ก่อนและหลังทำงาน ไม่ใช่ชื่อของโหมด
</Pitfall>

<Quiz question="ถ้าผู้สืบสั่ง dd กับ /dev/sdb1 ซึ่งเป็น partition แรกของการ์ด แทน /dev/sdb ทั้งใบ จะได้หลักฐานน้อยกว่าเดิมตรงไหน">
`/dev/sdb1` คือช่วงที่ partition table บอกว่าเป็น partition แรก ระบบจะอ่านให้แค่ช่วงนั้น ส่วนตัว partition table พื้นที่ที่ไม่อยู่ใน partition ไหน และ partition อื่น ๆ จะไม่ถูกคัดลอกเลย

คำตอบคือ **ได้แค่ช่วงที่ partition table ชี้ถึง** และในคดีนี้แย่กว่านั้น เพราะผู้ร้ายลบ partition ทิ้งไปแล้ว ส่วนถัดไปจะเห็นว่า `/dev/sdb1` ไม่มีให้อ่านตั้งแต่แรก

คำตอบที่ผิดบ่อยคือ "ได้เหมือนกัน เพราะข้อมูลทั้งหมดอยู่ใน partition แรกอยู่แล้ว" ซึ่งคือการเชื่อ partition table ของผู้ต้องสงสัย ทั้งที่หลักฐานมักอยู่ตรงที่ตารางไม่ได้ชี้ถึง
</Quiz>

## ส่วนที่ 3 — ลบแล้วไม่ได้หายไป

### การลบ ลบแค่สารบัญ

<Why>
ถ้าการลบไฟล์คือการเขียนศูนย์ทับทุกไบต์ การลบวิดีโอ 4 GB จะช้าพอ ๆ กับการเขียนไฟล์ 4 GB ใหม่ทั้งไฟล์ แต่ในชีวิตจริงการลบเสร็จแทบจะทันที

แปลว่าตอนลบ ระบบไฟล์ไม่ได้แตะเนื้อไฟล์เลย
</Why>

ระบบไฟล์แบ่งพื้นที่เป็นช่องขนาดเท่ากัน เรียกว่า <Term en="Block" th="ช่องเก็บข้อมูลของระบบไฟล์" /> บนการ์ดจำลองของหน้านี้คือช่องละ 4096 ไบต์

ระบบไฟล์เก็บของสองส่วนแยกกัน ส่วนแรกทำหน้าที่เหมือน **สารบัญ** บอกว่าไฟล์ชื่ออะไรอยู่ที่ block ไหน และ block ไหนว่าง ส่วนที่สองคือ **ตัวข้อมูล** ที่อยู่ใน block บนดิสก์

การลบไฟล์แก้แค่สารบัญ คือเอาชื่อออก แล้วนับ block ของไฟล์นั้นว่าว่าง ไบต์ทั้งหมดจึงยังอยู่ที่เดิม จนกว่าจะมีไฟล์ใหม่มาเขียนทับ

บนระบบไฟล์ตระกูล ext สารบัญของแต่ละไฟล์อยู่ใน <Term en="inode" th="ข้อมูลประจำไฟล์ เช่นขนาดและ block ที่ใช้" /> ซึ่งมีเลขประจำตัว ส่วนชื่อไฟล์อยู่ใน directory ที่ชี้ไปหาเลขนั้น เลข 13 หน้าชื่อ `mountain.jpg` ในรูปที่ 3 คือเลข inode

partition ก็เป็นแบบเดียวกันในอีกชั้นหนึ่ง partition table คือสารบัญของทั้งดิสก์ ลบรายการในตารางทิ้ง ข้อมูลใน partition ก็ยังอยู่ครบ

partition table จดตำแหน่งเป็นเลข <Term en="Sector" th="ช่องเล็กที่สุดของดิสก์" /> sector คือหน่วยเล็กที่สุดที่ดิสก์อ่านหรือเขียนได้ในครั้งเดียว บน microSD ในคดีคือช่องละ 512 ไบต์

sector เป็นหน่วยของดิสก์ ส่วน block เป็นหน่วยของระบบไฟล์ หนึ่ง block จึงมักกินหลาย sector

<Figure number={3} caption="สองระดับของการลบ ทั้งสองระดับลบแค่รายการในสารบัญ ไบต์จริงยังอยู่">
  <DeleteKeepsData />
</Figure>

<Analogy>
ระบบไฟล์เหมือนสมุดจดเลกเชอร์ที่มีหน้าสารบัญ หน้าสารบัญคือสารบัญของระบบไฟล์ แต่ละหน้ากระดาษคือ block และลายมือบนหน้าคือไบต์ของไฟล์

การลบไฟล์คือการขีดฆ่าบรรทัดในหน้าสารบัญ แล้วจดไว้ว่า "หน้า 12–15 ว่าง" โน้ตบนหน้า 12–15 ยังอยู่ครบ ใครพลิกดูทีละหน้าก็อ่านเจอ

อุปมานี้ใช้ไม่ได้ตรงที่คนจริงลบดินสอก่อนจดใหม่ แต่ระบบไฟล์เขียนทับไบต์เก่าตรงนั้นเลย ไฟล์เก่าจึงอาจถูกทับแค่บางส่วน และสิ่งที่กู้ได้อาจเป็นครึ่งหน้าเก่าปนครึ่งหน้าใหม่
</Analogy>

### กู้ไฟล์ด้วยการหาหัวไฟล์

เมื่อสารบัญไม่มีชื่อไฟล์แล้ว ก็ไม่รู้ว่าไฟล์เริ่มที่ไบต์ไหน แต่ไฟล์แต่ละชนิดขึ้นต้นด้วยไบต์ชุดเดิมเสมอ

ไบต์ชุดนั้นเรียกว่า <Term en="File Header" th="ไบต์ชุดที่ขึ้นต้นไฟล์ชนิดนั้นเสมอ" /> เช่นไฟล์ JPEG ขึ้นต้นด้วย `FF D8 FF` และจบด้วย footer `FF D9`

การกู้ไฟล์ที่ถูกลบจึงมีสามขั้น

1. **ทำ image ของดิสก์** ขั้นนี้ไม่บังคับ แต่ส่วนที่ 2 บอกแล้วว่าควรทำ
2. **ใช้เครื่องมือ scan หา file header ในดิสก์**
3. **อ่านช่วงที่เกี่ยวข้องออกมาเป็นไฟล์**

การแกะไฟล์จากไบต์ดิบโดยไม่พึ่งสารบัญแบบนี้ คืองาน carving ในช่วงที่ 3 ของรูปที่ 1

ลองทายก่อน: ถ้าค้นเจอ header สองตัวและ footer สองตัว รูปที่ถูกลบจบที่ footer ตัวไหน

<Example added title="แกะรูปที่ถูกลบออกจาก card-copy.img ของส่วนที่ 2">
```bash
LC_ALL=C grep -obUaP '\xff\xd8\xff' card-copy.img | cut -d: -f1
LC_ALL=C grep -obUaP '\xff\xd9' card-copy.img | cut -d: -f1
dd if=card-copy.img of=carved.jpg bs=1 skip=4890624 count=42261
sha256sum mountain.jpg carved.jpg
```

```text
4890624
4891116
4896184
4932883
6ecfeb9a7b08fcecba1c48e841ef90468a788aad530b582821cbc20d704229fe  mountain.jpg
6ecfeb9a7b08fcecba1c48e841ef90468a788aad530b582821cbc20d704229fe  carved.jpg
```

header ตัวที่สองกับ footer ตัวแรกคือ thumbnail ที่ฝังอยู่ข้างในรูปเต็ม รูปเต็มจึงเริ่มที่ header ตัวแรกและจบที่ footer ตัวสุดท้าย ยาว 4932883 + 2 − 4890624 = 42261 ไบต์ และ hash ตรงกับรูปต้นฉบับทุกตัว

<Detail label="ก่อนแกะ — directory ไม่มีชื่อรูปแล้ว และรูปเคยอยู่ที่ block ไหน">
ก่อนลบ รูปนี้อยู่ใน block 1194 ถึง 1204 ของระบบไฟล์ที่ใช้ block ละ 4096 ไบต์ ได้จาก `debugfs -R "blocks mountain.jpg" card.img`

```text
1194 1195 1196 1197 1198 1199 1200 1201 1202 1203 1204
```

หลังลบ `debugfs -R "ls -l /" card-copy.img` เหลือแค่ไฟล์อื่น

```text
      2   40755 (2)      0      0    4096 12-Nov-2026 15:05 .
      2   40755 (2)      0      0    4096 12-Nov-2026 15:05 ..
     11   40700 (2)      0      0   16384 12-Nov-2026 15:05 lost+found
     14  100664 (1)      0      0      10 12-Nov-2026 15:05 note.txt
```

header ตัวแรกที่ไบต์ 4890624 เท่ากับ 1194 × 4096 พอดี คือต้น block แรกของรูป ระบบไฟล์ส่วนใหญ่เริ่มไฟล์ที่ต้น block เครื่องมือ carving จึงมักหา header แค่ที่ต้น block

การ์ดจำลองสร้างด้วย `mkfs.ext4` บนไฟล์ 8 MiB ใส่รูปด้วย `debugfs -w -R "write ..."` แล้วลบด้วย `debugfs -w -R "rm mountain.jpg"` รูปคือ `/usr/share/pixmaps/faces/mountain.jpg` จากแพ็กเกจ `gnome-control-center-faces`
</Detail>
</Example>

<Quiz question="เพื่อนลบรูปทั้งหมดออกจากการ์ดกล้อง แล้วถ่ายรูปใหม่อีก 500 รูปจนการ์ดเกือบเต็ม ถ้าตอนนี้ลองกู้รูปชุดเก่า จะได้อะไรกลับมา">
การลบทำให้ block ของรูปเก่าถูกนับว่าว่าง กล้องจึงเขียนรูปใหม่ลงไปตรงนั้นได้ทันที ยิ่งการ์ดใกล้เต็ม block เก่าที่รอดจากการเขียนทับก็ยิ่งน้อย

คำตอบคือ **กู้ได้น้อยมาก และบางรูปที่กู้ได้จะเสียไปบางส่วน** เพราะ header ยังอยู่ แต่ block ถัดไปถูกรูปใหม่ทับไปแล้ว

คำตอบที่ผิดบ่อยคือ "กู้ได้ครบ เพราะการลบลบแค่สารบัญ" ซึ่งจริงแค่ช่วงก่อนมีการเขียนใหม่ ป้าย "ว่าง" คือคำเชิญให้เขียนทับ และการถ่ายรูปเพิ่มคือการรับคำเชิญนั้น
</Quiz>

### เครื่องมือขึ้นกับระบบไฟล์

**เครื่องมือที่ใช้กู้ต่างกันไปตามระบบไฟล์** เพราะแต่ละระบบไฟล์จัดสารบัญไม่เหมือนกัน

ระบบปฏิบัติการจะอ่าน partition ได้ ต้องรู้ก่อนว่า block ใหญ่เท่าไรและสารบัญอยู่ตรงไหน ค่าเหล่านี้อยู่ในส่วนหัวของระบบไฟล์ ถ้าส่วนหัวเสีย ทั้ง partition ก็อ่านไม่ได้ ทั้งที่ไฟล์ยังอยู่ครบ

ส่วนหัวนี้ในระบบไฟล์ตระกูล FAT เรียกว่า <Term en="Boot sector" th="ส่วนหัวของระบบไฟล์ FAT" /> ส่วนในตระกูล ext เรียกว่า <Term en="Superblock" th="ส่วนหัวของระบบไฟล์ ext" /> ซึ่งมีสำเนาสำรองกระจายอยู่หลายจุดใน partition กู้หรือสร้างส่วนหัวขึ้นใหม่ได้ ไฟล์ทั้ง partition ก็กลับมาอ่านได้

ระบบไฟล์ที่เครื่องมือข้างล่างรองรับมีสามตระกูล

| ระบบไฟล์ | ใช้ที่ไหน |
| --- | --- |
| FAT12, FAT16, FAT32, exFAT | Windows รุ่นเก่า แฟลชไดรฟ์ และการ์ดหน่วยความจำ |
| NTFS | ระบบไฟล์หลักของ Windows |
| ext2, ext3, ext4 | ระบบไฟล์ของ Linux ext3 และ ext4 มี journal เพิ่มเข้ามา |

<Term en="TestDisk" th="เครื่องมือกู้ partition และไฟล์" /> คือซอฟต์แวร์ open source ใช้ได้บนหลายระบบปฏิบัติการ และเป็นเครื่องมือที่ใช้ในกิจกรรมของวิชานี้ ความสามารถของมันมีเช่น

- **ซ่อม partition table และกู้ partition ที่ถูกลบ**
- **กู้ boot sector ของ FAT32 จากสำเนาสำรอง**
- **สร้าง boot sector ของ FAT12, FAT16 และ FAT32 ขึ้นใหม่**
- **หา superblock สำรองของ ext2, ext3 และ ext4**
- **กู้ไฟล์ที่ถูกลบจาก FAT, exFAT, NTFS และ ext2**
- **คัดลอกไฟล์ออกจาก partition FAT, exFAT, NTFS และ ext2/ext3/ext4 ที่ถูกลบไปแล้ว**

<Term en="debugfs" th="เครื่องมือดูโครงสร้างภายในของ ext" /> ใช้ได้บน Linux เท่านั้น ใช้ดูโครงสร้างของ ext3 และ ext4 ได้ดี มีคำสั่ง **แสดงรายการไฟล์ที่ถูกลบ** และ **กู้ไฟล์ที่ถูกลบ** แต่การกู้ได้ผลแค่บน ext2

<Callout type="warn" title="คู่มือของ debugfs จำกัดการกู้ไว้แค่ ext2">
คู่มือ `man debugfs` เขียนไว้ที่คำสั่ง `lsdel` ว่าใช้กู้ไฟล์ที่ลบโดยไม่ตั้งใจได้บน ext2 แต่ **ไม่มีประโยชน์ถ้าไฟล์ถูกลบบน ext3 หรือ ext4** เพราะ "the inode's data blocks are no longer available after the inode is released" คือเมื่อ inode ถูกปล่อย ก็เข้าถึง block ข้อมูลของมันไม่ได้อีก

บน ext4 การกู้เนื้อไฟล์จึงต้องพึ่ง carving แบบตัวอย่างข้างบน ซึ่งไม่ต้องรู้ว่าไฟล์เคยอยู่ block ไหน
</Callout>

### คดีตัวอย่าง — partition ที่ถูกลบ

แฮกเกอร์ทำให้การสืบสวนยากขึ้นมาก ถ้าไม่ถึงขั้นเป็นไปไม่ได้ ด้วยการ **ลบ partition ทิ้ง** ข้อมูลยังอยู่บนการ์ด แต่ระบบปกติอ่านไม่ได้ การ์ดทั้งใบดูเหมือนดิสก์ที่ยังไม่เคย format

ทางแก้คือใช้ `testdisk` บน Linux กู้ partition ext4 ที่สันนิษฐานว่าถูกลบไป ([TestDisk](https://www.cgsecurity.org/wiki/TestDisk)) งานบน `evidence.img` มีสี่ขั้น

<StepThrough>
<Step title="1 · เลือกสื่อ">
TestDisk 7.0 แสดงรายการสื่อให้เลือก และเจอ `Disk evidence.img - 8026 MB / 7655 MiB (RO)` คือไฟล์ image ขนาด 8026849280 ไบต์จากส่วนที่ 2 ส่วน `(RO)` แปลว่าเปิดได้แค่อ่าน
</Step>
<Step title="2 · ยอมรับว่าเขียนไม่ได้">
TestDisk เตือนว่า `Write access for this media is not available` และ `TestDisk won't be able to modify it` คำเตือนนี้คือสิ่งที่ต้องการ เพราะการค้นหาจะไม่แตะ image เลยแม้แต่ไบต์เดียว
</Step>
<Step title="3 · เลือกชนิด partition table">
TestDisk ตรวจเจอเองว่าเป็น `Intel` คือตารางแบบ PC ดั้งเดิม หรือ MBR
</Step>
<Step title="4 · เจอ partition Linux">
ผลการค้นคือ partition ชนิด `Linux` ขนาด `4194304` sector พร้อมตำแหน่งเริ่มและจบ
</Step>
</StepThrough>

TestDisk บอกตำแหน่งเริ่มและจบเป็นเลขแบบเก่าชื่อ <Term en="CHS" th="ตำแหน่งแบบ cylinder-head-sector" /> แปลงแล้วได้ว่า partition เริ่มที่ sector 8192 คือไบต์ที่ 4194304 (4 MiB) ของ image และยาว 4194304 sector หรือ 2 GiB

รู้จุดเริ่มแล้ว ก็ชี้เครื่องมือให้อ่านระบบไฟล์ ext4 ตรงนั้นได้ **พอ partition กลับมา การสืบสวนจริงจึงเริ่มได้**

<Detail label="หน้าจอ TestDisk และการแปลง CHS เป็นเลข sector">
ในขั้นที่ 3 ตัวเลือกชนิดตารางมี `Intel`, `EFI GPT`, `Humax`, `Mac`, `None`, `Sun` และ `XBox`

ในขั้นที่ 4 partition `Linux` เริ่มที่ CHS `0 130 3` จบที่ `261 151 18` บนดิสก์ที่ TestDisk มองเป็น CHS `976 255 63`

CHS เป็นวิธีบอกตำแหน่งแบบเก่าจากสมัยดิสก์จานหมุน head คือหัวอ่านของจานแต่ละหน้า track คือวงหนึ่งวงบนจาน cylinder คือชุดของ track ที่ทุกหัวอ่านอยู่พร้อมกัน และ sector คือช่องหนึ่งบน track

บนการ์ดที่ไม่มีจาน เลขชุดนี้เป็นแค่รูปทรงสมมติ ดิสก์นี้มี 255 head และ 63 sector ต่อ track จึงแปลงเป็นเลข sector เรียงตัวได้ด้วย (C × 255 + H) × 63 + (S − 1) ต้องลบ 1 เพราะ sector เริ่มนับที่ 1 ส่วน cylinder กับ head เริ่มที่ 0

| ค่า | คำนวณ | ผล |
| --- | --- | --- |
| sector เริ่ม | (0 × 255 + 130) × 63 + 2 | 8192 |
| sector สุดท้าย | (261 × 255 + 151) × 63 + 17 | 4202495 |
| ตรวจซ้ำ | 8192 + 4194304 − 1 | 4202495 |
| ขนาด | 4194304 × 512 ไบต์ | 2 GiB |
| ตำแหน่งเริ่มเป็นไบต์ | 8192 × 512 | 4194304 ไบต์ หรือ 4 MiB |

sector สุดท้ายที่ได้จากสองทางตรงกัน แปลว่าอ่านค่าจากหน้าจอถูก
</Detail>

### ถ้าไม่อยากให้ใครกู้ได้

<Why>
ก่อนขายฮาร์ดดิสก์ลูกเก่า ถ้าแค่ลบรูปทิ้งตามปกติ คนซื้อก็ carve รูปทุกรูปกลับมาได้แบบในส่วนนี้
</Why>

ถ้าเราไม่อยากให้ไฟล์ที่ลบถูกกู้กลับมา ต้องใช้ <Term en="Safe Delete" th="ลบโดยเขียนทับเนื้อไฟล์ก่อน" /> คือเขียนทับเนื้อไฟล์ก่อน แล้วค่อยลบชื่อออกจากสารบัญ บน Linux คำสั่งที่ทำแบบนี้คือ `shred -u` ซึ่งเขียนทับ 3 รอบตามค่าเริ่มต้น แล้วจึงลบไฟล์

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **`shred` ไฟล์แล้ว ไม่มีทางกู้กลับมาได้อีก**

ความเชื่อนี้ไม่จริงเสมอไป

มันดูจริงเพราะ `shred` เขียนทับตำแหน่งของไฟล์จริง ๆ หลายรอบ และบนดิสก์แบบดั้งเดิมมันก็ได้ผลตามนั้น

แต่ `shred` ตั้งอยู่บนสมมติฐานว่า **ระบบไฟล์เขียนทับที่ตำแหน่งเดิม** คู่มือ `man shred` ยอมรับเองว่าสมมติฐานนี้ไม่จริงกับระบบที่เขียนข้อมูลใหม่ไปที่อื่น เก็บสำเนาไว้หลายที่ หรือบีบอัดข้อมูล

<Detail label="ระบบที่ man shred ยกไว้">
ระบบไฟล์แบบ log-structured หรือ journal, ระบบไฟล์บน RAID, ระบบที่ทำ snapshot, ระบบที่ cache ไว้ที่อื่นอย่าง NFS และระบบไฟล์ที่บีบอัดข้อมูล
</Detail>

ตัวอย่างคือ ext3 ที่ mount ด้วย `data=journal` เนื้อไฟล์ถูกเขียนลง journal ก่อน `shred` ทับตำแหน่งจริงได้ครบ แต่สำเนาใน journal ยังอยู่จนกว่า journal จะวนมาทับ ส่วนโหมดค่าเริ่มต้น `data=ordered` จด journal แค่ข้อมูลของสารบัญ `shred` จึงได้ผลตามปกติ
</Pitfall>

## ส่วนที่ 4 — อ่านร่องรอยที่ระบบทิ้งไว้

<Why>
partition กลับมาแล้ว ระบบไฟล์ก็เปิดอ่านได้แล้ว แต่ยังไม่รู้ว่าเครื่องนี้ถูกตั้งให้ทำอะไร และไม่รู้ว่าควรเปิดไฟล์ไหนก่อน
</Why>

อีกสองงานในช่วงที่ 3 ของรูปที่ 1 ตอบคำถามนี้

- **Analyse raw data** — อ่านข้อมูลที่เปิดดูได้ตรง ๆ บนไดรฟ์ แล้วตัดสินว่าต้องตรวจอะไรต่อ
- **Analyse system artifacts** — อ่าน <Term en="System Artifact" th="ร่องรอยที่ระบบสร้างเองระหว่างใช้งาน" /> ซึ่งเก็บข้อมูลเกี่ยวกับผู้ใช้ การ login ข้อมูล สื่อภายนอกที่เคยเสียบ เครือข่าย และอื่น ๆ ร่องรอยของ browser (browser artifacts) ก็วิเคราะห์ได้เช่นกัน

### คดีตัวอย่าง — เครื่องนี้ทำอะไรตอนเปิด

ขั้นแรกคือ mount ระบบไฟล์ที่กู้มาให้เป็นโฟลเดอร์ที่เปิดดูได้

```bash
mount image.dd /mnt/evidence/
cd /mnt/evidence/
```

คำสั่งนี้ไม่ได้ใส่ `ro` แต่ไม่เป็นไร เพราะมันทำกับไฟล์สำเนา ถ้ามีอะไรถูกเขียนลงไป การ์ดต้นฉบับก็ยังอยู่ และทำสำเนาใหม่แล้วตรวจกับ hash เดิมได้เสมอ

ไฟล์ที่ mount ชื่อ `image.dd` ไม่ใช่ `evidence.img` จากส่วนที่ 2 และหลักฐานที่ยกมาไม่ได้บอกว่าสองไฟล์เกี่ยวกันยังไง ที่น่าจะเป็นคือ `image.dd` คือ partition ที่ถูกตัดออกจาก `evidence.img` มาเป็นไฟล์แยก

<Detail label="ทำไมน่าจะเป็น partition ที่ตัดออกมา">
`mount` ที่ไม่ใส่ `offset=` ใช้ได้กับไฟล์ที่ระบบไฟล์เริ่มที่ไบต์แรกเท่านั้น แต่ใน image ของทั้งการ์ด partition เริ่มที่ไบต์ 8192 × 512 = 4 MiB
</Detail>

เบาะแสแรกคือระบบปฏิบัติการ ไฟล์ `etc/debian_version` บอกว่าเป็น `stretch/sid` และระบบนี้คือ **Linux Armbian** ซึ่งเป็น Linux สำหรับบอร์ดเล็กอย่าง OrangePi

ชื่อ Armbian ไม่ได้มาจาก `debian_version` เพราะไฟล์นั้นบอกแค่ `stretch/sid` หลักฐานที่ยกมาไม่ได้บอกว่าผู้สืบรู้ชื่อนี้จากไฟล์ไหน

<Detail label="stretch/sid บอกอะไรได้แค่ไหน">
ค่า `stretch/sid` เป็นค่าที่ทั้ง Debian ช่วงก่อนออก Debian 9 และ Ubuntu 16.04 เขียนไว้ ค่านี้อย่างเดียวจึงบอกไม่ได้ว่า Armbian ตัวนี้สร้างบนฐานไหน
</Detail>

เบาะแสถัดมาอยู่ในสองที่ที่ทำให้โปรแกรมรันเองโดยไม่มีใครสั่ง ที่แรกคือ <Term en="rc.local" th="script ที่รันตอนบูต" /> ซึ่งระบบรันให้ทุกครั้งที่เปิดเครื่อง

```text
/mnt/evidence/etc$ cat rc.local
#!/bin/sh
# rc.local
rm /root/.bash_history
rm /root/.mobile.cfg.swp
#
switch 0
sleep 1
mobile &
exit 0
```

- `rm /root/.bash_history` ลบประวัติคำสั่งที่ root เคยพิมพ์ ทุกครั้งที่เปิดเครื่อง
- `rm /root/.mobile.cfg.swp` ลบไฟล์ชั่วคราวที่ editor ทิ้งไว้ตอนเปิดไฟล์ตั้งค่า `mobile.cfg`
- `switch 0` เรียกคำสั่ง `switch` (หัวข้อถัดไปจะเดาว่าคืออะไร) `sleep 1` รอ 1 วินาที แล้ว `mobile &` เปิดโปรแกรม `mobile` ให้รันอยู่เบื้องหลัง

ที่ที่สองคือ <Term en="cron" th="ตัวตั้งเวลารันคำสั่ง" /> ของ Unix

ตารางเวลาของมันเรียกว่า crontab ของ root บนการ์ดมีบรรทัดเดียวที่ใช้งานจริง

```text
/mnt/evidence/var/spool/cron/crontabs# cat root
...
# For more information see the manual pages of crontab(5) and cron(8)
#
# m h  dom mon dow   command
*/3 * * * * /usr/sbin/chkmobi
```

ห้าช่องแรกคือ นาที ชั่วโมง วันที่ เดือน และวันในสัปดาห์ `*` แปลว่าทุกค่า ส่วน `*/3` ในช่องนาทีแปลว่าทุก 3 นาที คือนาทีที่ 0, 3, 6 ไปเรื่อย ๆ บรรทัดนี้จึงรัน `/usr/sbin/chkmobi` ทุก 3 นาทีตลอดเวลา

คำสั่ง `file` บอกว่า `chkmobi` เป็น `POSIX shell script, ASCII text executable` เนื้อในมีแค่นี้

```sh
#!/bin/sh
if [ -z $(pidof mobile) ];then
      killall -9 mobile osmocon
      switch 0
      /usr/local/bin/mobile &
else
      echo "nothing"
fi
```

`pidof mobile` พิมพ์เลข process ของ `mobile` ที่กำลังรัน ถ้าไม่มีก็ไม่พิมพ์อะไร และ `-z` เป็นจริงเมื่อผลว่าง script นี้จึงแปลว่า **ถ้า `mobile` ไม่ได้รัน ให้ฆ่า `mobile` กับ `osmocon` ที่อาจค้างอยู่ สั่ง `switch 0` แล้วเปิด `mobile` ใหม่ ถ้ายังรันอยู่ก็ไม่ทำอะไร**

`osmocon` ส่ง firmware ที่คุมวิทยุเข้าไปในโทรศัพท์ผ่านสาย serial และเป็นทางส่งข้อความระหว่างโทรศัพท์กับโปรแกรมบนบอร์ด โทรศัพท์ที่ถูกดัดแปลงจึงต้องต่อสายเข้ากับ OrangePi

  <StartupWatchdog />

`debian_version`, `rc.local` และ crontab เป็นไฟล์ที่เปิดอ่านได้ตรง ๆ จึงเป็นงาน analyse raw data และบอกว่าต้องตรวจอะไรต่อ คือ `mobile` กับ `chkmobi` ส่วน `.bash_history` เป็น system artifact ที่ shell เขียนเองระหว่างใช้งาน ซึ่งเป็นเหตุที่ `rc.local` ลบมันทิ้งทุกครั้งที่บูต

ผลรวมคือ `mobile` เป็นโปรแกรมที่ทั้งเครื่องมีไว้รับใช้ ทุกอย่างบนการ์ดออกแบบมาให้มันไม่หยุดทำงาน ส่วนที่ 5 จะเปิดดูว่ามันคืออะไร

### script ที่สั่งขาของบอร์ด

ยังเหลือคำสั่ง `switch` ที่ `rc.local` และ `chkmobi` เรียก เบาะแสคือ start-up script ภาษา Python บนการ์ดที่คุม <Term en="GPIO" th="ขาที่โปรแกรมสั่งได้" />

GPIO คือขาโลหะบนบอร์ดที่โปรแกรมสั่งให้เป็นไฟสูงหรือไฟต่ำได้ บน Linux สั่งผ่านไฟล์ใน `/sys/class/gpio/`

ตัว script ทำสองอย่าง **ตั้งขา 11 เป็นค่าที่รับมาจาก argument ตัวแรก** แล้ว **ดึงขา 12 ลงเป็น 0 รอ 0.3 วินาที แล้วปล่อยกลับเป็น 1**

<Detail label="Python script ตัวเต็ม">
script มีสามฟังก์ชัน

- `pinexport(pin)` เขียนเลขขาลง `export` เพื่อเปิดใช้ขานั้น แล้วเขียน `out` ลง `direction` ให้เป็นขาส่งสัญญาณออก
- `pinmode(pin, mode)` เขียนค่า 0 หรือ 1 ลง `value` ของขานั้น
- `pinunexport(pin)` คืนขาให้ระบบ

```python
#!/usr/bin/python
#coding=utf-8
import os,time,sys
def pinexport(pin):
      file=open("/sys/class/gpio/export","w")
      file.write(str(pin))
      file.close()
      file=open("/sys/class/gpio/gpio"+str(pin)+"/direction","w")
      file.write("out")
      file.close()
def pinunexport(pin):
      file=open("/sys/class/gpio/unexport","w")
      file.write(str(pin))
      file.close()
def pinmode(pin,mode):
      file=open("/sys/class/gpio/gpio"+str(pin)+"/value","w")
      file.write(str(mode))
      file.close()
pinexport(11)
pinmode(11,int(sys.argv[1]))
pinunexport(11)
pinexport(12)
pinmode(12,0)
time.sleep(0.3)
pinmode(12,1)
pinunexport(12)
```

ในต้นฉบับ บรรทัดที่เปิด `direction` ถูกตัดขอบขวา argument ตัวที่สองน่าจะเป็น `"w"` เหมือนบรรทัดอื่น
</Detail>

หลักฐานที่ยกมาไม่ได้บอกว่าขา 11 และ 12 ต่อกับอะไร และไม่ได้บอกว่าไฟล์ไหนคือคำสั่ง `switch` ที่ `rc.local` กับ `chkmobi` เรียก

แต่ script นี้รับตัวเลขหนึ่งตัวเหมือน `switch 0` พอดี และการดึงขาลง 0.3 วินาทีแล้วปล่อย คือรูปแบบของการกดปุ่มหนึ่งครั้ง จึงน่าจะเป็นการสั่งเปิดหรือ reset โทรศัพท์ที่ต่อสายอยู่

<Pitfall>
ความเชื่อที่ต้องทิ้งคือ **ผู้ร้ายลบ `.bash_history` ทุกครั้งที่เปิดเครื่อง เราจึงไม่มีทางรู้ว่าเขาทำอะไรกับเครื่องนี้**

ความเชื่อนี้ไม่จริง

มันดูจริงเพราะ `.bash_history` คือบันทึกคำสั่งที่พิมพ์ไว้ตรง ๆ และมันก็หายไปจริง

แต่ประวัติคำสั่งเป็นร่องรอยแค่ชนิดเดียว คำสั่งที่ลบมันยังอยู่ใน `rc.local` ซึ่งบอกทันทีว่ามีคนตั้งใจซ่อน

`rc.local`, crontab และ script ที่ถูกเรียก บอกว่าเครื่องทำอะไรได้ละเอียดกว่าประวัติคำสั่งเสียอีก ทุกเบาะแสในส่วนนี้มาจากไฟล์พวกนั้น

ถ้ายังอยากได้ประวัติที่ถูกลบ ส่วนที่ 3 บอกแล้วว่า `rm` ไม่ได้ทำให้ไบต์หายไป
</Pitfall>

<Quiz question="สมมติว่า crontab เขียนเป็น */10 * * * * แทน */3 * * * * แล้ว mobile หยุดทำงานตอน 10:01 น. มันจะกลับมารันอีกครั้งตอนกี่โมง">
`*/10` ในช่องนาทีแปลว่านาทีที่หารสิบลงตัวตามนาฬิกา คือนาทีที่ 0, 10, 20 ไปเรื่อย ๆ cron ไม่ได้เริ่มนับจากตอนที่โปรแกรมหยุด รอบถัดไปหลัง 10:01 จึงเป็น 10:10 ซึ่ง `chkmobi` จะเห็นว่า `pidof mobile` ว่างแล้วเปิดใหม่

คำตอบคือ **10:10 น.** ส่วนค่าจริง `*/3` จะได้ 10:03 น.

คำตอบที่ผิดบ่อยคือ "10:11 น. เพราะทุก 10 นาทีหลังจากหยุด" ซึ่งมอง cron เป็นตัวจับเวลาถอยหลัง แต่ cron เทียบกับเวลาบนนาฬิกาเสมอ
</Quiz>

## ส่วนที่ 5 — เปิดโปรแกรมที่ไม่มีซอร์สโค้ด

<Why>
`mobile` ที่ถูกปลุกให้รันตลอด มีบนการ์ดแค่ในรูปที่ compile แล้ว ซึ่งเป็นรหัสเครื่องที่คนอ่านตรง ๆ ไม่ได้ ก่อนจะลงแรงแกะทั้งโปรแกรม ต้องมีวิธีถูก ๆ ที่บอกได้ก่อนว่ามันเป็นโปรแกรมประเภทไหน
</Why>

### file และ strings บอกอะไรได้ก่อนเปิดโค้ด

เครื่องมือถูกที่สุดสองตัวคือ `file` ที่บอกชนิดของไฟล์ และ `strings` ที่ดึงข้อความที่อ่านออกได้ในไฟล์ออกมา สองตัวนี้ช่วยเผยชื่อบางส่วนที่อยู่ในโปรแกรม เช่นชื่อไฟล์ source

```text
/root/usr/local/bin$ file mobile
mobile: ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV), dynamically linked,
interpreter /lib/ld-linux-armhf.so.3, for GNU/Linux 3.2.0,
BuildID[sha1]=81d28a2a833dfdddf50f9d02f77d5fc92951a408, with debug_info, not stripped
```

- `ELF 32-bit ... ARM` คือโปรแกรม Linux สำหรับ CPU ARM แบบบน OrangePi ไม่ใช่ x86 ของคอมพิวเตอร์ผู้สืบ เครื่องมือที่ต้องเข้าใจคำสั่งของ CPU จึงต้องเป็นรุ่นสำหรับ ARM เรียกว่า cross toolchain ชื่อขึ้นต้นด้วย `arm-linux-gnueabihf-`
- `with debug_info, not stripped` คือส่วนที่สำคัญที่สุด คนที่ compile ไม่ได้ลบชื่อฟังก์ชัน ชื่อตัวแปร และชื่อไฟล์ source ออกจากโปรแกรม

ดึงทุกข้อความที่มี `.c` ออกมา ได้รายชื่อไฟล์ source ของโปรแกรม

### Reverse Engineering

ขั้นถัดไปคือ <Term en="Reverse Engineering" th="แกะย้อนว่าโปรแกรมทำงานยังไง" /> คืออ่านย้อนจากรหัสเครื่องกลับไปเป็นสิ่งที่คนเข้าใจได้ มีสองทาง

- **`objdump -d` ของ ARM cross toolchain** ในทางเทคนิคทำได้ แต่ได้ผลเป็น assembly ทีละคำสั่ง ซึ่งอ่านยากมากสำหรับโปรแกรมขนาดนี้
- **เครื่องมือที่ฟรีและดีกว่า** ตัวที่เลือกใช้ในคดีนี้คือ **GHIDRA ของ NSA** ส่วน **IDA Pro** ซึ่งเป็นของเชิงพาณิชย์อาจทำงานได้ดีกว่า แต่ผู้ตรวจในคดีนี้ไม่มี license

GHIDRA เป็น <Term en="Decompiler" th="ตัวแปลรหัสเครื่องกลับเป็นโค้ด" /> คือแปลรหัสเครื่องกลับเป็นโค้ดที่หน้าตาคล้ายภาษา C ผลที่ได้ในคดีนี้คือ **โค้ด C ที่อ่านได้ทั้งโปรแกรม** ต้นฟังก์ชัน `main` หน้าตาแบบนี้

```c
int main(int argc,char **argv)

{
  int iVar1;
  FILE *__stream;
  int __status;
  uint __seed;
  size_t sVar2;
  long lVar3;
  uint8_t *puVar4;
  uint8_t *__s;
  int *piVar5;
  osmocom_ms *ms;
  uint8_t buf [20] [100];
  char call_num [16];
```

ชื่ออย่าง `iVar1`, `sVar2` และ `puVar4` คือชื่อที่ decompiler ตั้งเองตามชนิดข้อมูล เพราะไม่รู้ชื่อจริง แต่ชนิดข้อมูล `osmocom_ms` ติดมากับ debug info และบอกตรง ๆ ว่าโปรแกรมนี้สร้างบน <Term en="Osmocom" th="ชุดซอฟต์แวร์ GSM แบบ open source" />

Osmocom คือโครงการ open source ที่เขียนซอฟต์แวร์สำหรับเครือข่ายโทรศัพท์มือถือ ส่วนที่เป็นฝั่งโทรศัพท์ชื่อ OsmocomBB และทั้ง `mobile` กับ `osmocon` ในส่วนที่ 4 ก็เป็นโปรแกรมของ OsmocomBB ส่วนถัดไปจะดูว่ากล่องเอามันไปทำอะไร

<Quiz question="ถ้าผู้ร้ายรัน strip กับ mobile ก่อนถูกจับ ผู้สืบยังรู้ได้ไหมว่ามันเป็นซอฟต์แวร์โทรศัพท์ GSM">
`strip` ลบตารางชื่อและ debug info แต่ไม่แตะรหัสเครื่องหรือข้อความคงที่ที่โปรแกรมใช้ตอนทำงาน ข้อความอย่าง `Getting PM for ARFCN %s twice...` และ `/root/mobile.cfg` จึงยังอยู่ ARFCN คือหมายเลขช่องความถี่ของ GSM

รายชื่อ `gsm*.c` ก็น่าจะยังอยู่ เพราะคำสั่ง log `LOGP` ใน `logging.h` ของ libosmocore ซึ่งเป็น library กลางของ Osmocom ส่ง `__FILE__` ไปกับทุกข้อความ แบบเดียวกับใน Detail ของตัวอย่าง strip ข้างบน

คำตอบคือ **ยังรู้ได้** ที่หายไปคือชื่อที่มาจาก debug info เช่นชนิดข้อมูล `osmocom_ms` ชื่อฟังก์ชัน และชื่อตัวแปร Ghidra ยังแปลกลับเป็นโค้ดได้ แต่ชื่อพวกนั้นจะกลายเป็นชื่อที่มันตั้งเอง

คำตอบที่ผิดบ่อยคือ "ไม่ได้เลย เพราะ strip ลบทุกอย่างที่อ่านออก" แต่ `strip` ลบได้แค่ชื่อที่โปรแกรมไม่ได้ใช้ตอนทำงาน แบบ `sim.c` ในตัวอย่าง ข้อความที่โปรแกรมต้องใช้จริงลบไม่ได้ ไม่อย่างนั้นโปรแกรมก็ทำงานไม่ได้
</Quiz>

## ส่วนที่ 6 — กล่องนี้ทำอะไร: หลักฐานจากโลกโทรศัพท์มือถือ

### โทรศัพท์เก็บอะไรไว้บ้าง

mobile device forensics จากส่วนที่ 1 สนใจโทรศัพท์ เพราะมันเก็บข้อมูลที่มีประโยชน์ไว้หลายอย่าง

- **ซิมการ์ดมักบอกตำแหน่งล่าสุดที่เครื่องเคยไป** เพราะซิมจดรหัสพื้นที่ของกลุ่มเสาสัญญาณที่ลงทะเบียนครั้งล่าสุดไว้
- **SMS และบันทึกการโทรเป็นหลักฐานที่มีประโยชน์** บอกได้ว่าใครติดต่อใคร เมื่อไร

### IMSI และจุดอ่อนของ 2G

<Why>
เครือข่ายมือถือต้องรู้ว่าโทรศัพท์ที่กำลังคุยด้วยเป็นของลูกค้าคนไหน เพื่อส่งสายให้ถูกคนและเก็บเงินให้ถูกคน ชื่อที่ใช้ระบุลูกค้าจึงอยู่ในซิม ไม่ใช่ในตัวเครื่อง ลูกค้าย้ายซิมไปเครื่องไหนก็ได้ เครือข่ายเก็บเงินจากเจ้าของชื่อที่โทรศัพท์แจ้งมาและพิสูจน์ได้ว่าถือซิมนั้นจริง
</Why>

ชื่อนั้นคือ <Term en="IMSI" th="เลขประจำตัวผู้ใช้บริการในซิม" /> ย่อมาจาก International Mobile Subscriber Identity เป็นตัวเลขไม่เกิน 15 หลักที่เก็บในซิม ประกอบด้วยรหัสประเทศ รหัสเครือข่าย และเลขของผู้ใช้บริการ

IMSI ระบุตัว **ผู้ใช้บริการ** ไม่ใช่ตัวบัตรซิม เลขประจำบัตรซิมเป็นอีกเลขหนึ่งชื่อ ICCID เนื้อหาต้นฉบับเขียน IMSI ไว้ว่า "serial for SIM" ซึ่งตรงกับ ICCID มากกว่า

สิ่งที่ `mobile` ทำคือ **ใช้ Osmocom เป็นฐาน เพื่อดักจับ IMSI จากเครือข่าย GSM (2.5G) แล้วเอาไปซื้อของออนไลน์** เช่นของในเกมและการช็อปปิ้ง ผลคือผู้ใช้บริการที่ถูกจับ IMSI ไปถูกเก็บเงินแทน

<Callout type="info" title="ทำไมต้องเป็น 2G และทำไมโทรศัพท์ไม่มีซิม">
เนื้อหาต้นฉบับไม่ได้อธิบายว่าการรู้ IMSI ทำให้ใช้เงินของเหยื่อได้ยังไง กลไกในกล่องนี้เป็นไปได้ตามจุดอ่อนที่รู้กันของ GSM แต่หลักฐานในคดียังไม่ได้พิสูจน์

IMSI เป็นแค่ชื่อ การพิสูจน์ว่าถือซิมนั้นจริงใช้ challenge-response แบบใน [Lecture 3](/2110413-csy/lecture-3#challenge-and-response-ทำงานยังไง) เครือข่ายส่งเลขสุ่มมา ซิมตอบด้วยค่าที่คำนวณจากกุญแจลับในซิม ซึ่งไม่มีวันออกจากซิม

จุดอ่อนของ GSM คือ **เครือข่ายพิสูจน์โทรศัพท์ แต่โทรศัพท์ไม่ได้พิสูจน์เครือข่าย** ใครตั้งสถานีฐาน (เสาสัญญาณ) ปลอมได้ โทรศัพท์แถวนั้นก็ยอมเกาะและยอมบอก IMSI ให้

สถานีปลอมยังส่งต่อเลขสุ่มจากเครือข่ายจริงไปให้ซิมของเหยื่อตอบแทนได้ แบบเดียวกับ [man-in-the-middle](/2110413-csy/lecture-1#man-in-the-middle) เครือข่ายตั้งแต่ 3G ขึ้นไปปิดช่องนี้ด้วยการให้เครือข่ายพิสูจน์ตัวต่อโทรศัพท์ด้วย

โทรศัพท์ในกล่องจึงไม่ต้องมีซิมของตัวเอง เพราะมันไม่ได้ใช้ตัวตนของตัวเองเลย มันเป็นแค่วิทยุ GSM ให้ซอฟต์แวร์บน OrangePi ที่สวมตัวตนของคนอื่น

โปรแกรม GSM ที่ยกมาจากการ์ดมีแต่ฝั่งโทรศัพท์ คือ `mobile` กับ `osmocon` หลักฐานที่ยกมาจึงไม่ได้แสดงว่าส่วนไหนของกล่องทำหน้าที่สถานีฐานปลอม
</Callout>

### หลักฐานที่เชื่อมกล่องกับผู้เสียหาย

ถ้ากล่องสวมตัวตนเหยื่อซื้อของ ต้องมีคำสั่งซื้อถูกส่งออกไป บนการ์ดมีร่องรอยของ SMS แบบนั้น

| ช่อง | ค่า |
| --- | --- |
| sms sca | `+8613800230500` |
| sms | `41970` |
| ข้อความ | `CENT BST 225` |

`sca` คือ Service Centre Address หรือเบอร์ศูนย์ส่ง SMS ที่ตั้งไว้ในเครื่อง เบอร์นี้ขึ้นต้นด้วย `+86` ซึ่งเป็นรหัสประเทศจีน ปลายทางคือเลขสั้น `41970`

อีกฝั่งของเรื่องอยู่บนกระทู้ Pantip ชื่อ "เตือนภัยคนใช้ AIS-One2Call ระวังถูกหักเงินจากหมายเลข 4197005"

- เจ้าของกระทู้เพิ่งย้ายจาก TrueMove H มา AIS One2Call ได้ยังไม่ถึงสองเดือน และหลังใช้มาไม่ถึงเดือนก็ได้ข้อความจากหมายเลข `4197005` ว่า "การสั่งซื้อประสบความสำเร็จ คุณได้ชำระเงิน 26.75THB บาท โทร 023157577"
- ศูนย์บริการของ AIS ตอบว่า `4197005` คือเลขสั้นของบริการแบบจ่ายรายครั้ง ชื่อ game item and coins - **CENT BST** ราคา **ครั้งละ 25 บาท** ใช้ซื้อชีวิตในเกม NewFly บนมือถือ
- เจ้าของกระทู้ไม่เคยสมัครและไม่เคยเล่นเกมนี้ แต่ AIS ตอบว่าตรวจสอบและคืนเงินไม่ได้ ให้ติดต่อ Google Play หรือผู้ให้บริการโดยตรง

25 บาทบวก VAT 7% ได้ 25 × 1.07 = 26.75 บาท ตรงกับยอดที่ถูกหักพอดี ข้อความ `CENT BST` ตรงกับข้อความที่กล่องส่ง และ `41970` ก็เป็นต้นของ `4197005` หลักฐานจากสองฝั่งจึงชี้ไปที่บริการเดียวกัน

นอกจากนี้ยังมี **งานวิจัยหลายชิ้นที่อธิบายการใช้ osmocom แบบนี้** เช่นวิทยานิพนธ์ปริญญาโท *Shadow Phone and Ghost SIM: A Step Toward Geolocation Anonymous Calling* ของ Gerard Lawrence Pinto

<Quiz question="ผู้เสียหายรายหนึ่งถูกหักเงินจาก 4197005 ตอนบ่ายวันจันทร์ ถ้าคุณเป็นผู้สืบที่อยากรู้ว่าเงินก้อนนี้มาจากกล่องที่ยึดได้หรือเปล่า จะขอหลักฐานจากใคร และขออะไร">
ถ้ากลไกเป็นแบบในกล่องข้างบน SMS สั่งซื้อถูกส่งจากกล่อง ไม่ได้ส่งจากโทรศัพท์ของผู้เสียหาย หลักฐานที่ดีที่สุดจึงอยู่ฝั่งเครือข่าย คือบันทึกว่า SMS สั่งซื้อในนามเบอร์นี้ถูกส่งเมื่อไร ผ่านเสาสัญญาณไหน แล้วเทียบกับตำแหน่งของกล่อง

คำตอบคือ **ขอบันทึก SMS และข้อมูล cell site ของเบอร์ผู้เสียหายช่วงบ่ายวันนั้นจากผู้ให้บริการเครือข่าย** แล้วดูว่าเสาที่ใช้ส่งอยู่ใกล้ที่ตั้งกล่องไหม

คำตอบที่ผิดบ่อยคือ "ยึดโทรศัพท์ของผู้เสียหายมาเปิดดู SMS ขาออก" ซึ่งจะไม่เจอข้อความสั่งซื้อ เพราะเครื่องของผู้เสียหายไม่ได้เป็นคนส่ง มันได้รับแค่ข้อความแจ้งว่าถูกหักเงิน

<Why>

<Term en="Metadata" th="ข้อมูลที่อธิบายข้อมูล" /> คือข้อมูลเกี่ยวกับตัวไฟล์ เช่นใครสร้าง สร้างเมื่อไร ด้วยเครื่องอะไร **ไฟล์หลายรูปแบบมี metadata อยู่ในตัว และบางครั้งมันมีประโยชน์ต่องานนิติวิทยาศาสตร์**

### EXIF และ GEOTAG

<Term en="EXIF" th="ข้อมูลกล้องที่ฝังในไฟล์รูป" /> ย่อมาจาก Exchangeable Image File Format คือมาตรฐานรูปแบบไฟล์รูปและไฟล์เสียงจากกล้องดิจิทัล รวมถึง tag ประกอบที่ติดไปกับไฟล์ เช่นยี่ห้อกล้องและเวลาที่ถ่าย

มาตรฐานนี้ใช้ในกล้องดิจิทัล สมาร์ตโฟน เครื่องสแกน และระบบอื่นที่จัดการไฟล์รูปและไฟล์เสียงจากกล้องดิจิทัล

EXIF อาจมี <Term en="GEOTAG" th="พิกัดจุดที่ถ่ายรูป" /> คือพิกัด GPS ของจุดที่ถ่ายรูปนั้น

<Example added title="รูปที่แกะออกมาในส่วนที่ 3 บอกอะไรเกี่ยวกับตัวเอง">
อ่าน EXIF ของ `carved.jpg` ที่แกะได้ในส่วนที่ 3

```bash
python3 exif.py carved.jpg
```

```text

DateTimeOriginal 2014:08:21 04:44:51

GPS none
```

รูปเดียวบอกยี่ห้อกล้อง รุ่นเลนส์ เวลาที่ถ่ายจริงตอนตีสี่สี่สิบสี่ของวันที่ 21 สิงหาคม 2014 และว่าถูกแต่งด้วย GIMP ราวสี่ปีครึ่งต่อมา รูปนี้ไม่มี GPS แต่รูปจากสมาร์ตโฟนที่เปิดตำแหน่งไว้จะมีพิกัดอยู่ในกลุ่มเดียวกันนี้

<Detail label="exif.py ที่ใช้อ่านค่า">
`carved.jpg` คือรูปโปรไฟล์ขนาด 512 × 512 ที่มากับ Linux ที่ติดตั้ง GNOME script นี้ใช้ library Pillow

```python
import sys
from PIL import Image, ExifTags
im = Image.open(sys.argv[1])
exif = im.getexif()
tags = {**exif, **exif.get_ifd(0x8769)}
for k, v in tags.items():
    name = ExifTags.TAGS.get(k, k)
    if name in ("Make", "Model", "LensModel", "DateTimeOriginal", "Software", "DateTime"):
        print(f"{name:17}{v}")
print("GPS", "yes" if exif.get_ifd(0x8825) else "none")
```

`0x8769` คือกลุ่มค่าของกล้องที่เก็บแยกไว้ใน EXIF และ `0x8825` คือกลุ่มค่า GPS
</Detail>

### คดี BTK — metadata ในไฟล์ที่ถูกลบ

**Dennis Lynn Rader** คือฆาตกรต่อเนื่องชาวอเมริกันที่ถูกเรียกว่า **BTK** หรือ BTK Strangler เขาตั้งชื่อนี้ให้ตัวเอง ย่อมาจาก "bind, torture, kill" ระหว่างปี **1974 ถึง 1991** เขาฆ่าคนไป **สิบคน** ในเขตเมือง Wichita รัฐ Kansas

ตำรวจพบ **metadata ที่ฝังอยู่ในเอกสาร Microsoft Word ที่ถูกลบไปแล้ว** ซึ่งยังอยู่ในแผ่น floppy disk โดยที่ Rader ไม่รู้ metadata นั้นมีคำว่า **"Christ Lutheran Church"** และเอกสารถูกบันทึกว่า **แก้ไขครั้งล่าสุดโดย "Dennis"**

คดีนี้ใช้สองเรื่องของหน้านี้พร้อมกัน คือไฟล์ที่ลบแล้วยังกู้ได้ (ส่วนที่ 3) และไฟล์พกชื่อคนเขียนติดไปด้วย (ส่วนนี้) เรื่องนี้ถูกทำเป็นภาพยนตร์ชื่อ *The Hunt for the BTK Killer* (2005) อ่านรายละเอียดเพิ่มได้ที่ [Dennis Rader บน Wikipedia](https://en.wikipedia.org/wiki/Dennis_Rader)

<Quiz question="แหล่งข่าวนิรนามส่งไฟล์ .docx รายงานภายในของบริษัทให้นักข่าว นักข่าวลบชื่อแหล่งข่าวออกจากเนื้อหาจนหมด แล้วโพสต์ไฟล์ต้นฉบับให้ผู้อ่านดาวน์โหลด แหล่งข่าวปลอดภัยไหม">
ไฟล์ `.docx` พกช่อง Author, Company และผู้แก้ไขล่าสุดติดไปด้วย ช่องพวกนี้ไม่อยู่ในเนื้อหา การลบชื่อออกจากเนื้อหาจึงไม่แตะมันเลย และถ้าแหล่งข่าวเปิดแก้ไฟล์ก่อนส่ง ชื่อของเขาก็อาจอยู่ในช่องผู้แก้ไขล่าสุด

คำตอบคือ **ไม่ปลอดภัย** บริษัทดาวน์โหลดไฟล์แล้วเปิด Properties ก็อาจเห็นชื่อหรือแผนกของแหล่งข่าวทันที ทางที่ถูกคือลบ metadata ก่อน หรือเผยแพร่เป็นข้อความที่พิมพ์ใหม่

คำตอบที่ผิดบ่อยคือ "ปลอดภัย เพราะในเนื้อหาไม่มีชื่อเหลือแล้ว" ซึ่งคือความผิดพลาดแบบเดียวกับของ Rader คือเชื่อว่าไฟล์มีแค่สิ่งที่เห็นบนหน้าจอ
</Quiz>

## ส่วนที่ 8 — จะเก่งเรื่องนี้ต้องมีอะไร

คดีกล่องดักสัญญาณใช้ความรู้คนละด้านในแต่ละขั้น ระบบไฟล์และ partition ในส่วนที่ 3 การบูตของ Linux และ cron ในส่วนที่ 4 โปรแกรม ARM และภาษา C ในส่วนที่ 5 และโปรโตคอล GSM ในส่วนที่ 6

คำถามว่าจะเก่งเรื่องความปลอดภัยได้ยังไง หรืออีกชื่อคือจะเป็นแฮกเกอร์ได้ยังไง จึงมีคำตอบสี่ข้อ

- **ความรู้กว้างเรื่องระบบ สถาปัตยกรรม เครือข่าย โปรโตคอล และอื่น ๆ**
- **ความรู้กว้างเรื่องภาษาโปรแกรม** ขึ้นกับแอปหรือระบบที่เจอ เช่น C/C++, Python, Java และ JavaScript
- **คิดแบบคนร้าย**
- **ฝึก ฝึก และฝึก**

และต้องมี **ความอดทน** การหา partition ที่หายไป การไล่อ่าน script ทีละไฟล์ และการนั่งอ่านโค้ดที่ decompiler แปลออกมา เป็นงานที่ไม่มีทางลัด

<Recap>

**[Digital forensics คืออะไร](#ส่วนที่-1--digital-forensics-คืออะไร)**

- สาขาหนึ่งของนิติวิทยาศาสตร์ ว่าด้วย **การกู้และสืบสวนข้อมูลในอุปกรณ์ดิจิทัล** มักเกี่ยวกับอาชญากรรมคอมพิวเตอร์
- ห้าสาขา: **computer** (memory, storage), **mobile device** (cell site, SMS, อีเมล), **network** (ดัก packet), **forensic data analysis** (ต่อจุดคดีการเงิน), **database** (ฐานข้อมูลและ metadata)
- แยกตามชนิดของอุปกรณ์ สื่อ หรือ artifact และแต่ละสาขาต้องมีเครื่องมือและ framework ของตัวเอง
- computer forensics กู้ข้อมูลที่ลบ สถานะของหน่วยความจำ เอกสาร อีเมล และ access log

**[ห้ามแตะของกลาง](#ส่วนที่-2--กฎข้อแรก-ห้ามแตะของกลาง)**

- **Don't tamper with your evidence** หลักฐานที่มีตำหนิพาให้การสืบสวนผิดทาง แค่อ่านไฟล์ atime ก็เปลี่ยน
- ที่เกิดเหตุ: **Barring Access** และ **Never play with the machine** — ปิดอยู่ปล่อยปิด เปิดอยู่ถ่ายรูปจอ เก็บ live data และ RAM ก่อน ยึดทุกชิ้นใส่ถุงกันไฟฟ้าสถิต
- RAM เก็บด้วยการ dump หน่วยความจำลงดิสก์ บน Linux หรือ Unix ทำ image ของดิสก์หรือของ volume ได้
- **Image** = ดิสก์เป็นไฟล์ **Clone** = ดิสก์ลงดิสก์อีกลูก แล้ววิเคราะห์บนสำเนา (carving, raw data, system artifacts) และ **Submit the evidence** ในลักษณะเดียวกับที่ได้มา
- คดีกล่องดักสัญญาณ (TCSD ต้นปี 2020): กล่องเหมือนแบตเตอรี่ หุ้ม epoxy กัน x-ray ข้างในมี router 3G/4G กับ OrangePi หกบอร์ดต่อโทรศัพท์ 2.5G ไม่มีซิม เก็บกลับมาแค่ microSD
- ทำ image ผ่าน adapter แบบ read-only ด้วย `dd if=/dev/sdb of=evidence.img` ได้ **8026849280 ไบต์** แล้วยืนยันด้วย hash ว่าสำเนาตรงกับต้นฉบับ

**[ลบแล้วไม่ได้หายไป](#ส่วนที่-3--ลบแล้วไม่ได้หายไป)**

- การลบ **ลบแค่สารบัญ** ไบต์ยังอยู่จนถูกเขียนทับ ทั้งระดับไฟล์และระดับ partition
- กู้ไฟล์: ทำ image (ไม่บังคับ) → **scan หา file header** → อ่านช่วงนั้นออกมาเป็นไฟล์ ซึ่งคือ **carving**
- เครื่องมือขึ้นกับระบบไฟล์ **TestDisk** กู้ partition กู้และสร้าง boot sector ของ FAT หา superblock สำรองของ ext และกู้ไฟล์จาก FAT, exFAT, NTFS, ext2 ส่วน **debugfs** ใช้ได้บน Linux เท่านั้น ดูโครงสร้าง ext3/4 ได้ดี มีคำสั่งแสดงและกู้ไฟล์ที่ลบ แต่การกู้ได้ผลแค่บน ext2
- คดี: ผู้ร้ายลบ partition จนการ์ดดูเหมือนไม่เคย format TestDisk เจอ partition Linux ขนาด 4194304 sector (2 GiB) เริ่มที่ sector 8192
- ไม่อยากให้ใครกู้ได้ใช้ **safe delete** คือเขียนทับก่อนลบ แต่ `shred` ไม่ได้ผลบนระบบไฟล์ที่ไม่เขียนทับที่เดิม

**[ร่องรอยในระบบ](#ส่วนที่-4--อ่านร่องรอยที่ระบบทิ้งไว้)**

- **raw data** คือข้อมูลที่เปิดดูได้ตรง ๆ **system artifacts** คือร่องรอยเรื่องผู้ใช้ login สื่อภายนอก เครือข่าย และ browser
- คดี: Armbian (`stretch/sid`) `rc.local` ลบ `.bash_history` แล้วเปิด `mobile` ทุกครั้งที่บูต และ cron `*/3 * * * *` เรียก `chkmobi` ทุก 3 นาทีเพื่อเปิด `mobile` ใหม่ถ้ามันตาย
- Python script สั่งขา GPIO 11 ตามค่าที่รับมา และดึงขา 12 ลง 0.3 วินาที

**[อ่านโปรแกรมที่ไม่มี source](#ส่วนที่-5--เปิดโปรแกรมที่ไม่มีซอร์สโค้ด)**

- `file` บอกว่า `mobile` เป็น ELF 32-bit ARM **with debug_info, not stripped** และ `strings` เผยชื่อไฟล์ `gsm*.c` ซึ่งคือซอฟต์แวร์โทรศัพท์ GSM
- reverse engineering: `objdump -d` ทำได้แต่อ่านยาก **GHIDRA** ของ NSA ฟรีและแปลกลับเป็น C ได้ **IDA Pro** เป็นของเชิงพาณิชย์

**[หลักฐานจากโลกมือถือ](#ส่วนที่-6--กล่องนี้ทำอะไร-หลักฐานจากโลกโทรศัพท์มือถือ)**

- ซิมมักบอกตำแหน่งล่าสุด SMS และบันทึกการโทรเป็นหลักฐานที่ดี
- `mobile` ใช้ **Osmocom** ดักจับ **IMSI** จาก GSM (2.5G) แล้วเอาไปซื้อของออนไลน์ ร่องรอยคือ SMS `CENT BST 225` ไปที่ `41970` ผ่านศูนย์ SMS `+86...`
- ผู้เสียหายบน Pantip ถูกหัก 26.75 บาท (25 บาทบวก VAT) จาก `4197005` บริการ CENT BST มีงานวิจัยอย่าง *Shadow Phone and Ghost SIM* รองรับว่าทำแบบนี้ได้

**[Metadata](#ส่วนที่-7--metadata-ข้อมูลที่ไฟล์พกติดตัวไปเอง)**

- ไฟล์หลายรูปแบบมี metadata ที่มีประโยชน์ต่อการสืบสวน **EXIF** เก็บข้อมูลกล้องและอาจมี **GEOTAG** ซึ่งเป็นภัยต่อความเป็นส่วนตัว
- เอกสาร Office บอกว่าใครสร้าง ที่ไหน และบางทีมีประวัติการแก้ไข
- **BTK (Dennis Rader)** ถูกจับจาก metadata ในเอกสาร Word ที่ถูกลบบน floppy disk ซึ่งมีคำว่า "Christ Lutheran Church" และผู้แก้ไขล่าสุด "Dennis"

**[จะเก่งเรื่องนี้](#ส่วนที่-8--จะเก่งเรื่องนี้ต้องมีอะไร)**

- ความรู้กว้างเรื่องระบบ สถาปัตยกรรม เครือข่าย โปรโตคอล และภาษาโปรแกรม คิดแบบคนร้าย ฝึกให้มาก และอดทน
