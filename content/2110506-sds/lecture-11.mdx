## ส่วนที่ 1 — ทำไมต้องคำนวณใกล้ผู้ใช้

### อุปกรณ์เพิ่มเป็นพันล้าน แต่ที่คำนวณอยู่ไกล

<Why>
อุปกรณ์เพิ่มจากหลักล้านเป็นหลักพันล้านเครื่องที่เปิดตลอดเวลา หลายเครื่องติดตัวคน แต่ที่คำนวณกลับไปรวมอยู่ในศูนย์ข้อมูลไม่กี่แห่งที่อยู่ไกล edge computing เกิดขึ้นเพื่อปิดช่องว่างนี้
</Why>

**ฝั่งอุปกรณ์** เริ่มจาก PC ตั้งโต๊ะ มาเป็น laptop แล้วเป็น smartphone ยุคนี้อุปกรณ์อยู่กับที่หรือแค่ถูกหิ้วย้ายที่ (nomadic mobility) และมีจำนวนราวหลักล้านเครื่อง

ยุคถัดมาแตกเป็นสองสาย สายแรกคือ <Term en="Internet of Things (IoT)" th="อุปกรณ์รอบตัวที่ต่อเน็ตได้" /> เช่น เทอร์โมมิเตอร์ หลอดไฟ กล้องวงจรปิด สายที่สองคือ <Term en="wearable" th="อุปกรณ์ที่สวมติดตัว" /> เช่น นาฬิกาและแว่นที่ติดตัวคนเดิน ทั้งสองสายเปิดอยู่ตลอดเวลา (always on) และมีจำนวนราวหลักพันล้านเครื่อง

**ฝั่งที่คำนวณ** เริ่มจาก mainframe มาเป็น server ในยุค <Term en="client-server" th="เครื่องลูกส่งคำขอ เครื่องแม่ข่ายตอบ" /> แล้วรวมเข้าไปเป็น cloud computing ที่อยู่ในศูนย์ข้อมูลใหญ่ไม่กี่แห่ง ขั้นล่าสุดคือ <Term en="Edge computing" th="คำนวณที่ขอบเครือข่าย ใกล้ผู้ใช้" /> ซึ่งวางเครื่องคำนวณไว้ข้างจุดกระจาย WiFi ข้างเสาสัญญาณมือถือ หรือเป็นคลาวด์ย่อยใกล้ผู้ใช้

ช่วงเวลาที่มือถือและ wearable แพร่หลาย ตรงกับช่วงที่คลาวด์ขยับมาเป็น edge และเป็นช่วงของ <Term en="mobile code offloading" th="อุปกรณ์พกพาส่งงานคำนวณไปให้เครื่องอื่นทำ" /> คืออุปกรณ์ตัวเล็กไม่คิดเอง แต่ส่งงานไปให้เครื่องที่แรงกว่าทำแล้วรับผลกลับมา คำถามที่เหลือคือ **ส่งไปให้เครื่องไหน**

### สี่แรงกดดันที่ทำให้ต้องมี edge

**1. Real-time QoS และ delay sensitiveness** <Term en="QoS (Quality of Service)" th="ระดับคุณภาพที่บริการต้องทำให้ได้" /> ของงานแบบนี้คือเงื่อนไขอย่าง latency ต้องไม่เกินกี่ ms งานอย่างแว่นจำหน้าต้องได้คำตอบทันที <Term en="latency" th="เวลาตั้งแต่ส่งคำขอจนได้คำตอบ" /> ส่วนหนึ่งคือเวลาที่สัญญาณเดินทางไปกลับ ซึ่งขึ้นกับระยะทางและจำนวนจุดที่ข้อมูลต้องวิ่งผ่าน เครื่องปลายทางที่แรงขึ้นลดเวลาประมวลผลได้ แต่ลดเวลาเดินทางนี้ไม่ได้

<Example added title="ระยะทางกำหนด latency ขั้นต่ำ">
สัญญาณในสายใยแก้ววิ่งได้ราว 200,000 กิโลเมตรต่อวินาที ระยะทางไปกลับจึงกำหนดเวลาขั้นต่ำไว้แล้ว ก่อนจะนับเวลาประมวลผลหรือเวลาต่อคิวในอุปกรณ์เครือข่ายใด ๆ

```python
# minimum round-trip time over fibre, by straight-line distance
for name, km in [("Bangkok-Singapore", 1427), ("Bangkok-US East", 14140), ("cloudlet 50 m", 0.05)]:
    print(f"{name:18} {2 * km / 200_000 * 1000:10.4f} ms")
```

```text
Bangkok-Singapore     14.2700 ms
Bangkok-US East      141.4000 ms
cloudlet 50 m          0.0005 ms
```

สายจริงคดเคี้ยวกว่าเส้นตรง ตัวเลขจริงจึงสูงกว่านี้
</Example>

**2. Battery lifetime** การคำนวณหนัก ๆ ในเครื่องกินแบตเตอรี่ ย้ายงานส่วนนั้นออกไปให้เครื่องอื่นทำ แบตของแว่นก็อยู่ได้นานขึ้น

**3. Regulating core network traffic** ถ้าอุปกรณ์ทุกตัวส่งข้อมูลดิบขึ้นคลาวด์ ข้อมูลทั้งหมดต้องวิ่งผ่าน <Term en="core network" th="เครือข่ายแกนกลางที่เชื่อมเมืองและประเทศ" /> ในปี 2015 wearable ราว 97 ล้านเครื่องสร้าง traffic 15 PB ต่อเดือน ถ้า edge ประมวลผลข้อมูลไว้ใกล้ผู้ใช้ แล้วส่งขึ้นไปเฉพาะผลลัพธ์ core network ก็แบกน้อยลงมาก

**4. Scalability** อุปกรณ์หลักพันล้านเครื่องวิ่งเข้าศูนย์ข้อมูลไม่กี่แห่ง ศูนย์ข้อมูลกลายเป็นคอขวด แต่ถ้าวางเครื่อง edge เพิ่มตามพื้นที่ที่มีผู้ใช้ กำลังคำนวณก็โตตามจำนวนอุปกรณ์

### Edge กับ Cloud ต่างกันตรงไหน

| เรื่อง | Cloud Computing | Edge Computing |
| --- | --- | --- |
| Latency | สูง | ต่ำ |
| Network access type | ส่วนใหญ่ผ่าน WAN | LAN (WLAN) |
| Server location | ที่ไหนก็ได้ในเครือข่าย | ที่ขอบเครือข่าย ใกล้ผู้ใช้ |
| Mobility support | ต่ำ | สูง |
| Distribution | รวมศูนย์ (centralized) | กระจาย (distributed) |
| งานที่เหมาะ | ต้องการพลังคำนวณสูง | ต้องการ latency ต่ำ |
| User device | คอมพิวเตอร์ ส่วนมือถือรองรับได้จำกัด | มือถือ อุปกรณ์อัจฉริยะ wearable |
| ผู้ดูแล | ผู้ให้บริการคลาวด์ | ธุรกิจท้องถิ่น |
| Number of servers | มาก | น้อย |
| State | soft state และ hard state | soft state อย่างเดียว |

สองแถวแรกไปด้วยกัน edge อยู่ใน <Term en="LAN" th="เครือข่ายในพื้นที่เดียวกัน เช่น WiFi ในร้าน" /> เดียวกับผู้ใช้ ส่วนคลาวด์ต้องข้าม [WAN](/2110506-sds/lecture-10#เครือข่ายของ-google) ไป

แถวจำนวนเซิร์ฟเวอร์นับต่อแห่ง ศูนย์ข้อมูลคลาวด์แห่งหนึ่งมีเซิร์ฟเวอร์มหาศาล แต่จุด edge แต่ละจุดมีไม่กี่เครื่อง

แถวสุดท้ายตอบคำถามว่า ถ้า edge ดับหรือผู้ใช้เดินออกจากพื้นที่ ข้อมูลจะเป็นยังไง <Term en="Hard state" th="ข้อมูลที่ต้องอยู่ถาวร หายไม่ได้" /> คือข้อมูลอย่างฐานข้อมูลใบหน้าทั้งหมด <Term en="Soft state" th="ข้อมูลชั่วคราวที่หายแล้วสร้างใหม่ได้" /> คือภาพที่เพิ่งส่งมาหรือสำเนาที่ดึงมาจากคลาวด์

edge เก็บแค่ soft state จึงหายได้โดยไม่เสียของจริง ถ้า edge ดับ แว่นก็ถอยกลับไปใช้คลาวด์แทน (fallback) ช้าลงแต่ไม่พัง

  <OffloadTiers />
</Figure>

เพราะ edge มีเครื่องน้อยและเก็บแค่ soft state ระบบจริงจึงมีสามชั้น ชั้นล่างคืออุปกรณ์ ชั้นกลางคือเครื่อง edge แบบต่าง ๆ ที่กระจายอยู่ ซึ่งส่วนที่ 2 แยกให้ดูทีละแบบ ชั้นบนคือศูนย์ข้อมูลคลาวด์ที่รวมศูนย์ งานที่ไวต่อเวลา (delay-sensitive) ส่งไปชั้นกลางผ่าน LAN ส่วนงานที่รอได้ (delay-tolerant) ส่งขึ้นคลาวด์ผ่าน WAN

แว่นจำหน้าใช้ทั้งสองชั้น การหาว่าในภาพมีใบหน้าอยู่ตรงไหนต้องทำทันที จึงทำที่ edge ส่วนการเทียบใบหน้ากับฐานข้อมูลขนาดใหญ่ทำที่คลาวด์ ไม่ใช่เพราะรอได้ ผู้ใช้ยังรอชื่ออยู่ แต่เพราะฐานข้อมูลที่เก็บไว้ถาวรและพลังคำนวณที่ต้องใช้อยู่ที่นั่น ส่วนที่ 2 จะไล่ดูขั้นตอนนี้ทีละขั้น

<Quiz question="ระบบ smart grid ของหมู่บ้านหนึ่งมีสองงาน งานแรกคือตัดไฟทันทีเมื่อตรวจพบสายไฟลัดวงจร งานที่สองคือสรุปยอดใช้ไฟรายเดือนของทุกบ้านเพื่อออกบิล แต่ละงานควรไปทำที่ชั้นไหน">
งานตัดไฟรอไม่ได้ ทุกมิลลิวินาทีที่ช้าคือความเสียหาย จึงเป็นงาน delay-sensitive ส่วนยอดใช้ไฟรายเดือนรอได้เป็นวัน แต่ต้องเก็บไว้ถาวรและห้ามหาย ซึ่งเป็น hard state

คำตอบคือ **งานตัดไฟทำที่ edge ใกล้หมู่บ้าน ผ่าน LAN และงานออกบิลส่งขึ้นคลาวด์ ผ่าน WAN**

คำตอบที่ผิดบ่อยคือ "ทำที่ edge ทั้งคู่ เพราะ edge เร็วกว่า" ซึ่งลืมว่า edge เก็บแค่ soft state ถ้าเครื่อง edge ดับ ยอดใช้ไฟทั้งเดือนก็หายไปด้วย
</Quiz>

edge มีไว้สำหรับงานที่รอไม่ได้ เพราะระยะทางกำหนด latency ขั้นต่ำที่เครื่องแรงแค่ไหนก็ลดไม่ได้ ส่วนคลาวด์ยังเป็นที่ของงานหนักและข้อมูลถาวร ทั้งสองชั้นทำงานคู่กัน
</KeyIdea>

## ส่วนที่ 2 — Edge computing สี่แบบ

### Mobile Cloud Computing (MCC)

<Why>
มือถือมีทรัพยากรน้อยและแบตเตอรี่จำกัด แต่ผู้ใช้อยากได้แอปที่หลากหลายและหนักขึ้นเรื่อย ๆ
</Why>

<Term en="Mobile Cloud Computing (MCC)" th="ให้มือถือยืมพลังคำนวณจากที่อื่น" /> คือการให้อุปกรณ์พกพาใช้ทรัพยากรของเครื่องอื่นแทนของตัวเอง ซึ่งใช้ mobile code offloading ในส่วนที่ 1 เป็นกลไกหลัก แรงจูงใจมีสี่ข้อ คือยืดอายุแบตเตอรี่ ให้บริการแอปได้หลากหลาย แก้ปัญหาทรัพยากรในมือถือไม่พอ และใช้ประโยชน์จาก virtualization ที่แบ่งเครื่องใหญ่ให้ผู้ใช้หลายคน

MCC มีสามแบบ ต่างกันที่ว่าส่งงานไปให้ใคร

| แบบ | ส่งงานไปที่ไหน |
| --- | --- |
| Cloud/Infrastructure-based | ส่งผ่านอินเทอร์เน็ตไปคลาวด์ที่อยู่ไกล |
| Ad-hoc | อุปกรณ์พกพาที่อยู่ใกล้กันรวมทรัพยากรช่วยกันเอง โดยไม่ผ่านโครงสร้างพื้นฐาน |
| Cloudlet-based | ส่งไปเครื่องที่อยู่ใกล้ ๆ ซึ่งเป็นหัวข้อถัดไป |

เมื่อเทียบกับคลาวด์ธรรมดา MCC ทำได้ทุกอย่างที่คลาวด์ทำ คือลดเวลาทำงาน เพิ่มพื้นที่เก็บข้อมูล เชื่อถือได้ ขยายได้ เรียกใช้ได้ง่ายตามต้องการ และใช้ร่วมกันหลายผู้ใช้ ([multi-tenancy](/2110506-sds/lecture-7#ฝั่งผู้ให้บริการทำอะไร)) แต่มีสองอย่างที่คลาวด์ธรรมดาไม่มี คือ **ช่วยประหยัดพลังงานของอุปกรณ์** และ **จัดการการเคลื่อนที่ของผู้ใช้** (mobility management)

### Cloudlet

<Why>
MCC แบบส่งไปคลาวด์ไกลติด latency สูง แบบให้มือถือช่วยกันเองก็ติดที่มือถือแต่ละเครื่องมีพลังคำนวณน้อย ต้องมีชั้นกลางระหว่างสองแบบนี้
</Why>

<Term en="Cloudlet" th="คลาวด์ขนาดเล็กที่ตั้งอยู่ใกล้ผู้ใช้" /> คือชั้นกลางนั้น คุณสมบัติมีห้าข้อ

- **พลังคำนวณพอ** สำหรับงานที่อุปกรณ์ทำเองไม่ไหว
- **ตอบเร็ว เพราะห่างหนึ่ง hop** แว่นต่อ WiFi ของร้าน แล้วส่งถึง cloudlet ที่ต่ออยู่กับจุดกระจายสัญญาณตัวเดียวกันได้เลย
- **ใช้ได้แม้ออฟไลน์** (offline availability) ถ้าทางออกอินเทอร์เน็ตไปคลาวด์ขาด cloudlet ในร้านก็ยังทำงานต่อได้
- **คุ้มค่า** (cost effectiveness)
- **แทบไม่ต้องดูแล** (minimum management effort)

<Analogy>
cloudlet เหมือนร้านโชห่วยปากซอย ส่วนคลาวด์เหมือนห้างค้าส่งอย่างแม็คโครที่อยู่อีกฝั่งเมือง ร้านปากซอยคือ cloudlet ที่ห่างหนึ่ง hop เดินไปถึงในหนึ่งนาที ห้างค้าส่งคือคลาวด์ที่ต้องข้ามเมืองไป

ของในร้านคือ soft state ร้านไม่ได้ผลิตเอง แต่ขนมาจากห้างค้าส่งนั้น ของหมดก็ไปขนมาเติมใหม่ได้ วันที่ถนนเข้าเมืองน้ำท่วม ร้านก็ยังขายของที่มีอยู่ได้ เหมือน offline availability

อุปมานี้ใช้ไม่ได้ตรงที่ร้านแค่ขายต่อของสำเร็จรูปที่ขนมา แต่ cloudlet คำนวณงานใหม่ให้ทุกคำขอ
</Analogy>

### Fog Computing

<Why>
งานอย่างจำหน้าต้องใช้ทั้งเครื่องใกล้ตัวและฐานข้อมูลบนคลาวด์ในคำขอเดียว
</Why>

<Term en="Fog Computing" th="ชั้นคำนวณระหว่างอุปกรณ์กับคลาวด์ ที่ทำงานคู่กับคลาวด์" /> เน้นสองข้อ คือต้องรองรับงาน real-time และปกติทำงานต่อเนื่องเป็นเนื้อเดียวกับการคำนวณบนคลาวด์ แว่นจำหน้าคือตัวอย่างของบริการที่แบ่งงานระหว่าง fog server กับ cloud server

<StepThrough>
<Step title="แว่นอัปโหลดภาพ">

แว่นถ่ายภาพคนตรงหน้า แล้วส่งภาพไปที่ fog server ที่อยู่ใกล้ (image upload)

</Step>
<Step title="fog หาใบหน้า">

fog server ทำ face detection หาว่าในภาพมีใบหน้าอยู่ตรงไหน งานนี้ต้องเร็ว จึงทำใกล้ผู้ใช้

</Step>
<Step title="fog เตรียมภาพ">

fog server ทำ image preprocess เตรียมส่วนที่เป็นใบหน้าให้พร้อมเทียบ แล้วส่งต่อขึ้น cloud server

</Step>
<Step title="cloud จำว่าเป็นใคร">

cloud server ทำ pattern recognition เทียบใบหน้ากับ image DB ขนาดใหญ่ ซึ่งเป็น hard state ที่ต้องอยู่บนคลาวด์

</Step>
<Step title="ส่งชื่อกลับแว่น">

ผลส่งกลับลงมาที่ fog server แล้ว fog ส่งผล face identification กลับไปที่แว่น

</Step>
</StepThrough>

งานที่ต้องเร็วและทำได้ด้วยเครื่องเล็กอยู่ที่ fog งานที่ต้องใช้ข้อมูลมหาศาลอยู่ที่คลาวด์

### Mobile-Edge Computing (MEC)

traffic ของมือถือโตเร็วมาก <Term en="Mobile-Edge Computing (MEC)" th="วางเครื่องคำนวณไว้ในเครือข่ายมือถือ ข้างเสาสัญญาณ" /> จึงวางเครื่องคำนวณไว้ในเครือข่ายของผู้ให้บริการมือถือ

มาตรฐานของ MEC ออกในปี 2017 โดยกลุ่ม Industry Specification Group (ISG) ภายใน ETSI ซึ่งเป็นองค์กรออกมาตรฐานโทรคมนาคมของยุโรป

มาตรฐานแบ่งตัวที่ต้องวัดเป็นสองกลุ่ม

| กลุ่ม | สิ่งที่วัด |
| --- | --- |
| Functional | latency, energy efficiency, throughput, goodput (ข้อมูลที่มีประโยชน์จริงต่อวินาที ไม่นับส่วนที่ส่งซ้ำ), packet loss, jitter (ความไม่สม่ำเสมอของ latency), QoS |
| Non-functional | service availability, reliability, service load, จำนวน API request |

กลุ่มแรกคือคุณภาพของการส่งข้อมูล กลุ่มที่สองคือสุขภาพของบริการ ว่ายังเปิดอยู่ไหม รับภาระอยู่เท่าไหร่

### แผนที่ของ edge computing

edge computing เป็นชื่อรวมของหลายข้อเสนอ ที่ต่างกันตามสองแกน แกนแรกคือ **อยู่ใกล้ผู้ใช้แค่ไหน** (proximity/locality) ไล่จาก edge ผ่านชั้นกลาง (middle tier) ไปถึงศูนย์กลาง (center)

แกนที่สองคือ **โครงสร้างเป็นระเบียบแค่ไหน** (regularity/complexity) ศูนย์ข้อมูลคลาวด์เป็นเครื่องแบบเดียวกันเรียงเป็นแถว จึงเป็นระเบียบมาก (highly regular) ส่วนโลกของ IoT และ wearable มีอุปกรณ์ร้อยแบบที่ต่อเข้าออกตลอดเวลา จึงไม่เป็นระเบียบ (irregular)

| กลุ่ม | ใกล้ผู้ใช้แค่ไหน | ความเป็นระเบียบ | สมาชิก |
| --- | --- | --- | --- |
| IoT, mobile gadget, wearable | ที่ขอบ ถึงชั้นกลาง | ไม่เป็นระเบียบ | Cloudlet, Fog Computing, Mobile Cloud Computing (MCC) |
| โครงสร้างพื้นฐานโทรคมนาคม | ที่ขอบ ถึงชั้นกลาง | เป็นระเบียบ | Mobile-Edge Computing (MEC), Network Functions Virtualization (NFV) |
| Standard utility computing | ศูนย์กลาง | เป็นระเบียบมาก | คลาวด์และศูนย์ข้อมูลแบบเดิม |

NFV คือการทำหน้าที่ของอุปกรณ์เครือข่ายให้เป็นซอฟต์แวร์ ซึ่งพบครั้งแรกใน [Lecture 1](/2110506-sds/lecture-1) และจะกลับมาในส่วนที่ 4 อีกสี่ชื่อ คือ MCC, cloudlet, fog และ MEC คือสี่แบบของ edge ที่เพิ่งไล่ดูมา

### เทียบ Cloudlet, Fog และ MEC

สามแบบนี้มีเจ็ดอย่างที่เหมือนกัน คือให้ทรัพยากรคำนวณที่ขอบเครือข่าย, use case, อุปกรณ์ผู้ใช้, ตัววัดประสิทธิภาพ, การเข้าถึงแบบไร้สาย, เซิร์ฟเวอร์ที่กระจายอยู่ และการรับรู้บริบทของผู้ใช้ (context-awareness)

จุดที่ต่างกันมีเจ็ดเรื่อง คือ ownership, coverage, access technology, server density, cost/CAPEX, flow characteristics และ number of active users ห้าเรื่องในนั้นเทียบกันได้แบบนี้

| เรื่อง | MEC | Cloudlet | Fog |
| --- | --- | --- | --- |
| Coverage (พื้นที่ที่ครอบคลุม) | สูงมาก | ต่ำ | ต่ำ |
| Server density (ความหนาแน่นของเซิร์ฟเวอร์) | ต่ำ | สูงมาก | กลาง |
| Cost/CAPEX (เงินลงทุน) | สูง | ค่อนข้างต่ำ | ต่ำที่สุด |
| Flow characteristics (traffic continuity) | กลาง | สูงมาก | สูงมาก |
| Active users | ค่อนข้างต่ำ | สูง | สูงมาก |

ownership คือใครเป็นเจ้าของเครื่อง และ access technology คือผู้ใช้ต่อเข้ามาทางไหน สองเรื่องนี้ไม่มีระดับให้เทียบ ส่วน flow characteristics วัดความต่อเนื่องของ traffic (traffic continuity) ซึ่งสไลด์ไม่ได้อธิบายต่อว่าวัดอย่างไร

ระดับในตารางเป็นการเทียบกันเองสามแบบ ไม่มีหน่วย ภาพที่ได้คือ MEC ครอบคลุมพื้นที่กว้างด้วยเซิร์ฟเวอร์ไม่กี่จุดแต่ลงทุนสูง เพราะเกาะไปกับเสาสัญญาณมือถือ ส่วน cloudlet และ fog เป็นเครื่องเล็กราคาถูกจำนวนมาก แต่ละจุดครอบคลุมพื้นที่แคบ และรองรับผู้ใช้จำนวนมากในพื้นที่นั้น

<Quiz question="ห้างแห่งหนึ่งอยากทำแอป AR นำทางในห้าง ผู้ใช้อยู่แค่ในตัวห้าง มีคนใช้พร้อมกันหลายพันคน และงบลงทุนไม่มาก ควรเลือก MEC หรือ cloudlet/fog">
พื้นที่ที่ต้องครอบคลุมมีแค่ตัวห้าง coverage กว้างของ MEC จึงไม่ได้ช่วยอะไร แต่โจทย์ต้องการเซิร์ฟเวอร์หนาแน่นในพื้นที่แคบ รองรับผู้ใช้จำนวนมาก และลงทุนต่ำ ซึ่งเป็นจุดแข็งของ cloudlet และ fog ทั้งหมด

คำตอบคือ **cloudlet หรือ fog** วางไว้ในห้าง ให้มือถือต่อ WiFi ของห้างแล้วถึงเครื่องในหนึ่ง hop

คำตอบที่ผิดบ่อยคือ "MEC เพราะชื่อมีคำว่า mobile และผู้ใช้ถือมือถือ" ซึ่งดูแค่ชื่อ จุดเด่นของ MEC คือครอบคลุมทั้งเมืองผ่านเครือข่ายมือถือ ซึ่งงานในห้างไม่ต้องใช้ แต่ต้องจ่ายราคาของมัน
</Quiz>

<KeyIdea>
MCC คือแนวคิดให้อุปกรณ์พกพายืมพลังคำนวณจากที่อื่น cloudlet คือเครื่องที่ห่างหนึ่ง hop และใช้ได้แม้ออฟไลน์ fog ทำงานคู่กับคลาวด์ ส่วน MEC อยู่ในเครือข่ายมือถือ ครอบคลุมกว้างแต่ลงทุนสูง
</KeyIdea>

## ส่วนที่ 3 — ความยากของ edge และทำไมต้องใช้ SDN

### สี่โจทย์ที่ edge เพิ่มเข้ามา

<Why>
คลาวด์มีศูนย์ข้อมูลไม่กี่แห่ง จัดการจากที่เดียวได้ แต่ edge คือเครื่องเล็กหลายร้อยจุดกระจายทั่วเมือง หลายเจ้าของ และผู้ใช้เดินไปมาตลอด ความง่ายของการรวมศูนย์หายไป
</Why>

ผลคือมีโจทย์ทางเทคนิคสี่ข้อ

| โจทย์ | หมายถึงอะไร | ในตัวอย่างแว่นจำหน้า |
| --- | --- | --- |
| Service synchronization & orchestration | แต่ละชั้นต้องประสานงานกัน | ส่วนที่ fog กับส่วนที่คลาวด์ต้องทำงานเข้าจังหวะกัน |
| Seamless service delivery | บริการต้องไม่สะดุด ทั้งที่เครื่องในพื้นที่ถูกใช้ร่วมกันหลายผู้ใช้ (multi-tenancy) และมีผู้ให้บริการหลายเจ้า | ผู้ใช้เดินจาก cloudlet ของร้านกาแฟเข้าไปในเขต cloudlet ของห้าง |
| Service-centric structure | บริการกับเซิร์ฟเวอร์โยงกันซับซ้อน | บริการจำหน้ามีหลายสำเนาบนหลายเครื่อง และย้ายที่ได้ |
| Soft state | edge ต้องรองรับ fallback ให้ผู้ใช้ได้ | edge ดับ แว่นต้องหันไปใช้คลาวด์ได้ทันที |

### ยกความซับซ้อนทั้งหมดไปไว้ที่ control plane

คำตอบของสี่โจทย์นี้สรุปได้ในประโยคเดียว คือ **push all complexity to the control plane** ใน SDN ตัว switch ทำแค่ส่ง packet ตามกฎ ส่วนการตัดสินใจทั้งหมดอยู่ที่ SDN controller ซึ่งมองเห็นเครือข่ายทั้งผืน (ทบทวนได้ที่ [Lecture 10](/2110506-sds/lecture-10#สามชิ้นที่ทำงานด้วยกัน))

  <SdnEdgeLayers />
</Figure>

ระบบแบ่งเป็นสามชั้น

- **Northbound applications** ด้านบนคือแอปที่สั่งงานเครือข่าย เช่น service orchestration, load balancer, resource management, mobility management และ firewall รวมถึงบริการบน edge เช่น บริการสุขภาพ ความบันเทิง และการจำหน้า แอปพวกนี้คุยกับ controller ผ่าน Northbound API (ทบทวน [API สามทิศ](/2110506-sds/lecture-10#api-สามทิศ) ได้ใน Lecture 10)
- **SDN infrastructure** ตรงกลางคือ controller กับ switch ที่รองรับ OpenFlow controller คุมทุก switch ผ่าน Southbound API ซึ่งในที่นี้คือ OpenFlow
- **Edge layer** ด้านล่างคือผู้ใช้กับมือถือ นาฬิกา แว่น และเครื่องคำนวณอย่าง cloudlet และ host machine ที่ส่ง service request และรับ reply ผ่าน switch

### สี่งานที่ controller ทำให้ edge

แอปด้าน service management และ orchestration ที่อยู่บน controller มีสี่งาน

| งาน | ทำอะไร | ในตัวอย่างแว่นจำหน้า |
| --- | --- | --- |
| Service discovery | จดว่ามีบริการอะไรอยู่บ้าง และอยู่ที่ไหน | รู้ว่าบริการจำหน้ามีอยู่บน cloudlet ของเขต 1 |
| Service commissioning & migration | เปิดบริการขึ้นบน cloudlet แต่ละเครื่อง และย้ายบริการข้าม cloudlet เมื่อจำเป็น | เปิดบริการจำหน้าเพิ่มบน cloudlet ของเขต 2 |
| Performance tuning & optimisation | เฝ้าดูว่าบริการถูกใช้แค่ไหน และจัดภาระบนเครือข่าย | cloudlet เขต 1 แน่น ก็แบ่งผู้ใช้บางส่วนไปเครื่องอื่น |
| User handover | ส่งต่อผู้ใช้จากจุดหนึ่งไปอีกจุดเมื่อผู้ใช้เคลื่อนที่ | ผู้ใช้เดินจากเขต 1 เข้าเขต 2 ก็ส่งต่อไปเครื่องในเขต 2 |

ผลดีของการใช้ SDN กับ edge มีแปดด้าน

| ด้าน | ความหมาย |
| --- | --- |
| High resolution and effective control | controller เห็นเครือข่ายทั้งผืน และคุมได้ละเอียดถึงระดับ flow |
| Flexibility and low barrier on innovation | ฟังก์ชันใหม่คือแอปตัวใหม่บน controller ไม่ต้องซื้ออุปกรณ์ใหม่ |
| Service centric implementation | พาคำขอไปตามบริการที่ผู้ใช้ต้องการ ไม่ใช่ตามที่อยู่ของเครื่อง (ส่วนที่ 4) |
| Virtual machine mobility | บริการที่รันใน virtual machine ย้ายข้าม cloudlet ได้ แล้ว controller แก้เส้นทางตาม |
| Adaptability | ปรับเส้นทางได้ทันทีเมื่อภาระหรือสภาพเครือข่ายเปลี่ยน |
| Interoperability | OpenFlow เป็นมาตรฐานเปิด อุปกรณ์ต่างยี่ห้อทำงานร่วมกันได้ |
| Low cost solution | switch เหลือแค่งานส่ง packet จึงใช้อุปกรณ์ราคาถูกได้ |
| Multiplicity of scope | ตามตัวคำคือ SDN ใช้ได้กับหลายขอบเขต สไลด์มีแค่ชื่อ ไม่ได้บอกว่าขอบเขตในที่นี้หมายถึงอะไร |

<Quiz question="ผู้ใช้แว่นจำหน้าสองคนเดินจากเขต 1 เข้าเขต 2 ซึ่งยังไม่มีบริการจำหน้า คนแรกแวะแค่ 30 วินาทีแล้วเดินกลับเขต 1 คนที่สองนั่งทำงานในเขต 2 ทั้งบ่าย controller ควรจัดการสองคนนี้ต่างกันไหม">
ทั้งสองคนเริ่มเหมือนกัน controller เห็นว่าผู้ใช้ย้ายไปต่อกับ switch ของเขต 2 นี่คืองาน user handover จากนั้นมีสองทาง ทางแรกคือพา traffic ย้อนกลับไปหา cloudlet เขต 1 ซึ่งได้ผลทันทีแต่เส้นทางยาวขึ้น ทางที่สองคือเปิดบริการบน cloudlet เขต 2 (commissioning & migration) แล้วแจ้ง service discovery ว่าบริการมีที่ใหม่ controller จึงติดตั้งกฎให้ switch พาคำขอไปที่นั่น

ทางที่สองทำได้ง่ายเพราะ edge เก็บแค่ soft state ไม่มีข้อมูลถาวรต้องย้ายตาม แต่ก็ยังต้องใช้เวลาและเครื่องของเขต 2

คำตอบคือ **ต่างกัน คนแรกพา traffic ย้อนไปเขต 1 ก็พอ เพราะทางยาวขึ้นแค่ครู่เดียว ส่วนคนที่สองคุ้มที่จะเปิดบริการบน cloudlet เขต 2** ทั้งสองกรณีแว่นยังขอ "บริการจำหน้า" เหมือนเดิม

คำตอบที่ผิดบ่อยคือ "ย้ายบริการตามผู้ใช้ทุกครั้ง เพราะ edge ต้องอยู่ใกล้ที่สุด" ซึ่งลืมว่าการเปิดบริการใหม่มีต้นทุน ถ้าผู้ใช้เดินกลับก่อนบริการพร้อม ก็เสียแรงเปล่า
</Quiz>

<KeyIdea>
edge มีเครื่องกระจายหลายจุด หลายเจ้าของ และผู้ใช้เคลื่อนที่ตลอด SDN แก้ด้วยการยกความซับซ้อนทั้งหมดไปไว้ที่ controller ซึ่งรู้ว่าบริการอยู่ที่ไหน เปิดและย้ายบริการได้ และส่งต่อผู้ใช้ไปเครื่องใหม่ได้ โดยที่อุปกรณ์ไม่ต้องรู้อะไรเลย
</KeyIdea>

  <MultiTierEdge />
</Figure>

รูปที่ 3 คือรูปที่ 1 ที่ใส่ชั้นกลางเพิ่มและใส่เครือข่ายเข้าไป **Tier-1** คือผู้ใช้กับ cloudlet ที่อยู่ใต้ switch ตัวเดียวกัน **Tier-2** คือ metro cloud ระดับเมือง ต่อกันผ่าน <Term en="MAN (Metropolitan Area Network)" th="เครือข่ายระดับเมือง" /> และ **Tier-3** คือศูนย์ข้อมูลคลาวด์ ต่อผ่าน WAN

controller ต่อกับ switch ของทั้งสามชั้น และมี service orchestrator อยู่ด้านบน ผลคือมันเลือกได้ว่างานแต่ละชิ้นควรไปจบที่ชั้นไหน งานที่ต้องเร็วจบที่ Tier-1 งานที่หนักขึ้นส่งขึ้นไปชั้นบน

### เรียกบริการด้วยชื่อ ไม่ใช่ด้วยที่อยู่

<Why>
ในเครือข่ายธรรมดา ผู้ใช้ต้องรู้ที่อยู่ของเซิร์ฟเวอร์ก่อนจะส่งอะไรไปได้ แต่บน edge บริการหนึ่งมีหลายสำเนาและย้ายที่ได้ ที่อยู่ที่จำไว้เมื่อห้านาทีก่อนอาจใช้ไม่ได้แล้ว
</Why>

<Term en="Service-centric access" th="ขอใช้บริการด้วยชื่อบริการ แล้วเครือข่ายหาเครื่องให้" /> แก้ด้วยการให้ผู้ใช้บอกแค่ว่าต้องการบริการอะไร แล้วเครือข่ายเป็นฝ่ายหาว่าบริการนั้นอยู่ที่ไหน

<Figure number={4} caption="คำขอบริการสุขภาพวิ่งจากมือถือ ผ่าน switch ไปถึงเซิร์ฟเวอร์ Healthcare ใน 6 ขั้น">
  <ServiceCentricAccess />
</Figure>

ตลอดหกขั้น มือถือไม่เคยรู้ที่อยู่ของเซิร์ฟเวอร์ Healthcare มันบอกแค่ชื่อบริการ

ขั้น 2 และ 3 คือ table-miss แบบใน [Lecture 10](/2110506-sds/lecture-10#packet-แรกที่ไม่มีแถวรองรับ) switch ตัวแรกไม่มีกฎสำหรับคำขอนี้จึงถาม controller ต่างกันตรงที่ controller ถาม service discovery ผ่าน northbound interface ก่อน แล้วจึงติดตั้งกฎกลับลงมา

### Service Function Chaining บน NFV

<Why>
traffic ก่อนถึงเซิร์ฟเวอร์มักต้องผ่านหลายด่านตามลำดับ เช่น firewall ก่อน แล้วตรวจเนื้อหา แล้วค่อยกระจายภาระ แบบเดิมแต่ละด่านคือกล่องฮาร์ดแวร์ที่ต้องเดินสายเรียงกันจริง ๆ จะเพิ่มด่านหรือสลับลำดับก็ต้องเดินสายใหม่
</Why>

NFV ทำให้แต่ละด่านเป็นซอฟต์แวร์ที่รันใน virtual machine บนเครื่องไหนก็ได้ ปัญหาที่ตามมาคือ เมื่อด่านกระจายอยู่ทั่วเครือข่าย จะบังคับให้ traffic ผ่านครบทุกด่านตามลำดับได้ยังไง

<Term en="Service Function Chaining (SFC)" th="ร้อยฟังก์ชันเครือข่ายหลายตัวเป็นลำดับที่ traffic ต้องผ่าน" /> คือคำตอบ ลำดับในตัวอย่างคือ client → firewall → DPI → load balancer → server

<Term en="Deep Packet Inspector (DPI)" th="ตัวตรวจเนื้อหาข้างใน packet" /> คือด่านที่อ่านเนื้อหาข้างใน packet ไม่ใช่แค่ header

<Figure number={5} caption="บนแผนที่ลำดับคือ firewall → DPI → load balancer ส่วนในเครือข่ายจริงมี VM สี่ตัวกระจายอยู่คนละมุม สามตัวอยู่บนทางของ traffic แอป SFC สั่ง controller ให้ switch พา traffic ผ่านครบตามลำดับ">
  <ServiceChain />
</Figure>

แอป SFC อยู่บน controller (northbound) แล้ว controller ติดตั้งกฎผ่าน OpenFlow ให้ switch แต่ละตัวส่ง traffic ต่อไปยัง VM ตัวถัดไปในลำดับ VM จะอยู่ห่างกันแค่ไหน ลำดับที่ traffic ผ่านก็ยังเหมือนเดิม

<Quiz question="ในรูปที่ 5 DPI VM ตัวที่อยู่ใกล้ client รับภาระไม่ไหว ผู้ดูแลจึงเปิด DPI VM อีกตัวที่มุมอื่นของเครือข่าย ต้องเดินสายใหม่หรือแก้อะไรที่ฝั่ง client ไหม">
ลำดับ firewall → DPI → load balancer อยู่ในแอป SFC และถูกบังคับด้วยกฎที่ controller ติดตั้งใน switch ไม่ได้อยู่ที่สายไฟ แอป SFC จึงแค่สั่ง controller ให้ส่ง flow บางส่วนไปผ่าน DPI ตัวใหม่แทน

คำตอบคือ **ไม่ต้องเดินสายและไม่ต้องแก้ client** แค่เปลี่ยนกฎใน switch ลำดับของด่านยังเหมือนเดิมทุกประการ

คำตอบที่ผิดบ่อยคือ "ต้องย้าย DPI ตัวใหม่ไปวางระหว่าง firewall กับ load balancer" ซึ่งคิดแบบกล่องฮาร์ดแวร์ ใน SFC ตำแหน่งทางกายภาพของ VM ไม่ได้กำหนดลำดับ กฎใน switch เป็นตัวกำหนด
</Quiz>

<KeyIdea>
SDN controller คุม switch ทุกชั้นตั้งแต่ cloudlet ถึงคลาวด์ จึงพาคำขอไปหาบริการตามชื่อได้ (service-centric access) และบังคับให้ traffic ผ่านฟังก์ชันเครือข่ายที่กระจายอยู่ตามลำดับได้ (SFC) โดยไม่ต้องเดินสายใหม่และไม่ต้องให้อุปกรณ์รู้ที่อยู่ของอะไรเลย
</KeyIdea>

## ส่วนที่ 5 — Edge เหมาะกับงานไหน และยังต้องแก้อะไร

### งานที่เหมาะกับ edge

แต่ละงานต้องการ edge ด้วยเหตุผลต่างกัน ส่วนใหญ่คือแรงกดดันในส่วนที่ 1 คนละข้อ บางงานอย่าง military ต้องการคุณสมบัติของ cloudlet ที่ใช้ได้แม้ออฟไลน์

| Use case | edge ช่วยตรงไหน |
| --- | --- |
| Cognitive assistance ทั้งในโรงงานอุตสาหกรรมและสำหรับผู้พิการ | ต้องตอบทันที แบบแว่นจำหน้า |
| Body Area Network (BAN) และ healthcare | เซ็นเซอร์บนร่างกายแบตน้อย และสัญญาณผิดปกติต้องแจ้งทันที |
| Military และพื้นที่อันตราย (hostile environments) | ทางไปคลาวด์ไม่แน่นอน ต้องใช้ได้แม้ออฟไลน์ |
| Language and speech processing | คุยโต้ตอบต้องได้คำตอบทันที |
| Smart grid | ตัดไฟหรือสลับวงจรได้ทันที (Quiz ในส่วนที่ 1) |
| IoT และ wireless sensor networks | เซ็นเซอร์จำนวนมาก ส่งดิบขึ้นคลาวด์ทั้งหมดไม่ไหว |
| Video streaming and analysis | วิดีโอกิน bandwidth มาก วิเคราะห์ใกล้กล้องแล้วส่งแค่ผล (ส่วนที่ 6) |
| Augmented reality | ภาพซ้อนต้องตามการหันหัวทัน |
| Connected vehicles และ smart traffic lights | รถเคลื่อนที่เร็ว คำเตือนต้องมาทัน |

### รถยนต์และไฟจราจรอัจฉริยะ

<Term en="Vehicular edge computing" th="edge computing ที่ใช้กับรถยนต์และถนน" /> คือตัวอย่างที่งาน delay-sensitive ชัดที่สุด รถเคลื่อนที่เร็ว คำเตือนที่มาช้าไปหนึ่งวินาทีก็ไร้ค่าแล้ว

| การเชื่อมต่อ | ระหว่าง |
| --- | --- |
| V2V (vehicle-to-vehicle) | รถกับรถคันข้าง ๆ คุยกันตรง |
| I2V (infrastructure-to-vehicle) | เสาสัญญาณข้างถนนหรือไฟจราจรส่งข้อมูลถึงรถ |
| V2I (vehicle-to-infrastructure) | รถส่งข้อมูลถึงไฟจราจรหรือเสาสัญญาณ |

เสาสัญญาณข้างถนนกับไฟจราจรทำหน้าที่เป็นจุด edge ใกล้รถ ทั้งสองต่อกันเองและต่อขึ้นไปหาคลาวด์ คลาวด์เหมาะกับงานที่มองภาพรวมทั้งเมืองซึ่งรอได้ ส่วนคำเตือนระหว่างรถกับรถวิ่งตรงโดยไม่ผ่านคลาวด์

### โจทย์วิจัยที่ยังเปิดอยู่

SDN สำหรับ edge ยังมีงานค้างสามกลุ่ม

| กลุ่ม | หัวข้อ |
| --- | --- |
| Protocol and standardization | ปรับปรุง OpenFlow, ทำ northbound interface ให้เป็นมาตรฐาน, ความสามารถในการ debug SDN, และ East-West Interface |
| Scalability | administrative scalability (หลายเจ้าของ หลายฝ่ายดูแล), geographical scalability (กระจายกว้างทางภูมิศาสตร์), scalability คู่กับ reliability, และการควบคุมกับ abstraction ที่ละเอียดขึ้น |
| Networking | ปรับปรุง forwarding plane (ส่วนที่ส่ง packet ต่อ หรือ data plane) และ network visualization |

northbound interface ยังไม่มีมาตรฐานกลาง แอปที่เขียนให้ controller เจ้าหนึ่งจึงย้ายไปใช้กับอีกเจ้าได้ยาก ส่วน east-west interface สำคัญกับ edge เพราะเมืองหนึ่งอาจมี controller หลายตัวของหลายเจ้าของ ซึ่งต้องคุยกันเพื่อส่งต่อผู้ใช้ข้ามเขต

### ลองออกแบบเอง

ลองเลือก use case หนึ่งจากตาราง แล้วออกแบบระบบให้ครบสี่ช่อง

1. **Objectives** ระบบนี้ทำเพื่ออะไร
2. **Requirements** ต้องการอะไร เช่น latency เท่าไหร่ ต้องใช้ได้ออฟไลน์ไหม
3. **System architecture** งานส่วนไหนอยู่ที่อุปกรณ์ ที่ edge และที่คลาวด์ และเครือข่ายพาข้อมูลไปยังไง
4. **Discussion** ข้อดี ข้อเสีย และสิ่งที่ยังแก้ไม่ได้

ส่วนที่ 6 คือระบบจริงหนึ่งระบบที่แบ่งงานแบบนี้

<KeyIdea>
use case ของ edge ส่วนใหญ่โยงกลับไปที่แรงกดดันสี่ข้อ คือต้องตอบทันที แบตจำกัด traffic ล้น core network และอุปกรณ์มีจำนวนมหาศาล บางงานต้องการให้ระบบใช้ได้แม้ทางไปคลาวด์ขาด ส่วนโจทย์ที่ยังเปิดอยู่เป็นเรื่องของมาตรฐาน การขยายขนาด และตัวเครือข่ายเอง
</KeyIdea>

- **End devices** คือกล้อง เก็บข้อมูล IoT และภาพ real-time แล้วส่งให้ edge device
- **Edge devices** วิเคราะห์ภาพ real-time เอง และส่งภาพขึ้นคลาวด์เฉพาะเมื่อเจอวัตถุที่ไม่รู้จัก

### แยกของที่รู้จักออกจากของที่ไม่รู้จัก

edge device ทำสามขั้นกับทุกภาพ

1. <Term en="Image Matting (IM)" th="ลบพื้นหลังออก เหลือของที่อยู่ข้างหน้าเป็นสีขาว" /> ทำให้ทุกอย่างที่อยู่ข้างหน้า ทั้งที่รู้จักและไม่รู้จัก กลายเป็นพื้นที่สีขาว
2. **Object Detection (OD)** ตีกรอบรอบวัตถุที่โมเดลรู้จัก
3. **Image cutting** ตัดส่วนที่ IM กับ OD ซ้อนกันออก ส่วนนั้นคือวัตถุที่รู้จัก ส่วนสีขาวที่เหลืออยู่คือวัตถุที่ไม่รู้จัก ซึ่งจะถูกส่งขึ้นคลาวด์

ขั้นถัดมาคือวัดว่าเหลือสีขาวเท่าไหร่ <Term en="Residual area (ra)" th="สัดส่วนพื้นที่ของวัตถุที่ไม่รู้จักต่อพื้นที่ทั้งภาพ" /> คือพื้นที่ของวัตถุที่ไม่รู้จัก หารด้วยพื้นที่ทั้งภาพ

ถ้าค่า ra สูงถึงเกณฑ์ α ซ้ำบ่อยถึง β ครั้ง คลาวด์จะฝึกโมเดลใหม่ (AI retraining) เพื่อให้ได้ความรู้ใหม่ แล้วส่งโมเดลลงไปแทนตัวเก่าที่ edge (AI updating)

ลองทายก่อน ภาพจากสามจุด คือหน้าอาคารในมหาวิทยาลัยที่มีคนปั่นจักรยานกับคนเดิน ถนนที่มีรถแท็กซี่กับรถตู้ และซอยที่มีรถเก๋งแล่นผ่านหนึ่งคัน ภาพไหนมี ra สูงที่สุด

| จุด | สิ่งที่ YOLOv3 ตีกรอบได้ | ra |
| --- | --- | --- |
| Campus | คนปั่นจักรยานและคนเดิน | 0.05% |
| Street | รถทั้งสองคัน | 0.03% |
| Alley | วัตถุเล็กสองจุดทางซ้าย แต่ไม่ได้ตีกรอบรถเก๋ง | 10.82% |

ในซอย image matting เห็นรถเก๋งเป็นก้อนสีขาวใหญ่ แต่ object detection ไม่ได้ตีกรอบรอบมัน รถทั้งคันจึงเหลือเป็นพื้นที่ที่ไม่รู้จัก ra ของภาพนี้สูงกว่าอีกสองภาพหลายร้อยเท่า ส่วนอีกสองภาพเหลือสีขาวแค่จุดเล็ก ๆ ตรงที่ IM กับ OD ซ้อนกันไม่สนิท

### การทดลอง

ระบบทดลองมีคลาวด์หนึ่งชุด กับ edge node สามจุด ได้แก่ #1 ที่ campus, #2 ที่ alley และ #3 ที่ street คลาวด์ทำ global knowledge discovering & sharing คือค้นหาความรู้จากทุก node แล้วแบ่งปัน แล้วส่งโมเดลใหม่ลงไปให้ทุก node

แต่ละ node ผูกกับคลาสไม่เท่ากัน จากหกคลาส คือ pedestrian, bicycle, car, motorcycle, truck และ bus node #1 ผูกกับแค่ pedestrian node #2 กับสี่คลาสแรก และ node #3 กับครบทั้งหก

### ผลการทดลอง

ทุกครั้งที่วัตถุชนิดใหม่โผล่มา จำนวนชนิดที่เคยเห็นเพิ่มขึ้นหนึ่ง แต่จำนวนชนิดที่ edge ระบุได้ยังไม่เพิ่มทันที ra พุ่งขึ้นเกิน α ก่อนตัวเลขนี้เพิ่มแต่ละครั้ง ตามเงื่อนไขที่ว่าวัตถุไม่รู้จักต้องโผล่มาจนครบ β ครั้งที่ ra สูงถึง α คลาวด์จึงฝึกโมเดลใหม่และส่งลงมา จำนวนชนิดที่ edge ระบุได้จึงไล่ตามทันทุกครั้ง จาก 1 ไปถึง 6 ชนิด

ผลด้าน bandwidth คือ แบบเดิมที่ส่งทุกภาพขึ้นคลาวด์ ข้อมูลที่ส่งโตเป็นเส้นตรงตามจำนวนภาพ ส่วนแบบ edge ข้อมูลที่ส่งเพิ่มขึ้นทีละขั้นเล็ก ๆ เฉพาะช่วงที่มีวัตถุไม่รู้จักโผล่มา ผลคือ **ประหยัด bandwidth ของ core network ได้ราว 94%**

<Detail label="ตัวเลขของการทดลอง และสิ่งที่สไลด์ไม่ได้บอก">

- การทดลองวัดตลอดราว 1,240 data instance และวัตถุชนิดที่ไม่เคยเห็นแต่ละชนิดโผล่มา 10 ครั้ง
- เกณฑ์ α อยู่ที่ราว 0.01 บนแกน residual area ของกราฟผล ซึ่งไม่ได้บอกหน่วย ส่วนตาราง ra ด้านบนเป็นเปอร์เซ็นต์ จึงเทียบกันตรง ๆ ไม่ได้
- เกณฑ์ α กับ β ใช้ตัดสินว่าเมื่อไหร่จะอัปเดตโมเดล ส่วน edge ใช้เกณฑ์เดียวกันตัดสินด้วยหรือไม่ว่าภาพไหนต้องส่งขึ้นคลาวด์ สไลด์ไม่ได้บอก
- การผูก node กับคลาสข้างบนไม่ได้บอกว่าหมายถึงคลาสที่ node นั้นเจอ หรือคลาสที่โมเดลของ node นั้นรู้จัก

</Detail>

**ทำไมต้อง edge**

- อุปกรณ์เปลี่ยนจาก PC มาเป็น IoT และ wearable ราวพันล้านเครื่องที่เปิดตลอดเวลา ส่วนที่คำนวณเปลี่ยนจาก mainframe มาเป็นคลาวด์แล้วเป็น edge
- แรงกดดันสี่ข้อ: real-time QoS และ delay sensitiveness, battery lifetime, regulating core network traffic (2015: wearable ราว 97 ล้านเครื่อง 15 PB ต่อเดือน), scalability
- ระยะทางกำหนด latency ขั้นต่ำ เครื่องปลายทางที่แรงขึ้นลดส่วนนี้ไม่ได้
- Edge เทียบกับ cloud: latency ต่ำ, LAN, อยู่ที่ขอบ, รองรับการเคลื่อนที่, กระจาย, ธุรกิจท้องถิ่นดูแล, เซิร์ฟเวอร์น้อย, เก็บแค่ soft state
- งาน delay-sensitive ไป edge ผ่าน LAN งาน delay-tolerant ขึ้นคลาวด์ผ่าน WAN edge ไม่ได้มาแทนคลาวด์

**สี่แบบของ edge**

- MCC: ยืมพลังคำนวณจากที่อื่น สามแบบคือ cloud-based, ad-hoc, cloudlet-based ต่างจากคลาวด์ธรรมดาตรงประหยัดพลังงานและจัดการการเคลื่อนที่
- Cloudlet: ชั้นกลางระหว่าง MCC ที่พลังคำนวณน้อย กับคลาวด์ที่ latency สูง พลังคำนวณพอ ห่างหนึ่ง hop ใช้ได้แม้ออฟไลน์ คุ้มค่า แทบไม่ต้องดูแล
- Fog: real-time และทำงานคู่กับคลาวด์ เช่น fog หาใบหน้า คลาวด์เทียบกับ image DB
- MEC: อยู่ในเครือข่ายมือถือ มาตรฐานจาก ETSI ISG ปี 2017 วัดทั้ง functional และ non-functional
- แผนที่สองแกน: ใกล้ผู้ใช้แค่ไหน กับเป็นระเบียบแค่ไหน
- MEC ครอบคลุมกว้าง ลงทุนสูง cloudlet และ fog หนาแน่น ราคาถูก รองรับผู้ใช้มาก

**SDN กับ edge**

- สี่โจทย์: service synchronization & orchestration, seamless service delivery, service-centric structure, soft state
- Push all complexity to the control plane: northbound applications, SDN infrastructure (controller + OpenFlow switch), edge layer
- controller ทำ service discovery, commissioning & migration, performance tuning & optimisation, user handover
- ผลดีแปดด้าน: high resolution control, flexibility, service centric, VM mobility, adaptability, interoperability, low cost, multiplicity of scope
- สามชั้น: Tier-1 user & cloudlet, Tier-2 metro cloud (MAN), Tier-3 cloud datacenter (WAN)
- Service-centric access: ขอด้วยชื่อบริการ switch ถาม controller แล้ว controller ติดตั้งกฎ
- SFC บน NFV: firewall → DPI → load balancer เป็น VM คนละมุม controller บังคับลำดับด้วยกฎใน switch

**Edge เหมาะกับงานไหน**

- use case อย่าง cognitive assistance, healthcare, military, smart grid, video analysis และ AR ส่วนใหญ่ต้องการ edge เพราะแรงกดดันสี่ข้อ
- Vehicular edge: V2V, V2I, I2V คำเตือนระหว่างรถวิ่งตรงโดยไม่ผ่านคลาวด์

**กรณีศึกษากล้องวงจรปิด**

- image matting + object detection → image cutting → ส่วนที่ไม่รู้จักส่งขึ้นคลาวด์ → residual area (ra) → ถ้า ra ถึง α ซ้ำ β ครั้ง คลาวด์ฝึกโมเดลใหม่แล้วส่งลง edge
- ภาพในซอยที่รถไม่ถูกตีกรอบมี ra 10.82% ภาพอื่นราว 0.03–0.05%
- ประหยัด bandwidth ของ core network ได้ราว 94%
