## ส่วนที่ 1 — งานใน data center คุยข้ามเครื่องมากแค่ไหน

<Why>
คุณพิมพ์คำว่า `chula` ในช่องค้นหา แล้วได้ผลประมาณ 40,700,000 รายการกลับมาใน 0.78 วินาที

ไม่มีเซิร์ฟเวอร์เครื่องไหนเก็บดัชนีของทั้งเว็บไว้คนเดียว คำขอนั้นจึงถูกส่งต่อไปหาเซิร์ฟเวอร์จำนวนมากใน <Term en="data center" th="อาคารที่รวมเซิร์ฟเวอร์หลายหมื่นเครื่อง" /> แต่ละเครื่องค้นส่วนของตัวเอง แล้วส่งคำตอบกลับมารวมเป็นหน้าเดียว ทั้งหมดต้องจบในเวลาไม่ถึงหนึ่งวินาที
</Why>

### คำขอเดียว แตกเป็นงานหลายร้อยเครื่อง

รูปแบบที่ใช้กันเรียกว่า <Term en="partition-aggregate" th="แตกงานออกไป แล้วรวมคำตอบกลับ" /> เครื่องบนสุดแบ่งงานให้เครื่องชั้นล่าง เครื่องชั้นล่างแบ่งต่ออีกทอด แล้วคำตอบไหลย้อนขึ้นมารวมกันเป็นต้นไม้

การสร้างหน้าผลค้นหาหน้าแรกของ Bing มีได้ถึง 150 ขั้น (stage) แต่ละขั้นแตกงานออกไปได้ถึง 40 ทาง และเส้นทางจากคำขอถึงคำตอบยาว 10 ขั้นขึ้นไป แต่ละขั้น เช่น ตัวตรวจคำสะกด (Speller) หรือโฆษณา (Ads) ก็อาจเป็นงานซับซ้อนอีกชุดหนึ่งในตัวมันเอง

Facebook ก็เจอแบบเดียวกัน การเปิดหน้าเว็บยอดนิยมหนึ่งหน้าแตะเซิร์ฟเวอร์ต่างกันเฉลี่ย **521 เครื่อง** และที่เปอร์เซ็นไทล์ที่ 95 แตะถึง **1,740 เครื่อง**

ปัญหาแรกคือเครื่องที่ช้าที่สุด แต่ละเครื่องตอบช้าบ้างเป็นครั้งคราวด้วยเหตุบังเอิญ แต่หน้าเว็บต้องรอคำตอบครบทุกเครื่อง เครื่องที่ช้าที่สุดตัวเดียวจึงกำหนดความเร็วของทั้งหน้า

แล้วยังเกิด **ความหน่วงแบบสุ่มสะสมข้ามขั้น** เพราะแต่ละขั้นต้องรอขั้นที่มันพึ่งอยู่ทำเสร็จก่อน ความช้าจึงบวกกันตลอดเส้นทางยาว 10 ขั้นขึ้นไป

<Example added title="แตะ 521 เครื่อง แทบหนีเครื่องช้าไม่พ้น">

ถ้าแต่ละเครื่องตอบช้า 1 ครั้งใน 100 ครั้ง โอกาสที่คำขอซึ่งแตะ `n` เครื่องจะเจอเครื่องช้าอย่างน้อยหนึ่งตัวคือ `1 - 0.99^n` ตามที่คิดไว้ใน[ตัวอย่างของ Lecture 9](/2110506-sds/lecture-9#แอปจริงใหญ่และซับซ้อนแค่ไหน) ลองทายก่อน: คำขอของ Facebook ที่แตะ 521 เครื่องจะเจอเครื่องช้าบ่อยแค่ไหน

ที่ 521 เครื่อง สูตรให้ **99.5%** แปลว่าคำขอเกือบทุกครั้งของ Facebook ต้องรอเครื่องช้า

</Example>

ผลคือเครือข่ายที่ส่งของระหว่างเครื่องต้องเร็วและนิ่งทุกเส้นทาง ไม่ใช่แค่เร็วโดยเฉลี่ย เพราะเส้นทางที่ช้าเส้นเดียวก็ทำให้ทั้งคำขอช้า

<Quiz question="บริการหนึ่งแตกคำขอไป 50 เครื่อง แต่ละเครื่องตอบช้า 2 ครั้งใน 100 ครั้ง คำขอที่ต้องรอเครื่องช้าอย่างน้อยหนึ่งตัวมีกี่เปอร์เซ็นต์">

คำตอบคือ **ราว 63.6%**

คำตอบที่ผิดบ่อยคือ "2% เท่ากับแต่ละเครื่อง" ซึ่งลืมว่าคำขอต้องรอคำตอบครบทุกเครื่อง เครื่องช้าตัวเดียวก็ทำให้ทั้งคำขอช้า ความน่าจะเป็นจึงสะสมตามจำนวนเครื่อง
</Quiz>

### งานแบบอื่นก็คุยข้ามเครื่องเหมือนกัน

งานบน cloud และงาน big data ทำแบบเดียวกัน Spark และ Hadoop แบ่งข้อมูลก้อนใหญ่ไปประมวลผลบนหลายเครื่องแล้วส่งผลข้ามกันไปมา ที่เก็บข้อมูลแบบกระจายอย่าง S3 และ DynamoDB เก็บข้อมูลไว้บนหลายเครื่อง และ EC2 ก็กระจาย VM ของลูกค้าไปทั่ว data center ผลคือ traffic วิ่งจากเซิร์ฟเวอร์หนึ่งไปอีกเซิร์ฟเวอร์ทุกทิศทาง

งานกลุ่มล่าสุดคือ AI, deep learning และ LLM ซึ่งมีหน้าตา traffic ต่างจากงาน cloud ทั่วไปมาก ข้อมูลจาก Alibaba Cloud (SIGCOMM 2024) เทียบไว้ดังนี้

| งาน | หน้าตา traffic |
| --- | --- |
| cloud ทั่วไป | ขึ้นลงช้า ๆ ตามช่วงเวลาของวัน อยู่ราว 0.3–1.5 Gbps ต่อเครื่องตลอด 24 ชั่วโมง |
| LLM training | พุ่งเกือบ 400 Gbps ต่อการ์ดเครือข่ายหนึ่งใบ (เครื่องหนึ่งมี 8 ใบสำหรับงาน training) เป็นจังหวะ ราวทุก 20 วินาที แล้วตกลงเกือบศูนย์ |

ช่วงที่พุ่งคือช่วงที่ GPU ทุกตัวแลกผลการคำนวณกันพร้อมกัน ระหว่างนั้น GPU รอเครือข่ายอยู่ **การใช้ bandwidth ให้เต็มที่ระหว่าง LLM training จึงสำคัญมาก** เพราะทุกวินาทีที่เครือข่ายช้า คือ GPU ราคาแพงที่นั่งว่าง

### cloud เปลี่ยนโจทย์ของเครือข่ายสี่เรื่อง

การมาของ cloud เปลี่ยนโจทย์ของเครือข่ายไปสี่เรื่อง

- **ขนาด** จำนวนเซิร์ฟเวอร์ที่ต้องต่อถึงกันใน data center เดียว
- **งานแบบใหม่** อย่างที่เห็นในหัวข้อก่อนหน้า
- **การแยกลูกค้าออกจากกัน** เพราะลูกค้าหลายรายใช้ data center เดียวกัน เรื่องนี้จะกลับมาในส่วนที่ 3
- **cloud ที่กระจายข้ามภูมิภาค** data center หลายแห่งต้องต่อถึงกันผ่าน wide area network

<KeyIdea>
คำขอหนึ่งครั้งจากผู้ใช้แตกเป็นงานบนเซิร์ฟเวอร์หลายร้อยเครื่อง และงาน big data กับ AI ก็ส่งข้อมูลข้ามเครื่องตลอดเวลา traffic ส่วนใหญ่ใน data center จึงเป็นเซิร์ฟเวอร์คุยกับเซิร์ฟเวอร์ ไม่ใช่ผู้ใช้คุยกับเซิร์ฟเวอร์
</KeyIdea>

## ส่วนที่ 2 — data center ต่อสายกันยังไง และ traffic วิ่งไปทางไหน

### rack, cluster และต้นไม้สามชั้น

หน่วยเล็กสุดคือ <Term en="rack" th="ตู้ที่ใส่เซิร์ฟเวอร์ซ้อนกันเป็นชั้น" /> ตู้หนึ่งตู้มีเซิร์ฟเวอร์ซ้อนกันหลายสิบเครื่อง ทุกเครื่องเสียบสายเข้า <Term en="TOR switch" th="switch ที่อยู่บนหัวตู้ rack" /> ซึ่งย่อมาจาก top of the rack เซิร์ฟเวอร์จริงหนึ่งเครื่องอาจรัน VM ได้เป็นร้อยตัว

หลาย rack รวมกันเป็น <Term en="cluster" th="กลุ่มของหลาย rack" /> TOR ของทุก rack ใน cluster ต่อสายขึ้นไปที่ <Term en="aggregation switch" th="switch ที่รวมสายจากหลาย rack" /> และแต่ละ TOR ต่อขึ้นไปสองตัว ถ้าตัวหนึ่งเสีย อีกตัวยังรับต่อได้

เหนือ aggregation switch ขึ้นไปคือ <Term en="core switch" th="switch แกนกลางของ data center" /> ซึ่งเชื่อมทุก cluster ใน data center และบนสุดคือ router ที่ต่อออกไปนอก data center ทั้งหมดเรียงเป็นต้นไม้แบบนี้

<Figure number={1} caption="เครือข่าย data center แบบดั้งเดิม เส้นหนาคือทางจาก rack ใน cluster ซ้ายไป rack ใน cluster ขวา ซึ่งต้องปีนขึ้นถึง core switch">
  <DcnTrafficTree />
</Figure>

เส้นประแนวนอนใต้ router ในรูปแบ่งสองชั้นของเครือข่าย switch ข้างล่างทำงานที่ <Term en="Layer 2" th="ชั้น link layer ของเครือข่าย" /> คือส่ง frame ไปหาเครื่องในเครือข่ายย่อยเดียวกันด้วย MAC address

ส่วน router ข้างบนทำงานที่ <Term en="Layer 3" th="ชั้น network layer ของเครือข่าย" /> คือส่ง packet ข้ามเครือข่ายด้วย IP address

data center ใหญ่ ๆ แบ่งเครื่องออกเป็น <Term en="subnet" th="เครือข่ายย่อยที่ใช้ IP ขึ้นต้นเหมือนกัน" /> จำนวนมาก เพราะเครือข่าย Layer 2 วงเดียวที่ใหญ่เกินไปขยายต่อไม่ไหว ข้อความ broadcast ที่ส่งถึงทุกเครื่องในวง จะท่วมเครื่องเป็นหมื่นเครื่องพร้อมกัน

### traffic ส่วนใหญ่ออกจาก rack

ถ้า traffic ส่วนใหญ่อยู่ใน rack เดียว <Term en="uplink" th="สายที่ต่อจาก switch ขึ้นไปชั้นบน" /> จาก TOR ก็ไม่ต้องใหญ่ ลองทายก่อน: ใน data center ของ Facebook traffic กี่เปอร์เซ็นต์จบใน rack เดียวกัน

ตัวเลขของ Facebook (SIGCOMM 2015) เป็นดังนี้

| traffic ไปที่ไหน | สัดส่วน | ต้องปีนขึ้นถึงชั้นไหน |
| --- | --- | --- |
| ภายใน rack เดียวกัน | 12.9% | TOR |
| ข้าม rack ภายใน cluster เดียวกัน | 57.5% | aggregation |
| ข้าม cluster ภายใน data center | 11.9% | core |
| ออกไป data center อื่น | 17.7% | router |

มีแค่ 12.9% ที่จบใน rack อีก 87.1% ต้องออกจาก TOR ขึ้นไปข้างบน และในนั้น 69.4% ยังอยู่ใน data center เดียวกัน แค่ข้าม rack หรือข้าม cluster

ผู้ให้บริการ cloud รายอื่นก็เจอรูปแบบเดียวกัน นี่คือ **การเปลี่ยนแปลงครั้งใหญ่** จากงานเว็บยุคก่อน ซึ่งคาดเดาได้ว่า traffic จะวิ่งอยู่ใน rack หรือ cluster ของตัวเอง และควบคุมให้อยู่ในนั้นได้

<Quiz question="คำขอหนึ่งของ Facebook แตะเซิร์ฟเวอร์ 521 เครื่อง ถ้า rack หนึ่งมีเซิร์ฟเวอร์ 40 เครื่อง และทีมพยายามวางทุกเครื่องของบริการนี้ให้ชิดกันที่สุด traffic ของคำขอนี้อยู่ใน TOR ตัวเดียวได้ไหม">
521 หาร 40 ได้ 13.025 ต่อให้อัดเครื่องให้เต็มทุก rack ก็ต้องใช้อย่างน้อย 14 rack คำขอนี้จึงต้องวิ่งข้าม TOR อย่างน้อย 14 ตัว และต้องปีนขึ้นไปถึงชั้น aggregation เป็นอย่างน้อย ถ้า 14 rack นั้นอยู่คนละ cluster ก็ต้องขึ้นถึง core

คำตอบคือ **ไม่ได้**

คำตอบที่ผิดบ่อยคือ "ได้ ถ้าวางเครื่องดี ๆ" ซึ่งลืมว่า rack หนึ่งรับเครื่องได้จำกัด งานที่แตกไปหลายร้อยเครื่องจึงล้นออกนอก rack เสมอ ไม่ว่าจะวางเก่งแค่ไหน
</Quiz>

## ส่วนที่ 3 — ทำไมต้นไม้แบบเดิมไม่พอสำหรับ cloud

### ก่อนยุค cloud: จองเป็นก้อนตาม rack

ก่อนมี cloud แต่ละบริการได้ rack ของตัวเองเป็นก้อน ๆ วางไว้ใต้ aggregation switch เดียวกันเพื่อให้ traffic อยู่ใกล้กัน การวางแบบนี้คิดมาละเอียดมาก และนั่นคือต้นเหตุของปัญหาสามข้อ

**ข้อแรก ไม่คล่องตัว** บริการผูกอยู่กับ rack ของมัน จะย้ายหรือขยายต้องวางแผนใหม่ทั้งก้อน

**ข้อสอง ใช้เครื่องไม่เต็ม** บริการหนึ่งอาจใช้แค่ครึ่ง rack ที่ตัวเองจองไว้ อีกครึ่งว่างอยู่ แต่บริการอื่นที่กำลังขาดเครื่องก็เอามาใช้ไม่ได้

**ข้อสาม ขยายยาก** พอ rack เดิมเต็ม บริการต้องขยายไป rack ใหม่ซึ่งอยู่อีก subnet เครื่องที่ย้ายไปจึงต้องได้ IP ใหม่ และการเปลี่ยน IP ของบริการที่กำลังรันอยู่ทำได้ยากมาก

IP ผูกกับตำแหน่งเพราะ router เลือกทางด้วยส่วนต้นของ IP เช่น packet ทุกตัวที่ไป `10.1.0.25` ถูกส่งไป subnet A `10.1.0.0/24` เสมอ ต่อให้ย้ายเครื่องไป subnet B `10.2.0.0/24` แล้วก็ตาม

เครื่องที่ย้ายจึงต้องเปลี่ยน IP แล้วตามแก้ทุกที่ที่จำ IP เก่าไว้

### uplink แคบกว่าสายเซิร์ฟเวอร์รวมกัน: oversubscription

ต้นไม้ยังมีปัญหาเรื่องความเร็วอีกข้อ uplink จาก TOR ขึ้นไปข้างบนมีความจุน้อยกว่าผลรวมของสายจากเซิร์ฟเวอร์ข้างล่าง การออกแบบแบบนี้เรียกว่า <Term en="oversubscription" th="ขายความจุเกินกว่าที่ uplink รับได้จริง" />

เครือข่ายแบบต้นไม้มัก oversubscribe ไว้ที่ **2.5:1 ถึง 8:1** ถ้าเซิร์ฟเวอร์ทุกเครื่องส่งข้อมูลออกนอก rack พร้อมกัน แต่ละเครื่องจะได้แค่ 40% ถึง 12.5% ของความเร็วสายตัวเอง ผลคือ congestion โดยเฉพาะเมื่อเครื่องฝั่งซ้ายของต้นไม้คุยกับฝั่งขวาตลอดเวลา เพราะทุก packet ต้องเบียดกันผ่าน core

<Example title="data center ของ Google ปี 2004">

Google ปี 2004 มี 512 rack แต่ละ rack มีเซิร์ฟเวอร์ต่อเข้า TOR ด้วยสาย 1 Gbps รวม 40 เส้น และ TOR ต่อขึ้นไปที่ cluster router สี่ตัวด้วยสาย 1 Gbps รวม 4 เส้น cluster router ต่อกันเองด้วยสาย 2 เส้นขนาด 10 Gbps

แบบนี้มีแค่สองชั้น cluster router เป็นชั้นเดียวเหนือ TOR จึงทำหน้าที่ของชั้น aggregation กับ core รวมกัน

สายจากเซิร์ฟเวอร์รวม 40 Gbps แต่ uplink รวม 4 Gbps คือ oversubscribe 10:1 ถ้าเซิร์ฟเวอร์ทั้ง 40 เครื่องส่งออกนอก rack พร้อมกัน แต่ละเครื่องได้แค่ 100 Mbps จากสาย 1 Gbps

ตัว cluster router เองก็เป็นปัญหา มันต้องมี 512 พอร์ตเพื่อรับสายจากทุก rack switch ที่มีพอร์ตหนาแน่นขนาดนี้เป็นของเฉพาะของผู้ผลิตรายเดียว ราคาแพง และขยายต่อได้จำกัด สรุปคือทั้ง **ติดขัดและแพง**

</Example>

ทางแก้ตรง ๆ คือใช้ switch ที่ใหญ่ขึ้นที่ชั้นบน เพื่อให้ได้ความเร็วใกล้ <Term en="line rate" th="ความเร็วเต็มของสาย" />

data center ในอุดมคติคือ **เซิร์ฟเวอร์ทุกเครื่องคุยกับทุกเครื่องได้เต็มความเร็วสายพร้อมกัน** คุณสมบัตินี้เรียกว่า <Term en="full bisection bandwidth" th="ผ่าเครือข่ายเป็นสองซีกตรงไหนก็ส่งข้ามได้เต็มความเร็ว" /> หน้าตาของมันคือ crossbar switch ตัวมหึมาตัวเดียวที่ทุกเซิร์ฟเวอร์เสียบเข้า และทุกพอร์ตวิ่งได้เต็มความเร็วพร้อมกัน ปัญหาเดียวคือ **แพงมาก**

### cloud ต้องการห้าข้อ

<Term en="multi-tenancy" th="ลูกค้าหลายรายใช้ระบบเดียวกัน" /> คือสภาพของ cloud ที่ลูกค้าหลายราย ซึ่งเรียกว่า tenant ใช้ data center เดียวกัน VM ของแต่ละรายกระจายปนกันอยู่ทุก rack โจทย์นี้ต้องการเครือข่ายที่มีห้าคุณสมบัติ

| ข้อ | ต้องการอะไร | ต้นไม้แบบเดิมพังตรงไหน |
| --- | --- | --- |
| 1. Agility | ใช้เซิร์ฟเวอร์เครื่องไหนก็ได้ ให้บริการไหนก็ได้ เมื่อไหร่ก็ได้ | บริการผูกกับ rack ที่จองไว้ |
| 2. Location-independent addressing | VM ใช้ IP เดิมได้ไม่ว่าจะอยู่ตรงไหนใน data center | IP ผูกกับ subnet |
| 3. Performance uniformity | ความเร็วเท่ากันไม่ว่า VM จะอยู่ตรงไหน | ข้าม core แล้วโดน oversubscription |
| 4. Security and isolation | กั้นแยกระดับ tenant หรือระดับแอป | กั้นได้แค่ระดับ subnet หรือ VLAN |
| 5. Preserve network semantics | แอปยังเห็นเครือข่าย L2, L3, broadcast, multicast แบบปกติ | VM ของ tenant เดียวกระจายอยู่หลาย subnet |

ข้อสรุปคือ **เครือข่ายแบบดั้งเดิมตอบโจทย์ทั้งห้าข้อนี้ไม่ได้** ตามคอลัมน์ขวา ส่วนเหตุผลที่ cloud ต้องการแต่ละข้อมีดังนี้

**ข้อ 1 Agility** มีเหตุผลสองอย่าง อย่างแรกคือใช้เครื่องให้คุ้ม cloud manager อัด VM ลงเครื่องไหนก็ได้ที่ยังว่าง ด้วยนโยบายใน [Lecture 7.2 ส่วนที่ 4](/2110506-sds/lecture-7-2#ส่วนที่-4--cloud-manager-วาง-vm-ลงเครื่องไหน) อย่างที่สองคือความทนทาน เมื่อต้องปิดเครื่องไปซ่อม cloud ใช้ <Term en="live migration" th="ย้าย VM ที่กำลังรันไปเครื่องอื่นโดยไม่ต้องปิด" /> ย้าย VM ออกไปก่อน

**ข้อ 2 Location-independent addressing** ตามมาจากข้อ 1 ทันที VM ที่ถูกย้ายจากเครื่องที่จะปิดไปอีก rack ต้องใช้ IP เดิมต่อได้ ไม่อย่างนั้นทุกบริการที่คุยกับมันอยู่จะพังแบบข้างบน

**ข้อ 3 Performance uniformity** คือ full bisection bandwidth ในมุมของลูกค้า แม้ VM ตัวหนึ่งของ tenant อยู่ซีกซ้ายและอีกตัวอยู่ซีกขวาของ data center ก็ยังคุยกันได้เต็ม line rate

**ข้อ 4 Security and isolation** จำเป็นเพราะเพื่อนบ้านบนเครื่องเดียวกันหรือ rack เดียวกันอาจเป็นคนที่ไว้ใจไม่ได้ ต้องกั้นแยกแบบเดียวกับ <Term en="VLAN" th="การแบ่ง switch จริงชุดเดียวเป็นหลายเครือข่าย Layer 2" /> แต่ละเอียดกว่ามาก คือกั้นระดับ tenant หรือระดับแอป การกั้นละเอียดระดับนี้เรียกว่า <Term en="micro-segmentation" th="การกั้นแยกเครือข่ายเป็นชิ้นเล็กระดับแอป" />

<Detail label="เสริม — ทำไม VLAN ธรรมดาไม่พอ">
VLAN แยกเครือข่ายด้วยเลข VLAN ID ขนาด 12 บิต ซึ่งมี 4,096 ค่า และใช้งานได้จริง 4,094 ค่า cloud ที่มีลูกค้าเป็นหมื่นรายจึงแจกคนละ VLAN ให้ทุกรายไม่ได้

อีกเรื่องคือ VLAN กั้นที่ระดับเครือข่าย Layer 2 ทั้งวง แต่ micro-segmentation ต้องการกั้นละเอียดกว่านั้น เช่น อนุญาตให้ VM ฝั่งเว็บของ tenant หนึ่งคุยกับ VM ฐานข้อมูลของ tenant เดียวกันได้ แต่ห้าม VM อื่นทุกตัว
</Detail>

**ข้อ 5 Preserve network semantics** มีเพราะแอปเดิมคาดหวังเครือข่ายแบบปกติ เช่น หาเครื่องอื่นใน subnet ด้วย broadcast ต้องทำให้ tenant แต่ละรายรู้สึกว่าอยู่ในเครือข่ายธรรมดาที่มีแค่ตัวเอง ไม่ใช่ใน cloud ที่แชร์กับคนอื่น

<Pitfall>
"แค่ซื้อ switch ตัวใหญ่ขึ้นจน bandwidth พอ เครือข่ายเดิมก็รองรับ cloud ได้แล้ว"

ไม่จริง เพราะ switch ใหญ่แก้ได้แค่ข้อ 3 ข้อเดียว

ความเชื่อนี้ดูมีเหตุผลเพราะ congestion เป็นอาการที่เห็นชัดที่สุด แต่อีกสี่ข้อเป็นเรื่องว่าเครือข่าย **ตัดสินใจ** ยังไง ไม่ใช่เรื่องความเร็ว router ยังเลือกทางด้วยส่วนต้นของ IP ต่อให้สายหนาแค่ไหน VM `10.1.0.25` ที่ย้ายไป subnet B ก็ยังไม่ได้รับ packet ของตัวเอง และ broadcast ของ tenant หนึ่งก็ยังไม่รู้ว่าต้องไปถึงเครื่องไหนบ้าง สองเรื่องนี้ต้องแก้ที่ซอฟต์แวร์ที่ควบคุมเครือข่าย
</Pitfall>

### SDN: ย้ายการตัดสินใจออกมาเป็นซอฟต์แวร์

<Why>
แกนของเครือข่ายแทบไม่เปลี่ยนเลยตั้งแต่อินเทอร์เน็ตเริ่มแพร่หลาย ของใหม่เกือบทั้งหมดเกิดที่ชั้นแอปพลิเคชัน

เหตุผลคือการเพิ่มของใหม่อย่าง multicast, IPv6 หรือระบบความปลอดภัยลงในเครือข่ายทำได้ยาก เครือข่ายจึงกลายเป็นของซับซ้อนที่ไม่มีใครกล้าแตะ มีคนเสนอให้ออกแบบเครือข่ายใหม่ทั้งหมดตั้งแต่ต้น (clean-slate) หลายครั้ง แต่ไม่มีข้อเสนอไหนเกิดขึ้นจริง

สิ่งที่บังคับให้เปลี่ยนได้คืองานแบบใหม่ใน data center และ cloud ของ Google, Facebook, Microsoft และ Amazon ซึ่งพาไปสู่การใช้ <Term en="SDN" th="เครือข่ายที่ควบคุมด้วยซอฟต์แวร์" /> ในวงกว้าง SDN จึงเป็นหนึ่งในการเปลี่ยนแปลงครั้งใหญ่ที่สุดที่กำลังเกิดขึ้นจริงในวงการเครือข่าย และ wide area network ที่เชื่อม data center ของ Google เข้าด้วยกัน ([B4 ใน Lecture 10](/2110506-sds/lecture-10#เครือข่ายของ-google)) ก็สร้างบน SDN
</Why>

แนวคิดหลักของ SDN คือ **แยก data plane ออกจาก control plane** router และ switch เหลือแค่งานส่ง packet ตามตาราง ส่วนการคำนวณตารางย้ายไปอยู่ที่ controller ตัวเดียวที่เห็นทั้งเครือข่าย รายละเอียดอยู่ใน [Lecture 10](/2110506-sds/lecture-10) และ [Lecture 1 หัวข้อ control plane กับ data plane](/2110506-sds/lecture-1#แยก-control-plane-ออกจาก-data-plane)

<Callout type="info" title="SDN ตอบข้อไหนบ้าง สไลด์ไม่ได้ไล่ให้ดู">
controller รู้ว่าตอนนี้ VM แต่ละตัวอยู่บนเครื่องไหน เมื่อ VM ถูกย้าย controller แก้ตารางของ switch ให้ส่ง packet ของ IP นั้นไปตำแหน่งใหม่ IP จึงไม่ต้องเปลี่ยน ซึ่งตอบข้อ 1 และข้อ 2

controller ยังติดตั้งกฎแยกตาม tenant ลงทุก switch ได้ ซึ่งตอบข้อ 4 และส่ง broadcast ของ tenant หนึ่งไปเฉพาะ VM ของ tenant นั้นได้ ซึ่งตอบข้อ 5 ส่วนข้อ 3 ต้องมีฮาร์ดแวร์ที่มีทางให้เลือกพอก่อน ซึ่งคือเรื่องของส่วนถัดไป
</Callout>

<Quiz question="cloud หนึ่งยังใช้เครือข่ายแบบต้นไม้เดิม แต่เพิ่ม SDN controller เข้าไป แล้วเจอปัญหาสองเรื่อง (ก) VM ที่เพิ่งถูกย้ายไปอีก subnet ติดต่อไม่ได้ (ข) VM สองตัวของ tenant เดียวกันช้าลงมาก หลังตัวหนึ่งถูกย้ายไปอีกซีกของ data center controller แก้เรื่องไหนได้ด้วยซอฟต์แวร์อย่างเดียว">
(ก) เป็นเรื่องการตัดสินใจ controller รู้ว่าตอนนี้ VM อยู่ที่ไหน จึงแก้ตารางของ switch ให้ส่ง packet ของ IP เดิมไปตำแหน่งใหม่ได้ (ข) เป็นเรื่องความจุ ข้อมูลข้ามซีกต้องขึ้น uplink ที่ oversubscribe ไว้ ซึ่ง controller เลือกทางได้ แต่สร้างความจุที่ไม่มีอยู่ไม่ได้

คำตอบคือ **controller แก้ (ก) ได้ ส่วน (ข) ต้องมีฮาร์ดแวร์ที่มีทางมากพอ** ซึ่งคือเรื่องของส่วนที่ 4

คำตอบที่ผิดบ่อยคือ "แก้ได้ทั้งคู่ เพราะ controller เลือกเส้นทางเองได้" ซึ่งลืมว่าการเลือกทางช่วยได้เฉพาะเมื่อมีทางว่างให้เลือก บนต้นไม้ uplink ทุกเส้นถูก oversubscribe อยู่แล้ว เลือกเส้นไหนก็ยังแคบกว่าสายของเซิร์ฟเวอร์รวมกัน
</Quiz>

ดูวิธีนับพอร์ตในรูป switch ชั้นขาเข้าและชั้นขาออกแต่ละตัวใช้ 4 พอร์ตออกข้างนอก อีก 4 พอร์ตต่อเข้าชั้นกลาง สองชั้นนอกมีชั้นละ 4 ตัว จึงได้พอร์ตภายนอก 16 + 16 = 32 พอร์ต ส่วน switch ชั้นกลางใช้ทั้ง 8 พอร์ตต่อกับชั้นขาเข้า 4 ตัวและชั้นขาออก 4 ตัว

จุดสำคัญคือ **ทุก switch ขาเข้าต่อกับทุก switch ชั้นกลาง** จาก A ไป B จึงมีสี่ทาง ผ่าน switch ชั้นกลางตัวไหนก็ได้ ถ้าเลือกทางให้ดี ทุกพอร์ตขาเข้าคุยกับพอร์ตขาออกได้เต็มความเร็วพร้อมกัน และถ้า switch ชั้นกลางเสียหนึ่งตัวก็ยังเหลืออีกสามทาง

งานวิจัย <Term en="FatTree" th="โครงเครือข่าย data center แบบ Clos จาก switch ราคาถูก" /> (SIGCOMM 2008) เอาแนวคิดนี้มาใช้กับ data center โดยวาง Clos ทั้งก้อนแทนชั้น aggregation และ core ของต้นไม้เดิม แล้วให้ TOR ทุกตัวเสียบเข้าพอร์ตภายนอกของมัน ผลคือได้ full bisection bandwidth จาก switch ราคาถูกล้วน ๆ ไม่ต้องพึ่ง switch ใหญ่ของผู้ผลิตรายเดียว

<Detail label="เสริม — FatTree ใหญ่ได้แค่ไหน">
FatTree ที่สร้างจาก switch ขนาด `k` พอร์ต รองรับเซิร์ฟเวอร์ได้ `k³/4` เครื่อง ทุกเครื่องได้ full bisection bandwidth และใช้ switch ทั้งหมด `5k²/4` ตัว

| `k` (พอร์ตต่อ switch) | เซิร์ฟเวอร์ | switch |
| --- | --- | --- |
| 4 | 16 | 20 |
| 8 | 128 | 80 |
| 48 | 27,648 | 2,880 |

แถวสุดท้ายใช้ switch 48 พอร์ตรุ่นเดียวกับที่ราคา $7,000 ข้างบน ได้เครือข่ายสำหรับเซิร์ฟเวอร์เกือบสามหมื่นเครื่องที่ทุกเครื่องคุยกันได้เต็มความเร็ว
</Detail>

### ทางเยอะแล้วต้องใช้ทุกทาง: spanning tree ไม่พอ

switch ทุกตัวใต้ router ใน data center ส่งต่อกันแบบ Layer 2 ด้วย Ethernet และ Ethernet switch ส่ง broadcast ออกทุกพอร์ต ถ้าสายต่อกันเป็นวง frame เดียวจะวนไม่รู้จบ Ethernet จึงรัน <Term en="spanning tree protocol" th="โปรโตคอลที่ปิดสายบางเส้นจนไม่เหลือวง" /> ซึ่งปิดสายบางเส้นทิ้งจนเหลือเป็นต้นไม้

ลองทายก่อน: ถ้ารัน spanning tree บนเครือข่ายในรูปที่ 2 ซึ่งมีสายระหว่าง switch 32 เส้น จะเหลือสายที่ใช้งานได้กี่เส้น

ต้นไม้ที่เชื่อม switch 12 ตัวมีสายได้แค่ 11 เส้น อีก **21 เส้นจาก 32 ถูกปิด** และจาก A ไป B เหลือทางเดียวจากที่เคยมีสี่ทาง spanning tree จึงเสียเปล่ามากกับ FatTree เพราะมันเลือกต้นไม้ต้นเดียว ทั้งที่มีสายเหลือเฟือ

สิ่งที่ต้องใช้แทนคือ <Term en="multi-path routing" th="การส่งข้อมูลกระจายไปหลายเส้นทางพร้อมกัน" /> คือเปิดทุกสายไว้ แล้วกระจาย traffic ไปทุกเส้นทางพร้อมกัน

งาน FatTree ทำแบบนี้โดยให้ switch ส่งต่อตามตาราง routing ของ IP ปลายทาง แทนการส่ง broadcast ออกทุกพอร์ต ขาขึ้นใช้เลขท้ายของ IP ปลายทางเลือกว่าจะขึ้นทาง switch ชั้นบนตัวไหน traffic ที่ไปเครื่องต่างกันจึงกระจายไปคนละทาง และไม่มี frame วน เพราะทุก packet ขึ้นแล้วลงตามตารางเท่านั้น

### ต่อ TOR ด้วยวิธีอื่นนอกจากสาย

นอกจาก Clos ยังมีงานวิจัยที่ต่อ TOR ด้วยฮาร์ดแวร์แบบอื่นอีกสามแบบ ทั้งสามแบบเพิ่มทางระหว่าง rack สองตู้ได้โดยไม่ต้องเดินสายใหม่ และหันทางไปหาคู่ใหม่ได้เมื่อคู่ที่คุยกันหนักเปลี่ยนไป

| แบบ | ทำงานยังไง |
| --- | --- |
| Directional point-to-point wireless | ติดเสาอากาศแบบกำหนดทิศบนหัว TOR ยิงคลื่นวิทยุสะท้อนเพดานไปหา rack อีกตู้ |
| Optical (wireless) | ติดตัวยิงแสงบนหัว TOR ยิงลำแสงสะท้อนกระจกบนเพดานไปหา rack อีกตู้ |
| Optical MEMS | TOR ทุกตัวต่อใยแก้วเข้า MEMS optical switch ตัวเดียว ซึ่งใช้กระจกจิ๋วจำนวนมากสะท้อนแสงจากพอร์ตหนึ่งไปอีกพอร์ต |

<Detail label="ต้นแบบในห้องแล็บของงาน optical">
ต้นแบบของงาน optical (IEEE Photonics Technology Letters, 2013) เป็นตู้ rack สองตู้ ตู้หนึ่งมีเครื่องโฮสต์ อีกตู้มีตัวขยายสัญญาณแสง (optical amplifier) เครื่องวิเคราะห์สเปกตรัมแสง (OSA) กับ switch ของมัน ส่วน control plane และฮาร์ดแวร์ของสถานีหกสถานี
</Detail>

<Quiz question="ทีมหนึ่งสร้างเครือข่ายตามรูปที่ 2 แต่ยังใช้ Ethernet ที่รัน spanning tree ตามปกติ แล้วให้เซิร์ฟเวอร์ 4 เครื่องบน switch ขาเข้าตัวบนสุด ส่งข้อมูลหาเซิร์ฟเวอร์ 4 เครื่องบน switch ขาออกตัวที่สามพร้อมกัน แต่ละคู่ได้ความเร็วเท่าไร เทียบกับความเร็วสาย">
spanning tree เหลือทางเดียวระหว่าง switch สองตัวนี้ ข้อมูลทั้งสี่คู่จึงต้องเบียดกันบนสายชุดเดียวกัน สายเส้นแรกที่ออกจาก switch ขาเข้าต้องรับทั้งสี่คู่

คำตอบคือ **ได้คู่ละราว 1/4 ของความเร็วสาย** ถ้าใช้ multi-path routing สี่คู่จะแยกไปคนละ switch ชั้นกลาง และได้เต็มความเร็วทุกคู่

คำตอบที่ผิดบ่อยคือ "เต็มความเร็ว เพราะ Clos มีสี่ทาง" ซึ่งลืมว่าทางที่มีอยู่ในสายไม่ได้แปลว่าถูกใช้ spanning tree ปิดอีกสามทางทิ้งไปแล้ว
</Quiz>

## ส่วนที่ 5 — Data Center Operating System: ใช้ทั้ง data center เหมือนเครื่องเดียว

<Why>

</Why>

### ทั้ง data center ต้องมี OS ของมันเอง

<Term en="Data Center Operating System" th="OS ที่ดูแลทรัพยากรของทั้ง data center" /> คือซอฟต์แวร์ที่ดูแลทรัพยากรทุกชนิดและงานทุกงานที่รันใน data center หน้าที่แบ่งเป็นสองกลุ่ม คือ <Term en="cluster management" th="การดูแลเครื่องจำนวนมากให้ทำงานเป็นกลุ่มเดียว" /> กับบริการกลางให้แอป และแต่ละข้อมีคู่เทียบบน OS ของเครื่องเดียว

### OpenStack: DC OS แบบ open source

### ตัวอย่างจริง: Rackspace สร้างบริการแบบ EC2 ด้วย OpenStack

Rackspace ใช้ OpenStack สร้างบริการเช่า VM แบบเดียวกับ EC2 ของ Amazon โครงของมันแบ่งเครื่องเป็นสองฝั่ง

| ฝั่ง | เครื่องในฝั่งนี้ | ทำอะไร |
| --- | --- | --- |
| **control plane** (infrastructure nodes) | load balancer, deployment node, control plane node | รับคำขอ ตัดสินใจ ติดตั้งและดูแลระบบ |
| **data plane** (compute/storage nodes) | compute node, Ceph node (storage แบบกระจาย ให้ทั้งดิสก์แบบ block และ object), optional storage | รัน VM ของลูกค้าและเก็บข้อมูลจริง |

ทุกเครื่องเชื่อมผ่าน switch 10Gb ที่สำรองกันไว้ ซึ่งอยู่หลัง firewall ที่สำรองกันไว้อีกชั้นก่อนออกสู่เครือข่ายภายนอก traffic ถูกแยกเป็นสี่เครือข่าย ได้แก่ public network, management network, VM network และ Ceph replication network งานดูแลระบบและงานคัดลอกข้อมูลก้อนใหญ่ระหว่าง Ceph node จึงไม่แย่งทางกับ traffic ของ VM ลูกค้า

**ฝั่ง data plane**

- **Compute node** หลายเครื่อง รัน VM ของลูกค้า (instance) ด้วย hypervisor KVM หรือรันบนเครื่องจริงแบบ BareMetal
- **Ceph node** หลายเครื่อง เป็น storage แบบกระจาย มี OSD ที่เก็บข้อมูลจริง Ceph MON ที่ดูแลแผนที่ของ cluster, RBD ที่ให้ดิสก์แบบ block และ RGW ที่ให้ storage แบบ object
- **Optional storage** จากผู้ผลิตภายนอก ได้แก่ EMC VNX2, NetApp FAS และ NetApp SolidFire

</Detail>

<KeyIdea>
DC OS ทำให้ทั้ง data center ใช้เหมือนคอมพิวเตอร์เครื่องเดียว และโครงของ OpenStack ที่ Rackspace ใช้ ก็แยก control plane ออกจาก data plane ในแนวคิดเดียวกับ SDN เครื่องที่ตัดสินใจกับเครื่องที่ทำงานจริงเป็นคนละกลุ่ม แต่ละกลุ่มขยายแยกกันได้
</KeyIdea>

<Recap>

**ทำไมเครือข่ายต้องเปลี่ยน**

- แกนของเครือข่ายแทบไม่เปลี่ยนตั้งแต่อินเทอร์เน็ตแพร่หลาย เพราะเปลี่ยนยาก ข้อเสนอแบบ clean-slate ไม่เคยเกิดจริง งานใน data center ของ Google, Facebook, Microsoft และ Amazon คือแรงที่ทำให้ SDN ถูกใช้ในวงกว้าง
- งานแบบใหม่: เว็บขนาดใหญ่, cloud, big data และ AI/LLM คำขอเดียวแบบ partition-aggregate แตะได้หลายร้อยเครื่อง (Bing 150 ขั้น, Facebook เฉลี่ย 521 เครื่อง) ความหน่วงแบบสุ่มสะสมข้ามขั้น
- LLM training ส่ง traffic พุ่งเป็นจังหวะเกือบ 400 Gbps ต่อการ์ด ต้องใช้ bandwidth ให้เต็มที่
- cloud เปลี่ยนโจทย์สี่เรื่อง: ขนาด, งานแบบใหม่, การแยก tenant, cloud ข้ามภูมิภาค

**โครงสร้างและ traffic**

- rack มีเซิร์ฟเวอร์ต่อเข้า TOR → cluster ต่อเข้า aggregation → core → router switch ข้างล่างเป็น Layer 2 router ข้างบนเป็น Layer 3 และมี subnet จำนวนมาก
- traffic ของ Facebook: ใน rack 12.9%, ข้าม rack ใน cluster 57.5%, ข้าม cluster 11.9%, ไป data center อื่น 17.7% → 87.1% ออกจาก rack

**ปัญหาของต้นไม้**

- วางบริการเป็นก้อนตาม rack: ไม่คล่องตัว, ใช้เครื่องไม่เต็ม, ขยายข้าม subnet ต้องเปลี่ยน IP
- oversubscription ปกติ 2.5:1 ถึง 8:1 ทำให้ congestion Google ปี 2004 คือสายจากเซิร์ฟเวอร์รวม 40 Gbps ต่อ uplink รวม 4 Gbps = 10:1 และใช้ router 512 พอร์ตที่แพงและผูกผู้ผลิตรายเดียว
- อุดมคติคือ full bisection bandwidth แบบ crossbar ตัวใหญ่ แต่แพงมาก
- cloud ต้องการห้าข้อ: agility, IP ไม่ผูกตำแหน่ง, ความเร็วเท่ากันทุกที่, isolation ระดับ tenant (micro-segmentation), รักษาพฤติกรรม L2/L3/broadcast/multicast เครือข่ายแบบเดิมให้ไม่ได้
- SDN แยก control plane ออกจาก data plane ให้ซอฟต์แวร์คุมการตัดสินใจของเครือข่าย

**Clos และฮาร์ดแวร์แบบใหม่**

- switch ใหญ่แพงเกินสัดส่วน ($7,000 สำหรับ 48 พอร์ต, $700,000 สำหรับ 128 พอร์ต)
- Clos network ต่อ switch เล็กหลายชั้นให้เป็นตัวใหญ่: 8 พอร์ต 12 ตัว = 32 พอร์ต ทุกคู่มีหลายทาง FatTree เอามาใช้ใน data center
- spanning tree เหลือต้นไม้ต้นเดียวและปิดสายที่เหลือ FatTree จึงต้องใช้ multi-path routing
- ทางเลือกอื่นในการต่อ TOR: wireless แบบกำหนดทิศ, optical wireless สะท้อนกระจก, optical MEMS switch

**DC OS**

- DC OS ทำ cluster management (resource providers, schedulers, task execution, task management) และให้บริการกลาง (container platforms, package management, networking, storage, identity, logging and metrics)
- OpenStack มีเก้าบริการหลัก: Dashboard, Identity, Networking, Block storage, Compute, Image storage, Object storage, Telemetry, Orchestration รันได้ทั้ง bare metal, VM และ container
- Rackspace สร้างบริการแบบ EC2 ด้วย OpenStack แยกเครื่อง control plane ออกจากเครื่อง data plane และแยกเครือข่ายเป็นสี่วง

<Quiz question="rack หนึ่งมีเซิร์ฟเวอร์ 48 เครื่อง ต่อเข้า TOR ด้วยสาย 10 Gbps และ TOR มี uplink 40 Gbps 4 เส้น oversubscription เท่าไร และถ้าทุกเครื่องส่งออกนอก rack พร้อมกัน แต่ละเครื่องได้ความเร็วเท่าไร">
สายจากเซิร์ฟเวอร์รวม 48 × 10 = 480 Gbps uplink รวม 4 × 40 = 160 Gbps อัตราส่วนคือ 480 ต่อ 160 เมื่อทุกเครื่องส่งออกพร้อมกัน 160 Gbps ถูกแบ่ง 48 ทาง

คำตอบคือ **oversubscribe 3:1 แต่ละเครื่องได้ราว 3.33 Gbps** หรือหนึ่งในสามของความเร็วสาย

คำตอบที่ผิดบ่อยคือ "uplink 40 Gbps ใหญ่กว่าสายเซิร์ฟเวอร์ 10 Gbps จึงไม่ติดขัด" ซึ่งเทียบสายเส้นต่อเส้น ทั้งที่ต้องเทียบผลรวมทั้งสองฝั่ง
</Quiz>

<Quiz question="ลูกค้าของบริการแบบ Rackspace เพิ่มขึ้นเท่าตัว VM ลูกค้าเริ่มไม่มีที่ลง แต่ API ยังตอบเร็วดี ควรเพิ่มเครื่องในฝั่งไหน">
