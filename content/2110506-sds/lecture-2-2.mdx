## ส่วนที่ 1 — Docker คืออะไร และต่างจาก VM ตรงไหน

<Term en="Docker" th="แพลตฟอร์มสำหรับสร้างและรัน container" /> คือแพลตฟอร์มที่ให้นักพัฒนา **พัฒนา ส่งมอบ และรัน** โปรแกรมด้วย container ของ Linux

จุดที่ต้องรู้ก่อนใช้งานจริง — Docker for Mac และ Docker for Windows **ไม่ได้รัน container บน macOS หรือ Windows ตรง ๆ** แต่ยกเครื่อง Linux เสมือนขึ้นมาหนึ่งตัวแล้วรัน container ข้างในนั้น เพราะ container ต้องใช้ความสามารถของ Linux kernel

สิ่งที่ Docker เปลี่ยนไปจริง ๆ มีสองข้อ

- **Standardization** — เปลี่ยนการตั้งค่าเซิร์ฟเวอร์ที่เละและทำซ้ำไม่ได้ ให้กลายเป็นรูปแบบที่ย้ายที่ได้ คือ Dockerfile และ container image
- **ไม่มีคำว่า "เครื่องผมรันได้นะ" อีก** — เพราะไลบรารีและไฟล์ไบนารีถูกมัดไปพร้อมโค้ดเลย พฤติกรรมบนโน้ตบุ๊กกับบนเซิร์ฟเวอร์จริงจึงเหมือนกัน

### VM กับ container ต่างกันตรงไหนแน่

</Figure>

| | Virtual Machine | Container |
| --- | --- | --- |
| ซ่อนอะไรไว้ข้างใต้ | ฮาร์ดแวร์จริง | ทรัพยากรของระบบปฏิบัติการ |
| ข้างในมีอะไร | ระบบปฏิบัติการครบชุด + โค้ด + ไลบรารี | โค้ด + ไลบรารี + การตั้งค่า |
| ใครจัดการ | <Term en="Hypervisor" th="ตัวจัดการเครื่องเสมือน" /> | <Term en="Container Runtime" th="ตัวจัดการ container" /> เช่น Docker Engine |
| kernel | มีของตัวเองต่อหนึ่ง VM | ใช้ของ host ร่วมกัน แต่ละตัวเป็น process ที่แยกขาดใน user space |
| ขนาดและความเร็ว | ระดับ GB บูตช้า | ระดับ MB เริ่มเร็ว |

### สองอย่างนี้ใช้ด้วยกันก็ได้

มีสองแบบ

- **Docker without VM** — Docker Engine วางบนระบบปฏิบัติการที่วางบนเครื่องจริงเลย ทุก container แชร์ kernel เดียวกันหมด
- **Docker with VMs** — hypervisor แบ่งเครื่องจริงเป็นหลาย VM ก่อน แล้วค่อยลง Docker Engine ในบาง VM ส่วน VM อื่นรันโปรแกรมแบบปกติ

แบบหลังคือสิ่งที่ผู้ให้บริการคลาวด์ทำ: ผู้เช่าแต่ละรายได้ VM ของตัวเอง (แยกขาดจากผู้เช่าอื่น) แล้วในนั้นผู้เช่าจะรัน container กี่ตัวก็เรื่องของเขา

### Docker Engine ประกอบด้วยอะไร

<Figure number={2} caption="คำสั่งที่คุณพิมพ์คือฝั่ง client ส่วนตัวที่ครอบครองของจริงคือ daemon">
  <DockerEngine />

เวลาคุณพิมพ์ `docker run` CLI แปลงคำสั่งเป็นคำขอ REST API ส่งไปให้ daemon แล้ว daemon เป็นคนสร้าง container จริง ๆ ตัว daemon นี่เองที่ถือครองและจัดการ container, image, network และ data volume ทั้งหมด

<KeyIdea>
container ทุกตัวใช้ kernel ของ host ร่วมกัน จึงเล็กและเริ่มเร็วกว่า VM ที่มีระบบปฏิบัติการครบชุดต่อเครื่อง ส่วนคำสั่ง `docker` ที่คุณพิมพ์เป็นแค่ client ที่ส่งคำขอไปให้ daemon สร้างและดูแล container จริง
</KeyIdea>

## ส่วนที่ 2 — image ถูกเก็บ แจกจ่าย และรันยังไง

### image ของ Docker และการแบ่งชั้น

Docker image คือ **แม่แบบแบบอ่านอย่างเดียว** สำหรับสร้าง container กฎที่ต้องจำมีสี่ข้อ

1. Docker ใช้ [union file system](/2110506-sds/lecture-2#ทำไมระบบไฟล์ธรรมดาไม่พอ) ซึ่งซ้อนไฟล์เป็นชั้น ๆ รวมหลายชั้นให้กลายเป็น image เดียว
2. ชั้นล่างสุดเรียกว่า <Term en="Base Image" th="ชั้นฐาน" /> ซึ่งกำหนดสภาพแวดล้อมตอนรัน เช่น `ubuntu` หรือ `alpine`
3. ตอน build ชั้นใหม่จะถูกเขียนทับซ้อนขึ้นไปเรื่อย ๆ ชั้นเหล่านี้เปลี่ยนไม่ได้และแชร์กันได้
4. ตอนสร้าง container จาก image ระบบจะเอาระบบไฟล์แบบอ่านเขียนได้มา mount ทับด้านบนอีกหนึ่งชั้น

<Figure number={3} caption="วงจรของ image: รันเป็น container แก้ของ แล้ว commit กลับเป็น image ใหม่ที่ยังแชร์ชั้นล่างกับ image เดิม">
  <ImageEvolves />
</Figure>

จุดที่ทำให้ระบบนี้ประหยัดพื้นที่คือ **แต่ละชั้นมีลิงก์ชี้ไปชั้นที่อยู่ล่างกว่า** เวลาดึง image มา Docker จึงตามลิงก์ไปดึงครบทุกชั้นได้ และชั้นล่างชั้นเดียวกันถูกใช้ร่วมได้โดย image หลายอัน

### Registry: ที่เก็บและแจกจ่าย image

<Why>
สร้าง image เสร็จบนเครื่องตัวเองแล้วจะส่งให้เพื่อนหรือส่งขึ้นเซิร์ฟเวอร์ยังไง ก๊อปเป็นไฟล์ส่งไปทีละคนคงไม่ไหว
</Why>

<Term en="Registry" th="คลังเก็บและแจกจ่าย image" /> คือระบบเก็บและส่งมอบเนื้อหาที่ถือ Docker image ที่มีชื่อเอาไว้ Docker ดูแล registry สาธารณะชื่อ [Docker Hub](https://hub.docker.com/) และผู้ให้บริการรายอื่นก็มี registry ของตัวเองสำหรับ image คนละกลุ่ม

registry แบ่งเป็นสองฝั่ง

| ติดตั้งเอง (on-premises) | บนคลาวด์สาธารณะ |
| --- | --- |
| Hosted Docker Registry | Docker Hub Registry |
| Docker Trusted Registry on-prem | Docker Trusted Registry on-cloud |
| | Azure Container Registry |
| | AWS Container Registry |
| | Google Container Registry |
| | Quay Registry |

#### ชื่อ image อ่านยังไง

ชื่อเต็มของ image มีรูปแบบเดียว

```
registry/username/image_name:tag
```

ส่วนไหนไม่ได้เขียน Docker เติมค่าปริยายให้ ดังนั้น

```bash
docker pull hello-world
# เป็นทางลัดของ
docker pull docker.io/library/hello-world:latest
```

บน Docker Hub มีกติกาตั้งชื่อสองแบบ

- **image ทางการ** ใช้แค่ชื่อ เช่น `ubuntu`, `hello-world`
- **image ของคนอื่น** ต้องมีชื่อเจ้าของนำหน้า เช่น `ubuntu/nginx`, `grafana/grafana`, `prom/node-exporter`

### สามงานพื้นฐานของ Docker

ทุกอย่างที่ Docker ทำ ย่อลงมาได้เป็นสามเส้นทางระหว่าง client, host และ registry

| คำสั่ง | เกิดอะไรขึ้น |
| --- | --- |
| `docker build` | client สั่ง daemon ให้สร้าง image ใหม่จาก Dockerfile แล้วเก็บไว้ในคลัง image บนเครื่อง |
| `docker pull` | daemon ไปดึง image จาก registry มาเก็บไว้ในคลัง image บนเครื่อง |
| `docker run` | daemon เอา image จากคลังมาสร้าง container แล้วเริ่มรัน |

#### `docker run` ทำอะไรตามลำดับ

<StepThrough>
<Step title="ผู้ใช้สั่ง docker run">
คุณพิมพ์ `docker run IMAGE` ที่เทอร์มินัล CLI ส่งคำขอไปที่ daemon
</Step>
<Step title="Docker หา image ในเครื่องก่อน">
daemon ไปดูในคลัง image ของเครื่องนี้ว่ามี image ชื่อและ tag ตรงกันอยู่แล้วหรือเปล่า
</Step>
<Step title="ถ้ามีแล้ว ข้ามไปขั้นสร้าง container ได้เลย">
ไม่ต้องต่อเน็ต ไม่ต้องดาวน์โหลดอะไร นี่คือเหตุผลที่รันครั้งที่สองเร็วกว่าครั้งแรกมาก
</Step>
<Step title="ถ้ายังไม่มี Docker ไปค้นที่ Docker Hub">
ข้อความ `Unable to find image 'hello-world:latest' locally` ที่เห็นตอนรันครั้งแรก คือขั้นนี้
</Step>
<Step title="ถ้าเจอ ก็ดาวน์โหลด image มา">
ดาวน์โหลดมาทีละชั้นตามลิงก์ที่แต่ละชั้นชี้ไป ชั้นไหนมีอยู่แล้วในเครื่องก็ข้าม
</Step>
<Step title="ติดตั้งชั้นของ image ลงเครื่องนี้">
ชั้นทั้งหมดถูกวางเข้าที่ในระบบไฟล์แบบซ้อนชั้น พร้อมให้ container หลายตัวใช้ร่วมกันต่อไป
</Step>
<Step title="สร้าง container ใหม่แล้วเริ่มโปรแกรม">
daemon สร้าง [namespace](/2110506-sds/lecture-2#isolation-แยกด้วย-namespace) ชุดใหม่และ [cgroup](/2110506-sds/lecture-2#resource-control-จำกัดด้วย-cgroups) ชุดใหม่ วางชั้นเขียนได้ทับด้านบน แล้วเริ่มรันคำสั่ง — container ทำงานแล้ว
</Step>
</StepThrough>

## ส่วนที่ 3 — คำสั่งที่ต้องใช้จริง

### ชุดพื้นฐาน

```bash
## ดูรายการคำสั่งทั้งหมด
docker
docker COMMAND --help

## ดึง image จาก registry
docker pull IMAGE

## รัน image (สร้าง container) — ใส่ COMMAND เพื่อทับคำสั่งปริยายของ image ได้
docker run IMAGE [COMMAND]
docker run --name NAME IMAGE [COMMAND]

## ดูรายการ image
docker image ls          # เท่ากับ docker images
docker image ls --all    # เท่ากับ docker images -a

## ดูรายการ container
docker container ls          # เท่ากับ docker ps
docker container ls --all    # เท่ากับ docker ps -a
```

<Pitfall>
`docker ps` แสดงเฉพาะ container ที่ **กำลังรัน** เท่านั้น container ที่จบไปแล้วยังอยู่ในเครื่องแต่ไม่โผล่ ต้องใส่ `-a` ถึงจะเห็น หลายคนงงว่าทำไมพื้นที่ดิสก์หายไปทั้งที่ `docker ps` ว่างเปล่า
</Pitfall>

### ตัวเลือกของ `docker run` ที่ใช้บ่อยที่สุด

```bash
docker run [OPTIONS] IMAGE [COMMAND] [ARGS]
```

| ตัวเลือก | ทำอะไร |
| --- | --- |
| `--name` | ตั้งชื่อให้ container ถ้าไม่ตั้ง Docker สุ่มชื่อให้ เช่น `trusting_aryabhata` |
| `-d` / `--detach` | รันเบื้องหลัง คืนเทอร์มินัลให้ทันที |
| `-it` | รันแบบโต้ตอบพร้อมเทอร์มินัล ใช้ `-i` เดี่ยวได้ถ้าโปรแกรมไม่ต้องการเทอร์มินัล |
| `--rm` | ลบ container ทิ้งอัตโนมัติเมื่อมันหยุด |
| `-p` / `--publish` | จับคู่พอร์ตของ host เข้ากับพอร์ตของ container |
| `-v` / `--volume` | ต่อที่เก็บข้อมูลถาวรเข้ามา |
| `-e` | ตั้งตัวแปรสภาพแวดล้อม |

container "Hello World" ที่เล็กที่สุดคือ

```bash
docker run ubuntu /bin/echo 'Hello world'
```

### `docker run` กับ `docker exec` ไม่เหมือนกัน

<Compare>
<Wrong>
**`docker run IMAGE`**

สร้าง container **ใหม่** ทุกครั้ง

= namespace ชุดใหม่ + cgroup ชุดใหม่ + ชั้นเขียนได้ชุดใหม่

พิมพ์ซ้ำสิบครั้งได้ container สิบตัวและไฟล์สิบชุดที่ไม่รู้จักกัน
</Wrong>
<Right>
**`docker exec CONTAINER COMMAND`**

สร้าง **process ใหม่ใน container ที่มีอยู่แล้ว**

= เข้าไปร่วม namespace และ cgroup ของ container ตัวนั้น

เห็นไฟล์เดียวกัน เห็นเครือข่ายเดียวกัน กินโควตาก้อนเดียวกัน
</Right>
</Compare>

```bash
$ docker run --detach --tty --name ubuntu ubuntu
```

### หยุด เริ่มใหม่ และลบ

| คำสั่ง | ผล |
| --- | --- |
| `docker stop CONTAINER` | จบ process ในนั้น แต่โค้ดและข้อมูลยังอยู่ครบ ให้เวลาปิดตัวเองก่อน 10 วินาที |
| `docker kill CONTAINER` | บังคับจบทันที ไม่ให้เวลา |
| `docker start CONTAINER` | ปลุก container ที่หยุดอยู่ให้กลับมารัน พร้อมโค้ดและข้อมูลเดิม |
| `docker container rm CONTAINER` | ลบทิ้งจริง ข้อมูลในชั้นเขียนได้หายไปด้วย |

`docker start` จะรัน **คำสั่งเดิม** ที่ใช้ตอนสร้าง container นั้น ซึ่งก็คือ `CMD` ใน Dockerfile หรือ `COMMAND` ที่ใส่ต่อท้าย `docker run` ถ้าอยากรู้ว่าคำสั่งนั้นคืออะไร ให้ดูส่วน `Config` จาก `docker inspect CONTAINER`

ลบทีเดียวหลายตัว

```bash
docker container rm $(docker container ls --all --quiet)
# เขียนสั้นได้เป็น
docker rm $(docker ps -a -q)
```

<Quiz question="สั่ง docker stop แล้ว docker start ไฟล์ที่เขียนไว้ใน container ยังอยู่ไหม แล้วถ้าสั่ง docker rm ล่ะ">
`stop` แล้ว `start` — ไฟล์ยังอยู่ครบ เพราะชั้นเขียนได้ของ container ไม่ได้ถูกลบ แค่ process หยุดไปเฉย ๆ

`rm` — หายหมด เพราะชั้นเขียนได้ถูกลบไปพร้อม container ถ้าอยากเก็บ ต้อง `docker commit` ไว้ก่อน หรือใช้ volume/bind mount ตั้งแต่แรก
</Quiz>

## ส่วนที่ 4 — Persistent Storage: ทำยังไงให้ไฟล์ไม่หาย

<Why>
container ก็คือ process ตัวหนึ่ง ไฟล์ที่มันเขียนอยู่ในชั้นเขียนได้ซึ่งมีอายุเท่ากับ container พอ container ถูกลบ ไฟล์หายตาม ฐานข้อมูลที่รันใน container จึงล้างตัวเองทุกครั้งที่ deploy ใหม่ ถ้าไม่ทำอะไรเลย
</Why>

สไลด์ขัดกันเองในเรื่องนี้ หน้าหนึ่งบอกว่าไฟล์หายเมื่อ container หยุด อีกหน้าบอกว่า `stop` ยังเก็บโค้ดและข้อมูลไว้ ของจริงเป็นแบบหลัง ไฟล์อยู่รอดผ่าน `stop` และหายเมื่อ `rm`

Docker ให้สองวิธีในการฝากไฟล์ไว้นอก container

<Figure number={5} caption="bind mount ผูกโฟลเดอร์ของเครื่องจริงเข้ามา ส่วน volume ใช้พื้นที่ที่ Docker สร้างและดูแลเอง">
  <PersistentData />
</Figure>

### วิธีที่ 1: Bind Mount

ผูกโฟลเดอร์ของ host เข้ากับโฟลเดอร์ใน container ตรง ๆ

```bash
docker run -v [host_directory]:[container_directory] IMAGE
```

<Example title="เขียนไฟล์ใน container แล้วลบ container ทิ้ง">
```bash
$ ls /home/veera/container/
                                     # ว่างเปล่า
$ docker run --name ubuntu -it -v /home/veera/container:/home ubuntu
root@3cfc393b56a3:/# cat > /home/test.txt
test
root@3cfc393b56a3:/# exit

$ docker rm ubuntu
ubuntu
$ cat /home/veera/container/test.txt
test
```

container ถูกลบไปแล้ว แต่ไฟล์ยังอยู่บนเครื่อง เพราะมันไม่เคยอยู่ใน container ตั้งแต่แรก
</Example>

### วิธีที่ 2: Volume Mapping

<Term en="Volume" th="พื้นที่เก็บข้อมูลที่ Docker สร้างและดูแลให้" /> คือที่เก็บข้อมูลถาวรที่ถูกสร้างขึ้นนอก container เก็บอยู่ในระบบไฟล์ของ host แต่ **Docker เป็นคนจัดการให้** และเป็นวิธีที่แนะนำให้ใช้เป็นหลัก เพราะย้ายที่ได้ง่ายกว่า

```bash
docker volume create myvol
docker run -v [volume]:[container_directory] IMAGE
```

<Example title="สร้าง volume แล้วดูว่ามันไปอยู่ที่ไหนบนเครื่องจริง">
```bash

myvol

DRIVER    VOLUME NAME
local     myvol
$ docker volume inspect myvol
        "Mountpoint": "/var/lib/docker/volumes/myvol/_data",
```

```json
    {
        "CreatedAt": "2019-09-16T00:01:18+07:00",
```

```bash

$ docker rm ubuntu

$ sudo cat /var/lib/docker/volumes/myvol/_data/test

```

ต่างจาก bind mount ตรงที่คุณไม่ได้เลือกที่อยู่เอง Docker เลือกให้ที่ `/var/lib/docker/volumes/`
</Example>

<Wrong>

ผูกกับโครงสร้างโฟลเดอร์ของเครื่องนั้น ย้ายเครื่องแล้วพาธอาจไม่มี

เหมาะกับตอนพัฒนา เช่น ให้ container เห็นซอร์สโค้ดในโปรเจกต์ที่กำลังแก้อยู่
</Wrong>

เหมาะกับข้อมูลจริงที่ต้องอยู่ยาว เช่น ฐานข้อมูล — เป็นตัวเลือกที่แนะนำ
</Right>
</Compare>

<KeyIdea>
ไฟล์ที่ต้องอยู่ต่อหลัง container ถูกลบต้องเก็บไว้นอกชั้นเขียนได้ bind mount ใช้โฟลเดอร์ที่คุณเลือกเองบน host ส่วน volume ให้ Docker ดูแลที่อยู่ให้ และเป็นตัวเลือกที่แนะนำ
</KeyIdea>

## ส่วนที่ 5 — Docker Networking: ให้ container คุยกันและคุยกับข้างนอก

### container ทุกตัวได้ IP มาเองอัตโนมัติ

```bash
$ docker container inspect nginx | grep IPAddress
        "SecondaryIPAddresses": null,
        "IPAddress": "172.17.0.2",
```

### เปิดพอร์ตให้โลกภายนอกเข้าถึง

<Why>
container ถูกแยกขาดไว้ตั้งแต่ต้น ของข้างนอกจึงเข้าไม่ถึงจนกว่าจะประกาศเปิดพอร์ตให้ชัดเจน และเพราะ container หลายตัวมักใช้พอร์ตปริยายเดียวกัน (เว็บเซิร์ฟเวอร์ใช้ 80, MySQL ใช้ 3306) จะเอาพอร์ตเดิมของ host ให้ทุกตัวไม่ได้ ต้อง map ไปคนละพอร์ต
</Why>

```bash
docker run -p [host_port]:[container_port] IMAGE
docker run -p [container_port] IMAGE          # ให้ Docker สุ่มพอร์ตฝั่ง host ให้
```

<Example title="nginx บนพอร์ต 4000 ของเครื่อง แต่พอร์ต 80 ข้างใน">
```bash
$ docker run -d --name nginx -p 4000:80 nginx
533898a25687d5cda2911b935053c9740d646984d99025e2e2a3254b7f1bd6b4
$ docker ps
CONTAINER ID   IMAGE   COMMAND                  PORTS
533898a25687   nginx   "/docker-entrypoint.…"   0.0.0.0:4000->80/tcp, :::4000->80/tcp
```

ทดสอบสามทาง สองทางแรกเป็นคำสั่ง ทางที่สามคือเปิดเบราว์เซอร์ที่ `localhost:4000` ซึ่งได้หน้าเดียวกับทางที่ 1

```bash
# 1. จากเครื่อง host ผ่านพอร์ต 4000
$ curl localhost:4000
<title>Welcome to nginx!</title>

# 2. จากข้างใน container เดียวกัน ผ่านพอร์ต 80
$ docker exec -it nginx bash
root@0f5e4c2df1fb:/# curl localhost:80
<title>Welcome to nginx!</title>
```

เลข 4000 มีอยู่แค่ฝั่งนอก ส่วนข้างใน container ยังเป็น 80 เสมอ
</Example>

### ภาพรวมสามชั้นของที่อยู่

การทดลองนี้เราใช้ container ตัวช่วยชื่อ `ubuntu_tools` มันคือ ubuntu ที่ลงเครื่องมือเครือข่ายเพิ่มไว้

| --- | --- |
| `iputils-ping` | `ping` |
| `net-tools` | `ifconfig` |
| `iproute2` | `ip` |
| `curl` | `curl` |

<Example title="เข้าถึง nginx จากสองที่">
จากเครื่อง host เปิดเบราว์เซอร์ไปที่ `localhost:4000` — เห็นหน้า Welcome to nginx

จาก container `ubuntu_tools` เรียกด้วย IP ของ container โดยตรง

```bash
root@863d667ab61d:/# curl 172.17.0.2:80
<title>Welcome to nginx!</title>

root@863d667ab61d:/# ping 172.17.0.2
PING 172.17.0.2 (172.17.0.2) 56(84) bytes of data.
64 bytes from 172.17.0.2: icmp_seq=1 ttl=64 time=0.238 ms
```

ทั้งสองทางใช้ได้ แต่คนละพอร์ต — ข้างใน network ของ Docker ใช้ 80 ตรง ๆ ไม่ต้องผ่าน port mapping
</Example>

### ปัญหา: container ไม่รู้จักกันด้วยชื่อ

พอลองเรียกด้วยชื่อแทน IP กลับพัง

```bash
root@863d667ab61d:/# curl nginx:80
curl: (6) Could not resolve host: nginx

root@863d667ab61d:/# curl 9dc8ed7ab142:80
curl: (6) Could not resolve host: 9dc8ed7ab142
root@863d667ab61d:/# ping 9dc8ed7ab142
ping: 9dc8ed7ab142: Name or service not known
```

เหตุผลอยู่ในไฟล์ `/etc/hosts` ของ container ซึ่งเก็บการจับคู่ IP กับชื่อเครื่อง

```bash
root@863d667ab61d:/# cat /etc/hosts
127.0.0.1       localhost
172.17.0.3      863d667ab61d
```

มีแต่ชื่อของตัวเอง ไม่มีบรรทัดของ nginx เลย

<Detail label="ดูไฟล์ /etc/hosts ทั้งไฟล์">
```
127.0.0.1       localhost
::1     localhost ip6-localhost ip6-loopback
fe00::0 ip6-localnet
ff00::0 ip6-mcastprefix
ff02::1 ip6-allnodes
ff02::2 ip6-allrouters
172.17.0.3      863d667ab61d
```
</Detail>

<Pitfall>
ปัญหานี้ร้ายกว่าที่คิด เพราะ IP ของ container ไม่คงที่ พอลบแล้วสร้างใหม่ เลขเปลี่ยน โค้ดที่ hardcode `172.17.0.2` ไว้จะพังเงียบ ๆ ในวันที่คุณ restart อะไรสักอย่าง
</Pitfall>

### Bridge network

<Term en="Bridge Network" th="เครือข่ายสะพานภายในเครื่อง" /> คือเครือข่ายที่ทำให้ container ที่ต่ออยู่บน bridge เดียวกันคุยกันได้ ส่วน container ที่อยู่คนละ bridge จะคุยกันตรง ๆ ไม่ได้

กฎที่ต้องรู้

- Docker สร้าง bridge ปริยายชื่อ `bridge` ให้อัตโนมัติตอนเริ่มทำงาน
- container ที่สร้างใหม่จะต่อเข้ากับ bridge นี้เอง ถ้าไม่ระบุอย่างอื่น
- bridge network ใช้ได้เฉพาะ container ที่อยู่บน Docker daemon เครื่องเดียวกัน

```bash
$ docker network inspect bridge
        "Subnet": "172.17.0.0/16",
        "Gateway": "172.17.0.1"
        ...
        "Containers": {
            "863d667ab61d...": { "Name": "ubuntu_tools", "IPv4Address": "172.17.0.3/16" },
            "9dc8ed7ab142...": { "Name": "nginx",        "IPv4Address": "172.17.0.2/16" }
        }
```

### ทางแก้: สร้าง bridge ของตัวเอง

ความต่างมีข้อเดียว แต่เป็นข้อที่เปลี่ยนทุกอย่าง

| | bridge ปริยาย | bridge ที่สร้างเอง |
| --- | --- | --- |
| DNS ในตัว | **ไม่มี** | **มี** |
| เรียกกันยังไง | ได้แต่ IP | ใช้ชื่อ container หรือ alias ได้ |

<Step title="สร้างเครือข่ายใหม่">
```bash

$ docker network ls
```

</Step>
<Step title="ดูว่ามันได้ช่วง IP อะไรมา">
```bash
$ docker network inspect mynet
        "Subnet": "172.18.0.0/16",
        "Gateway": "172.18.0.1"
        "Containers": {},
```
`172.18.0.0/16` คนละช่วงกับ bridge ปริยาย และยังไม่มี container ต่ออยู่
</Step>
<Step title="เอา container ที่มีอยู่แล้วมาต่อเพิ่ม">
```bash
docker network connect mynet nginx
docker network connect mynet ubuntu_tools
```
ตอนนี้ `docker inspect nginx` จะเห็นสองเครือข่ายพร้อมกัน: `bridge` ที่ `172.17.0.2` และ `mynet` ที่ `172.18.0.2` — **container หนึ่งตัวอยู่ได้หลายเครือข่าย**
</Step>
<Step title="หรือสร้าง container ใหม่บนเครือข่ายนั้นเลย">

ระวังจุดนี้: container ที่ระบุ `--network` ตอนสร้าง จะ **ไม่** ต่อกับ bridge ปริยายด้วย
</Step>
<Step title="ทดสอบว่าเรียกด้วยชื่อได้แล้ว">


</Step>

```bash
docker network disconnect bridge nginx

```
`docker network inspect bridge` จะเห็น `"Containers": {}` — ว่างเปล่า ทั้งคู่ย้ายไปอยู่ `mynet` อย่างเดียวแล้ว

### ใช้หลายเครือข่ายเพื่อกันไม่ให้ของหลังบ้านโดนเข้าถึง

<Why>
ในระบบจริง มีบริการที่ต้องเปิดให้โลกภายนอกเข้า เช่น frontend และ API แต่มีบริการที่ **ไม่ควรเปิดเด็ดขาด** เช่น ฐานข้อมูล การใส่ไฟร์วอลล์ทีหลังเป็นการแก้ปลายเหตุ วิธีที่ตรงกว่าคือไม่ให้มันอยู่บนเครือข่ายเดียวกันตั้งแต่แรก
</Why>

<Example title="แยกเป็นสองเครือข่าย ให้ฐานข้อมูลไม่มีทางออกสู่ภายนอก">
```bash
docker network create backend-network
docker network create frontend-network

docker run -d --name backend-app --network backend-network my-backend-app

docker run -d --name frontend-app --network frontend-network \
  --network backend-network -p 80:80 my-frontend-app
```

ผลที่ได้

- `backend-app` อยู่บน `backend-network` อย่างเดียว และไม่มี `-p` จึงไม่มีพอร์ตไหนของ host ชี้มาถึงมันเลย
- `frontend-app` อยู่ทั้งสองเครือข่าย และเปิดพอร์ต 80 ออกสู่ภายนอก
- ผลลัพธ์คือ โลกภายนอกคุยกับ frontend ได้ frontend คุยกับ backend ได้ แต่โลกภายนอกไปถึง backend ไม่ได้
</Example>

<Quiz question="สร้าง container ด้วย docker run --network mynet ... แล้วสั่ง curl ไปที่ container อีกตัวที่อยู่บน bridge ปริยาย จะได้ผลไหม">
ไม่ได้ เพราะ container ที่ระบุ `--network` ตอนสร้าง จะไม่ถูกต่อเข้ากับ bridge ปริยายเลย และ container ที่อยู่คนละ bridge คุยกันตรง ๆ ไม่ได้

ถ้าอยากให้คุยกัน ต้องสั่ง `docker network connect` เพิ่มเครือข่ายให้ตัวใดตัวหนึ่ง
</Quiz>

<Figure number={8} caption="สาม container คนละหน้าที่บนเครือข่ายเดียวกัน จึงเรียกกันด้วยชื่อได้">

<StepThrough>
<Step title="Node Exporter — คนอ่านตัวเลขจากเครื่อง">
โปรแกรมที่เก็บ metric ของฮาร์ดแวร์และระบบปฏิบัติการ ใช้วัดทรัพยากรของเซิร์ฟเวอร์ เช่น การใช้ CPU, RAM, พื้นที่ดิสก์

```bash
docker run --rm -d -p 9100:9100 --network mynet --name node-exporter prom/node-exporter
```

เปิด `http://localhost:9100/metrics` จะเห็นตัวเลขดิบ ๆ เป็นบรรทัด ๆ กด refresh แล้วตัวเลขเปลี่ยน

```
# HELP go_goroutines Number of goroutines that currently exist.
# TYPE go_goroutines gauge
go_goroutines 8
```
</Step>
<Step title="Prometheus — คนไปดึงมาเก็บเป็นประวัติ">
ระบบเฝ้าดูที่เก็บ metric จากเป้าหมายที่ตั้งไว้ตามช่วงเวลาที่กำหนด ประเมินนิพจน์ของกฎ แล้วแสดงผล

ไฟล์ตั้งค่า `prometheus.yml`

```yaml
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: node
    static_configs:
      - targets: ['node-exporter:9100']
```

สังเกตว่าเป้าหมายเขียนเป็น `node-exporter:9100` — **ใช้ชื่อ container ได้เพราะอยู่บน `mynet` ที่สร้างเอง** ถ้าอยู่บน bridge ปริยาย ต้องกรอก IP ซึ่งเปลี่ยนทุกครั้งที่สร้างใหม่

```bash
docker run --rm -d -p 9090:9090 --network mynet --name prometheus \
  -v /home/veera/docker/monitoring/prometheus.yml:/etc/prometheus/prometheus.yml \
  prom/prometheus:v3.0.1
```

ไฟล์ตั้งค่าเข้าไปด้วย bind mount — แก้ไฟล์บนเครื่องแล้ว restart container ก็ใช้ค่าใหม่ได้ทันที
</Step>
<Step title="ลองใช้หน้าเว็บของ Prometheus">
เปิด `http://localhost:9090/` พิมพ์ชื่อ metric เช่น `node_procs_running` กด Execute แล้วสลับไปแท็บ Graph จะเห็นกราฟย้อนหลัง
</Step>
<Step title="Grafana — คนวาดกราฟให้สวยและตั้งเตือนได้">
เว็บแอปสำหรับวิเคราะห์และแสดงผลแบบโต้ตอบ ให้ทั้งกราฟ แผนภูมิ และการแจ้งเตือน เมื่อต่อกับแหล่งข้อมูลที่รองรับ

Grafana เก็บฐานข้อมูล dashboard ไว้ที่ `/var/lib/grafana` ถ้าไม่ทำอะไร dashboard ที่สร้างไว้จะหายเมื่อ container ตาย จึงต้องสร้าง volume มารับ

```bash
docker volume create grafana-vol

docker run --rm -d -p 3000:3000 --network mynet \
  -v grafana-vol:/var/lib/grafana --name grafana grafana/grafana:11.4.0
```

เปิด `http://localhost:3000` ล็อกอินด้วยชื่อผู้ใช้และรหัสผ่านเริ่มต้นของ Grafana คือ `admin` / `admin` เมื่อระบบขอให้เปลี่ยนรหัส ให้กด skip ไปก่อนสำหรับการทดลองในคาบ
</Step>
<Step title="ต่อ Grafana เข้ากับ Prometheus">
ไปที่ Connections → Data sources → Add data source → เลือก Prometheus

ช่อง Prometheus server URL กรอก `http://prometheus:9090` แล้วกด Save & test

ตรงนี้คือหัวใจของทั้งตัวอย่าง — Grafana เรียก Prometheus **ด้วยชื่อ** ได้ เพราะทั้งคู่อยู่บน `mynet`
</Step>
<Step title="สร้าง dashboard">
Dashboards → Create dashboard → Add visualization → เลือก data source `prometheus`

ในช่อง Metric ใช้ Metrics explorer ค้นหา เช่น `node_load1` (ค่าเฉลี่ยโหลด 1 นาที) แล้วกด Select
</Step>
<Step title="รัน query แล้ว Apply">
กด Run queries เพื่อดูผลก่อน ถ้ากราฟถูกต้องแล้วกด Apply เพื่อเอาแผงนี้เข้า dashboard
</Step>
<Step title="ตั้งอัตรารีเฟรชและบันทึก">
เลือกอัตรารีเฟรชที่มุมขวาบน เช่น `1m` เพื่อให้กราฟอัปเดตเอง แล้วกดปุ่มบันทึก ตั้งชื่อ dashboard เช่น `Node Monitoring` แล้วกด Save

เพราะสร้าง `grafana-vol` ไว้ dashboard นี้จะยังอยู่แม้ container ถูกลบและสร้างใหม่
</Step>

<KeyIdea>
ระบบจริงคือหลาย container บนเครือข่ายที่สร้างเองเพื่อให้เรียกกันด้วยชื่อ เปิดพอร์ตเฉพาะที่ต้องเข้าจากข้างนอก ส่งไฟล์ตั้งค่าเข้าไปด้วย bind mount และเก็บข้อมูลที่ต้องอยู่ต่อใน volume
</KeyIdea>

<Recap>
- **Docker** ประกอบด้วย CLI (client) → REST API → daemon (server) ซึ่งเป็นเจ้าของ container, image, network และ volume ทั้งหมด บน Mac และ Windows มันรัน container ใน Linux VM
- **ชื่อ image เต็ม** คือ `registry/username/image_name:tag` ที่ขาดไปจะถูกเติมเป็น `docker.io/library/...:latest`
- **`docker run` กับ `docker exec`** — run สร้าง container ใหม่พร้อม namespace และ cgroup ชุดใหม่ ส่วน exec สร้าง process ใหม่ที่เข้าไปร่วมของเดิม
- **สถานะของ container** — running, paused, exited, restarting `stop` ไม่ลบข้อมูล มีแต่ `rm` ที่ลบ
- **`docker diff` แล้ว `docker commit`** เปลี่ยนชั้นเขียนได้ให้เป็นชั้นอ่านอย่างเดียวชั้นใหม่ กลายเป็น image ใหม่
- **ที่เก็บข้อมูลถาวรมีสองแบบ** — bind mount ผูกพาธของ host เอง เหมาะกับตอนพัฒนา ส่วน volume ให้ Docker ดูแลที่อยู่ให้ ย้ายที่ง่ายกว่า และเป็นตัวเลือกที่แนะนำ
- **เครือข่าย** — container ได้ IP อัตโนมัติ ต้อง `-p` ถึงจะเข้าจากภายนอกได้ bridge ปริยายไม่มี DNS จึงเรียกกันได้แต่ด้วย IP ส่วน bridge ที่สร้างเองมี DNS เรียกด้วยชื่อ container ได้
- **container หนึ่งตัวอยู่ได้หลายเครือข่าย** ซึ่งเป็นวิธีกันไม่ให้ฐานข้อมูลถูกเข้าถึงจากภายนอก โดยให้ frontend อยู่ทั้งสองฝั่งแต่ backend อยู่ฝั่งในอย่างเดียว
- **ตัวอย่างรวม** — node-exporter (9100) → Prometheus (9090) → Grafana (3000) ทั้งหมดอยู่บน `mynet` จึงตั้งค่าเป้าหมายเป็น `node-exporter:9100` และ `http://prometheus:9090` ด้วยชื่อได้ ส่วน dashboard ของ Grafana ต้องมี volume ถึงจะไม่หาย

<Quiz question="nginx ฟังพอร์ต 80 ข้างใน container ตัวแรกรันด้วย `-p 4000:80` แล้ว คุณรันตัวที่สองด้วย `-p 4001:8080` เพราะคิดว่าพอร์ตข้างใน container ต้องไม่ซ้ำกับตัวแรก เปิด `localhost:4001` จะเจออะไร">
แต่ละ container มี network namespace ของตัวเอง พอร์ต 80 ข้างในตัวที่สองจึงไม่ชนกับพอร์ต 80 ของตัวแรก ที่ห้ามซ้ำคือพอร์ตฝั่ง host เท่านั้น `-p 4001:8080` ส่งคำขอเข้าไปที่พอร์ต 8080 ข้างใน container แต่ nginx ฟังอยู่ที่ 80 จึงไม่มีใครรับ

คำตอบคือ **เปิดไม่ขึ้น** การเชื่อมต่อถูกตัด ต้องใช้ `-p 4001:80`

คำตอบที่ผิดบ่อยคือ "เปิดได้ เพราะเลขพอร์ตไม่ชนกันแล้ว" ซึ่งมองว่าทุก container ใช้พอร์ตชุดเดียวกับ host แต่เลขหลังทวิภาคต้องตรงกับพอร์ตที่โปรแกรมข้างใน container ฟังจริง
</Quiz>

<Quiz question="container `small` ตั้ง `--cpus=0.5` และมี `yes` กิน CPU เต็มโควตาอยู่ คุณสั่ง `docker exec small sh -c 'yes >/dev/null'` เพิ่มอีกตัว container นี้จะใช้ CPU รวมเท่าไหร่">
`docker exec` ไม่ได้สร้าง container ใหม่ process ใหม่เข้าไปอยู่ใน cgroup เดียวกับ process เดิม และ `--cpus=0.5` คือ [`cpu.max`](/2110506-sds/lecture-2#เพดานเก็บไว้ที่ไหน) ของทั้งกลุ่ม สอง process จึงแบ่งเพดานเดียวกัน

คำตอบคือ **ยังราว 0.5 CPU รวมกัน** ตัวละราว 0.25 และ `docker stats` ยังแสดงราว 50%

คำตอบที่ผิดบ่อยคือ "1 CPU เพราะแต่ละ process ได้โควตาของตัวเอง" ซึ่งมองว่าโควตาผูกกับ process แต่ cgroup คุมทั้งกลุ่ม ใครเข้ามาในกลุ่มทีหลังก็ต้องแย่งจากเพดานเดิม
</Quiz>

</Recap>
