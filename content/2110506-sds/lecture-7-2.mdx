[Lecture 7.1](/2110506-sds/lecture-7) นิยาม IaaS ว่าเป็นการเช่า virtual machine (VM) ที่คุณคุมตั้งแต่ OS ขึ้นไป ผู้ให้บริการทำเงินได้จากสองกลไก กลไกแรกคือ resource pooling ซึ่งรวมเครื่องจริงเป็นกองกลางแล้วแบ่งให้ลูกค้าหลายรายใช้พร้อมกัน การที่ลูกค้าหลายรายอยู่บนเครื่องเดียวกันเรียกว่า multi-tenant กลไกที่สองคือ measured service ซึ่งวัดว่าใครใช้ไปเท่าไหร่แล้วคิดเงินตามนั้น

หน้านี้เปิดดูว่าการแบ่งเครื่องและการวัดการใช้งานทำงานยังไง ตั้งแต่คุณกด Launch จนได้เครื่อง

<Callout type="info" title="ข้อมูลในหน้านี้มาจากไหน">
เนื้อหามาจากสไลด์ Lecture 7 หน้า 42–56 และ 59–103 ภาพหน้าจอ ตัวเลข ผลการวัด ผลการรันคำสั่งบน EC2 และตารางมาจากสไลด์จริง ส่วนคำอธิบาย รูป ตารางคำนวณ overcommit ในส่วนที่ 4 ผลการรัน `truncate` และกล่องที่ติดป้าย "เสริม" เขียนขึ้นใหม่
</Callout>

<KeyIdea>
IaaS cloud คือ VM ที่ hypervisor แบ่งออกมาจากเครื่องจริงที่ใช้ร่วมกัน ทุกการตัดสินใจของผู้ให้บริการ ตั้งแต่วาง VM ลงเครื่องไหน ขายเกินจำนวน core จริงได้แค่ไหน ไปจนถึงคิดเงิน CPU ยังไง คือการชั่งระหว่าง **แชร์ให้มากเพื่อลดต้นทุน** กับ **แยกให้พอจนลูกค้าแต่ละรายไม่กระทบกัน**
</KeyIdea>

## ส่วนที่ 1 — ขอเครื่องหนึ่งเครื่องบน Amazon EC2

<Term en="Amazon EC2 (Elastic Compute Cloud)" th="บริการเช่า VM ของ AWS" /> คือบริการ IaaS แบบ public cloud ซึ่งเป็นส่วนหนึ่งของ AWS (Amazon Web Services) ผู้ใช้เข้า portal ที่ [console.aws.amazon.com/ec2](https://console.aws.amazon.com/ec2/) แล้วขอเครื่องที่มี CPU หน่วยความจำ และพื้นที่ดิสก์ตามที่ต้องการ พร้อม OS สำเร็จรูป และอาจมี middleware ติดมาด้วย

หน้า dashboard ของ EC2 มีตัวเลือก **region** มุมขวาบน เช่น Singapore เครื่องที่สร้างจะอยู่ใน data center ของ region นั้น จากนั้นกดปุ่ม **Launch instance**

### หกสิ่งที่ต้องเลือกก่อนกด Launch

<Term en="instance" th="เครื่องหนึ่งเครื่องที่เช่าบน EC2" /> คือคำที่ AWS ใช้เรียก VM หนึ่งเครื่อง หน้าขอ instance ให้เลือกหกเรื่อง

| เลือกอะไร | ค่าที่ใช้ในตัวอย่าง | ความหมาย |
| --- | --- | --- |
| **Name and tags** | `activity1` | ชื่อไว้แยกเครื่อง |
| **AMI** | Amazon Linux 2023, 64-bit x86 | software stack สำเร็จรูป มีให้เลือก Amazon Linux, macOS, Ubuntu, Windows, Red Hat, SUSE |
| **Instance type** | `t2.micro` — 1 vCPU, 1 GiB | ขนาด CPU และหน่วยความจำ ซึ่งกำหนดราคา |
| **Key pair** | สร้างใหม่แล้วดาวน์โหลด | กุญแจที่ใช้ login เข้าเครื่อง |
| **Network settings** | เครือข่ายปริยายของบัญชี (VPC), เปิด public IP, security group ใหม่ | เครือข่ายและ firewall ของเครื่อง |
| **Storage** | 8 GiB แบบ gp3 | ดิสก์ของเครื่อง เป็น EBS General Purpose (SSD) |

<Term en="AMI (Amazon Machine Image)" th="แม่แบบ software stack ของเครื่อง" /> คือแม่แบบที่มี OS และอาจมี application server กับแอปติดตั้งไว้แล้ว คล้ายกับ **virtual appliance** คือเครื่องเสมือนสำเร็จรูปที่พร้อมใช้ทันที ส่วนที่ 7 เปิดดูว่ามันถูกเก็บและคัดลอกยังไง

<Term en="vCPU (virtual CPU)" th="CPU ที่ VM มองเห็น" /> คือ CPU หนึ่งตัวในมุมของ VM ข้างใต้ hypervisor อาจให้มันใช้ core จริงเพียงบางส่วนของเวลา ส่วนที่ 5 วัดผลของการแบ่งนี้ และส่วนที่ 6 ดูว่ามันถูกคิดเงินยังไง

<Term en="EBS (Elastic Block Store)" th="ดิสก์ของ instance บน AWS" /> คือดิสก์แบบ block ที่ต่อเข้ากับ instance และอยู่ต่อได้แม้ instance หยุดทำงาน

ราคาของ `t2.micro` แบบ on-demand บนหน้าจอนี้ (ภาพหน้าจอปี 2023) ต่างกันตาม OS คือ Linux และ SUSE $0.0146, Windows $0.0192 และ Red Hat $0.0746 ต่อชั่วโมง เพราะค่า license ของ OS รวมอยู่ในค่าเช่า

<Term en="Security group" th="ชุดกฎ firewall ของ instance" /> คือชุดกฎ firewall ที่บอกว่ายอมให้ traffic แบบไหนเข้าเครื่อง ค่าที่หน้าจอเสนอมาให้คือสร้างกลุ่มใหม่ชื่อ `launch-wizard-14` ที่ **ยอมให้ SSH เข้าจากทุกที่ (`0.0.0.0/0`)** และไม่เปิด HTTP กับ HTTPS พร้อมคำเตือนว่ากฎที่มีต้นทาง `0.0.0.0/0` ยอมทุก IP และแนะนำให้ยอมเฉพาะ IP ที่รู้จัก

<Callout type="warn" title="เลือกเฉพาะ Free Tier">
ถ้าเลือกอะไรนอก Free Tier ค่าใช้จ่ายจะเรียกเก็บจากบัตรเครดิตจริง ตอนที่ทำสไลด์ Free Tier ในปีแรกให้ `t2.micro` 750 ชั่วโมงต่อเดือน, EBS 30 GB, 2 ล้าน IO, snapshot 1 GB และ bandwidth ออกอินเทอร์เน็ต 100 GB

</Callout>

### Key pair และกุญแจอื่นของบัญชี AWS

ตอนสร้าง instance คุณได้ไฟล์ private key มาหนึ่งไฟล์ แต่บัญชี AWS ยังมีกุญแจอีกหลายแบบ แต่ละแบบเปิดคนละประตู

| กุญแจ | ใช้ทำอะไร |
| --- | --- |
| Email และรหัสผ่าน | login เป็น **root user** ของบัญชี ซึ่งทำได้ทุกอย่าง |
| ชื่อผู้ใช้และรหัสผ่านของ IAM | login เป็นผู้ใช้ย่อยที่ได้สิทธิ์เท่าที่กำหนด |
| MFA | ชั้นพิสูจน์ตัวตนที่สอง ต่อจากรหัสผ่าน |
| Access key (access key ID + secret access key) | ให้โปรแกรมเรียก API ของ AWS |
| Key pair | private key ที่ใช้ login เข้า VM บน EC2 |

<Term en="IAM (Identity and Access Management)" th="ระบบจัดการผู้ใช้และสิทธิ์ของ AWS" /> คือระบบที่ให้สร้างผู้ใช้ย่อยในบัญชีเดียว แทนการแจก email และรหัสผ่านของ root user ให้ทุกคน

<Term en="Key pair" th="คู่กุญแจ public กับ private" /> ประกอบด้วย public key กับ private key คุณใช้ private key สร้าง digital signature แล้วฝั่ง AWS ใช้ public key ที่คู่กันตรวจลายเซ็นนั้น ในกรณี SSH public key ถูกใส่ไว้ใน instance และเครื่องใช้มันตรวจลายเซ็นตอนคุณ SSH เข้า

บน AWS key pair ใช้กับสองบริการเท่านั้น คือ Amazon EC2 และ Amazon CloudFront ซึ่งเป็นบริการกระจายเนื้อหาเว็บ บน EC2 งานหลักของ key pair คือ SSH เข้า Linux instance

<Pitfall>
"ถ้าทำไฟล์ private key หาย ก็ขอ AWS ส่งให้ใหม่ได้" ไม่ได้ ไฟล์นั้นกู้คืนไม่ได้ และคุณจะ SSH เข้าเครื่องด้วย key pair นั้นไม่ได้อีก

ที่ดูเหมือนขอใหม่ได้เพราะรหัสผ่านเว็บทั่วไปกด "ลืมรหัสผ่าน" ได้ แต่ key pair ทำงานคนละแบบ ตอน launch ระบบใส่แค่ **public key** ลงในเครื่อง เพื่อใช้ตรวจลายเซ็นที่ private key สร้าง private key มีอยู่ชุดเดียวในไฟล์ที่คุณดาวน์โหลด ฝั่ง AWS ไม่มีสำเนาให้ส่งคืน จึงต้องจำชื่อ key pair และเก็บไฟล์ไว้ในที่ปลอดภัยตั้งแต่ตอนสร้าง

ถ้าไฟล์หายไปแล้ว ทางกลับมีแต่ทางอ้อม เช่น หยุดเครื่อง ถอดดิสก์ไปต่อกับเครื่องอื่น แล้วใส่ public key ใหม่ลงไปแทน
</Pitfall>

<Quiz question="นิสิตคนหนึ่งสร้าง instance แล้วปล่อย security group ตามค่าที่หน้าจอเสนอไว้ จากนั้นติดตั้ง web server ที่ port 80 แต่เปิดเว็บจาก browser ไม่ขึ้น ทั้งที่ SSH เข้าเครื่องได้ปกติ ปัญหาอยู่ตรงไหน และแก้ยังไงให้ปลอดภัยกว่าเดิม">
ค่าที่หน้าจอเสนอคือยอม SSH (port 22) จาก `0.0.0.0/0` อย่างเดียว ช่อง "Allow HTTP traffic from the internet" ไม่ได้ติ๊ก security group จึงทิ้ง traffic ที่เข้า port 80 ก่อนถึง web server SSH ใช้ได้เพราะมีกฎของมันอยู่แล้ว

คำตอบคือ **security group ไม่มีกฎยอม HTTP** ให้เพิ่มกฎยอม port 80 และถ้าใช้ HTTPS ก็ port 443 ส่วนกฎ SSH ควรแก้จาก `0.0.0.0/0` เป็น IP ของตัวเองตามคำเตือนบนหน้าจอ เพราะเว็บต้องเปิดให้ทุกคน แต่ SSH ไม่จำเป็น

คำตอบที่พบบ่อยคือ "web server ตั้งค่าผิด" ซึ่งมองแค่ในเครื่อง แต่ firewall ของ EC2 อยู่ข้างนอก VM traffic ถูกทิ้งก่อนถึงเครื่องด้วยซ้ำ
</Quiz>

## ส่วนที่ 2 — ข้างหลังปุ่ม Launch: หกชิ้นส่วนของ IaaS cloud

จากมุมผู้ใช้ ขั้นทั้งหมดในส่วนที่ 1 สรุปได้หกข้อ

1. login เข้า portal
2. ขอเครื่องโดยระบุ CPU หน่วยความจำ ดิสก์ และ OS
3. cloud ส่งที่อยู่เครื่องกับข้อมูล login กลับมา
4. login เข้าเครื่องอย่างปลอดภัย
5. อาจขอให้ software stack ติดตั้งมากับ image ตั้งแต่แรก
6. อาจให้เครื่องโหลด stack สำเร็จรูปมาติดตั้งตอนเริ่มทำงาน ข้อนี้ต่างจากข้อ 5 ตรงที่ image ยังไม่มี stack นั้น

<Why>

## ส่วนที่ 3 — Virtualization: แบ่งเครื่องจริงเป็นหลายเครื่อง

### ทุกเครื่องที่คุณจะเจอเป็นเครื่องเสมือน

Physical resource pool คือกองเครื่องจริงที่ลูกค้าทุกรายใช้ร่วมกัน แต่ไม่มีลูกค้าคนไหนได้เครื่องจริงไปตรง ๆ เซิร์ฟเวอร์ที่คุณจะได้ใช้ในงานจริงแทบทั้งหมดเป็นเครื่องเสมือน และใน data center ปัจจุบันแทบไม่เหลือเซิร์ฟเวอร์ที่ไม่ผ่าน virtualization

ผลสำรวจของ RightScale ปี 2017 ก็พบองค์กรที่รัน VM บน VMware vSphere, AWS, Azure, OpenStack, Google Cloud และ IBM ตั้งแต่ 1–50 ไปจนถึงกว่า 1,000 เครื่อง

ก่อนมี virtualization เครื่องหนึ่งรันได้ OS เดียว แต่ละแอปจึงได้เครื่องของตัวเอง ซึ่งใช้งานจริงเพียง 5–15% <Term en="Virtualization" th="การสร้างของเสมือนแทนของจริง" /> คือการสร้างรุ่นเสมือนของบางสิ่ง เช่น เซิร์ฟเวอร์ เครือข่าย หรือ storage โดยแยกตัวทรัพยากร หรือคำขอใช้บริการ ออกจากฮาร์ดแวร์จริงที่อยู่ข้างใต้

| ก่อนมี virtualization | หลังมี virtualization |
| --- | --- |
| เครื่องหนึ่งรันได้ OS เดียว | OS และแอปไม่ผูกกับฮาร์ดแวร์ |
| ซอฟต์แวร์ผูกแน่นกับฮาร์ดแวร์ | สร้าง VM ลงเครื่องไหนก็ได้ |
| หลายแอปบนเครื่องเดียวมักตีกัน | จัดการ OS กับแอปเป็นก้อนเดียว เพราะห่อไว้ใน VM |
| ใช้ทรัพยากรไม่เต็ม | |
| โครงสร้างแข็งและแพง | |

ข้อดีของ virtualization มีห้าข้อ

- **รันหลาย OS บนเครื่องเดียวและแบ่งฮาร์ดแวร์กัน** เรียกว่า partitioning ผลคือ resource isolation แต่ละ VM แยกกันใช้ทรัพยากร
- **ผู้ดูแลจัดการทรัพยากรเป็นกองกลาง** ทั่วทั้งองค์กร
- **Server consolidation and containment** รวมเซิร์ฟเวอร์ที่กระจัดกระจาย (server sprawl) มาเป็น VM ที่ย้ายข้ามฮาร์ดแวร์ได้ ทำให้อัตราการใช้งานเซิร์ฟเวอร์ขึ้นจาก **5–15% เป็น 60–80%** และลดค่าไฟ
- **Test and development** สร้างเครื่องทดสอบได้เร็วจากระบบที่ตั้งค่าไว้แล้ว ทีมใช้สภาพแวดล้อมมาตรฐานเดียวกัน
- **Business continuity** ห่อทั้งระบบเป็นไฟล์ไม่กี่ไฟล์ ที่สำเนาไปเก็บและกู้คืนบนเครื่องไหนก็ได้ ลดต้นทุนของ high availability และ disaster recovery

ข้างใต้ VM คือ hypervisor ซึ่งสร้าง **virtual hardware** ให้แต่ละ VM คือ CPU หน่วยความจำ ดิสก์ และการ์ดเครือข่ายเสมือน แล้วแบ่ง physical hardware จริงให้ ทุก VM จึงมี OS ของตัวเองได้ ทั้งที่อยู่บนเครื่องเดียวกัน

<Pitfall>
"Cloud computing ก็คือ virtualization" ไม่ใช่ virtualization เป็นเทคโนโลยี ส่วน cloud computing เป็นบริการที่ virtualization ทำให้เกิดขึ้นได้ **cloud = virtualization + อีกหลายอย่าง**

ที่สับสนเพราะ IaaS ให้ VM ซึ่งมาจาก virtualization ตรง ๆ แต่ virtualization มีมาตั้งแต่ทศวรรษ 1960 บน mainframe ของ IBM หลายสิบปีก่อนจะมีคำว่า cloud computing สิ่งที่ต้องเพิ่มจนเป็น cloud คือชิ้นส่วนที่เหลือในรูปที่ 1 ได้แก่ portal ที่ขอเองได้ ตัวเลือกเครื่อง image library การวัด และการคิดเงิน ถ้าคุณลง VirtualBox บนโน้ตบุ๊ก คุณมี virtualization แต่ยังไม่มีคุณสมบัติข้อไหนของ cloud เลย
</Pitfall>

## ส่วนที่ 4 — Cloud manager วาง VM ลงเครื่องไหน

### ที่ว่างรวมพอ แต่วาง VM ไม่ลง

<Why>
เมื่อผู้ใช้ขอ VM หนึ่งตัว cloud resource manager ต้องเลือกว่าจะวางบน hypervisor ตัวไหน ถ้าเลือกไม่ดี ทรัพยากรที่ยังว่างอยู่ในระบบจะแตกเป็นเศษเล็ก ๆ จนคำขอถัดไปลงไม่ได้ ทั้งที่รวมกันแล้วยังพอ
</Why>

ระบบตัวอย่างมีเครื่องจริงสองเครื่อง แต่ละเครื่องมี **4 core และหน่วยความจำ 8 GB** สมมติว่า hypervisor ไม่กินทรัพยากรเลย VM มีสองขนาด

- **Small** 1 core, 2 GB
- **Large** 2 core, 4 GB

ถ้ามีแต่ small ระบบนี้รับได้ **8 ตัว** (เครื่องละ 4 ตัว จำกัดด้วยทั้ง core และหน่วยความจำพอดี)

คำขอมาตามลำดับ VM1 small, VM2 small, VM3 small, VM4 large, VM5 small, VM6 large ลองวางสองแบบ

ลองทายก่อน: ถ้าวาง VM แต่ละตัวลงเครื่องที่ว่างมากที่สุด VM6 จะลงได้ไหม

<Figure number={3} caption="คำขอหกตัวชุดเดียวกัน วางคนละนโยบาย largest remaining capacity กระจาย VM จนที่ว่างแตกและ VM6 ลงไม่ได้">

</Figure>

**Largest remaining capacity** วาง VM แต่ละตัวลงเครื่องที่เหลือที่ว่างมากที่สุด จึงกระจาย VM ไปทั่ว VM1 ไปเครื่อง 1, VM2 ไปเครื่อง 2, VM3 กลับเครื่อง 1, VM4 (large) ไปเครื่อง 2 ซึ่งว่าง 3 core, VM5 ไปเครื่อง 1 เมื่อ VM6 (large) มาถึง **แต่ละเครื่องเหลือ 1 core กับ 2 GB** รวมกันมี 2 core กับ 4 GB พอดีขนาดที่ขอ แต่ไม่มีเครื่องไหนรับได้

**Smallest remaining capacity** วาง VM ลงเครื่องที่เหลือที่ว่างน้อยที่สุดที่ยังพอ จึงอัดเครื่องหนึ่งให้เต็มก่อน VM1–VM3 ลงเครื่อง 1, VM4 (large) ไม่พอในเครื่อง 1 จึงลงเครื่อง 2, VM5 เติมเครื่อง 1 จนเต็ม และ VM6 ลงเครื่อง 2 ที่ยังว่าง 2 core ใช้ครบทั้ง 8 core

ปัญหาของ largest remaining capacity ในตัวอย่างนี้เรียกว่า <Term en="fragmentation" th="ที่ว่างแตกเป็นเศษที่ใช้ไม่ได้" /> คือที่ว่างรวมยังพอ แต่กระจายอยู่หลายเครื่องจนไม่มีเครื่องไหนว่างพอสำหรับคำขอเดียว

### นโยบายที่ cloud manager เลือกได้

นโยบายที่ใช้กันมีหลายแบบ

- **Round-robin** วนไปทีละเครื่อง
- **Smallest remaining capacity** และ **largest remaining capacity** สองแบบในรูปที่ 3
- **Random** สุ่ม
- **Bin-packing** มองการวาง VM เป็นปัญหาบรรจุของลงกล่องให้ใช้เครื่องน้อยที่สุด smallest remaining capacity คือวิธีหนึ่งของแนวคิดนี้ ซึ่งตำรา bin packing เรียกว่า best fit อีกแบบคือ bin-packing same-type instances ที่ให้แต่ละเครื่องรับ VM ขนาดเดียว

แต่การอัดก็ไม่ได้ดีกว่าเสมอ คำถามที่ต้องชั่งมีหลายข้อ

- **อัดให้เต็มทีละเครื่องดีไหม** เครื่องที่ว่างทั้งเครื่องปิดประหยัดไฟได้ แต่ถ้าเครื่องที่อัดไว้เสีย VM ทั้งหมดในเครื่องนั้นตายพร้อมกัน
- **ให้เครื่องหนึ่งรับ VM ขนาดเดียวดีไหม** ขนาดเท่ากันจึงไม่เหลือเศษ แต่ถ้าคำขอ large มามากกว่าที่คาด เครื่องที่จองไว้ให้ small ก็ว่างทิ้ง
- **ทรัพยากรอื่น** นอกจาก CPU กับหน่วยความจำ ต้องดูพื้นที่ดิสก์ การใช้พลังงาน <Term en="workload locality" th="วาง VM ที่คุยกันบ่อยไว้ใกล้กัน" /> และ high availability คือไม่วาง VM สำรองของงานเดียวกันไว้บนเครื่องเดียว

### ขายเกินจำนวน core จริง

ลองดู small VM สี่ตัวที่วัดการใช้ CPU ไว้ 30 ช่วงเวลา VM1 กับ VM2 ขึ้นลงแรง ตั้งแต่เกือบ 0 จนถึงราว 85–89% VM3 ส่วนใหญ่ต่ำกว่า 30% และ VM4 ส่วนใหญ่ต่ำกว่า 15% พอรวมสี่ตัวเข้าด้วยกัน ผลรวมอยู่ราว 84–99% เกือบทุกช่วง ต่ำสุดลงไปถึง 44% และ **ไม่เคยเกิน 100%** ช่วงที่ตัวหนึ่งพุ่ง ตัวอื่นมักอยู่ต่ำ

แปลว่า VM ทั้งสี่ตัวใช้ **core เดียวร่วมกันได้ ไม่ต้องใช้สี่ core** การแชร์โดยอาศัยว่าทุกตัวไม่พุ่งพร้อมกันเรียกว่า <Term en="statistical multiplexing" th="แชร์ทรัพยากรโดยอาศัยว่าทุกคนไม่ใช้เต็มพร้อมกัน" />

ผู้ให้บริการใช้หลักนี้ขาย VM เกินกว่าทรัพยากรจริง เรียกว่า <Term en="overcommit" th="ขายเกินกว่าทรัพยากรจริงที่มี" />

ลองทายก่อน: ถ้า small VM แต่ละตัวใช้ CPU และหน่วยความจำเฉลี่ยเพียง 25% เครื่องสองเครื่องในตัวอย่างรับ small VM ได้กี่ตัว

<Example added title="จำนวน VM เมื่อ overcommit">
คำถามนี้ไม่มีคำตอบในสไลด์ small VM หนึ่งตัวใช้เฉลี่ย 25% ของ 1 core = 0.25 core และ 25% ของ 2 GB = 0.5 GB

| | ไม่ overcommit | overcommit ตามค่าเฉลี่ย |
| --- | --: | --: |
| core ที่จองต่อ VM | 1 | 0.25 |
| จำนวน small VM บน 8 core | 8 | **32** |
| หน่วยความจำที่ใช้รวม | 16 GB | 32 × 0.5 = 16 GB |

ฮาร์ดแวร์ชุดเดิม ขายได้มากขึ้นสี่เท่า ตัวเลขนี้ใช้ได้ตราบที่ VM ส่วนใหญ่ไม่พุ่งพร้อมกัน
</Example>

### แชร์ให้มาก กับ แยกให้พอ

ผู้ให้บริการจึงต้องชั่งสองด้าน

| ด้าน | ได้อะไร | ทำยังไง |
| --- | --- | --- |
| **Multi-tenancy** | ต้นทุนต่ำ | statistical multiplexing และขยายสุดทางด้วย overcommit |
| **Isolation** | ลูกค้าแต่ละรายไม่กระทบกัน | **performance isolation** ทั้งด้าน virtualization เครือข่าย และ storage กับ **security isolation** คือไม่มีข้อมูลรั่วผ่าน side channel และไม่มี VM escape |

<Term en="side channel" th="ช่องที่ข้อมูลรั่วโดยอ้อม" /> คือการที่ VM หนึ่งอนุมานข้อมูลของ VM เพื่อนบ้านจากผลข้างเคียงของการแชร์ฮาร์ดแวร์ เช่นเวลาที่ใช้เข้าถึงหน่วยความจำ

<Term en="VM escape" th="หลุดจาก VM ไปคุม hypervisor" /> คือการที่โปรแกรมใน VM หลุดออกไปคุม hypervisor หรือ VM อื่นบนเครื่องเดียวกันได้

ยิ่ง overcommit มาก ต้นทุนยิ่งต่ำ แต่โอกาสที่ VM บนเครื่องเดียวกันพุ่งพร้อมกันแล้วแย่ง CPU กันก็ยิ่งสูง ส่วนที่ 5 ดูว่าการแย่งนั้นวัดออกมาเป็นตัวเลขได้ยังไง

<Quiz question="ระบบเดิมสองเครื่อง (เครื่องละ 4 core, 8 GB) วาง small VM ไว้ 3 ตัวบนเครื่อง 1 และ 3 ตัวบนเครื่อง 2 โดยไม่ overcommit แล้วมีคำขอ large VM เข้ามา cloud manager ทำอะไรได้บ้าง">
แต่ละเครื่องเหลือ 1 core กับ 2 GB รวมกัน 2 core กับ 4 GB พอดีกับ large VM หนึ่งตัว แต่ไม่มีเครื่องไหนว่างพอ นี่คือ fragmentation แบบเดียวกับรูปที่ 3

คำตอบคือ **วางไม่ได้ทันที** ต้องเลือกระหว่างปฏิเสธคำขอ ย้าย small VM สักตัวจากเครื่องหนึ่งไปอีกเครื่องเพื่อรวมที่ว่าง หรือ overcommit เครื่องใดเครื่องหนึ่ง ซึ่งเพิ่มโอกาสแย่ง CPU กับ VM เดิม ถ้าตอนแรกใช้ smallest remaining capacity ก็จะไม่ติดปัญหานี้

คำตอบที่พบบ่อยคือ "วางได้ เพราะที่ว่างรวมพอ" ซึ่งนับที่ว่างทั้งระบบรวมกัน แต่ VM หนึ่งตัวต้องอยู่บนเครื่องจริงเครื่องเดียว
</Quiz>

## ส่วนที่ 5 — ราคาของการแชร์: performance ที่วัดได้บน EC2

<Why>
ping จากเครื่องในส่วนที่ 1 ไป Google ใช้ 1.5–2.2 ms ทุกครั้ง ดูเหมือน VM ราคาเท่ากันควรเร็วเท่ากันทุกครั้ง แต่ VM ที่ต้องแบ่ง CPU กับเพื่อนบ้านทำงานไม่ต่อเนื่อง งานวิจัยของ Wang และคณะ (Infocom 2010) วัดผลนี้บน data center ของ Amazon EC2 ทั้ง CPU throughput ของเครือข่าย และ delay
</Why>

### CPU: เร็วตอนได้รัน แต่ถูกหยุดเป็นพัก ๆ

โปรแกรม CPUTest วนลูปหนึ่งล้านรอบ เรียก `gettimeofday()` ที่ต้นและท้ายลูป เก็บ timestamp ไว้ในหน่วยความจำ แล้วค่อยเขียนลงดิสก์ตอนจบ จะได้เห็นว่าลูปแต่ละช่วงใช้เวลาเท่าไหร่

ลองทายก่อน: VM ตัวเล็กที่ต้องแบ่ง core กับคนอื่น จะวนครบล้านรอบช้ากว่าหรือเร็วกว่าเครื่องจริงรุ่นเก่าที่ไม่มี virtualization

| เครื่อง | ลูปครบล้านรอบ | หน้าตาเส้นเวลา |
| --- | --: | --- |
| เครื่องจริงไม่มี virtualization (AMD Opteron 252, 2.6 GHz) | ราว 0.92 วินาที | เส้นตรง |
| EC2 small ที่แบ่ง core ของ AMD Opteron 2218E 2.6 GHz | ราว 0.65 วินาที | **ขั้นบันได** วิ่งแล้วหยุด สลับกัน |
| EC2 High-CPU medium (Intel Xeon 2.4 GHz) | ราว 0.47 วินาที | เส้นตรง |

ช่วงที่ small instance ได้ CPU มันวิ่งเร็วกว่าเครื่องจริงรุ่นเก่า จึงจบก่อนทั้งที่ถูกหยุดเป็นช่วง เส้นของมันขาดเป็นช่วง เพราะ hypervisor สลับไปให้ VM อื่น **small instance ได้ CPU จริงเพียงราว 40–50%** ของเวลา virtualization จึงไม่ได้ทำให้ CPU ช้าลงตอนทำงาน แต่ทำให้ **ถูกหยุดเป็นพัก ๆ**

### เครือข่าย: ส่งเป็นจังหวะเพราะ CPU มาเป็นจังหวะ

การวัด throughput ใช้สาม availability zone ในแต่ละ zone จับคู่ small instance 250 คู่ และ medium instance 50 คู่ ส่งข้อมูลหากันคู่ละไม่เกิน 800 MB ทั้งแบบ TCP และ UDP

- **Medium instance** TCP กับ UDP ได้ throughput ใกล้กัน ส่วนใหญ่อยู่ช่วงราว 500–900 Mbps
- **Small instance** สองแบบต่างกันชัด TCP ส่วนใหญ่ได้ราว 300–600 Mbps ส่วน UDP ราว 650–850 Mbps

ผู้วิจัยตัดสาเหตุเรื่องเครือข่ายแออัดออก เพราะไม่พบการส่งซ้ำ (retransmission) เลย

พอดู throughput ของ small instance ละเอียดระดับเศษเสี้ยววินาที จะเห็นว่ามันเป็นจังหวะ **ส่งเต็มที่แล้วตกเป็นศูนย์** สลับกัน TCP พุ่งถึงราว 1,000 Mbps ทุกช่วงที่ส่งได้ ส่วน UDP พุ่งถึงราว 1,500–2,000 Mbps และบางช่วงค้างอยู่ราว 900–1,000 Mbps โดยไม่ตกเป็นศูนย์

### Delay: RTT พุ่งเป็นพัก ๆ

การวัด delay ส่ง ping 10 ครั้งต่อวินาที เก็บ round-trip time (RTT) 5,000 ค่า

| คู่ที่วัด | RTT |
| --- | --- |
| เครื่องจริงไม่มี virtualization สองเครื่อง ห่าง 4 hop ในเครือข่ายมหาวิทยาลัย | ต่ำกว่า 1 ms เกือบคงที่ตลอด |
| EC2 medium สองตัว ห่าง 4 hop | ส่วนใหญ่ต่ำ มีพุ่งถึงราว 20 ms นาน ๆ ครั้ง |
| EC2 small สองตัว ห่าง 3 hop | **พุ่งถึง 20 ms บ่อยมาก** ทั้งที่ห่างกันน้อยกว่า |

small instance ห่างกันน้อยกว่า แต่ RTT แย่กว่า เพราะ ping ที่มาถึงตอนที่ VM ไม่ได้ CPU ต้องรอจนถึงตาของมันก่อนจึงตอบได้ ซึ่งเป็นสาเหตุเดียวกับเรื่อง CPU ราว 40–50% ข้างบน

### AWS แก้ปัญหาเครือข่ายยังไง

การรอ CPU ไม่ได้มีแค่ตาของ VM เรา ใน hypervisor แบบ Xen ข้อมูลเครือข่ายของ VM ของลูกค้า (guest domain) ต้องผ่าน **driver domain** ซึ่งเป็น VM พิเศษที่ถือ driver ของการ์ดเครือข่ายจริง ทุก packet จึงต้องรอทั้ง VM ของเราและ driver domain ได้ CPU

**Enhanced networking** ตัดทางอ้อมนี้ด้วยการ์ดเครือข่ายที่รองรับ <Term en="SR-IOV" th="การ์ดเครือข่ายจริงแบ่งตัวเองให้หลาย VM ใช้ตรง ๆ" /> เส้นทางใหม่มีสามจุด (1) แอปส่งข้อมูลผ่าน socket (2) NIC driver ใน VM ของเราเอง (3) ตรงไปที่การ์ด SR-IOV โดยไม่ผ่าน driver domain

รุ่นต่อมาคือ **Elastic Network Adapter (ENA)** ได้ถึง 20 Gbps ภายใน placement group ซึ่งในที่นี้คือการขอให้ AWS วาง instance กลุ่มหนึ่งไว้ใกล้กันใน availability zone เดียว

<Detail label="ตัวเลขเครือข่ายของ EC2 ที่ควรรู้">

- ENA ทำ checksum ในฮาร์ดแวร์ มีหลายคิว (multi-queue) กระจายงานรับข้อมูล (receive side steering) และใช้ driver แบบ open source ของ Amazon
- ความเร็ว 20 และ 10 Gigabit วัดทางเดียว ถ้าส่งสองทางพร้อมกัน (full duplex) ได้สองเท่า
- ระดับ High, Moderate, Low ขึ้นกับขนาด instance และการเปิด EBS optimization
- instance ขนาดเดียวกันไม่ได้เร็วเท่ากันเสมอ ถ้าสำคัญให้วัดเองด้วย `iperf`
- ใช้ **placement group** เมื่อต้องการ bandwidth ระหว่าง instance ที่สูงและสม่ำเสมอ
- traffic ที่ออกนอก EC2 ถูกจำกัดที่ 5 Gb/s

</Detail>

<Quiz question="คุณรันเกมเซิร์ฟเวอร์บน EC2 small instance ผู้เล่นบ่นว่าเกมกระตุกเป็นพัก ๆ ทั้งที่ CPU เฉลี่ยของ VM อยู่แค่ 30% และเครือข่ายไม่มี packet loss เพื่อนเสนอให้ย้ายไป region ที่ใกล้ผู้เล่นกว่า จะช่วยไหม">
อาการกระตุกเป็นพัก ๆ โดยไม่มี packet loss ตรงกับผลการวัดของ small instance คือ RTT พุ่งเพราะ VM ได้ CPU จริงเพียงราว 40–50% packet ที่มาตอนไม่ใช่ตาของ VM ต้องรอ CPU 30% ที่เห็นคือค่าเฉลี่ย ไม่ได้บอกว่าตอนมี packet มา VM ได้ CPU หรือไม่

คำตอบคือ **ย้าย region ไม่ช่วยตรงจุด** เพราะต้นเหตุอยู่ที่การแบ่ง CPU บนเครื่องจริง ไม่ใช่ระยะทาง ทางที่ตรงกว่าคือใช้ instance ขนาดใหญ่ขึ้นที่ไม่ต้องแบ่ง core กับใคร ซึ่งผลการวัดของ medium instance แสดงว่า RTT นิ่งกว่ามาก และใช้ enhanced networking

คำตอบที่พบบ่อยคือ "ช่วย เพราะ ping ไกลทำให้ช้า" ซึ่งอธิบาย delay ที่สูงคงที่ได้ แต่อธิบาย delay ที่พุ่งเป็นพัก ๆ ไม่ได้
</Quiz>

### T2: ขาย CPU เป็นเครดิต

<Term en="Burstable performance instance" th="instance ที่ใช้ CPU เกินฐานได้เป็นพัก ๆ" /> คือแนวคิดของตระกูล T2 ซึ่งเป็น EC2 ที่ถูกที่สุด เริ่มที่ $0.0065 ต่อชั่วโมงสำหรับ t2.nano ที่ US East (N. Virginia) มันรับประกัน **baseline** คือส่วนแบ่ง CPU ระดับหนึ่ง และยอมให้ **burst** ใช้เกิน baseline ได้ โดยคุมด้วย **CPU credit**

| Model | vCPU | Baseline | CPU credit ต่อชั่วโมง | หน่วยความจำ (GiB) |
| --- | :-: | --: | --: | --: |
| t2.nano | 1 | 5% | 3 | 0.5 |
| t2.micro | 1 | 10% | 6 | 1 |
| t2.small | 1 | 20% | 12 | 2 |
| t2.medium | 2 | 40% | 24 | 4 |
| t2.large | 2 | 60% | 36 | 8 |

ทุกรุ่นใช้ดิสก์แบบ EBS อย่างเดียว

กติกาของเครดิตมีสี่ข้อ

1. **1 CPU credit = ใช้ CPU เต็มหนึ่ง core นานหนึ่งนาที**
2. instance **ได้เครดิตในอัตราคงที่** ทุกชั่วโมง
3. instance **ใช้เครดิตเมื่อทำงาน**
4. เครดิต **หมดอายุหลัง 24 ชั่วโมง**

<Callout type="info" title="เสริม — กติกาข้อ 4 ของ AWS ปัจจุบัน">
ข้อ 4 เป็นกติกาในปีที่ทำสไลด์ เอกสารของ AWS ตอนนี้อธิบายว่าเครดิตบน instance ที่รันอยู่ไม่หมดอายุ แต่สะสมได้ไม่เกินจำนวนที่ได้ใน 24 ชั่วโมง ส่วนเกินถูกทิ้ง และ T2 เสียเครดิตทั้งหมดเมื่อหยุดเครื่อง ผลทางตัวเลขเหมือนกัน คือยอดสะสมไม่เกิน 24 ชั่วโมงของอัตราที่ได้
</Callout>

ภาพที่ควรนึกคือถังที่มีเครดิตไหลเข้าด้วยอัตรา baseline และไหลออกตามที่ใช้จริง หน้า monitoring ของ instance แสดงตัวเลขสองตัวนี้ทุกนาที เมื่อ CPU credit usage พุ่ง ยอดคงเหลือ (CPU credit balance) ก็ลดลง แล้วค่อย ๆ เพิ่มกลับเมื่องานเบา

สองตัวเลขในตารางเป็นเรื่องเดียวกัน baseline 10% ของ t2.micro คือได้ CPU เต็ม core 10% ของ 60 นาที = **6 credit ต่อชั่วโมง** ส่วน t2.medium ได้ 24 credit ต่อชั่วโมง เท่ากับ 40% ของหนึ่ง core รวมทั้งสอง vCPU หรือ vCPU ละ 20%

ลองทายก่อน: t2.micro ที่เก็บเครดิตไว้เต็มถัง ใช้ CPU เต็ม core ต่อเนื่องได้นานกี่นาที

<Example added title="t2.micro burst ได้นานแค่ไหน">

t2.micro ที่ว่างมาทั้งวันสะสมเครดิตที่ได้มาได้สูงสุด 6 × 24 = **144 credit** เพราะเพดานเท่ากับเครดิตที่ได้ใน 24 ชั่วโมง

ถ้าเริ่มใช้ CPU เต็ม core มันใช้ 1 credit ต่อนาที แต่ยังได้เครดิตเข้า 6 ต่อ 60 นาที = 0.1 ต่อนาที ยอดจึงลดสุทธิ 0.9 ต่อนาที

| | ค่า |
| --- | --: |
| เครดิตเต็มถัง | 144 |
| ลดสุทธิต่อนาทีตอนใช้เต็ม core | 0.9 |
| burst เต็ม core ได้นาน | 144 ÷ 0.9 = **160 นาที** |

หลังจากนั้นถูกลดกลับเหลือ baseline 10%

</Example>

กลไกนี้ทำให้ T2 เหมาะกับงานที่ไม่ได้ใช้ CPU เต็มบ่อยหรือต่อเนื่อง แต่ต้องพุ่งเป็นครั้งคราว เช่น web server สภาพแวดล้อมของนักพัฒนา และฐานข้อมูลขนาดเล็ก ซึ่งก็คือ VM แบบ VM3 กับ VM4 ในส่วนที่ 4

<Quiz question="t2.micro ที่เครดิตเต็มถัง 144 รันงานที่ใช้ CPU คงที่ 30% ตลอดเวลา ไม่เคยพุ่งเต็ม core เลย งานนี้จะได้ 30% ไปตลอดไหม">
t2.micro ได้เครดิตเข้า 6 ต่อชั่วโมง แต่ใช้ 30% ของหนึ่ง core × 60 นาที = 18 credit ต่อชั่วโมง ยอดจึงลดสุทธิ 12 ต่อชั่วโมง เครดิต 144 หมดใน 144 ÷ 12 = 12 ชั่วโมง

คำตอบคือ **ไม่ได้ หลัง 12 ชั่วโมงมันถูกลดกลับเหลือ baseline 10%** งานที่ใช้เกิน baseline ตลอดเวลาไม่เหมาะกับ T2 แม้จะไม่เคยใช้เต็ม core

คำตอบที่พบบ่อยคือ "ได้ตลอด เพราะ 30% ยังไม่ถึงเต็ม core" ซึ่งเทียบกับ 100% แต่เครดิตเทียบกับ baseline 10% ทุกนาทีที่ใช้เกิน baseline ก็กินเครดิตแล้ว
</Quiz>

<KeyIdea>
CPU credit เปลี่ยน statistical multiplexing ให้เป็นสัญญา ผู้ให้บริการขาย baseline ที่รู้แน่ว่าต้องจ่ายจริง แล้วให้ burst เท่าที่เครดิตมี จึง overcommit เครื่องได้มาก โดยมีเพดานกันไม่ให้ VM ตัวเดียวกิน CPU ตลอดเวลา
</KeyIdea>

## ส่วนที่ 7 — Image library: OS ที่ขอมาอยู่ที่ไหน

### Image กับ instance ต่างกันยังไง

<Why>
ลูกค้าพันคนขอ Amazon Linux 2023 รุ่นเดียวกัน ถ้าต้องติดตั้ง OS ใหม่ทุกครั้ง ผู้ใช้ต้องรอเป็นชั่วโมง ทางที่เร็วกว่าคือเก็บ OS ที่ติดตั้งเสร็จแล้วไว้เป็นแม่แบบ แล้วคัดลอกไปบูต
</Why>

<Term en="Image" th="แม่แบบ software stack ของ VM" /> คือ software stack สำเร็จรูปของ VM เมื่อสร้าง VM ระบบบูตจาก stack นี้ ส่วน instance คือสำเนาของ image ที่ถูกตั้งค่าให้ผู้ใช้คนหนึ่งแล้ว

บน AWS คำว่า instance ใช้เรียกทั้งเครื่องที่ตั้งค่าแล้วและเครื่องที่กำลังรัน ในโมเดลนี้ instance กลายเป็น VM เมื่อรันบน hypervisor และ AMI ในส่วนที่ 1 ก็คือ image ของ AWS

<Figure number={5} caption="Image กลายเป็น instance, instance รันเป็น VM และทางกลับคือเก็บสถานะไว้">
  <ImageLifecycle />
</Figure>

- **instantiate** สร้าง instance จาก image
- **start / resume** รัน instance เป็น VM บน hypervisor
- **stop / snapshot** หยุด VM แล้วเก็บสถานะของ instance ไว้
- **capture** เก็บ instance ที่ตั้งค่าแล้วกลับเป็น image ใหม่ ให้คนอื่นใช้ต่อ

Image ของ VMware ประกอบด้วยไฟล์ห้าชนิด

| นามสกุล | เก็บอะไร |
| --- | --- |
| `.vmdk` | เนื้อหาของฮาร์ดดิสก์ของ VM |
| `.nvram` | สถานะ BIOS ของ VM |
| `.vmx` | ค่าตั้งของ VM |
| `.vmxf` | ค่าตั้งเพิ่มเติม |
| `.vswp` | ไฟล์ swap |

ขนาดต่างกันมาก ตัวอย่าง VM แบบ VMware ของ Red Hat Enterprise Linux 4 มี `.vmdk` 1.52 GB, `.nvram` 12 KB และ `.vmx` 4 KB ดิสก์คือเกือบทั้งหมดของ image

### Image library อยู่ที่ไหน และขั้นที่ 4 ทำอะไร

**Image library** คือคลังเก็บ image มักอยู่บน shared storage ที่ hypervisor ทุกตัว mount ไว้ จึงเข้าถึงได้จากทุกเครื่อง ตัวอย่างคือ Amazon S3 ซึ่งเป็นบริการเก็บไฟล์ของ AWS ที่เก็บ AMI จำนวนมาก ซึ่งเป็นรายการที่ผู้ใช้เลือกในขั้นแรกของการขอเครื่อง

ขั้นที่ 4 ในรูปที่ 1 ที่ hypervisor "สร้าง VM" แตกออกเป็นสามงาน

<StepThrough>
<Step title="คัดลอก image">

คัดลอก image ที่ผู้ใช้เลือก เช่น Amazon Linux 2023 ในส่วนที่ 1 จาก image library มาที่เครื่องจริงที่ cloud manager เลือกไว้

</Step>
<Step title="ตั้งค่า instance">

ใส่ ssh key ของผู้ใช้ลงใน instance นี่คือ public key จาก key pair ในส่วนที่ 1 แล้วกำหนด IP address

</Step>
<Step title="บูตเป็น VM">

hypervisor กำหนด virtual hardware ตาม instance type เช่น small VM ในส่วนที่ 4 ได้ 1 core กับ 2 GB หรือ `t2.micro` ได้ 1 vCPU กับ 1 GiB แล้วบูต instance เป็น VM จนอยู่ในสถานะ running

</Step>
</StepThrough>

### ทำให้ขั้นที่ 4 เร็วขึ้น

ขั้นที่ช้าที่สุดคือการคัดลอก ซึ่งขึ้นกับว่า image ใหญ่แค่ไหน แต่ดิสก์ส่วนใหญ่ของ image ว่างเปล่า บน instance ตัวอย่าง คำสั่ง `df` ให้ผลนี้

```text
[ec2-user@ip-172-31-18-104 ~]$ df
Filesystem     1K-blocks    Used Available Use% Mounted on
/dev/xvda1       8123812 1109660   6913904  14% /
```

ดิสก์ขนาดราว 7.7 GiB แต่ใช้จริงเพียงราว 1.06 GiB หรือ 14% ถ้าคัดลอกทั้งก้อน ราว 6.6 GiB ที่ส่งไปคือพื้นที่ว่าง

<Term en="Sparse file" th="ไฟล์ที่ไม่จองดิสก์ให้ช่วงที่ว่าง" /> แก้ตรงนี้ คือไฟล์ที่ระบบไฟล์จำไว้ว่าช่วงไหนว่าง แล้วไม่จองพื้นที่จริงให้ช่วงนั้น

ลองทายก่อน: ไฟล์ขนาด 8 GB ที่ยังไม่เคยเขียนอะไรลงไปเลย กินพื้นที่ดิสก์จริงเท่าไหร่

<Example added title="ไฟล์ 8 GB ที่ใช้พื้นที่ 0 ไบต์">

```bash
$ truncate -s 8G disk.img
$ ls -lh disk.img
-rw-rw-r-- 1 user user 8.0G Nov 15 22:50 disk.img
$ du -h disk.img
0	disk.img
```

`ls` รายงานขนาดที่ไฟล์บอกว่าตัวเองมี ส่วน `du` รายงานพื้นที่ที่จองบนดิสก์จริง

แต่ประหยัดได้เฉพาะเมื่อตัวคัดลอกรู้จัก sparse เช่น `cp --sparse=always`, `rsync -S` หรือชั้น storage ที่จัดการทีละ block ถ้าอ่านไฟล์ตรง ๆ ช่วงว่างก็ออกมาเป็นศูนย์ครบทุกไบต์: `cat disk.img | wc -c` ได้ 8589934592

</Example>

การเพิ่มประสิทธิภาพอีกทางคือ **storage deduplication** image ราว 90% มีเนื้อหาเหมือนกัน เพราะส่วนใหญ่คือ OS ตัวเดียวกัน ระบบจึงเก็บส่วนที่ซ้ำไว้ชุดเดียว แล้วให้ทุก image ชี้มาที่ชุดนั้น

<Quiz question="ผู้ใช้คนที่หนึ่งขอ Image1 แล้วได้ VM1 บนเครื่อง 1 ต่อมาผู้ใช้คนที่สองขอ Image1 เหมือนกัน เครื่อง 1 และเครื่อง 2 ยังว่างพอทั้งคู่ ถ้าอยากให้ผู้ใช้คนที่สองได้เครื่องเร็วที่สุด cloud manager ควรวาง VM2 ที่ไหน และต้องแลกกับอะไร">
งานที่ช้าที่สุดของขั้นที่ 4 คือคัดลอก image จาก library เครื่อง 1 เพิ่งคัดลอก Image1 ไปสร้าง VM1 จึงมีสำเนาอยู่แล้ว ถ้าวาง VM2 ที่เครื่อง 1 ก็ข้ามการคัดลอกไปได้ เหลือแค่ตั้งค่าและบูต

คำตอบคือ **วางที่เครื่อง 1** ซึ่งเป็นการคิดเรื่อง locality ของ image ในตอนเลือกเครื่อง แต่ต้องแลกกับข้อพิจารณาในส่วนที่ 4 ถ้า VM1 กับ VM2 เป็นงานเดียวกันที่ต้องสำรองกัน การอยู่เครื่องเดียวกันทำให้เสียพร้อมกัน และเครื่อง 1 ก็ใกล้เต็มเร็วขึ้น

คำตอบที่พบบ่อยคือ "เครื่อง 2 เพราะยังว่างกว่า" ซึ่งใช้แค่ largest remaining capacity โดยไม่นับเวลาคัดลอก image ซึ่งเป็นสิ่งที่ผู้ใช้รอจริง
</Quiz>

<Recap>

**ขอเครื่องบน EC2**

- เลือก name, AMI (software stack สำเร็จรูป คล้าย virtual appliance), instance type, key pair, network/security group, storage (EBS gp3) แล้ว Launch ได้เครื่องที่มี public IP และ private IP
- เลือกเฉพาะ Free Tier ไม่งั้นโดนเก็บเงินจริง; security group ปริยายยอม SSH จาก `0.0.0.0/0` ควรจำกัดเฉพาะ IP ที่รู้จัก
- กุญแจของ AWS: root email/password, IAM, MFA, access key, key pair; key pair ใช้ private key เซ็น ตรวจด้วย public key ที่อยู่ใน instance ทำไฟล์หาย = SSH ด้วย key pair นั้นไม่ได้อีก

**สถาปัตยกรรม**

- หกชิ้น: self-service portal, cloud resource manager, physical resource pool, image library, monitoring, billing/charging
- เจ็ดขั้น: ขอ → ประมวล → เลือกเครื่อง → hypervisor สร้าง VM จาก image → แจ้งกลับ → เริ่ม monitoring/billing → ส่งรายละเอียดให้ผู้ใช้

**Virtualization**

- แยกทรัพยากรออกจากฮาร์ดแวร์จริง มีมาตั้งแต่ IBM ยุค 1960; cloud = virtualization + อีกหลายอย่าง
- ข้อดี: partitioning/isolation, จัดการกองกลาง, consolidation (5–15% → 60–80%), test/dev, business continuity
- Type II hosted (โปรแกรมบน host OS) กับ Type I bare-metal (kernel บนฮาร์ดแวร์); Azure ใช้ Hyper-V, Google ใช้ KVM, AWS ใช้ Xen (รุ่นใหม่ใช้ Nitro ที่มาจาก KVM); CPU ช่วยด้วย Intel VT, AMD-V

**วาง VM และ overcommit**

- นโยบาย: round-robin, smallest/largest remaining capacity, random, bin-packing; largest remaining capacity กระจาย VM จนเกิด fragmentation
- ต้องชั่งดิสก์ พลังงาน workload locality และ high availability ด้วย
- VM ไม่พุ่งพร้อมกัน → statistical multiplexing → overcommit (ใช้เฉลี่ย 25% → 8 เป็น 32 ตัว)
- ชั่งระหว่าง multi-tenancy กับ isolation (performance และ security: side channel, VM escape)

**Performance บน EC2**

- small instance ได้ CPU ราว 40–50%: CPU เร็วตอนได้รันแต่ถูกหยุดเป็นพัก, throughput เป็นจังหวะ (TCP แย่กว่า UDP), RTT พุ่งถึง 20 ms
- enhanced networking (SR-IOV) ข้าม driver domain; ENA ถึง 20 Gbps ใน placement group

**คิดเงินและ image**

- ชื่อ `c4.xlarge` = family + generation + size; ราคาต่างตาม region
- T2 burstable: baseline + CPU credit (1 credit = 1 core 1 นาที; สไลด์: เครดิตหมดอายุหลัง 24 ชั่วโมง, AWS ปัจจุบัน: ไม่หมดอายุแต่สะสมได้ไม่เกินที่ได้ใน 24 ชั่วโมง)
- image → instance → VM; image library บน shared storage (S3 เก็บ AMI)
- เร่งขั้นคัดลอก: sparse file, deduplication (90% ของ image เหมือนกัน), วาง VM ที่เครื่องที่มี image อยู่แล้ว

<Quiz question="ผู้ให้บริการรายหนึ่งตั้งนโยบายห้าม overcommit เด็ดขาด ทุก VM ได้ core จริงของตัวเอง ลูกค้าและผู้ให้บริการได้อะไร เสียอะไร เทียบกับการขาย T2 แบบ CPU credit">
ไม่ overcommit คือเลือกฝั่ง isolation เต็มที่ ทุก VM ได้ core ของตัวเอง จึงไม่มีช่วงที่ถูกหยุดเพราะเพื่อนบ้าน RTT และ throughput นิ่งแบบ medium instance แต่ VM ส่วนใหญ่ใช้ CPU เฉลี่ยต่ำ core ที่จองไว้จึงว่างเกือบตลอด จากตัวอย่างในส่วนที่ 4 เครื่องชุดเดิมขายได้ 8 ตัวแทนที่จะเป็น 32 ราคาต่อ VM จึงต้องสูงขึ้น

คำตอบคือ **ลูกค้าได้ performance ที่คาดเดาได้ แต่จ่ายแพงขึ้น ผู้ให้บริการเสียกำไรจาก statistical multiplexing** ส่วน T2 อยู่ตรงกลาง คือขาย baseline ต่ำในราคาถูก แล้วให้ burst ได้จำกัดด้วยเครดิต

คำตอบที่พบบ่อยคือ "ไม่ overcommit ดีกว่าเสมอเพราะเร็วกว่า" ซึ่งดูแค่ performance แต่งานส่วนใหญ่ไม่ได้ใช้ CPU เต็ม การจ่ายเต็ม core ให้งานที่ใช้ 10% ก็คือการซื้อเครื่องเผื่อจุดสูงสุดแบบเดียวกับที่ cloud ตั้งใจแก้

<Quiz question="เรียงสิ่งที่เกิดขึ้นในเครื่องจริง ตั้งแต่ cloud manager เลือกเครื่องนั้น จนผู้ใช้ SSH เข้า VM ได้ และบอกว่าแต่ละขั้นใช้ข้อมูลอะไรจากตอนที่ผู้ใช้กด Launch">
เมื่อ cloud manager เลือกเครื่อง (ขั้นที่ 3) จากขนาดที่ผู้ใช้เลือกใน instance type hypervisor บนเครื่องนั้นคัดลอก image ตาม AMI ที่ผู้ใช้เลือกจาก image library ใส่ public key ของ key pair ที่ผู้ใช้เลือกลง instance และกำหนด IP แล้วกำหนด virtual hardware ตามขนาด instance type และบูตจน running (ขั้นที่ 4) จากนั้นแจ้ง cloud manager (ขั้นที่ 5) ซึ่งเริ่ม monitoring และ billing (ขั้นที่ 6) แล้วส่ง IP และรายละเอียดให้ผู้ใช้ (ขั้นที่ 7) ผู้ใช้จึง SSH ด้วย private key ผ่าน security group ที่ยอม port 22

คำตอบคือ **คัดลอก image → ใส่ key และ IP → กำหนด virtual hardware และบูต → แจ้งกลับ → เริ่มคิดเงิน → ส่งรายละเอียด**

คำตอบที่พบบ่อยคือให้ติดตั้ง OS ลงเครื่องหลังบูต ซึ่งช้าเกินไป ระบบคัดลอก image ที่ติดตั้ง OS ไว้แล้ว อีกข้อที่มักลืมคือ billing เริ่มตั้งแต่ instance รัน ไม่ใช่ตอนผู้ใช้ login ครั้งแรก
