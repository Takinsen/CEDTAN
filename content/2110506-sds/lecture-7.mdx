## ส่วนที่ 1 — Cloud คืออะไร มองจากสองฝั่ง

### สามฝ่ายในเรื่องเดียว

เรื่องของ cloud มีคนเกี่ยวข้องสามฝ่าย และคำว่า "ผู้ใช้" หมายถึงคนละคนกันแล้วแต่ว่ามองจากตรงไหน

| ฝ่าย | ในตัวอย่างแอปใหม่ของคุณ |
| --- | --- |
| **ผู้ใช้แอป** (application users) | คนที่เปิดแอปของคุณบนเว็บหรือมือถือ |
| **ผู้ใช้ cloud** (cloud user) | ตัวคุณ ผู้เอาแอปไปรันบน cloud |
| **ผู้ให้บริการ cloud** (cloud provider) | บริษัทที่มีเครื่องและพื้นที่เก็บข้อมูลให้เช่า เช่น AWS |

ผู้ใช้แอปไม่เคยคุยกับผู้ให้บริการตรง ๆ พวกเขาคุยกับแอปของคุณ แล้วแอปของคุณใช้เครื่องของผู้ให้บริการอีกที

แอปบนอุปกรณ์สวมใส่ก็ทำงานแบบเดียวกัน อุปกรณ์เก็บข้อมูลจากสภาพแวดล้อมรอบตัวและจากคนที่ใส่ แล้วส่งไปเก็บที่บริการบน cloud เมื่อต้องการแสดงผล มันดึงข้อมูลที่ประมวลผลแล้วกลับมา ตัวอุปกรณ์จึงเล็กและเบาได้ เพราะงานหนักไปอยู่หลังบ้านบน cloud ซึ่งเรียกว่าใช้ cloud เป็น <Term en="back-end enabler" th="ระบบหลังบ้านที่ทำให้อุปกรณ์ทำงานได้" />

### ฝั่งผู้ใช้ cloud เห็นอะไร

จากมุมของคุณ cloud คือบริการสองแบบ

- **ซื้อทรัพยากรคอมพิวเตอร์แทนการลงทุนซื้อฮาร์ดแวร์** — เซิร์ฟเวอร์ พื้นที่เก็บข้อมูล แอปพลิเคชัน และเครือข่าย ตัวอย่างคือ Amazon AWS, Microsoft Azure, RackSpace
- **ใช้ซอฟต์แวร์ผ่านเครือข่ายตามที่ต้องการ** โดยไม่ต้องซื้อ license เต็มและไม่ต้องติดตั้งบนเครื่องตัวเอง ตัวอย่างคือ SalesForce และ Adobe Creative Cloud

ทั้งสองแบบมีหลักเดียวกัน คือใช้เมื่อต้องการ และจ่ายเท่าที่ใช้ ทรัพยากรถูกจัดให้และคืนได้เร็วตามต้องการ (on-demand rapidly provisioned and released) โดยแทบไม่ต้องติดต่อผู้ให้บริการ และแทบไม่มีงานดูแลเพิ่ม

### ฝั่งผู้ให้บริการทำอะไร

จากมุมของผู้ให้บริการ cloud คือฮาร์ดแวร์ ซอฟต์แวร์ และเครือข่ายใน data center ที่เปิดเป็นบริการให้คนจำนวนมากใช้ร่วมกัน มันทำงานบนสี่หลัก

1. **ใช้ virtualization** เครื่องจริงหนึ่งเครื่องจึงถูกแบ่งให้ลูกค้าหลายรายพร้อมกัน แบบนี้เรียกว่า <Term en="multi-tenant" th="ลูกค้าหลายรายใช้ฮาร์ดแวร์ชุดเดียวกัน" />
2. **แชร์ให้คุ้มที่สุด** แต่ยังต้องรักษาคุณภาพบริการให้ได้ระดับที่ตกลงกับลูกค้าไว้
3. **วัดว่าลูกค้าแต่ละรายใช้ไปเท่าไหร่** แล้วคิดเงินตามนั้น
4. ทั้งหมดอยู่ใน data center ขนาดใหญ่

[Lecture 7.2](/2110506-sds/lecture-7-2) เปิดดูว่าการแบ่งเครื่องและการวัดการใช้งานทำงานยังไงข้างใน ฝั่งผู้ให้บริการ **ได้กำไรจากการแชร์** ส่วนฝั่งคุณได้ประโยชน์จากการไม่ต้องซื้อ

<Detail label="data center ของผู้ให้บริการหน้าตาเป็นยังไง">

ผู้ให้บริการรายใหญ่สร้าง data center แบบ **modular และ pre-fab** คือประกอบห้องเครื่องเป็นกล่องสำเร็จรูปจากโรงงาน แล้วยกไปวางที่หน้างาน ตัวอย่างคือ Microsoft ITPAC และ Amazon Perdix

- ติดตั้งได้เร็วและถูก เพราะประกอบในโรงงาน
- ระบายความร้อนด้วยอากาศภายนอก (air-side economized)
- Dell, HP, SGI, IBM ก็ขายแบบนี้ในรูปตู้คอนเทนเนอร์ขนส่งขนาดมาตรฐาน ISO

ความร้อนคือต้นทุนก้อนใหญ่ data center ของ Facebook ใช้ **ละอองน้ำ** พ่นจากแนวท่อเพื่อลดอุณหภูมิอากาศ ใช้ **แผ่นกรอง** คุมความชื้นและอุณหภูมิ และใช้ **พัดลม** คุมทิศทางการไหลของอากาศ

</Detail>

### นิยามที่ใช้กันเป็นมาตรฐาน: NIST

ช่วงแรกคนเถียงกันมากว่า cloud คืออะไร บางคนนิยามจากคุณสมบัติ เช่น platform ที่ใช้ รูปแบบการส่งมอบ บริการที่มี หรือ feature ที่รองรับ นิยามที่พบบ่อยมีสองแนว

- **อัตโนมัติสุดทางด้วย virtualization** — ซ่อนรายละเอียดของเครื่องจริง ซ่อนงานตั้งค่าที่น่าเบื่อและพลาดง่ายจากผู้ใช้ และทำให้ทรัพยากรคอมพิวเตอร์เป็นเหมือนน้ำประปาไฟฟ้า (utility)
- **จ่ายตามที่ใช้ (pay as you go)** — ทั้งทรัพยากรและบริการได้มาเมื่อต้องการ

นิยามที่ยุติข้อถกเถียงคือของ <Term en="NIST" th="สถาบันมาตรฐานและเทคโนโลยีแห่งชาติของสหรัฐฯ" /> ปี 2011 ซึ่งบรรยาย cloud ด้วยสามด้าน

| ด้าน | ตอบคำถาม | มีอะไรบ้าง |
| --- | --- | --- |
| **Essential characteristics** | อะไรทำให้บริการหนึ่งนับเป็น cloud | 5 ข้อ — ส่วนที่ 2 |
| **Service models** | เช่าถึงชั้นไหน | SaaS, PaaS, IaaS — ส่วนที่ 3 |
| **Deployment models** | ใครใช้ร่วมกันได้บ้าง | private, community, public, hybrid — ส่วนที่ 4 |

<KeyIdea>
ผู้ใช้ cloud เห็นบริการที่จ่ายตามใช้และได้ทันที ผู้ให้บริการเห็นเครื่องชุดเดียวที่แบ่งให้หลายคนพร้อมกันแล้วคิดเงินตามที่วัดได้ นิยามของ NIST รวมสองมุมนี้ไว้ในสามด้าน
</KeyIdea>

## ส่วนที่ 2 — ห้าคุณสมบัติที่ทำให้บริการหนึ่งเป็น cloud

<Why>
บริษัทรับฝากเซิร์ฟเวอร์ที่ให้คุณโทรไปสั่งเครื่อง เซ็นสัญญาหนึ่งปี แล้วรอช่างติดตั้งสามวัน ก็ "ให้เช่าเครื่อง" เหมือนกัน แต่ไม่มีใครเรียกว่า cloud สิ่งที่แยกสองอย่างนี้ออกจากกันคือห้าข้อข้างล่าง
</Why>

**1. On-demand self-service** — ผู้ใช้ขอทรัพยากรเองได้ทันทีที่ต้องการ เช่นเวลาเครื่องหรือพื้นที่เก็บข้อมูล โดยระบบจัดให้อัตโนมัติ **ไม่ต้องมีคนของผู้ให้บริการมาเกี่ยว**

<Analogy>
On-demand self-service เหมือนร้านบุฟเฟต์ คุณเดินไปตักเองได้ทันที ส่วนบริการแบบเดิมเหมือนร้านอาหารที่ต้องเรียกพนักงานมารับออร์เดอร์แล้วรอ ถาดอาหารคือทรัพยากร การตักเองคือการกดขอผ่านหน้าเว็บหรือ API

อุปมานี้ใช้ไม่ได้ตรงที่บุฟเฟต์จ่ายเหมาต่อหัว ตักมากตักน้อยก็จ่ายเท่ากัน แต่ cloud วัดและคิดเงินตามที่ใช้จริงทุกชิ้น ซึ่งเป็นคุณสมบัติข้อ 5
</Analogy>

**2. Broad network access** — ใช้ได้ผ่านเครือข่ายด้วยวิธีมาตรฐาน จากอุปกรณ์หลากหลาย ทั้ง <Term en="thin client" th="เครื่องเบาที่พึ่งเซิร์ฟเวอร์ทำงานแทน" /> และ <Term en="thick client" th="เครื่องที่ทำงานส่วนใหญ่ได้เอง" /> เช่น มือถือ โน้ตบุ๊ก และ PDA

**3. Resource pooling** — ทรัพยากรของผู้ให้บริการถูกรวมเป็นกองกลางเพื่อบริการลูกค้าหลายราย แบบ multi-tenant แล้วถูกแจกและเรียกคืนตามความต้องการของลูกค้าตลอดเวลา ทรัพยากรนี้ได้แก่ storage, processing, หน่วยความจำ, network bandwidth และ virtual machine

ผลข้างเคียงของการรวมกองกลางคือ <Term en="location independence" th="ไม่ผูกกับตำแหน่งเครื่อง" /> ลูกค้าไม่รู้และคุมไม่ได้ว่าทรัพยากรอยู่ที่เครื่องไหน แต่อาจเลือกได้ในระดับกว้างกว่า เช่น ประเทศ รัฐ หรือ data center

**4. Rapid elasticity** — ขยายออกและหดกลับได้เร็ว บางครั้งอัตโนมัติ ในสายตาลูกค้า ทรัพยากรดูเหมือนไม่มีวันหมด และซื้อได้ทุกจำนวนทุกเวลา

**5. Measured service** — ระบบวัดการใช้งานในหน่วยที่เหมาะกับบริการนั้น เช่น พื้นที่เก็บข้อมูล เวลาประมวลผล bandwidth หรือจำนวนบัญชีผู้ใช้ที่ active แล้วใช้ตัวเลขนั้นคุมและปรับการใช้ทรัพยากรอัตโนมัติ ทั้งผู้ให้บริการและลูกค้าเห็นตัวเลขเดียวกัน

<Example title="แอปใหม่ของคุณ ในสี่ช่วงเวลา">
จำนวนผู้ใช้แอปของคุณพุ่งขึ้นแล้วค่อย ๆ ลดลง ระบบที่ยืดหดได้ใช้เซิร์ฟเวอร์ตามจำนวนผู้ใช้ในแต่ละช่วงดังนี้

| ช่วงเวลา | 1 | 2 | 3 | 4 |
| --- | :-: | :-: | :-: | :-: |
| เซิร์ฟเวอร์ที่ใช้ | 1 | 6 | 3 | 2 |

สมมติให้แต่ละช่วงยาวเท่ากัน รวมสี่ช่วงใช้ 1 + 6 + 3 + 2 = **12 เครื่อง-ช่วง** ถ้าคุณซื้อเครื่องเองให้พอกับช่วงที่คนเยอะที่สุด ต้องมี 6 เครื่องตลอด เท่ากับ 6 × 4 = **24 เครื่อง-ช่วง** ครึ่งหนึ่งจึงว่างเปล่า

Rapid elasticity ทำให้ได้ตัวเลข 12 และ measured service ทำให้จ่ายแค่ 12
</Example>

<Quiz question="Amazon EC2 ให้คุณเข้าหน้าเว็บ เลือกขนาดเครื่อง กด Launch แล้วได้เครื่องใน data center ของ AWS คิดเงินรายชั่วโมง ส่วนบริษัท ก ให้เช่าเซิร์ฟเวอร์โดยโทรนัดล่วงหน้า สัญญาขั้นต่ำหนึ่งปี ค่าเช่าเท่ากันทุกเดือน บริษัท ก ขาดคุณสมบัติข้อไหนบ้าง">
ไล่ทีละข้อ EC2 ผ่านครบทั้งห้า กดขอเองได้ (ข้อ 1) ใช้ผ่านอินเทอร์เน็ตได้จากทุกอุปกรณ์ (ข้อ 2) เครื่องที่ได้มาจากกองกลางของ AWS ที่แชร์กับลูกค้ารายอื่น (ข้อ 3) ขอเพิ่มหรือคืนได้ทุกเมื่อ (ข้อ 4) และคิดเงินตามชั่วโมงที่วัดได้ (ข้อ 5)

บริษัท ก ขาด **ข้อ 1** เพราะต้องโทรคุยกับคน **ข้อ 4** เพราะสัญญาหนึ่งปีหดกลับไม่ได้ และ **ข้อ 5** เพราะจ่ายเท่ากันไม่ว่าจะใช้มากหรือน้อย จึงไม่นับเป็น cloud

คำตอบที่พบบ่อยคือ "ทั้งสองเป็น cloud เพราะเครื่องไม่ได้อยู่ที่บริษัทเรา" ซึ่งใช้ที่ตั้งของเครื่องเป็นเกณฑ์ แต่ไม่มีคุณสมบัติข้อไหนในห้าข้อพูดถึงที่ตั้ง
</Quiz>

## ส่วนที่ 3 — SaaS, PaaS, IaaS: เช่าถึงชั้นไหน

<Why>

### SaaS — ใช้แอปของผู้ให้บริการ

<Term en="Software as a Service (SaaS)" th="เช่าใช้ซอฟต์แวร์สำเร็จรูป" /> ให้คุณใช้แอปของผู้ให้บริการที่รันบน cloud ผ่านโปรแกรมฝั่งผู้ใช้ที่บาง ๆ เช่น web browser ตัวอย่างใกล้ตัวคืออีเมลบนเว็บ คุณไม่ได้คุมเครือข่าย เซิร์ฟเวอร์ OS หรือ storage และไม่ได้คุมความสามารถของตัวแอปด้วย ยกเว้นค่าตั้งส่วนตัวบางอย่าง

ตัวอย่างคือ **Adobe Creative Cloud**

- ออก feature ใหม่บ่อยขึ้น รอบปล่อยสั้นลง
- ทุกคนใช้รุ่นเดียวกัน งานดูแลและซัพพอร์ตจึงน้อยลง
- คิดเงินแบบสมัครสมาชิก เช่นแผน Photography 300 บาทต่อเดือน แบบรายปีจ่ายรายเดือน

### PaaS — เอาแอปของคุณไปวางบน platform

<Term en="Platform as a Service (PaaS)" th="เช่า platform ไว้วางแอปที่เขียนเอง" /> ให้คุณนำแอปที่เขียนเองหรือซื้อมาไปวางบน cloud โดยต้องเขียนด้วยภาษาและเครื่องมือที่ผู้ให้บริการรองรับ คุณไม่ได้คุมเครือข่าย เซิร์ฟเวอร์ OS หรือ storage แต่คุมตัวแอป และอาจตั้งค่าสภาพแวดล้อมที่รันแอปได้บ้าง

ตัวอย่างคือ **Google App Engine**

- เน้นเว็บแอป รองรับ framework ยอดนิยม (Django, Spring) และภาษา Python, Java, PHP, Go
- **บังคับโครงสร้างของแอป** และแยกส่วนที่ไม่เก็บสถานะออกจากชั้นเก็บข้อมูลที่มีสถานะชัดเจน
- ข้อดีของการบังคับนี้คือ platform ขยายเครื่องอัตโนมัติ และสลับไปเครื่องสำรองเมื่อเครื่องเสียให้ได้
- จ่ายตามจำนวนธุรกรรมต่อวินาที

การบังคับโครงสร้างนี้คือหัวใจของ PaaS ส่วนของแอปที่ไม่เก็บสถานะไว้ในตัวเองเรียกว่า <Term en="stateless" th="ไม่เก็บสถานะไว้ในตัว" /> จะเปิดสำเนาเพิ่มกี่ตัวก็ได้ เพราะทุกตัวไปอ่านข้อมูลจากชั้นเก็บข้อมูลที่เดียวกัน (stateful)

ผลคือ platform เพิ่มลดสำเนาเองตามจำนวนผู้ใช้ได้โดยไม่ทำข้อมูลหาย เรียกว่า <Term en="auto-scaling" th="ขยายหรือลดเครื่องอัตโนมัติ" /> และเมื่อเครื่องหนึ่งเสีย ก็ย้ายงานไปเครื่องอื่นได้ทันที เรียกว่า <Term en="failover" th="สลับไปเครื่องสำรองเมื่อเครื่องเสีย" />

### IaaS — เช่าเครื่องเปล่า

<Term en="Infrastructure as a Service (IaaS)" th="เช่าเครื่องและเครือข่ายพื้นฐาน" /> ให้คุณขอหน่วยประมวลผล storage เครือข่าย และทรัพยากรพื้นฐานอื่น แล้วรันซอฟต์แวร์อะไรก็ได้บนนั้น รวมถึงเลือก OS เอง คุณไม่ได้คุมโครงสร้างข้างใต้ แต่คุม OS, storage, แอปที่ติดตั้ง และคุมเครือข่ายได้บางส่วน เช่น firewall ของเครื่อง

ตัวอย่างคือ **Amazon EC2**

- abstraction ระดับต่ำ ผู้ใช้ได้ virtual machine หนึ่งเครื่องไปจัดการเอง
- ผลคือผู้ให้บริการที่ขาย IaaS อย่างเดียว **ทำ auto-scaling และ failover ให้อัตโนมัติได้ยาก** เพราะไม่รู้ว่าข้างในเครื่องของคุณเก็บสถานะไว้ตรงไหน
- จ่ายตามรอบการประมวลผลและจำนวนไบต์ที่ใช้
- ไม่มีขั้นต่ำ ไม่มีสัญญา ไม่มีค่าใช้จ่ายล่วงหน้า

ทั้งสามแบบเรียงเป็นชั้นของบริการ IT

| ชั้น | ของที่อยู่ในชั้นนี้ |
| --- | --- |
| SaaS | collaboration, CRM/ERP/HR, business processes, แอปเฉพาะอุตสาหกรรม |
| PaaS | web application runtime, Java runtime, middleware, database, development tooling |
| IaaS | servers, data center fabric, networking, storage |

<KeyIdea>
**ยิ่งชั้นสูง ยิ่งคุมได้น้อย แต่ได้งานอัตโนมัติมากขึ้น ยิ่งชั้นต่ำ ยิ่งคุมได้มาก แต่ต้องรับผิดชอบเองมากขึ้น** PaaS ทำ auto-scaling ให้ได้เพราะมันบังคับโครงสร้างแอป ส่วน IaaS ไม่บังคับอะไร จึงทำให้ไม่ได้
</KeyIdea>

<Quiz question="ทีมหนึ่งเขียนเว็บด้วย Django แล้วอยากได้สองอย่าง คือให้ระบบเพิ่มเครื่องเองตอนคนเยอะ และต้องลงโปรแกรมแปลงวิดีโอตัวพิเศษที่ต้องแก้ค่าใน OS ควรเลือก PaaS หรือ IaaS">
สองความต้องการดึงไปคนละทาง การเพิ่มเครื่องอัตโนมัติคือจุดแข็งของ PaaS เพราะ platform รู้โครงสร้างแอป แต่การแก้ค่าใน OS ทำไม่ได้บน PaaS เพราะผู้ให้บริการคุมชั้น OS ไว้ มีแต่ IaaS ที่ให้คุม OS

คำตอบคือ **IaaS** เพราะความต้องการข้อสองทำบน PaaS ไม่ได้เลย ส่วนข้อแรกยังทำเองบน IaaS ได้ แค่ต้องตั้งเอง ทางที่ดีกว่าคือแยกงานแปลงวิดีโอไปไว้บน IaaS แล้ววางเว็บบน PaaS

คำตอบที่พบบ่อยคือ "PaaS เพราะขยายอัตโนมัติ" ซึ่งดูแค่ข้อดีของชั้นบน โดยลืมว่าชั้นบนแลกมาด้วยการเสียสิทธิ์คุมชั้นล่าง
</Quiz>

## ส่วนที่ 4 — Private, public, hybrid: ใครใช้ร่วมกันได้บ้าง

<Why>
ธนาคารแห่งหนึ่งอยากได้ความยืดหยุ่นของ cloud แต่กฎบังคับให้ข้อมูลลูกค้าห้ามออกนอกองค์กร service model บอกแค่ว่าเช่าถึงชั้นไหน ไม่ได้บอกว่า **โครงสร้างนั้นเป็นของใคร และแชร์กับใคร** deployment model ตอบเรื่องนี้
</Why>

| แบบ | ใครใช้ | รายละเอียด |
| --- | --- | --- |
| **Private cloud** | องค์กรเดียว | องค์กรดูแลเองหรือจ้างคนอื่นดูแลก็ได้ ตั้งอยู่ในสถานที่ขององค์กรหรือนอกสถานที่ก็ได้ |
| **Public cloud** | คนทั่วไปหรือกลุ่มอุตสาหกรรมขนาดใหญ่ | เป็นของบริษัทที่ขายบริการ cloud |
| **Hybrid cloud** | ผสม | cloud ตั้งแต่สองก้อนขึ้นไป (private, community หรือ public) ที่ยังแยกเป็นอิสระ แต่เชื่อมด้วยเทคโนโลยีที่ทำให้ย้ายข้อมูลและแอปข้ามกันได้ |

<Callout type="info" title="Community cloud ไม่มีนิยามในสไลด์">
นิยามของ NIST มีแบบที่สี่คือ <Term en="community cloud" th="cloud ที่หลายองค์กรในกลุ่มเดียวกันใช้ร่วมกัน" /> หมายถึง cloud ที่องค์กรกลุ่มหนึ่งซึ่งมีความต้องการร่วมกัน เช่นหน่วยงานรัฐที่ต้องทำตามกฎชุดเดียวกัน ใช้ร่วมกันเฉพาะในกลุ่ม อยู่ระหว่าง private ที่ใช้องค์กรเดียว กับ public ที่ใครก็ใช้ได้
</Callout>

ภาพที่ควรนึกคือ private cloud อยู่ **หลัง firewall ขององค์กร** ไม่ว่าเครื่องจะตั้งอยู่ที่ไหน public cloud อยู่ข้างนอก ส่วน hybrid cloud คร่อมทั้งสองฝั่ง อุปกรณ์ของผู้ใช้วิ่งไปที่ฝั่งไหนก็ได้ และสองฝั่งส่งงานถึงกันได้

ตัวอย่างการใช้ hybrid คือ <Term en="cloud bursting" th="ล้นจาก private ไปใช้ public ชั่วคราว" /> งานปกติรันใน private cloud ของธนาคาร พอมีช่วงที่งานล้น เช่นสิ้นเดือน ส่วนเกินถูกส่งไปรันบน public cloud แล้วคืนเครื่องเมื่อจบ ธนาคารในตัวอย่างข้างบนจึงเก็บข้อมูลลูกค้าไว้ข้างใน และส่งเฉพาะงานคำนวณที่ไม่แตะข้อมูลนั้นออกไป

### องค์กรใช้แบบไหนกันจริง

ผลสำรวจของ Flexera ปี 2025 พบว่าองค์กรส่วนใหญ่ไม่ได้เลือกแบบเดียว

| รูปแบบ | สัดส่วน |
| --- | --: |
| ใช้หลาย cloud (multi-cloud) | 86% |
| public cloud ก้อนเดียว | 12% |
| private cloud ก้อนเดียว | 2% |

86% ที่ใช้หลาย cloud แยกได้อีกเป็น hybrid 70% หลาย public 14% และหลาย private 2%

Flexera ใช้เกณฑ์ของตัวเอง คือนับเป็น hybrid เมื่อผสม public กับ private โดยไม่ได้ดูว่าเชื่อมกันหรือไม่ และนับการใช้หลาย public อย่าง AWS กับ Azure เป็นกลุ่ม 14% แยกต่างหาก

<Detail label="70% ที่เป็น hybrid ผสมกันแบบไหน">

| ผสม | สัดส่วน |
| --- | --: |
| หลาย public + หลาย private | 34% |
| หลาย public + private เดียว | 21% |
| public เดียว + หลาย private | 8% |
| public เดียว + private เดียว | 7% |

รวมได้ 70% พอดี

</Detail>

<Quiz question="บริษัท ก รันเว็บบน AWS และงานวิเคราะห์บน Azure แยกกันเด็ดขาด บริษัท ข มี private cloud และส่งงานส่วนเกินไปรันบน AWS ทุกสิ้นเดือน ตามนิยามของ NIST บริษัทไหนใช้ hybrid cloud">
ใช้เกณฑ์ของนิยาม hybrid คือ cloud ตั้งแต่สองก้อนที่ **เชื่อมกันจนย้ายข้อมูลและแอปข้ามได้** บริษัท ก ใช้สองก้อนแต่ไม่มีอะไรย้ายข้ามกัน ส่วนบริษัท ข ย้ายงานจาก private ไป public ได้จริง

คำตอบคือ **บริษัท ข** ซึ่งใช้ cloud bursting ส่วนบริษัท ก เป็นแค่ multi-cloud

คำตอบที่พบบ่อยคือ "บริษัท ก เพราะใช้สองเจ้า" ซึ่งนับจำนวน cloud แทนการดูว่าเชื่อมกันหรือไม่ ทั้งสองคำแปลว่าใช้ cloud มากกว่าหนึ่งก้อนจึงสับสนง่าย แต่ hybrid ต้องย้ายงานข้ามกันได้
</Quiz>

</Detail>

- **Animoto** บริการสร้างวิดีโอจากรูปถ่าย รันบน EC2 ภายในราวสามวัน (15–18 เมษายน) จำนวน app server เพิ่มจากไม่กี่สิบเป็นราว 500 เครื่อง และ worker หลังบ้านเพิ่มจากราว 100 เป็นกว่า 4,000 เครื่อง ไม่มีบริษัทไหนซื้อเครื่องสี่พันเครื่องมาติดตั้งทันในสามวัน
- **DISA** (Defense Information Systems Agency ของสหรัฐฯ) จ่าย **$5** บน EC2 แทนการซื้อเซิร์ฟเวอร์และซอฟต์แวร์มูลค่า **$30,000**
- **SmugMug** จ่ายค่า Amazon S3 **$23,000** ต่อเดือน แทนการซื้อฮาร์ดแวร์ใหม่ **$80,000** ต่อเดือน และตัวเลขหลังยังไม่รวมค่าไฟ ค่าระบบทำความเย็น ค่าพื้นที่ data center และค่าคนดูแล

- **(ก) ซื้อพอกับจุดสูงสุด** ต่อให้ทายจุดสูงสุดถูก ช่วงที่คนน้อยเครื่องก็ว่างทิ้งไว้ เหมือนแอปของคุณในส่วนที่ 2 ที่ 12 จาก 24 เครื่อง-ช่วงว่างเปล่า

- **(ค) ผลระยะยาวของ (ข)** ผู้ใช้ที่เจอบริการช้าบางคนหนีไปไม่กลับมา บวกกับข่าวไม่ดี ความต้องการจึงลดลงถาวร รายได้ส่วนหนึ่งหายไปตลอด

การจ่ายตามใช้แก้ทั้งสามแบบด้วยสองกลไก กลไกแรกคือ **extreme elasticity** ซึ่งมาจาก rapid elasticity ในส่วนที่ 2 คือยืดหดได้สุดทาง กลไกที่สองคือ **transference of risk** ซึ่งโอนความเสี่ยงของการซื้อเกินไปให้ผู้ให้บริการ ราคาต่อชั่วโมงที่แพงกว่าคือค่าประกันความเสี่ยงนั้น

สถานการณ์ที่ได้ประโยชน์ชัดที่สุดมีสามแบบ

1. **ภาระงานเปลี่ยนตามเวลาหรือพุ่งเป็นพัก ๆ** เช่นเว็บที่คนเข้ากลางวันมากกว่ากลางคืน
2. **ไม่รู้ความต้องการล่วงหน้า** เช่นโครงการใหม่ startup หรือแอปเปิดตัวใหม่อย่าง Animoto
3. **งานวิเคราะห์แบบ batch** ที่ได้ประโยชน์จากเครื่องจำนวนมากในเวลาสั้น ๆ

งานวิเคราะห์ชิ้นหนึ่งต้องใช้ m3.2xlarge รวม 1,000 ชั่วโมง ราคา $0.784 ต่อชั่วโมง ลองทายก่อน: ทางไหนแพงกว่า

| --- | --: | --: |
| 1 เครื่อง × 1,000 ชั่วโมง | ราว 42 วัน | $784 |
| 1,000 เครื่อง × 1 ชั่วโมง | 1 ชั่วโมง | $784 |

ค่าใช้จ่ายเท่ากันเพราะคิดเงินเป็นเครื่อง-ชั่วโมง ถ้าซื้อเครื่องเอง ทางที่สองต้องซื้อพันเครื่องไว้ใช้ชั่วโมงเดียว
</Example>

### เมื่อไหร่ควรพิจารณา และต้องดูอะไรก่อนย้าย

นอกจากสามแบบข้างบน ยังควรพิจารณา cloud เมื่อ

- ถึงรอบต้องเปลี่ยนเครื่อง
- ต้องการรวมระบบที่กระจายอยู่ให้เป็นที่เดียว
- ถูกกดดันเรื่องต้นทุน — **แต่ระวังกรณีของประเทศไทย** (ส่วนที่ 6)
- IT ไม่ใช่ความเชี่ยวชาญหลักขององค์กร

ก่อนย้ายต้องชั่งแปดเรื่อง

| เรื่อง | คำถาม |
| --- | --- |
| Model | IaaS, PaaS หรือ SaaS |
| Deployment | public, private หรือ hybrid |
| Performance | เร็วพอสำหรับงานไหม |
| Cost | ถูกลงจริงไหม |
| SLA | ผู้ให้บริการรับประกันอะไร |
| Ease of migration, lock-in | ย้ายเข้าง่ายไหม และถ้าวันหนึ่งอยากย้ายออก ติดกับผู้ให้บริการเจ้านี้แค่ไหน |
| Community, ecosystem | มีคนใช้และมีเครื่องมือรอบตัวมากพอไหม |
| Security | ข้อมูลปลอดภัยแค่ไหน |

<Term en="SLA (Service Level Agreement)" th="ข้อตกลงระดับบริการ" /> คือสัญญาที่ผู้ให้บริการระบุว่ารับประกันอะไร เช่นเปอร์เซ็นต์เวลาที่ระบบใช้งานได้

<Term en="lock-in" th="ติดอยู่กับผู้ให้บริการรายเดียว" /> คือสภาพที่แอปพึ่งบริการเฉพาะของเจ้าหนึ่งมากจนย้ายออกแพง

<Quiz question="บริษัทหนึ่งรันระบบเงินเดือนพนักงาน ใช้เครื่องเท่ากันทุกวันตลอดปี รู้จำนวนพนักงานล่วงหน้า และมีทีม IT ของตัวเองที่ดูแลเครื่องได้ดี เหตุผลทางเศรษฐศาสตร์ของ cloud ช่วยบริษัทนี้มากแค่ไหน">
ไล่ตามกลไก การจ่ายตามใช้คุ้มเพราะยืดหดได้และโอนความเสี่ยงของการซื้อผิดขนาด งานนี้ใช้เครื่องคงที่ จึงไม่มีช่วงว่างให้ประหยัด รู้ความต้องการล่วงหน้า จึงไม่มีความเสี่ยงให้โอน และไม่ใช่งาน batch จึงไม่เข้าทั้งสามแบบข้างบน และข้อ IT ไม่ใช่ความเชี่ยวชาญหลักก็ไม่เข้า เพราะ IT เป็นความเชี่ยวชาญที่บริษัทมีอยู่แล้ว

คำตอบคือ **ช่วยน้อย** และอาจแพงกว่าด้วย เพราะจ่ายราคาต่อชั่วโมงที่แพงกว่าโดยไม่ได้ใช้ประโยชน์ที่ราคานั้นซื้อมา

คำตอบที่พบบ่อยคือ "cloud ถูกกว่าเสมอเพราะไม่ต้องซื้อเครื่อง" ซึ่งลืมว่าค่าเช่ารวมค่าความยืดหยุ่นไว้แล้ว งานที่ไม่ต้องการความยืดหยุ่นก็จ่ายค่านั้นทิ้ง
</Quiz>

## ส่วนที่ 6 — กรณีของไทย และความเสี่ยงที่ต้องรู้

### ตัวเลขเดียวกัน ผลตรงข้าม

งานวิจัยปี 2012 ของ Sripanidkulchai และคณะ เทียบต้นทุนการรันระบบเดียวกันในองค์กรเอง (no cloud) กับบน cloud ทั้งในสหรัฐฯ และในไทย วางผลข้างกรณีของ DISA และ SmugMug แล้วจะเห็นว่าต่างกันมาก

| กรณี | ไม่ใช้ cloud | ใช้ cloud | ประหยัด |
| --- | --: | --: | --: |
| DISA | $30,000 | $5 | 99.98% |
| SmugMug | $80,000/เดือน | $23,000/เดือน | 71% |
| ระบบเดียวกันในสหรัฐฯ | $112,500 | $52,500 | 53% |
| ระบบเดียวกันในไทย | $51,500 | $61,500 | **−19%** |

ลองทายก่อน: ระบบเดียวกัน ทำไมในสหรัฐฯ ย้ายขึ้น cloud แล้วประหยัดครึ่งหนึ่ง แต่ในไทยกลับแพงขึ้น

คำตอบอยู่ในรายการต้นทุนของฝั่งไม่ใช้ cloud

| ต้นทุนในองค์กรเอง | สหรัฐฯ | ไทย |
| --- | --: | --: |
| เงินเดือนคนดูแล | $68.6k | $10.3k |
| ฮาร์ดแวร์ | $26.2k | $26.2k |
| ค่าไฟ | $12.4k | $10.7k |
| เครือข่าย | $5.3k | $4.3k |
| **รวม** | **$112.5k** | **$51.5k** |

ฮาร์ดแวร์ราคาเท่ากันทั้งสองประเทศ แต่ **เงินเดือนในสหรัฐฯ สูงกว่าไทยราว 6.7 เท่า** และเป็นก้อนใหญ่สุดของฝั่งสหรัฐฯ สิ่งที่ cloud ช่วยประหยัดได้มากที่สุดคือค่าแรงคนดูแลเครื่อง พอค่าแรงถูกอยู่แล้ว ส่วนที่ประหยัดได้ก็หายไป

แต่ค่า cloud ของไทยไม่ได้ถูกลงตาม กลับแพงกว่าของสหรัฐฯ 17% ($61.5k กับ $52.5k) ซึ่งสอดคล้องกับราคาเช่าที่ region ใกล้ไทยแพงกว่า เช่น m3.2xlarge ที่ Singapore ราคา $0.784 ต่อชั่วโมง ส่วนที่ N. Virginia ราคา $0.560 ([Lecture 7.2](/2110506-sds/lecture-7-2#ชื่อ-instance-type-บอกอะไร) มีตารางเทียบสอง region)

ถึงอย่างนั้นเงินเดือนก็ยังเป็นสาเหตุหลัก ต่อให้ไทยจ่ายค่า cloud ได้เท่าสหรัฐฯ ที่ $52.5k ก็ยังแพงกว่ารันเองซึ่งจ่าย $51.5k จึงต้องคำนวณด้วยต้นทุนของประเทศตัวเองทุกครั้ง

<Detail label="รายการต้นทุนฝั่ง cloud และตัวเลขที่ไม่ลงตัว">

| ต้นทุนบน cloud | สหรัฐฯ | ไทย |
| --- | --: | --: |
| Instances | $23.1k (44%) | $28.4k (47%) |
| Storage I/O | $11.6k (22%) | $12.8k (21%) |
| Snapshot storage | $10.2k (19%) | $10.2k (17%) |
| Provisioned storage | $6.8k (13%) | $7.5k (12%) |
| Network | $0.8k (2%) | $1.3k (4%) |

ตัวเลขในสไลด์ไม่ลงตัวสองจุด และสองจุดนี้ชี้ว่าตัวเลขที่พิมพ์ผิดเป็นคนละชนิดกัน

- **ค่าเครือข่ายในองค์กรของสหรัฐฯ** ระบุไว้ 19.5% ทั้งที่ $5.3k จาก $112.5k คิดเป็น 4.7% ยอดดอลลาร์สี่รายการรวมได้ $112.5k ตรง แต่เปอร์เซ็นต์รวมได้ 114.5% ถ้าใช้ 4.7% จะรวมได้ราว 100% ที่ผิดจึงน่าจะเป็นเปอร์เซ็นต์
- **ต้นทุน cloud ของไทย** ห้ารายการรวมได้ $60.2k ไม่ใช่ยอดรวม $61.5k ที่ระบุ ขาดไป $1.3k เปอร์เซ็นต์ของสี่รายการแรกต่างจากที่คำนวณจากดอลลาร์ไม่เกิน 1 จุด แต่ Network $1.3k คิดเป็นแค่ 2.1% ของ $61.5k ไม่ใช่ 4% ที่ระบุ ถ้าเติมส่วนที่ขาดให้ Network เป็น $2.6k จะได้ 4.2% และยอดรวมลงตัว ที่ผิดจึงน่าจะเป็นตัวเลขดอลลาร์ของ Network

ทั้งสองจุดไม่เปลี่ยนข้อสรุป ต่อให้ใช้ยอดของไทยที่บวกได้จริง $60.2k ค่า cloud ก็ยังแพงกว่ารันเอง $51.5k

</Detail>

### องค์กรไทยกังวลอะไรกับ public cloud

องค์กรไทยกังวลห้าเรื่องกับ public cloud

- **ไม่มีผู้ให้บริการในประเทศ** ในยุคของงานวิจัยข้างบน region ของผู้ให้บริการรายใหญ่ที่ใกล้ที่สุดอยู่นอกไทย คือ สิงคโปร์ ฮ่องกง และญี่ปุ่น
- **performance ของเครือข่าย** เพราะข้อมูลต้องวิ่งออกนอกประเทศ
- **ราคาที่แข่งได้**
- **ความปลอดภัย**
- **ความรู้ความชำนาญ** (know-how)

<Callout type="info" title="เสริม — AWS มี region ในไทยแล้ว">
ข้อกังวลข้อแรกเปลี่ยนไปแล้ว วันที่ 7 มกราคม 2025 AWS เปิด region Asia Pacific (Thailand) รหัส `ap-southeast-7` องค์กรไทยจึงเลือกเก็บข้อมูลบน AWS ไว้ในประเทศได้ ส่วนข้ออื่นยังต้องชั่งเหมือนเดิม
</Callout>

Private cloud มักเป็นทางเลือกที่ตอบข้อกังวลเหล่านี้ เพราะใช้งานองค์กรเดียว และองค์กรเลือกเองว่าเครื่องและข้อมูลอยู่ที่ไหน แต่เรื่องราคาและ know-how กลับมาเป็นโจทย์ของ private cloud เอง การสร้างและดูแล private cloud จึงมีโจทย์สามข้อ

1. **ทำให้ต้นทุนแข่งกับ public cloud ได้ทั้งสองก้อน**
   - <Term en="CapEx" th="เงินลงทุนก้อนแรก" /> ลดได้ด้วยการเลือกเทคโนโลยีให้ถูก ตั้งแต่ฮาร์ดแวร์ virtualization platform ไปจนถึง management platform
   - <Term en="OpEx" th="ค่าใช้จ่ายดำเนินงาน" /> ลดได้ด้วยการรันให้มีประสิทธิภาพที่สุด
2. **เลือก service model ที่เหมาะกับองค์กร** ว่าจะให้บริการภายในเป็น IaaS, PaaS หรือ SaaS
3. **เพิ่ม know-how** ให้ทั้งผู้ใช้และผู้ดูแลระบบ

ตัวอย่าง cloud ในประเทศมี **GDCC** ซึ่งเป็นรุ่นใหม่ของ G-Cloud บริการ cloud ภาครัฐของไทย ([gdcc.onde.go.th](https://gdcc.onde.go.th/gdcc-portal/)) และ **Nipa Cloud** ผู้ให้บริการ cloud ของไทย ([nipa.cloud](https://www.nipa.cloud/))

ลองประเมิน Nipa Cloud ด้วยห้าคุณสมบัติและสาม service model แบบเดียวกับที่ไล่ EC2 ในส่วนที่ 2 และ 3 GDCC ก็ประเมินด้วยวิธีเดียวกัน

<Quiz question="บริการ Nipa Cloud Space ให้คุณเข้า portal สร้าง virtual machine เอง เลือก OS image เอง คิดเงินรายชั่วโมงตามที่ใช้ และยกเลิกเมื่อไหร่ก็ได้ บริการนี้เป็น service model ไหน และผ่านห้าคุณสมบัติของ cloud ครบไหม">
ดูว่าใครดูแลชั้นไหน คุณได้ VM แล้วเลือก OS เอง จึงคุมตั้งแต่ OS ขึ้นไป แบบเดียวกับ EC2 คำตอบคือ **IaaS**

สร้างเองผ่าน portal เพิ่มหรือยกเลิกได้ทุกเมื่อ และคิดเงินรายชั่วโมง จึง **ผ่านครบห้าข้อ** ด้วยเหตุผลเดียวกับ EC2 ในส่วนที่ 2

คำตอบที่พบบ่อยคือ "SaaS เพราะใช้ผ่านหน้าเว็บ" ซึ่งดูที่ช่องทางเข้าใช้ แต่ portal เป็นแค่ที่สั่งงาน ของที่ได้คือ VM ที่คุณคุม OS เอง service model ดูที่ว่าใครดูแลชั้นไหน

### Cloud ก็ล่มได้

ในเดือนธันวาคม 2021 AWS ล่มสามครั้งในสามสัปดาห์

- **7 ธันวาคม** ราว 7 ชั่วโมง เริ่มประมาณ 11:20 น. เวลาฝั่งตะวันออกของสหรัฐฯ เครือข่ายภายในของ AWS ที่ใช้สำหรับ monitoring, <Term en="DNS" th="ระบบแปลงชื่อโดเมนเป็นหมายเลข IP" /> ภายใน และระบบตรวจสิทธิ์ เกิดการเชื่อมต่อพุ่งขึ้นมหาศาลจนอุปกรณ์เครือข่ายที่เชื่อมเครือข่ายภายในกับเครือข่ายหลักของ AWS รับไม่ไหว เพราะเครือข่ายภายในนี้ต่อกับเซิร์ฟเวอร์ AWS ทั่วโลก บริการทั่วโลกจึงช้าหรือล่มตาม ได้แก่ Ring, Alexa, Disney+, iRobot, Venmo, Prime Video
- **15 ธันวาคม** ล่มอีกครั้ง ได้แก่ Twitch, DoorDash, Xbox Live, PSN, Ring, Disney+, T-Mobile
- **22 ธันวาคม** **ไฟดับ** ที่ data center แห่งหนึ่งฝั่งตะวันออก ได้แก่ Fortnite, Hulu, Quora, Slack, Imgur

AWS มีส่วนแบ่งราว 33% ของตลาดบริการโครงสร้างพื้นฐาน cloud ทั้งตลาด ครั้งแรกจึงอาจลากบริการ cloud ราวหนึ่งในสามลงไปด้วย ตัวเลขนี้วัดคนละอย่างกับ 53% ข้างบน ซึ่งเป็นสัดส่วนขององค์กรที่ตอบผลสำรวจว่ารันงานจำนวนมากบน AWS องค์กรหนึ่งตอบได้หลายเจ้า ตัวเลขของทุกเจ้าจึงรวมกันเกิน 100%

เจ้าอื่นก็เจอ ในเดือนเมษายน 2021 **Microsoft** มีปัญหา DNS จากปริมาณคำขอ DNS ที่พุ่งขึ้นผิดคาด ทำให้ Azure, Teams และ Dynamics 365 ล่มราว 5 ชั่วโมง DNS เป็นสมุดรายชื่อที่ทุกบริการต้องเปิดก่อนจะคุยกันได้ ล่มจุดเดียวจึงล่มทั้งหมด

Google ก็เช่นกัน วันที่ 12 เมษายน 2021 **Google** Drive, Docs, Sheets ล่มบางส่วนราว 3 ชั่วโมง ผู้ใช้บางคนเจอการตอบสนองช้ามาก แต่ Gmail, Calendar, Meet ไม่กระทบ

บทเรียนของทุกครั้งคือ ผู้ใช้ cloud ฝากระบบไว้กับเครือข่ายและ data center ของผู้ให้บริการ เมื่อส่วนนั้นมีปัญหา ลูกค้าที่พึ่งส่วนนั้นช้าหรือล่มไปพร้อมกัน และแก้เองไม่ได้

<Quiz question="ร้านค้าออนไลน์ร้านหนึ่งเก็บทั้งหน้าเว็บ ฐานข้อมูล และระบบชำระเงินไว้ใน region เดียวของ AWS คือ us-east-1 (N. Virginia) วันที่ 7 ธันวาคม 2021 ร้านนี้น่าจะเจออะไร และบทเรียนนี้เกี่ยวกับเรื่องไหนในแปดเรื่องที่ต้องชั่งก่อนย้าย">
สาเหตุของวันนั้นอยู่ในเครือข่ายภายในของ AWS ไม่ใช่ในเครื่องของร้าน ร้านจึงแก้เองไม่ได้ และเพราะทุกชิ้นอยู่ที่ผู้ให้บริการรายเดียว ทุกชิ้นช้าหรือล่มพร้อมกันจนกว่า AWS จะแก้เสร็จ ราว 7 ชั่วโมง

บทเรียนตรงกับเรื่อง **SLA** คือต้องรู้ว่าผู้ให้บริการรับประกันเวลาใช้งานได้แค่ไหน และชดเชยอะไร และเรื่อง **lock-in** คือถ้าพึ่งรายเดียวจนย้ายไม่ได้ ก็ไม่มีทางหนี นี่คือเหตุผลหนึ่งที่ 86% ขององค์กรใช้หลาย cloud

คำตอบที่พบบ่อยคือ "ไม่กระทบ เพราะ cloud มีเครื่องสำรองเยอะ" ซึ่งคิดถึงแค่เครื่องเสีย แต่ครั้งนี้สิ่งที่พังคือเครือข่ายที่เครื่องทุกตัวใช้ร่วมกัน เครื่องสำรองก็อยู่หลังเครือข่ายเดียวกันนั้น
</Quiz>

<Recap>

**Cloud คืออะไร**

- ผู้ใช้ cloud: ซื้อทรัพยากรหรือใช้ซอฟต์แวร์เป็นบริการ ใช้เมื่อต้องการ จ่ายเท่าที่ใช้ ได้และคืนได้เร็ว แทบไม่ต้องติดต่อคน
- ผู้ให้บริการ: data center ที่แชร์ให้หลายรายด้วย virtualization (multi-tenant) รักษาคุณภาพตามที่ตกลง วัดการใช้แล้วคิดเงิน
- NIST 2011 นิยามด้วยสามด้าน: essential characteristics, service models, deployment models

**ห้าคุณสมบัติ**

- On-demand self-service (ขอเองไม่ต้องผ่านคน), broad network access, resource pooling (กองกลาง multi-tenant, location independence), rapid elasticity (ดูเหมือนไม่มีวันหมด), measured service (วัดและรายงานให้ทั้งสองฝั่งเห็น)

**Service models**

- SaaS: ใช้แอปของผู้ให้บริการ เช่น Adobe Creative Cloud (สมัครสมาชิก ทุกคนใช้รุ่นเดียวกัน)
- PaaS: วางแอปของคุณบน platform เช่น Google App Engine (บังคับโครงสร้าง แยก stateless กับ stateful จึง auto-scale ได้ จ่ายตามธุรกรรม)
- IaaS: เช่า VM เช่น Amazon EC2 (คุม OS เอง auto-scale ให้ยาก จ่ายตามใช้ ไม่มีสัญญา)
- ชั้นสูง คุมน้อย อัตโนมัติมาก / ชั้นต่ำ คุมมาก รับผิดชอบมาก

**Deployment models**

- Private (องค์กรเดียว), community (กลุ่มองค์กรที่มีความต้องการร่วมกัน), public (ใครก็ใช้), hybrid (cloud ตั้งแต่สองก้อนที่เชื่อมกันจนย้ายข้อมูลและแอปข้ามได้ เช่น cloud bursting)
- Flexera 2025: multi-cloud 86% (hybrid 70%), public เดียว 12%, private เดียว 2%

**คุ้มเมื่อไหร่**

- คุ้มเพราะยืดหดได้และโอนความเสี่ยงของการซื้อผิดขนาด แม้ราคาต่อชั่วโมงแพงกว่า
- ซื้อเท่าจุดสูงสุด = เครื่องว่าง / ซื้อน้อยกว่า = เสียรายได้ และผู้ใช้หนีถาวร
- เหมาะกับงานที่ขึ้นลงตามเวลา ไม่รู้ความต้องการล่วงหน้า หรือ batch (1,000 เครื่อง 1 ชั่วโมง = 1 เครื่อง 1,000 ชั่วโมง)
- ชั่งก่อนย้าย: model, deployment, performance, cost, SLA, lock-in, ecosystem, security

**ไทยและความเสี่ยง**

- ระบบเดียวกัน สหรัฐฯ ประหยัด 53% ไทยแพงขึ้น 19% เพราะส่วนที่ cloud ประหยัดคือค่าแรง ซึ่งในไทยถูกอยู่แล้ว และค่า cloud ของไทยก็ไม่ได้ถูกลงตาม
- องค์กรไทยกังวล: ไม่มีผู้ให้บริการในประเทศ (AWS เปิด region ไทยแล้วในปี 2025), เครือข่าย, ราคา, ความปลอดภัย, know-how → private cloud ซึ่งต้องคุม CapEx/OpEx
- ปัญหาอันดับหนึ่งคือค่าใช้จ่าย (84%) และ 21% ของงานถูกย้ายกลับ
- AWS ล่มสามครั้งในสามสัปดาห์ ธันวาคม 2021 Microsoft ล่มเพราะ DNS Google Drive ล่มบางส่วน
