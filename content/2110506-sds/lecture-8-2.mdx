[Lecture 8.1](/2110506-sds/lecture-8) วางรูปของอัลบั้มชมรมไว้ใน S3 ซึ่งเป็น [object storage](/2110506-sds/lecture-8#ส่วนที่-2--block-storage-กับ-object-storage) ที่รับ object ทั้งก้อน ทนทานทั่วทั้ง [region](/2110506-sds/lecture-8#ขนาด-region-และการเข้าถึง) และคิดเงินตาม GB ที่เก็บ จำนวนคำขอ และข้อมูลที่ส่งออก

แต่ฐานข้อมูลของชมรมแก้ยอดไลก์ทีละ 8 KB กลางไฟล์ทุกครั้งที่มีคนกดไลก์ จึงต้องอยู่บน block storage ซึ่งรองรับคำสั่งไฟล์แบบ POSIX และเขียนทับได้ทีละ block

หน้านี้ตอบว่า block storage สองแบบของ EC2 ต่างกันยังไง และไฟล์ชั่วคราวกับข้อมูลสำรองของชมรมควรอยู่ตรงไหน

<KeyIdea>
EC2 มีดิสก์สองแบบ **instance store** อยู่บนเครื่อง host จึงเร็วและฟรี แต่ข้อมูลหายเมื่อเครื่องหยุดหรือถูกลบ **EBS** อยู่นอกเครื่อง ต่อผ่านเครือข่าย มีสำเนาใน AZ เดียวกัน และอยู่ต่อได้หลังเครื่องหาย ข้อมูลสำรองของ EBS คือ snapshot ใน S3 ที่เก็บเฉพาะส่วนที่เปลี่ยน
</KeyIdea>

## ส่วนที่ 1 — ดิสก์ของ EC2: instance store กับ EBS

เครื่อง EC2 หนึ่งเครื่องมีที่เก็บได้สามแบบ คือ instance store, EBS และ S3 สองแบบแรกเป็น block storage ที่ระบบปฏิบัติการเห็นเป็นดิสก์ ต่างกันที่ **ดิสก์อยู่ที่ไหน**

<Term en="Availability Zone (AZ)" th="data center แยกกันภายใน region" /> คือกลุ่ม data center ที่แยกขาดจากกันภายใน region หนึ่ง region มีหลาย AZ รูปที่ 1 ใช้คำนี้เป็นกรอบ เพราะ EBS ผูกกับ AZ ส่วน S3 ผูกกับ region

### Instance store: ดิสก์บนเครื่อง host

<Term en="Instance store" th="ดิสก์ที่ติดอยู่กับเครื่อง host" /> คือดิสก์ที่อยู่ในเครื่องจริงที่ hypervisor รัน instance ของคุณอยู่ ในรูปที่ 1 Instance A ใช้ `eph0` ซึ่งอยู่ใต้หลังคาเดียวกัน ข้อมูลจึงไม่ต้องวิ่งผ่านเครือข่ายเลย

ผลตามมามีสามข้อ

- **เร็วมาก** เพราะเป็นดิสก์ในเครื่อง
- **ฟรี** มาพร้อมกับ instance
- **ไม่ถาวร** (ephemeral) ข้อมูลอยู่ได้แค่ตลอดอายุของ instance เมื่อ instance จบ ดิสก์ของ host ถูกคืนให้ระบบไปใช้กับคนอื่น

ข้อมูลบน instance store มี **สำเนาเดียว** บนดิสก์ทั่วไป ซึ่งมี <Term en="AFR (Annual Failure Rate)" th="อัตราดิสก์เสียต่อปี" /> ราว 1.5% ถึง 4% ต่อปี แปลว่าดิสก์ 100 ลูกจะเสียราว 1.5 ถึง 4 ลูกในหนึ่งปี และดิสก์ที่เสียพาข้อมูลไปด้วย

ข้อนี้คล้ายชั้นเขียนได้ (writable layer) ของ container ที่หายไปเมื่อสั่ง `docker rm` ใน [Lecture 2.2](/2110506-sds/lecture-2-2#หยุด-เริ่มใหม่-และลบ) แต่ต่างกันตอนหยุด container ที่ `stop` แล้ว `start` ยังมีไฟล์ครบ แต่ instance store ไม่รอดการหยุด

ไฟล์ชั่วคราวตอนย่อรูปของชมรมจึงเหมาะกับ instance store เพราะถ้าหายก็ย่อใหม่จากรูปต้นฉบับใน S3 ได้

### AMI มาจากไหน

เครื่อง EC2 บูตจาก AMI (Amazon Machine Image) ที่ hypervisor คัดลอกมาจาก image library ([Lecture 7.2 ส่วนที่ 7](/2110506-sds/lecture-7-2#ส่วนที่-7--image-library-os-ที่ขอมาอยู่ที่ไหน))

AMI กำหนดว่าดิสก์ root ของเครื่องเป็น instance store หรือ EBS ตอนเลือก AMI ใน Console จึงมีตัวกรอง **Root device type** ให้เลือก EBS หรือ Instance store

**AMI แบบ instance store-backed** เก็บอยู่ใน bucket ของ S3 ตอนเปิดเครื่อง AWS คัดลอก AMI ทั้งก้อนจาก S3 ลงดิสก์ `ephemeral0` ของ host (ในรูปที่ 1 คือ `eph0`)

ระบบปฏิบัติการรู้จักดิสก์ผ่าน <Term en="Block device mapping" th="ตารางจับคู่ชื่อดิสก์กับดิสก์จริง" /> ซึ่งบอกว่าชื่ออุปกรณ์อย่าง `/dev/sda1`, `/dev/sdh`, `/dev/sdj`, `/dev/sdb` ชี้ไปที่ดิสก์จริงตัวไหน ในกรณีนี้ `/dev/sda1` ซึ่งเป็นดิสก์ root ชี้ไปที่ `ephemeral0`

เพราะ root อยู่บน instance store เครื่องแบบนี้ **หยุดชั่วคราวไม่ได้** มีแค่สองสถานะ คือ running กับ terminated ถ้าหยุดเครื่อง ก็ไม่มีที่ไหนเก็บดิสก์ root ไว้รอ

### EBS: ดิสก์ที่อยู่นอกเครื่อง

<Term en="EBS (Elastic Block Store)" th="ดิสก์ถาวรที่ต่อกับ EC2 ผ่านเครือข่าย" /> คือ volume หรือดิสก์เสมือนหนึ่งลูก (คนละอย่างกับ volume ของ Docker) ที่อยู่นอกเครื่อง host และต่อเข้ามา **ผ่านเครือข่าย** ระบบปฏิบัติการเห็นมันเป็นดิสก์ลูกหนึ่งเหมือน hard drive เพราะ hypervisor นำ volume มาต่อ (attach) เป็นดิสก์เสมือนของ VM

**AMI แบบ EBS-backed** ใช้ EBS volume เป็นดิสก์ root block device mapping ชี้ `/dev/sda1` ไปที่ volume ที่ทำหน้าที่ root device volume และชี้ `/dev/sdh`, `/dev/sdj` ไปที่ EBS volume ตัวอื่น

EBS เป็นที่เก็บแบบ block ที่ **กระจายและทำสำเนา** ออกแบบมาให้ข้อมูลตรงกันเสมอและอ่านเขียนจาก EC2 ได้ด้วย latency ต่ำ ทุก volume มีตัวหลัก (primary) บน EBS node หนึ่ง และ mirror ทุกการเขียนไปยังตัวสำรอง (replica) บนอีก node แบบ peer-to-peer ทั้งคู่อยู่ใน AZ เดียวกัน

เพราะทุกการเขียนมีสองสำเนาบนสอง node ดิสก์ลูกหนึ่งเสียข้อมูลก็ยังอยู่ ผลคือ EBS มี AFR เพียง 0.1–0.2% ทนกว่าดิสก์ทั่วไปราว 20 เท่า

ข้อเท็จจริงของ EBS ที่ต้องรู้

- ดิสก์จริงข้างหลังมีสามแบบ คือ Magnetic Disk, Standard SSD และ Provisioned SSD ที่คุณกำหนดความเร็วในการอ่านเขียนที่ต้องการได้
- instance หนึ่งตัวต่อ EBS ได้หลาย volume สูงสุด 40 volume
- volume หนึ่งตัวต่อกับ instance ได้ทีละตัวเท่านั้น ยกเว้น Provisioned SSD รุ่น io1 หรือ io2 ที่เปิด Multi-Attach ซึ่งต่อได้ถึง 16 instance ใน AZ เดียวกัน
- volume แต่ละตัวอยู่ใน AZ เดียว

### เทียบ AMI สองแบบ

| เรื่อง | EBS-backed | Instance store-backed |
| --- | --- | --- |
| เวลาบูต | มักไม่ถึง 1 นาที | มักไม่ถึง 5 นาที |
| ขนาดดิสก์ root สูงสุด | 16 TiB | 10 GiB |
| ดิสก์ root | EBS volume | instance store volume |
| อัปเกรดเครื่อง | เปลี่ยน instance type, kernel, RAM disk และ user data ได้ตอนเครื่องหยุดอยู่ | ค่าของเครื่องตายตัวไปตลอดอายุ |
| ค่าใช้จ่าย | ค่า instance + ค่า EBS + ค่าเก็บ AMI เป็น EBS snapshot | ค่า instance + ค่าเก็บ AMI ใน S3 |
| สร้าง AMI | ใช้คำสั่งเดียว | ต้องติดตั้งและใช้ AMI tools |
| หยุดเครื่อง | หยุดได้ ดิสก์ root ยังเก็บอยู่ใน EBS | หยุดไม่ได้ มีแค่ running หรือ terminated |

สิ่งที่ต้องจำให้แม่นคือ **แต่ละดิสก์อยู่ได้นานแค่ไหนหลัง terminate**

- EBS volume ที่เป็นดิสก์ root ถูกลบเมื่อ instance ถูก terminate นี่คือค่าเริ่มต้นที่ตั้งเปลี่ยนได้
- EBS volume ตัวอื่นอยู่ต่อหลัง terminate เป็นค่าเริ่มต้น
- instance store อยู่ได้แค่ตลอดอายุของ instance ไม่ว่า AMI เป็นแบบไหน

เวลาบูตต่างกันเพราะ AMI แบบ instance store ต้องดึงจาก S3 มาให้ครบทั้งก้อนก่อนเครื่องจะพร้อม ส่วน AMI แบบ EBS ดึงมาแค่ส่วนที่ต้องใช้บูต ส่วนที่เหลือดึงตามมาทีหลัง กลไกนี้คือ lazy loading ในส่วนที่ 2

<Pitfall>
"instance store ก็คือดิสก์ ปิดเครื่องแล้วเปิดใหม่ ข้อมูลก็ยังอยู่เหมือนคอมที่บ้าน" ไม่จริง

ความเชื่อนี้ดูถูก เพราะระหว่างที่เครื่องรันอยู่ instance store ทำตัวเหมือนดิสก์ทุกอย่าง reboot ก็ยังอยู่

แต่ instance store เป็นดิสก์ของ **เครื่อง host** ไม่ใช่ของ instance เครื่องแบบ instance store-backed หยุดไม่ได้เลย ส่วนเครื่องแบบ EBS-backed ที่ถูกหยุด จะคืน host ไป และ AWS ล้างข้อมูลบน instance store ทุกครั้งที่หยุด ต่อให้เปิดใหม่บน host เครื่องเดิมก็ไม่ได้ข้อมูลคืน ซึ่งส่วนใหญ่ก็ได้ host เครื่องใหม่อยู่แล้ว ข้อมูลที่ต้องอยู่ต่อจึงต้องอยู่บน EBS หรือ S3
</Pitfall>

<Quiz question="เครื่อง EC2 ของชมรมเป็นแบบ EBS-backed มี EBS สองตัว คือดิสก์ root กับดิสก์ข้อมูล และมี instance store อีกหนึ่งลูก ถ้าเครื่องถูก terminate ด้วยค่าเริ่มต้นทั้งหมด อะไรเหลืออยู่">
ไล่ทีละลูกตามสามข้อข้างบน EBS ที่เป็นดิสก์ root ถูกลบตามค่าเริ่มต้น EBS ตัวอื่นอยู่ต่อ ส่วน instance store อยู่ได้แค่ตลอดอายุของ instance

คำตอบคือ **เหลือแค่ EBS ดิสก์ข้อมูล**

คำตอบที่ผิดบ่อยคือ "EBS เหลือทั้งสองตัว เพราะ EBS ถาวร" คำว่าถาวรหมายถึง EBS ไม่หายไปพร้อม host แต่ดิสก์ root ถูกตั้งให้ลบตอน terminate ไว้เป็นค่าเริ่มต้น
</Quiz>

## ส่วนที่ 2 — EBS snapshot

<Pitfall>
"EBS มี replica อยู่แล้ว ไม่ต้องสำรองข้อมูลก็ได้" ไม่จริง

ความเชื่อนี้ดูถูก เพราะ EBS mirror ทุกการเขียนไปอีก node จริง และทนกว่าดิสก์ทั่วไปราว 20 เท่า

แต่ mirror คัดลอก **ทุก** การเขียน รวมถึงการเขียนที่ผิด ถ้าแอปลบตารางสมาชิกทิ้ง replica ก็ลบตามในทันที นอกจากนั้นทั้ง primary และ replica อยู่ใน AZ เดียวกัน ถ้า AZ นั้นมีปัญหาทั้งคู่ก็ใช้ไม่ได้พร้อมกัน สิ่งที่แก้ทั้งสองเรื่องได้คือสำเนาของอดีตที่เก็บไว้นอก AZ ซึ่งก็คือ snapshot
</Pitfall>

<Term en="Snapshot" th="สำเนาของ volume ณ เวลาหนึ่ง" /> คือสำเนาของ EBS volume ณ เวลาหนึ่ง ที่ถูกเก็บลงใน S3 การทำงานระหว่าง EC2, EBS และ S3 มีสองทิศทาง

- **Create Snapshot** คัดลอก volume ใน AZ หนึ่งไปเก็บใน S3
- **Clone From Snapshot** สร้าง EBS volume ใหม่จาก snapshot ใน S3

snapshot จึงใช้ได้สามงาน

- **ย้ายข้อมูลข้าม AZ**
- **สำรองข้อมูล**
- **แชร์ข้อมูล** ให้คนอื่นสร้าง volume จาก snapshot เดียวกัน

### Snapshot แบบ incremental

ถ้าทุก snapshot คัดลอก volume ทั้งลูก การสำรองฐานข้อมูล 10 GB ทุกวันเป็นเวลาหนึ่งเดือนจะกินพื้นที่ 300 GB ทั้งที่ข้อมูลเปลี่ยนวันละนิดเดียว

volume ถูกแบ่งเป็นช่วงขนาดเท่ากัน เรียกว่า chunk หรือ block และ snapshot คัดลอกทีละ chunk

EBS แก้ด้วย snapshot แบบ <Term en="Incremental" th="เก็บเฉพาะส่วนที่เปลี่ยน" /> คือ snapshot แรกคัดลอกทุก chunk ของ volume ส่วน snapshot ถัดไปคัดลอกเฉพาะ chunk ที่เปลี่ยนตั้งแต่ครั้งก่อน chunk ที่ไม่เปลี่ยนก็ชี้ไปที่ของที่เก็บไว้แล้ว

<Figure number={2} caption="volume สี่ chunk ถ่าย snapshot สามครั้ง ระหว่างครั้งที่ 1 กับ 2 chunk 3 เปลี่ยนจาก C เป็น C2 ระหว่างครั้งที่ 2 กับ 3 chunk 1 เปลี่ยนจาก A เป็น A2">
  <SnapshotChunks />
</Figure>

snapshot ทั้งสามตัวยังกู้คืน volume ได้ครบสี่ chunk ทุกตัว แต่ S3 เก็บของจริงแค่ 6 chunk ไม่ใช่ 12

ลองทายก่อน: ถ้าลบ snapshot 1 ซึ่งเป็นตัวเดียวที่คัดลอกครบทั้งสี่ chunk แล้ว snapshot 3 ยังกู้คืน volume ได้ครบไหม และ S3 คืนพื้นที่ได้กี่ chunk

<Example added title="ลบ snapshot แรกแล้วเหลืออะไร">
สคริปต์จำลอง chunk ตามรูปที่ 2 แล้วลบ snapshot 1 ทิ้ง

```
snap1: copies ['1=A', '2=B', '3=C', '4=D']  stored total 4
snap2: copies ['3=C2']  stored total 5
snap3: copies ['1=A2']  stored total 6
after delete snap1, kept: ['1=A', '1=A2', '2=B', '3=C2', '4=D']
freed: ['3=C']
snap3 restore: {1: 'A2', 2: 'B', 3: 'C2', 4: 'D'}
```

ลบแล้วคืนพื้นที่ได้แค่ chunk เดียว คือ `C` ที่ไม่มี snapshot ไหนใช้แล้ว ส่วน `A`, `B`, `D` ยังอยู่เพราะ snapshot 2 ยังชี้ถึง และ snapshot 3 กู้คืนได้ครบ
</Example>

### อีกสองอย่างที่ทำให้ snapshot เร็ว

**Zero block compression** block ที่มีแต่เลขศูนย์ เช่นพื้นที่ว่างที่ยังไม่เคยเขียน ไม่ต้องคัดลอกไปเก็บ volume 100 GB ที่ใช้จริง 10 GB จึงไม่ต้องส่งข้อมูลครบ 100 GB

**Lazy loading จาก S3 ไป EBS** volume ที่สร้างจาก snapshot ใช้ได้ทันที โดยยังไม่ต้องดึงข้อมูลครบ ข้อมูลแต่ละส่วนถูกดึงจาก S3 ตอนที่ถูกอ่านครั้งแรก นี่คือเหตุผลที่ AMI แบบ EBS-backed บูตได้ในไม่ถึงนาที

<Detail label="ช่องในหน้า Create snapshot ของ Console">
หน้า **EC2 › Snapshots › Create snapshot** สร้าง point-in-time snapshot ของ EBS volume เพื่อใช้เป็นจุดเริ่มต้นของ volume ใหม่หรือเพื่อสำรองข้อมูล เลือก Resource type ได้สองแบบ

- **Volume** สร้าง snapshot จาก volume เดียว แล้วเลือก Volume ID
- **Instance** สร้าง snapshot ของทุก volume ที่ต่ออยู่กับ instance นั้นพร้อมกัน (multi-volume snapshot)

ช่อง Description ใส่คำอธิบายได้ไม่เกิน 255 ตัวอักษร
</Detail>

<Quiz question="ฐานข้อมูลของชมรมอยู่บน EBS volume ใน AZ แรก แต่เครื่องใหม่ที่จะใช้แทนอยู่ใน AZ ที่สองของ region เดียวกัน จะย้ายข้อมูลไปยังไง">
EBS volume อยู่ได้ใน AZ เดียว และต่อได้เฉพาะ instance ใน AZ นั้น จึงถอดไปต่อกับเครื่องใน AZ ที่สองตรง ๆ ไม่ได้ แต่ snapshot อยู่ใน S3 ซึ่งผูกกับ region ไม่ผูกกับ AZ

คำตอบคือ **สร้าง snapshot ของ volume แล้วสร้าง volume ใหม่จาก snapshot นั้นใน AZ ที่สอง** จากนั้นต่อ volume ใหม่เข้ากับเครื่องใหม่

คำตอบที่ผิดบ่อยคือ "detach volume จากเครื่องเก่า แล้ว attach กับเครื่องใหม่" ซึ่งทำได้เฉพาะเมื่อสองเครื่องอยู่ใน AZ เดียวกัน
</Quiz>

## ส่วนที่ 3 — เลือกที่เก็บให้ตรงกับงาน

### เทียบสามแบบในตารางเดียว

| เรื่อง | EC2 instance store | EBS | S3 |
| --- | --- | --- | --- |
| Interface | file system ไม่ถาวร (POSIX) | file system ถาวร (POSIX) | REST web service ถาวร (ไม่ใช่ POSIX) |
| ความเร็ว | เร็วมาก | เร็ว แต่ขึ้นกับเครือข่าย | ช้ากว่า ขึ้นกับเครือข่าย |
| ความทนทาน | สำเนาเดียวบนดิสก์ทั่วไป AFR 1.5–4% | ทนใน AZ, AFR 0.1–0.2% ทนกว่าดิสก์ทั่วไป 20 เท่า | 99.999999999% ใน region ทำสำเนาข้าม region ได้ (คลาส RRS 99.99%) |
| ราคา (สิงคโปร์) | ฟรีพร้อม instance (ถ้าดิสก์ root ไม่ใช่ EBS) | Disk $0.54, SSD $0.12 ต่อ GB ที่จองไว้ต่อเดือน | $0.025 ต่อ GB ที่เก็บ + ค่าคำขอ + ค่าส่งข้อมูล |
| ขนาด | Disk 160 GB – 48 TB, SSD 32 – 6,400 GB | ต่อ volume: Disk 500 GB – 16 TB, SSD 16 TB, 40 volume ต่อ instance | object ละไม่เกิน 5 TB, object ไม่จำกัด, 100 bucket (ขีดจำกัดตอนทำสไลด์) |
| ความปลอดภัย | เห็นได้แค่เจ้าของ | เห็นได้แค่เจ้าของ | ACL ตั้ง object เป็น private หรือ public |
| การดูแล | ทำสำเนาเอง | snapshot, RAID, ความถูกต้องของข้อมูล | ไม่ต้องดูแล |

RRS (Reduced Redundancy Storage) ในแถวความทนทานคือคลาสของ S3 ที่ทำสำเนาน้อยกว่า ความทนทานจึงต่ำกว่า

สองแถวที่มักถูกอ่านข้ามคือ **ราคา** กับ **การดูแล**

EBS คิดเงินตาม GB ที่ **จองไว้** volume 500 GB ที่ใช้แค่ 200 GB จึงจ่ายเต็ม 500 GB ส่วน S3 คิดตาม GB ที่ **เก็บอยู่จริง** บวกค่าคำขอ

instance store ต้อง **ทำสำเนาเอง** ถ้าอยากกันดิสก์เสีย EBS มี snapshot ให้ และรวมหลาย volume เป็น <Term en="RAID" th="การรวมหลายดิสก์ให้ทำงานเป็นลูกเดียว" /> ได้ ส่วน S3 ไม่ต้องดูแลอะไรเลย

### งานแบบไหนควรอยู่ที่ไหน

<Term en="CloudFront" th="CDN ของ AWS" /> คือบริการที่เก็บสำเนาของเนื้อหาไว้ในจุดที่ใกล้ผู้ใช้ทั่วโลก จับคู่กับ S3 เพื่อแจกไฟล์ให้คนจำนวนมาก

| | S3 + CloudFront | EC2 instance store | EBS |
| --- | --- | --- | --- |
| เหมาะกับ | object ใหญ่ที่เขียนครั้งเดียวอ่านหลายครั้ง, แจกจ่าย static content | ข้อมูลชั่วคราวที่ไม่ต้องอยู่ถาวร | ที่เก็บถาวรนอก instance สำหรับข้อมูลทุกแบบ |
| ตัวอย่างที่เหมาะ | ไฟล์สื่อ เสียง วิดีโอ รูป, ข้อมูลสำรอง, ข้อมูลเก็บถาวร, versioning | ไฟล์ตั้งค่า, scratch file, TempDB | cluster, ดิสก์บูต, log หรือข้อมูลของฐานข้อมูลเชิงพาณิชย์อย่าง Oracle, DB2 |
| ไม่เหมาะกับ | การค้นหาและ query | log หรือข้อมูลสำรองของฐานข้อมูล, ข้อมูลลูกค้า | ข้อมูลที่ไม่เปลี่ยน, เนื้อหาที่เปิดสู่เว็บ, ข้อมูลแบบ key-value |
| ตัวอย่างที่ไม่เหมาะ | ฐานข้อมูล, file system | ไดรฟ์ที่แชร์กัน, ข้อมูลอ่อนไหว | การแจกจ่ายเนื้อหา |

TempDB คือฐานข้อมูลชั่วคราวที่ SQL Server สร้างใหม่ทุกครั้งที่เปิด จึงไม่เสียหายถ้าหายไป

สไลด์ไม่ได้บอกว่างานแบบไหนเหมาะกับ RDS หรือ DynamoDB

ทั้งตารางสรุปได้ด้วยคำถามสามข้อ ข้อมูลต้องอยู่ต่อหลังเครื่องหายไหม โปรแกรมต้องแก้มันทีละส่วนไหม และมันถูกอ่านโดยคนจำนวนมากผ่านเครือข่ายไหม

<Quiz question="ชมรมจะรัน PostgreSQL เก็บข้อมูลสมาชิก ยอดไลก์ และคอมเมนต์ ควรวางไฟล์ของฐานข้อมูลไว้ที่ไหน">
ฐานข้อมูลเขียนทับทีละ block กลางไฟล์ตลอดเวลา จึงต้องการ POSIX ซึ่งตัด S3 ออก ข้อมูลสมาชิกต้องอยู่ต่อแม้เครื่องหาย ซึ่งตัด instance store ออก ตาราง "งานแบบไหนควรอยู่ที่ไหน" ก็ระบุว่า instance store ไม่เหมาะกับข้อมูลลูกค้าและ log ของฐานข้อมูล

คำตอบคือ **EBS** แล้วใช้ snapshot สำรองข้อมูลไว้ใน S3

คำตอบที่ผิดบ่อยคือ "instance store เพราะเร็วที่สุด" ความเร็วไม่ช่วยถ้าเครื่องถูกหยุดหรือดิสก์เสียแล้วข้อมูลสมาชิกหายหมด ส่วนอีกคำตอบคือ "S3 เพราะทนที่สุด" ซึ่งทำให้ทุกการแก้ต้องส่งไฟล์ทั้งก้อนใหม่
</Quiz>

<Quiz question="ชมรมจะรัน web proxy ที่เก็บ cache ของรูปที่ถูกเปิดบ่อย ไว้ส่งให้ผู้ใช้เร็วขึ้น ควรเก็บ cache ไว้ที่ไหน">
cache คือสำเนาของรูปที่มีตัวจริงอยู่ใน S3 แล้ว ถ้าหายไป proxy ก็ดึงใหม่ได้ ข้อมูลนี้จึงไม่ต้องถาวร สิ่งที่ต้องการคือความเร็ว ซึ่ง instance store ให้มากที่สุด และไม่คิดเงินเพิ่ม

คำตอบคือ **instance store** ตรงกับแถว "ข้อมูลชั่วคราวที่ไม่ต้องอยู่ถาวร" ในตาราง

คำตอบที่ผิดบ่อยคือ "EBS เพราะปลอดภัยกว่า" ซึ่งจ่ายเงินและเสียความเร็วไปกับความทนทานที่ข้อมูลนี้ไม่ต้องใช้
</Quiz>

<Recap>

**ดิสก์ของ EC2**

- instance store อยู่บน host: เร็วมาก ฟรี สำเนาเดียว หายไปพร้อม instance, AMI แบบนี้หยุดเครื่องไม่ได้
- EBS ต่อผ่านเครือข่าย, primary + replica ใน AZ เดียว, AFR 0.1–0.2%, ต่อ instance ได้ทีละตัว (เว้น io1/io2 ที่เปิด Multi-Attach)
- terminate แล้ว EBS root ถูกลบตามค่าเริ่มต้น EBS ตัวอื่นอยู่ต่อ
- snapshot เก็บ EBS ลง S3: ย้ายข้าม AZ, สำรอง, แชร์ — incremental, zero block compression, lazy loading

**เลือกที่เก็บ**

- รูปและไฟล์สื่อ → S3, ฐานข้อมูล → EBS + snapshot, cache และไฟล์ชั่วคราว → instance store
