## ส่วนที่ 1 — ทำไมที่เก็บข้อมูลแบบเดิมโตตามไม่ทัน

<Why>
ตอนแอปเพิ่งเปิด รูปทั้งหมดอยู่บนดิสก์ของเซิร์ฟเวอร์เครื่องเดียวก็พอ พอสมาชิกเพิ่มเป็นหลักพัน ดิสก์เต็ม ใส่ดิสก์เพิ่มได้อีกไม่กี่ลูกก็เต็มช่องของเครื่อง แล้วเครื่องที่สองที่เพิ่งซื้อมาช่วยรับโหลดก็มองไม่เห็นรูปบนเครื่องแรก
</Why>

ที่เก็บข้อมูลแบบเดิมมีสามแบบ แต่ละแบบแก้ปัญหาของแบบก่อนหน้า แล้วสร้างปัญหาใหม่ของตัวเอง

| แบบ | ต่อกับเครื่องยังไง | ติดตรงไหน |
| --- | --- | --- |
| <Term en="DAS (Direct Attached Storage)" th="ดิสก์ที่เสียบตรงกับเครื่อง" /> | hard disk หรือ SSD เสียบอยู่ในเซิร์ฟเวอร์ | **ขยายไม่ได้** ดิสก์เป็นของเครื่องเดียว และเพิ่มได้เท่าจำนวนช่องที่มี |
| <Term en="NAS (Network Attached Storage)" th="กล่องดิสก์ที่แชร์ผ่านเครือข่าย" /> | กล่องที่มีดิสก์หลายลูก ต่อสาย Ethernet และรัน network file system ให้หลายเครื่องใช้ไฟล์ร่วมกัน | **ช้า** ทุกการอ่านเขียนวิ่งผ่านกล่องเดียวและผ่านเครือข่าย |
| <Term en="SAN (Storage Area Network)" th="เครือข่ายเฉพาะสำหรับดิสก์" /> | ตู้ดิสก์หลายลูก ต่อผ่านเครือข่ายเฉพาะที่เรียกว่า Fibre Channel | **แพงเกินกว่าจะขยาย** และ **ผูกกับผู้ขายรายเดียว** (vendor lock-in) |

SAN เร็วเพราะมีเครือข่ายของตัวเองแยกจากเครือข่ายปกติ แต่ความเร็วนั้นมากับอุปกรณ์เฉพาะทั้งชุด พอจะขยายก็ต้องซื้อของรุ่นเดียวกันจากเจ้าเดิม เพราะเครื่องมือจัดการของแต่ละเจ้าใช้กับของเจ้าอื่นไม่ได้

### Software-defined storage คืออะไร

<Term en="Software-Defined Storage" th="ที่เก็บข้อมูลที่สั่งด้วยซอฟต์แวร์" /> หรือ SDS คือการกำหนดที่เก็บข้อมูลด้วยซอฟต์แวร์ แล้วให้ระบบจัดสรรให้อัตโนมัติ แบบเดียวกับที่ server virtualization ทำกับเครื่อง และที่ SDN ทำกับเครือข่าย

แนวคิดนี้มีสองด้าน

**ด้านแรก แยกที่เก็บข้อมูลที่ผู้ใช้มองเห็นออกจากฮาร์ดแวร์จริงข้างล่าง** ผู้ใช้ขอพื้นที่ 100 GB โดยไม่ต้องรู้ว่าอยู่บนดิสก์ลูกไหน ซอฟต์แวร์จึงทำสี่อย่างที่ฮาร์ดแวร์เดี่ยว ๆ ทำไม่ได้

- **รวมดิสก์ข้ามผู้ขาย** เป็นกองเดียว (cross-vendor resource pooling)
- **กระจายข้อมูล** ไว้บนหลายเครื่อง (distributed storage)
- **ขยายได้มาก** ด้วยการเพิ่มเครื่อง (highly scalable)
- **เก็บข้อมูลเป็น object** คือเป็นก้อนที่เรียกด้วยชื่อ แทนไฟล์ในโฟลเดอร์ (object stores) ซึ่งส่วนที่ 2 จะอธิบาย

**ด้านที่สอง สั่งงานอัตโนมัติและจัดการข้ามผู้ขายได้** ทำได้แบบเดียวกับ SDN ที่แยก control plane ออกจาก data plane และใช้โปรโตคอลควบคุมแบบเปิด ทวนเรื่องนี้ได้ที่ส่วนที่ 6 ของ [Lecture 1](/2110506-sds/lecture-1)

เมื่อใช้กับที่เก็บข้อมูล control plane คือซอฟต์แวร์ที่ตัดสินว่าข้อมูลก้อนนี้ไปอยู่ดิสก์ไหน มีกี่สำเนา และใครเข้าถึงได้ ส่วน data plane คือดิสก์ที่อ่านเขียนข้อมูลจริง

ในทางปฏิบัติ SDS บางครั้งก็เป็น **ฮาร์ดแวร์ราคาถูกทั่วไป** (commodity hardware) ที่ซอฟต์แวร์ทำให้ฉลาดขึ้น เร็วขึ้น และจัดการง่ายขึ้น ไม่ใช่ตู้ดิสก์ราคาแพงของผู้ขายรายเดียว

S3 ในหน้านี้ และ EBS ใน [Lecture 8.2](/2110506-sds/lecture-8-2) คือ SDS แบบนี้ คุณขอพื้นที่ด้วยการกดหรือเรียก API แล้วซอฟต์แวร์ของ AWS เลือกดิสก์ให้ คุณไม่เคยเห็นยี่ห้อของดิสก์เลย

<KeyIdea>
DAS ขยายไม่ได้ NAS ช้า SAN แพงและผูกผู้ขาย SDS แก้ด้วยการให้ซอฟต์แวร์คั่นกลางระหว่างผู้ใช้กับดิสก์ ผู้ใช้ขอพื้นที่เป็นตัวเลข แล้วซอฟต์แวร์รวมดิสก์ราคาถูกจำนวนมากให้ทำงานเหมือนที่เก็บก้อนเดียว
</KeyIdea>

## ส่วนที่ 2 — block storage กับ object storage

<Why>
ฐานข้อมูลของอัลบั้มชมรมเป็นไฟล์ขนาด 10 GB เมื่อมีคนกดไลก์รูปหนึ่งรูป ฐานข้อมูลต้องแก้ตัวเลขยอดไลก์ ซึ่งอยู่ในก้อนขนาด 8 KB ตรงกลางไฟล์

ถ้าไฟล์อยู่บนดิสก์ปกติ โปรแกรมกระโดดไปตำแหน่งนั้นแล้วเขียนทับ 8 KB ก็จบ แต่ถ้าไฟล์อยู่ใน S3 ไม่มีคำสั่งให้แก้กลางไฟล์ วิธีเดียวคือส่งไฟล์ใหม่ทั้ง 10 GB ขึ้นไปแทน ทุกครั้งที่มีคนกดไลก์
</Why>

<Term en="POSIX" th="มาตรฐานคำสั่งไฟล์ของระบบตระกูล Unix" /> คือมาตรฐานที่กำหนดว่าโปรแกรมทำอะไรกับไฟล์ได้บ้าง เช่น เปิดไฟล์ กระโดดไปตำแหน่งที่ต้องการ เขียนทับ ต่อท้าย และเปลี่ยนชื่อ ที่เก็บที่ "POSIX-compliant" รองรับคำสั่งพวกนี้ครบ โปรแกรมเดิมจึงใช้มันได้ทันทีเหมือนดิสก์ในเครื่อง

<Figure number={1} caption="block storage ยอมให้เขียนทับแค่ block เดียวกลางไฟล์ ส่วน object storage แก้ได้ทีละทั้ง object">
  <BlockVsObject />
</Figure>

<Term en="Block storage" th="ที่เก็บที่ OS เห็นเป็นดิสก์" /> คือที่เก็บที่ระบบปฏิบัติการเห็นเป็นดิสก์ลูกหนึ่ง แบ่งเป็นก้อนขนาดเท่ากันเรียกว่า block ระบบปฏิบัติการวาง file system ลงไป แล้วโปรแกรมใช้คำสั่ง POSIX กับไฟล์บนนั้น EBS และ instance store เป็นแบบนี้

<Term en="Object storage" th="ที่เก็บข้อมูลเป็นก้อนเรียกด้วยชื่อ" /> คือที่เก็บที่รับข้อมูลทั้งก้อนพร้อมชื่อหนึ่งชื่อ แล้วคืนทั้งก้อนเมื่อขอด้วยชื่อนั้น คุยกันผ่าน HTTP ไม่ใช่ผ่าน file system ของเครื่อง S3 เป็นแบบนี้

ที่เก็บข้อมูลบน AWS แบ่งได้สามกลุ่ม และคลาวด์เจ้าอื่นก็มีตัวเลือกแบบเดียวกัน

| กลุ่ม | บริการ | POSIX |
| --- | --- | --- |
| Block store | EC2 instance store (ดิสก์บนเครื่อง ข้อมูลไม่ถาวร), EBS (Elastic Block Store) | ใช่ |
| Object store | S3 (Simple Storage Service) | ไม่ใช่ |
| คล้ายฐานข้อมูล | RDS, Redshift, DynamoDB | — |

เส้นแบ่งที่สำคัญที่สุดของทั้งหน้าคือคอลัมน์ POSIX

กลุ่มที่สามคือบริการที่เก็บข้อมูลให้ แต่เราคุยกับมันด้วยภาษาของฐานข้อมูล ไม่ใช่ในรูปไฟล์หรือ object

| บริการ | คืออะไร |
| --- | --- |
| RDS (Relational Database Service) | ฐานข้อมูลเชิงสัมพันธ์ เช่น MySQL ที่ AWS ติดตั้งและดูแลให้ |
| Redshift | data warehouse สำหรับวิเคราะห์ข้อมูลปริมาณมาก |
| DynamoDB | ฐานข้อมูลแบบ key-value ที่ AWS ดูแลให้ |

<Quiz question="แอปของชมรมเขียน log ต่อท้ายไฟล์ทีละบรรทัดทุกวินาที ถ้าเก็บ log ทั้งวันไว้เป็น object เดียวใน S3 จะเกิดอะไรขึ้น">
bucket ทั่วไปของ S3 ไม่มีคำสั่งต่อท้าย object ที่มีอยู่แล้ว มีแค่คลาสพิเศษ S3 Express One Zone ที่ต่อท้ายได้ การเพิ่มบรรทัดหนึ่งบรรทัดจึงต้องส่ง object ใหม่ทั้งก้อนขึ้นไปแทนของเดิม ตอนเที่ยงคืน object ยังเล็ก แต่ตอนเย็น log ยาวทั้งวัน ทุกวินาทีต้องส่ง log ทั้งหมดซ้ำ

คำตอบคือ **เปลืองขึ้นเรื่อย ๆ จนใช้ไม่ได้** log ที่เขียนต่อท้ายตลอดเวลาควรเขียนลงดิสก์ block storage แล้วค่อยส่งเข้า S3 เป็นไฟล์ละชั่วโมงหรือไฟล์ละวัน

คำตอบที่ผิดบ่อยคือ "ไม่มีปัญหา เพราะต่อท้ายไม่ได้แก้ของเดิม" ซึ่งคิดแบบ file system การต่อท้ายต้องใช้คำสั่ง append ของ POSIX และ bucket ทั่วไปของ S3 ไม่มีคำสั่งนั้น
</Quiz>

## ส่วนที่ 3 — S3 เก็บ object ด้วย key

ชมรมจะเก็บรูปแมวหนึ่งรูปใน S3 ต้องบอก S3 สองอย่าง คือเก็บไว้กลุ่มไหน และเรียกรูปนี้ด้วยชื่ออะไร

- <Term en="Bucket" th="ถังที่ใส่ object" /> คือที่บรรจุ object จำนวนหนึ่ง
- คุณ **PUT** object ลงใน bucket และ **GET** object ออกมา
- แต่ละ object ถูกเรียกด้วย <Term en="Key" th="ชื่อของ object" /> ของมัน คู่ของ key กับข้อมูลจึงเรียกว่า key-value pair

ค่าที่เก็บเป็นอะไรก็ได้ S3 ไม่ดูข้างใน

| key | value |
| --- | --- |
| `myname` | ข้อความ `Kunwadee Sripanidkulchai` |
| `movie` | ไฟล์วิดีโอ `.mpg` ทั้งไฟล์ |

ในแอปของชมรม bucket ชื่อ `club-album` มี object ที่ key `photos/cat.jpg` เก็บไฟล์รูปแมวหนึ่งรูป

### ทุก object มี URL

object ทุกตัวเรียกได้ด้วย URL มาตรฐานรูปแบบ `https://s3.amazonaws.com/BucketName/ObjectName` รูปแมวของชมรมจึงอยู่ที่

```
https://s3.amazonaws.com/club-album/photos/cat.jpg
```

S3 คุยด้วย <Term en="REST" th="รูปแบบ API ที่ส่งคำขอผ่าน HTTP" /> interface ที่เป็นมาตรฐาน เครื่องมือเขียนโปรแกรมบนอินเทอร์เน็ตตัวไหนก็เรียกได้ การดาวน์โหลดใช้ HTTP เป็นค่าเริ่มต้น

ระบบออกแบบให้เพิ่มโปรโตคอลอื่นได้ง่าย ตัวอย่างคือในช่วงที่ทำสไลด์ S3 มีช่องทาง BitTorrent ไว้ลดค่าใช้จ่ายเวลาแจกไฟล์ให้คนจำนวนมาก เพราะผู้ดาวน์โหลดส่งชิ้นส่วนของไฟล์ให้กันเอง ข้อมูลที่ต้องออกจาก S3 จึงน้อยลง

<Pitfall>
"ชื่อ bucket ตั้งอะไรก็ได้ เหมือนตั้งชื่อโฟลเดอร์ในเครื่องตัวเอง" ไม่จริง

ความเชื่อนี้ดูถูก เพราะ bucket อยู่ในบัญชี AWS ของเรา และคนอื่นมองไม่เห็นของในนั้น

แต่ **ชื่อ bucket ใช้ร่วมกันทั้งระบบ** ทุกบัญชีของทุกคนอยู่ใน namespace เดียวกัน เหตุผลอยู่ใน URL ข้างบน ซึ่งมีแค่ชื่อ bucket กับ key ไม่มีชื่อบัญชีอยู่เลย ถ้าใครในโลกสร้าง `club-album` ไปก่อน ชมรมของคุณจะสร้างชื่อนี้ไม่ได้
</Pitfall>

### ขนาด region และการเข้าถึง

**ขนาด** object หนึ่งตัวมีได้ตั้งแต่ 0 byte ถึง 5 TB และเก็บกี่ object ก็ได้ไม่จำกัด key ที่นักพัฒนาตั้งเองต้องไม่ซ้ำกันภายใน bucket บัญชีหนึ่งมี bucket ได้ 100 ตัว ตามขีดจำกัดในช่วงที่ทำสไลด์ (ปัจจุบันค่าเริ่มต้นคือ 10,000 ตัว)

<Term en="Region" th="กลุ่ม data center ในพื้นที่หนึ่ง" /> คือพื้นที่ทางภูมิศาสตร์ที่ AWS ตั้ง data center ไว้ เช่น สิงคโปร์ bucket หนึ่งตัวอยู่ใน region เดียวที่คุณเลือก และเลือกได้จากสามเหตุผล

- **latency** — region ที่ใกล้ผู้ใช้ตอบเร็วกว่า
- **ค่าใช้จ่าย** — ราคาแต่ละ region ไม่เท่ากัน
- **กฎหมาย** — บางองค์กรถูกบังคับให้เก็บข้อมูลไว้ในบางประเทศ

ข้อมูลใน region หนึ่งจะไม่ออกจาก region นั้น นอกจากคุณสั่งโอนออกเอง ข้อนี้ทำให้เหตุผลข้อสามใช้ได้จริง

**ความทนทาน** S3 ออกแบบให้ทนทาน (durability) ใน region ได้ 99.999999999% (เลข 9 สิบเอ็ดตัว) ต่อ object ต่อปี แปลว่าถ้าเก็บ 10,000,000 object คาดว่าจะหายราวหนึ่ง object ในทุก 10,000 ปี และยังสั่งให้ทำสำเนาข้ามไปอีก region ได้ด้วย

ราคาของความทนทานนี้คือความเร็ว S3 ช้ากว่าดิสก์ในเครื่อง เพราะทุกคำขอวิ่งผ่านเครือข่าย

**การเข้าถึง** S3 มีกลไกยืนยันตัวตนกันคนที่ไม่มีสิทธิ์ object แต่ละตัวตั้งเป็น private หรือ public ก็ได้ และให้สิทธิ์เฉพาะผู้ใช้บางคนก็ได้

**Versioning** S3 เก็บหลายรุ่นของ object ที่ key เดียวกันได้ ส่วนที่ 4 จะดูว่าเปิดใช้ยังไงและช่วยอะไร

<Quiz question="สมาชิกคนหนึ่งอัปโหลดรูปใหม่ด้วย key เดิม photos/cat.jpg ลงใน bucket ที่ยังไม่ได้เปิด versioning รูปแมวรูปเดิมเป็นยังไง">
PUT คือการส่งค่าทั้งก้อนเข้าไปผูกกับ key หนึ่งตัว key `photos/cat.jpg` ผูกกับค่าได้ทีละค่า PUT ครั้งใหม่จึงแทนค่าเดิมทั้งก้อน

คำตอบคือ **รูปเดิมหายไป** URL เดิมจะได้รูปใหม่แทน ถ้าเปิด versioning ไว้ S3 จะเก็บรูปเดิมเป็นรุ่นก่อนหน้าให้กู้คืนได้

คำตอบที่ผิดบ่อยคือ "S3 ตั้งชื่อใหม่เป็น cat (1).jpg ให้เอง" ซึ่งเป็นพฤติกรรมของโปรแกรมจัดการไฟล์บนเครื่อง S3 ไม่ตั้งชื่อให้ เพราะ key คือสิ่งที่นักพัฒนากำหนดเอง
</Quiz>

## ส่วนที่ 4 — สร้าง bucket และอ่านบิลของ S3

### ลำดับการใช้งาน

การใช้ S3 ครั้งแรกเดินตามลำดับนี้

1. สมัครใช้ Amazon S3
2. สร้าง bucket
3. เพิ่ม object ลงใน bucket
4. เปิดดู object
5. ย้าย object
6. ลบ object แล้วลบ bucket

ในช่วงที่ทำสไลด์ บัญชีใหม่ได้ใช้ฟรีตาม AWS Free Usage Tier ทุกเดือนเป็นเวลาหนึ่งปี ได้พื้นที่ S3 standard storage 5 GB, GET 20,000 ครั้ง, PUT 2,000 ครั้ง และส่งข้อมูลออก 15 GB

### ค่าที่ต้องเลือกตอนสร้าง bucket

หน้า **Create bucket** ใน AWS Console ถามค่าตามลำดับนี้

**ชื่อและ region** ชื่อ bucket ต้องไม่ซ้ำกับใครใน namespace ของทั้งระบบ และต้องตามกฎการตั้งชื่อ จากนั้นเลือก AWS Region เช่น `us-west-1` ถ้ามี bucket อยู่แล้ว จะคัดลอกค่าตั้งจาก bucket นั้นมาใช้ก็ได้

สิทธิ์ใน S3 กำหนดได้สองทาง <Term en="ACL (Access Control List)" th="รายการว่าใครทำอะไรกับของชิ้นนี้ได้" /> คือรายการที่ติดกับ bucket หรือ object แต่ละตัว ว่าบัญชี AWS ไหน หรือกลุ่มอย่างทุกคนบนอินเทอร์เน็ต ทำอะไรกับมันได้ ส่วน bucket policy คือกฎสิทธิ์ที่ผูกกับ bucket และใช้กับ object ในนั้นทั้งหมดหรือบางส่วน

**Object Ownership** มีสองแบบ แบบที่แนะนำคือ **ACLs disabled** ทุก object ใน bucket เป็นของบัญชีเจ้าของ bucket และสิทธิ์ถูกกำหนดด้วย policy อย่างเดียว อีกแบบคือ **ACLs enabled** ให้บัญชี AWS อื่นเป็นเจ้าของ object ที่ตัวเองเขียนลงมาได้ และกำหนดสิทธิ์ทีละ object ด้วย ACL

**Block Public Access** ช่อง **Block all public access** ถูกติ๊กไว้เป็นค่าเริ่มต้น และ AWS แนะนำให้เปิดไว้ ช่องนี้ปิดทุกทางที่จะทำให้ bucket หรือ object กลายเป็น public ถ้าแอปต้องการ public จริง ค่อยปลดทีละข้อ

<Detail label="สี่ข้อย่อยของ Block all public access">
ติ๊กช่องใหญ่เท่ากับติ๊กสี่ข้อนี้พร้อมกัน แต่ละข้อทำงานแยกกัน

| ข้อ | ทำอะไร |
| --- | --- |
| บล็อก ACL ใหม่ | ไม่ยอมให้ตั้ง ACL ใหม่ที่เปิด public ค่าที่ตั้งไว้ก่อนแล้วไม่ถูกแตะ |
| บล็อก ACL ทุกตัว | ไม่สนใจ ACL ใดก็ตามที่ให้สิทธิ์ public |
| บล็อก policy ใหม่ | ไม่ยอมให้ตั้ง bucket policy หรือ access point policy ใหม่ที่เปิด public |
| บล็อก policy ทุกตัว | ถ้า bucket หรือ access point มี policy ที่เปิด public จะไม่สนใจทั้งการเข้าถึงแบบ public และจากบัญชีอื่น |

สิทธิ์ public ให้ได้สามทาง คือ ACL, bucket policy และ access point policy สี่ข้อนี้จึงครอบทั้ง ACL และ policy ทั้งของใหม่และของเก่า
</Detail>

**Bucket Versioning** ปิดไว้เป็นค่าเริ่มต้น ถ้าเปิด S3 จะเก็บทุกรุ่นของทุก object ไว้ใน bucket เดียวกัน คุณเรียกดูและกู้คืนรุ่นไหนก็ได้ จึงกู้ได้ทั้งตอนผู้ใช้ลบหรือเขียนทับพลาด และตอนแอปทำงานผิด

**Tags** ป้ายชื่อที่ติดกับ bucket ไว้แยกค่าใช้จ่ายและจัดกลุ่ม bucket ใส่หรือไม่ใส่ก็ได้

**Default encryption** S3 เข้ารหัส object ใหม่ทุกตัวฝั่งเซิร์ฟเวอร์ให้อัตโนมัติ คุณเลือกได้ว่าจะใช้กุญแจของใคร ค่าเริ่มต้นคือ SSE-S3 ที่ S3 จัดการกุญแจให้เอง

<Detail label="สามแบบของ server-side encryption">
| แบบ | กุญแจมาจากไหน |
| --- | --- |
| SSE-S3 | S3 สร้างและดูแลกุญแจให้ (ค่าเริ่มต้น) |
| SSE-KMS | กุญแจอยู่ใน AWS Key Management Service ซึ่งคุณกำหนดสิทธิ์และดูประวัติการใช้กุญแจได้ |
| DSSE-KMS | เข้ารหัสสองชั้นด้วยกุญแจจาก KMS คิดราคาแยกต่างหาก |

**Bucket Key** ใช้กับ SSE-KMS เพื่อลดจำนวนครั้งที่ S3 ต้องเรียก KMS ค่าใช้จ่ายการเข้ารหัสจึงลดลง ใช้กับ DSSE-KMS ไม่ได้
</Detail>

**Object Lock** อยู่ใน Advanced settings และปิดไว้เป็นค่าเริ่มต้น ถ้าเปิด object จะถูกเก็บแบบ <Term en="WORM (write-once-read-many)" th="เขียนได้ครั้งเดียว อ่านได้หลายครั้ง" /> ห้ามลบหรือเขียนทับเป็นระยะเวลาที่กำหนด หรือตลอดไป ถ้าไม่เปิด Object Lock ต่อให้ S3 เหมาะกับข้อมูลที่เขียนครั้งเดียวแล้วอ่านหลายครั้ง object ทุกตัวก็ยังถูก PUT ทับหรือ DELETE ได้ทุกเมื่อ

<Quiz question="ชมรมอยากให้หน้าเว็บแสดงรูปด้วย URL ของ S3 ตรง ๆ ตอนสร้าง bucket ทุกช่องถูกปล่อยไว้ตามค่าเริ่มต้น คนนอกที่เปิดหน้าเว็บจะเห็นรูปไหม">
ค่าเริ่มต้นติ๊ก **Block all public access** ไว้ object ทุกตัวจึงเป็น private ต่อให้ URL ถูกต้อง S3 ก็ตรวจสิทธิ์ก่อนส่งของ และคนที่ไม่ได้ยืนยันตัวตนไม่ผ่าน

คำตอบคือ **ไม่เห็น** ต้องปลด Block Public Access แล้วให้สิทธิ์อ่านแบบ public กับรูปที่ต้องการแสดงก่อน

คำตอบที่ผิดบ่อยคือ "เห็น เพราะทุก object มี URL" ซึ่งเอาการมีที่อยู่ไปปนกับการมีสิทธิ์ URL บอกแค่ว่าของอยู่ที่ไหน ไม่ได้บอกว่าใครเปิดได้
</Quiz>

put_cost = puts / 1000 * 0.005
get_cost = gets / 10_000 * 0.004
transfer = max(0, out_gb - 1) * 0.12
total = storage + put_cost + get_cost + transfer
print(out_gb, storage, put_cost, get_cost, transfer, total)

## ส่วนที่ 5 — ระบบจริงที่วางอยู่บน S3

S3 ถูกใช้ทำงานห้าแบบ และระบบใหญ่อย่าง Dropbox กับ Netflix ก็วางอยู่บน S3

- แชร์สื่อ เช่น รูปและวิดีโอ
- แชร์ไฟล์
- เป็นที่เก็บไฟล์ใหญ่ของเว็บไซต์ ที่ส่งให้ผู้ชมโดยไม่ต้องประมวลผล (static web content)
- สำรองข้อมูล
- ต่อกับบริการอื่น เช่น ระบบ big data

### Dropbox แยกเนื้อไฟล์ออกจากข้อมูลเกี่ยวกับไฟล์

<Why>
ผู้ใช้ Dropbox เห็นโฟลเดอร์ ชื่อไฟล์ และวันที่แก้ล่าสุด เหมือนดิสก์ในเครื่อง แต่ object storage ไม่มีโฟลเดอร์จริงและแก้ไฟล์บางส่วนไม่ได้ ระบบจึงต้องเก็บ "ข้อมูลเกี่ยวกับไฟล์" แยกไว้อีกที่หนึ่ง
</Why>

<Figure number={2} caption="Dropbox เก็บเนื้อไฟล์กับข้อมูลเกี่ยวกับไฟล์ไว้บนเซิร์ฟเวอร์คนละชุด">
  <DropboxSplit />
</Figure>

ระบบแบ่งเป็นสองฝั่ง

**ฝั่งเนื้อไฟล์** storage servers เก็บเนื้อไฟล์เป็น block ที่เข้ารหัสแล้ว เครื่องของผู้ใช้ไม่ได้คุยกับมันตรง ๆ แต่ผ่าน processing servers ซึ่งทำงานเข้ารหัส และให้บริการเปิดไฟล์กับแชร์ไฟล์ให้คนอื่น

**ฝั่งข้อมูลเกี่ยวกับไฟล์** metadata servers เก็บ <Term en="Metadata" th="ข้อมูลที่บอกเรื่องของข้อมูลอีกที" /> เช่น ชื่อไฟล์ ตำแหน่ง `/files/work` เวลาแก้ล่าสุด และชนิดไฟล์ แต่ไม่เก็บตัวไฟล์ ข้อมูลนี้อยู่ใน database ของ metadata servers และเวลาแก้ล่าสุดคือค่าที่ใช้ตอน sync

**Notification service** แจ้งเครื่องของผู้ใช้เมื่อมีไฟล์ถูกเพิ่ม แก้ หรือลบ

**ชั้น SSL** เข้ารหัสการสื่อสารสามเส้น คือเครื่องผู้ใช้กับ processing servers, เครื่องผู้ใช้กับ metadata servers และ storage servers กับ processing servers

ผลคือเมื่อคุณแก้ไฟล์บนโน้ตบุ๊ก เนื้อไฟล์ใหม่ไปลงฝั่ง storage ข้อมูลเกี่ยวกับไฟล์ถูกบันทึกใน metadata แล้ว notification service แจ้งมือถือของคุณ มือถือจึงรู้ว่าต้องดึงไฟล์ไหนมาใหม่ รายละเอียดเพิ่มเติมอยู่ที่ [dropbox.com/en/help/1968](https://www.dropbox.com/en/help/1968)

<Quiz question="ในระบบที่แยกแบบรูปที่ 2 ผู้ใช้เปลี่ยนชื่อไฟล์วิดีโอขนาด 2 GB ระบบต้องส่งอะไรไปที่ storage servers บ้าง">
ชื่อไฟล์อยู่ใน metadata ไม่ได้อยู่ในเนื้อไฟล์ การเปลี่ยนชื่อจึงแก้แค่ช่องชื่อและเวลาแก้ล่าสุดใน metadata service แล้ว notification service แจ้งเครื่องอื่นของผู้ใช้ เนื้อไฟล์ 2 GB ไม่เปลี่ยนเลย

คำตอบคือ **ไม่ต้องส่งเนื้อไฟล์ไปที่ storage servers เลย** สิ่งที่เปลี่ยนมีแค่ metadata

คำตอบที่ผิดบ่อยคือ "ต้องอัปโหลด 2 GB ใหม่ทั้งก้อน" ซึ่งคิดว่าชื่อเป็นส่วนหนึ่งของไฟล์ ในรูปที่ 2 ชื่ออยู่ฝั่ง metadata การแยกสองฝั่งจึงทำให้การเปลี่ยนชื่อไม่ต้องแตะเนื้อไฟล์
</Quiz>

### Netflix ใช้ S3 เป็นศูนย์กลางของข้อมูล

Netflix ใช้ S3 เป็น **data hub** ของระบบ big data ทั้งหมด ข้อมูลไหลเข้าจากสองทาง คือ event จากเซิร์ฟเวอร์จำนวนมากที่ส่งผ่าน Kafka และข้อมูลที่ดึงออกมาจากฐานข้อมูล Cassandra

จากนั้นเครื่องมือประมวลผลหลายตัวอ่านและเขียนกลับลง S3 ที่เดียวกัน และเครื่องมือทำรายงานดึงผลไปแสดง

<Detail label="เครื่องมือแต่ละตัวในระบบของ Netflix ทำอะไร">
| หน้าที่ | เครื่องมือ |
| --- | --- |
| พาข้อมูลเข้า S3 | Kafka (ระบบส่งข้อความ), Aegisthus (ดึงข้อมูลออกจาก Cassandra) |
| ประมวลผลข้อมูลใน S3 | Hadoop และ Spark (ระบบประมวลผลข้อมูลบนหลายเครื่อง), Hive (SQL บน Hadoop), Pig (ภาษาสคริปต์บน Hadoop), Python |
| ค้นและวิเคราะห์ | Presto (query engine แบบ SQL), Druid (ฐานข้อมูลวิเคราะห์), Redshift |
| ทำรายงาน | MicroStrategy, Tableau |
</Detail>

<Term en="ETL (Extract, Transform, Load)" th="ดึงข้อมูล แปลง แล้วเก็บลงที่ใหม่" /> คืองานที่ดึงข้อมูลดิบออกมา แปลงให้อยู่ในรูปที่ใช้วิเคราะห์ได้ แล้วเก็บผลกลับลงที่เก็บ ตัวเลขของ data hub นี้มีดังนี้

| สิ่งที่วัด | ปริมาณ |
| --- | --- |
| ขนาดรวม | มากกว่า 60 PB ในมากกว่า 1.5 พันล้าน object |
| ข้อมูลใหม่ไหลเข้า (ingest) | มากกว่า 100 TB ต่อวัน |
| ETL อ่านออกไปประมวลผล | ประมาณ 3.5 PB ต่อวัน |
| ETL เขียนผลกลับเข้า hub | มากกว่า 500 TB ต่อวัน |
| ข้อมูลหมดอายุถูกลบ | มากกว่า 400 TB ต่อวัน |

ตัวเลขข้างบนแสดงว่างานหลักของ hub นี้คือ **การอ่าน** วันละราว 3.5 PB มากกว่าข้อมูลใหม่ที่ไหลเข้าราว 35 เท่า

<KeyIdea>
S3 เหมาะกับข้อมูลก้อนใหญ่ที่เขียนครั้งเดียวแล้วถูกอ่านซ้ำมาก ระบบที่ต้องการความรู้สึกแบบ file system อย่าง Dropbox จะเก็บชื่อ โฟลเดอร์ และสถานะการ sync ไว้ใน metadata service แยกต่างหาก แล้วใช้ที่เก็บแบบ object เก็บเฉพาะเนื้อไฟล์
</KeyIdea>

## ส่วนที่ 6 — ให้โปรแกรมเข้า AWS โดยไม่ทำ key หลุด

โปรแกรมเรียก S3 ผ่าน SDK ที่มีให้หลายภาษา

- Java — [UsingTheMPDotJavaAPI](https://docs.aws.amazon.com/AmazonS3/latest/dev/UsingTheMPDotJavaAPI.html)
- Ruby — [UsingTheMPRubyAPI](https://docs.aws.amazon.com/AmazonS3/latest/dev/UsingTheMPRubyAPI.html)
- Python (boto3) — [boto3 documentation](https://boto3.amazonaws.com/v1/documentation/api/latest/index.html)
- PHP — [UsingTheMPphpAPI](https://docs.aws.amazon.com/AmazonS3/latest/dev/UsingTheMPphpAPI.html)

ทุกคำขอที่โปรแกรมส่งไป AWS ต้องพิสูจน์ได้ว่ามาจากใคร สิ่งที่ใช้พิสูจน์คือ <Term en="Credentials" th="ข้อมูลที่ใช้พิสูจน์ตัวตน" />

credentials ที่ตั้งไว้ใช้กับ S3 มีกฎสองข้อ คือให้ credentials นั้น **ทำได้แค่งานที่เกี่ยวกับ S3** และ **เก็บเป็นความลับ ห้ามให้ใคร**

บัญชี AWS มี credentials ห้าแบบ ซึ่ง[ส่วนที่ 1 ของ Lecture 7.2](/2110506-sds/lecture-7-2#key-pair-และกุญแจอื่นของบัญชี-aws) อธิบายไว้แล้ว ส่วนนี้ใช้สามแบบ คือ root user, IAM user และ access key

<Detail label="credentials ห้าแบบใช้ทำอะไร">
| แบบ | ใช้ทำอะไร |
| --- | --- |
| Email และ password ของ account root user | เข้าหน้าเว็บของ AWS ในฐานะเจ้าของบัญชี |
| ชื่อผู้ใช้และ password ของ IAM user | เข้าหน้าเว็บของ AWS ในฐานะผู้ใช้คนหนึ่งในบัญชี |
| Multi-Factor Authentication (MFA) | รหัสชั้นที่สองจากอุปกรณ์ที่ถืออยู่ ใช้คู่กับ password |
| Access keys | ให้โปรแกรมเรียก AWS |
| Key pairs | คู่กุญแจที่ใช้ SSH เข้าเครื่อง EC2 |
</Detail>

### root user ล็อกเก็บไว้

<Term en="Account root user" th="ผู้ใช้เจ้าของบัญชี" /> คือตัวตนที่ล็อกอินด้วย email กับ password ที่ใช้สมัครบัญชี ใช้เข้า AWS Management Console, กระดานสนทนาของ AWS และ support center

credentials ของ root เป็น **root-level** คือเข้าถึงทุกอย่างในบัญชี รวมถึงเรื่องเงินและการจ่ายค่าบริการ AWS จึงแนะนำให้ล็อก root เก็บไว้ แล้วล็อกอินด้วย IAM user แทน

งานเกือบทั้งหมดทำด้วย IAM user ได้ ยกเว้นงานไม่กี่อย่างที่ AWS ระบุไว้ใน [tasks that require root](http://docs.aws.amazon.com/general/latest/gr/aws_tasks-that-require-root.html)

### IAM user คนละชุดสำหรับแต่ละคน

IAM (Identity and Access Management) ใช้เมื่อมีหลายคนหรือหลายแอปต้องเข้าบัญชี AWS เดียวกัน IAM user แต่ละตัวได้ credentials ชุดของตัวเองไม่ซ้ำกับใคร และคุณเปลี่ยนหรือถอนสิทธิ์ของ user คนไหนก็ได้ทุกเมื่อ

หลักในการให้สิทธิ์คือ <Term en="Least privilege" th="ให้สิทธิ์เท่าที่งานต้องใช้" /> คือให้แค่สิทธิ์ที่จำเป็นต่องานนั้น IAM user ที่ตั้งไว้ใช้กับ S3 จึงทำได้แค่งาน S3 ตามกฎข้างบน

### Access key คือกุญแจของโปรแกรม

<Term en="Access key" th="กุญแจให้โปรแกรมเรียก AWS" /> ใช้เรียก AWS จากโปรแกรม เพื่อยืนยันตัวตนของคุณและของแอป access key หนึ่งชุดมีสองส่วน

- **access key ID** เช่น `AKIAIOSFODNN7EXAMPLE`
- **secret access key** เช่น `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY`

access key ผูกกับ IAM user หนึ่งคน โปรแกรมที่ถือกุญแจชุดนี้จึงทำได้เท่าที่ user คนนั้นทำได้ ถ้า root มี access key ให้ลบทิ้ง หรือไม่สร้างตั้งแต่แรก แล้วสร้าง IAM user พร้อมสิทธิ์ที่จำเป็นไว้ใช้งานประจำวันแทน

<Pitfall>
"ใส่ access key ไว้ในโค้ดก็ได้ ยังไงก็แค่การบ้าน และมีแค่เราที่เห็นโค้ด" ไม่จริง

ความเชื่อนี้ดูถูก เพราะโค้ดรันได้ปกติ และตอนที่เขียนก็ไม่มีใครเห็นจริง ๆ

แต่โค้ดเดินทางเสมอ ทั้งตอน push ขึ้น GitHub ตอนส่งงาน และตอนแชร์ให้เพื่อนในกลุ่ม key ในโค้ดเดินทางไปด้วยทุกครั้ง ใครที่ได้ key ไปก็เรียก AWS ในนามของคุณได้ทันที และ AWS คิดเงินกับบัญชีของคุณ ทางที่ถูกคือเก็บ key ไว้ในไฟล์นอกโค้ด แล้วให้ SDK อ่านเอง
</Pitfall>

ไฟล์ที่ SDK อ่านคือ credentials profile file อยู่ที่ `~/.aws/credentials` บน Linux, macOS หรือ Unix และ `C:\Users\USERNAME\.aws\credentials` บน Windows ไฟล์มีหน้าตาแบบนี้

```ini
[default]
aws_access_key_id = your_access_key_id
aws_secret_access_key = your_secret_access_key
```

ถ้า boto3 (SDK ของ Python) หา credentials ไม่เจอจากที่ไหนเลย ทั้งไฟล์นี้และ environment variable จะหยุดด้วย `NoCredentialsError: Unable to locate credentials`

<Quiz question="ชมรมมีสมาชิกห้าคนที่ต้องอัปโหลดรูปผ่านสคริปต์ คนหนึ่งลาออกและยังถือ key อยู่ ระหว่างแจก access key ของ root ชุดเดียวให้ทั้งห้าคน กับสร้าง IAM user คนละตัว แบบไหนจัดการเรื่องนี้ได้">
ถ้าทั้งห้าคนใช้ key ของ root ชุดเดียว การกันคนที่ลาออกต้องเลิกใช้ key ชุดนั้น อีกสี่คนก็ใช้งานไม่ได้ไปด้วย และระหว่างนั้นคนที่ลาออกยังถือสิทธิ์ทั้งบัญชี รวมถึงเรื่องเงิน

ถ้าแต่ละคนมี IAM user ของตัวเอง คุณถอนสิทธิ์ของ user คนนั้นคนเดียว อีกสี่คนทำงานต่อได้ และเพราะทุก user ได้แค่สิทธิ์ S3 ตาม least privilege ความเสียหายระหว่างนั้นก็จำกัดอยู่ใน S3

คำตอบคือ **IAM user คนละตัว**

คำตอบที่ผิดบ่อยคือ "แบบไหนก็ได้ แค่เปลี่ยน key ใหม่แล้วส่งให้สี่คนที่เหลือ" ซึ่งทำได้กับ IAM user แต่กับ root ยังมีปัญหาว่าทุกคนถือสิทธิ์เต็มบัญชีอยู่ดี เพราะสิทธิ์ของ root จำกัดไม่ได้
</Quiz>


<Recap>

**Software-defined storage**

- DAS ขยายไม่ได้ NAS แบบเดิมช้า SAN แพงเกินกว่าจะขยายและผูกผู้ขายรายเดียว
- SDS แยกที่เก็บที่ผู้ใช้เห็นออกจากฮาร์ดแวร์ รวมดิสก์ข้ามผู้ขาย กระจายข้อมูล ขยายได้มาก และเก็บเป็น object
- สั่งงานอัตโนมัติด้วยการแยก control plane กับ data plane แบบ SDN บางครั้งใช้ commodity hardware

**Block กับ object**

- Block store (instance store, EBS) เป็น POSIX แก้ไฟล์ทีละส่วนได้ Object store (S3) ไม่ใช่ POSIX ต้อง PUT ทั้ง object
- กลุ่มคล้ายฐานข้อมูล: RDS, Redshift, DynamoDB

**S3**

- bucket บรรจุ object ที่เรียกด้วย key, PUT/GET, URL `https://s3.amazonaws.com/BucketName/ObjectName`
- ชื่อ bucket ใช้ร่วมกันทั้งระบบ, object 0 B – 5 TB, ไม่จำกัดจำนวน, 100 bucket ต่อบัญชี (ขีดจำกัดตอนทำสไลด์)
- เลือก region ตาม latency ราคา กฎหมาย ข้อมูลไม่ออกจาก region เอง, durability 11 nines
- REST/HTTP, BitTorrent (ตอนทำสไลด์), versioning, object เป็น private หรือ public
- ตอนสร้าง bucket: ACLs disabled, Block all public access, versioning, tags, encryption SSE-S3, Object Lock (WORM)
- บิลมีค่าเก็บ ค่าคำขอ และค่าส่งข้อมูลออก งานที่มีคนเปิดดูมาก ค่าส่งออกอาจแพงกว่าค่าเก็บหลายเท่า
- Dropbox แยก metadata ออกจากเนื้อไฟล์ Netflix ใช้ S3 เป็น data hub ขนาด 60+ PB

**Credentials**

- root ล็อกเก็บไว้, ใช้ IAM user คนละชุด, ให้สิทธิ์แบบ least privilege
- access key = access key ID + secret access key ผูกกับ IAM user, ไม่สร้าง access key ให้ root
- เก็บ key ใน `~/.aws/credentials` ไม่ใส่ในโค้ด

<Quiz question="เดือนนี้อัลบั้มชมรมยังเก็บรูป 200 GB และอัปโหลด 20,000 ครั้งเท่าเดิม แต่มีคนเปิดดูแค่ 10,000 ครั้ง รูปละ 2 MB ค่าส่วนไหนแพงที่สุด">
ข้อมูลออกสู่อินเทอร์เน็ตเหลือ 10,000 × 2 MB = 20 GB คิดเป็น (20 − 1) × $0.12 = $2.28 ค่าเก็บยังเป็น 200 × $0.025 = $5.00 เท่าเดิม ส่วน PUT $0.10 และ GET ราว $0.004

คำตอบคือ **ค่าเก็บ** $5.00 จากบิลรวมราว $7.38

คำตอบที่ผิดบ่อยคือ "ค่าส่งข้อมูลออก เพราะในบิลตัวอย่างมันกินไป 97.8%" ค่าส่งออกโตตามจำนวนครั้งที่คนเปิดดู ส่วนค่าเก็บโตตามขนาดของที่เก็บ งานที่นาน ๆ มีคนเปิดอย่างข้อมูลสำรองจึงจ่ายค่าเก็บเป็นหลัก
</Quiz>

<Quiz question="นิสิตคนหนึ่ง push โค้ดที่มี access key ขึ้น GitHub แบบ public แล้วรู้ตัวในห้านาที จึงลบ commit นั้นทิ้ง ถือว่าปลอดภัยแล้วไหม">
