## ส่วนที่ 1 — Multi-cloud: เมื่อคลาวด์เจ้าเดียวก็ล่มได้

### คลาวด์ใหญ่ก็ล่ม: สามเหตุการณ์จริง

<Why>
การย้ายขึ้นคลาวด์ส่งความเสี่ยงเรื่องเครื่องพังไปให้ผู้ให้บริการ แต่ผู้ให้บริการเองก็ล่มได้ และเมื่อล่ม ทุกแอปที่ฝากไว้ล่มพร้อมกัน
</Why>

<Term en="DDoS" th="การยิงคำขอจากหลายเครื่องพร้อมกันให้ระบบล่ม" /> คือการโจมตีที่ยิงคำขอมาจากหลายแหล่งพร้อมกัน

<Term en="failover" th="สลับไปใช้ของสำรองเมื่อตัวหลักล่ม" /> คือการเปลี่ยนไปใช้ทางสำรองแทนทางที่มีปัญหา

| เหตุการณ์ | เกิดอะไรขึ้น | ต้นเหตุ |
| --- | --- | --- |
| AWS, 13 มิถุนายน | ผู้ใช้ AWS console เจอ 404 Page Not Found และ 504 Gateway Timeout, error rate และ latency สูงขึ้น ราว 11:49 ถึง 15:37 PDT แก้เสร็จ 15:42 PDT | subsystem ที่ดูแล capacity ของ AWS Lambda มีปัญหา |
| Microsoft Azure, 30 กรกฎาคม 2024 | ล่มเป็นวงกว้าง แก้ด้วยการเปลี่ยน network config และ failover ไปเส้นทางเครือข่ายสำรอง | การโจมตีแบบ DDoS เป็นตัวจุดชนวน แต่ข้อผิดพลาดในระบบป้องกัน DDoS ของ Microsoft เองขยายผลแทนที่จะลด |
| Google Cloud กับ UniSuper, พฤษภาคม 2024 | private cloud ของ UniSuper ถูกลบ ล่มราวหนึ่งสัปดาห์ | input parameter ตัวหนึ่งถูกเว้นว่างตอนใช้เครื่องมือภายในสร้าง private cloud ระบบจึงใส่ค่าตั้งต้นเป็นอายุ 1 ปีโดยไม่มีใครรู้ ครบปีระบบก็ลบทิ้ง |

ผู้ใช้คนหนึ่งทวีตถึงเหตุการณ์นี้ว่า เราไม่รู้เลยว่าฝากไข่ไว้ในตะกร้าของ AWS มากแค่ไหน จนวันที่มันล่มแล้วพาระบบที่ใช้ทุกวันส่วนใหญ่ล่มไปด้วย

สามเหตุการณ์มีต้นเหตุต่างกัน คือ capacity, การโจมตีผสมบั๊กในระบบป้องกัน และค่าที่ถูกเว้นว่างตัวเดียว แต่ผลเหมือนกัน ทุกอย่างที่ฝากไว้กับเจ้านั้นหยุดพร้อมกัน

<Callout type="warn" title="ปีของเหตุการณ์ AWS">
เหตุการณ์ของ AWS ถูกจัดไว้ในกลุ่มเหตุล่มปี 2024 แต่ทวีตที่ยกมาลงวันที่ 14 มิถุนายน 2023 และสรุปเหตุการณ์ของ AWS เอง (เหตุการณ์ Lambda ใน region us-east-1) ระบุวันที่ 13 มิถุนายน 2023 ปีที่ถูกจึงน่าจะเป็น 2023
</Callout>

### Multi-cloud คืออะไร

<Term en="Multi-cloud" th="ใช้คลาวด์สาธารณะมากกว่าหนึ่งเจ้า" /> คือการใช้ Public Cloud A + Public Cloud B + … พร้อมกัน สิ่งที่ได้มีสองอย่าง

- **availability สูงขึ้น** — เจ้าหนึ่งล่ม อีกเจ้ายังรับงาน
- **agility** — เลือกใช้และย้ายงานไปเจ้าที่เหมาะกว่าได้ ไม่ติดอยู่กับเจ้าเดียว

<Term en="Availability" th="สัดส่วนเวลาที่ระบบใช้งานได้" /> วัดเป็นเปอร์เซ็นต์ของเวลาทั้งหมด ตัวเลขที่ดูใกล้ 100% ทุกตัว ต่างกันมากเมื่อแปลงเป็นชั่วโมงที่ล่ม

<Example title="แปลงเปอร์เซ็นต์เป็นชั่วโมงที่ล่ม">
ปีหนึ่งมี 8,760 ชั่วโมง ชั่วโมงที่ล่ม = (100% − availability) × 8,760 ตัวเลขชุดนี้มาจากการวัดเว็บจริงปี 2007–2008 (Sripanidkulchai et al., LADIS 2009)

| | availability | ล่มได้ต่อปี |
| --- | --- | --- |
| เว็บรายย่อยและขนาดเล็ก (เฉลี่ย) | 99.368% | 55.4 ชั่วโมง |
| SLA ของคลาวด์ชั้นนำในตอนนั้น | 99.95% | 4.4 ชั่วโมง |
| เว็บขององค์กรใหญ่ (เฉลี่ย) | 99.987% | 1.1 ชั่วโมง |

เว็บองค์กรอย่าง amazon.com, ebay.com และ walmart.com ล่มเฉลี่ยราวชั่วโมงเดียวต่อปี แต่คลาวด์สัญญาไว้แค่ไม่เกินราวสี่ชั่วโมง
</Example>

**ช่องว่างตรงนี้คือโจทย์** คลาวด์เจ้าเดียวพอสำหรับเว็บเล็ก แต่องค์กรที่ต้องการล่มไม่เกินชั่วโมงเดียวต่อปี จะพึ่ง SLA ของคลาวด์เจ้าเดียวไม่ได้

SLA ของแต่ละเจ้าเปลี่ยนไปตามเวลา ทั้งขึ้นและลง

| บริการ | SLA เดิม | SLA ใหม่ |
| --- | --- | --- |
| Amazon EC2 | 99.95% | 99.99% |
| Google App Engine | 99.95% | — |
| Microsoft Azure, Windows instance | 99.95% | 99.9% |
| Microsoft Azure, SQL | 99.9% | 99.99% |

ถึง 99.99% ก็ยังเท่ากับล่มได้ราว 53 นาทีต่อปี และ SLA เป็นคำสัญญา ไม่ใช่สิ่งที่กันไม่ให้ล่ม

<Example added title="สองคลาวด์ช่วยได้แค่ไหน">
ถ้าสองเจ้าล่มอย่างเป็นอิสระต่อกัน ระบบจะล่มก็ต่อเมื่อทั้งสองเจ้าล่มพร้อมกัน ผลคือเวลาล่มลดจากหลายชั่วโมงเหลือไม่กี่วินาที แต่ตัวเลขนี้ตั้งอยู่บนสมมติฐานว่าสองเจ้าไม่เคยล่มด้วยสาเหตุเดียวกัน

```
one cloud  : 99.95%                        downtime 4.38 h/yr
two clouds : 1 - 0.0005^2 = 99.999975%     downtime 7.9 s/yr
```
</Example>

<Pitfall>
"เก็บสำเนาไว้สองที่ก็ปลอดภัยแล้ว" ไม่จริงเสมอไป

ที่ดูเหมือนจริงเพราะสำเนาสองที่กันเหตุที่เกิดกับที่เดียวได้จริง เช่น ไฟดับหรือไฟไหม้

แต่สำเนาช่วยได้เฉพาะเมื่อของเสียทีละที่ UniSuper มีสำเนาอยู่สองภูมิภาค แต่ค่าอายุ 1 ปีที่ผิดอยู่ใน subscription คือการสมัครใช้ private cloud ซึ่งอยู่เหนือสำเนาทั้งสอง

ครบอายุเมื่อไหร่ ระบบลบ private cloud ของ UniSuper ทั้งก้อน สำเนาทั้งสองภูมิภาคจึงหายไปพร้อมกัน

สำเนาจะเป็นอิสระต่อกันจริงก็ต่อเมื่อไม่ใช้อะไรร่วมกันเลย หลาย AZ กันเหตุระดับอาคาร หลาย region กันเหตุระดับพื้นที่ ส่วนเหตุที่เกิดจากผู้ให้บริการเอง ต้องมีสำเนาไว้กับผู้ให้บริการอีกเจ้า
</Pitfall>

### ที่ตั้งก็มีผลกับความเร็ว

แอปตัวเดียวกันที่รันในสอง data center ให้ response time ต่างกัน และเปลี่ยนไปทุกนาที ในการวัดช่วงสิบนาที DC1 ตอบส่วนใหญ่ราว 3,000–4,000 ms และกระโดดสูงสุดราว 7,300 ms ส่วน DC2 กระโดดบ่อยกว่า และพุ่งไปถึงราว 10,000 ms

ถ้ามีหลายที่ให้เลือก ก็ส่งคำขอไปที่ที่ตอบดีกว่าในขณะนั้นได้ นี่คืออีกด้านของ agility

### องค์กรใช้ multi-cloud กันแค่ไหน

ผลสำรวจ Flexera State of the Cloud 2025 ([Lecture 7 ส่วนที่ 4](/2110506-sds/lecture-7#องค์กรใช้แบบไหนกันจริง)) นับว่า 86% ขององค์กรใช้ multi-cloud ที่เหลือใช้ public เจ้าเดียว 12% และ private ชุดเดียว 2% ใน 86% นั้น 70% เป็น hybrid 14% ใช้ public หลายเจ้า และ 2% ใช้ private หลายชุด

ใน hybrid 70% มี 34% ที่ใช้ public หลายเจ้ากับ private หลายชุด และ 21% ใช้ public หลายเจ้ากับ private ชุดเดียว

<Pitfall>
"86% ใช้ multi-cloud แปลว่า 86% ใช้คลาวด์สาธารณะหลายเจ้า" ไม่ถูก

ที่ดูเหมือนถูกเพราะนิยามข้างบนบอกว่า multi-cloud คือ Public Cloud A + Public Cloud B

แต่ผลสำรวจนี้นับ multi-cloud แบบกว้าง คือใช้คลาวด์มากกว่าหนึ่งชุดในแบบใดก็ได้ รวม hybrid ด้วย องค์กรที่ใช้ public หลายเจ้าจริง ๆ คือ 14% + 34% + 21% = 69% เวลาเจอตัวเลข multi-cloud จึงต้องดูก่อนว่าใช้นิยามไหน
</Pitfall>

<Quiz question="บริษัทหนึ่งรันแอปบนทั้ง AWS และ Azure วันหนึ่งทีม deploy config ที่ผิดชุดเดียวกันลงทั้งสองเจ้า multi-cloud ช่วยให้แอปรอดไหม">
สองเจ้าเป็นอิสระต่อกันเฉพาะในของที่ไม่ได้ใช้ร่วมกัน เช่น เครื่อง เครือข่าย และระบบภายในของผู้ให้บริการ แต่ config ชุดนี้เป็นของทีมเอง และถูกส่งลงทั้งสองเจ้า ความผิดพลาดเดียวจึงโดนทั้งคู่พร้อมกัน

คำตอบคือ **ไม่ช่วย** สองคลาวด์กันได้เฉพาะเหตุที่เกิดกับเจ้าใดเจ้าหนึ่ง ถ้า deploy ทีละเจ้า เจ้าที่ยังไม่ได้รับ config ผิดจะยังรับงานต่อได้

คำตอบที่ผิดบ่อยคือ "ช่วย เพราะสองเจ้าเป็นอิสระต่อกัน" ความเป็นอิสระมีขอบเขต เหมือน UniSuper ที่สำเนาสองภูมิภาคหายพร้อมกัน เพราะสิ่งที่ผิดอยู่เหนือทั้งสอง
</Quiz>

## ส่วนที่ 2 — Hybrid cloud: data center ของเรากับคลาวด์สาธารณะ

### Hybrid cloud คืออะไร

<Why>
องค์กรที่มีข้อมูลซึ่งกฎบังคับให้อยู่ในที่ตัวเอง ย้ายทุกอย่างขึ้นคลาวด์ไม่ได้ แต่ยังอยากยืมเครื่องของคลาวด์ตอนงานล้น
</Why>

<Term en="Hybrid cloud" th="คลาวด์ของเราเองใช้คู่กับคลาวด์สาธารณะ" /> คือคลาวด์ส่วนตัวที่ตั้งอยู่ในที่ขององค์กรเอง ใช้ร่วมกับคลาวด์สาธารณะ เป็นแบบที่พบบ่อยที่สุด ราว 70% ตามผลสำรวจในส่วนที่ 1

เครื่องที่ตั้งอยู่ในที่ขององค์กรเองเรียกว่า <Term en="on-premises" th="ตั้งอยู่ในที่ขององค์กรเอง" />

Hybrid ให้สามอย่าง คือ compliance ดีขึ้นเพราะข้อมูลที่ถูกบังคับยังอยู่ในที่ของเรา, ขยายได้ด้วยการยืมคลาวด์ และได้ประโยชน์ด้านต้นทุน การใช้งานที่พบบ่อยมีหกแบบ

| การใช้งาน | ทำอะไร |
| --- | --- |
| Extend your data center | แบ่งงานบางส่วนไปไว้บนคลาวด์ |
| Disaster recovery / high availability | มีฝั่งสำรองบนคลาวด์ |
| Integrated resources / deployment management | จัดการและ deploy ทั้งสองฝั่งด้วยเครื่องมือชุดเดียว |
| Cloud bursting | ยืมคลาวด์ตอนงานล้น |
| Cloud on-premises | เอาฮาร์ดแวร์ของคลาวด์มาตั้งในที่ของเรา |
| Integrated devices and edge systems | เชื่อมอุปกรณ์ปลายทางเข้ากับคลาวด์ |

### ขยาย data center: แบ่งตามหน้าที่ หรือตามความอ่อนไหวของข้อมูล

**แบ่งตามหน้าที่** Samsung ใช้ AWS ส่งเนื้อหาและข้อมูลของแอปบน smart TV แต่งานที่เป็นธุรกรรมการเงินวิ่งกลับไปที่ data center ของ Samsung เอง

**แบ่งตามข้อมูล** หรือ <Term en="split architecture" th="แยกส่วนแอปกับส่วนข้อมูลไว้คนละที่" /> Web กับ App รันบน AWS ส่วนฐานข้อมูล Oracle ที่เก็บข้อมูลอ่อนไหวอยู่ใน data center ขององค์กร สองฝั่งเชื่อมกันด้วยเส้นทางเครือข่ายระหว่างกัน

แบบที่สองต่างจาก forklift ที่ยกแอปกับฐานข้อมูลไปด้วยกัน ที่นี่ตั้งใจแยกเพราะข้อมูลออกไปไม่ได้ และยอมจ่ายด้วยเวลาที่ทุก query ต้องข้ามเส้นเชื่อม

### Disaster recovery แบบ hot standby

<Why>
ถ้า data center ขององค์กรไฟดับทั้งอาคาร ระบบสำรองที่ต้องเปิดเครื่องและโหลดข้อมูลใหม่จะใช้เวลาเป็นชั่วโมง ระหว่างนั้นผู้ใช้เข้าระบบไม่ได้
</Why>

<Figure number={1} caption="hot standby: สองฝั่งรับผู้ใช้อยู่แล้ว และฐานข้อมูลบน AWS ได้ข้อมูลจาก master ตลอดเวลา">
  <HotStandby />
</Figure>

<Term en="Route 53" th="บริการ DNS ของ AWS" /> ตอบชื่อ www.example.com เป็นที่อยู่ของทั้งสองฝั่ง ทั้งสองฝั่งจึง active รับผู้ใช้จริงอยู่แล้ว แบบนี้เรียกว่า <Term en="hot standby" th="ฝั่งสำรองที่รันและรับงานจริงอยู่แล้ว" /> ฝั่งสำรองไม่ต้องรอบูต

ฝั่ง AWS มี load balancer (ตัวกระจายคำขอ), ชั้นรับคำขอหน้าแอป (reverse proxy/caching server) และ application server ครบเหมือนฝั่งองค์กร

ข้อมูลมี master ตัวเดียวอยู่ใน data center ขององค์กร master <Term en="replicate" th="คัดลอกข้อมูลไปอีกที่อย่างต่อเนื่อง" /> ข้อมูลไปที่ subordinate database บน AWS ตลอดเวลา application server ฝั่ง AWS อ่านจาก subordinate ในฝั่งตัวเอง แต่การเขียนต้องส่งกลับไปที่ master เพราะ subordinate รับข้อมูลได้ทางเดียว คือที่ replicate มาจาก master

เมื่อ master ใช้ไม่ได้ application server ฝั่งองค์กรเปลี่ยนแหล่งข้อมูล (cut over) ไปที่ subordinate ซึ่งมีข้อมูลที่ replicate มาแล้ว แต่ subordinate จะรับการเขียนได้ ต้อง <Term en="promote" th="ยกสำเนาขึ้นเป็นฐานข้อมูลหลัก" /> ขึ้นเป็น master ก่อน

### Deploy ทั้งสองฝั่งด้วย pipeline เดียว

<Why>
ถ้าสองฝั่ง deploy คนละวิธี สองฝั่งอาจรันโค้ดคนละรุ่นโดยไม่มีใครสังเกต
</Why>

หลักคือสร้างบน AWS แล้ว deploy ลงทั้งคลาวด์และเครื่องในที่ของเรา AWS CodePipeline ร้อยขั้นตอนปล่อยซอฟต์แวร์ไว้สี่ขั้น

| ขั้น | เครื่องมือ |
| --- | --- |
| Source | AWS CodeCommit |
| Build | AWS CodeBuild |
| Test | เครื่องมือของเจ้าอื่น (third-party tooling) |
| Production | AWS CodeDeploy ลงทั้ง EC2 และเครื่อง on-premises |

ขั้นสุดท้ายคือจุดที่ทำให้เป็น hybrid pipeline เดียว deploy ได้สองที่ (pipeline แบบนี้คือ CI/CD ใน [Lecture 6](/2110506-sds/lecture-6))

### Cloud bursting: ยืมคลาวด์ตอนงานล้น

<Term en="Cloud bursting" th="ยืมเครื่องบนคลาวด์ตอนงานล้นเครื่องของเรา" /> ([Lecture 7 ส่วนที่ 4](/2110506-sds/lecture-7#ส่วนที่-4--private-public-hybrid-ใครใช้ร่วมกันได้บ้าง)) ใช้กับงานที่ปกติเครื่องในที่ตัวเองพอ แต่บางช่วงล้น ตัวอย่างคือ FuseFX ซึ่งต้อง render ภาพจำนวนมาก

ปกติงาน render รันบน render farm ในสตูดิโอ (local render farm) และเก็บไฟล์ใน Isilon X410 Cluster

<Term en="Spot instance" th="เครื่องว่างของ AWS ราคาถูก ที่ถูกเรียกคืนได้" /> คือเครื่องที่ AWS ปล่อยเช่าราคาถูกเพราะว่างอยู่ Spot Fleet คือกลุ่มของเครื่องแบบนี้

เมื่องานล้น FuseFX เปิด Spot Fleet บน AWS จาก [AMI](/2110506-sds/lecture-7-2#หกสิ่งที่ต้องเลือกก่อนกด-launch) หรือ image ต้นแบบที่เตรียมไว้

<Detail label="สองฝั่งของ FuseFX ต่อกันยังไง">
Spot Fleet รันอยู่ใน VPC (เครือข่ายส่วนตัวของลูกค้าบน AWS) สองฝั่งเชื่อมกันด้วย AWS Direct Connect ซึ่งเป็นเส้นเชื่อมตรงเข้า AWS ทั้งสอง farm รับงานจาก Deadline DB and Repo ตัวเดียวกัน

ฝั่งคลาวด์เก็บไฟล์ใน Qumulo ที่รันบน m4.16xlarge กับ EBS แล้วใช้ custom sync solution ชื่อ Nucleus คอย sync ไฟล์ของสตูดิโอกับฝั่งในที่ตัวเอง
</Detail>

จุดที่ทำให้ burst ได้คือ **สองฝั่งรับงานจากคิวเดียวกัน และเห็นไฟล์ชุดเดียวกัน** เครื่องบนคลาวด์จึงทำงานเหมือนเป็นเครื่องเพิ่มใน farm

### คลาวด์ในที่ตัวเอง และที่ปลายทาง

**Cloud on-premises** AWS Outposts คือการเอาโครงสร้างพื้นฐานของ AWS มาตั้งในที่ขององค์กร ขั้นตอนมีสี่ขั้น

1. **Configure** — เลือกสเปกและสั่ง Outposts จาก AWS Console
2. **Connect** — ต่อ Outposts เข้ากับไฟฟ้าและเครือข่ายในที่ของเรา
3. **Launch** — ใช้ AWS Console สร้าง EC2 instance บน Outposts
4. **Build** — สร้างแอปด้วยบริการของ AWS ทั้งบน Outposts และใน region ที่อยู่ใกล้

ผลคือเครื่องอยู่ในที่ของเรา แต่สั่งงานด้วยเครื่องมือชุดเดียวกับบนคลาวด์

**Edge** อุปกรณ์ปลายทางอย่างเซ็นเซอร์และเครื่องจักรต่อเข้ากับคลาวด์เป็นสามชั้น

| ชั้น | ทำอะไร | บริการของ AWS |
| --- | --- | --- |
| Things (devices) | วัดค่าและสั่งงาน (sense & act) | AWS Greengrass, Amazon FreeRTOS |
| Cloud | เก็บข้อมูลและประมวลผล | AWS IoT Core, AWS IoT Device Defender, AWS IoT Device Management |
| Intelligence | เปลี่ยนข้อมูลเป็นการตัดสินใจ (insights & logic → action) | AWS IoT Analytics |

<Quiz question="สมมติข้อบังคับของมหาวิทยาลัยกำหนดว่าประวัติและผลการเรียนของนิสิตต้องเก็บใน data center ของมหาวิทยาลัยเท่านั้น แต่ช่วงเปิดลงทะเบียน Reg Chula มีคนเข้าพร้อมกันมากกว่าปกติหลายเท่า ควรใช้ hybrid แบบไหน">
ข้อบังคับผูกที่ข้อมูล ไม่ได้ผูกที่ส่วนที่รับผู้ใช้ ฐานข้อมูลจึงอยู่ใน data center ส่วน Web กับ App ซึ่งเป็นส่วนที่โหลดพุ่ง ย้ายไปบนคลาวด์และเพิ่มเครื่องได้ตามช่วงลงทะเบียน

คำตอบคือ **split architecture** แบบขยาย data center ตามความอ่อนไหวของข้อมูล หรือจะใช้ cloud bursting โดยปกติรันในที่ตัวเอง แล้วยืมเครื่องบนคลาวด์เฉพาะช่วงลงทะเบียนก็ได้ ทั้งสองแบบฐานข้อมูลไม่ออกจากมหาวิทยาลัย แต่จ่ายเวลาต่างกัน split architecture ให้ทุก query ข้ามเส้นเชื่อม ส่วน cloud bursting มีแค่ query จากเครื่องที่ยืมมาที่ต้องข้าม เครื่องในที่ตัวเองยัง query ฐานข้อมูลใกล้ ๆ

คำตอบที่ผิดบ่อยคือ "ย้ายทั้งระบบขึ้นคลาวด์ แล้วเข้ารหัสข้อมูลไว้" การเข้ารหัสปกป้องข้อมูลไม่ให้คนอื่นอ่าน แต่ไม่ได้เปลี่ยนว่าข้อมูลเก็บอยู่ที่ไหน ข้อบังคับนี้ถามเรื่องที่ตั้ง
</Quiz>
