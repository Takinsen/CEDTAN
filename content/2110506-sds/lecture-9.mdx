## ส่วนที่ 1 — สองทางขึ้นคลาวด์

ในหน้านี้ คุณคือผู้ใช้คลาวด์ (cloud user) ที่เช่าเครื่องจากผู้ให้บริการ (cloud provider) อย่าง AWS มารันแอปให้ผู้ใช้แอป (application users) สามฝ่ายนี้อยู่ใน [Lecture 7 ส่วนที่ 1](/2110506-sds/lecture-7#สามฝ่ายในเรื่องเดียว)

### แอปใหม่กับแอปเก่าเดินคนละทาง

กลยุทธ์ขึ้นคลาวด์แยกเป็นสองทางตั้งแต่แรก ตามว่าแอปมีอยู่แล้วหรือยัง ทางแยกนี้ใช้ได้ทั้งกับ startup, ธุรกิจขนาดกลางและเล็ก (SMB) และองค์กรใหญ่

- **แอปใหม่** — ออกแบบให้พร้อมสำหรับคลาวด์ตั้งแต่วันแรก (build a cloud-ready design)
- **แอปที่มีอยู่แล้ว** — แยกอีกสองทาง แอปที่ย้ายได้แทบไม่ต้องคิด (no-brainer to move) ย้ายได้เลย ส่วนที่เหลือย้ายตามแผนทีละระยะ (planned phased migration)

ทั้งสองทางมุ่งไปที่ประโยชน์ชุดเดียวกันแปดข้อ

| ประโยชน์ | หมายความว่า |
| --- | --- |
| Zero upfront investment | ไม่ต้องซื้อเครื่องล่วงหน้า |
| On-demand provisioning | ขอเครื่องได้ทันทีที่ต้องการ |
| Instant scalability | เพิ่มขนาดได้ทันที |
| Auto scaling and elasticity | ระบบเพิ่มและลดเครื่องเองตามโหลด |
| Pay as you go | จ่ายตามที่ใช้จริง |
| Removes undifferentiated heavy lifting | ตัดงานหนักที่ทุกบริษัทต้องทำเหมือนกัน เช่น ติดตั้งและซ่อมเครื่อง ซึ่งไม่ได้ทำให้แอปของคุณดีกว่าคู่แข่ง |
| Developer productivity | นักพัฒนาได้ใช้เวลากับตัวแอปมากขึ้น |
| Automation | สั่งงานโครงสร้างพื้นฐานผ่านโค้ดได้ |

<KeyIdea>
แอปใหม่ได้ออกแบบให้เข้ากับคลาวด์ตั้งแต่ต้น แอปเก่าต้องแยกก่อนว่าตัวไหนย้ายได้ทันที ตัวไหนต้องวางแผนย้ายทีละระยะ
</KeyIdea>

## ส่วนที่ 2 — แอปใหม่: ออกแบบให้เกิดบนคลาวด์

### แอปบนอินเทอร์เน็ตส่วนใหญ่มีสามชั้น

<Why>
แอปมือถือที่มีผู้ใช้เป็นแสนคน รับคำขอทั้งหมดด้วยเครื่องเดียวไม่ไหว และถ้าเครื่องนั้นพัง ทุกอย่างหยุด ทางออกที่ใช้กันมานานคือแบ่งแอปเป็นชั้นตามหน้าที่ แล้วให้แต่ละชั้นมีเครื่องได้หลายเครื่อง
</Why>

<Term en="3-tier architecture" th="สถาปัตยกรรมสามชั้น" /> แบ่งแอปเป็นสามชั้น แต่ละชั้นรันบนเครื่องและ OS ของตัวเอง

| ชั้น | ชื่อเรียกอีกแบบ | ทำอะไร |
| --- | --- | --- |
| Front-end | Web | รับคำขอจากผู้ใช้ แล้วส่งหน้าเว็บหรือข้อมูลกลับ |
| Business logic | App | ประมวลผลตามกฎของธุรกิจ |
| Back-end | DB | เก็บข้อมูล |

คำขอจากผู้ใช้ผ่าน <Term en="firewall" th="ด่านกรองว่าทราฟฟิกไหนเข้าได้" /> ก่อนถึงชั้นแรก

ระหว่างชั้นมี <Term en="load balancer" th="ตัวกระจายคำขอไปหลายเครื่อง" /> คั่นอยู่ คอยกระจายคำขอไปหลายเครื่องของชั้นถัดไป

ผลคือแต่ละชั้นเพิ่มเครื่องได้เอง โดยชั้นก่อนหน้าไม่ต้องรู้ว่าข้างหลังมีกี่เครื่อง

### KhunLook: แอปสามชั้นบน AWS

KhunLook เป็นแอปมือถือที่วางสามชั้นนี้ไว้บน AWS และเป็นตัวอย่างที่เดินไปตลอดส่วนนี้

| ชั้น | วางบน | ซอฟต์แวร์ข้างใน |
| --- | --- | --- |
| Front-end | EC2 instance | Content: Joomla (ระบบจัดการเนื้อหาเว็บ) · Web: Apache HTTP Server |
| Business logic | EC2 instance | Auth: Apache Directory (ที่เก็บบัญชีผู้ใช้) · App: Apache Tomcat (ตัวรันแอป Java) |
| Back-end | RDS instance และ S3 | DB: MariaDB · ไฟล์ใน S3 |

บริการของ AWS สามตัวในตารางจะเจออีกตลอดหน้า

- <Term en="EC2" th="VM ที่เช่าจาก AWS" /> — เครื่องเสมือนที่คุณเช่า เลือก OS ตอนเปิดเครื่อง แล้วติดตั้งซอฟต์แวร์และดูแลเอง ([Lecture 7.2](/2110506-sds/lecture-7-2#ส่วนที่-1--ขอเครื่องหนึ่งเครื่องบน-amazon-ec2))
- <Term en="RDS" th="ฐานข้อมูลที่ AWS ดูแลให้" /> — ได้ฐานข้อมูลที่พร้อมใช้ โดย AWS ดูแลเครื่องและ OS ให้
- <Term en="S3" th="ที่เก็บไฟล์บนคลาวด์" /> — ฝากไฟล์เป็นก้อน ๆ ไว้ แล้วเรียกกลับด้วยชื่อ ([Lecture 8.1 ส่วนที่ 3](/2110506-sds/lecture-8#ส่วนที่-3--s3-เก็บ-object-ด้วย-key))

  <KhunlookPaths />

ผู้ใช้ทำสามอย่าง แต่ละอย่างวิ่งผ่านชั้นต่างกัน **login** ไปที่ Auth **ดูเนื้อหาเว็บ** ดึงจาก DB ตรงโดยไม่ผ่านชั้นกลาง ส่วน **sync** ไปที่ App ซึ่ง backup ข้อมูลลงทั้ง S3 และ DB

สังเกตว่าทั้งสามทางเข้าทาง Web เครื่องเดียวกัน และ Auth กับ App อยู่บนเครื่องเดียวกัน ถ้าคืนหนึ่งมีคน sync พร้อมกันมาก งาน backup จะแย่งเครื่องกับคนที่กำลัง login

### ปรับแอปทีละขั้น: จาก VM ถึง serverless

KhunLook รุ่นแรกใช้งานได้ แต่ถ้าจะเพิ่มกำลังให้งานใดงานหนึ่ง ต้องเพิ่มทั้งเครื่อง การปรับให้ทันสมัยทำได้สามขั้น แต่ละขั้นเปลี่ยนคนละเรื่อง

<Figure number={2} caption="ชั้น business logic ของ KhunLook ในสี่ขั้น — แต่ละขั้นเปลี่ยนคนละเรื่อง">
  <KhunlookLogicTier />
</Figure>

**ขั้นที่ 1 containerize เปลี่ยนวิธีแพ็ก** ซอฟต์แวร์ของแต่ละชั้นถูกใส่ใน Docker container แล้วรันบน EC2 ตัวเดิม ส่วน back-end ยังเป็น RDS เหมือนเดิม โครงสามชั้นไม่เปลี่ยนเลย ที่ได้คือย้ายเครื่องและสร้างซ้ำได้ง่าย (container อยู่ใน [Lecture 2](/2110506-sds/lecture-2))

**ขั้นที่ 2 microservices เปลี่ยนวิธีแบ่ง** แบบ monolithic ยังมี Auth กับ App อยู่ใน container เดียว แบบ microservices แยกชั้นกลางเป็นสองบริการ คือ Auth กับ Backup ซึ่งเป็นงาน backup ที่เดิมอยู่ใน App แต่ละตัวมี container และ EC2 ของตัวเอง ผลคือ **พัฒนา ขยาย และดูแลแต่ละบริการได้อิสระ** (monolith กับ microservices อยู่ใน [Lecture 4](/2110506-sds/lecture-4))

**ขั้นที่ 3 serverless เลิกดูแลเครื่อง** Auth กับ Backup กลายเป็น function และชั้นกลางไม่มี EC2 อีกต่อไป ส่วน front-end ยังเป็น container บน EC2

<Term en="Serverless function" th="โค้ดที่คลาวด์รันให้เมื่อมีคำขอ" /> คือคุณส่งแค่โค้ดของฟังก์ชันขึ้นไป แล้วคลาวด์เป็นคนหาเครื่องมารันทุกครั้งที่มีคำขอ ข้อดีคือดูแลน้อย และคิดแค่เรื่องฟังก์ชัน ไม่ต้องคิดเรื่องทรัพยากร

ทางวิ่งของคำขอก็เปลี่ยนด้วย แอปบนมือถือเรียก login และ backup ตรงไปที่ Auth Function กับ Backup Function โดยไม่ผ่าน Web อีก Web เหลืองานเดียวคือส่งเนื้อหาเว็บที่ดึงจาก DB

<Quiz question="คืนวันอาทิตย์ผู้ใช้ KhunLook sync พร้อมกันจนชั้นกลางรับไม่ไหว แต่จำนวนคน login เท่าเดิม ถ้า KhunLook เป็นแบบ containerize ที่ Auth กับ App อยู่ใน container เดียว เทียบกับแบบ microservices คุณเพิ่มกำลังให้งาน backup ได้ต่างกันยังไง">
แบบ containerize มี Auth กับ App อยู่ใน container เดียว การเพิ่มกำลังคือรัน container นั้นเพิ่มอีกชุดบนเครื่องใหม่ ทุกชุดพก Auth ไปด้วยทั้งที่ไม่มีใครต้องการ Auth เพิ่ม แบบ microservices เพิ่มเฉพาะ container ของ Backup บน EC2 เพิ่ม โดย Auth ไม่ถูกแตะเลย

คำตอบคือ **microservices เพิ่มได้เฉพาะ Backup** ส่วนแบบ containerize ต้องเพิ่มทั้งก้อน ถ้าเป็น serverless คลาวด์จะรัน Backup function เพิ่มให้เองตามจำนวนคำขอ

คำตอบที่ผิดบ่อยคือ "containerize ก็พอแล้ว เพราะ container ขยายง่าย" container เปลี่ยนวิธีแพ็ก ไม่ได้เปลี่ยนวิธีแบ่ง สิ่งที่ถูกทำสำเนาจึงยังเป็น Auth กับ App ทั้งก้อน
</Quiz>

### ระบบจริงผสมหลายรุ่น: Wongnai ปี 2017

สถาปัตยกรรมของ Wongnai ช่วงต้นปี 2017 ยังแบ่งสามชั้นเหมือน KhunLook แต่แต่ละชั้นมีหลายชิ้น

<Detail label="ชิ้นส่วนทั้งหมดของ Wongnai ปี 2017">
| ชั้น | ชิ้นส่วน |
| --- | --- |
| Front-end | Request Dispatcher, API Gateway, Web Server |
| Business logic | Core Services, Legacy Monolithic Application Servers, ZooKeeper Cluster (ประสานงานระหว่างเครื่อง), Solr Cloud (ระบบค้นหา) |
| Back-end | Image Servers, S3, RDS MySQL, Cassandra Cluster (ฐานข้อมูลแบบกระจาย) |

ด้านหน้ามี HTTP/HTTPS load balancer สองตัว ตัวหนึ่งรับคำขอจากเว็บเบราว์เซอร์และแอปมือถือ อีกตัวรับคำขอรูปจาก <Term en="CDN" th="เครื่องที่กระจายอยู่ใกล้ผู้ใช้ เก็บสำเนาไฟล์ไว้ส่ง" /> servers แล้วส่งต่อไปที่ Image Servers นอกจากนี้ยังมี monitoring tools และ Kubernetes cluster อยู่ในระบบ
</Detail>

จุดที่ควรสังเกตคือ **Legacy Monolithic Application Servers ยังรันอยู่ข้าง Core Services** ที่ใหม่กว่า ระบบจริงไม่ได้เปลี่ยนจาก monolith เป็น microservices ในวันเดียว แต่ค่อย ๆ แยกออกมา ช่วงหนึ่งจึงมีของสองรุ่นทำงานด้วยกัน

<KeyIdea>
container เปลี่ยนวิธีแพ็ก microservices เปลี่ยนวิธีแบ่ง serverless เลิกดูแลเครื่อง และระบบจริงเปลี่ยนทีละส่วน ของสองรุ่นจึงรันด้วยกันได้
</KeyIdea>

## ส่วนที่ 3 — แอปที่มีอยู่แล้ว: ประเมินก่อนย้าย

### หกขั้นของการย้าย

กลับมาที่ Reg Chula กับ www.chula.ac.th สองระบบนี้รันอยู่แล้ว คำถามจึงไม่ใช่ "ออกแบบยังไง" แต่เป็น "ทำไมต้องย้าย และวางแผนย้ายยังไง"

การย้ายแอปที่มีอยู่แบ่งเป็นหกขั้น

1. **Cloud Assessment** — ประเมินว่าคุ้มไหม และตัวไหนควรย้าย
2. **POC** — ทดลองกับของชิ้นเล็กก่อน
3. **Data Migration** — ย้ายข้อมูล
4. **Application Migration** — ย้ายตัวแอป
5. **Leverage the Cloud** — ใช้ความสามารถของคลาวด์ให้เต็มที่
6. **Optimization** — ปรับให้คุ้มขึ้นเรื่อย ๆ

ส่วนนี้ว่าด้วยขั้นที่ 1 ซึ่งตัดสินว่าจะย้ายอะไร ส่วนที่ 4 ว่าด้วยขั้นที่ 2 ถึง 6

### ขั้นที่ 1 ประเมินอะไรบ้าง

Cloud assessment ประเมินสามด้าน

| ด้าน | คำถามที่ต้องตอบ |
| --- | --- |
| การเงิน | ต้นทุนรวมเทียบกับเดิมเป็นยังไง (TCO/ROI) และรันบนคลาวด์จะเสียเท่าไหร่ |
| Security และ compliance | ระบบนี้มีกฎหรือข้อบังคับอะไรกำกับอยู่ |
| เทคนิค | เลือกแอปไหนเป็นตัวแรก, ซอฟต์แวร์ที่ซื้อใบอนุญาตมาย้ายได้ไหม, เครื่องมือไหนใช้ต่อได้, ฟังก์ชันและสถาปัตยกรรมของแอปเข้ากับคลาวด์ไหม |

<Term en="Compliance" th="การทำตามกฎหมายและข้อบังคับ" /> ในที่นี้คือคำถามว่ากฎบังคับอะไรกับข้อมูลและระบบนี้บ้าง เช่น ข้อมูลต้องเก็บไว้ที่ไหน

ผลของขั้นนี้มีสามอย่าง คือตัวเลขต้นทุน แผนผังว่าระบบไหนพึ่งระบบไหน และรายการว่าอะไรใช้ซ้ำได้

### ย้ายแล้วถูกลงจริงไหม: TCO

<Why>
คำถามแรกที่ผู้บริหารถามคือย้ายแล้วถูกลงไหม คำตอบขึ้นกับว่าค่าใช้จ่ายก้อนใหญ่ของระบบเดิมอยู่ตรงไหน
</Why>

<Term en="TCO (Total Cost of Ownership)" th="ต้นทุนรวมของการมีระบบ" /> คือเงินทั้งหมดที่จ่ายเพื่อให้ระบบรันได้ ไม่ใช่แค่ค่าซื้อเครื่อง แต่รวมค่าไฟ ค่าเครือข่าย และเงินเดือนคนดูแล

<Term en="ROI (Return on Investment)" th="ผลตอบแทนเทียบกับเงินที่ลงไป" /> บอกว่าเงินที่ลงไปได้อะไรกลับมาเท่าไหร่

ผลออกได้ทั้งสองทาง งานวิจัยปี 2012 (Sripanidkulchai et al., BDIM 2012) เทียบระบบเดียวกันสองประเทศ ในไทย คลาวด์แพงกว่ารันเอง $10k (+19%: $61.5k กับ $51.5k) แต่ในสหรัฐฯ ถูกกว่า 53% ($52.5k กับ $112.5k)

ตัวที่ทำให้ผลกลับข้างคือเงินเดือนคนดูแล ซึ่งคลาวด์ช่วยให้เลิกจ่ายได้มากที่สุด เงินเดือนในสหรัฐฯ ($68.6k) สูงกว่าไทย ($10.3k) ราว 6.7 เท่า ตัวเลขทั้งชุด รวมถึงสองจุดที่บวกไม่ลงตัว อยู่ใน [Lecture 7 ส่วนที่ 6](/2110506-sds/lecture-7#ตัวเลขเดียวกัน-ผลตรงข้าม)

### วาด dependency tree ก่อนแตะอะไร

<Why>
ถ้าย้ายระบบ LDAP ซึ่งเก็บบัญชีผู้ใช้ขึ้นคลาวด์ โดยไม่รู้ว่าใครเรียกใช้มันบ้าง วันรุ่งขึ้นอาจมีระบบที่ไม่มีใครนึกถึงช้าลงหรือพัง เพราะมันเรียก LDAP ทุกครั้งที่มีคน login
</Why>

Technical assessment เริ่มจากลิสต์ IT asset ทั้งหมด แล้ววาด <Term en="dependency tree" th="แผนผังว่าระบบไหนพึ่งระบบไหน" /> จากนั้นหา dependency ของแต่ละตัวทั้งสองทิศ

  <MigrationDependencyTree />
</Figure>

- <Term en="Upward dependency" th="ระบบที่พึ่งเราอยู่" /> คือใครพึ่งเรา ถ้าย้าย LDAP ไป Auth ต้องเรียกข้ามเครือข่ายไปหามันทุกครั้ง และ Dashboard ที่พึ่ง Auth ก็ช้าตามไปด้วย

แผนผังขององค์กรจริงใหญ่กว่านี้มาก จนต้องใช้เครื่องมือ dependency mapping อย่าง ScienceLogic วาดให้ แผนผังที่เครื่องมือแบบนี้วาดโยงอุปกรณ์เครือข่าย (Cisco) ที่เก็บข้อมูล (NetApp) และ VM (VMware) เข้าหากันเป็นร้อยเส้น

เมื่อมีแผนผังแล้ว จัดกลุ่ม asset ตามสี่แกน เพื่อดูว่าตัวไหนย้ายง่าย ตัวไหนย้ายยาก

| แกน | กลุ่ม | ทำไมต้องรู้ |
| --- | --- | --- |
| Compliance | ต่ำ / กลาง / สูง | ระบบที่ compliance สูงมีกฎว่าข้อมูลเก็บที่ไหนได้ ต้องตรวจก่อนย้าย |
| ใครใช้ | ภายในเท่านั้น / คู่ค้า / ลูกค้า (customer-facing) | บอกว่าถ้าย้ายแล้วสะดุด ใครเดือดร้อน |
| <Term en="Coupling" th="ระดับที่ระบบผูกกัน" /> | ต่ำ / กลาง / สูง | ระบบที่ผูกกันแน่นต้องย้ายไปพร้อมกัน |
| Licensing | เข้ม (strict) / ผ่อน (relaxed) | ใบอนุญาตแบบเข้มอาจไม่ยอมให้ย้ายไปรันบนเครื่องที่ไม่ใช่ของเรา หรือคิดเงินเพิ่ม |

### แอปจริงใหญ่และซับซ้อนแค่ไหน

แผนผังสำคัญเพราะแอปขององค์กรไม่ได้มีสามเครื่องอย่าง KhunLook งานวิจัยที่สำรวจแอปองค์กรห้าตัว (Hajjat et al., SIGCOMM 2010) พบว่าแต่ละแอปใช้ตั้งแต่ราว 10 ไปจนถึงกว่า 100 เครื่อง และเครื่องส่วนใหญ่อยู่ในชั้น business logic

บริการเว็บขนาดใหญ่ซับซ้อนกว่านั้นอีก Bing สร้างหน้าผลลัพธ์แรกผ่านงานย่อยต่อกันได้ถึง 150 ขั้น (stage) เส้นทางหนึ่งยาว 10 ขั้นขึ้นไป แต่ละขั้นแตกงานออกไปได้ถึง 40 ทางพร้อมกัน และแต่ละขั้นเองก็อาจเป็น workflow ซับซ้อนอีกชั้น (Jalaparti et al., SIGCOMM 2013)

รูปแบบที่เจอบ่อยคือ <Term en="partition-aggregate" th="แตกงานไปหลายเครื่องพร้อมกัน แล้วรวมผล" /> คำขอถูกแบ่งให้หลายเครื่องทำพร้อมกัน แล้วรอรวมผลจากทุกเครื่อง ผลคือ **ความหน่วงแบบสุ่มของแต่ละ stage สะสมกัน** เพราะคำตอบต้องรอเครื่องที่ช้าที่สุด

<Example added title="ช้าแค่ 1% ต่อเครื่อง เมื่อแตกงานไป 40 เครื่อง">
สมมติแต่ละเครื่องมีโอกาสตอบช้า 1% และคำขอแตกไปให้ 40 เครื่องพร้อมกัน ลองทายก่อน: กี่เปอร์เซ็นต์ของคำขอจะช้า

```
fan-out   P(at least one machine slow) = 1 - 0.99^n
1         1.0%
10        9.6%
40        33.1%
```
</Example>

ราวหนึ่งในสามของคำขอช้า ทั้งที่แต่ละเครื่องช้าแค่ 1% นี่คือเหตุผลที่การย้ายบาง stage ขึ้นคลาวด์ยาก ทุกครั้งที่คำขอข้ามระหว่าง data center กับคลาวด์ จะมีเวลาเดินทางเพิ่มเข้ามา และเวลานั้นสะสมไปตามจำนวน stage เหมือนกัน

### กรณีจริง: 200 แอปในไม่ถึงห้าเดือน

วันที่ 19 พฤษภาคม 2015 บอร์ดของบริษัท CSC อนุมัติแผนแยกบริษัทเป็นสองบริษัท ฝั่งที่ดูแลลูกค้าภาครัฐของสหรัฐฯ กลายเป็นบริษัทใหม่ชื่อ CSRA ซึ่งต้องย้ายแอปกว่า 200 ตัวออกมาให้เสร็จภายในวันที่ 1 ตุลาคม 2015

<Detail label="ตัวเลขของการย้ายครั้งนี้">
| | CSC ก่อนแยก | CSRA หลังแยก |
| --- | --- | --- |
| พนักงาน | 70,000 คน | 14,000 คน |
| Data center | 14 แห่งขึ้นไป และผู้ให้บริการ SaaS | 2 แห่ง, Gov CSP หนึ่งราย และผู้ให้บริการ SaaS |

ที่ CSC แอปเหล่านี้รันปนกันบนเครื่อง physical, virtual, private cloud และ <Term en="SaaS" th="ซอฟต์แวร์ที่เช่าใช้ผ่านเว็บ" /> ปลายทางของ CSRA รวมถึง Gov CSP ซึ่งคือผู้ให้บริการคลาวด์สำหรับหน่วยงานรัฐ

ของที่ต้องย้ายมีราว 250 เครื่องทั้ง physical และ virtual หน่วยความจำรวม 3 TB และ 1,300 processor ครอบคลุมแอปหลายประเภท เช่น collaboration การเงิน HR payroll และ security
</Detail>

200 แอปในเวลาราวสี่เดือนครึ่ง ย้ายทีละตัวด้วยความระวังเท่ากันทุกตัวไม่ทัน ต้องจัดลำดับ

### เลือกตัวที่ย้ายง่ายก่อน

หลักคือ <Term en="stack rank" th="จัดอันดับทุกตัวเรียงจากง่ายไปยาก" /> เรียงลำดับ IT asset ทั้งหมด แล้วเก็บผลไม้ที่อยู่ต่ำก่อน (low-hanging fruit)

แอปที่ย้ายได้แทบไม่ต้องคิด (no-brainer) ได้แก่ แอปสำหรับ dev/test, เว็บแอปที่จบในตัว (self-contained), แคมเปญการตลาดบนโซเชียลมีเดีย, เว็บอบรมลูกค้า, video portal (แปลงไฟล์และให้บริการวิดีโอ), portal สาธิตก่อนขาย, หน้าดาวน์โหลดซอฟต์แวร์ และแอปทดลองใช้

แทบทุกตัวอยู่ปลายง่ายของสี่แกนข้างบน คือ coupling ต่ำและ compliance ต่ำ

เกณฑ์เลือกตัวแรกมีห้าข้อ

- IT asset ที่ใช้งานไม่เต็มกำลัง (under-utilized)
- แอปที่ธุรกิจต้องการขยายทันที
- แอปที่กำลังจะเต็มกำลังของเครื่อง
- **ย้ายได้ง่ายที่สุดในวันนี้**
- ย้ายแล้วสร้างแรงสนับสนุนในองค์กร ให้คนรู้จักและตื่นเต้นกับคลาวด์

ข้อสุดท้ายมีเหตุผล ความสำเร็จเล็ก ๆ ในช่วงแรกทำให้องค์กรเชื่อและยอมลงแรงกับตัวที่ยากกว่า

| อันดับ | Asset | ย้ายได้เมื่อไหร่ |
| --- | --- | --- |
| 1 | Product Marketing Site | วันนี้ |
| 2 | Internal Batch Process | 2 วัน |
| 3 | CRM System | 5 วัน |
| 4 | Log Processing apps | 1 สัปดาห์ |
| 5 | ERP System | ย้ายแบบแบ่งระยะ |

<Term en="ERP" th="ระบบบริหารทรัพยากรทั้งองค์กร" /> ผูกกับแทบทุกส่วนขององค์กร จึงอยู่ท้ายสุด และไม่ได้ย้ายในครั้งเดียว

## ส่วนที่ 4 — ย้ายจริงทีละขั้น

### ขั้นที่ 2 ทดลองด้วย POC

<Why>
ทีมที่ไม่เคยใช้ AWS ถ้าเริ่มด้วยการย้ายระบบใหญ่ทั้งระบบ จะต้องเรียนรู้ทุกอย่างพร้อมกันบนระบบที่ห้ามพัง
</Why>

<Term en="POC (Proof of Concept)" th="ต้นแบบเล็ก ๆ ที่พิสูจน์ว่าแนวทางใช้ได้" /> คือการสร้างสถาปัตยกรรมจำลองย่อส่วน ด้วยแอปเล็กและข้อมูลน้อย ๆ ขั้นนี้มีสองงาน

- **เรียน AWS** — สร้าง reference architecture คือแบบสถาปัตยกรรมต้นแบบ (template) ที่ระบบซึ่งจะย้ายจริงใช้ยึดตาม และรู้จักเครื่องมือด้าน security ที่มีให้
- **สร้าง prototype หรือ pilot** (ระบบทดลองขนาดเล็ก) — พิสูจน์ว่าเทคโนโลยีใช้ได้ ลองรันซอฟต์แวร์เก่าบนคลาวด์ วัดประสิทธิภาพเทียบกับของเดิม (benchmark) และสร้างแรงสนับสนุนในองค์กร

POC ที่ดีจำลองครบทั้ง Web, App และ DB

<Term en="IAM (Identity and Access Management)" th="ระบบจัดการตัวตนและสิทธิ์ของ AWS" /> ([Lecture 8.1](/2110506-sds/lecture-8#iam-user-คนละชุดสำหรับแต่ละคน)) เป็นสิ่งแรก ๆ ที่ต้องเรียน และควรใช้คุมสิทธิ์ใน POC ตั้งแต่ต้น ลำดับคือสร้าง group แล้วเขียน policy ให้ group นั้นว่าทำอะไรกับ resource ไหนได้ ภายใต้ condition อะไร

จากนั้นสร้าง user ออก access credentials ให้ แล้วใส่ user เข้า group ผลคือสิทธิ์ผูกกับ group ไม่ได้ผูกกับคนทีละคน

เส้นทางเรียนอีกเส้นเริ่มที่ EC2 คือเปิดเครื่องจาก <Term en="AMI (Amazon Machine Image)" th="image ต้นแบบสำหรับบูต EC2" /> ([Lecture 7.2](/2110506-sds/lecture-7-2#หกสิ่งที่ต้องเลือกก่อนกด-launch)) ปรับแต่งแล้วเก็บเป็น AMI ของตัวเอง จากนั้นแตกไปเรียน disk, IP ที่ไม่เปลี่ยน และที่เก็บไฟล์ เส้นทางแบบนี้มีได้อีกหลายเส้น

<Detail label="เส้นทางเรียน EC2 และบริการรอบตัว">
| เริ่มจาก | ทำต่อ | ปลายทาง |
| --- | --- | --- |
| Launch AMI | Customize AMI → Bundle AMI | Launch a customized AMI |
| Launch AMI | Learn about Security Groups → Test different Availability Zones | S3 Bucket, CloudFront |
| Create EBS Volume | Attach Volume → Create Snapshot of a Volume / Restore Snapshot | S3 Bucket |
| Create Elastic IP | Map DNS to Elastic IP | — |

Elastic IP คือ IP สาธารณะที่ไม่เปลี่ยนแม้เครื่องข้างหลังจะเปลี่ยน จึงผูกชื่อ DNS ไว้ได้
</Detail>

### เลือกปลายทาง: cloud native, hybrid หรือ multi-cloud

ระหว่าง POC ต้องเลือกด้วยว่าปลายทางเป็นแบบไหน

- <Term en="Cloud native" th="ออกแบบให้ใช้บริการของคลาวด์โดยตรง" /> — เลือกบริการสำเร็จรูปของคลาวด์ที่เหมาะกับแต่ละงาน แบบที่ KhunLook ใช้ RDS กับ S3
- **Hybrid** — บางส่วนอยู่ใน data center ของตัวเอง บางส่วนอยู่บนคลาวด์ ([Lecture 9.2 ส่วนที่ 2](/2110506-sds/lecture-9-2#ส่วนที่-2--hybrid-cloud-data-center-ของเรากับคลาวด์สาธารณะ))
- **Multi-cloud** — ใช้คลาวด์มากกว่าหนึ่งเจ้า ([Lecture 9.2 ส่วนที่ 1](/2110506-sds/lecture-9-2#ส่วนที่-1--multi-cloud-เมื่อคลาวด์เจ้าเดียวก็ล่มได้))

### ขั้นที่ 3 ย้ายข้อมูล

งานในขั้นนี้มีห้าอย่าง เรียนรู้ที่เก็บข้อมูลแบบต่าง ๆ, วิเคราะห์ฐานข้อมูลและชุดข้อมูลที่มี, สร้างเครื่องมือและสคริปต์สำหรับย้าย, ทยอยอัปโหลดข้อมูลเป็นชุด (batch) และดูแลความปลอดภัยของข้อมูลด้วยการเข้ารหัส

ที่เก็บแต่ละแบบเหมาะกับข้อมูลคนละลักษณะ เลือกผิดก็ช้าหรือแพง

ที่เก็บสองแบบในตารางข้างล่างคือ <Term en="EBS" th="disk ที่ต่อกับ EC2 ผ่านเครือข่าย" /> กับ <Term en="EC2 ephemeral store" th="disk ชั่วคราวที่ติดมากับเครื่อง" /> ข้อมูลบน ephemeral store หายไปพร้อมกับเครื่อง

ทั้งสองอยู่ใน [Lecture 8.2 ส่วนที่ 1](/2110506-sds/lecture-8-2#ส่วนที่-1--ดิสก์ของ-ec2-instance-store-กับ-ebs) ซึ่งเรียก ephemeral store ว่า instance store

<Term en="DynamoDB" th="ฐานข้อมูล NoSQL ของ AWS" /> คือฐานข้อมูลของ AWS ที่เก็บข้อมูลเป็นรายการ key กับค่า

| ที่เก็บ | เหมาะกับ | ไม่เหมาะกับ |
| --- | --- | --- |
| S3 + CloudFront | object ใหญ่ที่เขียนครั้งเดียวอ่านหลายครั้ง, static content | การ query และค้นหา, ใช้แทนฐานข้อมูลหรือ file system |
| EC2 ephemeral store | ข้อมูลชั่วคราวที่หายได้ | log หรือ backup ของฐานข้อมูล, ข้อมูลลูกค้า, shared drive, ข้อมูลอ่อนไหว |
| EBS | disk ถาวรที่อยู่นอกตัวเครื่อง ใช้กับข้อมูลได้ทุกแบบ | static data, web content, ข้อมูล key-value, การกระจายเนื้อหา |
| DynamoDB | ข้อมูลชิ้นเล็กที่ต้อง query ได้ | join ซับซ้อน, transaction, ไฟล์ก้อนใหญ่ (BLOB), ข้อมูลเชิง relational |
| RDS | ข้อมูล relational ที่มีโครงสร้าง | cluster ของฐานข้อมูล, การค้นแบบง่าย ๆ (simple lookups) |

<Term en="CloudFront" th="บริการกระจายสำเนาไฟล์ของ AWS" /> คือบริการของ AWS ที่เก็บสำเนาไฟล์ไว้ในจุดที่ใกล้ผู้ใช้ จับคู่กับ S3 เพื่อแจกไฟล์ให้คนจำนวนมาก

<Detail label="ตัวอย่างการใช้งานของ DynamoDB และ RDS">
| ที่เก็บ | ตัวอย่างที่เหมาะ | ตัวอย่างที่ไม่เหมาะ |
| --- | --- | --- |
| DynamoDB | query, indexing, mapping, tagging, clickstream log, metadata, configuration, catalog | OLTP, DW cube rollups |
| RDS | เว็บแอป, ระบบ transaction ซับซ้อน, ระบบคลังสินค้า, ระบบจัดการคำสั่งซื้อ | clustered DB, simple lookups |

ตัวอย่างของ S3 + CloudFront, ephemeral store และ EBS อยู่ใน [Lecture 8.2](/2110506-sds/lecture-8-2#งานแบบไหนควรอยู่ที่ไหน)
</Detail>

KhunLook เลือกตรงตามตารางนี้ ข้อมูลของแอปอยู่ใน RDS ส่วนไฟล์ backup อยู่ใน S3

### ขั้นที่ 4 ย้ายแอป: forklift หรือ hybrid

ขั้นนี้มีสามงาน

- ตัดสินใจกลยุทธ์ว่าจะ forklift หรือ hybrid
- ทำให้กระบวนการเป็นอัตโนมัติด้วยการสร้าง AMI เครื่องใหม่ทุกเครื่องบูตจาก AMI เดียวกัน ไม่ต้องติดตั้งด้วยมือ
- เขียนชั้นของโค้ดที่รู้จักคลาวด์ (cloud-aware layer) ให้แอปที่ผูกกันแน่น คือโค้ดตัวกลางที่ให้ส่วนที่อยู่ใน data center คุยกับส่วนที่ขึ้นคลาวด์ไปแล้วได้ และทนต่อความหน่วงของอินเทอร์เน็ตที่ขึ้นลง เช่น ส่งงานผ่านคิวแทนการรอคำตอบทันที

<Term en="Forklift migration" th="ยกแอปกับฐานข้อมูลของมันไปทั้งชุด" /> ยกแอปกับฐานข้อมูลของมันไปพร้อมกัน เช่น data center มี Billing Service กับ Billing DB และ Search Service กับ Search DB การ forklift ยกคู่ Billing ไปไว้บน AWS ทั้งคู่ ส่วนคู่ Search อยู่ที่เดิม

ที่ต้องยกไปเป็นคู่เพราะแอปคุยกับฐานข้อมูลของมันบ่อยที่สุด ถ้าแยกกันอยู่คนละฝั่ง ทุก query ต้องวิ่งข้ามเส้นเชื่อมระหว่าง data center กับคลาวด์

<Term en="Hybrid migration" th="ย้ายบางส่วนของแอป ปล่อยบางส่วนไว้ที่เดิม" /> ย้ายแค่บางชิ้น รูปที่ 4 มาจากงานวิจัยของ Hajjat et al. (2010)

<Term en="ACL (Access Control List)" th="รายการกฎว่าใครคุยกับใครได้" /> คือรายการกฎที่ router ใช้ตัดสินว่าใครคุยกับใครได้ และเป็นจุดที่ต้องระวังเมื่อย้ายแบบ hybrid

เดิมกฎที่ปกป้อง back-end อยู่ที่ ACL2 ใน data center หลังย้าย กฎชุดนั้นต้องเขียนใหม่ที่ ACL3 และ ACL4 ให้ยังกันได้เท่าเดิม และ front-end ที่ยังอยู่ใน data center ต้องคุยกับ back-end ข้ามเส้นเชื่อม

### ขั้นที่ 5 ใช้คลาวด์ให้คุ้ม

ย้ายขึ้นไปได้แล้วยังไม่ได้ประโยชน์เต็มที่ ขั้นนี้ทำห้าอย่าง ใช้บริการอื่นของ AWS, ทำ elasticity, ทำวงจรพัฒนาและ deploy บนคลาวด์ให้เป็นอัตโนมัติ (แนวคิด DevOps ใน [Lecture 6](/2110506-sds/lecture-6)), วางเครื่องไว้หลาย Availability Zone ให้ระบบยังใช้งานได้เมื่อส่วนหนึ่งล่ม และเสริม security

#### Elasticity สามแบบ

<Why>
ถ้าจำนวนเครื่องคงที่ ช่วงคนน้อยเครื่องว่างทิ้ง ช่วงคนแห่ระบบล่ม ([Lecture 7 ส่วนที่ 5](/2110506-sds/lecture-7#ส่วนที่-5--cloud-คุ้มเมื่อไหร่))
</Why>

<Term en="Elasticity" th="ขยายและหดทรัพยากรตามโหลด" /> เป็นหลักสำคัญของคลาวด์ ทำได้สามแบบ

| แบบ | เพิ่มเครื่องเมื่อไหร่ | ตัวอย่าง |
| --- | --- | --- |
| Proactive cyclic scaling | ตามรอบเวลาที่แน่นอน | รายวัน รายสัปดาห์ รายเดือน รายไตรมาส |
| Proactive event-based scaling | ก่อนเหตุการณ์ทางธุรกิจที่รู้วันล่วงหน้า | เปิดตัวสินค้าใหม่, แคมเปญการตลาด |
| Auto-scaling based on demand | เมื่อระบบ monitoring เห็นค่าวัดเกินเกณฑ์ | utilization ของเครื่อง, network I/O |

สองแบบแรกเป็น proactive คือเพิ่มเครื่องก่อนโหลดมา เพราะรู้ล่วงหน้าว่ามันจะมา แบบที่สามตอบสนองต่อโหลดที่เกิดขึ้นแล้ว และลดเครื่องลงได้เองเมื่อโหลดลด

#### Region กับ Availability Zone

<Why>
ถ้าเครื่องทั้งหมดของแอปอยู่ในอาคารเดียว ไฟดับที่อาคารนั้นครั้งเดียว แอปหยุดทั้งแอป
</Why>

<Term en="Region" th="ที่ตั้งของกลุ่ม data center" /> คือที่ตั้ง data center เช่น US-East, US-West และ EU ([Lecture 8.1](/2110506-sds/lecture-8#ขนาด-region-และการเข้าถึง))

<Term en="Availability Zone (AZ)" th="ชุดเครื่องที่เป็นอิสระต่อกันใน region เดียว" /> คือชุดเครื่องที่แยกเป็นอิสระต่อกันภายใน region ชื่อของ AZ คือชื่อ region ต่อท้ายด้วยตัวอักษร เช่น us-east-1a ถึง us-east-1d ([Lecture 8.2 ส่วนที่ 1](/2110506-sds/lecture-8-2#ส่วนที่-1--ดิสก์ของ-ec2-instance-store-กับ-ebs))

วางสำเนาของแอปไว้หลาย AZ แล้ว เมื่อ AZ หนึ่งล่ม AZ อื่นยังรับงานต่อได้

#### เสริม security

| เรื่อง | ทำอะไร |
| --- | --- |
| ดูแล credentials | เปลี่ยน access credentials ตามรอบ และเปิด <Term en="MFA" th="ยืนยันตัวตนหลายปัจจัย" /> |
| จำกัดสิทธิ์ | ใช้ IAM และ <Term en="security group" th="กฎ firewall ที่ผูกกับ EC2" /> |
| เข้ารหัส | ขณะเก็บ (at rest) ด้วย AES และขณะส่ง (in transit) ด้วย SSL |
| เตรียมกู้คืน | ทำ EBS snapshot และ RDS backup เป็นรอบ และลองกู้จาก backup เป็นครั้งคราวก่อนถึงวันที่ต้องใช้จริง |

ข้อสุดท้ายสำคัญกว่าที่คิด backup ที่ไม่เคยลองกู้ อาจกู้ไม่ได้ในวันที่ต้องใช้

### ขั้นที่ 6 ปรับให้คุ้มขึ้นเรื่อย ๆ

เมื่อระบบรันไปสักพัก จะเห็นรูปแบบการใช้งานจริง ขั้นนี้เอาข้อมูลนั้นมาปรับ utilization, performance และ efficiency ด้วยสี่งาน

- **จัดการทรัพยากรตามการใช้จริง** — ปิด instance ที่ใช้ไม่เต็ม และซื้อ <Term en="reserved instance" th="instance ที่จองระยะยาวแลกกับราคาถูกลง" />
- **เพิ่ม performance และ efficiency** — ทำ caching หลายระดับ
- **มองเห็นแอปมากขึ้น** — ทำ monitoring และ telemetry ขั้นสูง แล้วสร้าง dashboard ติดตาม <Term en="SLA (Service Level Agreement)" th="ระดับบริการที่สัญญาไว้" /> ของธุรกิจ ([Lecture 7](/2110506-sds/lecture-7#เมื่อไหร่ควรพิจารณา-และต้องดูอะไรก่อนย้าย))
- **อื่น ๆ** — เสริม security, refactor แอปเมื่อจำเป็น และทำตาม best practice ของ AWS

สุดท้ายต้องกำหนดเกณฑ์ความสำเร็จ และ **คลาวด์ไม่ได้มีไว้ประหยัดเงินอย่างเดียว** เกณฑ์ที่ควรวัดมีสิบข้อ

| เกณฑ์ | ความหมาย |
| --- | --- |
| Developer productivity | นักพัฒนาทำงานได้มากขึ้น |
| Business agility | ธุรกิจปรับตัวได้เร็ว |
| Reduced time to market | ออกของใหม่ได้เร็วขึ้น |
| Data center efficiency | ใช้ data center ที่มีอยู่คุ้มขึ้น |
| Redundancy | มีของสำรอง |
| Chargeback and billing | คิดค่าใช้จ่ายกลับไปที่แต่ละหน่วยงานตามที่ใช้จริง |
| Eliminates "heavy lifting" | ตัดงานหนักที่ไม่สร้างความต่าง |
| Foundation of 21st century architectures | เป็นฐานของสถาปัตยกรรมสมัยใหม่ |
| Hardware upgrades | ได้ฮาร์ดแวร์รุ่นใหม่โดยไม่ต้องซื้อเอง |
| Less number of 24/7 personnel | ใช้คนเฝ้าระบบตลอด 24 ชั่วโมงน้อยลง |

กลับไปที่ TCO ของไทยในส่วนที่ 3 ถึงคลาวด์จะแพงกว่า $10k องค์กรก็อาจยังย้าย เพราะเกณฑ์อื่นในตารางนี้

**สองทางขึ้นคลาวด์**

- แอปใหม่ → ออกแบบให้พร้อมสำหรับคลาวด์ · แอปเก่า → ย้ายทันทีถ้าเป็น no-brainer ที่เหลือย้ายทีละระยะ
- แอปบนอินเทอร์เน็ตแบ่งสามชั้น front-end, business logic, back-end มี firewall ด้านหน้าและ load balancer ระหว่างชั้น
- ปรับแอปสามขั้น containerize เปลี่ยนวิธีแพ็ก, microservices เปลี่ยนวิธีแบ่ง (ขยายแต่ละบริการได้อิสระ), serverless เลิกดูแลเครื่อง
- ระบบจริงอย่าง Wongnai มีของเก่า (monolith) กับของใหม่ทำงานด้วยกัน

**หกขั้นของการย้ายแอปเก่า**

1. **Assessment** — TCO/ROI, security และ compliance, dependency tree, จัดกลุ่มตาม compliance, ใครใช้, coupling, licensing แล้ว stack rank เลือกตัวง่ายก่อน
2. **POC** — ระบบย่อส่วน ข้อมูลน้อย เรียน IAM (group → policy, user → credentials → group) และเลือกปลายทาง cloud native, hybrid หรือ multi-cloud
3. **Data migration** — เลือกที่เก็บให้ตรงงาน S3 (ไฟล์เขียนครั้งเดียวอ่านบ่อย), ephemeral (ชั่วคราว), EBS (disk ถาวร), DynamoDB (ข้อมูลเล็กที่ query), RDS (relational)
4. **Application migration** — forklift ยกแอปกับ DB ไปด้วยกัน, hybrid ย้ายบางส่วนและต้องตั้ง ACL ใหม่ทั้งสองฝั่ง
5. **Leverage** — elasticity (cyclic, event-based, auto-scaling), หลาย AZ, security (MFA, IAM, เข้ารหัส, ลองกู้ backup)
6. **Optimization** — ปิดเครื่องที่ใช้ไม่เต็ม, reserved instance, caching, dashboard ของ SLA · คลาวด์ไม่ได้มีไว้ประหยัดเงินอย่างเดียว

**ตัวเลขที่ต้องจำ**

- TCO ไทย คลาวด์แพงกว่ารันเอง ($61.5k กับ $51.5k) สหรัฐฯ คลาวด์ถูกกว่าครึ่ง ($52.5k กับ $112.5k) เพราะเงินเดือนคนดูแลต่างกัน 6.7 เท่า
- Bing แตกงานไป 40 เครื่อง ความเสี่ยงช้าเล็ก ๆ ต่อเครื่องจึงคูณขึ้น ถ้าช้า 1% ต่อเครื่อง (ตัวอย่างเสริม) คำขอราวหนึ่งในสามช้า
